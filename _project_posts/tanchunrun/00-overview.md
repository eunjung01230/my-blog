> **프로젝트 기간** 2026.09.08 ~ 2026.09.21 · 4인 팀 프로젝트

처음 팀 프로젝트를 시작할 때는 솔직히 생각이 단순했다.

디자인을 만들고, 각자 기능을 나눠서 코드를 작성한 다음 마지막에 합치면 프로젝트가 완성되는 줄 알았다.

하지만 실제로 4명이 함께 하나의 서비스를 만들기 시작하니 생각보다 훨씬 많은 것들이 필요했다.

Git 브랜치를 어떻게 나눌지, 다른 사람이 만든 코드를 어떻게 합칠지, 데이터베이스는 어떻게 연결할지, Google과 Kakao 로그인은 어떻게 붙일지, 지도는 어떤 API를 사용할지, Vercel에서는 왜 Preview와 Production이 나뉘는지 등 처음 보는 개념이 계속 나왔다.

코드를 작성하는 것보다

**"이게 지금 왜 안 되는 거지?"**

라는 생각을 했던 시간이 더 길었던 것 같다.

탄천런은 나에게 단순한 팀 프로젝트라기보다, 실제 개발 과정이 어떻게 흘러가는지 처음 제대로 경험해 본 프로젝트였다.

## 탄천런은 어떤 프로젝트인가?

탄천런은 **탄천을 중심으로 러닝 기록을 측정하고, 탄천에서 달린 거리를 기준으로 개인 랭킹을 확인할 수 있는 러닝 서비스**다.

일반적인 러닝 앱처럼 전체 달리기 기록도 저장하지만, 탄천런에서 중요하게 생각한 부분은 따로 있었다.

사용자가 달린 전체 거리 중에서 **탄천으로 지정된 구역 안에서 달린 거리만 따로 계산**하는 것이다.

예를 들어 내가 총 5km를 달렸는데 그중 탄천 구역에서 달린 거리가 3km라면,

- 전체 러닝 거리: 5km
- 탄천 인정 거리: 3km

처럼 기록된다.

그리고 개인 랭킹에는 이 탄천 인정 거리가 사용된다.

즉 단순히 많이 달린 사람을 보여주는 것이 아니라,

**"탄천에서 얼마나 많이 달렸는가?"**

를 기준으로 경쟁하는 서비스다.

주요 대상은 탄천 주변에서 운동을 시작하거나 러닝을 즐기는 사람들이었다.

너무 많은 기능을 넣기보다는 처음 사용하는 사람도 쉽게 시작할 수 있는 러닝 앱을 만드는 것을 목표로 했다.

## 처음에는 기능이 훨씬 많았다

처음 기획할 때는 넣고 싶은 기능이 정말 많았다.

러닝 앱이라고 생각하니 자연스럽게 목표 설정, 친구, 크루, 피드, 댓글, 전국 랭킹, 여러 종류의 랭킹, 경로 공유 같은 기능까지 생각하게 됐다.

하지만 팀 프로젝트 기간이 길지 않았고, 네 명이서 모든 기능을 구현하는 것은 현실적으로 어려웠다.

그래서 계속 기능을 줄였다.

프로젝트에서 가장 중요한 기능이 무엇인지 다시 생각했고,

**"탄천에서 달린 거리를 측정하고 기록해서 개인 랭킹을 만든다."**

라는 핵심에 집중하기로 했다.

최종적으로 사용 흐름도 최대한 단순하게 만들었다.

사용자는 로그인을 하고 닉네임을 설정한 뒤 러닝을 시작한다.

러닝을 시작하면 GPS를 이용해 이동 거리를 측정하고, 전체 거리와 탄천 인정 거리를 계산한다.

러닝을 끝내면 결과 화면에서

- 전체 거리
- 탄천 인정 거리
- 러닝 시간
- 페이스
- 누적 거리
- 랭킹

등을 확인할 수 있도록 했다.

그리고 자신의 이전 러닝 기록도 다시 볼 수 있도록 구성했다.

이 과정을 거치면서 처음 알게 된 것이 있다.

**기능이 많다고 좋은 서비스가 되는 것은 아니었다.**

특히 기간이 정해진 프로젝트에서는 구현할 수 있는 범위를 정하는 것도 개발 과정의 중요한 부분이었다.

## 4명이 함께 만든 첫 번째 제대로 된 협업 프로젝트

탄천런은 4명이 함께 진행한 팀 프로젝트였다.

이전에는 Git을 사용하더라도 내가 만든 코드를 저장하거나 GitHub에 올리는 정도로 생각했다.

하지만 여러 명이 동시에 하나의 프로젝트를 수정하기 시작하니 완전히 달랐다.

한 사람이 작업하는 동안 다른 사람도 같은 프로젝트를 수정하고 있었다.

그래서 각자 맡은 기능마다 Issue를 만들고, 별도의 Branch에서 작업한 뒤 Pull Request를 이용해 코드를 합치는 방식을 사용했다.

처음에는

`branch → commit → push → PR`

정도의 순서만 알고 있었다.

하지만 실제로 작업하다 보니 훨씬 많은 상황이 생겼다.

내가 작업을 시작하기 전에 최신 코드를 받아야 했고, 다른 사람이 먼저 수정한 파일과 내가 수정한 파일이 겹칠 수도 있었다.

이미 만든 Pull Request를 수정해야 하는 상황도 있었고, `main`, `develop`, `origin/main` 같은 이름이 각각 무엇을 의미하는지도 처음에는 헷갈렸다.

Git 명령어 자체보다

**왜 이런 작업 순서가 필요한지를 이해하는 데 시간이 더 오래 걸렸다.**

하지만 여러 번 Branch를 만들고, Commit하고, Push하고, Pull Request를 만들면서 조금씩 흐름이 보이기 시작했다.

## 디자인도 생각보다 단순하지 않았다

프로젝트 초반에는 Figma를 이용해 화면을 설계했다.

처음에는 디자인을 한 번 만들면 그대로 개발하면 된다고 생각했다.

하지만 실제로는 디자인도 계속 수정됐다.

화면을 직접 만들어 보니 글이 너무 많기도 했고, 버튼이 작거나 사용자 입장에서 흐름이 자연스럽지 않은 부분도 있었다.

또 하나 어려웠던 점은 **기획 문서와 디자인을 맞추는 것**이었다.

기획 문서에는 없는 기능이 디자인에 들어가기도 하고, 반대로 기획에는 있는데 화면에서는 표현되지 않은 기능도 있었다.

AI 디자인 도구인 Claude Design도 사용했는데 여기서 또 다른 문제가 생겼다.

처음에는 디자인 이미지와 설명을 주면 Claude가 알아서 내가 원하는 방향을 이해할 것이라고 생각했다.

하지만 실제로는 그렇지 않았다.

예를 들어

"이 부분만 수정해줘."

라고 요청했는데 다른 부분까지 함께 변경되는 경우도 있었다.

그래서 점점 프롬프트도 구체적으로 작성하게 됐다.

- 기존 화면 구조는 유지할 것
- 이 부분만 수정할 것
- 새로운 기능은 추가하지 말 것
- 기획 문서에 없는 기능은 만들지 말 것
- 기존 디자인에서 바꾸면 안 되는 부분은 건드리지 말 것

이런 조건을 하나씩 명확하게 적기 시작했다.

이 경험을 통해 AI에게 작업을 맡길 때도 사람이 **어디까지 바꿔도 되고 어디부터는 바꾸면 안 되는지** 정확하게 알고 있어야 한다는 것을 배웠다.

## 화면이 만들어졌다고 서비스가 완성된 것은 아니었다

디자인이 어느 정도 만들어지고 화면도 구현되기 시작했을 때는 프로젝트가 거의 완성된 것처럼 느껴졌다.

하지만 사실 그때부터가 시작이었다.

버튼을 눌렀을 때 실제 데이터가 저장되어야 했고, 로그인한 사용자를 구분해야 했으며, 러닝 기록도 데이터베이스에 저장해야 했다.

처음에는 데이터베이스 구조를 코드로 작성하면 바로 데이터가 저장되는 줄 알았다.

하지만 실제로는 단계가 나뉘어 있었다.

데이터베이스의 구조를 설계하는 것과 실제 PostgreSQL 데이터베이스에 그 구조를 적용하는 것도 달랐고, 데이터베이스가 만들어졌다고 해서 화면에서 바로 데이터를 사용할 수 있는 것도 아니었다.

화면과 서버를 연결하고, 서버와 데이터베이스를 연결하는 과정이 따로 필요했다.

여기서부터

- PostgreSQL
- Drizzle
- Migration
- Schema
- API
- Server
- Database

같은 단어가 계속 등장했다.

처음에는 하나같이 비슷하게 느껴졌다.

그래서 개발을 진행하면서 새로운 기능을 구현하는 것과 동시에 **처음 보는 개발 용어가 정확히 무엇을 의미하는지 하나씩 이해하는 과정**도 필요했다.

## 배포하면 끝인 줄 알았는데 Vercel에도 환경이 있었다

탄천런은 Vercel을 이용해 배포했다.

처음 Vercel을 사용할 때는 GitHub 프로젝트를 연결하고 Deploy 버튼을 누르면 끝이라고 생각했다.

하지만 팀 프로젝트에서는 `develop`과 `main`을 나눠 사용했다.

`develop`은 팀에서 기능을 합치고 테스트하는 용도로 사용하고,

`main`은 실제 사용자에게 보여줄 최종 버전으로 사용했다.

그러다 보니 Vercel에서도

- Preview
- Production

이라는 환경을 만나게 됐다.

처음에는 이 두 개가 왜 나뉘어 있는지도 정확히 이해하지 못했다.

특히 Google 로그인, Kakao 로그인, 지도 API 같은 외부 서비스를 연결하기 시작하면서 더 복잡해졌다.

환경변수가 Preview와 Production에 각각 보이고, Client ID와 Secret 같은 값도 여러 개 생기다 보니

**"이 키를 환경마다 새로 만들어야 하는 건가?"**

라는 생각도 했다.

개발하면서 가장 많이 헷갈렸던 부분 중 하나였다.

결국 Git의 Branch, Vercel의 배포 환경, 환경변수, 외부 API 설정은 서로 관련되어 있지만 전부 같은 것은 아니라는 것을 조금씩 이해하게 됐다.

## 소셜 로그인도 버튼 하나 만드는 것이 아니었다

Google이나 Kakao 로그인 버튼은 정말 익숙하다.

그래서 개발하기 전에는 로그인 버튼을 만들고 API를 연결하면 간단하게 끝나는 기능이라고 생각했다.

직접 구현 과정을 보니 전혀 아니었다.

Google과 Kakao 개발자 페이지에서 애플리케이션을 만들고, Client ID나 Secret 같은 값을 발급받아야 했다.

그리고 로그인 후 다시 우리 서비스로 돌아올 주소도 설정해야 했다.

localhost에서 테스트하는 주소와 실제 배포된 주소도 달랐다.

여기서 Redirect URI, Callback, OAuth, Provider 같은 처음 보는 단어들이 계속 나왔다.

더 중요한 것은

**소셜 로그인이 성공하는 것과 우리 서비스의 사용자 데이터가 저장되는 것은 또 다른 문제**라는 점이었다.

Google 로그인이 성공했다고 해서 자동으로 우리 데이터베이스에 사용자가 원하는 형태로 저장되는 것은 아니었다.

로그인한 사람이 누구인지 저장하고, 로그인 상태를 관리하고, 이후 그 사용자의 러닝 기록과 연결할 수 있는 구조가 필요했다.

단순하게 보였던 로그인 기능 하나 안에도 생각보다 많은 과정이 들어 있었다.

## 지도 API도 직접 연결해 보기 전에는 몰랐다

러닝 서비스이기 때문에 지도와 위치 정보도 중요했다.

사용자의 현재 위치를 표시하고, 탄천 구역인지 판단하고, 이동한 거리도 계산해야 했다.

처음에는 지도 API도 그냥 지도 하나를 화면에 띄우는 기능이라고 생각했다.

하지만 실제로 사용하려면 외부 서비스에서 애플리케이션을 등록하고 키를 발급받아야 했다.

개발 환경과 배포 환경의 주소도 설정해야 했고, 어떤 지도 서비스를 사용할지도 결정해야 했다.

지도 화면을 만드는 것과 GPS 데이터를 실제 러닝 기록에 연결하는 것도 다른 문제였다.

프로젝트를 진행하면서

**화면에 지도가 보이는 것과 실제 러닝 기능이 동작하는 것은 완전히 다른 단계**

라는 것도 알게 됐다.

## Claude Code를 사용하면 모든 것이 쉬울 줄 알았다

이번 프로젝트에서는 Claude Code도 많이 사용했다.

처음에는 AI가 코드를 작성해 주기 때문에 개발 속도가 굉장히 빨라질 것이라고 생각했다.

실제로 코드 자체를 만드는 속도는 빨랐다.

하지만 또 다른 어려움이 생겼다.

AI가 현재 프로젝트 상황을 정확하게 이해하지 못하면 내가 원하지 않는 방향으로 수정할 수도 있었다.

예를 들어 나는 코드만 확인하고 싶었는데 파일을 수정할 수도 있고, 기존 Pull Request를 수정해야 하는데 새로운 PR을 만들 수도 있다.

그래서 Claude에게 작업을 요청할 때도 점점 조건이 많아졌다.

먼저 현재 Git 상태를 확인하고,

최신 Branch를 확인하고,

Issue 내용을 읽고,

수정하면 안 되는 파일을 지정하고,

어디까지 작업할 것인지 알려주고,

Commit이나 Push를 해도 되는지도 따로 알려줘야 했다.

결국 AI를 잘 사용하기 위해서도 내가 프로젝트 구조를 이해해야 했다.

이게 이번 프로젝트에서 가장 크게 느낀 부분 중 하나였다.

**AI가 개발자를 대신해서 모든 판단을 해주는 것이 아니라, 내가 정확하게 판단할 수 있어야 AI에게도 정확한 일을 시킬 수 있었다.**

## 앞으로의 기록

이 글에서는 탄천런 프로젝트의 전체 과정을 간단하게 정리했다.

하지만 실제 프로젝트를 진행하면서는 훨씬 많은 시행착오가 있었다.

그래서 이후 글에서는 각각의 경험을 따로 정리해 보려고 한다.

- 기획과 디자인을 어떻게 정리했는지
- Figma에서 Claude Design으로 디자인을 넘기면서 무엇이 어려웠는지
- 4명이 Git과 GitHub를 이용해 어떻게 협업했는지
- Branch, Pull Request, Merge가 왜 필요한지
- 데이터베이스 구조와 실제 데이터 연결은 무엇이 달랐는지
- Vercel의 Preview와 Production은 무엇인지
- 지도 API와 Google·Kakao 소셜 로그인은 어떻게 연결했는지
- Claude Code와 Claude Design을 사용하면서 프롬프트를 어떻게 바꾸게 됐는지
- 프로젝트를 끝내고 나서 어떤 부분이 가장 아쉬웠는지

프로젝트를 하면서 가장 어려웠던 점, 배운 점, 잘한 점과 아쉬운 점은 [프로젝트 최종 회고]({{ site.baseurl }}{% link _project_posts/tanchunrun/09-final-retrospective.md %})에서 따로 정리했다.

처음 개발을 공부할 때는 완성된 코드나 정답만 보면 이해가 잘되지 않는 경우가 많았다.

나도 이번 프로젝트에서 계속 헷갈렸기 때문에, 이후 글에서는 결과만 적기보다

**내가 처음에 무엇을 잘못 이해했고, 왜 문제가 생겼고, 어떻게 이해하게 됐는지**

를 최대한 쉽게 남겨보려고 한다.

탄천런은 완벽하게 모든 것을 알고 시작한 프로젝트가 아니었다.

오히려 모르는 것이 많은 상태에서 직접 부딪히면서 하나씩 배운 프로젝트였다.

그래서 나에게는 결과물 자체만큼이나 그 과정이 많이 남은 프로젝트다.
