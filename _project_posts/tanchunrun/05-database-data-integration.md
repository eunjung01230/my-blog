탄천런에서 가장 오래 헷갈렸던 부분 중 하나가 데이터베이스였다.

프로젝트를 시작하기 전에는 데이터베이스를 비교적 단순하게 생각했다.

> 사용자 정보를 저장한다.
> 러닝 기록을 저장한다.
> 랭킹에 필요한 거리를 저장한다.

이렇게 필요한 데이터를 정하고 테이블을 만들면 끝이라고 생각했다.

그런데 실제 개발을 시작하니 전혀 아니었다.

데이터베이스 구조를 코드로 작성했는데도 실제 데이터베이스에는 아무것도 없을 수 있었고,

데이터베이스에 테이블이 있어도 화면에서 바로 사용할 수 있는 것은 아니었다.

처음에는

**"DB 구조를 만들었는데 왜 데이터가 안 들어가지?"**

라는 부분이 가장 이해되지 않았다.

프로젝트를 진행하면서 조금씩 알게 된 것은

**데이터베이스 설계, 실제 데이터베이스 생성, 서버 연결, 화면에서의 사용은 모두 다른 단계**라는 것이었다.

---

## 처음에는 "DB 구조를 만들었다 = 데이터베이스를 만들었다"라고 생각했다

탄천런에서 사용자와 러닝 기록을 저장하기 위해 데이터 구조를 먼저 정리했다.

예를 들어 아주 단순하게 보면 사용자 정보에는 이런 데이터가 필요하다.

* 사용자 ID
* 닉네임
* 로그인 정보
* 생성 시간

러닝 기록에는 이런 데이터가 필요하다.

* 어떤 사용자의 기록인지
* 전체 러닝 거리
* 탄천 인정 거리
* 러닝 시간
* 페이스
* 시작 시간
* 종료 시간

이런 내용을 기준으로 데이터베이스 구조를 설계했다.

코드에도 테이블 구조가 작성되기 시작했다.

그때는 코드에 테이블이 정의되어 있으니 실제 데이터베이스도 이미 만들어진 것처럼 느껴졌다.

하지만 아니었다.

**코드에 데이터 구조를 적는 것과 실제 PostgreSQL에 테이블이 만들어지는 것은 다른 일이었다.**

이 차이를 이해하는 데 시간이 꽤 걸렸다.

---

## Schema는 실제 데이터가 아니라 "구조 설명서"에 가까웠다

프로젝트에서 계속 등장했던 단어가 `Schema`였다.

처음에는 Schema가 데이터베이스 그 자체인 줄 알았다.

하지만 내가 이해한 방식으로 쉽게 말하면 Schema는

**"우리 데이터베이스를 이런 모양으로 만들 것이다."**

라고 코드로 정의한 구조에 가까웠다.

예를 들어 사용자 테이블을 이렇게 만들겠다고 정했다고 생각해보자.

| 컬럼         | 의미          |
| ---------- | ----------- |
| id         | 사용자를 구분하는 값 |
| nickname   | 사용자 닉네임     |
| created_at | 가입 시간       |

이 구조를 코드로 작성했다고 해서 PostgreSQL 안에 테이블이 바로 생기는 것은 아니다.

Schema는 우선

> users라는 테이블이 필요하고,
> 그 안에는 이런 컬럼이 있어야 한다.

라고 정의한 상태다.

즉 나는 점점 이렇게 구분하게 됐다.

```text
Schema
= 데이터베이스를 어떤 구조로 만들지 정의한 코드

실제 Database
= 그 구조가 실제로 적용되어 데이터가 저장되는 공간
```

이 둘을 처음에는 같은 것으로 생각해서 많이 헷갈렸다.

---

## 그러면 Migration은 왜 필요한가?

Schema 다음으로 계속 등장했던 단어가 `Migration`이었다.

처음에는 또 새로운 어려운 용어가 나온 것처럼 느껴졌다.

하지만 Schema와 연결해서 생각하니 조금 쉬웠다.

Schema에서

> 이런 테이블을 만들고 싶다.

라고 정의했다면,

Migration은 그 변경사항을 **실제 데이터베이스에 적용하기 위한 과정**이라고 이해했다.

예를 들어 처음에는 사용자 테이블이

```text
id
nickname
```

두 개의 컬럼만 있었다고 해보자.

나중에

```text
created_at
```

을 추가했다면 코드의 Schema는 바뀐다.

하지만 이미 만들어져 있는 실제 데이터베이스도 같이 바뀌어야 한다.

이때 Migration을 이용해 실제 DB 구조를 변경한다.

내가 이해한 흐름은 대략 이랬다.

```text
Schema 작성
↓
Migration 생성
↓
실제 PostgreSQL에 Migration 적용
↓
실제 테이블 구조 변경
```

이 흐름을 알고 나서야

**"Schema를 수정했는데 왜 실제 DB에는 반영되지 않았지?"**

라는 질문이 이해되기 시작했다.

---

## 코드가 있다고 데이터가 자동으로 저장되는 것도 아니었다

여기서 또 하나 착각했던 부분이 있었다.

테이블 구조가 실제 데이터베이스에 만들어지면 이제 화면에서 입력한 데이터가 자동으로 저장될 것 같았다.

하지만 이것도 아니었다.

예를 들어 사용자가 러닝을 종료했다.

화면에는 이런 값이 있다.

```text
전체 거리: 5km
탄천 인정 거리: 3km
러닝 시간: 32분
```

이 값이 화면에 보인다고 해서 PostgreSQL에 자동으로 저장되는 것은 아니다.

화면에서 가지고 있는 값을 서버로 보내야 하고,

서버에서는 그 값을 확인한 뒤 데이터베이스에 저장해야 한다.

아주 단순하게 보면 이런 흐름이다.

```text
사용자 화면
↓
서버
↓
데이터베이스
```

반대로 이전 러닝 기록을 화면에 보여주려면 반대 방향으로 움직인다.

```text
데이터베이스
↓
서버
↓
사용자 화면
```

이 구조를 이해하면서 데이터 연동이 조금씩 보이기 시작했다.

---

## 화면에 보이는 데이터와 DB 데이터는 같은 것이 아니었다

개발 초반에는 화면에서 값이 보이면 실제 데이터도 있는 것처럼 느껴졌다.

하지만 프론트엔드에서는 테스트를 위해 임시 데이터를 넣을 수도 있다.

예를 들어 화면에

```text
닉네임: 탄천러너
누적 거리: 25km
랭킹: 3위
```

가 보인다고 해도 이 값이 실제 데이터베이스에서 가져온 값이라는 보장은 없다.

코드 안에 직접 적어놓은 테스트 값일 수도 있다.

이런 값을 흔히 Mock 데이터라고 부르기도 한다.

그래서 프로젝트를 진행하면서

**"화면이 만들어져 있다"와 "데이터가 연동되어 있다"를 구분해야 했다.**

처음에는 디자인 화면까지 나오면 기능도 상당히 완성된 것처럼 느껴졌다.

하지만 실제 서비스에서는

* 값을 DB에서 가져오는가?
* 로그인한 사용자에 맞는 데이터인가?
* 수정하면 DB에도 바뀌는가?
* 새로고침해도 값이 남아 있는가?

같은 것을 확인해야 했다.

---

## 데이터 연동은 여러 층이 연결되는 일이었다

처음에는 데이터 연동을

> DB 연결하기

한 문장으로 생각했다.

하지만 실제로는 여러 단계가 있었다.

내 기준에서는 이렇게 정리되었다.

| 단계         | 역할                            |
| ---------- | ----------------------------- |
| 화면         | 사용자가 데이터를 보고 입력하는 곳           |
| 서버         | 요청을 받고 데이터를 처리하는 곳            |
| ORM        | 서버 코드와 DB 사이에서 쿼리 작성을 도와주는 도구 |
| PostgreSQL | 실제 데이터를 저장하는 데이터베이스           |

탄천런에서는 PostgreSQL을 사용했고, 코드에서는 Drizzle을 이용해 데이터베이스 구조와 접근을 관리했다.

처음에는 Drizzle도 데이터베이스 종류인 줄 헷갈릴 수 있었다.

하지만 Drizzle은 PostgreSQL 자체가 아니었다.

쉽게 생각하면

**PostgreSQL은 실제 데이터 저장소이고, Drizzle은 코드에서 PostgreSQL을 다루기 쉽게 도와주는 도구**

라고 이해했다.

---

## ORM이라는 단어도 처음에는 어려웠다

Drizzle을 사용하면서 ORM이라는 말을 자주 보게 됐다.

처음에는 또 외워야 하는 용어처럼 느껴졌다.

내가 이해한 수준에서 간단하게 생각하면 ORM은

**코드와 데이터베이스 사이에서 데이터를 다루기 쉽게 도와주는 도구**

였다.

데이터베이스에서는 SQL이라는 언어를 이용해 데이터를 조회하거나 저장할 수 있다.

예를 들면

```text
사용자 데이터 조회
러닝 기록 추가
특정 기록 수정
기록 삭제
```

같은 일을 한다.

Drizzle 같은 ORM을 사용하면 이 작업을 애플리케이션 코드 안에서 조금 더 구조적으로 작성할 수 있었다.

중요한 것은 ORM이 데이터베이스를 대신하는 것이 아니라는 점이었다.

```text
애플리케이션 코드
↓
Drizzle
↓
PostgreSQL
```

이런 관계라고 생각하니 훨씬 이해하기 쉬웠다.

---

## 로컬 DB와 배포 DB가 왜 따로 있는지도 헷갈렸다

탄천런에서는 데이터베이스를 다루면서 또 하나 헷갈린 부분이 있었다.

**왜 데이터베이스가 하나가 아닌가?**

였다.

개발 과정에서는 로컬에서 Docker로 띄운 PostgreSQL 17을 사용하고,

통합 환경과 배포 환경에서는 Neon PostgreSQL을 사용하는 구조였다.

그리고 통합과 배포는 같은 Neon 안에서 서로 다른 프로젝트로 나눠져 있었다.

처음에는

> 어차피 PostgreSQL인데 그냥 하나만 쓰면 되는 것 아닌가?

라고 생각했다.

하지만 개발 중 실수로 데이터를 지우거나 테이블 구조를 계속 바꾸는 작업을 실제 사용자 환경에서 하면 위험하다.

그래서 개발용과 실제 서비스용 환경을 나누는 것이 필요했다.

내가 이해한 방식은 이랬다.

```text
로컬 개발 (Docker PostgreSQL 17)
= 개발하면서 마음껏 테스트하는 공간

통합 (Neon PostgreSQL)
= develop 을 합쳐 Preview 에서 확인하는 데이터베이스

배포 (Neon PostgreSQL)
= main 이 Production 에서 사용하는 데이터베이스
```

배포 기준으로 보면 `develop`이 Preview, `main`이 Production으로 연결되고, 각 환경이 바라보는 데이터베이스도 이렇게 나뉘어 있었다.

이 부분은 이후 Vercel 환경을 이해할 때도 연결됐다.

하지만 배포 환경 자체는 다음 글에서 따로 정리하려고 한다.

---

## Neon도 새로운 종류의 데이터베이스라고 생각했다

처음 Neon이라는 이름을 들었을 때는 MySQL이나 PostgreSQL처럼 새로운 데이터베이스 종류인 줄 알았다.

하지만 Neon은 PostgreSQL 기반의 데이터베이스를 클라우드에서 사용할 수 있게 해주는 서비스였다.

즉 비교하면

```text
PostgreSQL
= 데이터베이스 종류

Neon
= PostgreSQL을 클라우드에서 제공하는 서비스
```

였다.

이 차이를 이해하고 나니

> PostgreSQL을 쓴다면서 왜 Neon도 쓰지?

라는 혼란이 사라졌다.

둘 중 하나를 선택하는 관계가 아니라 **Neon에서 PostgreSQL을 사용할 수 있는 것**이었다.

---

## "DB가 연결됐다"는 말도 여러 뜻이 있었다

프로젝트를 진행하면서

> DB 연결됐어요.

라는 말도 생각보다 애매하다는 것을 알게 됐다.

무엇을 기준으로 연결됐다고 말하는지가 다를 수 있기 때문이다.

예를 들어

1. 환경변수에 DB 주소만 들어간 상태
2. 서버에서 DB 접속에 성공한 상태
3. Migration까지 적용된 상태
4. 데이터를 실제로 저장할 수 있는 상태
5. 화면에서 저장하고 다시 조회할 수 있는 상태

는 모두 다르다.

처음에는 1번만 되어도 거의 연결이 끝난 것처럼 느껴졌다.

하지만 실제 기능에서 필요한 것은 마지막 단계까지였다.

그래서 이후에는 단순히

**"DB 연결 완료"**

라고 하기보다

> DB 접속 확인

> Migration 적용 확인

> 데이터 저장 확인

> 조회 확인

처럼 조금 더 구체적으로 상태를 보는 것이 좋다고 느꼈다.

---

## 실제 PostgreSQL에 붙이지 않고 계속 검증만 하던 시기가 있었다

탄천런에서 데이터베이스 관련 작업을 하면서 꽤 오래 막혔던 부분이다.

Schema와 서버 코드를 계속 검토하고 있었는데 실제 PostgreSQL 환경에서 끝까지 검증하지 못한 상태가 이어졌다.

코드를 보면 구조적으로 맞는지 확인할 수 있다.

빌드가 되는지도 확인할 수 있다.

하지만 실제 데이터베이스에 연결하지 않으면

**정말 Migration이 적용되는지, 실제 저장과 조회가 되는지**

까지는 확실하게 알 수 없었다.

그러다 보니 계속

> 이 구조가 맞는지 다시 확인해보자.

> 이 부분도 검증해야 한다.

라는 작업이 반복됐다.

처음에는 검증을 많이 할수록 더 안전하다고 생각했다.

그런데 프로젝트 기간은 계속 줄어들고 있었고 실제 기능 구현은 앞으로 나가지 못했다.

이때 처음으로

**검증을 완벽하게 하는 것과 프로젝트를 진행시키는 것 사이에도 균형이 필요하다**

는 것을 느꼈다.

---

## 모든 것을 완벽하게 확정한 다음 개발하려니 진행이 멈췄다

처음에는 데이터베이스 구조를 완벽하게 확정해야 다음 기능으로 넘어갈 수 있다고 생각했다.

물론 DB 구조는 중요하다.

나중에 크게 변경하면 여러 코드에 영향을 줄 수 있기 때문이다.

하지만 완벽한 구조를 만들려고 계속 검토하다 보면 실제 사용해 보면서 발견할 수 있는 문제를 영원히 만나지 못한다.

그래서 당시에는 현재까지 확인한 구조를 일단 기준으로 두고 다음 구현을 진행하는 방향도 사용했다.

즉

> 현재 구조를 임시 기준으로 사용하고,
> 실제 통합 과정에서 문제가 나오면 다시 수정한다.

는 방식이었다.

처음에는 이렇게 진행하는 것이 불안하게 느껴졌다.

하지만 팀 프로젝트에서는 **완벽하게 확정되지 않았더라도 다음 단계가 진행될 수 있도록 임시 기준을 만드는 것**도 필요했다.

---

## `server-only` 때문에 예상하지 못한 문제가 생겼다

데이터베이스 관련 코드에서는 보안과 실행 위치도 중요했다.

DB에 직접 접근하는 코드는 브라우저에서 실행되면 안 된다.

그래서 서버에서만 사용하도록 제한하는 `server-only` 개념을 사용했다.

처음에는

> DB 관련 파일이면 전부 server-only로 막으면 더 안전하겠지.

라고 생각하기 쉬웠다.

그런데 문제가 생겼다.

Drizzle은 Migration 같은 작업을 위해 CLI에서도 Schema 파일을 읽어야 했다.

그런데 우리 프로젝트에서는 서버 전용 폴더에 있는 파일이 전부 `server-only`를 import 하도록 정해 두었고, Schema 파일도 그 폴더 안에 있었다.

문제는 Drizzle CLI가 Next 밖에서 따로 실행되는 도구라는 점이었다.

Next 안에서 실행될 때는 `server-only`가 정상적으로 처리되지만, Drizzle CLI는 Next의 처리 방식을 모른다.

그래서 CLI가 Schema 파일을 읽다가 `server-only` 모듈을 찾지 못하고 그대로 실패했다.

해결은 Drizzle 설정 파일 안에서만 `server-only`를 Next가 이미 가지고 있는 빈 모듈로 연결해 주는 방식이었다.

설정 파일에서만 처리했기 때문에 실제 앱 동작은 그대로다.

Next에서의 `server-only` 보호도 그대로 남아서, 클라이언트 코드가 서버 파일을 import 하면 여전히 빌드가 실패한다.

즉 같은 DB 관련 파일이어도 역할이 달랐다.

```text
DB 연결 / 실제 쿼리 실행 코드
→ 서버에서만 사용해야 함

Schema
→ 서버 코드뿐 아니라 Drizzle CLI도 읽어야 함
```

처음에는 둘 다 DB 관련 코드니까 똑같이 다루면 된다고 생각했다.

하지만 실제로는 **실행되는 코드와 도구가 읽어야 하는 설정용 코드의 역할이 다르다**는 것을 알게 됐다.

---

## server-only 문제에서 배운 것

이 문제를 겪으면서 보안 설정도 무조건 많이 넣는다고 좋은 것은 아니라는 것을 알게 됐다.

중요한 것은

**이 파일을 누가 사용하는가?**

였다.

브라우저에서 절대 실행되면 안 되는 DB 접근 코드는 서버 전용으로 보호하는 것이 맞다.

하지만 Schema처럼 Migration 도구도 읽어야 하는 파일은 다른 방식으로 관리할 필요가 있었다.

처음에는 단순히

> DB 관련 = 전부 server-only

라고 생각했다.

나중에는

> 실제 DB에 접근하는 코드인가?
> 아니면 DB 구조만 정의하는 파일인가?

를 구분해서 보게 됐다.

---

## 데이터가 저장될 때 사용자와 어떻게 연결되는지도 중요했다

탄천런은 로그인한 사용자의 러닝 기록을 저장해야 한다.

그렇다면 단순히 러닝 기록만 저장해서는 부족하다.

이 기록이 **누구의 기록인지**도 알아야 한다.

예를 들어 러닝 기록에

```text
거리: 5km
시간: 32분
```

만 저장되어 있다면 이 기록이 어떤 사용자의 것인지 알 수 없다.

그래서 사용자와 러닝 기록 사이의 관계가 필요했다.

아주 단순하게 보면

```text
사용자
↓
러닝 기록 1
러닝 기록 2
러닝 기록 3
```

같은 관계가 된다.

이런 관계를 만들면서 왜 데이터베이스에서 ID를 중요하게 사용하는지도 조금씩 이해하게 됐다.

닉네임은 사용자가 바꿀 수도 있지만 ID는 시스템 안에서 사용자를 안정적으로 구분하는 값으로 사용할 수 있기 때문이다.

---

## 랭킹도 단순히 화면에서 계산하는 것이 아니었다

탄천런의 핵심 기능 중 하나는 탄천 인정 거리 기준의 개인 랭킹이었다.

처음에는 각 사용자의 화면에서 거리를 계산하고 정렬하면 되는 것처럼 느껴졌다.

하지만 실제로 여러 사용자의 랭킹을 만들려면 서버가 여러 사용자의 데이터를 조회해야 한다.

예를 들면

```text
A 사용자: 탄천 누적 30km
B 사용자: 탄천 누적 45km
C 사용자: 탄천 누적 18km
```

라는 데이터가 있다면

```text
1위 B - 45km
2위 A - 30km
3위 C - 18km
```

처럼 정렬해서 결과를 보내줘야 한다.

즉 랭킹 화면도 결국 데이터베이스에 저장된 기록과 연결되어 있었다.

디자인에서는 단순한 숫자 목록처럼 보이지만 그 뒤에서는 여러 사용자의 기록을 모아 계산해야 했다.

이런 부분을 보면서 **화면 하나 뒤에도 필요한 데이터 구조가 있다는 것**을 알게 됐다.

---

## 데이터 연동을 확인할 때는 CRUD라는 개념도 알게 됐다

데이터베이스 기능을 만들다 보면 CRUD라는 단어를 자주 보게 된다.

처음에는 무슨 특별한 기술 이름인 줄 알았다.

하지만 각각 데이터의 기본 동작을 의미했다.

| 구분     | 의미         |
| ------ | ---------- |
| Create | 새로운 데이터 저장 |
| Read   | 저장된 데이터 조회 |
| Update | 기존 데이터 수정  |
| Delete | 데이터 삭제     |

러닝 기록을 예로 들면

```text
러닝 종료 후 기록 저장
→ Create

내 기록 목록 보기
→ Read

기록 정보 수정
→ Update

기록 삭제
→ Delete
```

처럼 연결해서 생각할 수 있었다.

이렇게 실제 기능과 연결하니 용어가 훨씬 이해하기 쉬웠다.

---

## 데이터베이스 문제인지 화면 문제인지 구분하는 것도 어려웠다

기능이 동작하지 않을 때 처음에는 그냥

> 데이터가 안 나와요.

라고 생각했다.

하지만 원인은 여러 곳에 있을 수 있었다.

예를 들어 기록 목록이 화면에 안 보인다면

* 데이터가 실제 DB에 저장되지 않은 것인지
* 서버가 조회하지 못한 것인지
* 서버에서는 정상 조회했는데 화면으로 전달되지 않은 것인지
* 화면이 받은 데이터를 잘못 표시하고 있는 것인지

확인해야 했다.

그래서 점점 데이터 흐름을 단계별로 보는 것이 중요하다는 것을 알게 됐다.

```text
DB에 데이터가 있는가?
↓
서버에서 조회되는가?
↓
API 또는 서버 로직에서 값이 전달되는가?
↓
화면에서 값을 받는가?
↓
화면에 정상적으로 표시되는가?
```

한 번에

**"왜 안 되지?"**

라고 보는 것보다 어느 단계까지 정상인지 확인하면 문제를 찾기가 훨씬 쉬웠다.

---

## 개발자 콘솔에 값이 보이는 것과 DB 저장도 달랐다

개발 중에는 `console.log()`를 이용해 값을 확인하기도 한다.

예를 들어 인증번호나 서버에서 받은 값을 콘솔에 출력해서 테스트할 수 있다.

처음에는 콘솔에 값이 보이면 기능이 어느 정도 연결된 것처럼 느껴질 수 있다.

하지만 콘솔에 출력되는 것과 실제 DB에 저장되는 것은 전혀 다르다.

```text
console.log()
= 현재 코드에서 값이 만들어졌는지 눈으로 확인

DB 저장
= 그 값을 실제 데이터베이스에 영구적으로 기록
```

브라우저를 새로고침하거나 서버를 다시 실행했을 때도 데이터가 남아 있어야 실제 DB 저장이라고 볼 수 있다.

이 차이도 프로젝트를 진행하면서 계속 확인하게 됐다.

---

## 실제 데이터 연동을 이해하고 나니 화면을 보는 방식도 달라졌다

이전에는 화면을 보면 디자인부터 봤다.

버튼이 어디에 있고,

텍스트가 어떻게 보이고,

페이지가 어떻게 이동하는지를 봤다.

데이터베이스를 경험한 이후에는 화면을 보면서도 다른 질문을 하게 됐다.

예를 들어 랭킹 화면을 보면

> 이 데이터는 어디에서 가져오지?

내 기록 화면을 보면

> 로그인한 사용자의 기록만 어떻게 가져오지?

결과 화면을 보면

> 종료할 때 어떤 값을 DB에 저장해야 하지?

프로필을 보면

> 닉네임을 수정하면 어떤 데이터가 변경되지?

처럼 화면 뒤에 있는 데이터 흐름을 같이 생각하게 됐다.

---

## 처음 생각했던 데이터베이스와 실제 데이터베이스 작업

처음에는 이렇게 생각했다.

```text
테이블 만든다
↓
데이터 저장한다
↓
끝
```

실제로는 훨씬 많은 단계가 있었다.

```text
필요한 데이터 결정
↓
테이블 관계 설계
↓
Schema 작성
↓
Migration 생성
↓
실제 PostgreSQL에 적용
↓
DB 연결
↓
서버에서 저장 / 조회 코드 작성
↓
사용자와 데이터 관계 연결
↓
화면과 서버 연결
↓
실제 데이터 저장 확인
↓
다시 조회되는지 확인
```

처음에는 이 단계들이 하나처럼 보였다.

직접 개발하면서 각각 다른 역할이라는 것을 알게 됐다.

---

## 자주 헷갈렸던 단어를 정리해보면

내가 프로젝트 중 헷갈렸던 데이터베이스 관련 용어를 아주 단순하게 정리하면 이렇다.

| 용어         | 내가 이해한 의미                           |
| ---------- | ----------------------------------- |
| Database   | 실제 데이터를 저장하는 공간                     |
| PostgreSQL | 우리가 사용한 관계형 데이터베이스 종류               |
| Neon       | PostgreSQL을 클라우드에서 사용할 수 있게 해주는 서비스 |
| Schema     | 데이터베이스 구조를 코드로 정의한 것                |
| Migration  | Schema 변경을 실제 DB 구조에 적용하는 과정        |
| Drizzle    | 코드에서 PostgreSQL을 다루기 쉽게 도와주는 도구     |
| ORM        | 애플리케이션 코드와 DB 사이의 작업을 도와주는 방식/도구    |
| Query      | DB에서 데이터를 조회하거나 변경하는 요청             |
| CRUD       | 데이터 생성, 조회, 수정, 삭제                  |
| ID         | 데이터를 구분하기 위한 값                      |

처음에는 이 단어들이 한꺼번에 등장해서 전부 비슷해 보였다.

실제 프로젝트 흐름에 하나씩 연결해서 보니 조금씩 구분할 수 있었다.

---

## 가장 어려웠던 것은 DB 자체보다 연결 관계였다

돌이켜보면 PostgreSQL의 문법이 가장 어려웠던 것은 아니었다.

더 어려웠던 것은

**각 기술이 어디에 위치하는지 이해하는 것**

이었다.

Schema가 어디까지 하는지,

Migration은 왜 필요한지,

Drizzle은 무엇인지,

Neon은 데이터베이스인지 서비스인지,

화면에서 보이는 데이터는 어디에서 오는지,

로그인한 사용자와 기록은 어떻게 연결되는지 등이 계속 헷갈렸다.

하지만 이것들을 하나의 흐름으로 연결하고 나니 조금씩 정리되기 시작했다.

```text
사용자
↓
화면
↓
서버
↓
Drizzle
↓
PostgreSQL
```

그리고 데이터베이스 구조를 바꾸고 싶다면

```text
Schema 변경
↓
Migration
↓
실제 PostgreSQL 반영
```

이라는 또 다른 흐름이 있었다.

---

## 이번 프로젝트에서 배운 것

탄천런 이전에는 데이터베이스를

**"데이터를 저장하는 곳"**

정도로만 생각했다.

물론 틀린 말은 아니다.

하지만 실제 프로젝트에서는 저장소 하나만 만드는 것으로 끝나지 않았다.

어떤 데이터를 저장할지 정하고,

데이터끼리 관계를 만들고,

그 구조를 실제 DB에 적용하고,

서버에서 접근하고,

로그인한 사용자와 연결하고,

마지막으로 화면까지 데이터를 전달해야 했다.

그래서 데이터베이스는 프로젝트 뒤에 따로 존재하는 기능이 아니라 **대부분의 기능을 서로 연결해 주는 중심 부분**에 가까웠다.

---

## 다음 프로젝트에서는 어떻게 할 것인가

다음 프로젝트에서 데이터베이스를 설계한다면 처음부터 모든 것을 완벽하게 만들려고 하지는 않을 것 같다.

먼저 MVP에서 실제로 필요한 데이터부터 정할 것이다.

그리고 다음 순서로 확인할 것 같다.

```text
1. 이 기능에서 어떤 데이터가 필요한가?
2. 누가 이 데이터를 소유하는가?
3. 다른 데이터와 어떤 관계가 있는가?
4. Schema에 제대로 표현되어 있는가?
5. Migration이 실제 DB에 적용됐는가?
6. 서버에서 Create / Read가 실제로 되는가?
7. 화면에서 저장한 값이 DB에 들어가는가?
8. 새로고침 후 다시 조회되는가?
```

그리고

**Schema가 만들어졌다는 이유만으로 DB 구현이 끝났다고 생각하지 않을 것이다.**

반대로 모든 구조를 완벽하게 검토하느라 실제 연결 테스트를 너무 늦게 하지도 않을 것이다.

가능하면 작은 데이터 하나라도 먼저 실제 DB에 넣어보고 다시 읽어오는 것까지 확인할 것이다.

---

## "데이터베이스를 만들었다"의 의미가 달라졌다

프로젝트를 시작할 때는 테이블 구조를 작성하면 데이터베이스를 만든 것이라고 생각했다.

탄천런을 진행하고 나서는 조금 다르게 생각하게 됐다.

내 기준에서 실제로 데이터베이스 기능이 동작한다고 말하려면

**구조를 만들고 → 실제 DB에 적용하고 → 서버에서 연결하고 → 데이터를 저장하고 → 다시 조회해서 화면에서 사용하는 것**

까지 이어져야 했다.

탄천런에서는 이 과정을 이해하는 데 생각보다 많은 시간이 걸렸다.

중간에는 검증만 계속하면서

**"그래서 실제로 만들어진 것은 뭐지?"**

라는 생각도 많이 했다.

하지만 그 과정을 거치면서 Schema, Migration, PostgreSQL, Drizzle, Neon, 서버와 화면이 각각 어떤 역할을 하는지 처음으로 연결해서 볼 수 있게 됐다.

이번 프로젝트에서 데이터베이스와 관련해 가장 크게 배운 것은 특정 명령어나 문법이 아니었다.

**코드에 적힌 데이터 구조가 실제 사용자 화면의 데이터가 되기까지 여러 단계가 필요하다는 것을 이해하게 된 것**이었다.
