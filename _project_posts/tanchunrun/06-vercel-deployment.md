탄천런을 개발하면서 처음에는 배포를 굉장히 단순하게 생각했다.

로컬에서 프로젝트가 잘 실행되면 GitHub에 올리고,

Vercel에 GitHub 저장소를 연결해서 배포하면 끝이라고 생각했다.

실제로 처음 배포 버튼을 눌렀을 때는 생각보다 쉽게 웹 주소가 만들어졌다.

그래서

**"배포는 생각보다 간단하네."**

라고 생각했다.

하지만 Google 로그인, Kakao 로그인, 지도 API, 데이터베이스처럼 외부 서비스가 하나씩 붙기 시작하면서 이야기가 달라졌다.

갑자기 Vercel에서

* Production
* Preview
* Development
* Environment Variables
* Deployment
* Domain

같은 단어가 계속 나오기 시작했다.

특히 우리 팀은 `develop`과 `main` 브랜치를 나눠 사용하고 있었기 때문에 더 헷갈렸다.

가장 혼란스러웠던 것은

**"Git 브랜치와 Vercel 환경은 같은 것인가?"**

그리고

**"왜 똑같은 API 키가 Preview와 Production에 따로 보이지?"**

라는 부분이었다.

이번 프로젝트를 진행하면서 배포는 단순히 사이트를 인터넷에 올리는 것이 아니라, **코드가 실행되는 환경을 구분하고 각 환경에 필요한 설정을 맞추는 과정**이라는 것을 처음 알게 됐다.

---

## 처음에는 로컬과 배포 환경 두 개만 있는 줄 알았다

내가 처음 생각했던 구조는 아주 단순했다.

```text
내 컴퓨터
↓
GitHub
↓
Vercel
↓
실제 사이트
```

로컬에서 개발한 뒤 GitHub에 올리고,

Vercel이 그 코드를 가져가서 실제 사이트로 보여준다고 생각했다.

큰 흐름은 맞았다.

하지만 실제 팀 프로젝트에서는 중간 단계가 더 있었다.

우리는 안정적으로 개발하기 위해 Git 브랜치를 크게 두 가지로 나눠 사용했다.

```text
develop
= 기능을 합치고 테스트하는 브랜치

main
= 최종적으로 사용자에게 보여줄 브랜치
```

그리고 Vercel에서도 이 구조와 비슷하게

```text
Preview
Production
```

이라는 환경이 있었다.

이때부터 헷갈리기 시작했다.

---

## develop은 Preview, main은 Production이라고 이해했다

탄천런에서는 `develop` 브랜치에서 여러 기능을 먼저 합쳐 테스트하고,

최종적으로 확인된 코드를 `main`에 반영하는 방식을 사용했다.

Vercel에서는 `main`이 실제 서비스용 Production 배포와 연결되고,

`develop` 같은 다른 브랜치는 Preview 배포로 확인할 수 있었다.

내가 이해한 구조는 대략 이랬다.

| Git     | Vercel     | 용도                 |
| ------- | ---------- | ------------------ |
| develop | Preview    | 개발 중 기능 통합 및 테스트   |
| main    | Production | 실제 사용자에게 보여줄 최종 버전 |

처음에는 이 표처럼 단순하게 보이지 않았다.

Git에서 `develop`, `main`을 보고 있었는데 Vercel에 들어가면 갑자기 `Preview`, `Production`이라는 새로운 이름이 나왔기 때문이다.

그래서

> develop이 Preview라는 뜻인가?

> main이라는 이름이 Production으로 바뀌는 건가?

처럼 생각하기도 했다.

하지만 둘은 같은 것이 아니었다.

`develop`, `main`은 **Git 브랜치**이고,

`Preview`, `Production`은 **Vercel에서 코드를 실행하는 배포 환경**이었다.

서로 연결해서 사용할 뿐 같은 개념은 아니었다.

---

## Preview는 왜 필요한가?

처음에는 Preview 환경이 왜 필요한지도 잘 몰랐다.

어차피 로컬에서 테스트할 수 있는데 굳이 인터넷에 테스트용 사이트를 하나 더 만들 필요가 있나 싶었다.

하지만 팀 프로젝트를 하면서 이유를 알게 됐다.

내 컴퓨터에서는 잘 동작해도 다른 환경에서는 문제가 생길 수 있었다.

예를 들어

* 배포 환경에서만 필요한 환경변수
* 외부 API에서 허용해야 하는 실제 URL
* HTTPS 환경
* Vercel에서 실행되는 서버 코드
* 실제 배포된 주소에서의 로그인

같은 것은 `localhost`만으로 확인하기 어려웠다.

그래서 Preview 환경은 내 기준에서

**"실제 서비스에 올리기 전에 인터넷 환경에서 확인하는 테스트 공간"**

으로 이해하게 됐다.

---

## Production은 실제 서비스 환경이었다

Production은 Preview와 다르게 실제 사용자에게 제공할 최종 환경이었다.

처음에는

> Preview에서도 사이트가 열리고 Production에서도 사이트가 열리는데 뭐가 다르지?

라는 생각이 들었다.

둘 다 웹사이트 주소가 있고 브라우저에서 접속할 수 있기 때문이다.

하지만 목적이 달랐다.

Preview에서는 아직 개발 중인 기능이나 새로운 변경사항을 시험할 수 있다.

잘못되어도 실제 서비스에는 바로 영향을 주지 않는다.

반대로 Production은 실제 서비스이므로 함부로 테스트하면 안 된다.

내가 이해한 방식은 이랬다.

```text
Preview
= 실전과 비슷한 연습 공간

Production
= 실제 사용자 공간
```

이 구분을 알고 나니 왜 배포 환경마다 설정을 따로 관리하는지도 조금 이해되기 시작했다.

---

## 환경변수가 나오면서 갑자기 복잡해졌다

Vercel에서 가장 헷갈렸던 부분 중 하나가 환경변수였다.

프로젝트에 Google 로그인, Kakao 로그인, 지도 API 같은 외부 기능이 들어가면서 여러 값이 필요해졌다.

예를 들면

```text
Client ID
Client Secret
API Key
Database URL
```

같은 값이다.

이런 값은 코드에 직접 작성하지 않고 환경변수로 관리한다.

처음에는 환경변수를 그냥

**"비밀번호 같은 값을 숨겨놓는 곳"**

정도로 생각했다.

실제로 Secret이나 API Key를 코드에 직접 넣지 않는 것도 중요한 이유다.

하지만 배포를 하면서 또 다른 역할을 알게 됐다.

**환경마다 다른 값을 사용할 수 있게 해주는 역할**도 있었다.

---

## 같은 이름의 환경변수가 여러 개 보여서 당황했다

Vercel에서 환경변수를 설정하다 보면 같은 이름의 키가

* Production
* Preview
* Development

같은 환경에 따로 설정될 수 있었다.

여기에 Google과 Kakao 로그인, 지도 관련 값까지 들어가면서 환경변수 목록이 갑자기 많아졌다.

처음에는 정말 헷갈렸다.

예를 들어 Google 로그인에 필요한 값이 있고,

Kakao 로그인에 필요한 값이 있고,

지도에 필요한 값까지 추가되니 비슷해 보이는 키가 여러 개 나타났다.

그래서

> Preview용 Google 앱을 따로 만들어야 하나?

> Production용으로 Client ID를 또 발급받아야 하나?

> 환경이 세 개인데 API Key도 세 개씩 필요한 건가?

라는 생각을 하게 됐다.

하지만 Vercel 환경이 여러 개라는 것과 외부 서비스의 애플리케이션을 반드시 여러 개 만들어야 한다는 것은 같은 의미가 아니었다.

---

## "환경이 다르다"와 "키가 다르다"는 다른 문제였다

처음에는 Vercel에 Preview와 Production이 나뉘어 있으니 모든 API Key도 환경마다 완전히 새로 만들어야 한다고 생각하기 쉬웠다.

하지만 실제로 중요한 것은 각 외부 서비스가 어떤 설정을 요구하는지였다.

어떤 서비스는 같은 애플리케이션 안에 여러 URL을 등록할 수 있고,

어떤 서비스는 개발 환경과 운영 환경을 더 엄격하게 구분할 수도 있다.

즉

```text
Vercel 환경이 두 개다
```

라고 해서 반드시

```text
외부 API 애플리케이션도 두 개가 필요하다
```

는 뜻은 아니었다.

이걸 모르고 있을 때는 Vercel 환경변수 목록만 보고

**"키가 왜 이렇게 많지?"**

라는 생각만 했다.

나중에는 먼저

> 이 값은 어떤 서비스에서 발급한 값인가?

> Preview와 Production에서 같은 값을 써도 되는가?

> 외부 서비스에서 각각의 주소를 허용했는가?

를 확인하는 것이 더 중요하다는 것을 알게 됐다.

---

## Kakao는 되는데 Google은 안 되는 상황도 있었다

배포 환경을 설정하면서 가장 혼란스러웠던 상황 중 하나였다.

같은 프로젝트인데 Kakao 로그인은 정상적으로 동작하고 Google 로그인은 `develop` 쪽에서 제대로 되지 않는 상황이 있었다.

처음에는

> 코드가 잘못된 건가?

라고 생각할 수밖에 없었다.

같은 로그인 기능인데 하나는 되고 하나는 안 됐기 때문이다.

하지만 외부 로그인은 우리 코드만으로 결정되지 않았다.

Google과 Kakao 각각의 개발자 콘솔에도

* 허용된 주소
* Redirect URI
* Client ID
* Secret

같은 설정이 있었다.

결국 배포된 사이트 주소가 외부 서비스 설정과 맞지 않으면 코드가 같아도 로그인에 문제가 생길 수 있었다.

이 경험을 하면서

**로컬에서는 되는데 배포에서 안 되는 문제는 코드만 볼 것이 아니라 외부 서비스 설정과 배포 URL도 같이 확인해야 한다**

는 것을 알게 됐다.

자세한 로그인 설정 과정은 다음 API 연동 글에서 따로 정리하려고 한다.

---

## localhost와 배포 주소는 외부 서비스 입장에서 다른 주소였다

개발할 때는 보통 이런 주소를 사용했다.

```text
http://localhost:...
```

또는

```text
http://127.0.0.1:...
```

하지만 Vercel에 배포하면 완전히 다른 인터넷 주소가 생긴다.

외부 서비스 입장에서는 이 둘은 다른 사이트다.

나는 내 입장에서는

> 같은 탄천런인데?

라고 생각했지만,

Google이나 Kakao 같은 외부 서비스는 주소를 기준으로 허용 여부를 확인할 수 있었다.

그래서 로컬에서 정상적으로 작동했다고 해서 Preview에서도 자동으로 작동하는 것은 아니었다.

Preview가 정상이어도 Production에서는 또 실제 Production 주소가 허용되어 있어야 할 수 있었다.

이 부분 때문에 **배포 후 테스트가 따로 필요하다는 것**을 이해하게 됐다.

---

## Preview URL이 생길 때마다 새로운 문제가 생기는 것처럼 느껴졌다

Vercel 자체는 브랜치나 배포에 따라 Preview 주소를 만들어줄 수 있다.

다만 탄천런에서는 모든 브랜치에 Preview를 만들지는 않았다.

`develop`을 Preview 환경의 기준 브랜치로 쓰고, 그 외 feature 브랜치는 배포하지 않도록 설정했다.

그래서 우리가 실제로 확인하는 Preview 주소는 `develop` 것 하나였다.

이 주소로 통합된 기능을 확인할 수 있는 것 자체는 편했다.

하지만 외부 API를 사용할 때는 이 주소가 문제가 될 수도 있었다.

외부 서비스에서 허용되지 않은 주소라면 로그인이나 API 기능이 정상적으로 작동하지 않을 수 있기 때문이다.

그래서 처음에는

> Vercel에서는 사이트가 잘 열리는데 왜 로그인만 안 되지?

라는 상황을 이해하기 어려웠다.

Vercel 배포 자체가 성공한 것과 외부 서비스 연동까지 정상이라는 것은 다른 문제였다.

```text
Vercel 배포 성공
≠
Google 로그인 정상
≠
Kakao 로그인 정상
≠
지도 API 정상
```

각각 따로 확인해야 했다.

---

## "배포 성공"이라는 말도 생각보다 여러 단계였다

처음에는 Vercel에서 `Ready`가 뜨고 사이트가 열리면 배포 성공이라고 생각했다.

물론 배포 자체는 성공한 것이다.

하지만 서비스 전체가 정상이라는 의미는 아니었다.

프로젝트를 진행하면서 내가 생각하는 확인 단계가 조금 달라졌다.

```text
1. Vercel Build 성공
↓
2. 사이트 접속 가능
↓
3. 화면 정상
↓
4. 환경변수 정상
↓
5. DB 연결 정상
↓
6. 외부 로그인 정상
↓
7. 지도 등 외부 API 정상
↓
8. 실제 기능 정상
```

즉 사이트가 열린 것은 시작에 가까웠다.

이걸 알고 나니

**배포됐다 = 완성됐다**

라고 생각하면 안 된다는 것을 알게 됐다.

---

## 로컬에서 잘 되는데 Vercel에서는 왜 안 되는지 이해하기 시작했다

처음 이런 상황을 만나면 정말 답답했다.

내 컴퓨터에서는 분명 정상적으로 동작한다.

그런데 Vercel 주소에서는 오류가 난다.

코드는 똑같은데 왜 결과가 다른지 이해가 안 됐다.

하지만 나중에는 환경이 다르다는 것을 먼저 보기 시작했다.

예를 들어

* 로컬 `.env`에는 값이 있는데 Vercel에는 없는가?
* Preview에는 있는데 Production에는 없는가?
* 외부 서비스에 localhost만 등록되어 있는가?
* DB 연결 주소가 배포 환경에 맞게 설정되어 있는가?
* 브라우저에서 실행해야 할 값과 서버에서만 사용할 값이 구분되어 있는가?

등을 확인했다.

**같은 코드라도 실행 환경의 설정이 다르면 결과도 달라질 수 있었다.**

---

## `.env`와 Vercel Environment Variables도 연결되어 있었다

로컬에서는 보통 `.env`나 `.env.local` 같은 파일을 이용해 환경변수를 사용했다.

예를 들면 로컬 개발 중에는

```text
DATABASE_URL
GOOGLE_CLIENT_ID
KAKAO_CLIENT_ID
```

같은 값이 `.env.local`에 있을 수 있다.

하지만 이 파일은 보통 GitHub에 올리지 않는다.

Secret이 들어 있을 수 있기 때문이다.

그렇다면 Vercel은 이 값을 어디에서 가져올까?

Vercel 프로젝트 설정의 Environment Variables에 직접 등록해야 했다.

내가 이해한 구조는 이렇다.

```text
내 컴퓨터
.env.local

Vercel
Project Settings
→ Environment Variables
```

둘 다 환경변수를 제공하지만 저장되는 장소가 다르다.

그래서 로컬 `.env.local`에 값이 있다고 Vercel에서도 자동으로 사용할 수 있는 것은 아니었다.

이 부분도 배포하면서 처음 제대로 이해했다.

---

## 환경변수는 Git으로 공유되지 않는다는 점도 중요했다

팀 프로젝트에서는 더 헷갈릴 수 있었다.

코드는 GitHub에서 모두 같이 받는다.

하지만 `.env` 같은 파일은 Git에서 제외하는 경우가 많다.

그러면 팀원이 코드를 clone했다고 해서 로그인이나 DB 연결에 필요한 환경변수까지 자동으로 생기지 않는다.

각자 필요한 값을 따로 설정해야 한다.

처음에는

> 코드 다 받았는데 왜 실행이 안 되지?

라고 생각할 수 있었다.

하지만 프로젝트 실행에 필요한 것은 코드뿐만 아니라 환경 설정도 있었다.

그래서 팀 프로젝트에서는

**어떤 환경변수가 필요한지는 공유하되 실제 Secret 값은 안전하게 관리**

해야 했다.

---

## 환경변수 이름이 같아도 값은 다를 수 있었다

예를 들어 같은

```text
DATABASE_URL
```

이라는 이름을 사용하더라도

개발 환경에서는 개발용 DB 주소,

Production에서는 실제 서비스 DB 주소를 넣을 수 있다.

```text
DATABASE_URL

Development
→ 개발 DB

Preview
→ 테스트 DB

Production
→ 운영 DB
```

이런 구조를 보고 처음에는

> 이름이 같은데 왜 여러 개지?

라고 생각했다.

하지만 환경마다 같은 역할을 하는 값이 다를 수 있기 때문에 이름은 같고 값만 달라질 수 있었다.

이 구조를 이해하면서 Vercel 환경을 나누는 이유도 더 잘 이해됐다.

---

## 배포 환경을 나누는 이유는 실수를 줄이기 위해서였다

Preview와 Production을 따로 관리하는 것이 처음에는 복잡하게만 느껴졌다.

환경변수도 여러 개 관리해야 하고 설정할 것도 늘어나기 때문이다.

하지만 하나의 환경만 사용한다고 생각해보면 더 위험했다.

개발 중 테스트하다가 실제 사용자 데이터가 있는 DB를 수정할 수도 있다.

아직 확인하지 않은 로그인 설정을 실제 서비스에 바로 적용할 수도 있다.

잘못된 환경변수를 넣으면 실제 서비스가 바로 영향을 받을 수도 있다.

그래서 환경을 나누는 것은 번거로운 규칙이 아니라 **개발 중인 작업과 실제 서비스를 분리해서 보호하기 위한 방법**이었다.

---

## Vercel에서 설정을 바꾸면 기존 배포가 자동으로 같은 상태인 것도 아니었다

처음에는 환경변수를 수정하면 이미 떠 있는 사이트가 바로 그 값을 사용하는 줄 알았다.

하지만 배포 환경에서는 설정 변경 후 새로운 배포가 필요한 경우가 있었다.

코드는 그대로여도 새로운 환경변수로 다시 빌드하거나 배포해야 실제 사이트가 그 설정을 사용할 수 있기 때문이다.

그래서

> 환경변수 넣었는데 왜 아직 안 되지?

라는 상황에서는

**설정을 저장했는지뿐 아니라 그 설정이 반영된 새로운 배포인지**

도 확인해야 했다.

이런 부분 때문에 배포 문제를 볼 때는 코드만 보는 것으로 부족했다.

---

## Vercel의 로그도 처음에는 무슨 말인지 몰랐다

로컬에서는 터미널에서 바로 오류를 볼 수 있다.

하지만 배포된 사이트에서 문제가 생기면 내 컴퓨터 터미널에 오류가 나오지 않는다.

Vercel에서 Build Log나 실행 로그를 확인해야 했다.

처음에는 영어 메시지도 많고 내용도 길어서 보기 어려웠다.

그래도 문제가 생겼을 때

> 빌드 단계에서 실패했는가?

> 사이트는 빌드됐는데 실행 중 서버 오류가 난 것인가?

를 구분하는 데 도움이 됐다.

단순히 화면에

**500 Error**

같은 것이 보인다고 해서 원인을 알 수 있는 것은 아니었다.

어느 단계에서 문제가 발생했는지를 로그로 확인해야 했다.

---

## Build 오류와 Runtime 오류도 구분하게 됐다

배포 문제를 겪으면서 이 둘도 조금씩 알게 됐다.

### Build 오류

Vercel이 프로젝트를 실제 사이트로 만들기 전에 코드 검사나 빌드 과정에서 실패한 경우다.

이 경우 사이트 자체가 새 버전으로 제대로 배포되지 않을 수 있다.

### Runtime 오류

빌드는 성공했지만 실제 사용자가 기능을 실행하는 과정에서 문제가 발생한 경우다.

예를 들어 DB 연결이나 서버 코드에서 문제가 생길 수 있다.

처음에는 둘 다 그냥

**"배포 오류"**

라고 생각했다.

하지만 어느 단계인지 구분하면 확인해야 할 범위도 달라졌다.

---

## 팀 프로젝트에서는 Preview가 특히 유용했다

Preview 환경을 이해하고 나니 팀 프로젝트에서 왜 유용한지도 알게 됐다.

로컬 화면을 보여주려면 다른 사람에게 내 컴퓨터를 직접 보여줘야 한다.

하지만 `develop`에 기능이 합쳐지고 나면 Preview 주소에서 팀원과 같은 화면을 확인할 수 있다.

예를 들어 기능을 `develop`에 합친 뒤

> 내 컴퓨터에서는 됩니다.

라고 설명하는 대신

> 이 Preview 주소에서 확인해 주세요.

라고 할 수 있다.

feature 브랜치마다 주소가 생기는 방식은 아니어서, 확인은 `develop`에 합친 뒤에 할 수 있었다.

디자인이나 로그인처럼 실제 브라우저 환경에서 확인해야 하는 기능에서는 특히 편했다.

---

## 하지만 Preview에서 된다고 Production에서도 무조건 되는 것은 아니었다

Preview에서 모든 기능이 정상 동작하면 이제 main에 합치기만 하면 끝일 것 같았다.

하지만 Production은 별도의 환경변수와 별도의 실제 URL을 사용할 수 있다.

그래서 Preview에서는 정상인데 Production에서는 문제가 생길 수도 있다.

예를 들어

```text
Preview
→ Preview용 환경변수 있음
→ 정상

Production
→ 필요한 환경변수 빠짐
→ 오류
```

같은 상황이 가능하다.

또 외부 서비스에 Preview URL은 등록했지만 Production URL을 등록하지 않았다면 Production에서 로그인 문제가 생길 수도 있다.

그래서 최종 배포에서도 다시 확인해야 했다.

---

## Git과 Vercel이 연결되어 자동 배포되는 것도 처음에는 신기했다

GitHub와 Vercel을 연결해 두면 Git의 변화가 Vercel 배포로 이어질 수 있었다.

내가 이해한 전체 흐름은 대략 이랬다.

```text
로컬에서 코드 작업
↓
GitHub에 push
↓
PR / merge
↓
GitHub branch 변경
↓
Vercel이 변경 감지
↓
새 배포 생성
```

처음에는 배포할 때마다 Vercel에 들어가 직접 파일을 올려야 하는 줄 알았다.

하지만 GitHub와 연결된 상태에서는 코드 변경이 배포 과정까지 이어졌다.

이 덕분에 Git 브랜치 구조와 배포 환경이 왜 같이 이야기되는지도 이해하게 됐다.

---

## 브랜치와 배포 환경은 연결되지만 같은 것은 아니다

이 부분은 프로젝트 내내 헷갈렸기 때문에 가장 확실하게 정리해 두고 싶었다.

```text
main / develop
= Git에서 코드를 관리하는 브랜치

Production / Preview
= Vercel에서 코드를 실행하는 환경
```

우리는

```text
main → Production
develop → Preview
```

처럼 사용했다.

하지만 그래서 `main = Production`이라는 뜻은 아니다.

Git과 Vercel이라는 서로 다른 시스템에서 각각 존재하는 개념이고, 우리가 그 둘을 연결해서 사용한 것이다.

이 차이를 알고 나니 Vercel 설정 화면도 훨씬 덜 복잡하게 느껴졌다.

---

## 환경변수도 한꺼번에 넣기보다 용도를 구분하는 것이 필요했다

Google, Kakao, 지도, DB까지 연결하면서 키가 많아지니 어떤 값이 어디에 쓰이는지 알기 어려워졌다.

그래서 내 기준에서는 최소한 다음 정도는 구분할 필요가 있었다.

| 종류            | 용도                |
| ------------- | ----------------- |
| Database      | 서버가 DB에 연결하기 위한 값 |
| Google OAuth  | Google 로그인        |
| Kakao OAuth   | Kakao 로그인         |
| Map API       | 지도 서비스 연결         |
| Public 환경변수   | 브라우저에서도 사용 가능한 값  |
| Server Secret | 서버에서만 사용해야 하는 값   |

특히 Secret 값은 브라우저에 노출되면 안 되기 때문에 아무 환경변수나 클라이언트 코드에서 사용하는 것도 위험할 수 있었다.

처음에는 전부 그냥

**"API 키"**

처럼 보였지만 역할이 모두 달랐다.

---

## 이름에 PUBLIC이 붙는 이유도 조금씩 이해했다

Next.js에서는 브라우저에서 사용할 수 있도록 노출하는 환경변수와 서버에서만 사용해야 하는 환경변수를 구분한다.

프로젝트를 진행하면서 `NEXT_PUBLIC_...`처럼 시작하는 이름도 보게 됐다.

처음에는

> 왜 어떤 환경변수에는 NEXT_PUBLIC이 붙고 어떤 것은 안 붙지?

라고 생각했다.

내가 이해한 핵심은 간단했다.

```text
NEXT_PUBLIC_...
→ 브라우저 코드에서도 사용할 수 있음

일반 환경변수
→ 서버에서만 사용하는 값으로 관리
```

그래서 비밀번호나 Client Secret 같은 민감한 값에 `NEXT_PUBLIC_`을 붙이면 안 된다는 것도 알게 됐다.

환경변수는 단순히 숨기는 것이 아니라 **어디에서 사용할 수 있는 값인지도 구분해야 했다.**

---

## 배포 문제를 확인할 때 순서가 생겼다

프로젝트 초반에는 배포 후 기능이 안 되면 어디부터 봐야 할지 몰랐다.

코드를 다시 보고,

Vercel도 보고,

Google Console도 보고,

다시 코드를 보고 하는 식이었다.

나중에는 대략 다음 순서로 확인하게 됐다.

```text
1. Vercel 배포 자체가 성공했는가?
2. 올바른 브랜치가 배포됐는가?
3. Preview인지 Production인지 확인했는가?
4. 해당 환경에 필요한 환경변수가 있는가?
5. 환경변수 이름에 오타가 없는가?
6. 설정 변경 후 새 배포가 만들어졌는가?
7. 외부 서비스에 현재 배포 URL이 허용되어 있는가?
8. Vercel 로그에 오류가 있는가?
```

이렇게 순서대로 확인하니

**"배포가 안 돼요."**

라는 큰 문제를 작은 문제들로 나눠 볼 수 있었다.

---

## 자주 헷갈렸던 용어를 정리해보면

이번 프로젝트에서 Vercel을 사용하면서 헷갈렸던 개념을 내 기준으로 정리하면 이렇다.

| 용어                   | 내가 이해한 의미                        |
| -------------------- | -------------------------------- |
| Deployment           | 특정 시점의 코드를 Vercel에 실제로 올려 실행한 결과 |
| Preview              | 개발 중 변경사항을 배포 환경에서 확인하는 공간       |
| Production           | 실제 서비스용 배포 환경                    |
| Environment Variable | 코드 밖에서 관리하는 설정값                  |
| Domain               | 사용자가 접속하는 웹 주소                   |
| Build                | 소스 코드를 실제 배포 가능한 형태로 만드는 과정      |
| Build Log            | 빌드 과정에서 어떤 일이 일어났는지 보여주는 기록      |
| Runtime              | 배포된 앱이 실제로 실행되는 단계               |
| Redeploy             | 기존 설정이나 코드를 기준으로 다시 배포하는 것       |

처음에는 Vercel 화면에 보이는 메뉴 이름처럼 느껴졌지만, 실제 문제를 겪으면서 각각 왜 필요한지 알게 됐다.

---

## 가장 어려웠던 것은 설정이 여러 곳에 있다는 것이었다

Vercel 배포에서 가장 어려웠던 것은 코드가 아니었다.

설정해야 하는 위치가 여러 곳에 있다는 것이 더 어려웠다.

예를 들어 Google 로그인 하나만 해도

```text
우리 코드
+
Vercel 환경변수
+
Google 개발자 설정
+
실제 배포 URL
```

이 모두 맞아야 할 수 있었다.

그래서 한곳만 보고 문제를 해결하려고 하면 답이 나오지 않았다.

Kakao와 지도도 마찬가지였다.

이 경험 때문에

**외부 서비스가 연결된 기능은 우리 코드만의 문제가 아니라 여러 서비스의 설정이 동시에 맞아야 동작한다**

는 것을 알게 됐다.

---

## 처음 생각했던 배포와 실제 배포

처음에는 이렇게 생각했다.

```text
코드 완성
↓
Vercel에 올림
↓
끝
```

실제로는 조금 달랐다.

```text
코드 작성
↓
GitHub 반영
↓
Vercel Build
↓
Preview 배포
↓
환경변수 확인
↓
외부 서비스 설정 확인
↓
기능 테스트
↓
문제 수정
↓
main 반영
↓
Production 배포
↓
Production 환경변수 확인
↓
실제 URL에서 다시 테스트
```

배포는 프로젝트 마지막에 한 번 하는 작업이 아니었다.

개발 중에도 Preview에서 계속 확인하고, 실제 서비스 환경에서도 다시 검증하는 과정이었다.

---

## 이번 프로젝트에서 배운 것

탄천런 이전에는 배포를

**"내 컴퓨터에 있는 사이트를 인터넷에 올리는 것"**

이라고 생각했다.

지금도 가장 기본적인 의미는 맞다고 생각한다.

하지만 실제 프로젝트에서는 그것보다 더 많은 것이 포함되어 있었다.

코드는 같아도

* 어떤 브랜치인지
* 어떤 환경인지
* 어떤 환경변수를 사용하는지
* 어떤 DB에 연결하는지
* 외부 서비스가 어떤 주소를 허용하는지

에 따라 결과가 달라질 수 있었다.

그래서 배포 환경은 단순한 웹 주소가 아니라 **코드가 실제로 실행되기 위한 설정 전체**에 가까웠다.

---

## 다음 프로젝트에서는 어떻게 할 것인가

다음 프로젝트에서 Vercel을 사용한다면 초반부터 환경을 먼저 정리할 것 같다.

예를 들어 이런 식이다.

| 환경         | Git              | 용도        |
| ---------- | ---------------- | --------- |
| Local      | 개인 작업 브랜치        | 내 컴퓨터 개발  |
| Preview    | develop / 기능 브랜치 | 배포 전 테스트  |
| Production | main             | 실제 사용자 환경 |

그리고 외부 서비스를 연결하기 전에 필요한 환경변수 목록을 먼저 만들 것이다.

```text
변수 이름
↓
어떤 서비스에서 사용하는가
↓
브라우저용인가 서버용인가
↓
Preview에 필요한가
↓
Production에 필요한가
```

를 정리해 두면 키가 많아져도 훨씬 덜 헷갈릴 것 같다.

또 로컬에서 정상적으로 작동했다고 바로 끝내지 않고

**Local → Preview → Production**

순서로 확인할 것이다.

## 배포가 되었다고 끝난 것이 아니었다

탄천런을 처음 Vercel에 올렸을 때 사이트 주소가 만들어지는 것을 보고 프로젝트가 거의 완성된 것처럼 느껴졌다.

하지만 실제로는 그 뒤에 더 많은 문제가 기다리고 있었다.

Preview와 Production을 구분하고,

환경변수를 각각 설정하고,

외부 API가 배포 주소를 허용하도록 맞추고,

실제 배포 환경에서 기능을 다시 테스트해야 했다.

처음에는 이런 과정이 복잡하고 번거롭게만 느껴졌다.

하지만 프로젝트를 끝낼 때쯤에는 왜 이런 구분이 있는지 조금 이해할 수 있었다.

**로컬에서 잘 작동하는 코드를 만드는 것과 실제 사용자가 안정적으로 사용할 수 있는 서비스를 만드는 것은 다른 일이었다.**

탄천런에서 Vercel을 사용하면서 가장 크게 배운 것도 바로 그 차이였다.
