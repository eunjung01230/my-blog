탄천런의 화면 구조를 어느 정도 정리한 뒤에는 Figma에서 만든 디자인을 Claude Design으로 가져가 수정하고 발전시키는 작업을 했다.

처음에는 이 과정이 단순할 것이라고 생각했다.

Figma에 이미 화면이 있으니 Claude에게 디자인을 보여주고,

**"이 디자인을 기준으로 조금 더 예쁘게 만들어줘."**

라고 하면 되는 줄 알았다.

하지만 실제로 해보니 가장 어려웠던 것은 디자인을 만드는 것 자체가 아니었다.

**Claude에게 지금 보고 있는 자료 중 무엇을 기준으로 판단해야 하는지 정확하게 알려주는 것**이 더 어려웠다.

같은 화면을 보고 있어도 Figma, 기획 문서, 참고 이미지가 서로 다른 내용을 가지고 있었고, Claude는 내가 말하지 않은 부분까지 수정하기도 했다.

그래서 점점 프롬프트를

**"무엇을 만들어줘"**

보다

**"무엇은 유지하고, 무엇만 바꾸고, 무엇은 절대 건드리지 말아줘"**

라는 방식으로 작성하게 됐다.

---

## Figma에서 바로 Claude Design으로 넘어가면 끝일 줄 알았다

처음에는 Figma에서 화면을 만들어 둔 상태였기 때문에 디자인 작업의 대부분이 끝났다고 생각했다.

이미 홈 화면, 러닝 진행 화면, 결과 화면, 랭킹 화면처럼 여러 화면이 만들어져 있었고, 버튼과 정보의 위치도 어느 정도 정리되어 있었다.

그래서 Claude Design에서는 기존 디자인을 조금 다듬는 정도만 하면 될 것 같았다.

하지만 실제로 Claude에게 디자인을 넘기고 수정 요청을 시작하니 문제가 생겼다.

Claude 입장에서는 내가 가지고 있는 여러 자료 중에서

* Figma 화면이 가장 중요한지
* 기획 문서가 가장 중요한지
* 내가 첨부한 참고 이미지의 색감이 가장 중요한지
* 기존 화면 구조를 그대로 유지해야 하는지

알 수 없었다.

나는 당연히 알고 있는 내용이었지만 Claude에게는 당연하지 않았다.

---

## 가장 먼저 필요했던 것은 "어떤 자료가 기준인지" 정하는 일이었다

작업하다 보니 디자인에 사용되는 자료가 하나가 아니었다.

Figma에는 현재 화면 구조가 있었고,

기획 문서에는 실제 구현해야 하는 기능이 있었고,

따로 첨부한 이미지에는 원하는 분위기나 색감이 있었다.

문제는 이 세 가지가 항상 완전히 같지는 않았다는 것이다.

예를 들어 참고 이미지에는 마음에 드는 색감이 있지만 그 이미지의 화면 구조까지 따라 하고 싶은 것은 아니었다.

반대로 Figma의 화면 구조는 유지하고 싶지만 색상이나 버튼 디자인은 바꾸고 싶을 수 있었다.

처음에는 이런 차이를 자세히 설명하지 않았다.

그래서 Claude가 참고 이미지의 분위기만 가져오는 것이 아니라 구조까지 비슷하게 바꾸거나, 기존에 있던 요소의 위치를 함께 수정하는 경우가 생겼다.

그때부터 자료의 역할을 따로 설명하기 시작했다.

내가 정리한 기준은 대략 이런 식이었다.

| 자료            | 기준으로 사용하는 부분          |
| ------------- | --------------------- |
| Figma         | 화면 구조, 정보 배치, 화면 흐름   |
| 기획 문서         | 실제 기능, 정책, 구현 범위      |
| 참고 이미지        | 색감, 분위기, 시각적인 느낌      |
| Claude Design | 위 기준 안에서 디자인을 수정하고 표현 |

이렇게 나누고 나니 요청하기가 훨씬 쉬워졌다.

예를 들어 참고 이미지를 보여줄 때도

> 이 이미지에서는 색감과 분위기만 참고하고, 현재 Figma의 화면 구조는 변경하지 마라.

라고 명확하게 이야기할 수 있었다.

이 경험을 하면서 **자료를 많이 주는 것보다 각각의 자료를 왜 주는지 설명하는 것이 중요하다는 것**을 알게 됐다.

---

## "비슷하게 만들어줘"라는 말은 생각보다 위험했다

Claude Design을 처음 사용할 때는 프롬프트도 짧았다.

예를 들어

> 이 디자인을 더 세련되게 만들어줘.

또는

> 이 이미지 같은 느낌으로 바꿔줘.

처럼 요청했다.

사람끼리 이야기한다면 어느 정도 의미를 이해할 수 있을 것 같았다.

하지만 AI에게는 너무 넓은 요청이었다.

"세련되게"라는 말에는 정해진 기준이 없다.

Claude가 생각하는 세련된 디자인과 내가 원하는 디자인이 다를 수 있었다.

그리고

"이 이미지 같은 느낌"

이라는 말도

* 색상만 비슷하게 할지
* 글꼴까지 따라 할지
* 카드 모양도 바꿀지
* 화면 배치까지 변경할지

범위가 정해져 있지 않았다.

그래서 결과를 보면 내가 바꾸고 싶지 않았던 부분까지 달라지는 경우가 있었다.

처음에는 결과가 마음에 들지 않으면 다시

> 이건 원래대로 돌려줘.

> 이 부분은 건드리지 마.

라고 수정 요청을 했다.

하지만 이렇게 하면 작업을 계속 되돌리는 일이 생겼다.

그래서 나중에는 **수정 요청을 하기 전에 변경 범위를 먼저 정하는 방식**으로 바꿨다.

---

## "바꿀 것"보다 "바꾸지 않을 것"을 더 많이 적게 됐다

프롬프트를 여러 번 작성하면서 가장 크게 달라진 부분이다.

처음에는 원하는 것만 적었다.

> 배경을 더 어둡게 해줘.

> 시작 버튼을 크게 해줘.

그런데 나중에는 그 앞뒤에 조건을 붙이기 시작했다.

예를 들면 이런 식이었다.

> 현재 화면 구조와 기능은 그대로 유지한다.
> 새로운 기능은 추가하지 않는다.
> 버튼의 위치는 변경하지 않는다.
> 이번 작업에서는 배경 색상과 버튼 크기만 수정한다.

이렇게 작성하면 Claude가 판단해야 하는 범위가 훨씬 줄어들었다.

결국 내가 자주 사용하게 된 프롬프트 구조는 세 부분으로 나뉘었다.

### 1. 유지할 것

현재 화면에서 절대 변경하지 않을 부분을 먼저 적었다.

예를 들면

* 현재 Navigation 구조 유지
* 화면의 정보 순서 유지
* 기존 버튼 기능 유지
* 이미 확정한 사용자 흐름 유지

같은 내용이었다.

### 2. 수정할 것

이번 작업에서 실제로 바꾸고 싶은 부분만 적었다.

예를 들면

* 배경 색감 변경
* 버튼 크기 조정
* 텍스트 크기 조정
* 여백 수정

같은 내용이었다.

### 3. 하지 않을 것

Claude가 임의로 판단하면 안 되는 부분을 적었다.

* 새로운 기능 추가 금지
* 새로운 버튼 추가 금지
* 기획 문서에 없는 화면 생성 금지
* 기존 기능 삭제 금지

이렇게 세 가지를 분리하고 나니 결과가 훨씬 안정적이었다.

---

## 디자인 작업에서도 "문서에 없는 기능 추가 금지"가 중요했다

기획 단계에서 이미 기능을 너무 많이 확장했다가 MVP를 다시 잡은 경험이 있었다.

그래서 디자인 작업에서도 같은 문제가 반복되는 것을 막고 싶었다.

Claude가 디자인을 더 완성도 있게 만들려고 하면서 내가 요청하지 않은 기능을 화면에 추가할 수도 있었다.

예를 들어 화면이 조금 비어 보인다고 해서 새로운 카드나 버튼을 추가하면 디자인만 보면 더 풍부해 보일 수 있다.

하지만 그 버튼이 실제 기능이라면 개발해야 할 기능도 하나 늘어난다.

그러면 디자인 한 번 수정한 것이 개발 범위까지 바꿔 버리게 된다.

그래서 Claude Design을 사용할 때도 계속

**"기획 문서에 없는 기능은 추가하지 않는다."**

라는 조건을 넣었다.

이 규칙은 단순히 디자인을 지키기 위한 것이 아니었다.

디자인 때문에 개발 범위가 다시 커지는 것을 막기 위한 기준이었다.

---

## 전체 화면을 Claude에게 어떻게 보여줄지도 문제였다

화면이 몇 개 없을 때는 하나씩 보여주면 된다.

하지만 탄천런처럼 여러 화면이 만들어지니 전체 디자인을 한 번에 확인하고 싶어졌다.

Figma에서는 각 화면이 각각의 Frame으로 나뉘어 있었기 때문에 한 화면만 캡처하면 전체 흐름을 보여주기 어려웠다.

나는 전체 디자인을 한 장의 큰 이미지처럼 보고 싶었다.

그래서 여러 화면을 한 번에 선택하거나 Export해서 전체 구조를 확인하는 방법도 찾아봤다.

이 과정에서 단순히 디자인을 만드는 것과 **디자인을 다른 도구에 전달하기 좋은 형태로 정리하는 것**도 별개의 작업이라는 것을 알게 됐다.

사람인 나는 Figma를 열어서 화면을 좌우로 보면서 전체 흐름을 이해할 수 있다.

하지만 Claude에게 이미지를 전달한다면 어떤 화면이 먼저이고, 어떤 화면이 다음인지 한눈에 알 수 있도록 정리하는 것이 더 중요했다.

---

## 모든 화면을 한 번에 보여주는 것이 항상 좋은 것도 아니었다

처음에는 전체 화면을 다 보여주면 Claude가 프로젝트를 더 잘 이해할 것이라고 생각했다.

하지만 작업 범위가 작을 때는 오히려 필요한 화면만 보여주는 것이 더 좋았다.

예를 들어 홈 화면의 색상만 수정하고 싶은데 전체 화면 10개를 모두 주면 Claude가 다른 화면까지 함께 판단할 수 있다.

그래서 상황에 따라 전달하는 자료를 다르게 하게 됐다.

전체적인 통일성을 볼 때는 전체 화면을 보여주고,

특정 화면을 수정할 때는 해당 화면과 필요한 참고 자료만 보여줬다.

즉,

**자료가 많다고 항상 더 정확해지는 것은 아니었다.**

이번 작업에서 Claude가 반드시 봐야 하는 정보가 무엇인지 정하는 것이 더 중요했다.

---

## Figma 화면과 실제 브라우저 화면도 다르게 보였다

Figma에서 디자인을 볼 때는 화면이 정돈되어 보였다.

하지만 실제 브라우저 크기나 화면 비율에서 보면 느낌이 달라지는 경우가 있었다.

텍스트가 예상보다 길어지거나,

버튼이 작아 보이거나,

공간이 너무 비어 보이거나,

반대로 한 화면에 정보가 너무 많아 보이기도 했다.

특히 러닝 중에 사용하는 화면은 일반 웹사이트처럼 천천히 읽는 화면이 아니다.

달리면서 빠르게 숫자를 봐야 하기 때문에 중요한 정보는 더 크게 보여야 했다.

그래서 디자인 이미지만 보고 판단하는 것이 아니라

**"실제로 사용자가 이 화면을 사용하는 상황"**

을 생각하면서 수정하기 시작했다.

이 과정에서 시작 버튼과 종료 버튼을 더 크게 만들고, 주요 기록 수치의 글씨도 키우는 방향으로 수정했다.

---

## 색감과 구조를 동시에 바꾸면 무엇이 좋아졌는지 알기 어려웠다

Claude에게 한 번에 너무 많은 변경을 요청했던 적도 있었다.

배경색을 바꾸고,

카드 모양도 바꾸고,

글씨 크기도 바꾸고,

버튼도 바꾸고,

여백도 바꾸는 식이었다.

결과는 크게 달라졌지만 어떤 수정 때문에 더 좋아졌는지 판단하기 어려웠다.

마음에 들지 않는 부분이 있어도 무엇을 되돌려야 할지도 애매했다.

그래서 나중에는 수정 범위를 더 작게 나눴다.

예를 들어 먼저

**색감만 변경**

한 뒤 확인하고,

그다음

**버튼 크기만 변경**

하고,

그다음

**텍스트와 간격을 조정**

하는 식이었다.

이렇게 하면 결과를 비교하기 쉬웠고, 잘못된 부분만 다시 수정하기도 편했다.

Claude Design에서도 한 번에 완성하려고 하기보다 **작은 수정 → 확인 → 다음 수정**의 반복이 더 편했다.

---

## 프롬프트도 점점 작업 지시서처럼 바뀌었다

처음 프롬프트는 한두 문장이었다.

하지만 여러 번 시행착오를 겪으면서 점점 작업 지시서처럼 바뀌었다.

예를 들면 이런 구조였다.

> 현재 화면 구조는 유지한다.
> 이번 작업의 목적은 시각적인 개선이다.
> 기능과 사용자 흐름은 변경하지 않는다.
>
> 수정할 부분:
>
> * 배경 색상
> * 버튼 크기
> * 텍스트 가독성
>
> 유지할 부분:
>
> * 현재 화면 배치
> * Navigation
> * 기능
>
> 금지:
>
> * 새로운 기능 추가
> * 새로운 화면 추가
> * 기획 문서에 없는 UI 추가

처음에는 이런 프롬프트가 너무 길다고 생각했다.

그런데 결과가 잘못되어 여러 번 수정하는 것보다 처음부터 범위를 명확하게 알려주는 것이 더 빠른 경우가 많았다.

여기서 알게 된 것이 있다.

**좋은 프롬프트는 길어서 좋은 것이 아니라, Claude가 판단하지 않아도 되는 부분을 명확하게 만들어주는 프롬프트였다.**

---

## Claude가 알아서 판단하게 두면 안 되는 부분이 있었다

AI 도구를 사용하다 보면

"알아서 예쁘게 해줘."

라고 맡기고 싶어지는 순간이 있다.

디자인 감각이 부족하다고 느낄수록 더 그랬다.

하지만 탄천런 작업에서는 모든 것을 Claude에게 맡길 수는 없었다.

Claude는 화면을 보기 좋게 만드는 방향으로 판단할 수 있지만,

그 기능이 실제 MVP에 포함되어 있는지,

우리 팀이 기간 안에 구현할 수 있는지,

다른 화면과 연결되는 기능인지까지 자동으로 알고 있는 것은 아니다.

결국

**시각적으로 어떻게 표현할지는 Claude의 도움을 받을 수 있지만, 무엇을 만들어야 하는지는 프로젝트를 진행하는 사람이 결정해야 했다.**

이 기준을 알게 된 뒤에는 Claude에게 맡길 부분과 내가 결정할 부분을 조금 더 구분할 수 있게 됐다.

---

## 디자인 결과를 확인하는 방법도 달라졌다

처음에는 Claude가 만든 화면이 보기 좋으면 성공이라고 생각했다.

하지만 나중에는 조금 다른 기준으로 확인했다.

### 기존 기능이 그대로 있는가?

디자인을 바꾸면서 기존 버튼이나 필요한 정보가 사라지지 않았는지 확인했다.

### 새로운 기능이 생기지 않았는가?

보기 좋게 만들기 위해 필요하지 않은 UI가 추가되지 않았는지 확인했다.

### 화면끼리 통일되어 있는가?

홈 화면은 한 디자인인데 결과 화면은 다른 서비스처럼 보이지 않는지 확인했다.

### 실제 사용 상황에서 읽기 쉬운가?

러닝 중 필요한 숫자나 버튼이 충분히 크게 보이는지 확인했다.

이렇게 기준을 세우고 나니 단순히

**"예쁜가?"**

만 보는 것이 아니라

**"우리 서비스에 맞는 디자인인가?"**

를 볼 수 있게 됐다.

## Figma와 Claude Design의 역할을 구분하게 됐다

처음에는 Figma와 Claude Design이 비슷한 역할을 하는 도구처럼 느껴졌다.

둘 다 결국 화면을 만드는 도구였기 때문이다.

하지만 사용하면서 내 기준에서는 역할이 조금 달라졌다.

Figma에서는 전체 화면 구조와 사용자 흐름을 확인하기 편했다.

Claude Design은 이미 있는 화면을 바탕으로 시각적인 방향을 빠르게 바꿔보고 비교하기 좋았다.

그래서 나중에는

**Figma에서 구조를 확인하고, Claude Design으로 표현을 개선한다**

는 식으로 생각하게 됐다.

물론 실제 작업에서는 두 도구 사이를 여러 번 오갔다.

Claude에서 수정한 결과를 보고 다시 구조를 생각하기도 했고, Figma 화면을 다시 확인한 뒤 Claude에게 수정 지시를 하기도 했다.

중요했던 것은 어떤 도구를 사용하는가보다

**현재 작업에서 무엇을 결정하려고 하는지 알고 있는 것**이었다.

---

## 이번 과정에서 가장 많이 바뀐 것은 프롬프트 작성 방식이었다

처음과 마지막의 프롬프트를 비교하면 가장 차이가 컸다.

처음에는

> 더 예쁘게 해줘.

> 이런 느낌으로 바꿔줘.

와 같은 요청이었다.

나중에는

> 현재 구조는 유지하고,
> 기능은 추가하지 않고,
> 이번에는 색상과 버튼 크기만 수정하고,
> 참고 이미지는 색감만 참고한다.

처럼 작업의 범위를 먼저 설명했다.

결과적으로 Claude가 더 똑똑해진 것이 아니라

**내가 Claude에게 필요한 정보를 더 정확하게 주게 된 것**에 가까웠다.

## 이번 작업에서 배운 것

Figma에서 Claude Design으로 디자인을 전달하면서 가장 크게 배운 것은 AI 도구를 사용하는 데도 기준이 필요하다는 것이었다.

처음에는 Claude에게 디자인을 보여주면 알아서 좋은 결과를 만들어 줄 것이라고 생각했다.

하지만 실제로는 내가 먼저 정해야 하는 것이 많았다.

* 어떤 자료가 기준인지
* 어떤 부분을 유지할지
* 어떤 부분을 수정할지
* 참고 자료에서 무엇만 가져올지
* 절대 추가하면 안 되는 것이 무엇인지

이것들이 정리되어 있어야 Claude도 원하는 방향으로 작업할 수 있었다.

결국 AI에게 디자인을 맡기는 것도 단순히

**"예쁘게 만들어줘."**

라고 말하는 일이 아니었다.

내가 원하는 결과를 설명하고, 작업 범위를 정하고, 결과를 확인하고, 필요한 부분만 다시 수정하는 과정이었다.

## 다음에는 어떻게 할 것인가

다음 프로젝트에서 Figma와 AI 디자인 도구를 함께 사용한다면 처음부터 다음 순서로 작업할 것 같다.

먼저 현재 디자인에서 **절대 바꾸지 않을 구조**를 정한다.

그다음 이번 작업에서 **수정할 범위**를 하나 정한다.

참고 이미지를 사용한다면

**색상 / 분위기 / 형태 / 배치 중 무엇을 참고하는지**

정확하게 적는다.

그리고 AI에게 새로운 기능을 임의로 추가하지 못하도록 기능 기준 문서를 함께 알려준다.

마지막으로 한 번에 전체 디자인을 바꾸기보다 작은 단위로 수정하고 결과를 확인한다.

탄천런에서는 이 방법을 처음부터 알고 시작한 것이 아니었다.

Claude가 예상과 다르게 수정한 화면을 다시 고치고,

Figma 전체 화면을 어떻게 전달할지 고민하고,

프롬프트를 계속 수정하면서 하나씩 알게 됐다.

그래서 이번 경험에서 가장 기억에 남는 것은 Claude가 만들어준 특정 디자인이 아니다.

**AI에게 디자인을 맡길 때도 결국 내가 기준을 만들어야 한다는 것을 알게 된 과정**이다.
