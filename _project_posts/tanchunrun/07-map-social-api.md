탄천런에는 우리가 직접 만들 수 없는 기능이 몇 가지 있었다.

대표적인 것이 **지도와 소셜 로그인**이었다.

사용자의 현재 위치와 러닝 경로를 보여주려면 지도 서비스가 필요했고,

Google이나 Kakao 계정으로 로그인하게 만들려면 각 회사가 제공하는 로그인 기능을 사용해야 했다.

처음에는 이 과정도 비교적 단순하게 생각했다.

> Google이나 Kakao에서 API 키를 하나 받는다.
> 그 값을 코드에 넣는다.
> 끝.

지도도 비슷했다.

> 지도 API 키를 받아서 화면에 지도를 띄우면 되겠지.

하지만 실제로 연결해 보니 `API Key` 하나만 넣는 것으로 끝나는 일이 아니었다.

외부 서비스의 개발자 페이지에서 애플리케이션을 만들고,

사용할 기능을 설정하고,

우리 서비스의 주소를 등록하고,

필요한 키를 발급받고,

환경변수에 넣고,

코드에서 사용하고,

실제 로그인이나 지도 기능이 동작하는지 다시 확인해야 했다.

특히 소셜 로그인에서는 `Client ID`, `Client Secret`, `Redirect URI`, `Callback`, `OAuth` 같은 처음 보는 단어들이 한꺼번에 등장했다.

처음에는 전부 비슷한 설정처럼 보였다.

프로젝트를 진행하면서 하나씩 연결해 보니 결국 중요한 것은

**우리 서비스와 외부 서비스가 서로를 안전하게 확인하고 데이터를 주고받는 과정**

이라는 것을 조금씩 이해하게 됐다.

---

## API가 무엇인지부터 정확하게 몰랐다

프로젝트에서 계속

> API를 연결해야 한다.

라는 말을 사용했다.

하지만 처음에는 API가 정확히 무엇인지 설명하라고 하면 어려웠다.

내가 프로젝트를 하면서 이해한 수준에서 아주 간단하게 생각하면,

API는 **우리 서비스가 다른 서비스의 기능이나 데이터를 사용할 수 있도록 연결해 주는 방법**이었다.

탄천런이 직접 Google 계정을 관리하는 것은 아니다.

대신 Google이 제공하는 로그인 기능을 이용한다.

탄천런이 처음부터 지도 데이터를 직접 만드는 것도 아니다.

이미 지도 데이터를 가지고 있는 외부 서비스를 이용한다.

아주 단순하게 보면 이런 구조였다.

```text
탄천런
↓
외부 서비스 API
↓
Google / Kakao / 지도 서비스
```

이렇게 생각하니 API를 왜 사용하는지 조금 이해하기 쉬웠다.

---

## 소셜 로그인은 "로그인 버튼 만들기"가 아니었다

처음에는 Google 로그인 버튼이나 Kakao 로그인 버튼을 만드는 것이 소셜 로그인 구현의 대부분이라고 생각했다.

사용자가 버튼을 누르면 Google이나 Kakao 로그인 화면이 뜨고,

로그인이 성공하면 다시 탄천런으로 돌아오면 된다고 생각했다.

큰 흐름은 맞았다.

하지만 그 사이에 생각보다 많은 단계가 있었다.

대략적인 흐름은 이랬다.

```text
사용자가 Google 로그인 버튼 클릭
↓
Google 로그인 페이지로 이동
↓
사용자가 Google 계정으로 로그인
↓
Google이 사용자 확인
↓
우리 서비스로 다시 이동
↓
로그인 결과 확인
↓
탄천런에서 로그인 상태 생성
```

버튼 하나 뒤에 외부 서비스와 우리 서비스가 여러 번 정보를 주고받고 있었다.

---

## 가장 먼저 해야 했던 것은 개발자 콘솔에서 앱을 만드는 것이었다

Google이나 Kakao 로그인을 사용하고 싶다고 해서 바로 사용할 수 있는 것은 아니었다.

먼저 각 서비스의 개발자 페이지에 들어가서

**"탄천런이라는 서비스가 이 로그인 기능을 사용할 것이다."**

라는 애플리케이션을 등록해야 했다.

이 과정에서 프로젝트 이름이나 서비스 주소 같은 정보를 설정하고,

로그인 기능에 필요한 값을 발급받았다.

처음에는

> 왜 내 웹사이트를 만들고 있는데 Google에서도 또 앱을 만들어야 하지?

라는 생각이 들었다.

하지만 외부 서비스 입장에서는 아무 웹사이트나 Google 로그인을 사용할 수 있게 할 수는 없다.

어떤 서비스가 요청하는 것인지 확인해야 한다.

그래서 Google이나 Kakao 쪽에도 우리 서비스를 등록하는 과정이 필요했다.

---

## Client ID는 무엇인가?

개발자 콘솔에서 처음 받은 값 중 하나가 `Client ID`였다.

이름만 보면 무엇인지 감이 잘 오지 않았다.

내가 이해한 방식은 아주 단순하다.

**Client ID는 "로그인을 요청하는 서비스가 누구인지 알려주는 식별값"에 가까웠다.**

예를 들어 Google 입장에서는 로그인 요청이 들어왔을 때

> 이 요청이 어떤 애플리케이션에서 온 거지?

를 알아야 한다.

그때 사용하는 값 중 하나가 Client ID였다.

쉽게 비유하면

```text
탄천런의 외부 서비스용 이름표
```

처럼 생각했다.

물론 실제 동작은 더 복잡하지만 처음 개념을 이해할 때는 이 정도가 가장 편했다.

---

## Client Secret은 왜 따로 있을까?

Client ID와 함께 `Client Secret`이라는 값도 등장했다.

처음에는

> 둘 다 그냥 API Key 아닌가?

라는 생각이 들었다.

하지만 이름 그대로 Secret은 외부에 공개하면 안 되는 값이었다.

Client ID는 서비스를 구분하기 위한 값이라 브라우저에서 사용되는 경우도 있지만,

Client Secret은 서버가 외부 서비스와 통신하면서 우리 서비스임을 확인하는 데 사용되는 민감한 값이었다.

그래서 이런 값은 코드에 직접 적거나 GitHub에 올리면 안 됐다.

```text
Client ID
→ 서비스 식별에 사용

Client Secret
→ 외부에 노출되면 안 되는 비밀 값
```

이 차이를 알게 되면서 왜 환경변수를 사용하는지도 더 이해할 수 있었다.

---

## API Key, Client ID, Client Secret은 다 같은 것이 아니었다

외부 서비스를 여러 개 연결하면서 가장 헷갈렸던 부분 중 하나다.

어떤 서비스에서는 API Key라고 하고,

어떤 곳에서는 Client ID라고 하고,

Client Secret도 있었다.

처음에는 전부

**"외부 서비스 연결할 때 코드에 넣는 이상한 문자열"**

처럼 보였다.

하지만 용도가 조금씩 달랐다.

| 값             | 내가 이해한 역할                      |
| ------------- | ------------------------------ |
| API Key       | 특정 API를 사용하는 애플리케이션을 확인하기 위한 값 |
| Client ID     | OAuth에서 어떤 애플리케이션인지 구분하는 값     |
| Client Secret | 서버에서 안전하게 보관해야 하는 비밀 인증값       |

서비스마다 이름이나 사용 방식이 다르기 때문에

**이름만 보고 같은 방식으로 사용하면 안 된다는 것**

도 알게 됐다.

---

## 가장 많이 헷갈렸던 Redirect URI

소셜 로그인 설정을 하면서 가장 낯설었던 단어 중 하나가 `Redirect URI`였다.

처음에는

> 왜 로그인하는데 URL을 따로 등록하지?

라는 생각이 들었다.

소셜 로그인 과정을 따라가 보니 이유가 있었다.

Google이나 Kakao 로그인 페이지로 갔다가 로그인이 성공하면 사용자는 다시 탄천런으로 돌아와야 한다.

그렇다면 외부 서비스는

> 로그인 성공 후 이 사용자를 어디로 보내야 하지?

를 알아야 한다.

그 주소가 Redirect URI였다.

아주 단순하게 보면

```text
탄천런
↓
Google 로그인
↓
로그인 성공
↓
등록된 Redirect URI
↓
다시 탄천런
```

이라는 구조였다.

---

## Redirect URI를 아무 주소로나 설정할 수 없는 이유

처음에는 로그인 후 돌아올 주소라면 코드에서 알아서 지정하면 될 것 같았다.

하지만 외부 서비스의 개발자 콘솔에도 Redirect URI를 미리 등록해야 했다.

이유를 생각해 보면 당연했다.

만약 아무 사이트나 로그인 결과를 받을 수 있다면 사용자의 로그인 정보가 엉뚱한 사이트로 전달될 수도 있다.

그래서 외부 서비스는

**미리 허용한 주소로만 로그인 결과를 돌려보내도록 제한**

하고 있었다.

이 때문에 코드에 있는 주소와 개발자 콘솔에 등록한 주소가 정확하게 맞아야 했다.

---

## localhost와 배포 주소는 따로 등록해야 했다

개발할 때는 내 컴퓨터에서 서비스를 실행한다.

예를 들면

```text
http://localhost:3000
```

같은 주소를 사용할 수 있다.

하지만 Vercel에 배포하면 전혀 다른 주소가 생긴다.

내 입장에서는 둘 다 똑같은 탄천런이다.

하지만 Google이나 Kakao 입장에서는 서로 다른 주소다.

그래서

```text
로컬 개발 주소
배포 Preview 주소
실제 Production 주소
```

를 상황에 맞게 설정해야 했다.

이걸 모르고 있을 때는

> 로컬에서는 로그인이 되는데 왜 배포에서는 안 되지?

라는 문제가 생길 수 있었다.

---

## 코드가 똑같은데 Kakao는 되고 Google은 안 될 수도 있었다

실제로 탄천런을 배포하면서 비슷한 상황을 경험했다.

하나는 정상적으로 로그인되는데 다른 로그인은 같은 환경에서 제대로 동작하지 않았다.

처음에는 코드 문제라고 생각하기 쉬웠다.

하지만 Google과 Kakao는 서로 다른 회사의 서비스다.

각각 별도의 개발자 콘솔과 별도의 설정 규칙이 있다.

즉 탄천런 코드 하나에 로그인 버튼이 여러 개 있어도 실제로는

```text
탄천런
├─ Google 설정
└─ Kakao 설정
```

처럼 각각 따로 연결되어 있었다.

그래서 하나가 정상이라고 다른 하나도 자동으로 정상인 것은 아니었다.

이 경험 이후 외부 API 문제를 확인할 때는 우리 코드만 보지 않고 **해당 서비스의 개발자 설정도 따로 확인**하게 됐다.

---

## OAuth라는 단어도 계속 등장했다

Google이나 Kakao 로그인 설정을 하면서 `OAuth`라는 말을 계속 보게 됐다.

처음에는 매우 어려운 인증 기술처럼 느껴졌다.

실제로 OAuth에는 더 많은 개념이 있지만,

프로젝트를 처음 이해할 때 나는 이렇게 생각했다.

**사용자의 Google이나 Kakao 비밀번호를 우리 서비스가 직접 받지 않고, 해당 서비스에서 사용자를 확인한 뒤 필요한 로그인 결과만 우리에게 전달받는 방식**

이라고 이해했다.

즉 탄천런 사용자가 Google 로그인을 한다고 해서

Google 비밀번호를 탄천런 DB에 저장하는 것이 아니다.

사용자는 Google에서 로그인한다.

Google이 사용자를 확인한다.

그 결과를 이용해 탄천런에서도 로그인 상태를 만든다.

이 구조를 알고 나니 소셜 로그인을 사용하는 이유도 더 명확해졌다.

---

## 소셜 로그인 성공과 탄천런 회원 저장은 다른 문제였다

이 부분은 정말 중요했다.

처음에는 Google 로그인이 성공하면 탄천런의 회원가입도 전부 끝난 것이라고 생각했다.

하지만 실제로는 두 단계가 달랐다.

```text
Google 로그인 성공
↓
Google이 사용자를 확인함
```

여기까지와

```text
탄천런 DB에 사용자를 저장
↓
우리 서비스의 사용자 ID 생성
↓
러닝 기록과 연결
```

은 별도의 문제였다.

Google은

> 이 Google 사용자가 정상적으로 로그인했다.

라는 정보를 줄 수 있다.

하지만 탄천런에서 이 사용자를 어떤 ID로 관리하고,

닉네임은 무엇으로 저장하고,

러닝 기록은 누구에게 연결할지는 우리가 정해야 했다.

즉

**외부 로그인 성공 ≠ 우리 서비스의 사용자 데이터 구현 완료**

였다.

---

## Session도 여기서 등장했다

로그인 후에는 사용자가 페이지를 이동할 때마다 다시 Google 로그인을 하게 만들 수 없다.

서비스는

**현재 이 사용자가 로그인한 상태라는 것**

을 기억해야 한다.

이 과정에서 Session이라는 개념을 접하게 됐다.

내가 이해한 수준에서는

> 현재 로그인한 사용자가 누구인지 서비스가 계속 확인할 수 있도록 유지하는 정보

정도로 생각했다.

예를 들어 사용자가 러닝 기록을 저장하려면 서버에서는

> 지금 로그인한 사용자가 누구지?

를 알아야 한다.

그래야

```text
사용자 A
→ 사용자 A의 러닝 기록
```

처럼 연결할 수 있다.

로그인 화면 하나가 결국 DB와 러닝 기록까지 연결되는 이유였다.

---

## 외부 로그인 ID와 우리 서비스 사용자 ID도 달랐다

Google에서는 Google만의 사용자 식별값이 있을 수 있고,

Kakao에는 Kakao의 사용자 식별값이 있다.

하지만 탄천런 내부에서도 사용자를 구분하기 위한 ID가 필요하다.

예를 들어 아주 단순하게 생각하면

```text
Google 사용자 정보
↓
탄천런 사용자
↓
탄천런 user_id
↓
러닝 기록
```

같은 흐름이다.

이 과정에서

**외부 서비스 계정과 우리 서비스 사용자를 어떻게 연결할 것인가**

라는 문제가 생긴다는 것도 처음 알게 됐다.

로그인 버튼을 구현하는 것보다 훨씬 뒤에 있는 문제였다.

---

## 지도 API도 키만 넣으면 끝인 줄 알았다

소셜 로그인과 비슷하게 지도도 처음에는 단순하게 생각했다.

지도 API Key를 발급받아 코드에 넣으면 바로 지도가 나올 것 같았다.

하지만 지도 서비스 역시 우리 서비스를 등록하고,

사용할 기능을 설정하고,

필요하다면 허용할 웹 주소를 등록해야 했다.

특히 배포까지 고려하면

```text
localhost
Preview 주소
Production 주소
```

가 각각 지도 서비스 설정에서 문제가 없는지도 확인해야 했다.

소셜 로그인에서 Redirect URI가 중요했다면,

지도에서는 **API를 사용할 수 있도록 허용한 도메인이나 서비스 설정**이 중요했다.

---

## 지도가 화면에 보이는 것과 위치 기능이 완성된 것은 아니었다

처음 화면에 지도가 나타났을 때는 지도 기능이 거의 완성된 것처럼 느껴졌다.

하지만 탄천런에서 필요한 것은 단순한 지도 화면이 아니었다.

러닝 서비스이기 때문에 사용자의 현재 위치를 알아야 했다.

그리고 사용자가 움직이면 그 위치도 계속 바뀐다.

탄천런에서는 더 나아가 사용자가 달린 거리가 탄천 구역 안인지도 판단해야 했다.

그래서 단계가 나뉘었다.

```text
지도 화면 표시
↓
현재 위치 확인
↓
현재 위치를 지도에 표시
↓
이동 위치 기록
↓
이동 거리 계산
↓
탄천 구역 여부 판단
↓
탄천 인정 거리 계산
```

처음에는 이것을 모두

**"지도 기능"**

이라고 한 번에 생각했다.

실제로는 여러 기능이 연결된 것이었다.

---

## 지도와 GPS도 같은 것이 아니었다

처음에는 지도에서 현재 위치를 보여주니까 지도 API가 내 GPS 위치까지 전부 만들어주는 것처럼 느껴질 수 있었다.

하지만 역할은 달랐다.

내가 이해한 방식은 이렇다.

```text
위치 정보 / GPS
→ 내가 현재 어디에 있는지 확인

지도 API
→ 그 위치를 사용자가 보기 쉽게 지도 위에 표시
```

즉 위치를 얻는 것과 지도를 그리는 것은 서로 연결되어 있지만 같은 기능은 아니었다.

탄천런에서는 두 기능이 모두 필요했다.

---

## 탄천 구역 안인지 판단하는 것은 또 다른 로직이었다

현재 위치를 알았다고 해서 자동으로

> 지금 탄천 안에 있다.

라는 결과가 나오는 것도 아니었다.

먼저 우리가 탄천으로 인정할 구역이 어디인지 정의해야 한다.

그리고 사용자의 위치가 그 구역 안에 있는지 확인해야 한다.

그다음 해당 구역 안에서 이동한 거리만 따로 누적해야 했다.

전체 흐름을 단순하게 정리하면

```text
GPS 위치
↓
현재 좌표
↓
탄천 지정 구역과 비교
↓
구역 내부인지 판단
↓
구역 내부 이동 거리만 누적
```

이라는 별도 로직이 필요했다.

이걸 이해하면서 지도 화면과 실제 탄천 인정 거리 계산은 완전히 다른 영역이라는 것도 알게 됐다.

---

## "지도에 점이 보인다"와 "러닝 기록이 된다"도 달랐다

지도에 현재 위치 표시까지 성공하면 기능이 많이 완성된 것처럼 보인다.

하지만 실제 러닝 기록을 만들려면 이전 위치와 현재 위치를 비교해서 이동 거리도 계산해야 한다.

또 GPS 값이 이상하게 튀거나 위치를 제대로 가져오지 못하는 상황도 생각해야 한다.

탄천런에서는 러닝 시작 전에 GPS 상태를 확인하고,

진행 중에도 GPS 문제를 사용자에게 알려주는 흐름을 생각했다.

그래서 지도는 단순한 시각적인 기능이 아니라 러닝 기록 계산과 연결된 중요한 입력값이기도 했다.

---

## API 권한도 필요한 기능만 선택해야 했다

외부 서비스를 등록할 때 여러 권한이나 기능 선택지가 보였다.

처음에는

> 다 켜두면 나중에 편하지 않을까?

라고 생각할 수 있다.

하지만 필요하지 않은 권한까지 요청하는 것은 좋지 않았다.

예를 들어 소셜 로그인에서 우리 서비스에 필요하지 않은 사용자 정보까지 요청할 이유는 없다.

지도 API도 사용하지 않는 기능까지 전부 켤 필요는 없다.

이 경험을 통해 외부 API를 사용할 때는

**"무엇을 받을 수 있는가?"보다 "우리 서비스에 무엇이 실제로 필요한가?"**

를 먼저 생각해야 한다는 것을 알게 됐다.

---

## 키를 코드에 직접 넣으면 안 되는 이유도 체감했다

처음에는 API Key를 발급받으면 코드에 그대로 넣으면 가장 쉬워 보였다.

하지만 GitHub에 코드를 올리는 프로젝트에서 이런 방식은 위험하다.

Client Secret 같은 값이 GitHub에 올라가면 다른 사람이 볼 수도 있기 때문이다.

그래서 환경변수를 사용했다.

예를 들면

```text
코드
→ GOOGLE_CLIENT_ID라는 이름만 사용

실제 값
→ .env 또는 Vercel Environment Variables에 저장
```

하는 식이다.

앞의 Vercel 글에서 환경변수를 자세히 다뤘지만,

외부 API를 사용해 보면서 **왜 Secret을 코드와 분리해야 하는지를 실제로 체감**할 수 있었다.

---

## API 키마다 공개 가능한 범위도 달랐다

모든 키가 똑같이 비밀인 것도 아니었다.

브라우저에서 지도 기능을 사용하기 위해 클라이언트에 노출되는 키가 있을 수도 있고,

반대로 서버에서만 사용해야 하는 Client Secret도 있다.

그래서 단순히

> API Key니까 전부 숨겨야 한다.

또는

> 코드에 들어가는 값이니까 다 공개해도 된다.

처럼 생각하면 안 됐다.

각 서비스의 설명을 확인해서

**어디에서 사용하도록 만들어진 값인지**

구분해야 했다.

특히 Secret이라는 이름이 붙은 값은 공개 저장소에 올라가지 않도록 더 조심해야 했다.

---

## 외부 API는 설정하는 곳이 너무 많아서 헷갈렸다

프로젝트 중 실제로 가장 힘들었던 부분 중 하나였다.

예를 들어 Google 로그인 하나만 봐도 설정 위치가 여러 곳이었다.

```text
Google 개발자 콘솔
+
우리 프로젝트 코드
+
로컬 환경변수
+
Vercel 환경변수
+
Redirect URI
```

Kakao도 별도의 개발자 페이지가 있다.

지도 API도 별도의 콘솔이 있다.

처음에는

> 분명 설정했는데 왜 안 되지?

라는 일이 반복됐다.

나중에는 **설정을 했는지가 아니라 어디에 설정했는지**를 확인하는 것이 중요하다는 것을 알게 됐다.

---

## 문제가 생겼을 때 코드부터 고치면 오히려 꼬일 수 있었다

외부 API 기능이 동작하지 않으면 가장 먼저 코드를 의심했다.

그래서 Claude에게

> 로그인 코드 고쳐줘.

라고 바로 요청하고 싶을 때가 많았다.

하지만 코드에는 문제가 없고 개발자 콘솔의 URL 설정 하나가 빠진 경우도 있었다.

이 상태에서 코드를 계속 수정하면 원래 정상인 코드까지 바뀔 수 있다.

그래서 나중에는 문제가 생기면 단계별로 확인하려고 했다.

```text
1. 외부 서비스 앱이 제대로 만들어졌는가?
2. 필요한 기능이 활성화되어 있는가?
3. 올바른 Client ID / Key를 사용하고 있는가?
4. Redirect URI 또는 허용 도메인이 맞는가?
5. 환경변수가 현재 환경에 들어 있는가?
6. 코드가 해당 환경변수를 제대로 읽는가?
7. 실제 요청에서 어떤 오류가 나는가?
```

이 순서로 확인하면 무작정 코드를 변경하는 것보다 안전했다.

---

## 소셜 로그인 테스트도 단계별로 볼 필요가 있었다

처음에는

> 로그인 된다 / 안 된다

두 가지 상태만 생각했다.

하지만 실제로는 여러 단계가 있었다.

예를 들어

```text
로그인 버튼 클릭 가능
↓
Google/Kakao 페이지 이동
↓
외부 서비스 로그인 성공
↓
우리 Callback으로 정상 복귀
↓
Session 생성
↓
사용자 정보 확인
↓
우리 DB 사용자와 연결
↓
로그인 후 기능 사용
```

어느 단계에서 실패하는지에 따라 원인이 완전히 달랐다.

외부 로그인 페이지 자체가 열리지 않는 것과,

로그인은 됐는데 우리 사이트로 돌아오지 못하는 것은 다른 문제다.

사이트로 돌아왔는데 DB에 사용자가 없는 것도 또 다른 문제다.

이렇게 나누어 생각하기 시작하면서 오류를 조금 더 정확하게 설명할 수 있었다.

---

## "API 연결 완료"라는 말도 애매했다

데이터베이스 글에서도 비슷하게 느꼈지만 외부 API에서도 마찬가지였다.

누군가

> Google API 연결 끝났습니다.

라고 말했을 때 어디까지 끝난 것인지 확인할 필요가 있다.

예를 들어

* 개발자 콘솔 앱 생성
* Client ID 발급
* 환경변수 등록
* 로그인 페이지 이동 성공
* 로그인 후 Callback 성공
* Session 확인
* 사용자 DB 저장
* 배포 환경 테스트

가 전부 다른 단계다.

그래서 나중에는

**"연결 완료"라고 한 번에 표현하기보다 어느 단계까지 검증했는지를 말하는 것이 더 정확하다**

고 느꼈다.

---

## 소셜 로그인과 지도 API는 공통점이 많았다

처음에는 완전히 다른 기능이라고 생각했다.

하나는 로그인이고 하나는 지도이기 때문이다.

하지만 직접 연결하면서 공통적인 흐름이 보였다.

```text
외부 서비스에서 앱 등록
↓
키 또는 ID 발급
↓
우리 서비스 주소 등록
↓
환경변수 설정
↓
코드에서 사용
↓
로컬 테스트
↓
배포 환경 테스트
```

기능은 다르지만 **외부 서비스를 우리 프로젝트 안으로 가져오는 기본 흐름**은 비슷했다.

한 번 이 구조를 이해하니 새로운 API를 연결할 때도 무엇부터 확인해야 할지 조금 감이 생겼다.

---

## 자주 헷갈렸던 용어를 정리해보면

이번 프로젝트에서 소셜 로그인과 지도 API를 설정하면서 자주 봤던 용어를 내 기준으로 정리하면 이렇다.

| 용어            | 내가 이해한 의미                                    |
| ------------- | -------------------------------------------- |
| API           | 다른 서비스의 기능이나 데이터를 우리 서비스에서 사용할 수 있도록 연결하는 방법 |
| API Key       | API를 사용하는 애플리케이션을 식별하기 위한 값                  |
| Client ID     | OAuth에서 우리 애플리케이션을 구분하는 값                    |
| Client Secret | 외부에 공개하면 안 되는 서버용 비밀 값                       |
| OAuth         | 외부 서비스가 사용자를 인증하고 그 결과를 우리 서비스에서 이용하는 방식     |
| Redirect URI  | 외부 로그인 성공 후 다시 돌아올 우리 서비스 주소                 |
| Callback      | 외부 인증 결과를 우리 서비스가 받아 처리하는 단계나 주소             |
| Domain        | 서비스가 실행되는 웹 주소                               |
| Session       | 현재 로그인한 사용자가 누구인지 유지하기 위한 정보                 |
| GPS           | 현재 위치 정보를 얻는 기능                              |
| Map API       | 지도 화면이나 지도 관련 기능을 제공하는 외부 API                |

처음에는 이 단어들이 한꺼번에 등장해서 너무 복잡했다.

하지만 실제 로그인 흐름과 지도 흐름에 하나씩 넣어보니 서로의 역할이 조금씩 보였다.

---

## 처음 생각했던 소셜 로그인과 실제 구현 과정

처음에는 이렇게 생각했다.

```text
로그인 버튼
↓
Google / Kakao 로그인
↓
완료
```

실제로는 훨씬 많은 단계가 있었다.

```text
외부 개발자 콘솔에서 앱 생성
↓
Client ID / Secret 발급
↓
Redirect URI 설정
↓
환경변수 등록
↓
프로젝트 코드와 연결
↓
로그인 버튼
↓
외부 로그인
↓
Callback
↓
Session 생성
↓
우리 사용자 정보와 연결
↓
로그인한 사용자의 기능 사용
```

로그인 화면 하나 뒤에 이렇게 많은 과정이 있다는 것을 처음 알았다.

---

## 처음 생각했던 지도 기능과 실제 구현 과정

지도도 비슷했다.

처음에는 이렇게 생각했다.

```text
지도 API 연결
↓
지도 표시
↓
완료
```

하지만 탄천런에서 필요했던 실제 흐름은 훨씬 길었다.

```text
지도 서비스 앱 등록
↓
Key 발급
↓
허용 도메인 설정
↓
지도 화면 표시
↓
현재 위치 가져오기
↓
지도에 위치 표시
↓
위치 변화 추적
↓
이동 거리 계산
↓
탄천 구역 여부 판단
↓
탄천 인정 거리 계산
↓
러닝 기록 저장
```

**지도는 화면의 배경이 아니라 러닝 데이터를 만들기 위한 기능의 일부**였다.

---

## 이번 프로젝트에서 배운 것

탄천런 이전에는 외부 API 연동을

**"키 받아서 코드에 넣는 작업"**

정도로 생각했다.

직접 해보니 외부 서비스를 연결하는 과정에는 코드보다 설정이 더 중요한 경우도 있었다.

Client ID가 맞아야 하고,

Secret을 안전하게 관리해야 하고,

Redirect URI가 정확해야 하고,

localhost와 배포 주소를 각각 생각해야 하고,

외부 로그인 결과를 다시 우리 서비스 데이터와 연결해야 했다.

지도 역시 화면에 띄우는 것과 실제 위치 데이터를 이용하는 것이 전혀 다른 단계였다.

---

## 다음 프로젝트에서는 어떻게 할 것인가

다음에 외부 API를 연결한다면 처음부터 다음 내용을 먼저 정리할 것 같다.

| 확인 항목         | 내용                                      |
| ------------- | --------------------------------------- |
| 사용할 서비스       | 어떤 외부 서비스를 사용할 것인가                      |
| 필요한 기능        | 그 서비스에서 어떤 기능만 사용할 것인가                  |
| 필요한 Key       | API Key / Client ID / Secret 중 무엇이 필요한가 |
| 로컬 주소         | localhost에서 어떤 URL을 사용하는가               |
| Preview 주소    | 테스트 배포에서는 어떤 주소를 사용하는가                  |
| Production 주소 | 실제 서비스 주소는 무엇인가                         |
| 허용 주소         | Redirect URI / Domain 등록이 필요한가          |
| 환경변수          | 어느 값을 어디에 저장해야 하는가                      |
| 검증 기준         | 어디까지 되어야 연동 완료라고 볼 것인가                  |

그리고 무언가 동작하지 않는다고 바로 코드를 수정하지 않을 것이다.

**외부 서비스 설정 → 환경변수 → URL → 코드 → 데이터 연결**

순서로 어느 단계까지 정상인지 먼저 확인할 것 같다.

---

## API를 붙이는 것보다 흐름을 이해하는 것이 더 중요했다

탄천런에서 Google, Kakao 로그인과 지도 기능을 연결하면서 처음에는 키와 설정값만 따라 입력하기 바빴다.

어떤 값을 어디에 넣어야 하는지 몰라 하나씩 확인했다.

하지만 프로젝트가 진행되면서 조금씩 전체 흐름이 보이기 시작했다.

소셜 로그인은

**외부 서비스에서 사용자를 확인하고 → 다시 탄천런으로 돌아오고 → 그 사용자를 우리 서비스의 데이터와 연결하는 과정**

이었다.

지도는

**외부 지도 서비스를 화면에 보여주고 → 실제 위치 정보를 받아 → 탄천런의 러닝 데이터로 바꾸는 과정**

이었다.

처음에는 각각의 콘솔 설정과 키 이름만 보느라 복잡하게 느껴졌다.

결국 가장 중요했던 것은 키 이름을 외우는 것이 아니었다.

**외부 서비스에서 받은 정보가 우리 서비스 안에서 어디까지 들어오고, 그다음 어떤 기능과 연결되는지를 이해하는 것**이었다.
