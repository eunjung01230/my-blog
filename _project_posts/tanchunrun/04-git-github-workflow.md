탄천런을 시작하기 전에도 Git과 GitHub를 아예 처음 보는 것은 아니었다.

`commit`, `push`, `branch` 같은 단어는 알고 있었고, GitHub에 코드를 올려본 경험도 있었다.

그래서 팀 프로젝트를 시작할 때는 Git도 크게 어렵지 않을 것이라고 생각했다.

처음 내가 알고 있던 흐름은 대략 이 정도였다.

> 브랜치를 만든다.
> 코드를 수정한다.
> commit한다.
> push한다.
> Pull Request를 만든다.

순서만 보면 어렵지 않아 보였다.

하지만 네 명이 동시에 하나의 저장소에서 작업하기 시작하니 Git은 단순히 코드를 저장하는 도구가 아니었다.

**내가 지금 어떤 코드를 기준으로 작업하고 있는지, 내 변경사항은 어디까지 올라가 있는지, 다른 사람의 변경사항은 내 컴퓨터에 들어와 있는지 계속 확인해야 하는 협업 도구**에 가까웠다.

프로젝트를 진행하면서 가장 많이 했던 질문도 이런 것이었다.

> 지금 이게 local에만 있는 건가?

> push했으면 팀원도 볼 수 있는 건가?

> PR을 또 만들어야 하나?

> main하고 origin/main은 왜 따로 있는 거지?

> merge했는데 왜 내 컴퓨터에는 예전 코드가 있지?

처음에는 각각 다른 문제처럼 느껴졌다.

하지만 여러 번 작업하다 보니 결국 모두 **Git의 각 단계가 어디에서 일어나는지를 정확하게 구분하지 못해서 생긴 혼란**이었다.

---

## 처음 가장 헷갈렸던 것은 Git과 GitHub의 차이였다

처음에는 Git과 GitHub를 거의 같은 것으로 생각했다.

둘 다 코드를 저장하고 관리하는 도구라고 생각했기 때문이다.

하지만 실제로 사용하면서 역할이 조금 다르다는 것을 알게 됐다.

Git은 내 컴퓨터에서 코드 변경 기록을 관리한다.

GitHub는 그 Git 저장소를 인터넷의 원격 저장소에 올려서 다른 사람과 함께 사용할 수 있게 해준다.

아주 단순하게 생각하면 나는 이렇게 이해하게 됐다.

| 구분     | 내가 이해한 역할        |
| ------ | ---------------- |
| Git    | 내 컴퓨터에서 변경 기록 관리 |
| GitHub | 팀원과 공유하는 원격 저장소  |

이 차이를 이해하니 이후에 헷갈렸던 많은 단어들이 조금씩 정리되기 시작했다.

---

## Commit했다고 GitHub에 올라간 것은 아니었다

처음에는 `commit`을 하면 작업이 저장된 것이니 GitHub에서도 바로 보이는 줄 알았다.

하지만 commit은 우선 **내 로컬 Git 저장소에 변경 기록을 남기는 작업**이었다.

예를 들어 코드를 수정하고

```text
commit 완료
```

상태가 되더라도 아직 GitHub에는 그 commit이 없을 수 있다.

GitHub 원격 저장소까지 보내기 위해서는 `push`가 필요했다.

그래서 흐름을 이렇게 구분하게 됐다.

```text
파일 수정
↓
commit
↓
내 컴퓨터의 Git 기록에 저장됨
↓
push
↓
GitHub 원격 저장소에 올라감
```

이걸 이해하기 전에는

> commit했는데 왜 팀원이 안 보이지?

같은 상황이 헷갈릴 수 있었다.

프로젝트를 진행하면서 **commit과 push는 같은 저장 작업이 아니라 저장되는 위치가 다르다**는 것을 확실히 알게 됐다.

---

## Push했다고 main에 들어간 것도 아니었다

다음으로 헷갈렸던 부분이었다.

내 브랜치에서 작업한 뒤 push까지 성공하면 GitHub에도 코드가 올라간다.

처음에는 여기까지 하면 팀 프로젝트에 코드가 반영된 것처럼 느껴졌다.

하지만 실제로는 내가 작업한 **브랜치가 GitHub에 올라간 것**일 뿐이었다.

예를 들어 내가

```text
feature/settings
```

라는 브랜치에서 작업했다면,

push 후에도 코드는 `feature/settings`에 있다.

팀이 사용하는 `main`이나 `develop`에 자동으로 들어가는 것이 아니다.

그래서 그다음 Pull Request가 필요했다.

내가 이해한 흐름은 이렇게 바뀌었다.

```text
내 브랜치에서 작업
↓
commit
↓
push
↓
GitHub에 내 브랜치가 생김
↓
Pull Request 생성
↓
리뷰
↓
merge
↓
공용 브랜치에 반영
```

이걸 이해하고 나니

**push와 merge 사이에 왜 PR이 있는지**

조금씩 이해할 수 있었다.

---

## Pull Request는 "코드를 올리는 것"이 아니었다

처음에는 PR도 단순히 코드를 GitHub에 올리는 과정이라고 생각했다.

하지만 코드는 이미 push 단계에서 GitHub에 올라가 있다.

PR은 그 코드를

> 이 변경사항을 공용 브랜치에 합쳐도 될까요?

라고 팀에 보여주는 과정에 가까웠다.

그래서 Pull Request에서는 단순히 코드만 보는 것이 아니라

* 어떤 Issue를 구현했는지
* 어떤 파일이 바뀌었는지
* 왜 이렇게 수정했는지
* 테스트는 했는지
* 아직 확인하지 못한 부분은 있는지

등을 같이 확인했다.

PR을 여러 번 만들면서 점점

**PR은 업로드 버튼이 아니라 변경사항을 검토하고 합의하기 위한 공간**

이라고 생각하게 됐다.

---

## 기존 PR을 수정할 때 새 PR을 만들 필요가 없었다

프로젝트를 진행하면서 정말 많이 헷갈렸던 부분 중 하나였다.

PR을 만들었는데 리뷰를 받고 수정할 부분이 생겼다.

처음에는

> PR을 이미 만들었으니 수정한 코드는 새 PR을 만들어야 하나?

라고 생각했다.

하지만 같은 작업 브랜치에서 수정한 뒤 다시 commit하고 push하면 기존 Pull Request에 새로운 commit이 자동으로 추가됐다.

예를 들어

```text
feature/settings
↓
commit A
↓
push
↓
PR 생성
```

한 상태에서 리뷰를 받고 수정했다면

```text
feature/settings
↓
추가 수정
↓
commit B
↓
같은 브랜치로 push
```

하면 된다.

그러면 기존 PR 안에 `commit B`도 같이 들어간다.

처음 이 구조를 이해하지 못했을 때는 PR을 수정해야 할지 새로 만들어야 할지 계속 헷갈렸다.

직접 몇 번 해보고 나서야

**PR은 특정 commit 하나가 아니라 브랜치의 변경 흐름을 보고 있다는 것**

을 이해하게 됐다.

---

## main과 origin/main은 같은 것인 줄 알았다

처음 Git을 사용할 때 특히 어려웠던 개념이었다.

터미널에서 보면

```text
main
origin/main
```

이 둘이 따로 보인다.

처음에는

> 둘 다 main인데 왜 두 개지?

라는 생각이 들었다.

내가 이해한 방식은 다음과 같다.

`main`은 **내 컴퓨터에 있는 main 브랜치**다.

`origin/main`은 **GitHub 원격 저장소에 있는 main을 내 Git이 기억하고 있는 상태**다.

즉 장소가 다르다.

```text
내 컴퓨터
└─ main

GitHub
└─ main
```

Git에서는 GitHub 원격 저장소를 보통 `origin`이라고 부르기 때문에 GitHub의 main을 가리키는 이름으로 `origin/main`이 보인다.

이 개념을 알고 나니 왜 작업 전에 최신 main을 받아와야 하는지도 이해하기 쉬워졌다.

---

## GitHub의 main이 최신이어도 내 main은 예전일 수 있었다

팀원이 PR을 merge하면 GitHub의 main은 바뀐다.

하지만 그렇다고 내 컴퓨터의 main까지 자동으로 바뀌는 것은 아니었다.

예를 들어 GitHub에서는

```text
A → B → C
```

까지 main에 들어가 있는데,

내 컴퓨터는 아직

```text
A → B
```

상태일 수 있다.

그 상태에서 새로운 기능 브랜치를 만들면 나는 최신 `C`가 없는 코드에서 작업을 시작하는 것이 된다.

이것이 나중에 충돌이나 예상하지 못한 문제로 이어질 수 있었다.

그래서 새 작업을 시작하기 전에 main을 최신 상태로 맞추는 과정이 중요했다.

---

## 새 작업을 시작하기 전에 main부터 확인하게 됐다

프로젝트 초반에는 기능 구현부터 바로 시작하고 싶었다.

하지만 여러 번 작업하면서 작업 전 확인이 더 중요하다는 것을 알게 됐다.

나중에는 새로운 Issue를 시작하기 전 먼저 현재 상태를 확인하도록 했다.

대표적으로 확인했던 것은 이런 것들이었다.

```text
현재 어떤 브랜치에 있는가?
↓
수정 중인 파일이 남아 있는가?
↓
원격 저장소가 올바른 저장소인가?
↓
local main이 최신인가?
↓
그다음 새 작업 브랜치를 만든다
```

특히 수정 중인 파일이 있는 상태에서 무작정 브랜치를 바꾸거나 pull을 하는 것은 위험할 수 있었다.

그래서 `git status`를 자주 확인하게 됐다.

초기에는 main 중심으로 진행했지만, 협업 과정에서 9월 15일부터 feature → develop → main 구조로 변경했다.

---

## git status가 생각보다 중요했다

처음에는 `git status`를 단순히 참고용 명령어라고 생각했다.

하지만 팀 프로젝트를 하면서 가장 자주 확인한 명령어 중 하나가 됐다.

`git status`를 보면 현재

* 수정한 파일이 있는지
* 아직 commit하지 않은 파일이 있는지
* 현재 브랜치가 원격보다 앞서 있는지
* 원격과 같은 상태인지

등을 확인할 수 있다.

특히 Claude Code에게 Git 작업을 맡길 때도 먼저 상태를 확인하게 했다.

예를 들어 작업 시작 전에 수정된 파일이 이미 있는데 Claude가 모르고 새로운 작업을 시작하면 기존 작업과 섞일 수 있었다.

그래서

> working tree에 기존 변경사항이 있으면 임의로 stash하거나 reset하지 말고 멈춰서 알려줘.

같은 조건을 자주 사용하게 됐다.

---

## 왜 기존 변경사항이 있으면 함부로 건드리면 안 될까?

처음에는 변경사항이 있으면 그냥 잠깐 치우고 작업하면 되는 것 아닌가 생각할 수 있다.

하지만 그 변경사항이 내가 이전에 작업하던 중요한 코드일 수도 있고, 다른 작업 중 생긴 파일일 수도 있다.

Claude나 Git 명령어가 그것을 자동으로 정리해버리면 내가 의도하지 않은 코드가 사라질 수도 있다.

그래서 팀 프로젝트를 하면서

* 임의 `reset` 금지
* 임의 `stash` 금지
* 임의 파일 삭제 금지
* 충돌이 생기면 먼저 확인

같은 조건을 중요하게 생각하게 됐다.

Git에서 무언가를 빠르게 해결하는 것보다 **현재 변경사항을 잃지 않는 것이 더 중요할 때가 많았다.**

---

## 작업마다 브랜치를 새로 만드는 이유를 이해하게 됐다

처음에는 기능 하나를 만들고 merge한 다음 또 새로운 브랜치를 만드는 과정이 조금 번거롭게 느껴졌다.

그냥 하나의 브랜치에서 여러 기능을 계속 만들면 더 편해 보였다.

하지만 그렇게 하면 여러 기능의 변경사항이 한곳에 섞이게 된다.

예를 들어 같은 브랜치에서

```text
설정 화면
+
지도 기능
+
로그인 수정
```

을 모두 작업했다고 생각해보면,

나중에 설정 화면만 먼저 merge하고 싶어도 분리하기 어렵다.

반대로 기능마다 브랜치를 나누면

```text
feature/settings
feature/map
feature/login
```

처럼 각각의 작업을 따로 검토할 수 있다.

한 기능에 문제가 생겨도 다른 기능까지 함께 영향을 받지 않는다.

탄천런을 하면서 기능별 브랜치가 단순한 규칙이 아니라 **작업을 분리해서 안전하게 관리하는 방법**이라는 것을 이해하게 됐다.

---

## Issue와 Branch를 같이 보니 작업 범위가 더 명확해졌다

탄천런에서는 GitHub Issue 단위로 작업을 많이 나눴다.

그래서 브랜치도 해당 Issue에서 해야 하는 기능과 연결해서 사용하는 것이 편했다.

내 입장에서는 이렇게 연결해서 이해하기 시작했다.

```text
Issue
↓
이번에 해야 할 일 정의

Branch
↓
그 일을 실제로 구현하는 독립된 작업 공간

Commit
↓
작업 중 의미 있는 변경 기록

Push
↓
GitHub에 작업 공유

Pull Request
↓
공용 코드에 합칠 수 있는지 검토

Merge
↓
공용 브랜치에 실제 반영
```

처음에는 각각 따로 외웠던 단어들이 실제 프로젝트 안에서 하나의 흐름으로 연결되기 시작했다.

---

## Merge됐다고 내 로컬 코드도 자동으로 바뀌는 것은 아니었다

PR이 성공적으로 merge되면 작업이 끝난 것처럼 느껴진다.

GitHub에서는 실제로 공용 브랜치에 반영된 상태다.

하지만 다시 문제가 하나 생겼다.

내 로컬 main은 여전히 merge 전 상태일 수 있었다.

그래서 다음 작업을 시작하기 전에 다시 GitHub의 최신 상태를 받아와야 했다.

이 과정을 여러 번 반복하면서

**원격에서 merge되는 것과 내 컴퓨터가 최신 상태가 되는 것은 별개의 작업**

이라는 것을 이해하게 됐다.

---

## pull도 그냥 아무 때나 하면 되는 것이 아니었다

처음에는 최신 코드를 받으려면 그냥 `git pull`을 사용하면 된다고 생각했다.

하지만 작업 중인 변경사항이 있는 상태에서 pull을 하면 예상하지 못한 충돌이 생길 수 있다.

그래서 먼저 현재 상태를 확인하는 것이 중요했다.

탄천런 작업에서는 main을 최신으로 맞출 때

```bash
git switch main
git fetch origin
git pull --ff-only origin main
```

같은 흐름을 사용하기도 했다.

처음에는 `--ff-only`가 무엇인지 몰랐다.

간단하게 이해하면 **필요하지 않은 merge commit을 Git이 임의로 만들지 말고, 깔끔하게 앞으로 이동할 수 있을 때만 pull하라는 조건**이었다.

만약 단순하게 최신 상태로 이동할 수 없는 상황이면 Git이 자동으로 복잡한 병합을 하는 대신 멈춘다.

초보자인 내 입장에서는 오히려 이런 방식이 안전했다.

문제가 생기면 Git이 알아서 처리하게 두기보다 내가 상태를 확인할 수 있었기 때문이다.

---

## fetch와 pull도 처음에는 같은 것처럼 느껴졌다

둘 다 GitHub의 최신 코드를 가져오는 명령어처럼 보였다.

하지만 사용하면서 차이를 알게 됐다.

`fetch`는 원격 저장소의 최신 정보를 가져와서 **원격에 어떤 변화가 있는지 확인할 수 있게 해준다.**

반면 `pull`은 그 내용을 가져와 **현재 로컬 브랜치에도 실제로 반영한다.**

아주 단순하게 이해하면 나는 이렇게 생각했다.

```text
fetch
= GitHub에 뭐가 바뀌었는지 가져와서 확인

pull
= 그 변경사항을 내 현재 브랜치에도 반영
```

정확한 내부 동작은 더 복잡하지만, 프로젝트를 처음 이해할 때는 이 정도 구분만 해도 많은 혼란이 줄었다.

---

## 실제로 local과 origin/main이 같은지도 확인했다

처음에는

> pull 성공했습니다.

라는 메시지가 나오면 그냥 최신 상태라고 생각했다.

하지만 나중에는 실제 commit 값을 비교하기도 했다.

예를 들어

```bash
git rev-parse HEAD
git rev-parse origin/main
```

을 실행하면 각각 현재 local HEAD와 `origin/main`이 가리키는 commit을 볼 수 있다.

두 값이 같다면

```text
local main = origin/main
```

인 상태라고 확인할 수 있었다.

처음에는 이런 확인까지 해야 하나 싶었지만, 여러 사람이 동시에 작업하는 팀 프로젝트에서는 **"아마 최신일 것이다"보다 직접 확인하는 것이 훨씬 안전했다.**

---

## PR 리뷰를 받고 수정하는 과정도 처음에는 낯설었다

PR을 만들었다고 바로 merge되는 것은 아니었다.

다른 사람이 코드를 확인하고 수정 요청을 할 수도 있었다.

처음에는 수정 요청이 오면

> 기존 PR을 닫아야 하나?

> 브랜치를 다시 만들어야 하나?

> 새 PR을 만들어야 하나?

같은 생각이 들었다.

하지만 같은 작업이라면 기존 브랜치에서 계속 수정하면 됐다.

이 과정을 반복하면서 PR은 한 번 만들어 놓고 끝나는 문서가 아니라 **작업이 완성될 때까지 계속 업데이트될 수 있는 공간**이라는 것을 알게 됐다.

---

## Approve와 Request Changes도 실제로 써보면서 이해했다

GitHub에서 Pull Request를 리뷰할 때

* Approve
* Comment
* Request changes

같은 선택지가 있었다.

처음에는 버튼 이름만 보고 정확한 차이를 이해하기 어려웠다.

실제로 리뷰를 진행해 보면서

`Approve`는 현재 변경사항을 합쳐도 괜찮다고 보는 경우,

`Request changes`는 merge 전에 수정이 필요하다고 보는 경우라는 것을 이해했다.

즉 코드 리뷰도 단순한 댓글이 아니라 **이 작업이 현재 공용 코드에 들어가도 되는지 판단하는 과정**이었다.

---

## Squash Merge를 사용한 이유도 알게 됐다

작업 브랜치에는 commit이 여러 개 생길 수 있다.

예를 들어 하나의 기능을 만들면서

```text
기본 화면 구현
수정
오류 수정
리뷰 반영
마지막 정리
```

처럼 여러 commit이 생길 수 있다.

이 commit을 그대로 main에 모두 남길 수도 있지만, 탄천런에서는 squash merge를 사용하기도 했다.

Squash merge는 작업 브랜치의 여러 commit을 하나의 commit으로 합쳐 main에 넣는 방식이다.

내 입장에서는

```text
작업 과정의 여러 작은 기록
↓
하나의 기능 단위 기록
```

으로 정리하는 느낌이었다.

덕분에 main의 commit 기록을 봤을 때 어떤 기능이 들어왔는지 비교적 확인하기 쉬웠다.

---

## GitHub에 있는 코드와 VS Code에 있는 코드가 다를 수 있었다

이것도 처음에는 꽤 이상하게 느껴졌다.

GitHub 웹사이트에서 확인한 코드는 최신인데 VS Code에서는 예전 코드가 보이는 경우가 있었다.

처음에는

> GitHub가 잘못된 건가?

> VS Code가 새로고침되지 않은 건가?

라고 생각하기 쉬웠다.

하지만 대부분은 내 로컬 브랜치가 아직 최신 원격 상태를 받아오지 않은 경우였다.

GitHub와 VS Code가 같은 저장소를 보고 있어도 **한쪽은 원격이고 한쪽은 로컬**이라는 차이를 이해하고 나니 자연스러운 상황이었다.

---

## Git을 사용할 때 명령어보다 현재 상태가 더 중요했다

프로젝트 초반에는 Git 문제를 해결하려고 할 때 가장 먼저 명령어를 찾았다.

> 어떤 명령어를 입력해야 하지?

를 먼저 생각했다.

하지만 프로젝트가 진행될수록 순서가 바뀌었다.

먼저

> 지금 어느 브랜치인가?

> 수정 중인 파일이 있는가?

> commit은 되어 있는가?

> push는 되어 있는가?

> PR은 만들어져 있는가?

> merge는 되었는가?

> local과 원격 중 어느 쪽이 최신인가?

를 확인했다.

그다음에 필요한 명령어를 선택하는 것이 더 안전했다.

**Git에서는 명령어를 많이 외우는 것보다 현재 상태를 정확하게 이해하는 것이 중요했다.**

---

## Claude Code를 사용할 때 Git 상태 확인을 더 강조한 이유

탄천런에서는 Claude Code에게 Git 작업도 많이 요청했다.

AI가 명령어를 대신 실행해 줄 수 있기 때문에 편했다.

하지만 그만큼 위험한 부분도 있었다.

Claude가 현재 브랜치를 잘못 이해하거나 기존 변경사항을 모르고 작업하면 내가 원하지 않는 commit이나 push가 생길 수 있었다.

그래서 나중에는 작업 요청을 할 때 거의 항상 먼저 확인하도록 했다.

예를 들면 이런 식이었다.

```text
먼저 현재 repository와 branch를 확인한다.
git status를 확인한다.
working tree가 clean인지 확인한다.
원격 저장소가 올바른 저장소인지 확인한다.
local main과 origin/main을 확인한다.
```

그리고 상황이 예상과 다르면

**임의로 해결하지 말고 멈춰서 보고하도록 했다.**

이 방식은 조금 느려 보일 수 있지만 실제로는 잘못된 브랜치에 작업하거나 기존 변경사항을 잃는 일을 막는 데 도움이 됐다.

---

## "분석만"과 "실제로 GitHub에 반영"하는 것도 구분했다

Claude Code를 처음 사용할 때는

> 이 PR 확인해줘.

라고 하면 단순히 내용을 확인할 것이라고 생각하기 쉽다.

하지만 요청 방식에 따라 실제 파일을 수정하거나 GitHub 작업까지 이어질 수 있었다.

그래서 점점 작업 범위를 더 명확하게 말했다.

예를 들어

> 지금은 분석만 해라.

> 로컬 파일 수정까지만 해라.

> commit은 하지 마라.

> push는 하지 마라.

> 기존 PR만 업데이트하고 새 PR은 만들지 마라.

처럼 어느 단계까지 허용하는지를 따로 적었다.

Git을 사람이 직접 사용할 때도 현재 단계가 중요했지만, AI와 함께 사용할 때는 **어디까지 실행해도 되는지를 명확히 말하는 것**이 더 중요했다.

---

## 처음과 지금의 Git 흐름을 비교하면

처음에는 이렇게 알고 있었다.

```text
branch
↓
commit
↓
push
↓
PR
↓
끝
```

프로젝트를 경험한 뒤에는 이렇게 보이기 시작했다.

```text
최신 원격 상태 확인
↓
working tree 확인
↓
main 최신화
↓
새 작업 브랜치 생성
↓
Issue 범위 구현
↓
변경사항 확인
↓
commit
↓
push
↓
Pull Request
↓
리뷰
↓
필요하면 같은 브랜치에서 수정
↓
다시 commit / push
↓
merge
↓
local main 다시 최신화
↓
다음 작업 시작
```

단계가 훨씬 많아졌다.

하지만 오히려 왜 이런 순서가 필요한지는 전보다 이해하기 쉬워졌다.

---

## 자주 헷갈렸던 단어를 정리해보면

프로젝트를 진행하면서 반복해서 헷갈렸던 단어들을 내 기준으로 간단하게 정리하면 다음과 같다.

| 용어           | 내가 이해한 의미                        |
| ------------ | -------------------------------- |
| Working Tree | 현재 직접 수정하고 있는 파일 상태              |
| Commit       | 변경사항을 로컬 Git 기록으로 남김             |
| Push         | 로컬 commit을 GitHub 원격 저장소로 보냄     |
| Branch       | 다른 작업과 분리해서 개발하는 공간              |
| Pull Request | 내 브랜치의 변경사항을 공용 브랜치에 합칠지 검토하는 공간 |
| Merge        | 한 브랜치의 변경사항을 다른 브랜치에 실제로 합침      |
| main         | 내 컴퓨터의 main 브랜치                  |
| origin/main  | 원격 GitHub main의 상태를 나타내는 참조      |
| Fetch        | 원격의 최신 정보를 가져옴                   |
| Pull         | 원격 변경사항을 현재 로컬 브랜치에 반영           |
| HEAD         | 현재 내가 보고 있는 commit 위치            |

처음에는 이 단어들을 각각 외우려고 했다.

하지만 실제로 여러 번 작업하면서 **하나의 흐름 안에서 이해하는 것이 훨씬 쉬웠다.**

---

## Git에서 가장 어려웠던 점

Git에서 가장 어려웠던 것은 명령어 자체가 아니었다.

명령어는 검색하면 찾을 수 있었다.

더 어려웠던 것은

**지금 내 코드가 어느 단계에 있는지 파악하는 것**

이었다.

같은 파일이라도

* 수정만 한 상태
* commit한 상태
* push한 상태
* PR이 열린 상태
* merge된 상태

가 모두 달랐다.

그리고 GitHub main이 바뀌었다고 해서 내 로컬 main도 자동으로 바뀌는 것이 아니었다.

이 위치와 상태를 이해하기 시작하면서 Git에 대한 두려움이 조금 줄었다.

---

## 이번 프로젝트에서 배운 것

탄천런을 하기 전에는 Git을

**코드를 저장하고 이전 버전으로 돌아가기 위한 도구**

정도로 생각했다.

팀 프로젝트를 진행하면서는 조금 다르게 보였다.

Git은 여러 명이 서로 다른 작업을 하면서도 하나의 프로젝트를 안전하게 유지하기 위한 도구였다.

브랜치를 나누는 이유도,

PR을 만드는 이유도,

리뷰 후 같은 브랜치에 다시 push하는 이유도,

main을 계속 최신화하는 이유도 결국 서로의 작업을 섞지 않고 연결하기 위한 것이었다.

---

## 다음 프로젝트에서는 어떻게 할 것인가

다음 팀 프로젝트에서는 새 작업을 시작할 때 다음 순서를 기본으로 사용할 것 같다.

```text
1. 현재 브랜치 확인
2. git status 확인
3. 기존 변경사항이 없는지 확인
4. 원격 저장소 최신 상태 확인
5. main 최신화
6. local main과 origin/main 상태 확인
7. Issue별 새 브랜치 생성
8. 해당 Issue 범위만 작업
9. 변경사항 확인 후 commit
10. push
11. PR 생성
12. 리뷰 반영
13. merge
14. 다시 main 최신화
15. 다음 작업 시작
```

그리고 Git에서 예상하지 못한 상태가 나오면 바로 해결 명령어부터 입력하지 않을 것이다.

먼저 현재 상태부터 확인할 것이다.

특히 팀 프로젝트에서는

**"일단 실행해 보자."**

보다

**"지금 무엇이 어디에 있는 상태인지 먼저 확인하자."**

가 훨씬 안전하다는 것을 배웠다.

---

## Git 명령어를 외운 것보다 흐름을 이해한 것이 더 컸다

탄천런을 진행하면서 Git 명령어도 이전보다 많이 사용하게 됐다.

하지만 가장 크게 달라진 것은 명령어를 몇 개 더 알게 된 것이 아니었다.

처음에는

`commit`, `push`, `PR`, `merge`

가 각각 따로 존재하는 단어처럼 느껴졌다.

프로젝트가 끝날 때쯤에는 이것들이 하나의 흐름으로 이어져 보였다.

**내 컴퓨터에서 작업하고 → 기록하고 → 원격에 공유하고 → 팀이 검토하고 → 공용 코드에 합치고 → 다시 최신 상태를 받아 다음 작업을 시작한다.**

이 흐름을 실제로 여러 번 반복해 본 것이 탄천런에서 얻은 가장 큰 Git 경험이었다.
