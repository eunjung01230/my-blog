탄천런 프로젝트에서는 Claude Code와 Claude Design을 정말 많이 사용했다.

처음에는 AI를 이용하면 개발 과정이 훨씬 단순해질 것이라고 생각했다.

코드를 직접 처음부터 작성하지 않아도 되고,

디자인 수정도 설명만 하면 빠르게 바꿀 수 있고,

오류가 생겼을 때도 원인을 바로 찾아줄 것 같았다.

실제로 많은 부분에서 도움이 됐다.

하지만 프로젝트를 진행하면서 알게 된 것은 **AI를 사용한다고 해서 판단해야 할 일이 줄어드는 것은 아니라는 것**이었다.

오히려 내가 현재 프로젝트 상태를 정확하게 이해하지 못하면 Claude에게 잘못된 작업을 시킬 수도 있었다.

처음에는

> 이거 확인해줘.

> 문제 해결해줘.

> 이 Issue 구현해줘.

처럼 짧게 요청했다.

하지만 프로젝트 후반에는 요청 방식이 완전히 달라졌다.

> 먼저 현재 상태만 분석해라.
> 아직 파일은 수정하지 마라.
> 최신 GitHub main과 Issue를 다시 확인해라.
> 다른 팀원의 작업 범위는 건드리지 마라.
> 문제가 있더라도 임의로 해결하지 말고 먼저 보고해라.
> commit이나 push는 아직 하지 마라.

처럼 작업의 범위와 권한까지 자세히 설명하게 됐다.

탄천런에서 Claude를 사용하며 가장 많이 배운 것은 좋은 프롬프트 문장을 만드는 방법이라기보다,

**AI에게 어떤 상태에서 어떤 권한으로 어떤 일까지 맡길 것인지 정하는 방법**이었다.

---

## 처음에는 "확인해줘"면 확인만 하는 줄 알았다

Claude Code를 처음 사용할 때는 내가 자연스럽게 사용하는 표현이 Claude에게도 같은 의미일 것이라고 생각했다.

예를 들어

> 이 코드에 문제가 있는지 확인해줘.

라고 말하면 당연히 코드를 읽고 문제만 알려줄 것이라고 생각했다.

하지만 AI 입장에서 문제를 확인한다는 것은

**문제를 발견하고 → 고치는 것까지 포함하는 작업**

으로 해석될 수도 있었다.

나는 원인을 먼저 알고 싶었는데 바로 파일을 수정하려고 할 수도 있었고,

현재 코드만 검토하고 싶었는데 새로운 파일을 만들 수도 있었다.

이 경험 이후

**분석과 수정은 따로 요청해야 한다**

는 것을 알게 됐다.

---

## "분석만"이라는 단어를 자주 쓰게 됐다

이후 Claude Code에게 작업을 요청할 때 가장 많이 사용한 표현 중 하나가

**"먼저 분석만 해라."**

였다.

예를 들어 새로운 Issue를 작업하기 전에는 바로 구현하게 하지 않고,

먼저 다음을 확인하도록 했다.

* 현재 저장소가 맞는지
* 현재 브랜치가 무엇인지
* 기존 변경사항이 있는지
* 최신 main 상태가 무엇인지
* Issue에서 실제로 요구하는 내용이 무엇인지
* 관련된 기존 코드가 어디에 있는지

그리고 그 결과를 보고 실제 구현 여부를 결정했다.

내가 원하는 흐름은 점점 이런 식이 됐다.

```text
상태 확인
↓
분석 결과 보고
↓
내가 확인
↓
구현
↓
검증
↓
Git 작업
```

처음에는 이 과정이 번거롭게 느껴졌다.

하지만 바로 구현부터 시작했다가 범위가 틀린 것을 발견하고 되돌리는 것보다 훨씬 안전했다.

---

## Claude에게 "문제가 보여도 고치지 마"라고 말하게 됐다

이것도 처음에는 이상하게 느껴졌다.

문제가 있는데 왜 고치지 말라고 해야 할까?

하지만 팀 프로젝트에서는 이유가 있었다.

Claude가 현재 작업과 관계없는 문제까지 발견할 수 있기 때문이다.

예를 들어 내가 설정 화면 Issue 하나를 작업하고 있는데,

Claude가 다른 서버 파일에서 문제를 발견할 수도 있다.

AI 입장에서는 같이 고치면 프로젝트가 더 좋아지는 것처럼 보일 수 있다.

하지만 그 파일이 다른 팀원의 작업 영역이라면 이야기가 달라진다.

그래서 점점 이런 조건을 넣었다.

> 이번 Issue와 직접 관련된 부분만 작업한다.
> 범위 밖의 문제를 발견하면 수정하지 말고 보고만 한다.

이 원칙 덕분에

**좋아 보이는 수정과 지금 해야 하는 수정을 구분**

할 수 있었다.

---

## 최신 코드보다 Claude가 알고 있는 이전 상황이 오래된 경우가 있었다

프로젝트는 계속 변한다.

팀원이 PR을 merge하면 main이 바뀌고,

Issue 내용도 수정될 수 있고,

이미 결정한 정책이 달라질 수도 있다.

하지만 Claude와 이전에 이야기한 내용은 그보다 오래된 상태일 수 있다.

처음에는 Claude가 앞에서 이야기했던 내용을 알고 있으니 그대로 이어서 시키면 된다고 생각했다.

하지만 그러다 보면

**현재 GitHub에 있는 실제 코드보다 이전 대화 내용을 기준으로 판단할 위험**

이 있었다.

그래서 나중에는 새로운 작업을 시작할 때 자주 이렇게 요청했다.

> 이전 Plan이나 기억을 기준으로 작업하지 말고,
> 원격 GitHub의 최신 main과 최신 Issue를 다시 확인해라.

이 문장이 꽤 중요해졌다.

---

## Source of Truth를 Claude에게도 알려줘야 했다

협업 글에서도 Source of Truth라는 개념을 다뤘지만 Claude를 사용할 때는 더 직접적으로 필요했다.

Claude가 참고할 수 있는 정보가 너무 많았기 때문이다.

예를 들면

* 이전 대화
* 오래된 기획 문서
* 최신 기획 문서
* Figma
* GitHub Issue
* GitHub main
* 현재 로컬 코드

가 동시에 존재할 수 있었다.

그런데 이 중 어느 것이 가장 최신인지 Claude가 항상 알 수 있는 것은 아니다.

그래서 작업을 요청할 때

> 이번 작업에서는 최신 Issue를 요구사항의 기준으로 사용한다.

또는

> 디자인 구조는 현재 Figma를 기준으로 하고, 기능은 최신 기획 문서를 기준으로 한다.

처럼 **어떤 자료를 무엇의 기준으로 사용할지 지정**해야 했다.

Claude가 자료를 잘 읽는 것과

**어떤 자료를 더 우선해서 판단해야 하는지 아는 것**

은 다른 문제였다.

---

## Claude Code에게 Git 권한을 어디까지 줄지도 중요했다

처음에는 Claude Code가 Git 명령도 실행해주니 굉장히 편했다.

직접 명령어를 하나씩 입력하지 않아도

* 파일 수정
* commit
* push
* PR 생성

같은 작업을 이어서 할 수 있었다.

하지만 편한 만큼 조심해야 했다.

예를 들어 나는 단순히 코드 수정까지만 생각했는데 Claude가 commit까지 진행할 수 있고,

기존 PR을 수정하고 싶은데 새로운 PR을 만들 수도 있었다.

그래서 이후에는 요청할 때 Git 작업의 범위를 따로 적었다.

예를 들어

> 파일 수정까지만 해라.
> commit은 하지 마라.

또는

> commit까지 가능하지만 push는 하지 마라.

또는

> 현재 PR을 업데이트하는 push까지만 하고 새 PR은 만들지 마라.

처럼 구체적으로 나눴다.

---

## GitHub write 작업은 특히 한 번 더 확인했다

코드를 로컬에서 수정하는 것과 GitHub에 실제로 반영하는 것은 무게가 달랐다.

로컬 파일은 다시 수정할 수 있지만,

push나 PR 수정처럼 원격에 반영하는 작업은 팀원에게도 영향을 준다.

그래서 어떤 작업에서는 Claude가 PR까지 만든 뒤에도

**추가 push나 PR 본문 수정은 리드 승인 전 하지 않도록**

범위를 다시 제한하기도 했다.

이 경험을 하면서

**AI에게 무엇을 할 수 있는지보다 무엇을 해도 되는지를 알려주는 것이 중요하다**

고 느꼈다.

---

## "Yes"를 누르는 것도 작업의 일부였다

Claude Code를 사용하다 보면 명령 실행이나 파일 수정 전에 허용 여부를 묻는 경우가 있었다.

처음에는 이런 확인 창이 나오면 그냥 `Yes`를 누르면 되는 줄 알았다.

하지만 프로젝트를 진행하면서 질문을 조금 더 자세히 보기 시작했다.

지금 허용하려는 것이

* 파일 읽기인지
* 파일 수정인지
* Git commit인지
* GitHub에 push하는 작업인지

에 따라 의미가 달랐다.

실제로 실수로 `No`를 선택해서 다시 진행 방법을 확인하기도 했다.

이런 경험을 하면서 Claude Code를 사용하는 동안에도

**AI가 무엇을 실행하려고 하는지 사람이 계속 확인해야 한다**

는 것을 알게 됐다.

---

## Claude가 "완료"라고 해도 내가 원하는 완료와 다를 수 있었다

Claude가 작업 후

> 완료했습니다.

라고 보고하면 처음에는 정말 모든 것이 끝난 것처럼 느껴졌다.

하지만 자세히 보면

* 코드 작성만 완료
* Build만 성공
* 정적 검증까지만 완료
* 실제 DB 검증은 안 함
* 브라우저 테스트는 안 함
* OAuth 실제 로그인은 안 함

처럼 미검증 항목이 남아 있을 수 있었다.

실제로 탄천런 작업에서도 실행 환경이 없거나 실제 인증 정보가 없어

**코드는 작성했지만 실제 DB 적용이나 OAuth 흐름은 검증하지 못한 상태**

가 있었다.

이후에는 Claude가

**무엇을 했는지보다 무엇을 확인하지 못했는지도 같이 보게 됐다.**

---

## Build 성공과 기능 정상은 같은 말이 아니었다

이 부분도 AI를 사용하면서 자주 헷갈릴 수 있었다.

Claude가

> Build 성공했습니다.

라고 하면 기능까지 정상인 것처럼 느껴진다.

하지만 Build는 코드가 빌드 가능한지 확인한 것이다.

예를 들어 로그인 코드는 문제없이 빌드될 수 있지만,

실제 Google 로그인을 해보면 Redirect URI 문제로 실패할 수 있다.

DB 코드도 Build는 성공하지만 실제 PostgreSQL 연결이 안 될 수 있다.

그래서 점점 검증 단계를 나누게 됐다.

```text
코드 작성
↓
Lint / Build
↓
로컬 실행
↓
실제 기능 테스트
↓
외부 서비스 테스트
↓
통합 테스트
```

Claude가 어느 단계까지 했는지를 확인하지 않고

**"검증 완료"**

라고 받아들이면 안 됐다.

---

## 검증을 많이 시키면 무조건 좋은 줄 알았다

프로젝트 중간에는 오류를 만들고 싶지 않아서 Claude에게 정말 많은 검증을 요청했다.

데이터베이스 구조를 다시 확인하고,

Issue와 비교하고,

서버 계약을 확인하고,

관련 파일을 다시 검토하고,

또 문제가 없는지 확인했다.

처음에는 이렇게 할수록 안전하다고 생각했다.

하지만 어느 순간

**검증은 계속하는데 실제 결과물이 나오지 않는 상황**

이 생겼다.

같은 부분을 계속 다른 각도에서 검토하면서 프로젝트 시간이 지나가고 있었다.

---

## "검증만 하다가 프로젝트가 안 나간다"는 문제를 겪었다

당시에는 프로젝트 종료까지 시간이 많지 않았다.

그런데 DB와 서버 구조를 계속 확인하다 보니 다음 Issue 구현으로 넘어가지 못했다.

내 입장에서는 답답했다.

> 구조가 완벽하게 확정되지 않은 건 알겠는데,
> 계속 검증만 하면 실제 백엔드 구현은 언제 하지?

라는 생각이 들었다.

결국 모든 실환경 검증을 한 단계에서 끝내려 하지 않고,

현재 가능한 정적 검증과 구현을 진행한 뒤 실제 DB, OAuth, GPS 같은 검증은 통합 단계에서 다시 확인하는 방식으로 나눴다.

이 경험은 Claude를 사용할 때도 중요했다.

**AI가 더 확인할 수 있다고 해서 무조건 계속 확인시키는 것이 좋은 것은 아니었다.**

---

## Claude에게 종료 조건도 알려주는 것이 필요했다

검증이 계속되는 문제를 겪고 나니 작업 요청에 종료 기준도 필요하다고 느꼈다.

예를 들어

> 이번 작업에서는 코드 구조와 Build까지만 확인한다.
> 실제 OAuth 로그인은 이번 작업 범위가 아니다.

처럼 정할 수 있었다.

또는

> 이 조건까지 만족하면 다음 Issue로 넘어갈 수 있는 상태로 본다.

라고 완료 기준을 정할 수도 있었다.

처음에는 해야 할 일만 적었다.

나중에는

**어디까지 하면 이번 작업이 끝나는지도 같이 적는 것이 중요**

하다는 것을 알게 됐다.

---

## Claude Design에서는 결과보다 수정 범위를 관리하는 것이 어려웠다

Claude Design에서 겪었던 디자인 프롬프트 문제는 앞의 Figma 글에서 자세히 정리했다.

여기서 가장 크게 연결되는 점은 Claude Code와 비슷했다는 것이다.

Claude Design도

> 더 예쁘게 만들어줘.

처럼 넓게 요청하면 수정 범위가 너무 커질 수 있었다.

Claude Code에서

> 문제 해결해줘.

라고 했을 때 필요 이상으로 여러 파일을 볼 수 있는 것과 비슷했다.

둘 다 결국

**AI가 판단해야 하는 범위를 줄여주는 것이 중요했다.**

Claude Code에서는 수정 파일과 Issue 범위를 제한했고,

Claude Design에서는 유지할 화면 구조와 변경할 디자인 요소를 제한했다.

도구는 달랐지만 원리는 비슷했다.

---

## 한 번에 너무 큰 작업을 맡기면 확인하기도 어려웠다

처음에는 AI니까 많은 일을 한 번에 맡기면 더 효율적이라고 생각했다.

예를 들어

> 전체 구조를 확인하고 문제를 수정하고 테스트하고 commit하고 PR까지 만들어줘.

처럼 한 번에 요청할 수 있다.

실제로 Claude는 많은 일을 처리할 수 있다.

하지만 문제가 생겼다.

결과가 내가 원한 것과 다를 때

**어느 단계에서 잘못됐는지 찾기가 어려웠다.**

그래서 나중에는 작업을 더 작게 나눴다.

```text
1. 분석
2. 내가 확인
3. 구현
4. 결과 확인
5. Git 상태 확인
6. commit
7. push / PR
```

각 단계 사이에서 상태를 확인할 수 있어서 훨씬 안전했다.

---

## 프롬프트가 길다고 좋은 것도 아니었다

Claude를 사용하면서 프롬프트가 점점 길어졌다.

조건을 많이 적으면 실수가 줄어들었기 때문이다.

하지만 긴 프롬프트 자체가 좋은 것은 아니었다.

중요하지 않은 설명이 너무 많으면 오히려 핵심 작업을 찾기 어려워질 수 있었다.

그래서 내가 점점 중요하게 본 것은 길이가 아니라 구조였다.

예를 들어 이런 순서가 편했다.

### 현재 상황

지금 어떤 프로젝트이고 어떤 상태인지 설명한다.

### 이번 작업의 목적

정확히 무엇을 해결하려는지 적는다.

### 기준

Issue, 문서, 코드 중 무엇을 Source of Truth로 사용할지 정한다.

### 허용 범위

어떤 파일이나 기능까지 수정할 수 있는지 적는다.

### 금지 사항

하지 않았으면 하는 작업을 적는다.

### 완료 기준

어디까지 확인하면 끝인지 정한다.

이 구조로 작성하니 길더라도 Claude가 작업 범위를 이해하기 쉬웠다.

---

## "임의로"라는 말을 정말 많이 쓰게 됐다

프로젝트 후반의 Claude 프롬프트를 보면

**임의로**

라는 단어가 자주 들어갔다.

예를 들면

> 임의로 기능을 추가하지 마라.

> 임의로 충돌을 해결하지 마라.

> 임의로 branch를 삭제하지 마라.

> 임의로 reset하지 마라.

> 임의로 다른 팀원 코드를 수정하지 마라.

처음에는 이렇게까지 적어야 하나 싶었다.

하지만 AI는 문제 해결을 목표로 움직이기 때문에,

사람이 보기에는

**"지금은 건드리면 안 되는 영역"**

도 해결 대상으로 볼 수 있다.

그래서 작업 범위를 지키기 위해 금지 조건을 적는 것이 도움이 됐다.

---

## 실행 중인 프로세스 문제도 Claude에게 상황부터 설명하게 됐다

개발하면서 코드 자체가 아닌 실행 환경 때문에 문제가 생기는 경우도 있었다.

한 번은 Claude 관련 플러그인을 이용해 화면 캡처 작업을 진행하고 있었는데,

창을 이동하고 다시 작업하려다 기존 실행 프로세스와 새 프로세스가 겹친 것처럼 보이는 상황이 있었다.

처음에는

> 포트를 강제로 종료하는 명령부터 실행해야 하나?

라고 생각했다.

하지만 실제 원인이

* 기존 프로세스가 아직 살아 있는 것인지
* 같은 포트를 새로 사용하려는 것인지
* 창 상태만 바뀐 것인지

정확하지 않았다.

그래서 바로 종료 명령을 주기보다 Claude에게

**현재 어떤 일이 있었는지 상황부터 설명하고 원인을 확인하도록 하는 방식**

을 사용했다.

이 경험에서도 같은 교훈을 얻었다.

**원인을 모르는 상태에서 해결 명령부터 실행하면 오히려 상황을 더 복잡하게 만들 수 있었다.**

---

## 도구 이름이나 명령을 잘못 이해한 적도 있었다

Claude 관련 기능을 사용하면서 어떤 기능이 실제 명령어인지,

Claude 안에서 사용하는 기능인지,

터미널에서 직접 실행하는 것인지 헷갈린 적도 있었다.

예를 들어 Claude 내부에서 사용해야 할 작업 흐름을 PowerShell에서 바로 명령처럼 실행하면 당연히 동작하지 않는다.

이런 경험을 통해

**명령어처럼 보인다고 전부 운영체제 터미널 명령은 아니라는 것**

도 알게 됐다.

Claude Code 안에서 실행해야 하는 것인지,

일반 터미널에서 실행해야 하는 것인지,

Git 명령인지,

npm 명령인지 구분하는 것도 중요했다.

---

## AI에게 프로젝트 전체를 보여준다고 항상 좋은 것은 아니었다

처음에는 Claude가 최대한 많은 정보를 알수록 더 잘 작업할 것이라고 생각했다.

그래서 관련 문서와 코드, 디자인 자료를 많이 보여주려고 했다.

하지만 정보가 많을수록 오래된 자료와 최신 자료가 같이 들어갈 가능성도 커졌다.

그러면 Claude 입장에서는

**어떤 정보를 우선해야 하는지 판단하기 어려워질 수 있다.**

그래서 나중에는 필요한 정보만 주고,

필요하다면 최신 기준을 명시하는 방식을 더 선호하게 됐다.

Claude Design에서도 특정 화면을 수정할 때 필요한 화면만 보여주는 것이 더 안정적인 경우가 있었고,

Claude Code에서도 현재 Issue와 직접 관련 있는 문서부터 확인하는 것이 편했다.

---

## 다른 프로젝트 설정을 그대로 복사하는 것도 위험했다

탄천런에서 사용한 Claude Code 운영 구조가 편해 보여서 다른 프로젝트에도 활용하고 싶었던 적이 있다.

`.claude`, `CLAUDE.md`, `AGENTS.md` 같은 파일을 다른 프로젝트에도 적용할 수 있었다.

하지만 그대로 복사하면 안 되는 내용도 있었다.

프로젝트 이름,

경로,

사용하는 DB,

실행 명령,

팀 규칙처럼 프로젝트마다 다른 내용이 있기 때문이다.

특히 로컬 환경에만 필요한 설정 파일은 다른 프로젝트나 다른 사람 환경에 그대로 적용하면 문제가 생길 수 있었다.

이 경험을 통해 AI 설정도 코드처럼

**재사용할 부분과 프로젝트마다 바꿔야 할 부분을 구분해야 한다**

는 것을 알게 됐다.

---

## Claude 결과를 다시 Claude에게 검증시키는 것도 한계가 있었다

작업이 끝난 뒤 Claude에게

> 네가 한 작업 다시 검증해줘.

라고 요청할 수 있었다.

물론 도움이 됐다.

하지만 같은 AI가 같은 기준으로 다시 확인하면 처음 판단에서 놓친 부분을 그대로 놓칠 수도 있다.

그래서 중요한 작업에서는 가능한 경우

* 실제 Build
* 실제 Git 상태
* 실제 브라우저 화면
* 실제 GitHub PR
* 실제 DB나 외부 서비스

같은 결과를 함께 확인했다.

**설명상 맞는 것과 실제로 동작하는 것은 다를 수 있었다.**

---

## AI가 틀린 것이 아니라 내가 요청을 애매하게 한 경우도 많았다

처음에는 Claude 결과가 내 의도와 다르면

> 왜 이렇게 했지?

라고 생각했다.

하지만 다시 프롬프트를 보면 내가 범위를 제대로 말하지 않은 경우도 많았다.

예를 들어

> 이 PR 수정해줘.

라고만 하면

기존 PR에 commit을 추가하라는 것인지,

PR 본문을 수정하라는 것인지,

새로운 PR을 만들라는 것인지 정확하지 않다.

그래서 점점

> 현재 열려 있는 PR #92를 유지한다.
> 새 PR은 만들지 않는다.
> 같은 브랜치에 수정 commit을 push해서 기존 PR에 반영한다.

처럼 더 정확하게 말하게 됐다.

결과적으로 Claude의 성능 문제만큼이나

**내가 작업 상태와 원하는 결과를 얼마나 정확하게 설명했는지도 중요했다.**

---

## 내가 Claude에게 자주 넣게 된 규칙

프로젝트 후반에는 작업 종류에 따라 조금씩 다르지만 대략 이런 조건을 자주 사용했다.

| 구분              | 자주 사용한 조건                                  |
| --------------- | ------------------------------------------ |
| 분석              | 먼저 읽고 분석만 할 것                              |
| Source of Truth | 최신 main / 최신 Issue / 최신 문서를 기준으로 할 것       |
| 작업 범위           | 현재 Issue에 필요한 부분만 수정할 것                    |
| 다른 작업 보호        | 다른 팀원 영역을 임의로 수정하지 않을 것                    |
| 문제 발견           | 범위 밖 문제는 수정하지 말고 보고할 것                     |
| Git             | commit / push / PR 허용 범위를 명확히 할 것          |
| 위험한 작업          | reset / delete / force push 등을 임의로 하지 않을 것 |
| 검증              | 실제로 확인하지 못한 것은 확인했다고 말하지 않을 것              |
| 완료              | 이번 작업의 완료 기준을 지킬 것                         |

처음부터 이 규칙들을 알고 있었던 것은 아니다.

한 번씩 문제가 생길 때마다 하나씩 추가됐다.

## 처음과 나중의 Claude 요청은 완전히 달라졌다

처음에는 이런 식이었다.

> Issue #46 구현해줘.

나중에는 대략 이런 생각을 먼저 했다.

```text
현재 저장소가 맞는가?
↓
최신 main인가?
↓
최신 Issue 내용은 무엇인가?
↓
working tree가 깨끗한가?
↓
이번 작업 범위는 어디까지인가?
↓
다른 사람 작업과 겹치는가?
↓
분석만 할 것인가, 수정할 것인가?
↓
commit까지 할 것인가?
↓
push / PR까지 할 것인가?
↓
완료 기준은 무엇인가?
```

프롬프트가 길어진 이유는 AI를 불신해서가 아니었다.

**프로젝트 자체가 생각보다 많은 상태를 가지고 있었기 때문**이었다.

---

## Claude Code와 Claude Design에서 공통적으로 배운 것

둘은 사용하는 목적이 다르다.

Claude Code는 코드와 프로젝트 파일을 다루고,

Claude Design은 화면 디자인을 빠르게 수정하고 비교하는 데 도움을 줬다.

하지만 두 도구를 사용하면서 공통적으로 배운 것이 있었다.

### 1. AI가 기준을 대신 정해주지는 않는다

무엇이 최신인지,

어떤 기능이 MVP인지,

어디까지 수정해도 되는지는 내가 알려줘야 했다.

### 2. 작업 범위가 넓을수록 예상하지 않은 변경도 늘어난다

한 번에 작은 범위로 나눌수록 결과를 확인하기 쉬웠다.

### 3. 완료 보고를 그대로 믿기보다 실제 결과를 확인해야 한다

코드가 존재하는 것과 실제 동작은 다를 수 있었다.

### 4. AI에게도 권한 관리가 필요했다

읽기만 할지,

파일을 수정할지,

GitHub까지 변경할지 구분해야 했다.

### 5. 문제가 생겼을 때 현재 상태부터 확인해야 했다

바로 수정 명령을 실행하기보다 무엇이 현재 실행되고 있고 어떤 파일이 바뀌었는지 먼저 보는 것이 안전했다.

---

## Claude를 사용하면서 오히려 내가 더 알아야 했다

프로젝트를 시작하기 전에는 AI를 이용하면 내가 모르는 부분을 AI가 대신 처리해줄 것이라고 생각했다.

물론 실제로 많은 부분을 도와줬다.

하지만 내가 Git을 전혀 모르면 Claude가 올바른 브랜치에서 작업했는지 판단하기 어렵다.

DB 흐름을 모르면 Schema만 만든 것을 DB 구현 완료라고 착각할 수 있다.

Vercel 환경을 모르면 Preview에서 안 되는 원인이 코드인지 환경설정인지 판단하기 어렵다.

OAuth 흐름을 모르면 로그인 버튼이 뜨는 것만 보고 구현이 끝났다고 생각할 수 있다.

결국 AI를 사용하면서 오히려

**결과가 맞는지 판단하기 위해 기본 구조를 내가 이해해야 한다**

는 것을 크게 느꼈다.

---

## 이번 프로젝트에서 가장 크게 바뀐 점

처음에는 Claude에게

**정답을 받으려고 했다.**

프로젝트 후반에는 조금 달라졌다.

Claude를

**내가 정한 범위 안에서 빠르게 조사하고 구현하고 검증하는 작업 도구**

처럼 사용하기 시작했다.

결정 자체를 전부 맡기기보다는

내가 작업의 기준과 범위를 정하고,

Claude가 그 안에서 빠르게 작업하도록 하는 방식이었다.

이 차이가 생각보다 컸다.

---

## 다음 프로젝트에서는 어떻게 사용할 것인가

다음 프로젝트에서 Claude Code를 사용한다면 처음부터 작업을 네 단계 정도로 나눌 것 같다.

```text
1. 현재 상태 확인
2. 분석
3. 구현
4. 검증 및 Git 반영
```

그리고 매 단계마다 필요한 권한만 줄 것이다.

새로운 작업을 시작할 때는 최소한 다음을 확인할 것 같다.

```text
현재 브랜치
현재 변경사항
최신 원격 상태
최신 요구사항
이번 작업 범위
수정 금지 범위
완료 기준
GitHub write 허용 여부
```

Claude Design에서도 마찬가지로

**현재 디자인 기준 → 이번 수정 범위 → 유지할 것 → 바꾸지 않을 것 → 결과 확인**

순서를 사용할 것 같다.

---

## AI를 잘 사용하는 것은 프롬프트 한 줄의 문제가 아니었다

탄천런을 시작할 때는 AI를 잘 사용하는 사람은

**프롬프트를 잘 쓰는 사람**

이라고 생각했다.

프로젝트를 끝내고 나서는 조금 다르게 생각하게 됐다.

물론 프롬프트도 중요하다.

하지만 실제 프로젝트에서는 그보다 먼저

* 현재 상태를 이해하고
* 기준을 정하고
* 작업 범위를 나누고
* 위험한 작업을 제한하고
* 결과를 검증하고
* 다음 단계로 넘어갈지 판단하는 것

이 필요했다.

Claude가 빠르게 많은 일을 해줄 수 있었기 때문에 오히려 이런 기준이 없으면 더 빠르게 잘못된 방향으로 갈 수도 있었다.

탄천런에서 Claude Code와 Claude Design을 사용하면서 가장 크게 배운 것은

**AI에게 모든 것을 맡기는 방법이 아니라, AI가 잘 일할 수 있도록 작업의 경계를 만드는 방법**이었다.

처음에는 Claude에게

> 이거 해줘.

라고 말했다.

프로젝트가 끝날 때쯤에는

> 지금 상태는 이렇고,
> 이번 목표는 이것이고,
> 여기까지는 수정해도 되지만,
> 이 부분은 건드리지 말고,
> 여기까지 검증한 뒤 결과를 보고해줘.

라고 말하게 됐다.

내가 Claude를 더 잘 사용하게 된 이유는 더 어려운 프롬프트 기술을 배웠기 때문이라기보다,

**프로젝트에서 내가 무엇을 원하는지 조금 더 정확하게 알게 되었기 때문이라고 생각한다.**
