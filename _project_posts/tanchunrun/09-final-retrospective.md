탄천런 프로젝트를 시작할 때는 우리가 이렇게 많은 부분에서 막힐 것이라고 생각하지 못했다.

기획과 디자인을 어느 정도 만들고,

4명이 기능을 나눠서,

Claude Code를 이용해 빠르게 구현하면,

짧은 기간 안에도 꽤 완성도 있는 서비스를 만들 수 있을 것이라고 생각했다.

특히 이번 프로젝트는 나에게 **바이브 코딩을 실제 팀 프로젝트에서 제대로 사용해본 첫 경험**에 가까웠다.

AI에게 필요한 기능을 설명하면 코드를 만들어주고,

오류가 생기면 다시 물어보고,

Git 작업도 도와주고,

디자인도 Claude를 이용해 수정할 수 있었다.

처음에는 이것이 개발을 훨씬 쉽게 만들어줄 것이라고 생각했다.

실제로 코드가 만들어지는 속도는 정말 빨랐다.

하지만 프로젝트가 진행될수록 다른 문제가 보이기 시작했다.

**코드를 빠르게 만드는 것과 프로젝트를 제대로 이해하면서 만드는 것은 전혀 다른 일이었다.**

우리는 개발 경험이 많지 않은 상태에서 바이브 코딩을 사용했고,

Git, 데이터베이스, API, 배포, 인증, 지도처럼 서로 연결된 기술을 동시에 다뤄야 했다.

그러다 보니 Claude가 만들어준 코드가 맞는지 판단하기 어려운 순간도 있었고,

어떤 기능을 누가 맡아야 하는지도 예상보다 복잡했다.

지금 돌아보면 프로젝트에서 많이 헤맸던 이유는 단순히 기술을 몰라서만은 아니었다.

**무엇을 모르는지조차 정확히 모르는 상태에서 AI의 속도를 따라가려고 했던 것**도 큰 이유였던 것 같다.

---

## 처음에는 "바이브 코딩이면 빠르게 만들 수 있다"고 생각했다

바이브 코딩을 처음 접했을 때 가장 크게 느낀 장점은 속도였다.

직접 모든 코드를 처음부터 작성하지 않아도

> 로그인 기능을 만들어줘.

> 이 화면을 구현해줘.

> DB 구조를 만들어줘.

처럼 설명하면 Claude가 빠르게 코드를 만들어줬다.

내가 아직 익숙하지 않은 Next.js나 서버 코드도 만들어줄 수 있었다.

그래서 처음에는

**"내가 모든 문법을 완벽하게 몰라도 서비스를 만들 수 있겠구나."**

라는 생각을 했다.

이 말 자체는 어느 정도 맞았다.

하지만 프로젝트를 진행하면서 중요한 조건 하나가 빠져 있었다는 것을 알게 됐다.

**코드를 직접 다 작성하지 않더라도, 그 코드가 프로젝트 안에서 어떤 역할을 하는지는 이해해야 했다.**

---

## 코드는 만들어지는데 나는 어디까지 만들어진 건지 몰랐다

바이브 코딩을 하면서 가장 당황스러웠던 순간 중 하나였다.

Claude가 많은 파일을 만들고

> 구현했습니다.

라고 알려준다.

그런데 나는 그다음에

> 그래서 지금 어디까지 된 거지?

라는 생각이 들었다.

예를 들어 데이터베이스 Schema가 만들어졌다.

처음에는

> DB가 만들어졌구나.

라고 생각하기 쉬웠다.

하지만 실제 PostgreSQL에 Migration이 적용된 것은 아니었다.

로그인 코드가 만들어졌다.

그러면

> 로그인이 구현됐구나.

라고 생각하기 쉽다.

하지만 Google이나 Kakao 개발자 설정이 끝난 것은 아니고,

실제 사용자 정보가 DB에 저장되는 것도 별도의 작업이었다.

지도 컴포넌트가 만들어졌다고 해서 GPS 기반 러닝 기록까지 구현된 것도 아니었다.

이런 경험을 반복하면서 알게 됐다.

**AI가 "구현했다"고 말하는 것과 내가 생각하는 "기능이 완성됐다"는 의미가 다를 수 있었다.**

---

## 가장 어려웠던 것은 역할을 나누는 일이었다

프로젝트를 시작할 때는 4명이니까 역할을 네 부분으로 나누면 된다고 생각했다.

예를 들어

* 백엔드
* 로그인 API
* 지도
* 배포

같은 식으로 나누면 될 것 같았다.

그런데 실제로 개발을 시작하니 이 기능들이 전부 연결되어 있었다.

지도 담당이 지도 화면만 만들면 끝나는 것이 아니었다.

GPS 위치 정보가 필요했고,

그 위치를 기준으로 탄천 구역인지 판단해야 했고,

그 결과를 러닝 기록으로 저장하려면 데이터베이스가 필요했다.

로그인 담당도 로그인 버튼 하나만 만들면 끝나는 것이 아니었다.

Google이나 Kakao 설정이 필요했고,

Callback이 필요했고,

로그인한 사용자를 서버에서 확인해야 했으며,

결국 사용자 DB와도 연결되어야 했다.

배포 역시 마지막에 한 명이 Vercel에 올리는 단순 작업이 아니었다.

Google 로그인과 Kakao 로그인은 배포 URL과 연결되어 있었고,

지도 API도 허용 도메인 설정이 필요했고,

데이터베이스 연결 역시 배포 환경의 환경변수와 연결되어 있었다.

즉 우리가 처음에는 각각 독립된 일이라고 생각했던 것들이 실제로는 서로 강하게 연결되어 있었다.

---

## "API 담당", "백엔드 담당", "배포 담당"처럼 나누기 어려웠던 이유

지금 돌아보면 우리가 역할을 나눌 때 기능의 이름만 보고 나눈 부분이 있었다.

예를 들어

> API니까 이 사람이 담당.

> DB니까 백엔드 담당.

> 배포니까 마지막에 Vercel 담당.

이라고 생각하기 쉽다.

하지만 실제 프로젝트에서는 하나의 기능이 여러 기술을 지나간다.

소셜 로그인을 예로 들면

```text
로그인 버튼
↓
외부 OAuth
↓
Callback
↓
Session
↓
사용자 DB
↓
배포 환경변수
```

까지 연결된다.

지도를 예로 들면

```text
지도 API
↓
현재 위치
↓
GPS
↓
탄천 구역 판단
↓
거리 계산
↓
러닝 기록
↓
DB 저장
```

까지 연결된다.

그래서 기능을 단순히

**프론트 / 백엔드 / API / 배포**

로 나누면 중간에 누가 책임져야 하는지 애매한 구간이 생길 수 있었다.

이번 프로젝트를 통해 다음에는 역할을 기술 이름으로 나누기보다

**사용자 기능이 처음부터 끝까지 어떻게 흐르는지 먼저 보고 나누는 것이 더 좋겠다**

고 생각하게 됐다.

---

## 한 사람이 만든 기능의 끝이 다른 사람 작업의 시작이었다

팀 프로젝트에서 가장 많이 느낀 부분이었다.

내가 작업을 끝냈다고 해서 전체 기능이 끝나는 것이 아니었다.

내 결과물이 다른 사람이 사용할 수 있는 상태여야 했다.

예를 들어 DB 구조를 만든 사람이

> Schema 작성 완료

라고 하면,

다음 사람 입장에서는 실제로 어떤 테이블을 사용할 수 있는지,

Migration은 되었는지,

어떤 데이터가 들어가는지 알아야 했다.

OAuth 설정을 담당한 사람이

> Google 설정 완료

라고 하면,

다음 사람은 Client ID만 준비된 것인지,

실제 Callback까지 테스트된 것인지,

Session까지 확인된 것인지 알아야 했다.

이런 경계가 명확하지 않으면

**나는 끝났다고 생각하는데 다음 사람은 시작할 수 없는 상태**

가 생겼다.

---

## 우리에게 부족했던 것은 코딩보다 전체 구조 이해였던 것 같다

처음에는 프로젝트를 잘 만들기 위해 코딩 실력이 가장 중요하다고 생각했다.

하지만 탄천런에서는 조금 다르게 느꼈다.

AI가 코드를 많이 작성해줬기 때문에 문법을 몰라서 아예 진행하지 못하는 경우는 줄었다.

대신 다른 문제가 생겼다.

> 이 코드는 프론트에서 실행되는가?

> 서버에서 실행되는가?

> DB에 실제로 연결된 것인가?

> 이 키는 브라우저에 노출되어도 되는가?

> Preview와 Production 중 어디에 설정해야 하는가?

> Google에서 설정해야 하는가, Vercel에서 설정해야 하는가?

같은 질문들이 계속 생겼다.

이건 코드 한 줄의 문법보다 **전체 시스템의 구조를 이해해야 답할 수 있는 문제**였다.

---

## 바이브 코딩의 가장 큰 장점은 속도였다

물론 바이브 코딩이 문제만 있었던 것은 아니다.

오히려 이번 프로젝트를 끝까지 진행할 수 있었던 이유 중 하나도 AI의 도움이 컸다고 생각한다.

모르는 기술이 나와도 바로 설명을 들을 수 있었고,

필요한 코드의 초안을 빠르게 만들 수 있었으며,

오류 로그를 같이 보면서 원인을 찾을 수도 있었다.

기존 프로젝트 구조를 분석하고,

Issue에 맞는 파일을 찾고,

Git 상태를 확인하는 일에도 도움을 받을 수 있었다.

혼자 모든 문법과 프레임워크를 공부한 뒤 프로젝트를 시작했다면 실제 구현까지 훨씬 오래 걸렸을 것이다.

그래서 나는 바이브 코딩 자체가 나쁘다고 생각하지 않는다.

오히려 초보자가 실제 프로젝트를 경험할 수 있게 해주는 강력한 도구라고 느꼈다.

---

## 문제는 속도가 이해보다 빨라질 때였다

바이브 코딩에서 가장 위험하다고 느낀 순간은

**코드가 만들어지는 속도가 내가 이해하는 속도보다 빨라졌을 때**였다.

Claude는 몇 초 만에 여러 파일을 수정할 수 있다.

하지만 나는 그 파일들이 왜 바뀌었는지 이해하는 데 시간이 필요하다.

이 상태에서

> 다음 기능도 만들어줘.

> 이것도 연결해줘.

를 계속 반복하면 코드 양은 빠르게 늘어난다.

하지만 어느 순간 오류가 생기면 어디서부터 확인해야 하는지 모르게 된다.

실제로 프로젝트 중에도

**코드는 계속 늘어나는데 실제로 무엇이 검증된 상태인지 알기 어려운 순간**

이 있었다.

이때부터 조금씩 속도를 줄이게 됐다.

---

## "일단 만들어줘"보다 "지금 상태를 확인해줘"가 많아졌다

프로젝트 초반에는 Claude에게

> 이거 만들어줘.

라는 말을 많이 했다.

후반에는

> 현재 상태부터 확인해줘.

라는 말을 더 많이 하게 됐다.

현재 브랜치는 무엇인지,

어떤 코드가 이미 있는지,

어떤 Issue까지 완료됐는지,

DB는 실제로 연결됐는지,

배포 환경은 어떻게 되어 있는지 등을 먼저 확인했다.

처음에는 이런 과정이 개발 속도를 늦추는 것처럼 느껴졌다.

하지만 프로젝트가 복잡해질수록 오히려 필요했다.

**현재 상태를 모르고 새로운 코드를 추가하는 것이 더 큰 시간을 낭비할 수 있었기 때문이다.**

---

## 검증을 너무 많이 하면서 반대 문제도 생겼다

흥미로운 것은 나중에는 반대로 검증을 너무 많이 하기도 했다는 점이다.

바이브 코딩으로 코드가 빠르게 만들어지다 보니

> 이게 정말 맞는 코드인가?

가 불안했다.

그래서 Claude에게 계속 검증을 시켰다.

Schema를 다시 확인하고,

Issue와 비교하고,

서버 구조를 확인하고,

다시 코드를 읽고,

또 문제가 없는지 확인했다.

그런데 어느 순간

**검증은 계속하는데 실제 개발은 앞으로 나가지 않는 상태**

가 되었다.

특히 프로젝트 일정이 얼마 남지 않았을 때 이 부분이 많이 답답했다.

---

## 완벽하게 아는 것과 프로젝트를 진행하는 것 사이의 균형

처음에는 완전히 이해하고 완전히 검증된 상태에서 다음 단계로 가야 한다고 생각했다.

물론 중요한 태도라고 생각한다.

하지만 팀 프로젝트 기간은 정해져 있었다.

모든 것을 완벽하게 확인하고 넘어가려다 보면 실제 기능이 완성되지 않을 수도 있었다.

그래서 이후에는

**지금 반드시 검증해야 하는 것**

과

**통합 단계에서 검증해도 되는 것**

을 나눠야 한다는 것을 배웠다.

바이브 코딩에서도 마찬가지였다.

AI 결과를 무조건 믿는 것도 위험하지만,

모든 코드 한 줄을 완벽하게 이해할 때까지 아무것도 진행하지 않는 것도 현실적으로 어려웠다.

---

## 모르는 것을 AI에게 넘기기만 하면 결국 다시 돌아왔다

프로젝트 중 이해하기 어려운 부분이 나오면

> Claude가 알아서 처리해주겠지.

라고 넘기고 싶은 순간도 있었다.

하지만 그런 부분은 나중에 오류가 생겼을 때 다시 돌아왔다.

예를 들어 Git을 정확히 모르면 브랜치와 PR 작업에서 막혔고,

DB를 정확히 모르면 Migration과 실제 데이터 저장에서 막혔다.

OAuth를 모르면 로그인 설정에서 막혔고,

Vercel 환경을 모르면 배포 후 기능이 왜 안 되는지 알기 어려웠다.

결국 AI가 대신 구현해줘도 **내가 이해하지 않은 개념 자체가 사라지는 것은 아니었다.**

조금 늦게 다시 만나게 될 뿐이었다.

---

## 내가 질문하는 방식도 많이 달라졌다

처음에는 오류가 생기면

> 이거 왜 안 돼?

라고 물었다.

하지만 이런 질문은 상황이 너무 넓다.

프로젝트 후반에는 조금 더 구체적으로 보려고 했다.

예를 들어

> 로그인 버튼을 누르면 Google 페이지까지는 이동한다.
> 로그인도 성공한다.
> 그런데 우리 서비스로 돌아오는 단계에서 실패한다.

처럼 어디까지 정상인지 설명했다.

또는

> Migration 파일은 생성됐다.
> 하지만 실제 PostgreSQL에 적용됐는지는 확인하지 않았다.

처럼 **완료된 것과 확인하지 못한 것을 구분**해서 말하게 됐다.

이런 질문 방식의 변화도 이번 프로젝트에서 얻은 큰 경험이었다.

---

## 바이브 코딩에서는 "프롬프트 능력"보다 "판단 능력"이 더 중요했다

처음에는 바이브 코딩을 잘하려면 프롬프트를 잘 쓰면 된다고 생각했다.

물론 프롬프트도 중요했다.

하지만 실제 프로젝트를 하면서 느낀 것은 조금 달랐다.

AI에게

> 정확한 코드를 만들어줘.

라고 말하는 것보다 먼저 내가 판단해야 하는 것이 있었다.

* 지금 정말 코드 수정이 필요한가?
* 설정 문제는 아닌가?
* 이 기능은 현재 MVP인가?
* 이 파일을 수정해도 되는가?
* 다른 팀원 작업과 겹치지 않는가?
* 실제로 검증할 수 있는 환경인가?
* 어디까지 되면 이번 작업을 완료라고 할 것인가?

이런 판단이 먼저 필요했다.

그래서 바이브 코딩 실력도 결국 **개발에 대한 기본 이해와 연결되어 있다**고 느꼈다.

---

## 이번 프로젝트에서 특히 부족하다고 느낀 공부

탄천런을 하면서 앞으로 무엇을 더 공부해야 하는지도 많이 보였다.

### Git과 GitHub

명령어를 외우는 수준이 아니라

브랜치,

원격 저장소,

PR,

Merge,

충돌이 실제로 어떻게 연결되는지 더 익숙해지고 싶다.

이제는 기본 흐름을 알지만 아직 예상하지 못한 상태가 나오면 긴장하게 된다.

### 백엔드 흐름

프론트 화면에서 발생한 요청이

서버를 지나고,

DB에 저장되고,

다시 화면으로 돌아오는 흐름을 더 제대로 이해하고 싶다.

특히 인증과 사용자 데이터의 연결을 더 공부하고 싶다.

### 데이터베이스

Schema와 Migration 정도의 개념은 이번 프로젝트에서 처음 연결해서 이해했다.

앞으로는 SQL 자체도 더 공부하고,

테이블 관계나 데이터 설계를 혼자서 판단할 수 있는 수준까지 가고 싶다.

### API와 인증

OAuth에서 Client ID와 Secret, Redirect URI가 어떤 역할을 하는지는 알게 됐다.

하지만 단순히 콘솔 설정을 따라 하는 수준을 넘어 인증 흐름 자체를 조금 더 이해하고 싶다.

### 배포

Local, Preview, Production을 구분하게 됐지만

환경변수와 서버 실행 환경,

빌드와 런타임의 차이까지 더 공부하고 싶다.

### 네트워크와 웹의 기본 구조

프로젝트를 하면서 결국 많은 문제가

**브라우저 → 서버 → 외부 API → DB**

사이의 통신에서 발생했다.

HTTP 요청이나 서버와 클라이언트의 차이를 더 잘 이해하면 앞으로 문제를 훨씬 빨리 찾을 수 있을 것 같다.

---

## 이제는 "코딩 공부"의 의미도 조금 달라졌다

예전에는 코딩 공부라고 하면 주로 문법을 생각했다.

Java 문법,

React 문법,

SQL 문법처럼

**어떻게 작성하는가**

가 가장 중요하다고 생각했다.

탄천런 이후에는 그보다 더 넓게 보게 됐다.

코드를 어떻게 작성하는지도 중요하지만

* 데이터는 어디에서 오는가?
* 어떤 서버에서 실행되는가?
* 사용자는 어떻게 구분되는가?
* 외부 서비스와 어떻게 통신하는가?
* 코드는 어떻게 팀원과 공유되는가?
* 실제 사용자에게는 어떻게 배포되는가?

같은 흐름도 개발 공부라고 느끼게 됐다.

---

## 앞으로는 AI가 만든 코드를 그냥 넘기지 않으려고 한다

앞으로도 나는 Claude Code 같은 AI 도구를 계속 사용할 생각이다.

이번 프로젝트에서 실제로 많은 도움을 받았기 때문이다.

하지만 사용하는 방법은 조금 달라질 것 같다.

코드가 만들어졌을 때 최소한

> 이 파일은 왜 필요한가?

> 입력은 어디에서 오는가?

> 결과는 어디로 가는가?

> DB와 연결되는 부분은 어디인가?

> 서버 코드인가 클라이언트 코드인가?

> 실제로 어떤 방법으로 검증했는가?

정도는 이해하고 넘어가려고 한다.

모든 코드를 한 줄씩 완벽하게 설명할 수 있어야 한다는 뜻은 아니다.

하지만 적어도 **프로젝트 안에서 이 코드가 어떤 역할을 하는지는 알고 싶다.**

---

## 구현 전에 흐름을 먼저 그리는 습관을 만들고 싶다

탄천런에서는 기능을 바로 나누고 구현을 시작한 뒤

나중에 연결 관계를 발견하는 경우가 많았다.

다음 프로젝트에서는 먼저 간단하게라도 흐름을 그려보고 싶다.

예를 들어 소셜 로그인이라면

```text
사용자
↓
로그인 버튼
↓
외부 OAuth
↓
Callback
↓
Session
↓
User DB
```

지도 러닝이라면

```text
GPS
↓
현재 위치
↓
탄천 구역 판정
↓
거리 계산
↓
러닝 기록
↓
DB
```

처럼 먼저 연결 관계를 보고 역할을 나눌 것이다.

이렇게 하면

**"이건 누구 담당이지?"**

가 중간에서 애매해지는 일이 조금 줄어들 것 같다.

---

## 역할 분담도 기술이 아니라 기능 흐름을 기준으로 해보고 싶다

다음 팀 프로젝트에서는 단순히

> 너는 API, 나는 DB, 다른 사람은 지도.

처럼 나누는 것을 조심할 것 같다.

대신 하나의 기능이 끝까지 동작하기 위해 필요한 작업을 먼저 나누고 싶다.

예를 들어

**소셜 로그인 기능**

이라는 하나의 큰 흐름을 만들고,

그 안에서

* 외부 서비스 설정
* 서버 인증
* 사용자 저장
* 화면 연결
* Preview 테스트

같은 하위 작업을 구분하는 방식이다.

그러면 각자의 결과물이 어디에서 연결되는지 더 명확할 것 같다.

---

## 작은 단위로 실제 동작을 확인하고 넘어가고 싶다

이번 프로젝트에서는 여러 기능을 동시에 만들다 보니 나중에

> 어느 부분부터 안 되는 거지?

라는 상황도 있었다.

다음에는 가능한 경우 작은 단위로 실제 동작을 확인하고 넘어가고 싶다.

예를 들어 DB라면

```text
테이블 설계
↓
실제 Migration
↓
데이터 하나 저장
↓
다시 조회
```

까지 먼저 확인한다.

로그인이라면

```text
외부 로그인
↓
Callback
↓
Session 확인
↓
DB 사용자 확인
```

을 순서대로 확인한다.

이렇게 작은 성공 단위를 만들면 문제가 생겨도 확인해야 할 범위가 줄어들 것 같다.

---

## 완성도보다 배운 것이 더 많았던 프로젝트

탄천런은 내가 원하는 모든 것을 완벽하게 구현한 프로젝트라고 말하기는 어렵다.

처음 생각했던 기능 중 빠진 것도 있고,

시간 때문에 완벽하게 검증하지 못한 부분도 있고,

다시 한다면 다르게 설계하고 싶은 부분도 많다.

하지만 이번 프로젝트에서 처음 경험한 것들이 정말 많았다.

* 4명이 Issue를 나누어 개발하는 과정
* Branch와 PR을 이용한 협업
* Figma와 Claude Design을 이용한 디자인 작업
* Claude Code를 이용한 바이브 코딩
* 데이터베이스 Schema와 Migration
* PostgreSQL과 서버 데이터 연결
* Vercel Preview와 Production
* 환경변수
* Google / Kakao 소셜 로그인
* 지도 API와 GPS
* 코드 리뷰와 Merge
* 실제 배포 환경에서의 테스트

수업에서 각각 따로 들으면 서로 다른 단어처럼 보였던 것들이

하나의 프로젝트 안에서 전부 연결되어 있었다.

그 연결을 직접 경험한 것이 이번 프로젝트에서 가장 큰 수확이었다.

---

## 실패하거나 막힌 순간도 기록으로 남기고 싶었다

이번 블로그 시리즈를 작성한 이유도 여기에 있다.

완성된 코드만 보면 프로젝트가 굉장히 자연스럽게 진행된 것처럼 보인다.

하지만 실제로는 그렇지 않았다.

Git 브랜치 하나를 이해하는 데도 여러 번 질문했고,

DB를 만들었다고 생각했는데 실제 DB에는 적용되지 않았다는 것을 뒤늦게 이해하기도 했다.

Preview와 Production이 무엇인지 몰라 환경변수를 보면서 혼란스러워했고,

소셜 로그인 키가 많아지면서 무엇이 어디에서 사용되는지도 헷갈렸다.

Claude에게 너무 넓은 작업을 맡겨 결과를 다시 확인하기도 했고,

검증만 계속하면서 실제 개발이 진행되지 않아 답답해하기도 했다.

이런 과정이 오히려 지금의 나에게는 완성된 코드보다 더 중요한 기록이라고 생각했다.

---

## 다음 프로젝트에서는 덜 헤매고 싶지만, 안 헤매려고 하지는 않을 것이다

이번 프로젝트를 진행하면서 정말 많이 헤맸다.

처음에는 이런 시간이 전부 낭비라고 생각했다.

하지만 지금 돌아보면 가장 많이 배운 순간도 대부분 막혔던 순간이었다.

물론 다음 프로젝트에서는 같은 문제로 또 몇 시간을 보내고 싶지는 않다.

이번에 배운 것은 미리 정리해서 더 효율적으로 진행하고 싶다.

하지만 새로운 프로젝트를 한다면 또 새로운 문제가 생길 것이다.

그때는

**"왜 나는 이것도 모르지?"**

라고 생각하기보다

**"지금 어떤 단계까지 알고 있고, 무엇을 새로 이해해야 하지?"**

라고 생각하려고 한다.

---

## 바이브 코딩을 계속 사용할 것이다

이번 프로젝트를 하면서 바이브 코딩의 한계를 많이 느꼈지만,

그렇다고 앞으로 AI 없이 개발해야겠다고 생각하지는 않는다.

오히려 반대다.

AI를 더 잘 활용하고 싶다.

다만 이전처럼

> 내가 모르니까 Claude가 알아서 해주겠지.

라는 방식이 아니라,

> 내가 전체 흐름과 기준을 이해하고,
> Claude를 빠르게 구현하고 분석하는 도구로 사용한다.

는 방식으로 바꾸고 싶다.

내가 모르는 것을 숨기기 위해 AI를 사용하는 것이 아니라,

**더 빠르게 배우고 더 많은 것을 직접 경험하기 위해 AI를 사용하고 싶다.**

## 앞으로의 공부 목표

탄천런을 끝내고 가장 크게 느낀 것은 공부할 것이 많다는 것이었다.

예전에는 이것이 조금 막막하게 느껴졌을 것 같다.

하지만 지금은 오히려 공부해야 할 방향이 보인다는 점이 좋다.

앞으로는 단순히 자격증이나 문법 공부만 하는 것이 아니라,

작은 프로젝트를 계속 만들면서 다음 내용을 같이 연습하고 싶다.

* Git과 GitHub 협업 흐름
* Java와 Spring Boot를 이용한 서버 구조
* REST API의 기본
* SQL과 데이터베이스 설계
* 인증과 Session
* React와 서버 사이 데이터 흐름
* HTTP와 웹의 기본 구조
* 배포 환경과 환경변수
* 로그를 보고 오류 위치 찾기
* AI가 작성한 코드를 읽고 검증하는 습관

처음부터 전부 잘하려고 하기보다 하나씩 직접 연결해 보면서 익힐 생각이다.

## 탄천런을 하기 전과 후

탄천런을 시작하기 전에는 프로젝트를 이렇게 생각했다.

```text
기획
↓
디자인
↓
코딩
↓
배포
↓
완성
```

지금은 조금 다르게 보인다.

```text
문제 정의
↓
MVP 결정
↓
사용자 흐름
↓
디자인
↓
작업 분리
↓
Git 협업
↓
프론트엔드
↕
백엔드
↕
데이터베이스
↕
외부 API
↓
배포 환경
↓
실제 테스트
↓
문제 수정
↓
다시 검증
```

그리고 이 모든 과정 사이에 팀원 간의 의사소통과 판단이 계속 들어간다.

프로젝트는 코드를 많이 작성하면 완성되는 것이 아니었다.

**서로 다른 기술과 사람의 작업을 하나의 흐름으로 연결해야 하나의 서비스가 됐다.**

---

## 마지막으로

탄천런은 잘 알고 시작한 프로젝트가 아니었다.

Git도 헷갈렸고,

백엔드 구조도 낯설었고,

데이터베이스도 정확히 몰랐고,

OAuth나 Vercel 환경은 거의 처음 경험했다.

바이브 코딩 역시 처음이었다.

그래서 정말 많이 물어보고,

여러 번 되돌아가고,

문서를 다시 만들고,

같은 개념을 반복해서 확인했다.

당시에는

**"왜 이렇게 하나하나 오래 걸리지?"**

라는 생각을 많이 했다.

하지만 프로젝트를 끝내고 나니 적어도 이전에는 보이지 않던 것들이 보이기 시작했다.

이제는 화면 하나를 보더라도 그 뒤에 데이터가 어디에서 오는지 생각하게 되고,

로그인 버튼을 보면 OAuth와 사용자 DB를 생각하게 되고,

배포된 사이트를 보면 환경변수와 Production 환경을 생각하게 된다.

아직 능숙하게 개발할 수 있다고 말하기는 어렵다.

하지만 이전보다

**무엇을 모르는지 조금 더 잘 알게 됐다.**

그리고 다음에는 무엇을 공부해야 하는지도 조금 더 명확해졌다.

탄천런에서 얻은 가장 큰 결과는 완성된 화면이나 코드가 아니라 이것이라고 생각한다.

**AI가 대신 코드를 작성해줄 수 있는 시대에도, 결국 프로젝트를 이해하고 판단하는 능력은 내가 계속 공부해야 한다는 것.**

그래서 다음 프로젝트에서는 이번보다 조금 덜 헤매고,

조금 더 이해하면서 만들고,

AI가 만들어준 결과를 내가 설명할 수 있는 범위를 조금씩 넓혀가고 싶다.
