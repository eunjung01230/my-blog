프로젝트를 만들 때 가장 먼저 신경 쓰게 되는 것은 보통 큰 화면이다.

```text
Home

Login

Detail

Settings
```

같은 페이지를 만들고,

버튼과 카드의 위치를 조정하고,

색상을 맞추고,

반응형까지 확인한다.

여기까지 끝나면

```text
디자인은 거의 끝났다.
```

고 생각하기 쉽다.

나도 그랬다.

그런데 어느 날 배포한 사이트를 브라우저에서 다시 보다가 작은 부분이 눈에 들어왔다.

브라우저 탭 왼쪽에 있는 아이콘이었다.

```text
[기본 아이콘] 프로젝트 이름
```

사이트 화면 안쪽은 꽤 정리되어 있는데,

탭에는 여전히 기본 아이콘이 보이니 이상하게 덜 완성된 느낌이 들었다.

기능에는 아무 문제가 없다.

클릭도 되고,

페이지도 열리고,

배포도 정상이다.

그런데 서비스 전체를 놓고 보면

```text
뭔가 하나 빠진 느낌
```

이 있었다.

그 작은 아이콘이 **favicon**이었다.

이번 글에서는 직접 블로그의 파비콘을 바꾸려고 하면서 알게 된

```text
파비콘이 무엇인지

왜 필요한지

어떤 이미지를 사용해야 하는지

왜 단순한 아이콘이 더 잘 보이는지

어떻게 적용하는지
```

를 정리해보려고 한다.

---

## Favicon이란?

Favicon은

```text
favorite icon
```

에서 나온 말이다.

웹사이트를 나타내는 아주 작은 아이콘이다.

브라우저의 탭이나 북마크 같은 곳에서 사이트를 구분하는 데 사용된다. [MDN](https://developer.mozilla.org/en-US/docs/Glossary/Favicon)에서도 favicon을 웹사이트를 나타내는 작은 아이콘으로 설명하며 브라우저 탭과 북마크 등에서 사용된다고 안내하고 있다.

예를 들어 브라우저에 여러 사이트를 띄워두면

```text
[G] Google

[▶] YouTube

[고양이] GitHub

[내 아이콘] MY-BLOG
```

처럼 아이콘만 보고도 사이트를 빠르게 구분할 수 있다.

---

## 처음에는 없어도 되는 장식이라고 생각했다

파비콘이 없다고 사이트가 작동하지 않는 것은 아니다.

```text
로그인

DB

API

라우팅

배포
```

같은 핵심 기능과도 직접적인 관계가 없다.

그래서 처음 프로젝트를 만들 때는 우선순위가 낮을 수밖에 없다.

나 역시

```text
이건 마지막에 해도 되겠지.
```

라고 생각하기 쉬웠다.

실제로 MVP 개발 단계에서는 그 판단이 틀린 것도 아니다.

핵심 기능을 만들기도 바쁜데

파비콘부터 붙잡고 있을 필요는 없다.

그런데 서비스가 어느 정도 완성되고 나면 이야기가 달라진다.

---

## 기능이 완성될수록 작은 부분이 더 보였다

처음에는

```text
페이지가 열리나?

버튼이 눌리나?

DB에 저장되나?
```

같은 것이 중요하다.

이 단계에서는 파비콘이 없어도 신경 쓰이지 않는다.

그런데 큰 기능이 하나씩 정리되면

다음부터 이런 것들이 눈에 들어오기 시작한다.

```text
브라우저 탭 아이콘

페이지 제목

공유 이미지

로딩 상태

Empty State

버튼 간격

작은 정렬 차이
```

기능 오류는 아니지만

서비스의 완성도에는 영향을 주는 요소들이다.

파비콘도 그중 하나였다.

---

## 파비콘은 화면 안에 없지만 서비스의 일부였다

처음에는 디자인이라고 하면

```text
웹페이지 안에서 보이는 것
```

만 생각했다.

하지만 사용자가 서비스를 만나는 위치는 페이지 내부만이 아니다.

```text
브라우저 탭

검색 결과

북마크

공유 링크

홈 화면
```

에서도 서비스를 볼 수 있다.

파비콘은 그중

```text
브라우저 밖에서
사이트를 대표하는 디자인
```

이라고 볼 수 있었다.

---

## 탭이 하나일 때는 별 차이를 못 느낄 수 있다

사이트 하나만 열어놓으면

```text
[아이콘] MY-BLOG
```

아이콘이 없어도 크게 불편하지 않다.

하지만 실제로 개발하다 보면 탭을 많이 열어둔다.

```text
GitHub

Vercel

Figma

ChatGPT

Claude

내 프로젝트

공식 문서
```

이렇게 열려 있으면

탭의 폭이 점점 좁아진다.

결국 사이트 제목도 일부만 보인다.

```text
[아이콘] MY...
```

이런 상황에서는 파비콘이 사이트를 구분하는 역할을 한다.

작은 아이콘 하나가 단순 장식 이상의 역할을 하는 것이다.

---

## 파비콘은 브랜드의 가장 작은 버전이었다

큰 로고는 많은 정보를 넣을 수 있다.

예를 들어

```text
[심볼] MY-BLOG
```

처럼

```text
심볼

서비스 이름

색상

문구
```

를 사용할 수 있다.

하지만 파비콘은 매우 작다.

그래서 로고 전체를 그대로 줄이면 잘 안 보일 수 있다.

예를 들어

```text
[심볼 + MY-BLOG]
```

를 아주 작게 만들면

```text
[작은 복잡한 덩어리]
```

처럼 보일 수 있다.

그래서 파비콘에서는

```text
브랜드의 핵심 요소 하나
```

만 남기는 것이 더 적합할 수 있었다.

---

## 로고와 파비콘은 반드시 같은 이미지일 필요가 없었다

처음에는

```text
로고 파일 하나 만들고
그걸 작게 줄이면 파비콘 아닌가?
```

라고 생각했다.

하지만 실제로는 역할이 다르다.

### 로고

```text
서비스 이름 표현

브랜드 분위기

조금 더 복잡한 형태 가능
```

### 파비콘

```text
아주 작은 크기

빠른 식별

단순한 형태
```

그래서

```text
Logo
→ 심볼 + 이름

Favicon
→ 심볼만
```

으로 나눌 수 있다.

---

## 작은 크기에서는 단순한 것이 더 강했다

아이콘을 크게 보면

```text
작은 선

그림자

미세한 색 변화

세부 장식
```

이 예뻐 보인다.

그런데 favicon 크기로 줄이면 거의 보이지 않는다.

오히려 형태를 방해한다.

예를 들어

```text
커피 컵
+
쿠폰
+
별
+
작은 글자
+
그림자
```

가 모두 들어간 아이콘은 크게 보면 의미가 많다.

하지만 아주 작게 만들면

```text
정체를 알 수 없는 복잡한 이미지
```

가 될 수 있다.

반대로

```text
컵 하나

혹은

단순한 심볼 하나
```

는 작은 상태에서도 알아보기 쉽다.

---

## 파비콘을 만들 때는 확대된 이미지만 보면 안 됐다

ChatGPT나 Figma에서 아이콘을 만들면

화면에서는 크게 본다.

```text
512 × 512

1024 × 1024
```

정도의 원본이 크게 표시된다.

그 상태에서는 아주 예쁘다.

하지만 실제로 사용할 곳은 훨씬 작다.

그래서 파비콘을 확인할 때는

```text
원본

↓

64px

↓

32px

↓

16px
```

정도로 계속 줄여보는 것이 좋았다.

---

## 작게 만들었을 때 질문할 것

```text
형태를 알아볼 수 있는가?

다른 아이콘과 구분되는가?

선이 너무 얇지는 않은가?

색상이 배경과 구분되는가?

세부 요소가 뭉개지지는 않는가?
```

큰 화면에서 예쁜 것보다

작은 화면에서 식별 가능한 것이 더 중요했다.

---

## 글자를 파비콘에 넣기 어려운 이유

예를 들어

```text
MY-BLOG
```

를 아이콘 안에 넣고 싶을 수 있다.

큰 로고에서는 잘 보인다.

하지만 favicon 크기로 줄이면

글자를 거의 읽을 수 없다.

그래서 파비콘에서는

```text
M

MB

심볼
```

처럼 아주 단순하게 사용하거나

글자를 완전히 빼는 방법도 있다.

특히 긴 서비스 이름 전체를 파비콘에 넣는 것은 피하는 편이 좋았다.

---

## 원형 아이콘을 사용할 때도 실제 결과를 확인해야 했다

내 블로그에서도 단순한 파일 아이콘보다

```text
작은 원형 심볼
```

처럼 서비스의 인상이 있는 아이콘을 쓰고 싶었다.

그런데 원형 아이콘도 그대로 적용한다고 끝이 아니다.

예를 들어 원본 이미지 자체에 이미

```text
큰 빈 여백
```

이 있다면,

favicon으로 표시될 때 실제 심볼은 더 작아진다.

```text
[        ●        ]

↓

[ · ]
```

처럼 보일 수 있다.

그래서 이미지 전체 크기뿐 아니라

**아이콘 내부에서 실제 심볼이 차지하는 비율**

도 중요했다.

---

## 이미지 주변 여백을 확인한다

예를 들어 512 × 512 이미지 안에

심볼이 200 × 200 정도만 차지한다면

브라우저가 16 × 16 수준으로 축소했을 때 실제 심볼은 매우 작게 보일 수 있다.

그래서

```text
Canvas는 정사각형

심볼은 중앙

불필요한 여백 최소화
```

가 도움이 된다.

---

## 파비콘은 정사각형으로 준비하는 것이 편했다

파비콘용 원본은 기본적으로

```text
1 : 1
```

비율로 만드는 것이 관리하기 쉽다.

[Google 검색에서 favicon으로 사용되기 위한 가이드](https://developers.google.com/search/docs/appearance/favicon-in-search) 역시 정사각형 비율을 요구하고, 검색 결과 등 다양한 표시 환경을 고려해 충분히 큰 원본을 사용하는 것을 권장한다.

예를 들어

```text
512 × 512
```

같은 큰 정사각형 원본을 만들어두고

필요한 크기로 변환하는 방식이다.

중요한 것은

```text
처음부터 16 × 16으로 그리는 것
```

이 아니라

```text
큰 원본 제작
↓
작은 환경에서 확인
```

하는 것이다.

---

## 파비콘 파일은 하나의 형식만 있는 것이 아니었다

파비콘을 찾아보면 여러 확장자를 만나게 된다.

```text
.ico

.png

.svg
```

등이다.

웹에서는 `<link rel="icon">`을 사용해 파비콘 파일을 지정할 수 있고, 브라우저는 `type`이나 `sizes` 같은 정보를 바탕으로 적절한 아이콘을 선택할 수 있다.

처음에는

```text
favicon은 무조건 .ico
```

라고 생각했는데,

현대 웹에서는 PNG 등도 널리 사용할 수 있다.

---

## 그렇다면 어떤 형식을 쓰면 될까?

처음 프로젝트를 만드는 단계에서는

```text
PNG

또는

ICO
```

정도로 시작해도 이해하기 쉽다.

예를 들어

```text
favicon.png
```

파일을 준비하고

HTML에서는

```html
<link rel="icon" href="/favicon.png">
```

처럼 연결할 수 있다.

[MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel)과 [Google Search 문서](https://developers.google.com/search/docs/appearance/favicon-in-search)에서도 favicon은 `<link rel="icon">` 형태로 연결하는 방식을 안내하고 있다.

---

## favicon.ico는 왜 많이 보일까?

오래된 프로젝트를 보면

```text
favicon.ico
```

파일이 자주 있다.

favicon 자체가 오래된 웹 기능이기 때문에

`ICO` 형식이 전통적으로 많이 사용되었다.

그래서 프로젝트 루트에서

```text
favicon.ico
```

를 발견하는 일이 많다.

처음에는

```text
이 파일 뭐지?
```

하고 지나가기 쉽다.

하지만 바로 사이트 아이콘을 담당하는 파일일 수 있다.

---

## 프레임워크마다 위치와 적용 방식은 달라질 수 있다

순수 HTML이라면 `<head>` 안에서 직접

```html
<link rel="icon" href="/favicon.ico">
```

를 지정하는 방식을 이해하기 쉽다.

하지만

```text
Jekyll

Next.js

React 기반 프레임워크
```

처럼 사용하는 환경에 따라 파일 위치나 Metadata 처리 방식은 달라질 수 있다.

그래서

```text
인터넷에서 본 코드를 그대로 복사
```

하기보다

```text
현재 프로젝트가 어떤 구조인가?
```

를 먼저 확인하는 편이 좋았다.

---

## 기존 favicon이 이미 있을 수도 있다

새 프로젝트를 만들면 기본 favicon이 들어 있는 경우가 있다.

그래서 내가 새 파일을 추가했는데도

기존 아이콘이 계속 나올 수 있다.

이럴 때는 먼저

```text
현재 favicon 파일이 어디에 있는가?

HTML이나 Layout에서 어떤 파일을 참조하는가?
```

를 확인해야 한다.

무조건 새 코드부터 추가하면

파비콘 설정이 중복될 수도 있다.

---

## 실제 프로젝트에서는 먼저 기존 구조를 확인한다

예를 들어 Claude에게 수정시킨다면

```text
현재 프로젝트의 favicon 설정을 먼저 확인해줘.

기존 favicon 파일과
<head> 또는 metadata 설정을 확인하고,

새로운 설정을 중복 추가하지 말고
현재 구조에 맞는 방식으로 교체해줘.
```

처럼 요청할 수 있다.

이 방식이

```text
favicon 넣어줘.
```

보다 안전하다.

---

## 브라우저에서 바로 안 바뀔 수도 있었다

favicon을 교체했는데

페이지를 새로고침해도 이전 아이콘이 그대로 보일 수 있다.

그러면

```text
적용이 실패했나?
```

라고 생각하게 된다.

파비콘은 브라우저 캐시 등의 영향으로 이전 이미지가 잠시 남아 보일 수 있다.

그래서 적용 후에는

```text
새로고침

강력 새로고침

새 탭

시크릿 창

배포된 URL
```

등에서 확인해볼 수 있다.

---

## 로컬에서 바뀌었다고 배포까지 끝난 것은 아니다

개발 환경에서는 새 favicon이 보인다.

하지만 실제 사이트에는 이전 것이 남아 있을 수 있다.

```text
Local
→ 새 아이콘

Production
→ 기존 아이콘
```

이럴 수 있다.

따라서 실제 배포가 끝난 뒤

배포 URL에서도 확인해야 한다.

특히 블로그처럼 실제 공개 사이트라면

```text
브라우저 탭

직접 URL 접속

모바일
```

에서 확인해보는 편이 좋다.

---

## 검색 결과는 바로 바뀌지 않을 수도 있다

favicon은 브라우저 탭에서만 사용되는 것은 아니다.

검색 서비스가 사이트의 favicon을 검색 결과에 사용하는 경우도 있다.

[Google](https://developers.google.com/search/docs/appearance/favicon-in-search)은 사이트의 `<link rel="icon">` 정보를 사용해 검색 결과의 favicon 후보를 파악하지만, 변경 내용이 반영되려면 다시 크롤링하고 처리하는 시간이 필요할 수 있다고 안내한다.

즉

```text
사이트에서 favicon 변경
↓
Google 검색 결과도 즉시 변경
```

되는 것은 아니다.

---

## 검색 결과에서도 브랜드를 구분하는 작은 표시였다

검색 결과에는 사이트 이름과 함께 작은 아이콘이 표시될 수 있다.

이때 기본 아이콘보다

내 사이트를 나타내는 아이콘이 있다면

여러 결과 사이에서 구분하기 쉬워진다.

[Google](https://developers.google.com/search/docs/appearance/favicon-in-search) 역시 사용자가 검색 결과를 훑을 때 사이트를 빠르게 식별할 수 있도록 favicon이 웹사이트 브랜드를 시각적으로 나타내야 한다고 안내한다.

그래서 파비콘은 단순히

```text
브라우저 탭 꾸미기
```

만의 문제는 아니었다.

---

## Apple Touch Icon도 따로 존재했다

웹 아이콘을 공부하다 보면

```text
apple-touch-icon
```

이라는 것도 보게 된다.

이는 웹사이트를 Apple 기기의 홈 화면 등에 저장할 때 사용할 수 있는 별도의 아이콘 설정이다. [MDN](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/Webpage_metadata)에서도 일반 favicon과 별도로 `apple-touch-icon` 같은 아이콘을 지정할 수 있다고 설명한다.

예를 들어

```html
<link
  rel="apple-touch-icon"
  href="/apple-touch-icon.png">
```

같은 형태다.

처음 파비콘을 공부할 때부터 모든 플랫폼 아이콘 규칙을 완벽하게 구현할 필요는 없다.

다만

```text
favicon 하나가
모든 환경의 아이콘을 완전히 책임지는 것은 아닐 수도 있다.
```

정도로 이해해두면 좋았다.

---

## 파비콘을 만들 때 서비스 색상을 그대로 써도 될까?

가능하다.

하지만 작은 아이콘에서는 대비가 더 중요하다.

예를 들어

```text
연한 베이지 심볼

+

흰색 배경
```

이면

큰 로고에서는 분위기가 좋지만

작은 탭에서는 거의 안 보일 수 있다.

반대로

```text
진한 심볼

+

밝은 배경
```

처럼 대비가 명확하면 작은 크기에서도 잘 보인다.

그래서 파비콘에서는

```text
브랜드 색 유지

+

작은 크기 가독성
```

을 같이 확인해야 했다.

---

## 다크모드 탭도 생각해볼 수 있었다

브라우저 UI는 사용자의 설정에 따라

```text
밝은 테마

어두운 테마
```

일 수 있다.

예를 들어 검은색 심볼인데 배경이 완전히 투명하다면

어두운 브라우저 환경에서는 형태가 약하게 보일 수도 있다.

그래서

```text
밝은 배경

어두운 배경
```

양쪽에서 아이콘이 어느 정도 구분되는지 확인하는 것도 도움이 된다.

---

## 투명 배경이 항상 정답은 아니었다

로고를 만들 때는

```text
투명 배경
```

이 편하다.

하지만 favicon에서는 경우에 따라

```text
배경 색상이 있는 정사각형 또는 원형 아이콘
```

이 더 잘 보일 수도 있다.

예를 들어

```text
[갈색 원] + [밝은 심볼]
```

처럼 만든다면

브라우저 테마와 상관없이 비교적 일정하게 보일 수 있다.

즉

```text
투명해야 고급스럽다.
```

가 아니라

```text
작게 표시됐을 때 잘 보이는가?
```

가 우선이다.

---

## ChatGPT로 파비콘 원본을 만들 수도 있었다

「ChatGPT로 이미지·아이콘 만들기」에서 ChatGPT로 이미지와 아이콘을 만드는 방법을 정리했다.

파비콘도 비슷하게 만들 수 있다.

예를 들어

```text
개발 블로그용 favicon을 만들어줘.

1:1 비율의 단순한 심볼.

아주 작은 브라우저 탭에서도
형태를 알아볼 수 있도록
요소는 최대한 단순하게.

텍스트 없음.

그림자와 복잡한 배경 없음.
```

처럼 요청할 수 있다.

그리고 첫 결과를 바로 사용하지 않고

작게 줄여본다.

---

## AI가 만든 아이콘은 특히 단순화가 필요할 수 있었다

AI 이미지 생성은 큰 화면에서 보기 좋은 디테일을 많이 만들어줄 수 있다.

```text
그림자

작은 점

선

빛 효과

미세한 질감
```

같은 것들이다.

앱 아이콘이라면 어느 정도 활용할 수 있지만,

favicon에서는 대부분 사라진다.

그래서

```text
현재 형태는 유지하되

세부 장식을 모두 제거하고

선은 더 굵게,

심볼은 하나만 남겨줘.
```

처럼 다시 단순화할 수 있다.

---

## 파비콘에서는 "더 예쁘게"보다 "더 단순하게"가 더 자주 필요했다

이미지 작업을 하면 보통

```text
조금 더 예쁘게 해줘.
```

라고 수정하고 싶어진다.

favicon에서는 반대일 수 있다.

```text
조금 더 단순하게.

요소 하나 빼기.

색상 줄이기.

선 굵게.

여백 줄이기.
```

같은 수정이 더 효과적일 수 있다.

작은 UI일수록

```text
더하기
```

보다

```text
빼기
```

가 중요했다.

---

## 파비콘과 앱 아이콘도 구분해야 했다

둘 다 작은 아이콘처럼 보인다.

하지만 사용 위치가 다르다.

앱 아이콘은 스마트폰 홈 화면 등에서 상대적으로 크게 표시되고,

브랜드 표현을 위한 공간도 favicon보다 넓다.

favicon은 브라우저 탭처럼 훨씬 작은 영역에서 보일 수 있다.

따라서

```text
App Icon
→ 어느 정도 디테일 가능

Favicon
→ 더 강한 단순화 필요
```

라고 생각할 수 있다.

하나의 기본 심볼에서 파생하되

완전히 같은 파일을 사용할 필요는 없다.

---

## 같은 브랜드의 여러 크기 버전을 생각하게 됐다

예를 들어 기본 심볼이 있다고 해보자.

```text
Original Symbol
```

그것을

```text
Logo
→ 심볼 + 서비스명

App Icon
→ 심볼 + 배경

Favicon
→ 더 단순화된 심볼
```

로 발전시킬 수 있다.

이렇게 하면

형태는 연결되면서도

사용 환경에는 각각 맞출 수 있다.

---

## 파비콘 파일명도 명확하게 관리한다

프로젝트에 이미지가 많아지면

```text
icon.png

icon2.png

final-icon.png

final-real.png
```

처럼 관리하기 쉽다.

대신

```text
favicon.ico

favicon.png

apple-touch-icon.png
```

처럼 역할이 분명한 이름을 사용하면 이해하기 쉽다.

나중에 다른 사람이 Repository를 봐도

```text
아, 사이트 아이콘이구나.
```

라고 바로 알 수 있다.

---

## 원본 파일과 실제 사용 파일을 나눠두는 것도 좋았다

예를 들어 원본 AI 이미지가

```text
1024 × 1024
```

라고 하자.

실제 favicon으로 사용할 파일은 별도로 가공할 수 있다.

```text
design/
└─ favicon-source.png

site/
└─ favicon.png
```

처럼 원본을 남겨두면

나중에 다시 크기를 바꾸거나

다른 형태로 만들기 편하다.

---

## 파비콘을 바꿀 때 로고도 같이 바꿔야 할까?

반드시 그렇지는 않다.

파비콘만 서비스의 기본 아이콘으로 남아 있었고,

페이지 내부 로고는 이미 괜찮다면

파비콘만 수정할 수도 있다.

반대로 favicon을 만들면서

```text
현재 로고와 너무 다른데?
```

라는 생각이 든다면

브랜드 전체를 다시 볼 수도 있다.

하지만 작은 수정 하나 때문에

서비스 전체 디자인을 무조건 바꿀 필요는 없다.

---

## 디자인 일관성은 "완전히 똑같음"과 달랐다

예를 들어

```text
Logo
→ 가로형

Favicon
→ 원형

OG Image
→ 카드형
```

으로 생김새가 다를 수 있다.

그렇더라도

```text
같은 심볼

같은 주요 색상

같은 분위기
```

가 유지되면

같은 서비스라고 느낄 수 있다.

일관성은 모든 이미지를 똑같이 복사하는 것이 아니었다.

---

## 파비콘을 적용하고 나면 브라우저 탭을 다시 보게 됐다

화면 내부에서는 아주 작은 변화다.

아니,

정확히 말하면 페이지 내부에서는 보이지도 않는다.

그런데 브라우저 전체를 보면 차이가 느껴진다.

```text
Before

[기본 아이콘] MY-BLOG
```

에서

```text
After

[내 심볼] MY-BLOG
```

로 바뀐다.

사이트가

```text
내가 만든 HTML 페이지
```

에서

```text
하나의 이름과 얼굴이 있는 사이트
```

처럼 느껴질 수 있다.

---

## 작은 요소인데 생각보다 기억에 남았다

사용자는 사이트의 세부 디자인 값을 기억하지 않는다.

```text
Border Radius가 12px이었는지

Padding이 20px이었는지
```

기억하지 않는다.

하지만

```text
그 갈색 아이콘 있는 사이트

그 고양이 아이콘 있는 사이트
```

처럼 시각적 특징은 기억할 수 있다.

파비콘은 굉장히 작지만

서비스를 반복해서 볼 때 계속 노출되는 이미지다.

---

## 파비콘이 없다고 나쁜 사이트는 아니다

이 부분도 중요하다.

파비콘 하나로

```text
좋은 서비스

나쁜 서비스
```

가 결정되는 것은 아니다.

기능이 제대로 작동하지 않는데

파비콘만 예쁘게 만든다고 의미가 없다.

그래서 우선순위는 여전히

```text
핵심 기능

↓

사용성

↓

UI

↓

브랜딩 디테일
```

이라고 생각한다.

다만 위쪽 작업들이 어느 정도 끝났는데도

기본 favicon을 그대로 두고 있다면

비교적 적은 작업으로 완성도를 높일 수 있는 부분이다.

---

## 언제 파비콘을 만드는 것이 좋을까?

내 기준에서는

프로젝트 시작 직후 꼭 만들 필요는 없다.

초기에는

```text
서비스 기능

화면 구조

핵심 디자인
```

이 바뀔 수 있기 때문이다.

브랜드 방향 자체가 아직 결정되지 않았는데

favicon만 계속 수정하는 것은 효율적이지 않다.

그래서

```text
서비스 방향 결정
↓
주요 디자인 확정
↓
기본 심볼 결정
↓
favicon 제작
```

정도가 자연스러웠다.

---

## MVP에서도 최종 공개 전에는 확인하고 싶었다

내부 테스트 단계에서는 기본 favicon이어도 큰 문제는 없다.

하지만

```text
포트폴리오 공개

프로젝트 발표

실제 배포

블로그 운영
```

처럼 외부 사람이 접속하기 시작한다면

한 번쯤 확인하고 싶다.

```text
favicon이 있는가?

서비스 디자인과 어울리는가?

작은 크기에서도 보이는가?
```

정도다.

---

## 파비콘을 확인하는 간단한 체크리스트

내가 파비콘을 만들 때는 이렇게 확인할 수 있다.

```text
□ 1:1 비율의 원본인가?

□ 작은 크기에서도 형태를 알아볼 수 있는가?

□ 불필요한 글자가 들어가 있지 않은가?

□ 선이 너무 얇지 않은가?

□ 내부 요소가 너무 많지 않은가?

□ 이미지 주변에 과도한 여백이 없는가?

□ 밝은 브라우저 환경에서 보이는가?

□ 어두운 환경에서도 어느 정도 구분되는가?

□ 기존 로고와 완전히 동떨어져 있지 않은가?

□ 실제 배포 사이트에서 정상적으로 보이는가?
```

---

## 코드에서도 확인할 것

구현 측면에서는 이런 부분을 확인할 수 있다.

```text
□ 기존 favicon 설정이 있는가?

□ 기존 설정과 중복되지 않는가?

□ 파일 경로가 올바른가?

□ 배포 결과에도 파일이 포함되는가?

□ 로컬뿐 아니라 실제 배포 URL에서도 보이는가?

□ 변경 후 이전 favicon이 캐시에 남아 있는 것은 아닌가?
```

단순히 파일 하나 추가했다고 끝내지 않는 것이다.

---

## Google 검색까지 생각한다면

검색 결과에서도 favicon 사용을 고려한다면

몇 가지 조건이 있다.

[Google](https://developers.google.com/search/docs/appearance/favicon-in-search)은 검색 결과용 favicon에 대해

```text
정사각형 비율

크롤링 가능한 파일

안정적인 favicon URL

사이트를 대표하는 이미지
```

등을 안내하고 있다.

다만 조건을 충족한다고 검색 결과에 반드시 favicon이 표시된다고 보장되는 것은 아니다.

즉

```text
favicon 설정
=
검색 결과 즉시 확정
```

은 아니다.

---

## 처음 공부할 때는 너무 복잡하게 시작하지 않아도 됐다

favicon을 검색하다 보면

```text
ICO

PNG

SVG

Apple Touch Icon

Manifest

PWA Icon

여러 해상도
```

등이 계속 나온다.

그러면

```text
favicon 하나 넣는데
왜 이렇게 복잡하지?
```

싶어진다.

처음에는 모든 것을 한 번에 공부할 필요는 없다.

우선

```text
1. 정사각형 아이콘 만들기

2. 작은 크기에서 확인

3. favicon으로 연결

4. 브라우저에서 확인
```

정도부터 하면 된다.

필요해질 때 다른 환경용 아이콘을 추가할 수 있다.

---

## 파비콘을 공부하면서 다시 느낀 것

처음에는 이것도 단순한 파일 작업이라고 생각했다.

```text
favicon.png 넣기

↓

코드 연결

↓

끝
```

하지만 디자인 관점에서 보면 더 많은 판단이 들어간다.

```text
어떤 이미지가 우리 서비스를 대표하는가?

작은 크기에서는 무엇을 빼야 하는가?

로고와 얼마나 같아야 하는가?

어떤 색상이 잘 보이는가?

사용자가 반복해서 봐도 기억할 수 있는가?
```

작은 아이콘 하나에도

앞에서 공부한 디자인 원칙들이 다시 등장했다.

---

## 작은 공간에서는 우선순위가 더 중요했다

favicon에는 공간이 거의 없다.

그래서 모든 것을 넣을 수 없다.

결국

```text
가장 중요한 형태 하나
```

를 골라야 한다.

「버튼과 정보의 우선순위」에서 정보 우선순위를 정했던 것처럼

파비콘에서도

```text
브랜드에서 무엇을 남길 것인가?
```

를 정해야 한다.

공간이 작아질수록 우선순위가 더 명확해야 했다.

---

## 단순화는 정보를 버리는 것이 아니었다

처음에는 요소를 빼면

```text
서비스 의미가 약해지는 것 아닌가?
```

라고 생각했다.

하지만 작은 아이콘에서는

요소가 많을수록 오히려 아무것도 보이지 않을 수 있다.

그래서

```text
정보를 줄인다
```

가 아니라

```text
핵심 형태만 남긴다
```

라고 생각하는 편이 맞았다.

---

## 파비콘도 실제 환경에서 확인해야 했다

Figma에서 512px로 보고

```text
완성.
```

하면 안 된다.

실제 브라우저 탭에 넣어봐야 한다.

```text
Chrome

브라우저 탭

북마크

배포 사이트
```

등에서 보고

```text
너무 작지 않은지

색이 잘 보이는지

모양이 뭉개지지 않는지
```

확인한다.

「실제 시연 후 발견한 UI 문제」에서 이야기했던

```text
Figma
↓
구현
↓
실제 시연
```

과 같은 과정이다.

---

## 결국 작은 디테일도 사용자 경험이었다

파비콘을 바꾼다고

서비스의 핵심 기능이 좋아지는 것은 아니다.

하지만 사용자가 서비스를 경험하는 과정에는 포함된다.

```text
검색해서 발견

↓

링크 클릭

↓

브라우저 탭 열림

↓

페이지 사용

↓

북마크
```

사용자가 사이트를 보는 모든 순간 중

파비콘이 보이는 순간도 있다.

그래서 화면 안쪽만 디자인하고 끝나는 것이 아니라

**서비스를 만나는 주변 환경까지 디자인의 범위로 볼 수 있었다.**

---

## 내가 파비콘을 만들 때 지키고 싶은 기준

정리하면 다음과 같다.

```text
1. 파비콘을 단순 장식으로만 생각하지 않는다.

2. 서비스의 핵심 심볼을 사용한다.

3. 로고 전체를 그대로 축소하지 않는다.

4. 작은 크기를 기준으로 단순화한다.

5. 긴 텍스트를 넣지 않는다.

6. 불필요한 세부 장식을 제거한다.

7. 심볼 주변의 과도한 여백을 줄인다.

8. 밝고 어두운 환경에서 확인한다.

9. 실제 브라우저 탭에서 확인한다.

10. 기존 favicon 설정을 먼저 확인한 뒤 수정한다.

11. 로컬뿐 아니라 배포 사이트에서도 확인한다.

12. 핵심 기능이 안정된 뒤 브랜딩 디테일을 다듬는다.
```

## 마무리

처음에는 파비콘을

```text
있어도 되고
없어도 되는 작은 이미지
```

라고 생각했다.

기능적으로만 보면 맞다.

파비콘이 없어도 웹사이트는 작동한다.

하지만 실제로 사이트를 완성해놓고 보면

그 작은 이미지 하나가 생각보다 눈에 들어온다.

```text
기본 아이콘

vs

내 서비스를 나타내는 아이콘
```

의 차이다.

파비콘을 직접 바꾸려고 하면서 알게 된 것은

단순히

```text
favicon 파일 넣는 방법
```

만은 아니었다.

작은 공간일수록 더 많이 넣는 것이 아니라

```text
무엇을 남길 것인가
```

를 결정해야 했다.

결국 파비콘도 디자인이었다.

화면 안에서 사용자가 누르는 UI는 아니지만

서비스를 식별하고,

기억하고,

조금 더 완성된 하나의 사이트처럼 느끼게 만드는

**가장 작은 디자인 요소 중 하나**였다.

그리고 브라우저 탭보다 한 단계 더 밖으로 나가면

또 하나의 이미지가 있다.

내 사이트 주소를

```text
카카오톡

Discord

Slack

SNS
```

등에 공유했을 때 나타나는

```text
제목

설명

큰 미리보기 이미지
```

다.

처음에는 URL만 공유하면 끝이라고 생각했지만,

이 미리보기 역시 다른 사람이 내 서비스를 처음 만나는 화면이 될 수 있다.
