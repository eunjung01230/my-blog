## 들어가며

처음에 나는 Git을 "코드 저장하고 GitHub에 올리는 것"이라고 생각했다. 명령어 몇 개를 순서대로 치면 끝나는 작업인 줄 알았다.

그런데 팀 프로젝트를 해보니 그게 아니었다. 분명히 commit을 했는데 GitHub에는 없었고, push를 했는데 main에는 반영되지 않았고, PR이 merge됐는데 내 VS Code의 코드는 그대로였다.

commit, push, branch, PR, merge, main, origin/main이 전부 **서로 다른 상태**를 가리키고 있었던 것이다. 하나씩 따로 외워서는 계속 헷갈릴 수밖에 없었다.

그래서 이번에는 명령어를 외우는 대신, 내 변경사항이 **어디에서 어디로 이동하는지**를 하나의 흐름으로 이어서 정리해보려고 한다. 이 글은 프로젝트 회고가 아니라 개념 정리 노트다.

## 1. Git과 GitHub는 무엇이 다른가

가장 먼저 구분해야 할 둘이다.

| 구분 | 무엇인가 |
|---|---|
| Git | 저장소에서 변경 이력을 관리하는 버전 관리 시스템 |
| GitHub | Git 저장소를 원격에 두고 공유하며 협업 기능을 제공하는 서비스 |

쉽게 말하면 이렇다.

```text
Git      →  변경 기록을 관리하는 도구
GitHub   →  그 Git 저장소를 팀과 공유하는 장소
```

**GitHub가 Git 자체는 아니다.** Git은 내 컴퓨터에서 GitHub 없이도 혼자 쓸 수 있다. 인터넷이 끊겨도 commit은 된다. 반대로 GitHub는 Git 저장소를 다루기 위한 서비스이고, 여기에 더해 PR이나 Issue 같은 협업 기능을 얹어준다.

내가 이해한 방식으로 정리하면, **Git은 기록 방식이고 GitHub는 그 기록을 모아두고 함께 보는 공간**이다.

## 2. Repository란 무엇인가

**Repository(저장소, 줄여서 Repo)** 는 **Git이 변경 이력을 관리하는 단위**다. 보통 프로젝트 하나가 저장소 하나다.

중요한 건 저장소가 **한 곳에만 있는 게 아니라는 점**이다.

| 구분 | 어디에 있는가 |
|---|---|
| Local Repository | 내 컴퓨터 안에 있는 저장소 |
| Remote Repository | GitHub 같은 원격 서버에 있는 저장소 |

```text
내 컴퓨터
Local Repository

        (서로 주고받는다)

GitHub
Remote Repository
```

둘은 **같은 프로젝트의 복사본이지만 서로 다른 저장소**다. 자동으로 동기화되지 않는다. 내가 명령을 내려서 보내거나 받아와야 내용이 오간다.

앞으로 나올 push, pull, fetch가 전부 이 둘 사이를 오가는 동작이다. **지금 내 변경사항이 둘 중 어디에 있는가**를 계속 의식하는 것이 이 글의 핵심이다.

## 3. Working Tree란 무엇인가

**Working Tree(작업 트리)** 는 **지금 내가 직접 열어서 수정하고 있는 파일들의 상태**다. VS Code에서 보고 있는 그 파일들이다.

```text
코드 수정
↓
Working Tree 변경 발생
```

여기서 짚어둘 점이 있다. **파일을 수정하고 저장했다고 해서 Git에 기록된 것은 아니다.**

파일 저장은 그냥 내 컴퓨터의 디스크에 쓰는 것이다. Git은 그 변화를 알아차리기는 하지만, "변경된 파일이 있다"고 알려줄 뿐 아직 기록으로 남기지는 않았다.

Git에 기록되려면 앞으로 두 단계를 더 거쳐야 한다.

## 4. Staging Area는 왜 있는가

**Staging Area(스테이징 영역)** 는 **Working Tree에서 수정한 것 중, 다음 commit에 포함할 변경사항을 골라 담아두는 공간**이다. `git add`가 여기에 담는 동작이다.

```text
Working Tree
↓ git add
Staging Area
↓ git commit
Local Repository
```

처음에는 이 단계가 왜 필요한지 몰랐다. 수정한 걸 그냥 다 기록하면 되지 않나 싶었다.

그런데 실제로 작업해보면 한 번에 여러 가지를 건드리게 된다. 기능을 만들다가 오타도 고치고, 설정 파일도 잠깐 바꿔보고, 테스트용 코드도 넣어본다. 이걸 전부 하나의 기록으로 묶으면 나중에 **"이 commit이 무엇을 바꿨는지"** 를 알 수 없다.

Staging Area가 있어서 **"이번 기록에는 이 파일들만 포함"** 이라고 고를 수 있다. 장바구니에 담았다가 결제하는 것과 비슷하다. 담는 것과 결제하는 것이 나뉘어 있어야 무엇을 살지 조정할 수 있다.

## 5. Commit이란 무엇인가

**Commit(커밋)** 은 **Staging Area에 담긴 변경사항을 Git의 기록으로 남기는 것**이다.

commit을 "저장 버튼"이라고 이해하면 안 된다. 파일 저장은 현재 상태를 덮어쓰는 것이지만, commit은 **"이 시점의 변경사항을 이런 이유로 만들었다"는 기록 하나를 역사에 추가하는 것**이다. 그래서 commit에는 메시지가 붙는다.

기록으로 남았기 때문에 나중에 그 시점으로 돌아가 볼 수도 있고, 누가 언제 왜 바꿨는지 확인할 수도 있다.

여기까지의 차이를 정리하면 이렇다.

```text
파일 저장
       (같지 않다)
git add
       (같지 않다)
commit
```

| 단계 | 무엇이 일어났는가 |
|---|---|
| 파일 저장 | 디스크에 내용이 쓰였다. Git 기록과는 무관하다 |
| git add | 다음 기록에 포함할 것으로 선택했다 |
| commit | Git 역사에 기록 하나가 추가됐다 |

## 6. Commit했다고 GitHub에 올라가는 것은 아니다

이게 처음에 가장 많이 헷갈렸던 부분이다.

```text
파일 수정
↓
git add
↓
commit
↓
아직 Local        여기까지는 전부 내 컴퓨터 안의 일이다
```

commit은 **Local Repository에 기록하는 동작**이다. 인터넷이 끊겨 있어도 commit은 된다. 그 말은 곧, **commit만으로는 GitHub에 아무 일도 일어나지 않는다**는 뜻이다.

내가 commit을 열 개 쌓아놔도 팀원은 그중 하나도 볼 수 없다. 전부 내 컴퓨터 안에만 있기 때문이다.

GitHub까지 보내려면 다음 단계가 필요하다.

## 7. Push란 무엇인가

**Push(푸시)** 는 **Local Repository의 commit들을 Remote Repository로 보내는 과정**이다.

```text
Local Repository
↓ git push
Remote Repository (GitHub)
```

이제 팀원도 내 변경사항을 볼 수 있게 된다.

### push는 main에 합치는 것이 아니다

여기서 또 하나 중요한 구분이 있다.

```text
push
       (같지 않다)
main에 merge
```

내가 `feature/login`이라는 branch에서 작업하고 push했다면, **GitHub의 `feature/login` branch에 올라간 것**이다. main에는 아무 변화가 없다.

처음에는 push하면 코드가 프로젝트에 반영되는 줄 알았다. 하지만 push는 **"내 작업 갈래를 원격에도 올려두는 것"** 까지다. 그 작업을 main에 합칠지는 이후에 PR과 merge를 거쳐 따로 결정된다.

## 8. Branch란 무엇인가

**Branch(브랜치)** 는 **기존 코드에서 갈라져 나와 독립적으로 작업할 수 있는 갈래**다.

```text
main
├─ feature/login
├─ feature/map
└─ feature/settings
```

왜 나눌까? **작업이 서로 섞이지 않게 하기 위해서**다.

세 사람이 각각 로그인, 지도, 설정 기능을 만든다고 하자. 모두 같은 곳에서 작업하면 누구의 코드가 어디까지인지 알 수 없고, 한 사람의 미완성 코드가 다른 사람의 작업을 망가뜨릴 수 있다.

branch를 나누면 이런 것들이 가능해진다.

| 장점 | 설명 |
|---|---|
| 독립 작업 | 다른 사람 작업에 영향을 주지 않는다 |
| 개별 검토 | 변경사항을 기능 단위로 따로 볼 수 있다 |
| 안전한 실험 | 잘못되면 그 branch만 버리면 된다 |
| 기준 보호 | main은 정상 동작하는 상태로 유지할 수 있다 |

한 가지 짚어둘 점이 있다. **branch를 만든다고 새 저장소가 생기는 게 아니다.** 같은 저장소 안에서 갈래만 나뉘는 것이다. 폴더가 복사되지도 않는다.

## 9. main은 무엇인가

**main**은 프로젝트의 **기준이 되는 branch로 많이 사용되는 이름**이다.

여기서 오해하기 쉬운 부분이 있다. **main이 Git에서 특별한 힘을 가진 branch는 아니다.** 기술적으로는 다른 branch와 똑같다. 단지 팀이 "여기를 기준으로 삼자"고 약속했기 때문에 기준이 되는 것이다.

이름도 반드시 main이어야 하는 건 아니다. 예전에는 master를 많이 썼고, 프로젝트에 따라 다른 이름을 쓰기도 한다. 기준 branch가 두 개 이상인 경우도 있다.

그래서 **"main이니까 자동으로 특별하다"가 아니라 "팀이 기준으로 정했으니 함부로 건드리지 않는다"** 로 이해하는 편이 정확했다.

## 10. HEAD란 무엇인가

**HEAD**는 **지금 내가 어디에서 작업하고 있는지를 가리키는 표시**다.

```text
현재 feature/login 에서 작업 중
→ HEAD는 그 작업 위치를 가리킨다
```

branch를 바꾸면 HEAD도 따라 움직이고, 그에 맞춰 Working Tree의 파일 내용도 그 branch의 상태로 바뀐다.

"분명히 코드를 고쳤는데 사라졌다"고 느낄 때, 사실은 **다른 branch로 이동해서 그 branch의 파일을 보고 있는 경우**가 많았다. HEAD가 어디를 가리키는지 확인하면 그런 혼란이 줄어든다.

지금 단계에서는 **"현재 위치 표시"** 정도로만 알아둬도 충분했다.

## 11. origin은 무엇인가

`git push origin main` 같은 명령에서 나오는 그 **origin**이다.

**origin은 원격 저장소에 붙은 별칭(이름표)** 이다. 저장소를 clone하면 보통 자동으로 이 이름이 붙는다.

원격 저장소 주소는 길다. 매번 전체 주소를 치는 대신 짧은 이름을 붙여두고 그걸 쓰는 것이다.

여기서 단정하면 안 되는 것이 있다.

- **origin이 GitHub의 다른 이름은 아니다.** GitHub가 아닌 다른 원격 저장소에도 origin이라는 이름을 붙일 수 있다.
- **이름이 반드시 origin일 필요도 없다.** 관례적으로 많이 쓰는 기본 이름일 뿐이고, 원격을 여러 개 등록하면 upstream 같은 다른 이름도 함께 쓰인다.

그래서 **origin은 "내가 등록해둔 원격 저장소 중 하나를 부르는 이름"** 이라고 이해하는 게 맞았다.

## 12. main과 origin/main은 무엇이 다른가

이 둘의 차이를 이해하고 나서 Git이 훨씬 덜 헷갈리게 됐다.

| 이름 | 무엇인가 |
|---|---|
| main | 내 Local Repository에 있는 main branch |
| origin/main | 마지막으로 원격 정보를 가져왔을 때 확인한 원격 main의 상태 |

쉽게 말하면 이렇다.

```text
main         →  내 컴퓨터의 main
origin/main  →  내가 마지막으로 확인한 원격 main 상태
```

`origin/main`은 **remote-tracking branch**라고 부른다. 이름에 "tracking(추적)"이 들어간 이유가 있다. 원격을 실시간으로 비추는 거울이 아니라, **내 Git이 마지막으로 확인해서 기억해둔 기록**이기 때문이다.

여기서 조심할 점이 있다.

**`origin/main`을 "GitHub 서버에 있는 branch 그 자체"라고 단정하면 안 된다.** 내가 원격 정보를 가져온 이후에 팀원이 새 commit을 올렸다면, GitHub의 실제 main은 앞서 나가 있는데 내 `origin/main`은 예전 상태 그대로다.

```text
GitHub의 실제 main     A → B → C → D    팀원이 D를 올렸다
내 origin/main         A → B → C        나는 아직 D를 모른다
내 main                A → B            나는 C도 안 받았다
```

이렇게 **세 가지가 서로 다를 수 있다.** 그래서 원격 상태를 알고 싶으면 먼저 정보를 가져오는 동작이 필요하다. 그게 다음에 나올 fetch다.

## 13. Clone은 무엇인가

**Clone(클론)** 은 **Remote Repository를 처음으로 내 컴퓨터에 가져오면서 Git 저장소로 만드는 것**이다.

단순히 파일을 내려받는 것과는 다르다.

| 구분 | 받아오는 것 |
|---|---|
| 파일 다운로드 | 현재 시점의 파일들만 |
| Clone | 파일 + 전체 commit 기록 + 원격 저장소 연결 정보 |

clone을 하면 그 순간부터 그 폴더는 Git 저장소가 된다. 과거 commit을 볼 수 있고, `origin`이라는 이름으로 원격과 연결되어 있어서 바로 push나 pull을 할 수 있다.

압축 파일로 코드만 받으면 이런 것들이 전부 없다. 기록도 없고 원격 연결도 없어서 협업에 쓸 수 없다.

## 14. Fetch란 무엇인가

**Fetch(페치)** 는 **원격 저장소의 최신 정보를 내 Git으로 가져오는 것**이다.

핵심은 **가져오기만 하고 내 작업 branch에 합치지는 않는다**는 점이다.

```text
git fetch

GitHub의 최신 상태  →  내 origin/main 이 갱신됨
내 main             →  그대로
Working Tree        →  그대로
```

쉽게 말하면 **"원격에 뭐가 바뀌었는지 먼저 가져와서 확인만 해보는 것"** 이다.

앞에서 `origin/main`이 "마지막으로 확인한 원격 상태"라고 했는데, **그 "마지막 확인"을 갱신해주는 동작이 fetch**다.

내 파일은 전혀 건드리지 않기 때문에 안전하다. 지금 작업 중이어도 부담 없이 실행해서 원격 상황을 파악할 수 있다.

## 15. Pull이란 무엇인가

**Pull(풀)** 은 **원격의 변경사항을 가져와서 현재 내 branch에 반영하는 것**이다.

`git pull`은 보통 **fetch한 다음 그 내용을 현재 branch에 합치는 동작까지** 포함한다. 설정에 따라 merge 방식으로 합칠 수도 있고 rebase 방식으로 합칠 수도 있다.

| 구분 | 원격 정보 가져오기 | 내 branch에 반영 | 내 파일이 바뀌는가 |
|---|---|---|---|
| fetch | 한다 | 안 한다 | 안 바뀐다 |
| pull | 한다 | 한다 | 바뀐다 |

그래서 이렇게 나눠 쓰면 편했다.

- **상황만 확인하고 싶을 때** → fetch
- **최신 상태로 맞추고 싶을 때** → pull

작업 중에 갑자기 파일이 바뀌면 곤란하니까, 먼저 fetch로 확인하고 괜찮을 때 pull하는 순서가 안전했다.

## 16. 왜 새 작업 전에 main을 최신화할까

이제 앞의 개념들이 실제로 왜 필요한지 보여주는 상황이다.

```text
Remote main      A → B → C      팀원이 C까지 올려뒀다
내 Local main    A → B          나는 B까지만 가지고 있다
```

이 상태에서 새 branch를 만들면 어떻게 될까? **C가 없는 상태에서 작업을 시작하게 된다.**

문제는 나중에 드러난다. 내 작업을 main에 합치려 할 때, main에는 C가 있는데 내 작업은 C를 모르는 상태에서 만들어졌다. 같은 곳을 건드렸다면 충돌이 나고, 아니더라도 C에서 바뀐 내용을 고려하지 못한 코드가 된다.

그래서 새 작업을 시작하기 전에 이 순서를 밟는다.

```text
1. Remote 확인         원격에 무엇이 바뀌었는지 가져온다
↓
2. Local main 최신화   내 main을 원격과 같은 상태로 맞춘다
↓
3. 새 Branch 생성      최신 상태에서 갈라져 나온다
```

**최신 상태에서 시작하면 나중에 합칠 때 문제가 훨씬 적다.** 작업이 끝난 뒤에 맞추려면 이미 많이 벌어져 있어서 힘들어진다.

## 17. Pull Request란 무엇인가

**Pull Request(PR)** 는 처음에 이름 때문에 가장 많이 오해했던 개념이다.

**PR은 코드를 GitHub에 업로드하는 기능이 아니다.**

앞에서 정리했듯이 **코드는 push 단계에서 이미 원격에 올라가 있다.** PR을 만든다고 코드가 새로 전송되지 않는다.

그럼 PR은 무엇일까?

> 내 branch의 변경사항을 기준 branch에 합쳐도 될지 검토하고 의견을 나누는 협업 공간

```text
push        →  내 작업을 원격의 내 branch에 올린다
Pull Request →  "이 변경사항을 main에 합쳐도 될까요?" 하고 묻는다
```

이름을 풀어보면 의미가 보인다. "내 변경사항을 당겨가 달라(pull)고 요청(request)한다"는 뜻이다. **요청**이지 **실행**이 아니다.

PR 화면에서는 무엇이 바뀌었는지 한눈에 보이고, 팀원이 줄 단위로 의견을 남길 수 있고, 대화 기록이 남는다. **코드를 옮기는 기능이 아니라 합칠지 결정하는 과정**이다.

## 18. Issue와 PR의 관계

협업할 때 Issue와 PR이 함께 나오는데, 역할이 다르다.

| 단계 | 무엇을 담당하는가 |
|---|---|
| Issue | 무엇을 해야 하는가. 할 일과 문제를 적어두는 곳 |
| Branch | 그 작업을 실제로 구현하는 공간 |
| PR | 그 결과를 검토하고 합칠지 정하는 공간 |

```text
Issue     "지도에 마커가 안 보이는 문제 해결"
↓
Branch    fix/map-marker 에서 작업
↓
PR        "이렇게 고쳤는데 확인해주세요"
```

이렇게 연결해서 보니 각자의 자리가 분명해졌다. Issue는 **할 일 목록**이고, PR은 **결과물에 대한 대화**다.

다만 **Issue가 반드시 있어야 PR을 만들 수 있는 것은 아니다.** 팀에 따라 Issue를 먼저 만드는 규칙을 둘 수도 있고, 간단한 수정은 PR만 올리기도 한다. 도구가 강제하는 순서가 아니라 팀이 정하는 방식이다.

## 19. 기존 PR을 수정하려면 새 PR이 필요한가

PR을 올렸는데 리뷰에서 수정 요청을 받았다. 새 PR을 만들어야 할까?

**대부분의 경우 그럴 필요가 없다.**

PR은 **특정 branch를 바라보고 있다.** 그래서 그 branch에 새 commit이 올라가면 **PR 내용도 함께 갱신된다.**

```text
같은 branch에서
수정
↓
commit
↓
push
↓
열려 있는 PR에 새 commit이 반영된다
```

새 PR을 만들면 오히려 리뷰 대화가 끊긴다. 앞서 나눈 의견과 수정 이력이 이전 PR에 남아 있는데, 새로 만들면 그 맥락이 사라진다.

**같은 작업에 대한 수정이라면 같은 branch에 계속 commit하고 push하면 된다.** 이걸 알기 전에는 수정할 때마다 PR을 새로 만들어서 번호만 늘렸던 적이 있다.

## 20. Code Review란 무엇인가

**Code Review(코드 리뷰)** 는 PR에 올라온 변경사항을 팀원이 살펴보는 과정이다.

처음에는 리뷰가 **오류를 찾아내는 검사**인 줄 알았다. 그래서 리뷰를 받는 게 시험 보는 것처럼 느껴졌다.

하지만 실제로 리뷰에서 확인하는 것은 더 넓었다.

| 확인하는 것 | 질문 |
|---|---|
| 요구사항 충족 | 원래 하려던 일이 실제로 해결됐는가 |
| 영향 범위 | 다른 기능을 망가뜨리지는 않는가 |
| 이해 가능성 | 나중에 다른 사람이 읽고 이해할 수 있는가 |
| 병합 가능성 | 지금 main에 합쳐도 되는 상태인가 |

오류 찾기는 그중 일부일 뿐이었다. **"이 코드를 우리 프로젝트에 넣어도 되는가"를 함께 판단하는 과정**에 가깝다.

그리고 리뷰는 코드를 받는 쪽에도 도움이 된다. 내가 만든 것을 남에게 설명할 수 있는 형태로 정리하게 되고, 내가 놓친 부분을 다른 시각에서 발견하게 된다.

## 21. Approve / Comment / Request Changes

GitHub에서 리뷰를 남길 때 세 가지 중 하나를 고르게 된다.

| 선택 | 의미 |
|---|---|
| Approve | 현재 변경사항을 받아들일 수 있다고 본다 |
| Comment | 의견만 남긴다. 승인도 반대도 아니다 |
| Request Changes | merge하기 전에 수정이 필요하다고 본다 |

**Comment와 Request Changes의 차이**가 처음에는 헷갈렸다.

Comment는 "이렇게 하면 더 좋을 것 같은데 꼭 고쳐야 하는 건 아니다" 같은 의견이다. Request Changes는 "이건 고친 다음에 합쳐야 한다"는 분명한 표시다.

팀에 따라 **Approve가 몇 개 이상이어야 merge할 수 있게** 설정해두기도 한다. 그러면 리뷰가 형식적인 절차가 아니라 실제로 merge를 막는 장치가 된다.

## 22. Merge란 무엇인가

**Merge(병합)** 는 **한 branch의 변경사항을 다른 branch에 합치는 것**이다.

PR이 승인되면 merge를 실행하고, 그러면 내 작업이 드디어 main에 들어간다.

여기서 push와의 차이를 다시 정리해둔다.

| 구분 | 무엇을 하는가 | 무엇이 바뀌는가 |
|---|---|---|
| Push | Local의 commit을 Remote로 보낸다 | 원격의 내 branch |
| Merge | 한 branch의 내용을 다른 branch에 합친다 | 합쳐지는 쪽 branch |

```text
Push    →  Local에서 Remote로 (저장소 사이의 이동)
Merge   →  Branch에서 Branch로 (갈래 사이의 합침)
```

방향 자체가 다르다. push는 **같은 branch가 다른 저장소로** 가는 것이고, merge는 **다른 branch끼리** 합쳐지는 것이다.

이 둘을 구분하고 나서야 "push했는데 왜 main에 없지?"라는 질문이 해결됐다. 이동한 곳이 애초에 달랐던 것이다.

## 23. Merge 방식

merge에는 몇 가지 방식이 있다. GitHub에서 PR을 합칠 때 선택할 수 있다.

| 방식 | 대략의 동작 |
|---|---|
| Merge Commit | 양쪽 기록을 모두 남기고 합쳤다는 commit을 하나 추가한다 |
| Squash Merge | 여러 commit을 하나로 합쳐서 정리한 뒤 넣는다 |
| Rebase and Merge | 내 commit들을 기준 branch 뒤에 이어 붙인다 |

특히 **Squash Merge**를 이해하는 데 시간이 걸렸다.

```text
작업 branch의 commit들
  "로그인 폼 추가"
  "오타 수정"
  "다시 수정"
  "리뷰 반영"
↓ Squash Merge
main에 남는 것
  "로그인 기능 추가"    하나의 commit으로 정리됨
```

작업 중에는 자잘한 commit이 많이 생긴다. 그걸 전부 main 기록에 남기면 히스토리가 지저분해진다. Squash는 그걸 **하나의 의미 있는 기록으로 정리해서 넣는 방식**이다.

어떤 방식이 무조건 낫다고 할 수는 없다. 기록을 자세히 남기고 싶은 프로젝트도 있고, main 히스토리를 깔끔하게 유지하고 싶은 프로젝트도 있다. **팀이 정해둔 방식을 따르면 된다.**

## 24. Merge된 뒤 내 Local main은 자동으로 바뀌지 않는다

이게 실제로 겪으면 제일 당황스러운 부분이다.

PR이 merge됐다. GitHub에서 확인해보니 main에 내 코드가 잘 들어가 있다. 그런데 VS Code를 보니 **내 main은 그대로다.**

```text
GitHub에서 PR merge 완료
       (같지 않다)
내 컴퓨터 main 자동 최신화
```

이유는 2번에서 정리한 그대로다. **Local Repository와 Remote Repository는 서로 다른 저장소**이고, 자동으로 동기화되지 않는다.

merge는 **원격에서 일어난 일**이다. 내 컴퓨터는 그 사실조차 모른다. 원격 main이 앞서 나갔을 뿐이다.

```text
Remote main     A → B → C → D    내 작업 D가 합쳐졌다
내 Local main   A → B → C        아직 D를 모른다
```

그래서 **merge가 끝나면 Local main을 최신화하는 단계가 반드시 따라와야 한다.** 이걸 건너뛰고 바로 다음 작업 branch를 만들면, 16번에서 본 것처럼 낡은 상태에서 시작하게 된다.

## 25. Conflict란 무엇인가

**Conflict(충돌)** 는 **Git이 어느 변경을 선택해야 할지 스스로 판단할 수 없는 상황**이다.

Git은 대부분의 경우 알아서 합친다. 서로 다른 파일을 고쳤거나, 같은 파일이라도 다른 부분을 고쳤다면 문제없이 합쳐진다.

문제는 이럴 때 생긴다.

```text
같은 파일의 같은 부분을
두 branch에서 서로 다르게 수정했다

A branch:  버튼 색을 파란색으로
B branch:  버튼 색을 초록색으로
```

Git 입장에서는 둘 중 무엇이 맞는지 알 수 없다. 둘 다 정당한 변경이기 때문이다. 그래서 **"여기는 사람이 정해달라"고 표시하고 멈춘다.**

여기서 오해하지 말아야 할 것이 있다.

**Conflict는 Git이 망가진 상태가 아니다.** 오히려 Git이 제대로 동작하고 있다는 증거다. 판단할 수 없는 상황에서 마음대로 하나를 골라버리면 그게 더 위험하다. 누군가의 작업이 조용히 사라질 테니까.

충돌은 **협업하면 자연스럽게 생기는 일**이고, 처리 절차가 있는 정상적인 상황이다.

## 26. Conflict가 나면 왜 임의로 해결하면 안 되는가

충돌을 없애는 것 자체는 어렵지 않다. 표시된 부분에서 한쪽을 지우면 된다.

하지만 **기술적으로 해결하는 것과 올바르게 해결하는 것은 다르다.**

앞의 예로 돌아가 보자. 버튼 색이 파란색과 초록색으로 충돌했다. 파란색을 남기면 충돌은 사라진다. 그런데 초록색으로 바꾼 사람에게는 이유가 있었을 수 있다. 디자인이 변경됐거나, 접근성 문제로 바꿨거나, 다른 화면과 맞추려던 것일 수 있다.

**충돌이 난 자리는 두 사람이 같은 곳을 다르게 판단한 자리다.** 그 판단의 근거는 코드에 적혀 있지 않다.

| 해결 방식 | 결과 |
|---|---|
| 임의로 한쪽 선택 | 충돌은 사라지지만 누군가의 의도가 조용히 지워질 수 있다 |
| 담당자와 확인 후 결정 | 왜 그렇게 바꿨는지 알고 나서 정할 수 있다 |

그래서 충돌이 나면 **어느 쪽이 맞는지 담당자에게 확인하는 것**이 먼저였다.

같은 이유로 **AI에게 충돌 해결을 맡기는 것도 조심해야 한다.** AI는 문법적으로 말이 되는 결과를 만들 수는 있지만, **두 사람이 왜 다르게 판단했는지는 알 수 없다.** 충돌 표시를 지우는 것과 옳은 코드를 남기는 것은 다른 문제다.

## 27. git status가 중요한 이유

`git status`는 명령어 목록에서 가장 평범해 보이는 것 중 하나지만, 실제로는 가장 자주 쓰게 된 명령이다.

이 하나로 지금 상태를 거의 다 볼 수 있다.

| 확인할 수 있는 것 | 왜 중요한가 |
|---|---|
| 현재 branch | 엉뚱한 branch에서 작업하고 있지 않은지 |
| 수정된 파일 | 무엇을 건드렸는지 |
| staged 여부 | 어떤 것이 다음 commit에 포함되는지 |
| commit 안 된 내용 | 아직 기록되지 않은 것이 있는지 |
| 원격과의 차이 | push할 것이 남아 있는지 |

지금까지 정리한 개념들이 **전부 이 화면 하나에 나타난다.** Working Tree, Staging Area, Local, Remote의 상태가 한눈에 보인다.

Git에서 뭔가 꼬였다고 느낄 때, 검색해서 나온 명령어를 바로 실행하는 건 위험했다. **지금 상태를 모르는 채로 명령을 내리면 더 꼬인다.**

그래서 습관을 이렇게 바꿨다. **문제가 생기면 명령어보다 status를 먼저 본다.** 대부분은 상태만 확인해도 무엇이 문제인지 알 수 있었다.

## 28. git log는 무엇을 보는가

`git log`는 **지금까지 쌓인 commit 기록을 보는 명령**이다.

누가 언제 어떤 메시지로 무엇을 기록했는지 순서대로 볼 수 있다.

혼자 작업할 때는 잘 쓰지 않았는데, 팀 프로젝트에서는 쓸 일이 생겼다.

- 이 기능이 언제 들어왔는지 확인할 때
- 내 branch가 어느 시점에서 갈라졌는지 볼 때
- 원격과 내 Local 중 어느 쪽이 앞서 있는지 파악할 때

commit 메시지를 왜 잘 써야 하는지도 여기서 체감했다. **log에 남는 것이 결국 그 메시지**다. "수정", "ㅇㅇ" 같은 메시지만 잔뜩 있으면 기록을 봐도 아무것도 알 수 없다.

옵션이 많지만 이번 글에서는 **"기록을 확인하는 도구"** 라는 것까지만 정리해둔다.

## 29. .gitignore란 무엇인가

**`.gitignore`** 는 **Git이 추적하지 않았으면 하는 파일들을 적어두는 파일**이다.

모든 파일을 Git으로 관리할 필요는 없다.

| 제외하는 것 | 이유 |
|---|---|
| `.env` 같은 설정 파일 | Secret이 들어 있어서 공개되면 안 된다 |
| Build 결과물 | 코드에서 다시 만들 수 있어서 기록할 필요가 없다 |
| Local 전용 설정 | 사람마다 달라서 공유하면 오히려 방해가 된다 |

특히 Secret이 든 파일은 중요하다. 한 번 올라가면 저장소를 볼 수 있는 사람 모두가 볼 수 있게 된다.

여기서 알아둬야 할 함정이 하나 있다.

**`.gitignore`에 추가해도, 이미 Git이 추적 중이던 파일은 계속 추적된다.**

`.gitignore`는 **아직 추적하지 않는 파일을 앞으로도 무시하겠다**는 설정이다. 이미 commit된 적이 있는 파일은 이미 추적 대상이라서 그냥 적어두는 것만으로는 빠지지 않는다. 추적에서 빼는 작업을 따로 해줘야 한다.

그래서 **`.gitignore`는 파일을 만들 때 미리 챙겨두는 게 가장 편했다.**

## 30. Untracked / Modified / Staged

`git status`에서 자주 보게 되는 상태들이다. 지금까지의 단계와 그대로 대응된다.

| 상태 | 무엇을 뜻하는가 |
|---|---|
| Untracked | Git이 아직 추적하지 않는 새 파일. 한 번도 add된 적이 없다 |
| Modified | 추적 중인 파일이 변경됐다. 아직 stage되지 않았다 |
| Staged | 다음 commit에 포함되도록 선택됐다 |
| Committed | Local Git 기록에 남았다 |

```text
새 파일 생성        →  Untracked
기존 파일 수정      →  Modified
git add             →  Staged
git commit          →  Committed
```

처음에는 Untracked와 Modified가 왜 다르게 표시되는지 몰랐다. 차이는 **Git이 그 파일을 알고 있느냐**다. 한 번도 add한 적 없는 새 파일은 Git 입장에서 처음 보는 파일이고, 이미 관리 중인 파일이 바뀐 것과는 다른 상황이다.

## 31. Local / Remote 상태를 한 번에 연결하기

지금까지 나온 것들을 하나의 그림으로 이으면 이렇게 된다. **이 글의 핵심 그림이다.**

```text
파일 작성
↓
Working Tree          지금 내가 수정 중인 파일
↓ git add
Staging Area          다음 commit에 넣을 것 선택
↓ git commit
Local Repository      내 컴퓨터에 기록됨
↓ git push
Remote Branch         GitHub의 내 작업 branch에 올라감
↓
Pull Request          "합쳐도 될까요?" 하고 요청
↓
Review                팀원이 검토하고 의견을 남김
↓
Merge                 기준 branch에 합쳐짐
↓
Remote main           원격 main이 최신이 됨
↓ pull / fetch
Local main            내 컴퓨터 main도 최신이 됨
```

이 그림을 그려놓고 나서 얻은 게 있다. **"어디까지 됐는가"를 물으면 이 사다리의 몇 번째 칸인지로 답할 수 있게 됐다.**

- commit만 했다 → 아직 세 번째 칸. 팀원은 볼 수 없다
- push까지 했다 → 다섯 번째 칸. 원격에 있지만 main은 아니다
- PR을 만들었다 → 여섯 번째 칸. 아직 합쳐지지 않았다
- merge됐다 → 아홉 번째 칸. 하지만 내 Local main은 아직 예전 상태다

각 칸 사이는 **자동으로 넘어가지 않는다.** 전부 내가 하거나 누군가 해줘야 다음 칸으로 간다. 이것이 Git이 헷갈렸던 이유 전부였다.

## 32. 팀 프로젝트의 기본 작업 흐름

위 그림을 실제 작업 순서로 풀면 이렇게 된다.

```text
1.  현재 상태 확인              git status 로 지금 상황 파악
2.  Remote 최신 정보 확인       원격에 무엇이 바뀌었는지 가져오기
3.  Local main 최신화           내 main을 원격과 맞추기
4.  새 작업 branch 생성         최신 상태에서 갈라져 나오기
5.  기능 구현                   실제 작업
6.  git status 확인             무엇을 건드렸는지 점검
7.  필요한 파일 stage           이번 기록에 넣을 것만 선택
8.  commit                      의미 있는 메시지와 함께 기록
9.  push                        원격의 내 branch로 보내기
10. PR 생성                     "합쳐도 될까요?" 요청
11. Review                      팀원의 검토 받기
12. 수정이 있으면               같은 branch에서 commit / push
13. Merge                       기준 branch에 합치기
14. Local main 최신화           내 컴퓨터도 최신으로
15. 다음 Issue 시작             1번으로 돌아가기
```

눈여겨볼 부분이 두 군데 있다.

**시작(1~3번)과 끝(14번)이 둘 다 최신화**라는 점이다. 최신 상태에서 시작해서, 끝나면 다시 최신 상태로 돌아온다. 그래야 다음 작업도 같은 조건에서 시작할 수 있다.

그리고 **12번에서 새 PR을 만들지 않는다**는 점이다. 19번에서 정리한 대로 같은 branch에 이어서 작업하면 된다.

이건 **일반적인 협업 흐름의 예시**이고, 팀마다 세부 규칙은 다르다. 리뷰 인원 수, branch 이름 규칙, merge 방식 같은 것들은 팀에서 정한다.

## 33. 자주 쓰는 명령어 흐름

명령어 사전을 만들 생각은 없어서, 위 흐름에서 실제로 쓰게 되는 것만 정리한다.

| 명령어 | 하는 일 |
|---|---|
| `git status` | 지금 상태를 확인한다. 가장 자주 쓰게 된다 |
| `git switch` | 다른 branch로 이동한다 |
| `git fetch` | 원격의 최신 정보를 가져온다. 내 파일은 그대로다 |
| `git pull` | 원격의 변경사항을 가져와 현재 branch에 반영한다 |
| `git add` | 다음 commit에 포함할 파일을 선택한다 |
| `git commit` | 선택한 변경사항을 기록으로 남긴다 |
| `git push` | Local의 commit을 원격으로 보낸다 |
| `git log` | 지금까지의 commit 기록을 본다 |
| `git branch` | branch 목록을 보거나 새로 만든다 |

`reset`이나 강제 push 같은 명령은 여기에 넣지 않았다. **이미 있는 기록을 되돌리거나 덮어쓰는 동작**이라, 팀 저장소에서 잘못 쓰면 다른 사람의 작업에 영향을 줄 수 있다. 상황을 충분히 이해한 뒤에 배우는 게 맞다고 판단했다.

## 34. 자주 헷갈리는 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Git | 변경 이력을 관리하는 버전 관리 시스템 |
| GitHub | Git 저장소를 원격에 두고 공유하며 협업 기능을 제공하는 서비스 |
| Repository | Git이 변경 이력을 관리하는 단위. 보통 프로젝트 하나 |
| Local | 내 컴퓨터에 있는 저장소 |
| Remote | 원격 서버에 있는 저장소 |
| Working Tree | 지금 내가 직접 수정하고 있는 파일들의 상태 |
| Staging Area | 다음 commit에 포함할 변경사항을 골라 담아두는 공간 |
| Commit | 변경사항을 Git 기록으로 남기는 것 |
| Branch | 기존 코드에서 갈라져 나와 독립적으로 작업하는 갈래 |
| HEAD | 지금 내가 어디에서 작업하고 있는지를 가리키는 표시 |
| origin | 원격 저장소에 붙은 별칭. clone하면 보통 자동으로 생긴다 |
| origin/main | 마지막으로 정보를 가져왔을 때 확인한 원격 main의 상태 |
| Clone | 원격 저장소를 기록과 연결 정보까지 함께 내 컴퓨터로 가져오는 것 |
| Fetch | 원격의 최신 정보를 가져오되 내 branch에는 합치지 않는 것 |
| Pull | 원격의 변경사항을 가져와 현재 branch에 반영하는 것 |
| Push | Local의 commit을 원격 저장소로 보내는 것 |
| Issue | 무엇을 해야 하는지 적어두는 할 일 단위 |
| Pull Request | 변경사항을 합쳐도 될지 검토하고 의견을 나누는 공간 |
| Review | PR의 변경사항을 살펴보고 의견을 남기는 과정 |
| Merge | 한 branch의 변경사항을 다른 branch에 합치는 것 |
| Squash Merge | 여러 commit을 하나로 정리해서 합치는 방식 |
| Conflict | Git이 어느 변경을 선택할지 판단할 수 없는 상황 |
| `.gitignore` | Git이 추적하지 않을 파일을 지정하는 파일 |

## 35. 자주 헷갈리는 차이 정리

| 구분 | 차이 |
|---|---|
| Git vs GitHub | 변경 기록을 관리하는 도구 / 그 저장소를 공유하는 서비스 |
| Save vs Commit | 디스크에 파일을 쓰는 것 / Git 기록에 한 줄을 남기는 것 |
| Commit vs Push | 내 컴퓨터에 기록 / 원격 저장소로 전송 |
| Push vs Merge | 저장소 사이의 이동 / branch 사이의 합침 |
| main vs origin/main | 내 컴퓨터의 main / 마지막으로 확인한 원격 main 상태 |
| Fetch vs Pull | 가져와서 확인만 / 가져와서 내 branch에 반영 |
| Branch vs PR | 작업하는 공간 / 그 결과를 검토하는 공간 |
| PR vs Merge | 합치자는 요청 / 실제로 합치는 실행 |
| Local vs Remote | 내 컴퓨터의 저장소 / 원격 서버의 저장소. 자동 동기화되지 않는다 |
| Merge 완료 vs Local 최신화 | 원격에서 합쳐진 것 / 내 컴퓨터가 그 결과를 받아온 것 |

## 36. "작업 완료"는 어디까지인가

Database 글의 "DB 연결 완료", Backend 글의 "백엔드 구현 완료", Deployment 글의 "배포 성공"과 똑같은 문제가 Git에도 있었다.

아래는 **전부 다른 상태**다.

| 단계 | 어디까지 된 것인가 |
|---|---|
| 1 | 코드 작성 완료 — 에디터에 타이핑까지 |
| 2 | 파일 저장 — 디스크에 쓰였다. Git은 아직 모른다 |
| 3 | Stage — 이번 기록에 넣기로 선택했다 |
| 4 | Commit — 내 컴퓨터에 기록됐다 |
| 5 | Push — 원격의 내 branch에 올라갔다 |
| 6 | PR 생성 — 합쳐달라고 요청했다 |
| 7 | Review — 검토를 받았다 |
| 8 | Merge — 기준 branch에 합쳐졌다 |
| 9 | Local main 최신화 — 내 컴퓨터도 그 결과를 받았다 |

**"Git 작업 끝났어요"라는 말로는 이 중 몇 번인지 알 수 없다.**

실제로 협업할 때 이 차이 때문에 대화가 어긋났다. 한 사람은 commit까지를 "끝냈다"고 말하고, 다른 사람은 merge까지를 "끝났다"고 이해한다. 그러면 "왜 코드가 없냐"는 이야기가 나온다.

그래서 **"push까지 했어요", "PR 올렸어요", "merge됐어요"처럼 단계를 말하는 편이 훨씬 정확했다.**

## 37. Git에서 문제가 생겼을 때 먼저 볼 것

Git이 꼬였다고 느낄 때 쓰는 체크리스트를 만들어뒀다.

```text
1. 현재 어떤 Repository인가        엉뚱한 폴더에 있지 않은가
2. 현재 Branch는 무엇인가          의도한 branch가 맞는가
3. git status는 어떤가             지금 상태가 어떻게 보이는가
4. 수정 중인 파일이 있는가         저장하지 않았거나 stage 안 된 것이 있는가
5. commit은 했는가                 기록으로 남겼는가
6. push는 했는가                   원격에 보냈는가
7. PR이 있는가                     요청은 올렸는가
8. merge됐는가                     실제로 합쳐졌는가
9. Local과 Remote 중 어느 쪽이 최신인가
```

이 순서는 31번의 흐름 그림을 **위에서부터 따라 내려가며 확인하는 것**이다. 어느 칸에서 멈춰 있는지 찾으면 해야 할 일이 정해진다.

가장 강조하고 싶은 건 이것이다. **명령어부터 실행하지 않는다.**

Git 문제로 검색하면 명령어가 바로 나온다. 하지만 그 명령어는 **특정 상황을 전제로 한 답**이다. 내 상황이 그 전제와 다르면 문제가 더 커진다. 특히 기록을 되돌리는 명령은 잘못 쓰면 작업이 사라진다.

**상태를 먼저 파악하고, 그 다음에 무엇을 할지 정한다.** 이 순서만 지켜도 대부분의 사고를 피할 수 있었다.

## 38. 이번에 이해한 핵심

이번에도 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### 파일 저장, 은 Commit과 다르다

저장은 디스크에 쓰는 것이고, commit은 Git 역사에 기록을 남기는 것이다.

### Commit, 은 Push와 다르다

commit은 내 컴퓨터 안의 일이다. push해야 원격으로 간다.

### Push, 는 Merge와 다르다

push는 내 branch를 원격에 올린 것이고, merge는 그 내용이 기준 branch에 합쳐진 것이다.

### PR 생성, 은 Merge 완료와 다르다

PR은 합치자는 요청이다. 실제로 합쳐지는 건 merge를 실행한 다음이다.

### Remote main 업데이트, 는 Local main 자동 업데이트와 다르다

원격에서 일어난 일은 내 컴퓨터에 자동으로 오지 않는다. 받아와야 온다.

### main, 은 origin/main과 다르다

하나는 내 컴퓨터의 branch이고, 하나는 마지막으로 확인한 원격 상태의 기록이다.

### Branch를 만들었다, 는 새 Repository를 만든 것과 다르다

같은 저장소 안에서 갈래만 나뉜 것이다. 폴더가 복사되지 않는다.

### GitHub, 는 Git과 다르다

Git은 도구이고 GitHub는 그 저장소를 공유하는 서비스다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> Git은 명령어를 많이 외우는 것보다, 현재 변경사항이 Local과 Remote 중 어디에 있는지, 그리고 지금 어떤 단계에 있는지를 이해하는 것이 더 중요했다.

처음에는 Git을 명령어 목록으로 배우려고 했다. add, commit, push를 순서대로 외웠다. 그런데 정작 문제가 생기면 어떤 명령을 써야 할지 알 수 없었다. **내가 지금 어디에 있는지를 몰랐기 때문**이다.

31번의 사다리 그림이 머릿속에 들어오고 나서는 달라졌다. 명령어는 **칸과 칸 사이를 이동하는 수단**일 뿐이었다. 지금 어느 칸에 있고 어디로 가고 싶은지만 알면, 필요한 명령은 그때 찾아봐도 됐다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **Rebase** — 기록을 다시 정리해서 이어 붙이는 방식. merge와 결과가 다르게 남는다
- **Cherry-pick** — 특정 commit 하나만 골라서 다른 branch에 가져오는 것
- **Tag** — 특정 시점에 이름표를 붙여두는 것. 버전을 표시할 때 쓴다
- **Release** — Tag를 기준으로 배포 버전을 정리해 공개하는 GitHub 기능
- **Git Hooks** — commit이나 push 같은 시점에 자동으로 실행되는 스크립트
- **GitHub Actions** — PR이나 push에 맞춰 검사와 배포를 자동으로 돌리는 기능
- **Branch Protection** — 특정 branch에 바로 push하지 못하게 막는 설정
- **Conventional Commits** — commit 메시지를 일정한 형식으로 쓰자는 규칙
- **Semantic Versioning** — 버전 번호에 의미를 부여해서 매기는 방식
