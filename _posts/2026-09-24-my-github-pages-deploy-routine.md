GitHub Pages 배포는 처음 보면 `commit`, `push`, `Pages`, `Actions`가 따로 있는 것처럼 보여서 복잡하게 느껴질 수 있다.

하지만 내가 실제로 반복하는 순서는 비교적 단순하다.

```text
1. 로컬에서 작업
2. 변경 파일 확인
3. 로컬 화면 확인
4. git add
5. git commit
6. git push
7. GitHub에서 push 확인
8. Pages 빌드·배포 상태 확인
9. 실제 블로그에서 최종 확인
```

중요한 것은 `push` 하나만 보는 것이 아니라 **로컬 → GitHub → Pages → 실제 사이트**까지 단계별로 확인하는 것이다.

---

## 1. 먼저 현재 브랜치와 변경사항을 확인한다

작업을 끝낸 뒤 바로 commit부터 하지 않고 먼저 현재 상태를 확인하는 편이 안전했다.

```bash
git status
```

이 명령으로

* 현재 어떤 브랜치에 있는지
* 수정된 파일은 무엇인지
* 새로 추가된 파일은 무엇인지
* 의도하지 않은 파일까지 변경되지는 않았는지

확인할 수 있다.

특히 Claude와 함께 작업하면 한 번에 여러 파일이 수정될 수도 있기 때문에 이 단계가 중요했다.

내가 포스트 하나만 추가하려고 했는데 다른 레이아웃 파일까지 바뀌어 있다면 push하기 전에 먼저 확인해야 한다.

---

## 2. 실제로 무엇이 바뀌었는지 확인한다

`git status`는 어떤 파일이 바뀌었는지는 알려주지만 내용까지 보여주지는 않는다.

그래서 필요하면 변경 내용을 직접 확인한다.

```bash
git diff
```

새로 만든 포스트라면 파일 내용을 다시 읽고,

CSS나 레이아웃을 수정했다면 의도했던 부분만 바뀌었는지 확인한다.

이 단계에서 자주 보는 것은 단순하다.

```text
내가 요청한 부분만 수정됐는가?

기존 기능이 같이 바뀌지는 않았는가?

삭제하면 안 되는 코드가 사라지지 않았는가?

임시 테스트 코드가 남아 있지는 않은가?
```

AI가 코드를 수정해 줬더라도 최종적으로 공개할 변경사항을 결정하는 것은 나다.

---

## 3. 로컬 블로그에서 먼저 확인한다

GitHub에 올리기 전에 로컬에서 실제 화면을 확인한다.

새 글을 추가했다면

* 포스트 목록에 나타나는지
* 제목이 정상적으로 보이는지
* 카테고리와 태그가 제대로 표시되는지
* 본문이 깨지지 않는지

확인한다.

디자인을 수정했다면

* 홈
* 포스트
* 카테고리
* 필요한 경우 모바일 화면

까지 살펴본다.

링크를 수정했다면 직접 눌러본다.

이 단계에서 문제가 있다면 아직 내 컴퓨터 안의 문제이기 때문에 수정하기 쉽다.

---

## 4. 배포할 파일을 Git에 추가한다

확인이 끝났다면 변경사항을 staging한다.

모든 변경사항을 한 번에 올려도 되는 상황이라면

```bash
git add .
```

을 사용할 수 있다.

하지만 다른 작업이 섞여 있다면 필요한 파일만 지정하는 편이 안전하다.

```bash
git add _posts/포스트파일.md
```

`git add .`가 편하다고 무조건 사용하는 것보다 **지금 배포하려는 변경사항이 무엇인지 알고 추가하는 것**이 중요했다.

---

## 5. commit으로 변경사항을 기록한다

다음은 commit이다.

```bash
git commit -m "docs: add GitHub Pages deployment post"
```

commit은 GitHub에 업로드하는 작업이 아니라 **현재 변경사항을 하나의 기록으로 만드는 작업**이다.

그래서 commit 메시지만 봐도 무엇을 했는지 알 수 있게 남기려고 한다.

예를 들면

```text
docs: add blog post
fix: correct broken links
feat: add search
style: adjust sidebar layout
```

처럼 작업 목적을 구분할 수 있다.

블로그에서 문제가 생겼을 때 최근 어떤 작업을 했는지 찾기도 훨씬 편하다.

---

## 6. push하기 전에 한 번 더 상태를 확인한다

commit까지 했다면 다시 상태를 확인할 수 있다.

```bash
git status
```

정상적으로 commit됐다면 보통 현재 작업 트리가 깨끗한지 확인할 수 있다.

이때 의도하지 않은 수정 파일이 남아 있다면

> 이 파일도 같이 배포해야 하나?

를 다시 판단할 수 있다.

바로 push하기보다 이 한 번의 확인이 실수를 줄이는 데 도움이 됐다.

---

## 7. GitHub로 push한다

이제 로컬에 만든 commit을 원격 GitHub 저장소에 올린다.

```bash
git push
```

현재 브랜치가 원격 브랜치와 연결되어 있다면 이 정도로 충분하다.

처음 만든 브랜치처럼 upstream이 설정되지 않은 경우라면 다른 명령이 필요할 수 있지만, 평소 main에서 블로그를 운영하는 흐름에서는 이미 연결되어 있기 때문에 단순하게 push할 수 있다.

여기에서 중요한 것은

```text
commit
→ 로컬에 기록

push
→ GitHub에 전달
```

이라는 차이다.

commit만 하고 push하지 않았다면 공개 사이트에는 아무 변화도 없다.

---

## 8. GitHub에서 실제로 커밋이 올라갔는지 확인한다

터미널에서 push 성공 메시지가 나왔다면 GitHub 저장소에서도 방금 만든 commit이 올라갔는지 확인할 수 있다.

여기에서 확인하는 것은

* 최신 commit 메시지가 내가 만든 것인지
* 예상한 파일이 올라갔는지
* main 브랜치가 최신 상태인지

정도다.

이 단계까지 정상이라면

```text
로컬 변경
→ commit 완료
→ GitHub 원격 저장소 반영 완료
```

상태라고 볼 수 있다.

하지만 아직 Pages 배포가 끝났다는 뜻은 아니다.

---

## 9. GitHub Pages 빌드 상태를 확인한다

push가 들어오면 GitHub Pages가 새로운 내용을 기준으로 사이트를 다시 만든다.

내가 매번 별도로 배포 명령을 실행하는 것이 아니라 GitHub 쪽에서 이 과정이 이어진다.

배포 상태는 GitHub의 Actions나 Pages 관련 영역에서 확인할 수 있다.

여기서 보고 싶은 것은 크게 세 가지다.

```text
빌드가 시작됐는가?

실패하지 않았는가?

내가 방금 올린 commit을 기준으로 배포되고 있는가?
```

배포가 진행 중이라면 공개 블로그에는 아직 이전 버전이 보일 수 있다.

그래서 push하자마자 사이트가 안 바뀌었다고 다시 commit하거나 push할 필요는 없다.

먼저 빌드 상태를 확인하는 편이 맞다.

---

## 10. Pages 빌드가 실패했다면 로그부터 본다

배포에 실패했을 때는 무작정 명령을 다시 실행하지 않는다.

이미 GitHub에는 코드가 정상적으로 올라갔을 수도 있기 때문이다.

이 경우 문제는 Git push가 아니라 **사이트를 만드는 과정**에 있을 가능성이 있다.

예를 들어

* Markdown이나 front matter 형식 문제
* Jekyll 빌드 오류
* 잘못된 설정
* 파일 경로 문제

등을 생각할 수 있다.

그래서 순서를 이렇게 나누면 된다.

```text
push 실패
→ Git / 원격 저장소 문제 확인

push 성공 + Pages 실패
→ Pages 빌드 로그 확인
```

문제가 어느 단계에 있는지 구분하면 같은 명령을 반복하는 일을 줄일 수 있다.

---

## 11. 배포 성공 후 실제 사이트를 확인한다

Pages에서 성공했다고 표시돼도 마지막으로 실제 블로그를 직접 확인한다.

이 단계가 최종 검수다.

새 포스트를 배포했다면

```text
홈 또는 포스트 목록에 보이는가?

포스트가 정상적으로 열리는가?

제목·날짜·카테고리가 맞는가?

TOC나 코드 블록이 깨지지 않았는가?

내부 링크가 정상적으로 동작하는가?
```

디자인 수정이라면 실제 배포된 화면에서 위치와 크기를 확인한다.

특히 GitHub Pages에서는 로컬과 실제 배포 경로가 다를 수 있기 때문에 이미지나 링크는 배포본에서 다시 보는 편이 좋다.

---

## 12. 브라우저 캐시 때문에 이전 화면이 보일 수도 있다

GitHub Pages 배포까지 성공했는데 브라우저에서는 이전 화면이 보이는 경우도 있을 수 있다.

이때는 무조건 배포 실패라고 판단하지 않는다.

브라우저에 이전 CSS나 이미지가 남아 있을 수도 있기 때문이다.

그래서

```text
Pages 배포 성공 여부 확인
↓
실제 배포 commit 확인
↓
새로고침
↓
필요하면 캐시 영향 확인
```

순서로 보는 편이 좋다.

favicon처럼 캐시가 강하게 남는 파일은 특히 바로 변경되지 않는 것처럼 느껴질 수 있다.

---

## 내가 보는 배포 완료 기준

예전에는 `git push`가 성공하면 배포도 끝났다고 생각하기 쉬웠다.

지금은 조금 다르게 보고 있다.

내 기준에서 배포 완료는 다음 조건이 모두 확인된 상태다.

```text
로컬에서 정상
+
원하는 파일만 commit
+
GitHub push 성공
+
Pages 빌드 성공
+
실제 배포 사이트 정상
```

즉 터미널에서 명령 하나가 성공했다고 끝나는 것이 아니다.

사용자가 실제로 보는 페이지까지 정상이어야 작업이 끝난 것이다.

---

## 평소에는 이 정도로 단순하게 반복한다

모든 설명을 한 번에 보면 배포 절차가 길어 보일 수 있다.

하지만 익숙해지면 실제 작업은 이 정도로 정리된다.

```bash
git status
git add .
git commit -m "작업 내용"
git push
```

그리고

```text
GitHub Pages 성공 확인
↓
실제 블로그 확인
```

을 하면 된다.

단, `git add .`을 사용하기 전에는 어떤 파일이 변경됐는지를 먼저 확인한다.

배포 명령이 어려운 것이 아니라 **무엇을 올리고 있는지 확인하는 습관**이 더 중요했다.

---

## 포스트 하나를 추가한다고 가정하면

예를 들어 새로운 글 하나를 작성했다고 하면 실제 흐름은 다음과 같다.

```text
1. _posts에 새 포스트 작성

2. 로컬 블로그 실행

3. 글 목록에서 새 글 확인

4. 본문·카테고리·날짜 확인

5. git status

6. 새 포스트 파일이 변경 목록에 있는지 확인

7. git add

8. git commit

9. git push

10. GitHub에서 최신 commit 확인

11. Pages 빌드 성공 확인

12. 실제 블로그에서 새 글 확인
```

이 흐름을 몇 번 반복하고 나니

> 글을 작성한다.

와

> 글을 배포한다.

가 따로 떨어진 작업이 아니라 하나의 과정처럼 느껴지기 시작했다.

---

## 자동 배포가 있어도 내가 확인할 단계는 남아 있었다

GitHub Pages 덕분에 서버에 파일을 직접 올리는 과정은 필요하지 않았다.

push 이후 빌드와 배포는 자동으로 이어진다.

하지만 자동화된 것은 **배포 실행**이지 **내 변경사항의 정확성**이 아니었다.

잘못된 글도 push하면 그대로 배포될 수 있고,

깨진 링크도 자동으로 고쳐주지 않는다.

그래서 GitHub Pages를 사용하면서 가장 중요하게 느낀 것은 배포 명령 자체보다 다음 흐름이었다.

> **로컬에서 확인하고, 변경사항을 검토하고, GitHub에 올리고, 실제 배포 결과까지 다시 본다.**

GitHub Pages가 가운데의 반복 작업을 줄여주기 때문에 나는 무엇을 공개할 것인지와 최종 결과 확인에 더 집중할 수 있었다.

처음에는 `push하면 자동 배포된다` 정도로만 이해했지만, 실제 운영에서는 **수정부터 최종 검수까지가 하나의 배포 절차**라는 것을 알게 됐다.
