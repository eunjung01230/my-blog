Figma에서 화면을 만들 때는 보통 하나의 크기를 기준으로 작업한다.

예를 들어 모바일이라면

```text
390 × 844
```

같은 Frame을 만들고,

웹이라면

```text
1440px
```

정도의 Desktop 화면을 기준으로 만들 수 있다.

그 상태에서는 모든 것이 잘 맞아 보인다.

```text
제목 위치

카드 너비

버튼 크기

이미지

여백
```

도 깔끔하다.

그런데 실제 브라우저에서 창 크기를 줄여보면 갑자기 문제가 생긴다.

```text
카드가 화면 밖으로 나감

버튼 글자가 두 줄이 됨

메뉴가 겹침

이미지가 너무 커짐

텍스트가 이상하게 줄바꿈됨
```

반대로 큰 모니터에서 보면

```text
콘텐츠가 너무 넓어짐

텍스트 한 줄이 지나치게 길어짐

카드 사이가 너무 벌어짐
```

같은 문제가 생길 수 있다.

처음에는 반응형 디자인을

```text
화면이 작아지면
전체를 같이 줄이는 것
```

이라고 생각했다.

하지만 실제로는 조금 달랐다.

> **반응형 디자인은 화면 크기에 따라 같은 정보를 가장 적절한 구조로 다시 배치하는 일에 가까웠다.**

이번 글에서는 내가 반응형 UI를 이해하면서 알게 된 기본 개념들을 정리해보려고 한다.

---

## 반응형 디자인이란?

반응형 디자인은 하나의 웹이나 서비스를

```text
Desktop

Tablet

Mobile
```

같은 다양한 화면 크기에서 사용할 수 있도록 만드는 방식이다.

예를 들어 Desktop에서는

```text
┌─────────┬─────────┬─────────┐
│ Card 1  │ Card 2  │ Card 3  │
└─────────┴─────────┴─────────┘
```

카드 세 개가 한 줄에 보일 수 있다.

화면이 좁아지면

```text
┌─────────┬─────────┐
│ Card 1  │ Card 2  │
├─────────┴─────────┤
│ Card 3            │
└───────────────────┘
```

두 열로 바뀔 수 있고,

모바일에서는

```text
┌─────────┐
│ Card 1  │
├─────────┤
│ Card 2  │
├─────────┤
│ Card 3  │
└─────────┘
```

한 열로 내려갈 수 있다.

중요한 것은

```text
카드 크기를 무조건 축소
```

한 것이 아니라

```text
화면 크기에 맞게
배치 방식이 바뀜
```

이라는 점이다.

---

## 처음에는 px로 고정하면 편했다

CSS를 처음 배울 때는 고정된 크기가 이해하기 쉽다.

```css
.container {
  width: 1200px;
}
```

이렇게 만들면 Desktop 화면에서는 정확하게 보인다.

카드도

```css
.card {
  width: 350px;
}
```

처럼 정할 수 있다.

Figma 디자인을 그대로 옮기기도 쉽다.

문제는 화면이

```text
390px
```

짜리 모바일이 되었을 때다.

1200px짜리 콘텐츠는 화면 안에 들어갈 수 없다.

결국

```text
가로 스크롤
```

이 생기거나,

일부 요소가 화면 밖으로 나간다.

---

## 고정 크기가 나쁜 것은 아니다

여기서

```text
px를 쓰면 안 된다.
```

는 뜻은 아니다.

버튼 높이,

아이콘 크기,

Border Radius처럼

고정된 값을 사용하는 것이 자연스러운 요소도 많다.

예를 들어

```css
.button {
  height: 48px;
  border-radius: 12px;
}
```

같은 값이다.

문제는 화면 전체 구조까지

```text
항상 같은 너비
```

라고 가정하는 것이다.

---

## width: 100%를 처음 알았을 때

고정 폭 대신 부모 영역을 채우게 만들 수 있다.

```css
.container {
  width: 100%;
}
```

그러면 화면 크기에 따라 같이 줄어든다.

예를 들어

```text
Desktop
1200px

↓

Tablet
768px

↓

Mobile
390px
```

에서 부모 너비를 따라간다.

처음에는

```text
그러면 전부 100% 쓰면 되는 것 아닌가?
```

라고 생각할 수 있다.

하지만 큰 화면에서는 또 문제가 생긴다.

---

## 큰 화면에서 너무 넓어지는 문제

예를 들어 블로그 본문이

```css
width: 100%;
```

라고 되어 있다고 해보자.

큰 모니터에서는 문장이 화면 끝에서 끝까지 이어질 수 있다.

```text
이 문장이 화면 전체 폭을 사용해서 아주 길게 이어지고 읽을 때 눈이 계속 오른쪽 끝까지 이동해야 한다...
```

읽기 불편하다.

그래서

```text
최대 너비
```

라는 개념이 필요해진다.

---

## max-width

예를 들어

```css
.container {
  width: 100%;
  max-width: 1200px;
}
```

라고 할 수 있다.

뜻은

```text
화면이 작으면
→ 화면에 맞게 줄어듦

화면이 커져도
→ 1200px 이상은 커지지 않음
```

이다.

이 구조는 실제 웹에서 매우 자주 사용된다.

그리고 가운데 배치하려면

```css
.container {
  width: 100%;
  max-width: 1200px;
  margin: 0 auto;
}
```

처럼 만들 수 있다.

---

## 좌우 Padding도 필요했다

모바일에서

```css
width: 100%;
```

만 적용하면 콘텐츠가 화면 가장자리까지 붙을 수 있다.

```text
|텍스트가바로시작
```

답답해 보인다.

그래서

```css
.container {
  padding: 0 20px;
}
```

처럼 좌우 여백을 둔다.

결과는

```text
|    콘텐츠    |
```

처럼 된다.

Desktop에서는 넓은 여백,

Mobile에서는 작은 여백을 사용할 수도 있다.

---

## 반응형에서 중요한 세 가지 값

내가 처음 이해하기 좋았던 것은

```text
width

max-width

padding
```

세 가지였다.

예를 들어

```css
.container {
  width: 100%;
  max-width: 1200px;
  padding: 0 20px;
  margin: 0 auto;
}
```

이 구조만 이해해도

```text
화면에 맞게 줄어들고

너무 커지지는 않고

양옆 여백도 유지되는
```

기본적인 반응형 Container를 만들 수 있다.

---

## Breakpoint란?

화면이 줄어들다가 어느 순간

```text
이 구조는 이제 더 이상 유지하기 어렵다.
```

라는 지점이 온다.

그 지점에서 Layout을 바꾸는 기준을

```text
Breakpoint
```

라고 한다.

예를 들어

```text
Desktop
→ 카드 3개

Tablet
→ 카드 2개

Mobile
→ 카드 1개
```

처럼 바꿀 수 있다.

CSS에서는 Media Query를 사용할 수 있다.

```css
.cards {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
}

@media (max-width: 768px) {
  .cards {
    grid-template-columns: 1fr;
  }
}
```

화면이 768px 이하가 되면 한 열로 바뀌는 구조다.

---

## Breakpoint 숫자를 외우는 것이 핵심은 아니었다

처음 반응형을 공부하면

```text
768px

1024px

1280px
```

같은 숫자를 외워야 할 것처럼 느껴진다.

하지만 더 중요한 것은

```text
어느 순간 디자인이 깨지는가?
```

다.

예를 들어 카드 세 개가

```text
900px
```

까지는 괜찮은데

850px에서 너무 좁아진다면

그 주변에서 구조를 바꾸는 것을 생각할 수 있다.

즉,

```text
기기 이름에 맞춰 Breakpoint 지정
```

보다

```text
콘텐츠가 자연스럽게 보이는 기준
```

으로 생각하는 편이 이해하기 쉬웠다.

---

## 모든 기기의 크기를 하나씩 대응할 수는 없다

실제 기기는 정말 다양하다.

```text
작은 스마트폰

큰 스마트폰

태블릿

작은 노트북

큰 노트북

울트라와이드 모니터
```

모든 기기마다 별도 CSS를 작성하는 것은 현실적이지 않다.

그래서 보통 몇 개의 주요 Layout 변화 지점을 만들고

그 사이에서는 유동적으로 크기가 변하도록 한다.

예를 들면

```text
Mobile

Tablet

Desktop
```

정도의 큰 구간을 먼저 생각할 수 있다.

---

## 반응형은 화면 크기를 줄이는 것이 아니었다

예를 들어 Desktop 화면이 이렇게 되어 있다고 하자.

```text
┌──────────────────────────────┐
│ 설명 영역       │ 이미지     │
│                 │            │
│ [버튼]          │            │
└──────────────────────────────┘
```

모바일에서 이것을 그냥 축소하면

```text
설명 │ 작은 이미지
```

가 되어 너무 좁다.

대신

```text
설명
↓
이미지
↓
버튼
```

처럼 구조 자체를 세로로 변경할 수 있다.

즉 반응형은

```text
Scale Down
```

보다

```text
Re-layout
```

에 더 가까운 경우가 많았다.

---

## Flex 방향을 바꾸는 방법

예를 들어 Desktop에서는

```css
.wrapper {
  display: flex;
  flex-direction: row;
}
```

로 좌우 배치한다.

모바일에서는

```css
@media (max-width: 768px) {
  .wrapper {
    flex-direction: column;
  }
}
```

으로 바꿀 수 있다.

결과는

```text
Desktop
A | B

Mobile
A
B
```

가 된다.

CSS를 배우면서

```text
flex-direction
```

이 반응형에서 왜 중요한지 이해하게 되는 순간이었다.

---

## CSS Grid도 반응형에서 유용했다

카드 목록처럼 반복되는 UI에는 Grid를 사용할 수 있다.

예를 들어

```css
.grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  gap: 24px;
}
```

Desktop에서는 3열이다.

화면이 줄어들면

```css
@media (max-width: 900px) {
  .grid {
    grid-template-columns: repeat(2, 1fr);
  }
}

@media (max-width: 600px) {
  .grid {
    grid-template-columns: 1fr;
  }
}
```

처럼 바꿀 수 있다.

```text
3열
↓
2열
↓
1열
```

구조가 된다.

---

## auto-fit과 minmax도 알게 됐다

Grid에서는 조금 더 유동적으로 만들 수도 있다.

예를 들어

```css
.grid {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(240px, 1fr));
  gap: 24px;
}
```

처럼 작성할 수 있다.

처음 보면 어렵다.

나는 이렇게 이해했다.

```text
카드는 최소 240px 정도는 유지한다.

공간이 충분하면 여러 개를 한 줄에 놓는다.

공간이 부족하면 다음 줄로 내려간다.
```

즉 몇 px에서 무조건 3열 → 2열이라고 전부 직접 지정하지 않아도

공간에 맞춰 자연스럽게 바뀔 수 있다.

---

## Figma Auto Layout과도 연결됐다

Figma에서 Auto Layout을 사용할 때도 비슷한 생각을 할 수 있다.

```text
Fixed

Hug

Fill
```

같은 설정이 있었다.

이것을 개발과 연결해서 생각하면 이해가 조금 쉬웠다.

```text
Fixed
→ 고정 크기

Fill
→ 남은 공간 채우기

Hug
→ 콘텐츠 크기에 맞추기
```

CSS와 완전히 동일한 개념은 아니지만

Layout을 유동적으로 생각하는 연습이 됐다.

---

## Figma에서 한 사이즈만 만들어도 될까?

작은 프로젝트라면 하나의 기본 화면에서 시작할 수 있다.

하지만

```text
Desktop과 Mobile에서
Layout이 크게 달라진다면
```

두 버전을 모두 보는 것이 좋았다.

예를 들어

```text
Desktop

Mobile
```

두 Frame만 만들어도

어떤 요소가

```text
옆에서 아래로 내려가는지

숨겨지는지

크기가 바뀌는지
```

확인할 수 있다.

---

## 모든 크기의 Figma Frame을 만들 필요는 없다

반대로

```text
320

360

375

390

412

768

1024

1280

1440
```

을 전부 디자인하는 것도 비효율적이다.

중요한 대표 화면을 만들고

그 사이 크기는 개발 단계에서 자연스럽게 대응하도록 하는 편이 현실적이다.

예를 들어

```text
Mobile

Desktop
```

을 기본으로 만들고,

Tablet에서 구조가 크게 달라진다면

```text
Tablet
```

을 추가할 수 있다.

---

## Mobile First라는 방식

반응형을 공부하다 보면

```text
Mobile First
```

라는 표현을 자주 보게 된다.

말 그대로 작은 화면을 먼저 기준으로 만든 뒤

화면이 커질수록 Layout을 확장하는 방식이다.

예를 들어 기본 CSS를

```css
.grid {
  display: grid;
  grid-template-columns: 1fr;
}
```

로 작성한다.

그리고 큰 화면에서

```css
@media (min-width: 768px) {
  .grid {
    grid-template-columns: repeat(2, 1fr);
  }
}
```

처럼 확장한다.

---

## 왜 Mobile First가 이해하기 쉬웠을까?

작은 화면에는 공간이 적다.

따라서

```text
정말 필요한 것
```

부터 남겨야 한다.

예를 들어 Desktop에서는

```text
제목

설명

추가 정보

큰 이미지

여러 버튼
```

을 전부 넣을 수 있다.

모바일에서는 공간이 부족하다.

그래서

```text
무엇이 꼭 필요한가?
```

를 먼저 결정하게 된다.

이 과정이 정보 우선순위를 생각하는 데도 도움이 됐다.

---

## 하지만 모바일에서 기능을 무조건 없애는 것은 아니다

화면이 좁다고 해서

```text
기능 삭제
```

가 자동으로 정답은 아니다.

Desktop에 있던 중요한 기능이라면 모바일에서도 접근할 수 있어야 한다.

단지 표현 방식이 달라질 수 있다.

예를 들어 Desktop에서는

```text
[검색] [필터] [정렬] [설정]
```

을 모두 보여줄 수 있다.

모바일에서는

```text
[검색] [필터]

⋮
```

처럼 일부 보조 기능을 메뉴로 정리할 수 있다.

기능을 없앤 것이 아니라

**우선순위에 따라 표현 방식을 바꾼 것**이다.

---

## Desktop First도 틀린 것은 아니다

기존 Desktop 웹을 반응형으로 바꾸거나

업무용 Dashboard처럼 큰 화면이 핵심인 서비스라면

Desktop을 먼저 설계할 수도 있다.

중요한 것은

```text
무조건 Mobile First
```

라는 규칙보다

```text
주 사용 환경이 무엇인지
```

를 파악하는 것이다.

---

## 모바일 앱과 반응형 웹도 구분해야 했다

모바일 앱만 만드는 프로젝트라면

Desktop Layout 자체가 필요하지 않을 수도 있다.

하지만 그렇다고 반응형 생각이 완전히 필요 없는 것은 아니다.

스마트폰도 크기가 다르다.

```text
작은 화면

큰 화면

화면 비율이 긴 기기
```

가 있고,

글자 크기나 시스템 UI에 따라 공간도 달라질 수 있다.

그래서 모바일 앱에서도

```text
특정 높이와 너비에만 맞춘 디자인
```

은 문제가 될 수 있다.

---

## 절대 위치를 많이 쓰면 반응형이 어려웠다

예를 들어

```css
.button {
  position: absolute;
  left: 320px;
  top: 700px;
}
```

처럼 화면 좌표에 맞춰 배치하면

특정 화면에서는 정확하다.

하지만 화면 크기가 달라지면

```text
버튼 위치가 어긋남

다른 요소와 겹침
```

이 발생할 수 있다.

그래서 일반적인 Layout은

```text
Flex

Grid

Normal Flow
```

를 이용해서 요소 관계로 배치하는 것이 반응형에 더 유리했다.

---

## Figma에서도 Absolute Position을 조심하게 됐다

Figma에서 자유롭게 요소를 배치하면

원하는 위치에 정확히 둘 수 있다.

하지만 Auto Layout 없이 모두 좌표로 배치하면

Frame 크기를 바꿨을 때

```text
요소들이 따라오지 않음
```

문제가 생긴다.

그래서 반응형을 생각하기 시작하니

Auto Layout의 의미도 더 잘 이해됐다.

---

## 텍스트가 반응형에서 가장 먼저 문제를 일으켰다

디자인할 때는 예쁜 샘플 텍스트를 사용한다.

```text
메가MGC 판교점
```

딱 한 줄이다.

실제 데이터는

```text
메가MGC 성남판교테크노밸리역점
```

처럼 길 수 있다.

모바일에서는 두 줄이 된다.

그러면 카드 높이도 달라진다.

---

## 텍스트는 줄바꿈을 전제로 디자인해야 했다

예를 들어

```text
매장명
거리
혜택
```

을 한 줄에 모두 넣었다고 하자.

```text
메가MGC 판교점 | 7분 | 쿠폰 1개
```

Desktop에서는 괜찮다.

모바일에서는

```text
메가MGC 판교테크노...
7분
쿠폰 1개
```

처럼 깨질 수 있다.

이때

```text
글씨를 계속 작게 만들기
```

보다 구조를 바꾸는 편이 나을 수 있다.

```text
메가MGC 판교점

도보 7분 · 쿠폰 1개
```

처럼 말이다.

---

## 글씨를 무조건 줄이는 것은 해결책이 아니었다

화면이 좁아지면

```text
폰트 16px
↓
14px
↓
12px
↓
10px
```

로 계속 줄이고 싶어진다.

그러면 내용은 들어간다.

하지만 읽기 어려워진다.

따라서

```text
글자를 줄여서 억지로 넣기
```

보다

```text
줄바꿈

배치 변경

정보 일부 접기
```

를 먼저 고려하는 것이 좋았다.

---

## 제목 크기는 조금 달라질 수 있다

반대로 매우 큰 Hero 제목은 모바일에서 그대로 사용하면 화면 대부분을 차지할 수 있다.

예를 들어 Desktop에서

```text
64px
```

제목이 자연스럽더라도

모바일에서는

```text
36px
```

정도로 조정할 수 있다.

이런 값은 Media Query로 바꿀 수 있고,

`clamp()`를 이용해 유동적으로 만드는 방법도 있다.

예를 들어

```css
.title {
  font-size: clamp(32px, 5vw, 64px);
}
```

처럼 만들 수 있다.

개념적으로는

```text
최소 32px

화면에 따라 증가

최대 64px
```

이다.

---

## 이미지는 width: 100%가 유용했다

이미지 크기가 원본 픽셀로 고정되어 있으면

모바일 화면보다 커질 수 있다.

그래서

```css
img {
  max-width: 100%;
  height: auto;
}
```

처럼 부모 영역을 넘지 않도록 만들 수 있다.

이렇게 하면 이미지 비율을 유지하면서 화면에 맞게 줄어든다.

---

## object-fit도 자주 만나게 됐다

카드에 사진을 넣을 때

```text
사진마다 크기가 다름
```

문제가 있다.

예를 들어 이미지 영역을

```css
.image {
  width: 100%;
  height: 200px;
  object-fit: cover;
}
```

처럼 만들 수 있다.

그러면 지정한 영역을 채우면서 이미지 비율을 유지하고,

넘치는 부분은 잘릴 수 있다.

반대로 전체 이미지를 모두 보여줘야 한다면

```text
contain
```

이 더 적절할 수도 있다.

---

## 배경 이미지와 콘텐츠 이미지는 다르게 생각했다

배경 이미지라면 일부가 잘려도 괜찮을 수 있다.

하지만

```text
QR 코드

상품 이미지

정보가 포함된 이미지
```

처럼 전체가 보여야 하는 이미지라면

잘리면 문제가 된다.

반응형에서도

```text
이 이미지가 장식인가?

정보인가?
```

를 구분해야 했다.

---

## Navigation이 가장 크게 바뀌는 경우가 많았다

Desktop에서는 상단에

```text
Home  Project  Blog  About  Settings
```

을 모두 보여줄 수 있다.

모바일에서는 공간이 부족하다.

그래서

```text
☰
```

메뉴 안으로 들어갈 수도 있다.

또 앱이라면

```text
Bottom Navigation
```

으로 바뀔 수도 있다.

Navigation은 반응형에서 단순 크기 조절이 아니라

구조 자체가 달라지는 대표적인 요소였다.

---

## 모든 메뉴를 햄버거 안에 넣는 것이 정답은 아니다

모바일이라고 무조건

```text
☰
```

를 쓰는 것은 아니다.

사용자가 자주 이동하는 주요 영역이라면

```text
Home

Map

Benefits

My
```

같은 Bottom Navigation이 더 편할 수 있다.

반대로 자주 쓰지 않는 웹 메뉴라면 햄버거 메뉴가 자연스러울 수 있다.

결국 사용 빈도와 서비스 구조를 봐야 한다.

---

## Header 높이도 달라질 수 있다

Desktop에서는

```text
Logo       Navigation       Profile
```

이 한 줄에 들어간다.

모바일에서는

```text
Logo                  Menu
```

정도만 남길 수 있다.

Header 자체도 더 작아진다.

즉 Header를 그대로 축소하는 것이 아니라

**필요한 요소만 다시 구성**하는 것이다.

---

## Side Bar도 모바일에서는 문제가 됐다

블로그나 Dashboard에서는 왼쪽 Sidebar를 사용할 수 있다.

Desktop에서는

```text
Sidebar | Content
```

가 편하다.

하지만 모바일에서 그대로 유지하면

콘텐츠 영역이 너무 좁아진다.

그래서

```text
Sidebar
→ 접기

또는

→ Drawer

또는

→ 상단 메뉴
```

처럼 바꿀 수 있다.

---

## 숨긴다고 없어지는 것은 아니다

예를 들어 Sidebar를 모바일에서 숨겼다면

Sidebar 안의 중요한 기능으로 들어갈 다른 방법이 있어야 한다.

```text
display: none;
```

만 적용하면

사용자가 해당 메뉴에 접근할 수 없게 될 수도 있다.

그래서 항상

```text
숨긴 요소의 기능은 어디로 갔는가?
```

를 확인해야 했다.

---

## 카드 높이를 고정할 때도 조심했다

예를 들어 모든 카드를

```css
.card {
  height: 180px;
}
```

로 고정하면 정렬이 깔끔하다.

하지만 텍스트가 길어지면

```text
내용 잘림

Overflow

버튼 밀림
```

이 생길 수 있다.

콘텐츠 길이가 달라질 수 있다면

```text
min-height
```

나 자연스러운 콘텐츠 높이를 사용하는 방법도 생각할 수 있다.

---

## 모바일의 세로 길이도 항상 같지 않다

보통 화면 폭만 반응형이라고 생각하기 쉽다.

하지만 높이도 다르다.

특히

```text
100vh
```

를 사용한 Full Screen UI에서는 모바일 브라우저의 주소창이나 시스템 UI 때문에 예상과 다르게 보일 수도 있다.

그래서 Full Screen UI를 만들 때도 실제 기기에서 확인하는 것이 중요했다.

---

## 버튼을 화면 아래에 고정할 때

모바일에서

```text
[시작하기]
```

같은 버튼을 하단에 고정할 수 있다.

편하다.

하지만 내용이 길면 버튼이 콘텐츠를 가릴 수 있다.

그래서 콘텐츠 하단에

```text
버튼 높이만큼의 Padding
```

을 추가하는 등의 처리가 필요할 수 있다.

디자인에서는 버튼만 보지만

실제 구현에서는 겹침까지 생각해야 한다.

---

## Safe Area도 알게 됐다

스마트폰에는

```text
노치

홈 인디케이터
```

같은 영역이 있을 수 있다.

하단 버튼을 화면 끝에 붙이면

기기 UI와 너무 가까워질 수도 있다.

모바일 앱이나 웹앱에서는 이런 Safe Area도 고려해야 한다.

처음 디자인 화면 한 장만 만들 때는 놓치기 쉬운 부분이었다.

---

## Hover는 모바일에 없다

Desktop에서는 마우스를 올렸을 때

```text
Hover
```

상태를 사용할 수 있다.

예를 들어

```text
마우스를 올리면
카드 색 변경
```

같은 것이다.

하지만 모바일에는 기본적으로 마우스 Hover가 없다.

따라서 중요한 정보를

```text
Hover해야만 볼 수 있게
```

만들면 모바일 사용자에게는 접근할 수 없는 정보가 될 수 있다.

---

## 모바일에서는 Touch를 기준으로 생각한다

Desktop에서는 마우스 포인터로 작은 영역도 정확하게 클릭할 수 있다.

모바일에서는 손가락을 사용한다.

그래서 작은 아이콘이라도

실제 터치 가능한 영역은 충분히 크게 만들어야 한다.

예를 들어 시각적으로는

```text
24px 아이콘
```

이어도

터치 영역은 더 넓게 잡을 수 있다.

---

## 반응형은 디자인만의 문제가 아니었다

처음에는

```text
CSS 문제
```

라고 생각했다.

하지만 반응형을 제대로 만들려면

```text
정보 우선순위

페이지 구조

Navigation

텍스트 길이

사용자 행동
```

까지 연결된다.

즉 UI/UX와 개발이 만나는 영역이었다.

---

## 화면이 좁아질 때 무엇을 먼저 지킬 것인가

반응형을 만들 때 내가 가장 중요하게 생각하게 된 질문이다.

```text
공간이 부족해지면
무엇을 먼저 지켜야 할까?
```

예를 들어

```text
브랜드 로고

검색

현재 위치

설정

프로필
```

이 Header에 있다.

모바일에서는 다 들어가지 않는다.

그러면 우선순위를 정해야 한다.

```text
검색

현재 위치
→ 중요

설정
→ 메뉴 안으로

프로필
→ 메뉴 안으로
```

처럼 바꿀 수 있다.

「버튼과 정보의 우선순위」에서 공부했던 우선순위가 반응형에서도 다시 사용된다.

---

## 모든 것을 작게 만드는 것보다 덜 중요한 것을 재배치한다

공간이 부족할 때 가장 쉬운 방법은

```text
전부 축소
```

다.

하지만 그러면

```text
버튼도 작아지고

폰트도 작아지고

아이콘도 작아지고
```

사용성이 떨어진다.

대신

```text
보조 정보 접기

버튼 구조 변경

Navigation 변경

Layout 세로 전환
```

을 먼저 생각할 수 있다.

---

## Desktop에서는 추가 정보가 옆에 있어도 된다

Desktop에는 공간이 많다.

예를 들어

```text
Main Content | Summary
```

처럼 보조 정보를 옆에 둘 수 있다.

모바일에서는

```text
Main Content
↓
Summary
```

로 내려간다.

여기서 중요한 것은

```text
어느 것이 먼저 와야 하는가?
```

다.

단순히 왼쪽 요소부터 위로 보내는 것이 아니라

사용자의 중요도 순서를 기준으로 재배치해야 한다.

---

## CSS order를 사용할 수도 있지만 구조도 중요했다

Flex에서는

```css
order
```

를 사용해 시각적 순서를 바꿀 수도 있다.

하지만 화면마다 너무 복잡하게 순서를 뒤집으면

HTML 구조와 시각적 구조가 달라져 접근성이나 유지보수 측면에서 혼란이 생길 수 있다.

가능하면 기본 구조부터 자연스럽게 만드는 편이 좋았다.

---

## 반응형 디자인은 실제 콘텐츠로 테스트해야 했다

디자인에서는

```text
짧은 제목

예쁜 사진

정확히 맞는 카드
```

를 사용한다.

실제 데이터는 다르다.

그래서 테스트할 때는 일부러

```text
긴 제목

짧은 제목

이미지 없음

많은 카드

카드 1개

긴 설명
```

같은 데이터를 넣어본다.

이때도 Layout이 유지되는지 확인한다.

---

## 작은 화면만 테스트하면 안 됐다

반응형 오류는 모바일에서만 생기는 것이 아니다.

아주 큰 화면에서도 문제가 생길 수 있다.

예를 들어 콘텐츠가

```text
width: 100%
```

라면

4K 모니터에서 카드가 지나치게 넓어질 수 있다.

그래서

```text
작은 화면

중간 화면

큰 화면
```

을 모두 확인하는 편이 좋았다.

---

## 브라우저 창을 직접 줄여보는 방법

가장 간단한 테스트 방법이다.

페이지를 띄우고

```text
창 너비를 천천히 줄인다.
```

그러면서 본다.

```text
어느 순간 깨지는가?

텍스트는 언제 줄바꿈되는가?

카드가 언제 너무 좁아지는가?

Navigation이 언제 겹치는가?
```

이 과정에서 실제 Breakpoint가 필요한 위치도 발견할 수 있다.

---

## 개발자 도구의 기기 모드도 유용했다

브라우저 개발자 도구에서는 여러 기기 크기를 확인할 수 있다.

예를 들어

```text
모바일 크기

태블릿 크기

직접 입력한 크기
```

로 테스트할 수 있다.

다만 특정 기기 프리셋 몇 개만 확인하고

```text
반응형 완료
```

라고 생각하면 놓치는 구간이 생길 수 있다.

그래서 자유롭게 너비도 바꿔보는 편이 좋다.

---

## 가로 모드도 존재한다

모바일이라고 항상 세로 화면만 사용하는 것은 아니다.

특히 지도,

영상,

게임,

특정 데이터 화면에서는

```text
Landscape
```

상황도 생길 수 있다.

모든 프로젝트에서 완벽하게 지원해야 하는 것은 아니지만

필요한 서비스라면 고려해야 한다.

---

## 지도 화면은 반응형에서 특히 달랐다

지도 중심 서비스는 일반적인 카드형 웹과 조금 다르다.

Desktop에서는

```text
List | Map
```

을 동시에 보여줄 수 있다.

모바일에서는 공간이 부족하기 때문에

```text
Map
+
Bottom Sheet
```

형태가 더 자연스러울 수도 있다.

즉 같은 기능이라도 화면 크기에 따라 UI 패턴 자체가 달라질 수 있다.

---

## 반응형에서 Modal도 달라질 수 있다

Desktop에서는 화면 중앙에 작은 Modal이 자연스럽다.

```text
      ┌──────────┐
      │  Modal   │
      └──────────┘
```

모바일에서는 같은 크기의 Modal이 너무 좁을 수 있다.

그래서

```text
Full Screen Modal

Bottom Sheet
```

처럼 바뀔 수 있다.

단순히 Modal 너비를 줄이는 것보다 다른 패턴이 적절할 때가 있다.

---

## 표는 모바일에서 특히 어려웠다

Desktop에서는

```text
| 이름 | 날짜 | 상태 | 금액 | 관리 |
```

같은 Table이 편하다.

모바일에서는 모든 Column을 넣기 어렵다.

해결 방법도 여러 가지다.

```text
가로 스크롤

중요 Column만 표시

카드 형태로 변경

상세 화면으로 이동
```

중 서비스에 맞는 방법을 선택한다.

Table을 무조건 작게 압축하는 것이 정답은 아니다.

---

## 긴 블로그 글도 반응형이 필요했다

블로그에서는 본문만 있는 것이 아니다.

```text
Sidebar

TOC

본문

프로필

Navigation
```

같은 요소가 있다.

Desktop에서는

```text
Sidebar | 본문 | TOC
```

가 가능하다.

하지만 모바일에서는 공간이 없다.

그렇다면

```text
Sidebar 접기

TOC 접기

본문 전체 폭 사용
```

처럼 우선순위를 다시 정할 수 있다.

이 과정에서도

```text
글을 읽는 것
```

이 블로그의 가장 중요한 행동이라는 기준이 필요하다.

---

## 반응형에서 장식을 먼저 줄일 수 있다

화면이 좁아졌는데

```text
큰 장식 이미지

배경 그래픽

보조 일러스트
```

때문에 핵심 콘텐츠가 작아진다면

장식 요소를 줄이거나 숨길 수 있다.

하지만 중요한 정보나 행동부터 숨겨서는 안 된다.

```text
기능

vs

장식
```

을 구분하는 것이 필요했다.

---

## 이미지를 숨기는 것도 이유가 있어야 한다

Desktop Hero에 큰 이미지가 있다고 해보자.

모바일에서 이미지가 공간을 너무 많이 차지한다.

그래서 숨길 수 있다.

하지만 그 이미지 안에 제품 사용법처럼 중요한 정보가 들어 있다면 숨기면 안 된다.

즉

```text
없어도 서비스 이해에 문제가 없는가?
```

를 먼저 본다.

---

## 반응형을 AI에게 맡길 때도 기준을 줘야 했다

AI에게

```text
반응형으로 만들어줘.
```

라고 하면 알아서 Media Query를 만들 수 있다.

하지만

```text
모바일에서 무엇을 숨길지

카드는 몇 열인지

Navigation은 어떻게 변할지
```

를 AI가 결정하게 된다.

내 기획과 다를 수 있다.

그래서 중요한 부분은 직접 알려주는 것이 좋았다.

---

## 예를 들어 Claude에게 이렇게 요청할 수 있다

```text
현재 Desktop 디자인을 기준으로 반응형을 구현해줘.

Desktop
- 카드 3열
- 상단 Navigation 유지
- 콘텐츠 max-width 1200px

Tablet
- 카드 2열

Mobile
- 카드 1열
- 좌우 padding 20px
- 상단 Navigation은 메뉴 버튼으로 변경

중요 기능은 숨기지 말고,
디자인에 없는 새 기능은 추가하지 마.
```

이런 식이다.

---

## 아직 반응형 기준을 정하지 않았다면 AI가 임의로 만들지 않게 한다

예를 들어 모바일 디자인만 완성된 상태라면

```text
현재는 모바일 화면만 구현해줘.

Desktop Layout을 임의로 새로 만들지 말고,
반응형 확장은 나중에 진행한다.
```

라고 할 수 있다.

이것도 작업 범위 관리다.

---

## AI가 만든 반응형도 실제로 확인해야 했다

Claude나 다른 AI가

```text
Responsive 적용 완료
```

라고 해도

실제 브라우저에서는 문제가 있을 수 있다.

```text
769px에서 메뉴 겹침

긴 제목에서 카드 깨짐

고정 버튼이 콘텐츠를 가림
```

같은 것이다.

그래서 코드가 작성됐다는 것과

```text
실제로 모든 크기에서 사용할 수 있다
```

는 별도로 검증해야 한다.

---

## 반응형을 만들 때 완벽하게 모든 화면을 맞추려고 하면 끝이 없었다

화면 크기는 무한하다.

```text
389px에서는 1px 어긋남

411px에서는 줄바꿈

853px에서는 카드 폭이 조금 다름
```

을 전부 하나씩 완벽하게 맞추려고 하면 작업이 끝나지 않는다.

그래서 중요한 것은

```text
모든 픽셀에서 완전히 같은 비율
```

이 아니라

```text
어느 크기에서도
콘텐츠를 이해하고 사용할 수 있는가
```

라고 생각하게 됐다.

---

## Pixel Perfect보다 Layout 규칙

Figma와 390px에서 정확하게 같아도

391px에서 깨진다면 좋은 반응형은 아니다.

반대로 Figma와 몇 px 차이가 나더라도

```text
정보 우선순위

간격 체계

기능

Layout
```

이 자연스럽게 유지된다면 더 안정적인 구현일 수 있다.

그래서 디자인 숫자를 그대로 복사하는 것보다

```text
왜 이런 크기와 구조를 사용했는지
```

를 이해하는 것이 중요했다.

---

## 내가 반응형을 확인하는 순서

화면 하나를 만든다면 대략 이런 순서로 확인하려고 한다.

```text
1. 가장 작은 화면에서도 가로 스크롤이 생기지 않는가?

2. 콘텐츠가 화면 가장자리에 너무 붙지는 않는가?

3. 긴 텍스트가 들어가도 깨지지 않는가?

4. 이미지가 부모 영역을 넘어가지 않는가?

5. 카드 열 수가 화면 크기에 맞게 변하는가?

6. Navigation이 좁은 화면에서 겹치지 않는가?

7. 중요한 기능이 모바일에서 사라지지 않았는가?

8. 버튼을 손가락으로 누르기 쉬운가?

9. 고정 요소가 다른 콘텐츠를 가리지 않는가?

10. 큰 화면에서 콘텐츠가 지나치게 넓어지지 않는가?
```

---

## 디자인 단계에서 확인할 것

Figma에서도 이런 질문을 할 수 있다.

```text
이 Frame을 100px 줄이면 어떻게 될까?

텍스트가 두 줄이면 어떻게 될까?

카드가 1개일 때는?

카드가 10개일 때는?

Desktop에서 이 Sidebar가 필요한가?

Mobile에서는 어디로 이동해야 하지?
```

한 화면을 완성된 그림으로 보는 것이 아니라

**크기가 변할 수 있는 구조**

로 보는 연습이다.

---

## 개발 단계에서 확인할 것

개발에서는 조금 더 구체적으로 볼 수 있다.

```text
고정 width가 너무 많지 않은가?

max-width가 필요한가?

Flex가 줄어들 수 있는가?

Grid Column이 변경되는가?

overflow가 생기는가?

텍스트가 정상적으로 wrap되는가?

absolute 위치를 지나치게 사용하지 않았는가?
```

디자인과 개발이 같이 연결되는 부분이다.

---

## 반응형에서 자주 했던 실수

내가 기억하려고 하는 실수들을 정리하면 이렇다.

```text
Desktop 화면을 그대로 축소함

모든 크기를 px로 고정함

글자가 넘치면 폰트부터 줄임

모바일에서 메뉴를 그냥 숨김

이미지를 고정 크기로 둠

한 가지 샘플 텍스트만 테스트함

특정 휴대폰 크기 하나에서만 확인함

큰 화면 테스트를 하지 않음

Hover에 중요한 기능을 넣음

고정 버튼이 콘텐츠를 가리는지 확인하지 않음
```

---

## 반응형은 마지막에 한 번에 처리하는 작업일까?

처음에는 Desktop 화면을 모두 만든 뒤

```text
마지막에 모바일 대응
```

을 하면 될 것 같았다.

하지만 구조 자체가 잘못되어 있으면 마지막에 고치는 비용이 커진다.

예를 들어 모든 카드가

```text
width: 400px
```

고정이고

모든 요소가 Absolute Position으로 배치되어 있다면

나중에 모바일로 바꾸기 어렵다.

그래서 처음부터

```text
이 요소는 줄어들 수 있는가?

이 Layout은 세로로 바뀔 수 있는가?
```

정도는 생각해두는 것이 좋았다.

---

## 그렇다고 처음부터 모든 Breakpoint를 완성할 필요도 없다

반대로 디자인 초반부터

```text
320px

375px

768px

1024px

1440px
```

모두 완벽하게 만들려 하면 진행이 느려진다.

MVP라면 주요 환경부터 만든 뒤

실제 사용과 테스트를 통해 추가할 수 있다.

중요한 것은

```text
나중에 반응형으로 확장할 수 없는 구조
```

를 만들지 않는 것이다.

---

## 서비스의 주 사용 환경을 먼저 생각한다

모든 서비스가 모든 화면에서 똑같이 중요하지는 않다.

예를 들어

```text
러닝 서비스
→ Mobile 중심

개발자 Dashboard
→ Desktop 중심

개발 블로그
→ Mobile + Desktop 모두 중요
```

할 수 있다.

그러면 디자인과 테스트의 우선순위도 달라진다.

주 사용자와 사용 상황을 생각해야 하는 이유다.

---

## 반응형은 "화면 크기"보다 "사용 상황"의 문제일 수도 있었다

모바일에서는 사용자가

```text
이동 중

한 손 사용

짧은 시간 확인
```

을 할 수 있다.

Desktop에서는

```text
앉아서

큰 화면으로

여러 정보를 동시에 확인
```

할 수 있다.

그래서 같은 기능이라도 단순히 화면 크기뿐 아니라

사용 상황에 맞게 UI가 달라질 수 있다.

---

## Mobile에서는 행동을 빠르게

예를 들어 러닝 서비스라면 모바일에서

```text
러닝 시작
```

이 빠르게 보여야 할 수 있다.

Desktop 버전이 있다고 해도

Desktop에서와 똑같은 Navigation과 정보량을 모바일에 유지할 이유는 없다.

이처럼 반응형은 기술적인 Layout 변화와

UX 변화가 같이 들어갈 수 있다.

---

## 반응형도 결국 우선순위 문제였다

「화면 정렬과 시선의 흐름」에서는

```text
시선의 흐름
```

을 공부했다.

「예쁜 화면보다 사용하기 쉬운 화면」에서는

```text
사용하기 쉬운 화면
```

을 생각했다.

「버튼과 정보의 우선순위」에서는

```text
버튼과 정보의 우선순위
```

를 정했다.

「정보 구조와 페이지 구성」에서는

```text
페이지에 정보를 나누는 법
```

을 봤다.

반응형에서도 같은 질문이 반복됐다.

```text
화면이 좁아졌을 때
무엇을 가장 먼저 남길 것인가?
```

였다.

결국 반응형 디자인도 새로운 별개의 주제가 아니라

앞에서 공부한 UI/UX 기준을

**다른 화면 크기에서도 유지하는 방법**

이었다.

---

## 내가 반응형 디자인에서 지키고 싶은 기준

정리하면 다음과 같다.

```text
1. 특정 화면 크기 하나에만 맞추지 않는다.

2. 화면을 단순히 축소하지 않는다.

3. 고정 width와 유동 width를 구분한다.

4. 너무 큰 화면에서는 max-width를 고려한다.

5. Mobile에서 적절한 좌우 Padding을 유지한다.

6. Layout이 깨지는 지점을 기준으로 Breakpoint를 생각한다.

7. 카드 열 수는 화면 크기에 맞게 변경한다.

8. 좁은 화면에서는 가로 Layout을 세로로 바꿀 수 있다.

9. 중요한 기능을 단순히 숨기지 않는다.

10. 텍스트가 길어질 것을 전제로 디자인한다.

11. 글씨를 무조건 작게 만들어 해결하지 않는다.

12. 이미지가 컨테이너를 벗어나지 않게 한다.

13. Navigation도 화면 크기에 맞게 다시 구성한다.

14. Hover에 핵심 기능을 의존하지 않는다.

15. 실제 모바일 터치 영역을 고려한다.

16. 작은 화면뿐 아니라 큰 화면도 확인한다.

17. AI가 만든 반응형도 직접 브라우저에서 검증한다.
```

---

## 반응형 체크리스트

실제 화면을 확인할 때는 이렇게 볼 수 있다.

```text
□ 320~400px 수준의 작은 화면에서도 사용할 수 있는가?

□ 가로 스크롤이 의도치 않게 생기지 않는가?

□ 긴 제목이 들어가도 깨지지 않는가?

□ 버튼 텍스트가 두 줄이 되어도 문제없는가?

□ Navigation이 겹치지 않는가?

□ 이미지가 찌그러지지 않는가?

□ 카드가 지나치게 좁아지지 않는가?

□ 고정 버튼이 콘텐츠를 가리지 않는가?

□ 중요 기능이 Mobile에서도 접근 가능한가?

□ Tablet 크기 중간 구간에서 어색하지 않은가?

□ 큰 Desktop에서 콘텐츠가 지나치게 넓지 않은가?

□ 실제 데이터를 넣었을 때도 Layout이 유지되는가?
```

## 반응형을 공부하면서 달라진 생각

처음에는

```text
Desktop 디자인

+

Mobile 디자인
```

두 개를 따로 만드는 것이라고 생각했다.

지금은 조금 다르게 생각한다.

```text
하나의 정보 구조
↓
화면 공간에 따라
가장 적절한 Layout으로 변화
```

에 더 가깝다.

같은 서비스이기 때문에

```text
정보의 의미

주요 행동

브랜드
```

는 유지된다.

대신

```text
배치
```

## 마무리

처음 반응형을 생각했을 때는

```text
모바일에서는
Desktop을 작게 만들면 되겠지.
```

라고 생각했다.

하지만 실제로는

```text
줄일 것

쌓을 것

옮길 것

접을 것

그대로 유지할 것
```

을 하나씩 결정해야 했다.

그리고 그 기준은 결국

```text
사용자가 이 화면에서
무엇을 가장 중요하게 해야 하는가?
```

였다.

반응형 디자인은 단순히

```text
CSS Media Query를 넣는 기술
```

이 아니라

> **화면 크기가 달라져도 사용자의 정보 이해와 행동 흐름이 유지되도록 만드는 과정**

이었다.

Figma에서 화면을 예쁘게 만들고,

반응형까지 고려했다고 해도

아직 디자인이 끝난 것은 아니었다.

실제로 사람 앞에서 서비스를 실행해보면

생각하지 못했던 문제가 나타난다.

```text
버튼을 못 찾고

설명을 읽지 않고

예상하지 않은 곳을 누르고

모바일에서 직접 사용하니 불편한 부분이 생긴다.
```

디자인 화면에서는 문제가 없어 보였던 것이

실제 사용 순간에는 달라질 수 있다.
