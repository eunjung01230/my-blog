MY-BLOG를 처음 만들었을 때는 검색 기능이 전혀 필요하지 않았다.

글의 개수가 많지 않았고,

홈에서 조금만 내려가도 원하는 글을 찾을 수 있었다.

카테고리도 있었기 때문에 특정 분야의 글을 보고 싶다면 해당 카테고리를 선택하면 됐다.

그래서 검색은 있어도 좋지만 없어도 크게 불편하지 않은 기능에 가까웠다.

그런데 포스트를 계속 추가하면서 상황이 조금씩 달라졌다.

Git,

프론트엔드,

백엔드,

데이터베이스,

배포,

AI 활용,

블로그 제작 과정처럼 기록하는 주제가 늘어났다.

한 카테고리 안에서도 글이 여러 개 생기기 시작했다.

그리고 어느 순간 이런 상황이 생겼다.

> 예전에 `git pull`에 대해 정리했던 글이 있었는데 어디 있었지?

카테고리를 찾아 들어가는 것보다 내가 기억하고 있는 단어 하나를 입력해서 바로 찾을 수 있다면 훨씬 편할 것 같았다.

그때부터 개발 블로그에도 검색 기능이 필요한지 고민하기 시작했다.

---

## 글이 적을 때는 검색보다 목록이 빨랐다

검색 기능이 있다고 무조건 더 편한 것은 아니었다.

포스트가 열 개도 되지 않는다면 검색창에 단어를 입력하는 것보다 목록을 직접 보는 편이 빠를 수도 있다.

특히 블로그 초기에는 내가 어떤 글을 작성했는지도 거의 기억하고 있었다.

```text
홈
↓
글 목록 확인
↓
원하는 포스트 선택
```

이 정도면 충분했다.

그래서 처음부터 검색 기능을 만들지 않았던 것이 잘못된 선택이라고 생각하지는 않는다.

당시에는 실제로 필요하지 않았다.

블로그 기능을 발전시키면서 계속 느낀 것처럼 기능은 많을수록 좋은 것이 아니라 **현재 사용하는 데 필요한가**가 더 중요했다.

검색도 글이 쌓이고 나서야 필요성이 보이기 시작한 기능이었다.

---

## 카테고리가 있는데 검색까지 필요한가?

검색을 생각하면서 가장 먼저 들었던 의문이었다.

이미 사이드바에 카테고리가 있다.

Git 글을 찾고 싶으면 Git 카테고리를 선택하면 된다.

Database 관련 내용을 찾고 싶으면 해당 카테고리로 이동할 수 있다.

그렇다면 검색은 카테고리와 기능이 겹치는 것 아닐까 싶었다.

하지만 사용 목적을 생각해 보니 둘의 역할은 조금 달랐다.

카테고리는

> Git 관련 글을 보고 싶다.

처럼 **어떤 분야의 글이 있는지 둘러볼 때** 편했다.

검색은

> `origin/main`에 대해 정리했던 그 글을 다시 찾고 싶다.

처럼 **이미 찾고 싶은 내용이 어느 정도 정해져 있을 때** 편했다.

정리하면 이런 차이에 가까웠다.

```text
카테고리
→ 주제를 기준으로 글을 둘러보기

검색
→ 기억나는 단어를 기준으로 특정 글 찾기
```

둘이 완전히 같은 기능은 아니었다.

---

## 특히 공부 기록에서는 검색할 일이 많았다

내 블로그의 목적을 생각하면 검색 기능의 필요성이 더 분명해졌다.

나는 글을 한 번 작성하고 끝내기보다 나중에 다시 찾아보기 위해 블로그를 사용하고 있었다.

공부를 하다가 비슷한 문제를 만나면

> 이거 예전에 정리했던 것 같은데.

라고 생각하는 경우가 있다.

그때 내가 기억하는 것은 정확한 포스트 제목이 아닐 수 있다.

카테고리가 무엇이었는지도 기억하지 못할 수 있다.

대신

`git pull`

`origin/main`

`selected`

`Vercel`

같은 단어 하나는 기억날 수 있다.

그 단어로 예전에 작성한 포스트를 바로 찾을 수 있다면 블로그를 **내 공부 자료처럼 다시 사용하는 과정**이 훨씬 편해진다.

그래서 검색은 다른 방문자를 위한 기능이기도 하지만 나에게 필요한 기능이라는 생각이 더 컸다.

---

## 포스트 제목만으로 찾기에는 한계가 있었다

처음에는 브라우저의 페이지 검색이나 글 제목 목록 정도로도 충분할 것 같았다.

하지만 포스트 제목에 내가 찾으려는 모든 단어가 들어가는 것은 아니다.

예를 들어 제목이

```text
Git 브랜치 이동 과정에서 헷갈렸던 것
```

인데 본문에서 `origin/main`을 자세히 설명했을 수도 있다.

내가 나중에 기억하는 것은 제목이 아니라 `origin/main`일 수 있다.

그렇다면 제목만 검색하는 것보다 본문의 내용까지 찾을 수 있는 검색이 더 유용할 수 있다.

다만 검색 범위를 어디까지 할지는 실제 기능을 만들면서 결정해야 할 문제라고 생각했다.

처음부터 복잡한 검색 시스템을 만드는 것보다 **내가 글을 찾는 데 필요한 수준부터 시작하는 것**이 더 맞았다.

---

## 검색 기능도 너무 크게 만들 필요는 없었다

검색을 생각한다고 해서 검색 전용 페이지에 여러 필터와 정렬 기능까지 한꺼번에 넣고 싶지는 않았다.

검색 날짜,

카테고리 필터,

태그 필터,

정렬 옵션,

추천 검색어 같은 기능을 생각하면 계속 확장할 수 있다.

하지만 지금 해결하고 싶은 문제는 단순했다.

> 기억나는 단어로 예전에 작성한 글을 빠르게 찾고 싶다.

그렇다면 처음에는 검색어를 입력하고 관련된 포스트를 확인할 수 있는 정도면 충분했다.

블로그 자체가 거대한 문서 사이트는 아니기 때문에 검색 기능 역시 현재 규모에 맞게 단순하게 시작하는 편이 맞다고 생각했다.

---

## 검색창을 어디에 둘지도 고민됐다

검색 기능이 필요하다고 생각한 뒤에는 위치도 고민하게 됐다.

사이드바에 둘 수도 있고,

포스트 목록 위에 둘 수도 있고,

상단 메뉴에서 접근하게 할 수도 있다.

내 블로그에는 이미 카테고리가 사이드바에 있었다.

검색까지 사이드바에 추가하면 탐색 기능이 한곳에 모인다는 장점은 있지만, 앞에서 단순하게 정리했던 사이드바가 다시 복잡해질 수도 있었다.

반면 상단 메뉴는 주요 페이지로 이동할 때 항상 보는 영역이다.

검색 역시 블로그 전체의 글을 찾는 기능이므로 상단에서 접근하는 것이 자연스럽게 느껴졌다.

그래서 **상단 메뉴에서 Posts 앞쪽에 검색 기능을 두기로** 했다.

```text
Search | Posts | Projects | About
```

위치 하나만으로 검색 기능이 완성되는 것은 아니지만, 적어도 글을 찾고 싶을 때 어디를 봐야 하는지는 쉽게 알 수 있었다.

---

## 검색 기능이 항상 화면을 크게 차지할 필요는 없었다

상단에 검색을 둔다고 해서 넓은 검색창을 항상 보여주고 싶지는 않았다.

블로그에서 가장 중요한 것은 여전히 글이다.

검색은 필요한 순간에 사용하는 기능이다.

그래서 검색 기능 역시 지금까지 블로그를 정리하면서 잡았던 방향과 비슷하게 생각했다.

**필요한 기능은 쉽게 찾을 수 있게 하되, 사용하지 않을 때 본문보다 눈에 띄지 않게 한다.**

카테고리 접기·펼치기를 만들면서 느꼈던 것과도 비슷했다.

유용한 기능이라고 항상 많은 공간을 차지할 필요는 없다.

---

## 모바일에서는 검색 위치도 달라질 수 있었다

데스크톱에서는 상단 메뉴에 검색 기능을 추가할 공간이 어느 정도 있다.

하지만 모바일에서는 메뉴 자체의 공간이 제한적이다.

검색창까지 항상 펼쳐놓으면 헤더가 지나치게 커질 수도 있다.

그래서 모바일에서는 같은 검색 기능이라도 데스크톱과 똑같은 모양으로 보여줄 필요는 없다고 생각했다.

앞에서 모바일 디자인을 고민하면서 정했던 기준처럼

> 기능의 목적은 유지하되 화면에 맞게 노출 방식은 바꿀 수 있다.

는 방향이면 충분했다.

이 단계에서는 정확한 모바일 검색 UI를 미리 확정하기보다 검색 기능을 추가했을 때 작은 화면에서도 본문을 방해하지 않도록 해야 한다는 정도를 기준으로 두고 싶었다.

---

## 검색 결과가 너무 많아도 의미가 없었다

검색 기능을 만들 때 단순히 검색어가 포함된 모든 글을 보여주기만 하면 되는지도 생각해 봤다.

예를 들어 `git`처럼 자주 등장하는 단어를 검색하면 많은 포스트가 나올 수 있다.

그때 제목만 줄줄이 보여주면 어느 글에 내가 원하는 내용이 있는지 다시 하나씩 열어봐야 할 수도 있다.

그래서 검색 결과에서는 최소한

포스트 제목,

카테고리,

날짜처럼 글을 구분할 수 있는 정보가 같이 있으면 찾기 편할 것 같았다.

필요하다면 검색어가 어떤 내용과 연결되는지도 조금 확인할 수 있으면 좋을 수 있다.

실제 검색 결과에는 검색어가 들어 있는 본문 일부도 함께 보이도록 했다.

검색 기능을 시작하기 전부터 모든 경우를 해결하려고 하지는 않았다.

---

## 한글과 영어가 섞여 있는 것도 생각해야 했다

개발 블로그에는 일반적인 글보다 영어 단어가 많이 들어간다.

Git,

React,

Vercel,

database,

branch,

push 같은 기술 용어가 계속 등장한다.

같은 개념도 글에 따라 한글로 설명하기도 하고 영어 이름을 그대로 사용하기도 한다.

예를 들어 나는

```text
데이터베이스
```

를 기억할 수도 있고

```text
database
```

를 기억할 수도 있다.

검색 기능을 사용하다 보면 이런 표현 차이도 실제 사용성에 영향을 줄 수 있을 것 같았다.

하지만 처음부터 검색 엔진처럼 동의어까지 처리하려고 하면 기능이 지나치게 커진다.

우선은 실제 글에 있는 단어를 기준으로 찾을 수 있는 정도부터 시작하고, 불편함이 확인되면 개선하는 편이 더 현실적이었다.

---

## 검색도 결국 기록을 다시 사용하기 위한 기능이었다

검색 기능을 왜 추가했는지 다시 생각해 보면 단순히 다른 개발 블로그에 있어서가 아니었다.

내 블로그에 글이 쌓이기 시작했고 그 글을 다시 찾는 일이 생겼기 때문이다.

처음 블로그에서는 새 글을 작성하는 것만 생각했다.

지금은 조금 달라졌다.

글을 작성한 뒤

어떻게 분류할지,

긴 글에서 어떻게 이동할지,

여러 글 중 어떻게 찾을지까지 생각하고 있다.

블로그가 글을 **저장하는 공간**에서 글을 **다시 사용하는 공간**으로 조금씩 바뀌고 있었다.

검색은 그 변화를 가장 직접적으로 보여주는 기능 중 하나였다.

---

## 모든 글이 검색만으로 해결되는 것은 아니었다

검색 기능이 생긴다고 카테고리나 태그가 필요 없어지는 것은 아니다.

어떤 경우에는 내가 무엇을 찾고 싶은지 정확히 모를 수도 있다.

그냥

> Git 관련해서 내가 어떤 글들을 작성했지?

라고 보고 싶다면 카테고리가 더 편하다.

비슷한 프로젝트 기록을 연결해서 보고 싶다면 태그가 도움이 된다.

정확한 단어나 주제를 기억하고 있다면 검색이 빠르다.

```text
카테고리
→ 분야를 둘러보기

태그
→ 관련 글을 연결하기

검색
→ 특정 내용을 빠르게 찾기
```

각각 역할이 달랐다.

검색 기능은 기존 탐색 구조를 대체하기보다 그 사이의 부족한 부분을 채우는 기능으로 보는 편이 자연스러웠다.

---

## 그래서 검색 기능은 추가하는 쪽으로 결정했다

처음에는

> 개발 블로그에 굳이 검색까지 필요한가?

라고 생각했다.

글이 적을 때는 실제로 필요하지 않았다.

하지만 포스트가 계속 늘어나고 예전에 작성했던 내용을 다시 찾는 일이 생기면서 생각이 달라졌다.

특히 이 블로그를 내 공부 기록으로 계속 사용할 생각이라면 글을 작성하는 것만큼 **다시 찾을 수 있는 구조**도 중요했다.

그래서 검색 기능을 추가하기로 했다.

다만 처음부터 복잡한 검색 시스템을 만들지는 않았다.

현재 필요한 것은 기억나는 단어를 입력했을 때 관련된 포스트로 빠르게 이동할 수 있는 정도다.

위치는 상단 메뉴에서 쉽게 접근할 수 있게 두고, 기존 블로그의 단순한 디자인을 해치지 않도록 했다.

---

## 검색이 필요해졌다는 것 자체가 블로그가 달라졌다는 뜻이었다

처음에는 검색 기능이 없어서 불편할 일이 없었다.

찾아야 할 글 자체가 많지 않았기 때문이다.

지금 검색이 필요해졌다는 것은 반대로 말하면 그동안 기록한 글이 조금씩 쌓이고 있다는 뜻이기도 했다.

그리고 이제는 새 글을 만드는 것만큼 이미 작성한 내용을 **어떻게 다시 찾고 활용할 것인지**가 중요해졌다.

결국 검색 기능을 추가한 이유는 블로그를 더 기능적으로 보이게 만들기 위해서가 아니다.

> **예전에 공부한 내용을 필요할 때 다시 꺼내보기 위해서다.**

내가 계속 공부하면서 블로그를 사용할 생각이라면 이 기능은 점점 더 유용해질 것 같았다.

처음에는 없어도 됐지만, 글이 쌓인 지금은 필요한 기능이 됐다.

블로그가 발전하면서 기능을 판단하는 기준도 다시 확인할 수 있었다.

**좋은 기능은 처음부터 많이 갖춰놓은 기능이 아니라 실제 사용하다 필요해진 순간 추가하는 기능에 더 가까웠다.**
