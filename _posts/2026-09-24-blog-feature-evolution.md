처음 블로그를 만들었을 때 필요한 기능은 많지 않았다.

글을 작성하고,

카테고리로 나누고,

목록에서 포스트를 선택해 읽을 수 있으면 됐다.

처음에는 그것만으로도 충분했다.

하지만 실제로 글을 계속 쌓고 블로그를 직접 사용하다 보니 필요한 기능이 조금씩 달라졌다.

글이 길어지니 원하는 부분으로 바로 이동하고 싶었고,

카테고리가 늘어나니 화면을 조금 더 단순하게 사용하고 싶었다.

개인 블로그라는 느낌을 더하기 위해 프로필과 GitHub를 연결했고, 방문자가 짧은 글을 남길 수 있는 공간도 생각하게 됐다.

최근에는 글을 단순히 날짜순으로 보는 것만으로는 부족하다는 생각도 들었다.

블로그가 처음에는 **글을 보여주는 정적인 공간**에 가까웠다면, 점점 **쌓인 기록을 실제로 사용할 수 있는 공간**으로 발전하기 시작했다.

---

## 처음에는 '읽을 수 있으면 된다'가 기준이었다

초기 블로그에서 가장 중요했던 것은 글이었다.

포스트를 작성하면 목록에 보이고,

글을 선택하면 본문을 읽을 수 있고,

카테고리로 어느 정도 분류할 수 있으면 됐다.

기능을 많이 넣는 것보다 기록을 계속 남기는 것이 먼저였다.

그래서 처음부터 검색이나 관리자 화면, 방문자 기능 같은 것을 모두 만들려고 하지 않았다.

아직 글도 많지 않은데 복잡한 기능부터 추가하면 오히려 블로그 자체를 관리하는 일이 더 커질 수 있다고 생각했다.

이 판단은 지금도 크게 달라지지 않았다.

다만 글이 실제로 쌓이기 시작하면서 **필요 없던 기능이 필요해지는 순간**이 생겼다.

---

## 긴 글이 생기면서 TOC가 필요해졌다

가장 먼저 체감했던 변화 중 하나가 글의 길이였다.

공부한 내용을 단순히 정의만 적는 것이 아니라

왜 궁금했는지,

어디에서 막혔는지,

무엇을 시도했는지,

최종적으로 어떻게 이해했는지까지 기록하다 보니 글이 자연스럽게 길어졌다.

처음 읽을 때는 위에서부터 읽으면 되지만 나중에 다시 볼 때는 특정 부분만 찾고 싶은 경우가 많았다.

그래서 긴 글에서는 소제목을 기준으로 원하는 위치로 이동할 수 있는 TOC가 필요하다고 느꼈다.

이 기능을 생각하면서 블로그를 보는 관점도 조금 달라졌다.

처음에는

> 글이 잘 보이는가?

가 중요했다면 이후에는

> **다시 찾아보기 편한가?**

까지 생각하게 됐다.

---

## 카테고리도 단순한 목록에서 탐색 기능으로 바뀌었다

글이 많지 않을 때는 카테고리를 그냥 나열해도 큰 문제가 없었다.

하지만 카테고리가 늘어나면 사이드바의 세로 길이도 같이 늘어난다.

항상 전체 목록을 펼쳐놓으면 실제로 글을 읽고 있을 때는 필요하지 않은 정보까지 계속 보이게 된다.

그래서 카테고리를 단순한 고정 목록이 아니라 **필요할 때 확인할 수 있는 탐색 영역**으로 보는 방향으로 바뀌었다.

카테고리를 접었다 펼칠 수 있는 구조도 이런 생각에서 나왔다.

중요한 것은 화려한 동작을 추가하는 것이 아니었다.

글을 찾을 때는 충분히 사용할 수 있고,

글을 읽을 때는 화면을 지나치게 차지하지 않는 것이 목적이었다.

블로그 기능을 추가할 때도 점점

> 무엇을 더 넣을까?

보다

> 지금 사용하면서 무엇이 불편한가?

를 먼저 보게 됐다.

---

## 프로필과 GitHub로 블로그 밖의 개발 기록도 연결했다

글을 읽고 탐색하는 기능을 정리하고 나니 블로그가 조금 문서 사이트처럼 느껴지는 부분도 있었다.

그래서 작성자를 알 수 있는 간단한 프로필과 GitHub 연결도 추가하게 됐다.

블로그와 GitHub는 역할이 달랐다.

```text
GitHub
→ 실제 코드와 프로젝트

블로그
→ 그 과정에서 배운 내용과 고민
```

블로그 글에서 프로젝트 이야기를 읽다가 실제 결과물이 궁금하면 GitHub로 이어질 수 있다.

반대로 GitHub에 있는 코드만으로는 알기 어려운 시행착오와 의사결정 과정은 블로그에서 남길 수 있다.

프로필과 GitHub 연결은 새로운 기능 하나를 추가하는 것보다 **흩어져 있던 개발 기록을 서로 연결하는 역할**에 가까웠다.

---

## 방문자가 남길 수 있는 공간도 생겼다

처음 블로그는 거의 일방향이었다.

내가 글을 작성하고 방문자는 읽는다.

그런데 개인 블로그를 계속 운영하다 보니 포스트가 아닌 짧은 메시지를 남길 수 있는 공간도 있으면 좋겠다는 생각이 들었다.

그래서 방문자 코멘트를 남길 수 있는 영역을 추가하는 방향으로 발전했다.

이 과정에서는 Giscus를 사용하게 됐다.

GitHub 계정을 기반으로 댓글을 남길 수 있고, 별도의 댓글 시스템을 처음부터 직접 만드는 부담을 줄일 수 있다는 점이 좋았다.

하지만 사용하면서 한계도 알게 됐다.

로그인 자체는 Giscus 내부에서 처리되기 때문에 블로그 페이지에서는 **현재 로그인한 사람이 누구인지 직접 알 수 없었다.**

처음에는 GitHub 로그인을 활용하면 방문자를 블로그 사용자처럼 구분할 수 있을 것이라고 생각할 수도 있었지만 실제 구조는 달랐다.

이 경험을 통해 외부 서비스를 연결했다고 해서 그 서비스가 가진 정보를 내 블로그에서도 모두 사용할 수 있는 것은 아니라는 것을 알게 됐다.

---

## 외부 기능을 붙이는 것과 내 서비스 기능을 만드는 것은 달랐다

Giscus를 사용하면서 이 차이를 더 분명하게 느꼈다.

이미 만들어진 서비스를 붙이면 빠르게 기능을 추가할 수 있다.

하지만 사용할 수 있는 범위도 그 서비스가 제공하는 기능 안에 있다.

예를 들어 댓글 작성은 가능하지만,

블로그에서 사용자를 직접 구분하거나,

내가 원하는 방식으로 사용자별 데이터를 저장하거나,

로그인한 사용자에게 별도의 기능을 제공하려면 이야기가 달라진다.

그런 기능까지 필요하다면 결국 블로그 자체에서 사용자와 데이터를 관리할 방법이 필요해진다.

처음에는 정적인 GitHub Pages 블로그에서 시작했지만, 기능을 계속 발전시키다 보면 어느 순간부터 데이터베이스나 별도의 인증 구조가 필요한 이유도 보이기 시작했다.

다만 이 부분은 필요성이 생겼다고 바로 연결하지는 않았다.

지금 당장 필요한 기능과 이후에 구현해야 할 기능을 구분하려고 했다.

---

## 관리하는 사람의 편의도 생각하게 됐다

방문자 입장에서 사용하는 기능뿐 아니라 블로그를 운영하는 나에게 필요한 기능도 생겼다.

포스트를 추가하려면 프로젝트 파일을 열고 직접 작성할 수 있다.

프로젝트 페이지를 수정하는 것도 같은 방식으로 가능하다.

하지만 블로그를 계속 사용하다 보면

> 지금 보고 있는 화면에서 바로 관련 작업으로 이어질 수 없을까?

라는 생각이 들었다.

그래서 포스트 화면에서는 글 추가,

프로젝트에서는 프로젝트 추가,

About에서는 소개 수정처럼 **현재 페이지의 목적과 연결되는 관리 기능**도 생각하기 시작했다.

처음부터 별도의 거대한 관리자 페이지를 만드는 것이 목표는 아니었다.

내가 자주 하는 작업으로 쉽게 이어질 수 있으면 충분했다.

블로그를 보는 사람에게 편한 구조뿐 아니라 **작성하고 관리하는 사람에게도 편한 구조**를 고민하기 시작한 것이다.

---

## 관리자 기능은 단순 버튼보다 더 큰 문제였다

처음에는 수정 버튼 하나가 있으면 될 것처럼 보였다.

하지만 실제로 블로그 안에서 글의 날짜나 내용, 프로젝트 정보를 직접 수정하려면 단순히 버튼을 보여주는 것만으로 끝나지 않는다.

누가 관리자인지 구분해야 하고,

수정한 내용을 저장할 위치도 필요하다.

지금처럼 파일을 기반으로 생성되는 블로그에서는 브라우저에서 값을 수정했다고 해서 원본 포스트 파일이 자동으로 바뀌는 것도 아니다.

결국 제대로 된 관리자 기능을 만들려면

```text
관리자 확인
+
데이터 저장
+
기존 블로그 파일과의 관계
```

까지 생각해야 했다.

그래서 이 부분은 화면에 버튼을 추가하는 것과 실제 관리 시스템을 만드는 것을 구분해서 보기 시작했다.

필요성은 있지만, 데이터베이스까지 연결해야 하는 작업은 별도의 단계로 미뤄두기로 했다.

---

## 글이 많아지니 검색도 필요해졌다

카테고리는 큰 범위에서 글을 찾는 데 도움이 된다.

하지만 내가 정확히 어떤 내용을 찾고 싶은지 알고 있다면 카테고리를 하나씩 이동하는 것보다 검색이 더 빠를 수 있다.

예를 들어

> `git pull`에 대해 썼던 글이 어디였지?

처럼 구체적인 키워드가 기억날 수 있다.

글이 몇 개 없을 때는 목록을 직접 보면 된다.

하지만 포스트가 계속 늘어난다면 이런 방식은 점점 불편해진다.

그래서 상단 메뉴에서도 바로 포스트를 검색할 수 있는 기능을 생각하게 됐다.

검색은 단순히 새로운 기능을 하나 더 추가하는 것이 아니라 **쌓인 기록을 다시 사용하는 방법**이었다.

다만 이 기능 역시 필요성을 확인한 뒤 별도의 작업으로 진행하려고 했다.

---

## 날짜순만으로는 공부 흐름을 표현하기 어려웠다

포스트가 많아지면서 정렬 방식도 다시 생각하게 됐다.

일반적인 블로그에서는 최신 글부터 보여주는 것이 자연스럽다.

나 역시 처음에는 별도의 정렬 기준 없이 글을 보여줬다.

하지만 공부 기록에서는 날짜와 학습 순서가 항상 같지는 않았다.

나중에 작성한 글이 실제로는 앞에서 먼저 알아야 하는 내용일 수도 있다.

반대로 먼저 작성한 글이 더 깊은 내용을 다룰 수도 있다.

그래서 특정 학습 카테고리에서는

```text
최신순
```

뿐 아니라

```text
학습순
```

처럼 **공부하는 흐름을 기준으로 보는 방식**도 있으면 좋겠다는 생각이 들었다.

아직 모든 포스트에 동일한 정렬 기능을 적용한 것은 아니었지만, 글이 쌓이면서 블로그가 단순한 시간순 기록을 넘어 **학습 자료처럼 사용될 가능성**도 보이기 시작했다.

---

## 모든 기능을 한꺼번에 넣지는 않으려고 했다

기능 아이디어는 계속 생겼다.

검색,

정렬,

댓글,

관리자 기능,

사용자 구분,

데이터 저장까지 생각하면 블로그를 계속 확장할 수 있다.

하지만 가능하다는 이유만으로 전부 바로 추가하고 싶지는 않았다.

기능을 하나 추가하면 관리해야 할 코드도 늘어난다.

외부 서비스가 추가되면 설정도 늘어난다.

데이터베이스가 생기면 배포와 보안까지 생각해야 한다.

결국 기능이 많아질수록 블로그를 유지하는 비용도 커진다.

그래서 기능을 발전시키면서도 기준은 계속 같았다.

> **실제로 사용하면서 불편했던 문제를 해결하는 기능인가?**

TOC는 긴 글을 다시 찾기 불편해서 필요했다.

카테고리 구조는 탐색 영역이 복잡해져서 바꿨다.

GitHub 연결은 실제 프로젝트와 글을 이어주기 위해 추가했다.

방문자 코멘트는 짧은 소통 공간이 필요해서 사용했다.

검색과 학습순 정렬 역시 글이 많아지면서 필요성이 생긴 기능이었다.

기능을 먼저 만들고 사용할 이유를 찾기보다 **필요가 생긴 다음 기능을 만드는 순서**를 유지하고 싶었다.

---

## 블로그가 조금씩 하나의 서비스처럼 보이기 시작했다

처음에는 글을 올리는 정적인 사이트에 가까웠다.

하지만 기능을 하나씩 고민하면서 블로그를 보는 시각도 달라졌다.

방문자는 어떻게 글을 찾는가.

긴 글에서는 어떻게 이동하는가.

모바일에서는 어떻게 읽는가.

방문자가 메시지를 남기려면 어떻게 해야 하는가.

운영자는 어떻게 글을 추가하고 관리하는가.

데이터가 필요해지면 어디에 저장해야 하는가.

이런 질문들은 단순한 디자인 문제보다 실제 서비스를 만들 때 고민하는 문제와 더 비슷했다.

물론 내 블로그를 거대한 웹 서비스로 만들 생각은 없다.

하지만 직접 사용하는 기능을 하나씩 추가하면서 **프론트 화면만 만드는 것과 실제로 운영할 수 있는 서비스를 만드는 것의 차이**도 조금씩 경험하게 됐다.

## 기능이 늘어나는 것보다 사용하는 이유가 분명해지는 것이 중요했다

블로그 기능은 앞으로도 더 늘어날 수 있다.

글이 많아지면 지금은 생각하지 못한 탐색 방식이 필요할 수도 있고, 실제 관리자 기능을 만들게 될 수도 있다.

하지만 이번에 기능을 하나씩 발전시키면서 가장 중요하게 느낀 것은 기능의 개수가 아니었다.

처음에는

> 이런 기능도 있으면 멋있겠다.

에서 시작하기 쉬웠다.

지금은 조금 다르게 생각하게 됐다.

> 지금 사용하면서 어떤 문제가 생겼는가?

> 그 문제를 기능으로 해결할 필요가 있는가?

> 기존 구조만으로 해결할 수는 없는가?

> 추가한 뒤에도 계속 관리할 가치가 있는가?

이 질문을 먼저 하게 됐다.

결국 블로그 기능 발전은 블로그를 복잡하게 만드는 과정이 아니었다.

**쌓인 기록을 더 쉽게 찾고, 읽고, 연결하고, 관리할 수 있도록 필요한 기능만 하나씩 추가하는 과정**이었다.

처음에는 글을 보여주는 것만으로 충분했던 블로그가 실제 사용을 통해 조금씩 필요한 기능을 찾아가고 있었다.

그리고 그 과정에서 블로그 자체도 하나의 작은 개발 프로젝트에서, 내가 계속 직접 사용하며 개선하는 **작은 서비스**에 가까워지고 있었다.
