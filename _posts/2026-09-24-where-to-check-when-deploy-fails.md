GitHub Pages를 사용하면서 배포 과정 자체는 생각보다 단순했다.

```text
수정
↓
commit
↓
push
↓
GitHub Pages 빌드·배포
↓
공개 사이트 반영
```

평소에는 이 흐름대로 잘 동작한다.

문제는 어느 날 수정한 내용이 블로그에 보이지 않거나, Pages 배포가 실패했을 때다.

처음에는 이런 상황이 생기면 자연스럽게

> push가 잘못됐나?

부터 생각하기 쉽다.

그래서 같은 명령을 다시 실행하거나 블로그를 계속 새로고침하게 된다.

하지만 배포 과정을 단계별로 나눠보면 확인해야 할 곳도 조금 더 명확해진다.

중요한 것은 **처음부터 모든 것을 다시 하는 것이 아니라 어디까지 정상적으로 진행됐는지를 찾는 것**이었다.

---

## 먼저 내가 정말 push했는지 확인한다

가장 기본적인 부분부터 확인하는 편이 좋다.

로컬에서 파일을 수정했다고 해서 GitHub에도 자동으로 올라가는 것은 아니다.

commit까지만 하고 push를 하지 않았을 수도 있다.

```bash
git status
```

를 확인하면 현재 작업 상태를 볼 수 있다.

필요하면 최근 커밋도 확인할 수 있다.

```bash
git log --oneline -5
```

내가 방금 만든 커밋이 로컬에는 있는데 GitHub에는 없다면 아직 배포 문제가 아니다.

단순히 원격 저장소까지 변경사항이 전달되지 않은 상태다.

---

## GitHub에 최신 커밋이 올라갔는지 확인한다

push까지 했다면 다음은 GitHub 저장소다.

브라우저에서 저장소를 열고 최신 커밋이 내가 방금 만든 것인지 확인한다.

여기에서 최신 커밋이 보인다면 적어도

```text
로컬
↓
commit
↓
push
↓
GitHub
```

까지는 정상적으로 진행된 것이다.

반대로 GitHub에 최신 커밋이 없다면 Pages를 볼 단계가 아니다.

push 과정부터 다시 확인해야 한다.

이렇게 단계를 나누면 원인을 찾는 범위를 빠르게 줄일 수 있다.

---

## 배포 대상 브랜치도 확인한다

GitHub에는 코드가 정상적으로 올라갔는데 공개 블로그가 바뀌지 않을 수도 있다.

그럴 때는 **내가 어느 브랜치에 push했는지**도 확인할 필요가 있다.

GitHub Pages가 운영 사이트와 연결된 브랜치가 따로 있다면 다른 브랜치에 작업한 내용은 바로 공개되지 않는다.

예를 들어 작업 브랜치에 commit과 push까지 모두 성공했어도 운영 브랜치에 반영되지 않았다면 실제 블로그는 그대로일 수 있다.

그래서

```text
GitHub에 코드가 올라갔다
```

와

```text
배포 대상 브랜치에 코드가 올라갔다
```

는 구분해야 한다.

---

## 그다음은 GitHub Pages 빌드 상태를 본다

GitHub에 최신 커밋도 있고 배포 대상도 맞다면 이제 Pages 쪽을 확인한다.

배포가 정상적으로 끝났는지,

아직 진행 중인지,

실패했는지를 보는 단계다.

GitHub에서는 Actions나 Pages 관련 배포 기록을 통해 상태를 확인할 수 있다.

대략 세 가지 상황으로 나눌 수 있다.

```text
진행 중
→ 아직 기다려야 함

성공
→ 실제 사이트 확인 단계

실패
→ 빌드 로그 확인
```

push 직후 블로그가 바뀌지 않는다고 바로 오류라고 생각할 필요는 없다.

단순히 아직 배포가 끝나지 않았을 수도 있기 때문이다.

---

## 실패했다면 로그에서 처음 실패한 부분을 본다

Pages 배포가 실패했다면 가장 먼저 봐야 할 것은 로그다.

처음에는 긴 오류 메시지가 나오면 어디부터 봐야 할지 막막할 수 있다.

하지만 모든 문장을 이해하려고 하기보다 **처음 실패한 지점과 파일 이름**을 먼저 찾는 편이 낫다.

예를 들어 로그에서 이런 정보를 본다.

```text
어떤 파일에서 문제가 발생했는가?

어떤 설정을 읽다가 실패했는가?

문법이나 형식 오류가 있는가?

파일 또는 경로를 찾지 못했는가?
```

오류의 마지막 줄만 보는 것보다 위쪽에서 실제 문제가 처음 발생한 부분을 보는 것이 더 도움이 될 때가 많다.

---

## 새 포스트를 추가한 직후 실패했다면 그 파일부터 본다

블로그에서 배포 문제가 생겼다면 최근에 무엇을 바꿨는지가 중요하다.

예를 들어 새 포스트 하나를 추가한 직후 Pages 빌드가 실패했다면 우선 그 포스트부터 확인한다.

특히 파일 기반 블로그에서는 글 상단의 metadata나 front matter 형식이 잘못돼도 문제가 생길 수 있다.

예를 들어

```yaml
---
title: "글 제목"
date: 2026-09-24
categories: [blog]
---
```

같은 영역에서

따옴표가 잘못 닫혔거나,

구분선이 빠졌거나,

기존 글과 다른 형식을 사용했다면 빌드 과정에 영향을 줄 수 있다.

그래서 오류가 발생했을 때는 전체 프로젝트부터 의심하기보다 **가장 최근에 수정한 파일부터 확인하는 편**이 효율적이다.

---

## 설정 파일을 수정했다면 영향 범위가 더 클 수 있다

포스트 하나를 추가한 것과 사이트 설정 파일을 수정한 것은 영향 범위가 다르다.

예를 들어 블로그의 기본 설정,

플러그인,

경로,

빌드 관련 파일을 수정했다면 사이트 전체에 영향을 줄 수 있다.

이런 파일을 건드린 직후 배포가 실패했다면 최근 변경 내용을 다시 비교해 보는 편이 좋다.

```bash
git diff
```

아직 commit 전이라면 현재 변경사항을 볼 수 있고, 이미 commit했다면 이전 커밋과 비교해서 어떤 부분이 달라졌는지 확인할 수 있다.

문제가 생겼을 때 중요한 것은

> 무엇이 틀렸지?

라고 프로젝트 전체를 보는 것보다

> **정상적으로 배포되던 마지막 상태 이후 무엇을 바꿨지?**

를 찾는 것이었다.

---

## 파일 이름과 경로도 확인한다

배포 자체는 되는데 일부 페이지나 이미지가 보이지 않는다면 빌드 문제와는 조금 다를 수 있다.

특히 GitHub Pages에서는 파일 경로를 주의해야 한다.

로컬에서는 정상적으로 보였지만 실제 배포 환경에서는 프로젝트가 특정 하위 경로에서 열릴 수 있기 때문이다.

그래서

이미지,

CSS,

JavaScript,

내부 링크

등이 깨졌다면 경로부터 확인하는 편이 좋다.

이 경우 Pages 배포 상태에는 `success`가 표시될 수도 있다.

즉,

```text
빌드 실패
```

와

```text
빌드는 성공했지만 일부 경로가 잘못됨
```

은 다른 문제다.

---

## 배포 성공인데 화면이 그대로라면 캐시도 확인한다

GitHub Pages에서는 배포가 성공했고 최신 커밋도 맞는데 브라우저에서는 이전 화면이 보일 수도 있다.

이때는 바로 코드를 다시 수정하기보다 캐시 가능성도 생각해 본다.

특히

favicon,

CSS,

이미지,

OG 이미지

처럼 브라우저나 외부 서비스가 저장해 두는 파일은 바로 바뀌지 않는 것처럼 보일 수 있다.

따라서

```text
최신 커밋 확인
↓
Pages 배포 성공 확인
↓
실제 주소 확인
↓
그래도 이전 화면이면 캐시 확인
```

순서로 보는 편이 안전하다.

캐시 문제인데 코드를 계속 바꾸면 오히려 원인을 더 찾기 어려워질 수 있다.

---

## 404가 나온다고 항상 배포 실패는 아니다

페이지에 접속했는데 404가 나오면 사이트 전체 배포가 실패했다고 생각할 수도 있다.

하지만 홈은 정상적으로 열리고 특정 주소만 404가 나온다면 다른 문제일 가능성이 있다.

예를 들어

```text
잘못된 URL

변경된 포스트 주소

존재하지 않는 파일

잘못된 내부 링크
```

같은 경우다.

이런 상황에서는 Pages 전체 상태보다 해당 페이지의 경로와 링크를 먼저 확인하는 편이 맞다.

배포 오류와 깨진 링크를 구분해야 하는 이유다.

---

## AI와 작업했다면 수정 범위를 다시 확인한다

Claude와 함께 블로그를 수정하다 보면 내가 요청한 파일 외에 다른 파일이 함께 변경될 수도 있다.

화면에서는 작은 수정처럼 보였는데 실제로는 레이아웃이나 설정 파일까지 바뀌었을 수 있다.

그래서 배포 실패가 발생하면

```bash
git status
```

와 변경 파일 목록을 다시 확인한다.

특히

> 내가 의도하지 않은 파일이 수정됐는가?

를 보는 것이 중요하다.

AI가 작성한 코드라고 해서 무조건 문제라는 뜻은 아니다.

하지만 수정 속도가 빠른 만큼 **실제로 어떤 파일이 바뀌었는지를 확인하는 과정**은 더 중요해졌다.

---

## 같은 push를 반복한다고 문제가 해결되지는 않는다

배포가 안 되면 가장 쉽게 할 수 있는 행동이 다시 `git push`하는 것이다.

하지만 이미 최신 commit이 GitHub에 정상적으로 올라가 있다면 같은 내용을 다시 push한다고 빌드 오류가 해결되는 것은 아니다.

예를 들어 포스트 형식이 잘못되어 Pages 빌드가 실패하고 있다면 해야 할 일은

```text
다시 push
```

가 아니라

```text
오류 확인
↓
파일 수정
↓
새 commit
↓
push
```

다.

문제가 어느 단계에 있는지 확인하지 않고 명령을 반복하면 해결되지 않을 뿐 아니라 상황을 더 헷갈리게 만들 수 있다.

---

## 최근 변경사항을 기준으로 범위를 좁힌다

배포 오류를 볼 때 가장 도움이 되는 기준 중 하나는 **마지막으로 정상 배포됐던 시점**이다.

예를 들어 어제까지 잘 됐고 오늘 포스트 하나를 추가한 뒤 실패했다면 우선 오늘 추가한 작업부터 본다.

반대로 오늘

포스트 추가,

설정 파일 수정,

레이아웃 변경,

플러그인 수정

을 한꺼번에 했다면 원인을 찾기가 훨씬 어려워진다.

그래서 평소에 작업 목적별로 commit을 나누는 것이 여기서 도움이 된다.

```text
정상 배포 commit
↓
새로운 변경 commit
↓
배포 실패
```

구조가 분명하면 어떤 변경 이후 문제가 발생했는지 찾기도 쉽다.

---

## 내가 확인할 순서를 정해두기로 했다

배포가 실패했을 때마다 처음부터 고민하지 않도록 확인 순서를 정리해 두는 편이 좋았다.

```text
1. 로컬에서 commit이 만들어졌는지 확인

2. push가 성공했는지 확인

3. GitHub에 최신 commit이 올라갔는지 확인

4. 배포 대상 브랜치가 맞는지 확인

5. Pages / Actions 상태 확인

6. 실패했다면 빌드 로그 확인

7. 최근 수정한 파일부터 점검

8. 배포 성공이라면 실제 사이트와 경로 확인

9. 그래도 이전 화면이면 캐시 확인
```

이 순서대로 보면 처음부터 모든 파일을 뒤질 필요가 없다.

어느 단계까지 정상인지 확인하면서 문제 범위를 좁힐 수 있다.

---

## 배포 오류는 한 번에 전체를 보는 문제가 아니었다

처음에는 배포가 실패하면 블로그 전체에 무언가 큰 문제가 생긴 것처럼 느껴질 수 있다.

하지만 실제로는

Git 문제인지,

GitHub까지 전달되지 않은 것인지,

Pages 빌드 문제인지,

파일 경로 문제인지,

브라우저 캐시 문제인지

서로 다른 단계로 나눠볼 수 있었다.

그래서 가장 먼저 할 일은 고치는 것이 아니라 **어디에서 멈췄는지 확인하는 것**이었다.

```text
로컬
→ GitHub
→ Pages 빌드
→ 배포
→ 실제 브라우저
```

이 흐름을 알고 나니 오류가 나도 무작정 다시 시작할 필요는 없었다.

정상인 단계는 그대로 두고 문제가 생긴 지점부터 보면 된다.

배포 과정도 결국 하나의 긴 작업이 아니라 여러 단계가 연결된 흐름이었다.

그리고 그 흐름을 구분할 수 있게 된 것이, 오류 자체를 외우는 것보다 더 도움이 됐다.
