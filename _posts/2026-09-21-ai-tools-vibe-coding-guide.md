## 들어가며

처음에 나는 AI 코딩 도구를 "원하는 기능을 말하면 알아서 구현해 주는 도구"라고 생각했다. 하고 싶은 걸 문장으로 적으면 나머지는 알아서 되는 줄 알았다.

그런데 실제로 써보니 그게 아니었다. AI는 빠르게 움직였지만, **내가 무엇을 어디까지 맡긴 건지 정하지 않으면 그 속도가 오히려 문제가 됐다.** 확인만 해달라고 했는데 파일이 고쳐져 있거나, 완료됐다는 말을 듣고 확인해보니 아직 안 되고 있거나, 예전 계획을 기준으로 작업이 진행되어 있기도 했다.

결국 중요한 건 AI를 잘 쓰는 기술이 아니라 **현재 프로젝트 상태, 작업 범위, 수정 금지 영역, 기준이 되는 정보, 완료 기준, 검증 방법을 사람이 먼저 정하는 것**이었다.

그래서 AI 도구를 개발에 안전하게 쓰는 방법을 다시 정리해보려고 한다. 이 글은 도구 후기가 아니라 작업 원칙 노트다. 중심은 **Context → Source of Truth → Scope → Analysis → Edit → Verification → Human Decision** 이 흐름이다.

## 1. 바이브 코딩이란 무엇인가

**바이브 코딩(Vibe Coding)** 은 **자연어로 AI에게 의도를 전달하고, AI가 코드 작성이나 수정, 분석을 도와주는 개발 방식**을 가리키는 말이다.

엄밀하게 정해진 표준 용어는 아니고, 쓰는 사람에 따라 범위가 조금씩 다르다. 그래서 정의보다는 **"코드를 한 줄씩 직접 치는 대신 의도를 말로 전달해서 작업하는 방식"** 정도로 이해하고 있다.

여기서 반드시 짚어둘 오해가 하나 있다.

```text
바이브 코딩
       (같지 않다)
코드를 전혀 이해하지 않아도 되는 개발
```

말로 시키면 코드가 나오니까 이해하지 않아도 될 것 같지만, 실제로는 반대였다. **결과를 판단하고 문제가 생겼을 때 어디를 볼지 정하는 건 여전히 사람의 몫**이었다. 이 이야기는 35번에서 다시 다룬다.

## 2. AI 코딩 도구가 잘하는 일

먼저 잘하는 것부터 정리해둔다. 실제로 도움을 받은 것들이다.

| 잘하는 일 | 설명 |
|---|---|
| 반복 코드 작성 | 비슷한 구조를 여러 개 만들 때 빠르다 |
| 구조 초안 만들기 | 처음부터 뭘 만들지 막막할 때 출발점을 준다 |
| 에러 원인 후보 정리 | 오류 메시지를 보고 가능한 원인을 나열해준다 |
| 코드 설명 | 처음 보는 코드가 무엇을 하는지 풀어준다 |
| 리팩터링 후보 제안 | 정리하면 좋을 부분을 짚어준다 |
| 문서 정리 | 흩어진 내용을 읽기 좋게 모아준다 |
| 테스트 케이스 초안 | 무엇을 확인해야 할지 목록을 만들어준다 |
| Git 상태 해석 | 지금 상태가 무슨 뜻인지 설명해준다 |
| UI 수정안 제시 | 여러 가지 방향을 빠르게 보여준다 |

공통점이 보인다. **대부분 "초안"과 "후보"와 "설명"** 이다. 빠르게 만들고 빠르게 정리하는 일에 강하다.

다만 여기서 바로 이어져야 할 전제가 있다. **이 도구가 내 프로젝트의 실제 상태를 완전히 알고 있다고 가정하면 안 된다는 것**이다.

## 3. AI가 모르는 것

이게 가장 중요한 부분이었다.

**AI는 내가 주지 않은 정보나 프로젝트의 실제 현재 상태를 자동으로 다 알 수 없다.**

내가 겪은 것들을 정리하면 이렇다.

| 모를 수 있는 것 | 왜 |
|---|---|
| 최신 main 상태 | 방금 원격에 올라온 변경은 확인하지 않으면 모른다 |
| 팀원의 변경사항 | 다른 사람이 지금 무엇을 고치고 있는지 알 수 없다 |
| 실제 DB 상태 | 데이터베이스에 실제로 무엇이 들어 있는지 알 수 없다 |
| 외부 서비스 설정 | 등록된 주소나 권한 설정은 다른 곳에 있다 |
| 현재 배포 환경 | 어떤 환경변수가 설정되어 있는지 알 수 없다 |
| 내가 방금 다른 창에서 수정한 내용 | 알려주지 않으면 알 수 없다 |

실제로 이 블로그 작업 중에도 겪었다. 내가 파일을 읽는 동안 다른 곳에서 파일 세 개가 수정됐는데, **그건 내가 다시 확인하기 전까지는 알 수 없는 변화**였다.

그래서 작업을 시작할 때 **현재 상태부터 확인하는 단계**가 필요했다. 23번에서 다시 다룬다.

## 4. Context란 무엇인가

**Context(컨텍스트)** 는 **AI가 현재 작업을 이해하기 위해 참고하는 정보**다.

| Context가 될 수 있는 것 |
|---|
| 프로젝트 구조 |
| 관련 파일의 내용 |
| Issue에 적힌 요구사항 |
| 기획이나 설계 문서 |
| 이전에 내가 준 지시 |
| 현재 Git 상태 |

AI는 이 정보를 바탕으로 판단한다. **정보가 없으면 추측하게 되고, 추측은 틀릴 수 있다.**

그런데 여기서 함정이 하나 있다. **Context가 많다고 항상 좋은 것은 아니다.**

관련 없는 정보가 잔뜩 섞여 있으면, 무엇이 지금 중요한지 판단하기 어려워진다. 버튼 하나를 고치는데 프로젝트 전체 파일을 다 주면, 오히려 엉뚱한 곳을 건드릴 여지가 생긴다.

**필요한 것을 주는 것과 가능한 모든 것을 주는 것은 다르다.** 이 이야기는 31번에서 이어진다.

## 5. Source of Truth란 무엇인가

이번 글의 핵심 개념 중 하나다.

**Source of Truth**는 **지금 이 작업에서 무엇을 가장 신뢰할 기준으로 삼을 것인지**를 정하는 것이다.

| Source of Truth가 될 수 있는 것 |
|---|
| 최신 GitHub main 브랜치 |
| 최신 Issue 본문 |
| 확정된 기획 문서 |
| 최종 확정된 디자인 |
| 현재 DB Schema |

작업하다 보면 같은 내용에 대한 정보가 여러 군데 있다. 예전 대화에도 있고, 문서에도 있고, 코드에도 있다. **그런데 서로 다를 수 있다.**

그럴 때 무엇을 믿을지 정해두는 것이다.

```text
예전 대화 내용
AI가 기억하는 계획
이전에 세운 Plan

     ↓ 보다

최신 공식 상태를 우선한다
```

**"이게 기준이다"라고 한 줄 적어주는 것만으로도** 작업 방향이 달라졌다.

## 6. Source of Truth를 왜 명시해야 하는가

명시하지 않으면 **AI가 오래된 정보를 기준으로 작업할 수 있기 때문**이다.

가장 자주 겪은 상황은 이런 것이다.

```text
"예전 계획에서는 있었던 기능"
       vs
"현재 범위에서 제외된 기능"
```

기획 초기에 논의했던 내용이 나중에 빠지는 일은 흔하다. 그런데 그 결정이 **최신 문서에만 반영되고 예전 대화나 예전 문서에는 그대로 남아 있으면**, 어느 쪽을 보느냐에 따라 결과가 달라진다.

AI는 둘 중 무엇이 최신인지 스스로 알 수 없다. **둘 다 그럴듯한 정보로 보인다.**

그래서 작업을 시작할 때 이런 식으로 적어두게 됐다.

```text
Source of Truth: 현재 main 브랜치의 코드와 Issue #12 본문
이전 대화나 예전 문서는 참고만 하고 기준으로 삼지 마라
```

## 7. 분석과 수정은 분리해야 한다

이것도 실제로 겪고 나서 원칙으로 삼은 것이다.

**"확인해줘"라고 했는데 파일이 수정되어 있는 상황**이 있을 수 있다. AI 입장에서는 문제를 찾았으니 고치는 게 도움이 된다고 판단한 것이다.

그런데 그게 곤란할 때가 있다. 아직 **고칠지 말지를 내가 결정하지 않았기 때문**이다.

그래서 순서를 나누게 됐다.

```text
1. 먼저 분석만          무엇이 문제인지 파악한다
↓
2. 문제 보고            발견한 것을 알려준다
↓
3. 수정 여부 결정        고칠지 말지 내가 정한다
↓
4. 수정                 허락한 범위만 고친다
```

핵심은 **3번이 사람의 자리**라는 것이다.

```text
분석 요청
       (같지 않다)
수정 허용
```

"확인해줘"와 "고쳐줘"는 다른 말인데, 명확히 구분해서 말하지 않으면 같은 뜻으로 전달될 수 있었다.

## 8. "먼저 분석만 해라"가 왜 중요한가

7번을 좀 더 풀어보면, 분석 단계에서 확인해야 할 것들이 따로 있다.

| 확인할 것 | 왜 |
|---|---|
| 문제 원인 | 증상과 원인이 다를 수 있다 |
| 영향 범위 | 고치면 다른 곳이 깨질 수 있다 |
| 다른 사람 작업 여부 | 내가 건드리면 안 되는 부분일 수 있다 |
| 수정 필요성 | 사실은 의도된 동작일 수도 있다 |

이게 끝나기 전에 코드를 바꾸면 **문제를 더 크게 만들 수 있다.**

특히 마지막이 중요했다. **"이상해 보인다"와 "잘못됐다"는 다르다.** 내가 모르는 이유로 그렇게 되어 있을 수 있다. 팀 프로젝트라면 더 그렇다.

Git 글에서 "충돌이 나면 명령어부터 실행하지 말고 상태를 먼저 보라"고 정리했는데, 구조가 같은 이야기였다. **파악이 먼저이고 조치가 나중이다.**

## 9. 작업 범위를 명확히 하는 방법

그래서 요청할 때 넣게 된 항목들이 있다.

```text
현재 상황
↓
이번 목표
↓
Source of Truth
↓
수정 허용 범위
↓
수정 금지 범위
↓
검증 방법
↓
완료 기준
```

각 항목이 하는 일은 이렇다.

| 항목 | 없으면 생기는 일 |
|---|---|
| 현재 상황 | AI가 상태를 추측한다 |
| 이번 목표 | 무엇이 끝인지 서로 다르게 이해한다 |
| Source of Truth | 오래된 정보를 기준으로 작업할 수 있다 |
| 수정 허용 범위 | 어디까지 손대도 되는지 모른다 |
| 수정 금지 범위 | 건드리면 안 되는 곳을 건드린다 |
| 검증 방법 | 확인을 너무 적게 하거나 너무 많이 한다 |
| 완료 기준 | "완료"의 뜻이 서로 다르다 |

전부 적는 게 번거로워 보이지만, **적지 않으면 나중에 되돌리는 데 더 오래 걸렸다.**

## 10. 수정 금지 범위가 필요한 이유

9번의 항목 중에서 특히 효과가 컸던 게 이것이다.

**AI는 관련 있어 보이는 파일까지 "도움이 되겠다"고 판단해서 수정할 수 있다.** 나쁜 의도가 아니라 더 잘하려는 판단이다.

그래서 이런 제한을 적어둔다.

| 제한 | 막으려는 것 |
|---|---|
| 이 파일만 수정 | 관련 파일까지 번지는 것 |
| 다른 팀원 파일 수정 금지 | 내 담당이 아닌 곳을 건드리는 것 |
| Git write 금지 | 확인 전에 기록이 남는 것 |
| 설정 파일 수정 금지 | 프로젝트 전체에 영향이 가는 것 |

**금지 범위는 허용 범위만큼 중요했다.** "이것만 해라"라고 하면 그 바깥은 자연스럽게 제외될 것 같지만, 실제로는 **"이건 하지 마라"까지 적어야 확실했다.**

## 11. 한 번에 너무 큰 작업을 맡기면 왜 어려운가

처음에는 크게 맡기는 게 효율적이라고 생각했다.

```text
"로그인부터 DB, 지도, 배포까지 다 해줘"
```

이렇게 요청하면 범위가 너무 넓어진다. 문제는 **결과가 나왔을 때 확인할 수가 없다는 것**이다. 파일이 수십 개 바뀌어 있으면 어디부터 봐야 할지 모른다.

그리고 중간에 뭔가 잘못되면, **어느 단계에서 어긋난 건지 찾기 어렵다.**

그래서 나누게 됐다.

```text
문제 분석
↓
작은 기능 하나
↓
검증
↓
다음 기능
```

**한 번에 하나씩 하고 매번 확인하는 편**이 결과적으로 빨랐다. 큰 덩어리를 한 번에 받아서 전부 검토하는 것보다 나았다.

## 12. 작은 단위 작업의 장점

정리하면 이렇다.

| 장점 | 설명 |
|---|---|
| 오류 범위가 작다 | 문제가 생겨도 방금 한 것 안에 있다 |
| 변경 파일이 적다 | 무엇이 바뀌었는지 한눈에 본다 |
| 확인하기 쉽다 | 하나씩 눌러보고 넘어갈 수 있다 |
| 되돌리기 쉽다 | 잘못되면 그 단계만 되돌린다 |
| AI가 덜 혼동한다 | 지금 집중할 대상이 분명하다 |
| 내가 이해하기 쉽다 | 따라갈 수 있는 속도로 진행된다 |

마지막이 가장 컸다. **내가 따라갈 수 있는 크기로 쪼개는 것**이 결국 핵심이었다.

## 13. AI의 "완료"는 무엇을 의미할까

이 글에서 가장 강조하고 싶은 부분이다.

AI가 "완료했습니다"라고 말해도, **실제로는 아래 중 하나일 수 있다.**

| 상태 | 어디까지 된 것인가 |
|---|---|
| 코드 작성 완료 | 코드를 만들었다 |
| 파일 저장 완료 | 디스크에 썼다 |
| Build 성공 | 실행 가능한 형태로 만들어졌다 |
| 로컬 실행 성공 | 내 컴퓨터에서 돌아간다 |
| 기능 동작 확인 | 실제로 눌러서 되는 걸 봤다 |
| 실제 배포 환경 확인 | 배포된 곳에서도 된다 |
| 외부 서비스까지 통합 확인 | 연결된 것까지 전부 된다 |

**전부 다른 상태다.** 그런데 말로 표현하면 똑같이 "완료"다.

다른 공부 글에서도 같은 문제를 계속 만났다. "DB 연결 완료", "백엔드 구현 완료", "배포 성공", "프론트 구현 끝", "Git 작업 끝". 전부 **한 단어가 여러 단계를 뭉뜽그린 경우**였다.

AI와 작업할 때는 이 문제가 더 커진다. **진행이 빠르니까 확인할 틈 없이 "완료"가 쌓인다.**

## 14. 완료 기준을 미리 정하기

그래서 시작할 때 완료 조건을 적어두게 됐다.

```text
이번 작업 완료 조건

1. 파일 생성
2. 코드 작성
3. Build 성공
4. 실제 버튼 동작 확인
5. DB 저장 확인
```

이렇게 적어두면 두 가지가 좋다.

**첫째, "완료"의 뜻이 하나로 맞춰진다.** 3번까지만 하고 완료라고 하지 않는다.

**둘째, 어디까지 할지 내가 정하게 된다.** 초안만 필요한 작업이면 2번까지만 적으면 된다. **모든 작업에 5번까지 요구할 필요는 없다.**

중요한 건 **매번 최대한 하는 게 아니라 이번에는 어디까지인지 정하는 것**이었다.

## 15. Build 성공과 기능 성공은 다르다

13번의 항목 중에서 특히 헷갈리기 쉬운 지점이다.

```text
"build 성공, 작업 완료"
```

이 말을 들으면 다 된 것 같다. 그런데 Build가 확인하는 건 **실행 가능한 결과물이 만들어지는가**까지다.

| Build가 확인하는 것 | Build가 확인하지 않는 것 |
|---|---|
| 문법 오류 | Database 연결 |
| 타입 오류 | 외부 API 응답 |
| 없는 파일 참조 | 환경변수 존재 여부 |
| 빌드 설정 문제 | 실제 기능 동작 |

Backend 글과 Deployment 글에서 이미 정리한 내용이라 여기서는 짧게만 연결한다. **Build 성공은 Runtime 정상을 보장하지 않는다.**

AI가 빌드까지 돌려보고 "성공"이라고 하면 믿기 쉬운데, **그건 13번 표의 세 번째 칸까지**라는 걸 기억해야 했다.

## 16. 검증도 범위를 정해야 한다

13~15번을 보면 검증을 많이 할수록 좋을 것 같다. 그런데 그것도 아니었다.

**검증 범위도 작업에 맞게 정해야 한다.**

| 상황 | 필요한 검증 수준 |
|---|---|
| 빠른 초안 작성 | 파일이 저장됐는지만 확인 |
| 중요 기능 merge 전 | Build + 실제 기능 테스트 |
| 배포 전 | 실제 환경에서 동작 확인 |

글 초안을 하나 쓰는 작업에 배포 환경 검증까지 요구하면, **검증이 작업보다 오래 걸린다.**

반대로 실제 사용자에게 나가는 기능을 파일 저장만 확인하고 넘기면 위험하다.

**작업의 무게에 검증을 맞추는 것**이 필요했다.

## 17. 검증을 너무 많이 하면 생기는 문제

실제로 겪은 문제다.

"다시 확인해줘", "전체 검증해줘", "한 번 더 봐줘"를 반복하면 **실제 구현보다 검증에 더 많은 시간이 들어간다.**

특히 AI와 작업할 때는 검증 자체도 빠르게 실행되기 때문에, **부담 없이 계속 시키게 된다.** 그러다 보면 같은 것을 여러 번 확인하고 있다.

여기서 오해하면 안 되는 게 있다.

```text
검증하지 말자
       (아니다)
필요한 수준의 검증 기준을 먼저 정하자
```

**검증을 줄이자는 게 아니라, 이번 작업에서 무엇을 확인할지 먼저 정하자**는 것이다. 정해두면 그것만 하고 넘어갈 수 있다. 정해두지 않으면 불안해서 계속 확인하게 된다.

## 18. Git 작업은 일반 파일 수정과 다르다

여기서부터는 권한 이야기다.

파일을 수정하는 것과 Git에 반영하는 것은 **영향 범위가 완전히 다르다.**

| 동작 | 영향 범위 |
|---|---|
| 파일 수정 | 내 컴퓨터의 파일 하나 |
| commit | 내 Local Git 기록 |
| push | 원격 저장소. 팀원이 보게 된다 |
| PR | 팀의 협업 상태 |
| merge | 기준 branch. 모두에게 영향 |

**아래로 갈수록 되돌리기 어렵고 영향받는 사람이 늘어난다.**

그래서 이 구분이 필요했다.

```text
AI에게 파일 수정을 허용했다
       (같지 않다)
push까지 해도 된다
```

파일은 고쳐보고 아니면 되돌리면 된다. 하지만 **push는 다른 사람에게 이미 전달된 것**이다. Git 글에서 push와 merge를 구분했던 이유가 여기서도 그대로 적용됐다.

## 19. Git Write 권한을 분리하기

그래서 단계별로 나눠서 생각하게 됐다.

| 권한 | 무엇을 하는가 | 영향 |
|---|---|---|
| Read | 상태와 파일을 확인한다 | 없음 |
| Edit | 파일을 수정한다 | 내 작업 파일 |
| Commit | Local Git 기록에 남긴다 | 내 저장소 기록 |
| Push | 원격 저장소를 변경한다 | 팀원이 보게 됨 |
| PR | GitHub 협업 상태를 만든다 | 팀의 작업 흐름 |
| Merge | 기준 branch를 변경한다 | 프로젝트 전체 |

**Read는 거의 항상 허용해도 된다.** 상태를 확인하는 건 아무것도 바꾸지 않는다. 오히려 3번에서 본 것처럼 **확인을 먼저 시키는 게 안전하다.**

반대로 아래쪽으로 갈수록 **내가 결과를 보고 판단한 다음에 하는 게 맞았다.**

실제로 작업할 때 "파일은 만들어도 되지만 commit과 push는 하지 마라"라고 미리 적어두면, 결과를 먼저 보고 결정할 수 있었다.

## 20. 위험한 Git 작업을 자동으로 맡기지 않는 이유

Git 명령 중에는 **기존 작업에 큰 영향을 주는 것들**이 있다.

| 작업 | 왜 위험한가 |
|---|---|
| reset | 기록을 되돌린다. 작업이 사라질 수 있다 |
| force push | 원격 기록을 덮어쓴다. 남의 작업이 지워질 수 있다 |
| rebase | 기록을 다시 쓴다. 공유된 상태면 문제가 커진다 |
| branch 삭제 | 작업 갈래가 사라진다 |
| conflict 임의 해결 | 누군가의 변경이 조용히 지워질 수 있다 |

이번 글에서 이 명령들의 사용법을 다루지는 않는다. Git 글에서도 같은 이유로 제외했다.

여기서 중요한 건 사용법이 아니라 원칙이다.

```text
확인 없이 자동으로 실행되지 않게 한다
```

이 명령들은 **실행되고 나서 "아 그거 하지 말았어야 했는데"가 통하지 않는 경우**가 있다. 그래서 실행 전에 멈추게 하는 게 맞았다.

## 21. Conflict를 AI가 임의로 해결하면 안 되는 이유

20번의 마지막 항목을 따로 다룰 만하다.

충돌을 없애는 것 자체는 어렵지 않다. 한쪽을 지우면 된다. **AI는 문법적으로 말이 되는 결과를 충분히 만들 수 있다.**

문제는 그게 **맞는 결과인지는 다른 문제**라는 것이다.

충돌이 났다는 건 **두 사람이 같은 곳을 다르게 판단했다**는 뜻이다. 그런데 **왜 그렇게 판단했는지는 코드에 적혀 있지 않다.** 디자인이 바뀌었을 수도 있고, 다른 요구사항이 생겼을 수도 있다.

```text
기술적으로 합칠 수 있다
       (같지 않다)
어느 쪽이 맞는지 안다
```

그래서 충돌은 **담당자나 Source of Truth를 확인한 다음에 해결**하는 게 맞았다. 특히 팀 프로젝트에서는 그렇다.

Git 글에서도 같은 이야기를 했는데, AI와 작업할 때 더 조심해야 했다. **빠르게 해결해주니까 그대로 받아들이기 쉽기 때문**이다.

## 22. 다른 사람 파일을 수정할 때 주의할 점

팀 프로젝트에서 작업하다 보면 내 담당이 아닌 곳에서 문제를 발견할 때가 있다.

여기서 구분이 필요했다.

```text
문제를 발견했다
       (같지 않다)
내가 수정해도 되는 문제다
```

상황에 따라 다르게 대응하는 게 맞았다.

| 상황 | 어떻게 |
|---|---|
| 문제 발견 | 일단 보고한다 |
| 내 담당 범위 | 수정한다 |
| 다른 팀원 담당 | 먼저 확인하고 결정한다 |

고치는 게 도움이 될 것 같아도, **그 사람이 지금 그 파일을 작업 중일 수 있다.** 그러면 나중에 충돌이 나고, 누가 뭘 고쳤는지 알기 어려워진다.

AI에게도 이 구분을 알려줘야 했다. **"문제를 찾으면 고쳐라"가 아니라 "문제를 찾으면 알려달라"** 로 요청하는 게 안전했다.

## 23. AI에게 현재 상태부터 확인시키기

3번에서 AI가 현재 상태를 모른다고 했는데, 해결 방법은 단순하다. **확인시키면 된다.**

작업 시작 전에 확인하면 좋았던 것들이다.

| 확인할 것 | 왜 |
|---|---|
| git status | 지금 뭐가 수정되어 있는지 |
| 현재 branch | 어디에서 작업하려는지 |
| 최신 main 여부 | 낡은 상태에서 시작하지 않는지 |
| 관련 파일 | 실제 코드가 어떻게 되어 있는지 |
| 관련 Issue | 무엇을 하기로 했는지 |

Read 권한은 아무것도 바꾸지 않으니 **부담 없이 먼저 시킬 수 있다.**

다만 **모든 작업에서 똑같은 확인을 매번 해야 한다고 일반화하지는 않는다.** 글 하나 새로 쓰는 작업과 여러 파일을 고치는 작업은 확인할 것이 다르다. **작업 크기에 맞춰 정하면 됐다.**

## 24. 오래된 Plan이나 기억을 그대로 믿지 않기

5~6번의 Source of Truth와 이어지는 이야기다.

AI가 **이전 세션에서 세운 계획이나 오래된 문서를 기준으로 작업**할 수 있다. 그 정보가 틀린 게 아니라 **그때는 맞았던 정보**다.

문제는 그 사이에 상황이 바뀌었을 수 있다는 것이다.

- 기능 범위가 조정됐다
- 다른 방식으로 하기로 했다
- 이미 누군가 다르게 구현했다

그래서 작업을 이어갈 때 **"예전 계획 말고 지금 상태를 먼저 읽어라"** 라고 명시하게 됐다.

특히 며칠 지난 뒤에 이어서 작업할 때 필요했다. **내 기억도 예전 상태에 머물러 있기 때문**에, 둘 다 낡은 정보로 작업하게 될 수 있었다.

## 25. AI 기억과 프로젝트 실제 상태는 다르다

24번을 좀 더 분명히 해두면 이렇다.

**AI가 기억하는 내용은 프로젝트 파일이나 Git 상태 그 자체가 아니다.**

```text
AI가 기억하는 것    이전에 오간 대화와 그때 확인한 내용
프로젝트의 실제 상태  지금 저장소와 파일에 있는 것
```

이 둘은 **같을 수도 있고 다를 수도 있다.** 그 사이에 무엇이 바뀌었는지는 확인해봐야 안다.

그래서 **중요한 기술적 사실은 기억이 아니라 실제 코드나 문서나 저장소에서 다시 확인하는 게** 맞았다.

"아까 그 파일 있잖아"보다 **"그 파일을 다시 읽고 확인해달라"** 가 안전했다. 확인하는 데 드는 시간은 짧고, 틀린 정보로 작업했을 때 되돌리는 시간은 훨씬 길었다.

## 26. Claude Code는 무엇에 적합한가

실제로 사용한 도구 두 개를 정리해둔다. 먼저 **Claude Code**다.

개발 프로젝트 안에서 이런 작업을 도와줄 수 있는 도구다.

| 할 수 있는 일 |
|---|
| 파일 읽기 |
| 코드 수정 |
| 프로젝트 구조 분석 |
| Terminal 명령 실행 |
| Git 상태 확인 |
| 테스트나 빌드 실행 |

특징은 **실제 파일과 실행 환경에 접근한다**는 점이다. 코드를 제안만 하는 게 아니라 직접 읽고 고치고 실행해볼 수 있다.

그래서 편한 만큼 **범위를 정해야 할 이유도 커진다.** 지금까지 정리한 권한 분리와 수정 금지 범위가 필요한 이유가 여기에 있다.

한 가지 짚어둘 점이 있다. **실제로 가능한 작업은 권한 설정과 환경에 따라 다를 수 있다.** 어떤 환경에서는 특정 명령이 제한되어 있기도 하다. **모든 환경에서 똑같이 동작한다고 가정하지 않는 게** 맞았다.

## 27. Claude Design은 무엇에 적합한가

**Claude Design**은 디자인 작업 쪽이다.

| 도움이 됐던 것 |
|---|
| 기존 화면 구조를 기반으로 시각적으로 수정하기 |
| 색상, 간격, 타이포 조정 |
| 여러 화면의 톤을 통일하기 |
| 시안을 여러 번 반복해서 다듬기 |

특히 **반복 수정**에서 유용했다. 조금씩 바꿔가며 여러 안을 보는 작업은 손으로 하면 오래 걸린다.

여기서도 경계가 필요했다.

```text
시각적으로 다듬는 것
       (같지 않다)
서비스 정책이나 기능을 결정하는 것
```

"이 버튼을 없애는 게 깔끔하겠다"는 판단은 **디자인 판단처럼 보이지만 사실 기능 결정**이다. 그 버튼이 왜 있는지는 기획 쪽 이야기다.

**보기 좋게 만드는 것과 무엇을 만들지 정하는 것은 다른 일**이었다.

## 28. Figma와 Claude Design 역할 나누기

그래서 역할을 나눠서 생각하게 됐다.

| 어디 | 무엇을 정하는가 |
|---|---|
| Figma | 화면 구조, 정보 배치, 흐름 |
| 기획 문서 | 기능, 정책, 범위 |
| Reference | 분위기, 색감 |
| Claude Design | 정해진 범위 안에서 시각적으로 다듬기 |

```text
무엇을 만들 것인가        기획 문서
어떻게 배치할 것인가       Figma
어떤 느낌으로 할 것인가    Reference
그 안에서 다듬기          Claude Design
```

이렇게 나눠두니 **요청할 때 무엇을 알려줘야 하는지**가 분명해졌다. 구조와 기능은 이미 정해져 있으니 그건 유지하라고 하고, 다듬을 부분만 말하면 됐다.

다만 이건 **내가 써본 하나의 작업 방식 예시**다. 팀과 프로젝트에 따라 다르게 나눌 수 있다.

## 29. 디자인 AI에게도 수정 범위가 필요하다

10번에서 코드 작업에 수정 금지 범위가 필요하다고 했는데, **디자인 작업도 마찬가지**였다.

세 가지로 나눠서 적는 방식이 잘 맞았다.

| 구분 | 예 |
|---|---|
| 유지 (Keep) | 화면 구조, 기능, 표시되는 정보 |
| 변경 (Change) | 색상, 간격, 크기 |
| 금지 (Do Not Change) | 새 기능 추가, Navigation 변경 |

```text
Keep            지금 이대로 두어야 하는 것
Change          이번에 바꿀 것
Do Not Change   절대 건드리면 안 되는 것
```

Keep과 Do Not Change가 비슷해 보이는데, 나눠 쓰니 도움이 됐다. **Keep은 "지금 형태를 유지"이고, Do Not Change는 "새로 만들거나 없애지 마라"** 에 가까웠다.

## 30. "예쁘게 해줘"가 위험한 이유

29번이 필요한 이유가 이것이다.

```text
"예쁘게 해줘"
```

이렇게 요청하면 **어디까지 바꿔도 되는지 알 수 없다.** 그래서 더 나아 보이는 방향으로 판단하게 되고, 그 과정에서 **기능 구조나 정보 배치까지 바뀔 수 있다.**

보기에는 확실히 나아졌는데, 있던 정보가 사라졌거나 메뉴 위치가 달라져 있는 경우다. **디자인은 좋아졌지만 내가 원한 건 그게 아니었다.**

그래서 이렇게 바꿔 말하게 됐다.

```text
"예쁘게 해줘"

     ↓

"구조와 정보는 그대로 두고
간격과 색상만 정리해줘.
메뉴는 추가하거나 빼지 마라."
```

**추상적인 요청보다 변경 범위를 구체적으로 알려주는 것**이 결과적으로 원하는 것에 가까웠다.

## 31. 모든 Context를 한 번에 주면 좋은가

4번에서 남겨둔 이야기다.

**정보를 많이 줄수록 좋을 것 같지만 항상 그렇지는 않았다.**

| 작업 | 필요한 Context |
|---|---|
| 프로젝트 구조를 바꾸는 작업 | 전체 구조를 봐야 한다 |
| 버튼 하나 수정 | 그 화면과 관련 파일이면 충분하다 |
| 오류 하나 해결 | 오류 메시지와 관련 코드 |

작은 작업에 전체 프로젝트를 다 주면 **지금 중요한 게 무엇인지 흐려진다.** 그리고 관련 없어 보이는 곳까지 개선 대상으로 보게 될 수 있다.

```text
필요한 Context
       (같지 않다)
가능한 모든 Context
```

**"무엇을 줄까"보다 "이 작업에 무엇이 필요한가"** 를 먼저 생각하는 게 나았다.

## 32. AI가 예상과 다른 방향으로 갈 때

결과가 원하는 것과 다를 때, 처음에는 더 긴 설명을 덧붙였다. 그런데 그러면 **점점 길어지기만 하고 원하는 방향으로 수렴하지 않았다.**

순서를 바꿔봤다.

```text
1. 현재 결과 확인        실제로 무엇이 나왔는지 본다
↓
2. 어떤 부분이 다른지 특정  전부가 아니라 어디가 다른지 짚는다
↓
3. 유지할 부분 지정       괜찮은 부분은 건드리지 말라고 한다
↓
4. 수정할 부분만 다시 요청  그 부분만 바꾼다
```

**3번이 특히 효과가 있었다.** 유지할 것을 말해주지 않으면, 고치는 과정에서 잘 됐던 부분까지 바뀔 수 있다.

전체를 다시 시키는 것보다 **차이만 좁혀가는 편**이 빨랐다.

## 33. 프롬프트를 수정할 때 중요한 것

32번을 실제 문장으로 보면 차이가 분명하다.

```text
"아니야 다시 해줘"
```

이건 무엇이 아닌지 알려주지 않는다. 다시 해도 같은 방향으로 갈 가능성이 높다.

```text
"Header 구조는 유지하고
버튼 크기만 20% 키우고
색상은 바꾸지 마라"
```

이건 **유지할 것, 바꿀 것, 건드리지 말 것**이 전부 들어 있다.

| 요청 방식 | 결과 |
|---|---|
| 전체를 부정 | 어디를 고쳐야 할지 모른다 |
| 차이를 구체적으로 | 그 부분만 바뀐다 |

**"틀렸다"보다 "무엇이 어떻게 달라야 하는지"** 를 말하는 게 핵심이었다. 이건 사람과 일할 때와도 같았다.

## 34. AI 결과를 실제로 확인해야 하는 이유

13번에서 "완료"라는 말을 그대로 믿으면 안 된다고 했다. 그럼 어떻게 확인할까?

**설명이 아니라 실제 결과를 본다.**

| 대상 | 무엇으로 확인하는가 |
|---|---|
| 코드 | 실제 파일을 열어본다 |
| Git | `git status`로 상태를 본다 |
| Frontend | 브라우저에서 실제로 눌러본다 |
| Backend | 요청과 응답을 확인한다 |
| Database | 실제로 데이터가 들어갔는지 본다 |
| Deployment | 배포된 URL에 들어가본다 |

공통점이 있다. **전부 AI의 설명이 아니라 시스템의 실제 상태를 보는 것**이다.

"파일을 생성했습니다"라는 말과 파일이 실제로 있는 것은 다르다. 대부분은 맞지만, **다를 수 있다는 걸 전제로 확인하는 습관**이 필요했다.

그리고 이 확인 방법은 결국 **다른 공부 글에서 정리했던 것들**이었다. Git status, Request/Response, DB 조회, 배포 URL. **AI와 일하려면 그 기초를 알고 있어야** 확인할 수 있었다.

## 35. AI가 빠를수록 사람이 더 알아야 하는 이유

이 글에서 가장 중요한 부분이다.

AI는 코드를 매우 빠르게 만든다. 그런데 **내 이해 속도는 같은 속도로 늘어나지 않는다.**

```text
생성 속도  >  이해 속도
```

이 상태가 계속되면 어떻게 될까? **프로젝트 안에 내가 모르는 코드가 쌓인다.**

평소에는 문제가 없다. 잘 돌아가니까. 문제는 **뭔가 잘못됐을 때** 생긴다. 어디부터 봐야 할지 모른다. 파일이 무슨 역할인지도 모르고, 데이터가 어디서 오는지도 모르고, 어느 단계에서 막혔는지도 모른다.

그래서 1번에서 말한 오해로 돌아간다.

```text
바이브 코딩
       (같지 않다)
코드를 이해하지 않아도 되는 개발
```

오히려 반대였다. **빨리 만들어지는 만큼, 만들어진 것을 따라갈 수 있어야** 했다. 따라가지 못하면 속도가 의미가 없어진다.

그래서 12번에서 "작게 나누는 것"이 중요했던 이유가 여기와 이어진다. **내가 이해할 수 있는 크기로 진행하는 것**이 결국 속도를 유지하는 방법이었다.

## 36. 코드를 전부 직접 작성하지 않아도 이해해야 하는 것

그럼 무엇을 이해해야 할까? **문법을 전부 외워야 한다는 뜻은 아니었다.**

최소한 이 정도는 알고 있어야 했다.

| 알아야 할 것 | 왜 |
|---|---|
| 이 파일은 무슨 역할인가 | 문제가 어디 있는지 좁힐 수 있다 |
| 데이터는 어디서 오는가 | Mock인지 실제인지 구분할 수 있다 |
| 요청은 어디로 가는가 | 어느 단계에서 막혔는지 알 수 있다 |
| 이 기능은 어떤 파일과 연결되는가 | 고쳤을 때 영향 범위를 안다 |
| Secret은 어디에 있는가 | 노출 위험을 판단할 수 있다 |
| 오류가 나면 어디부터 볼 것인가 | 막혔을 때 움직일 수 있다 |

전부 **"구조와 흐름"** 에 대한 것이다. 한 줄 한 줄의 문법이 아니다.

다른 공부 글에서 계속 "전체 흐름"을 정리했던 이유가 여기에 있었다. **흐름을 알면 어느 칸에서 막혔는지 말할 수 있고, 그러면 AI에게도 정확히 요청할 수 있다.**

## 37. AI가 만든 코드를 공부 자료로 사용하기

35~36번을 해결하는 방법이 하나 있었다. **AI가 만든 코드를 그대로 넘기지 않고 질문하는 것**이다.

| 던져볼 질문 |
|---|
| 이 함수는 왜 필요한가? |
| 입력과 출력은 무엇인가? |
| 이 파일이 없어지면 무엇이 깨지는가? |
| 이 데이터는 어디서 오는가? |
| 이 부분을 안 쓰면 어떻게 되는가? |

AI는 자기가 만든 코드를 설명하는 데는 강하다. **코드를 받는 것과 설명을 받는 것을 같이 하면** 이해 속도가 조금 따라잡혔다.

특히 **"이 파일이 없어지면 무엇이 깨지는가"** 라는 질문이 좋았다. 그 파일이 무슨 역할인지 가장 빨리 알 수 있었다.

이렇게 보니 AI 도구가 **코드 생성기이면서 동시에 코드 설명기**이기도 했다. 두 번째 쪽을 더 많이 쓰는 게 나한테는 도움이 됐다.

## 38. 작업 중 멈춰야 하는 상황

계속 진행하지 말고 **사람 판단을 받아야 하는 상황**들이 있다. 정리해두면 미리 요청에 넣을 수 있다.

| 상황 | 왜 멈춰야 하는가 |
|---|---|
| Conflict 발생 | 어느 쪽이 맞는지 판단이 필요하다 |
| 다른 사람 작업 발견 | 내가 건드릴 범위가 아닐 수 있다 |
| 요구사항 충돌 | 무엇이 맞는지 정해야 한다 |
| Source of Truth 불명확 | 기준이 없으면 추측하게 된다 |
| Secret 입력 필요 | 민감한 값은 사람이 직접 다뤄야 한다 |
| 외부 Console 설정 필요 | 저장소 바깥의 설정은 확인이 필요하다 |
| 데이터 삭제 가능성 | 되돌릴 수 없을 수 있다 |
| Git history 변경 가능성 | 팀 전체에 영향이 갈 수 있다 |

공통점은 **되돌리기 어렵거나, 판단에 프로젝트 맥락이 필요한 경우**다.

이런 상황에서 "멈추고 보고해달라"고 미리 적어두면, **진행되고 나서 발견하는 것보다 훨씬 나았다.**

## 39. "임의로 하지 마라"를 구체화하기

38번을 요청에 담을 때 처음에는 이렇게 적었다.

```text
"임의로 하지 마"
```

그런데 이건 **무엇이 임의인지 정하기 어렵다.** 도움이 될 거라고 판단한 행동은 임의가 아니라고 볼 수도 있다.

구체적으로 적으니 훨씬 효과적이었다.

| 추상적 | 구체적 |
|---|---|
| 임의로 하지 마 | 기능 추가 금지 |
| 알아서 하지 마 | Conflict 임의 해결 금지 |
| 조심해서 해 | Branch 삭제 금지 |
| 함부로 바꾸지 마 | reset 금지 |
| 다른 건 건드리지 마 | 다른 팀원 파일 수정 금지 |
| 설정은 두고 | 설정 파일 변경 금지 |

**하지 말아야 할 행동을 이름으로 적는 것**이 핵심이었다. 그러면 해석의 여지가 줄어든다.

이건 사람과 일할 때도 비슷했다. "알아서 잘해줘"보다 구체적인 범위가 서로 편했다.

## 40. AI와 협업할 때 좋은 기본 프롬프트 구조

9번의 항목들을 템플릿으로 정리하면 이렇다.

```text
[현재 상황]

[이번 목표]

[Source of Truth]

[수정 허용 범위]

[수정 금지 범위]

[작업 순서]

[검증 범위]

[완료 기준]

[최종 보고 형식]
```

각 항목이 하는 일이다.

| 항목 | 역할 |
|---|---|
| 현재 상황 | 추측하지 않게 상태를 알려준다 |
| 이번 목표 | 무엇을 하려는지 하나로 맞춘다 |
| Source of Truth | 무엇을 믿을지 정한다 |
| 수정 허용 범위 | 어디까지 손대도 되는지 정한다 |
| 수정 금지 범위 | 건드리면 안 되는 곳을 막는다 |
| 작업 순서 | 분석과 수정을 분리한다 |
| 검증 범위 | 확인을 어디까지 할지 정한다 |
| 완료 기준 | "완료"의 뜻을 맞춘다 |
| 최종 보고 형식 | 무엇을 확인하고 싶은지 정한다 |

**전부 넣어야 하는 건 아니다.** 작업에 따라 필요한 것만 쓰면 된다. 다음 항목이 그 이야기다.

## 41. 빠른 작업용 프롬프트와 중요한 작업용 프롬프트

모든 작업에 40번 전체를 쓰면 오히려 느려진다. **작업 무게에 맞춰 나눠 쓰는 게** 맞았다.

| 구분 | 빠른 초안 | 중요한 통합 작업 |
|---|---|---|
| 상태 확인 | 생략 가능 | 최신 상태 먼저 확인 |
| Source of Truth | 간단히 | 명확히 지정 |
| 영향 범위 | 파일 하나 | 어디까지 영향 가는지 확인 |
| 검증 | 저장 확인 | Build, 테스트, 실제 기능 |
| Git | 손대지 않음 | 상태 확인하고 단계별로 결정 |

```text
빠른 초안         파일 하나 작성 → 저장 확인 → 충돌만 확인

중요한 통합 작업   최신 상태 확인 → Source of Truth → 영향 범위
                 → Build/Test → 실제 기능 확인 → Git 상태 확인
```

**모든 작업에 최대 검증을 적용할 필요는 없다.** 16~17번에서 정리한 이야기가 프롬프트 수준에서도 똑같이 적용됐다.

## 42. AI 작업의 전체 흐름

지금까지 나온 것들을 하나로 이으면 이렇게 된다. **이 글의 핵심 그림이다.**

```text
문제 발생
↓
현재 상태 확인          추측하지 않고 실제 상태를 본다
↓
Source of Truth 확인    무엇을 기준으로 삼을지 정한다
↓
작업 범위 지정          허용과 금지를 명확히 한다
↓
AI 분석                 먼저 파악만 한다
↓
수정                    허락한 범위 안에서 고친다
↓
필요한 수준의 검증       이번 작업에 맞는 만큼 확인한다
↓
실제 결과 확인          설명이 아니라 시스템 상태를 본다
↓
Git 반영 여부 결정      commit과 push는 따로 판단한다
```

여기서 **사람의 자리가 어디인지** 보인다. 시작(상태 확인, 기준 정하기, 범위 지정)과 끝(결과 확인, Git 결정)이다. **가운데가 AI가 빠르게 움직이는 구간**이다.

이 구조가 잡히고 나서 작업이 훨씬 안정적이었다.

## 43. Claude Code 작업 흐름 예시

42번을 코드 작업에 적용하면 이렇게 된다.

```text
현재 Git 상태 확인      무엇이 수정되어 있고 어느 branch인지
↓
관련 파일 읽기          실제 코드가 어떻게 되어 있는지
↓
문제 분석               원인과 영향 범위를 파악
↓
수정 범위 확인          어디를 고칠지 내가 확인하고 결정
↓
파일 수정               정한 범위만
↓
필요한 검증             이번 작업에 맞는 수준으로
↓
git status              무엇이 바뀌었는지 확인
↓
보고                    결과와 남은 것을 정리
```

마지막 `git status`가 중요했다. **의도한 파일만 바뀌었는지 확인**하는 단계다. 여기서 예상 못 한 파일이 보이면 그때 멈추면 된다.

그리고 **Git 작업은 이 흐름에 들어 있지 않다.** commit이나 push는 보고를 받고 결과를 본 다음 **별도로 허용할 때만** 하는 구조로 두는 게 안전했다.

## 44. Claude Design 작업 흐름 예시

디자인 쪽은 이렇게 정리했다.

```text
기존 디자인             현재 상태에서 출발한다
↓
유지할 요소 지정         Keep
↓
변경할 요소 지정         Change
↓
변경 금지 요소 지정      Do Not Change
↓
시안 생성               정한 범위 안에서
↓
실제 화면 확인           설명이 아니라 결과를 본다
↓
작은 수정 반복           차이만 좁혀간다
```

29번의 Keep/Change/Do Not Change가 가운데에 들어간다.

마지막 **"작은 수정 반복"** 이 32번에서 정리한 방식이다. 전체를 다시 시키지 않고 **다른 부분만 짚어서 좁혀가는 것**이다.

코드와 디자인 둘 다 **범위를 먼저 정하고, 결과를 실제로 보고, 차이만 좁힌다**는 구조가 같았다.

## 45. 자주 헷갈리는 용어 정리

| AI Coding Tool | 코드 작성과 수정, 분석을 도와주는 AI 도구 |
| Vibe Coding | 자연어로 의도를 전달해 AI와 함께 개발하는 방식 |
| Context | AI가 현재 작업을 이해하기 위해 참고하는 정보 |
| Prompt | AI에게 전달하는 요청 내용 |
| Source of Truth | 이 작업에서 가장 신뢰할 기준으로 삼는 정보 |
| Scope | 이번 작업에서 손대도 되는 범위 |
| Analysis | 고치기 전에 문제와 영향 범위를 파악하는 단계 |
| Edit | 실제로 파일을 수정하는 단계 |
| Validation | 값이나 조건이 올바른지 확인하는 것 |
| Verification | 결과가 의도대로 됐는지 실제로 확인하는 것 |
| Completion Criteria | 어디까지 되면 완료로 볼지 미리 정한 기준 |
| Read | 상태와 내용을 확인하는 권한. 아무것도 바꾸지 않는다 |
| Write | 파일을 수정하는 권한 |
| Git Write | commit, push처럼 Git 상태를 바꾸는 권한 |
| Build | 코드를 실행 가능한 형태로 만드는 과정 |
| Runtime | 실제로 실행되는 단계 |
| Conflict | 두 변경이 충돌해 사람이 판단해야 하는 상황 |
| Claude Code | 프로젝트 안에서 파일과 명령을 다룰 수 있는 AI 개발 도구 |
| Claude Design | 시각적 디자인 작업을 도와주는 AI 도구 |
| Figma | 화면 구조와 정보 배치를 설계하는 디자인 도구 |
| Reference | 분위기나 색감의 참고 자료 |
| Agent | 여러 단계를 스스로 이어서 수행하는 AI 실행 단위 |
| Tool | AI가 사용할 수 있는 기능. 파일 읽기나 명령 실행 같은 것 |
| Permission | AI가 어떤 작업을 할 수 있는지 정해둔 권한 |

## 46. 자주 헷갈리는 차이 정리

| 구분 | 차이 |
|---|---|
| 분석 vs 수정 | 파악만 하는 것 / 실제로 고치는 것 |
| Context vs Source of Truth | 참고하는 정보 전체 / 그중 기준으로 삼을 것 |
| 코드 작성 완료 vs 기능 완료 | 코드가 생긴 것 / 실제로 동작하는 것 |
| Build 성공 vs 실제 기능 성공 | 결과물이 만들어진 것 / 써봤을 때 되는 것 |
| 파일 수정 vs Git Write | 내 파일 하나 / 기록과 원격에 반영되는 것 |
| Commit vs Push | 내 컴퓨터의 기록 / 팀에게 전달되는 것 |
| 빠른 검증 vs 통합 검증 | 저장 확인 수준 / 실제 환경까지 확인 |
| AI 제안 vs 실제 프로젝트 결정 | 하나의 후보 / 사람이 내리는 판단 |
| Claude Code vs Claude Design | 코드와 프로젝트 작업 / 시각 디자인 작업 |
| 많은 Context vs 필요한 Context | 줄 수 있는 전부 / 이 작업에 필요한 것 |

## 47. "AI 작업 완료"는 어디까지인가

다른 공부 글마다 나왔던 문제가 여기서도 그대로 나온다.

아래는 **전부 다른 상태**다.

| 단계 | 어디까지 된 것인가 |
|---|---|
| 1 | 문제 분석 — 원인을 파악했다 |
| 2 | 코드 초안 생성 — 만들 내용을 제안했다 |
| 3 | 파일 수정 — 실제로 고쳤다 |
| 4 | 저장 — 디스크에 쓰였다 |
| 5 | Build — 실행 가능한 형태가 됐다 |
| 6 | Local 기능 확인 — 내 컴퓨터에서 동작한다 |
| 7 | 실제 데이터 연결 — Mock이 아닌 진짜 데이터다 |
| 8 | 외부 API 확인 — 연결된 서비스도 동작한다 |
| 9 | 배포 환경 확인 — 배포된 곳에서도 된다 |
| 10 | Git 반영 — commit하고 push했다 |
| 11 | Review / Merge — 검토를 받고 합쳐졌다 |

**11개 중 어디까지인지 말하지 않으면 알 수 없다.**

```text
"AI가 완료했다고 했다"
       (같지 않다)
"프로젝트 기능이 완전히 끝났다"
```

그래서 14번에서 완료 기준을 미리 정하자고 한 것이다. **"이번 작업은 5번까지"** 라고 정해두면, 완료라는 말이 같은 뜻이 된다.

## 48. 이번에 이해한 핵심

이번에도 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### AI가 코드를 만들었다, 는 내가 기능을 이해했다와 다르다

코드가 생기는 속도와 내가 따라가는 속도는 다르다.

### 파일 수정 완료, 는 기능 정상과 다르다

고쳤다는 것과 의도대로 동작한다는 것은 별개다.

### Build 성공, 은 실제 기능 성공과 다르다

빌드는 결과물이 만들어지는지까지만 확인한다.

### 분석 요청, 은 수정 허용과 다르다

"확인해줘"와 "고쳐줘"는 다른 말이다.

### 파일 수정 허용, 은 Commit 허용과 다르다

파일은 되돌릴 수 있지만 기록은 남는다.

### Commit 허용, 은 Push 허용과 다르다

내 컴퓨터 안의 일과 팀에게 전달되는 일은 다르다.

### 문제 발견, 은 AI가 임의로 수정해도 됨과 다르다

발견한 것과 고쳐도 되는 것은 별개다.

### Context가 많다, 는 항상 더 정확하다와 다르다

관련 없는 정보는 오히려 방향을 흐린다.

### AI가 빠르다, 는 내 이해도 같이 빨라진다와 다르다

속도가 붙을수록 따라가는 게 중요해진다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> 바이브 코딩에서 가장 중요한 것은 AI에게 모든 판단을 맡기는 것이 아니라, 사람이 목표와 범위를 정하고 AI가 그 안에서 빠르게 작업하도록 만드는 것이었다.

처음에는 AI에게 얼마나 많이 맡길 수 있는지가 중요하다고 생각했다. 그런데 실제로 해보니, **얼마나 명확하게 맡기는지**가 결과를 갈랐다.

목표와 범위가 분명하면 AI는 그 안에서 굉장히 빠르다. 반대로 그게 없으면, 빠른 만큼 엉뚱한 방향으로도 빠르게 간다.

> AI는 코드를 대신 써줄 수 있지만, 무엇을 만들고 있는지 이해하고 어디까지 믿고 어디서 검증할지는 결국 내가 판단해야 한다.

지금까지 정리한 여섯 개의 공부 글이 여기서 의미가 생겼다. Database, Backend, Deployment, Git, Frontend, Terminal. **그 기초를 알아야 AI의 결과를 확인할 수 있었다.**

확인할 수 없으면 믿을 수밖에 없고, 믿을 수밖에 없으면 문제가 생겼을 때 할 수 있는 게 없었다. **AI를 잘 쓰기 위해서라도 기초가 필요했다는 것**이 이번에 가장 크게 남은 것이다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **Prompt Engineering** — 요청을 어떻게 구성하면 의도가 정확히 전달되는지
- **Agent** — 여러 단계를 스스로 이어서 수행하는 방식과 그 한계
- **Tool Calling** — AI가 외부 기능을 호출해서 실제 작업을 수행하는 구조
- **MCP** — AI 도구가 외부 시스템과 연결되는 방식
- **Context Window** — 한 번에 다룰 수 있는 정보량과 그 한계
- **RAG** — 필요한 정보를 찾아와서 참고하게 하는 방식
- **AI Code Review** — AI를 코드 리뷰에 활용할 때의 방법과 주의점
- **Test Automation** — AI가 만든 코드를 자동으로 검증하는 방법
- **CI/CD와 AI** — 자동화된 흐름 안에 AI를 넣을 때의 고려사항
- **AI Security** — 프롬프트를 통한 공격이나 정보 유출 위험
- **Secret 관리** — AI 도구에 민감한 값을 노출하지 않는 방법
- **AI Generated Code의 라이선스와 책임** — 생성된 코드를 쓸 때의 법적, 윤리적 고려
