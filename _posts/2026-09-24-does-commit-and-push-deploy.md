GitHub Pages로 블로그를 운영하면서 한동안 헷갈렸던 것이 있었다.

글을 수정한 뒤 `commit`하고 `push`까지 했는데, 그다음에는 별도로 배포 명령을 실행해야 하는 걸까?

한때는

```text
commit
→ push
→ deploy
```

처럼 세 단계가 각각 따로 동작하는 줄 알았다.

다른 프로젝트에서 Vercel 배포를 경험하기도 했고, `배포`라는 말을 들으면 서버에 무언가를 따로 올리는 과정이 있을 것처럼 느껴졌기 때문이다.

하지만 현재 내 블로그의 GitHub Pages 설정에서는 흐름이 조금 더 단순했다.

```text
로컬 수정
↓
commit
↓
push
↓
GitHub Pages 자동 빌드·배포
↓
공개 블로그 반영
```

즉 **내가 직접 하는 것은 변경사항을 GitHub에 push하는 것까지이고, 이후 배포는 GitHub Pages가 이어서 처리한다.**

다만 여기에는 한 가지 중요한 조건이 있었다.

`commit`과 `push`가 무엇을 하는지 구분해야 했고, `push 성공`과 `배포 성공`도 같은 의미는 아니었다.

---

## commit만 해서는 블로그가 바뀌지 않았다

먼저 `commit`부터 다시 정리할 필요가 있었다.

블로그 파일을 수정한 뒤 다음과 같이 작업할 수 있다.

```bash
git add .
git commit -m "docs: add new blog post"
```

이렇게 하면 변경사항이 Git 기록으로 남는다.

하지만 아직 내 컴퓨터 안의 로컬 저장소에 있는 상태다.

```text
파일 수정
↓
git add
↓
git commit
↓
로컬 Git에 변경 기록 생성
```

이 단계까지만 진행하고 실제 블로그를 확인해도 공개된 사이트는 바뀌지 않는다.

GitHub에는 아직 새로운 커밋이 전달되지 않았기 때문이다.

처음에는 `commit`이라는 단어 때문에 저장소 전체에 작업이 반영된 것처럼 느껴졌지만, **commit은 곧바로 인터넷에 올리는 작업이 아니었다.**

---

## GitHub로 보내는 작업이 push였다

로컬에 만든 커밋을 GitHub 저장소로 보내는 것이 `push`다.

```bash
git push
```

현재 브랜치와 원격 브랜치가 연결되어 있다면 평소에는 이 명령으로 GitHub에 변경사항을 전달할 수 있다.

그래서 두 작업을 구분하면 훨씬 이해하기 쉬웠다.

```text
commit
→ 내 컴퓨터에 변경사항 기록

push
→ 그 기록을 GitHub 원격 저장소로 전달
```

내 블로그에서는 이 `push`가 GitHub Pages 배포와 연결되어 있다.

GitHub에 새로운 변경사항이 들어오면 Pages가 그 내용을 바탕으로 사이트를 다시 빌드하고 공개한다.

---

## 그러면 deploy 명령은 따로 필요 없을까?

현재 내 블로그에서는 평소 수정할 때 별도의 `deploy` 명령을 실행하지 않는다.

기본 흐름은 이 정도다.

```bash
git add .
git commit -m "작업 내용"
git push
```

그다음 GitHub Pages가 자동으로 빌드와 배포를 진행한다.

따라서 매번

```bash
npm run deploy
```

같은 별도의 명령을 추가로 실행하거나 GitHub에서 수동으로 배포 버튼을 누르는 방식은 사용하지 않고 있다.

처음에 궁금했던

> commit과 push까지 하면 되는 건가?

에 대한 답은 현재 블로그 기준으로는 **그렇다.**

정확히 말하면

> **commit으로 변경사항을 기록하고 push로 GitHub에 올리면, 그 push를 기준으로 GitHub Pages가 자동 배포를 진행한다.**

는 의미다.

---

## 그렇다고 commit 자체가 배포를 실행하는 것은 아니다

처음에는 `commit + push`를 하나의 묶음처럼 사용하다 보니 둘 중 무엇이 배포와 연결되는지도 헷갈렸다.

현재 흐름에서는 실제 GitHub 쪽에 변경사항이 전달되는 시점이 중요하다.

```text
commit만 함
→ 로컬에만 있음
→ 공개 블로그 변화 없음

commit + push
→ GitHub에 변경사항 전달
→ Pages 빌드·배포 시작
```

그래서 commit을 여러 번 만들어두었다가 나중에 한 번에 push한다면 그 커밋들은 push되기 전까지 공개 블로그에는 반영되지 않는다.

---

## push가 성공했다고 바로 화면이 바뀌는 것은 아니었다

또 하나 헷갈렸던 부분은 시간 차이였다.

터미널에서 `git push`가 성공했다고 나오면 바로 블로그도 바뀌어 있을 것 같았다.

하지만 실제 흐름에는 Pages 빌드와 배포 과정이 하나 더 있다.

```text
git push 성공
↓
GitHub 저장소 업데이트
↓
GitHub Pages 빌드
↓
배포
↓
공개 사이트 변경
```

따라서 push 직후 블로그를 열었는데 이전 내용이 보여도 곧바로 실패했다고 판단할 필요는 없다.

GitHub Pages가 새로운 사이트를 만드는 데 약간의 시간이 필요할 수 있기 때문이다.

이 점을 모르고 있으면

> push가 안 됐나?

싶어서 다시 push하거나 불필요하게 코드를 수정할 수도 있다.

---

## push 성공과 배포 성공도 같은 것은 아니었다

자동 배포가 연결되어 있다고 해서 항상 성공하는 것은 아니다.

GitHub 저장소에는 새로운 커밋이 정상적으로 올라갔지만 Pages 빌드 과정에서 오류가 발생할 수도 있다.

그래서

```text
push 성공
=
배포 성공
```

은 아니다.

조금 더 정확하게는

```text
push 성공
→ GitHub가 변경사항을 받음

Pages 성공
→ 그 변경사항으로 사이트 생성 완료

실제 사이트 확인
→ 사용자에게 정상적으로 보임
```

으로 나눠볼 수 있었다.

덕분에 문제가 생겼을 때도 어디부터 확인해야 하는지가 조금 명확해졌다.

---

## 블로그가 안 바뀌면 무엇부터 확인할까

예전에는 공개 블로그를 계속 새로고침하면서

> 왜 안 바뀌지?

라고 생각하기 쉬웠다.

지금은 순서를 나눠서 확인하는 편이 더 낫다고 생각한다.

```text
1. commit은 했는가?

2. push는 성공했는가?

3. GitHub 저장소에 최신 커밋이 올라갔는가?

4. GitHub Pages 빌드는 성공했는가?

5. 실제 블로그에 반영됐는가?
```

예를 들어 GitHub에 최신 커밋 자체가 없다면 Pages 문제가 아니다.

아직 push가 제대로 되지 않은 것이다.

반대로 GitHub에는 최신 커밋이 있는데 Pages가 실패했다면 Git 명령을 다시 실행하는 것보다 배포 과정의 오류를 확인하는 편이 맞다.

---

## Pages가 성공해도 실제 블로그까지 확인한다

GitHub에서 배포 성공 표시가 나타났다고 해서 바로 작업을 끝내지는 않으려고 한다.

실제 공개된 블로그를 한 번 열어보는 편이 안전하다.

새 포스트를 올렸다면

* 포스트 목록에 보이는지
* 글이 정상적으로 열리는지
* 제목과 카테고리가 맞는지

확인할 수 있다.

링크나 이미지를 수정했다면 직접 눌러보거나 실제 이미지가 표시되는지도 확인한다.

특히 내 블로그는 GitHub Pages의 프로젝트 경로 아래에서 배포되고 있기 때문에 로컬에서는 괜찮았던 경로가 배포 후 다르게 동작하지 않는지도 확인할 필요가 있었다.

결국

**빌드가 성공했다는 것과 실제 페이지가 내가 원하는 모습이라는 것은 완전히 같은 의미가 아니었다.**

---

## 자동 배포라서 오히려 push 전에 확인이 중요했다

자동 배포는 확실히 편하다.

별도의 서버에 접속하거나 파일을 직접 옮길 필요가 없다.

GitHub에 변경사항을 올리면 나머지 과정이 이어진다.

하지만 그만큼 잘못된 변경사항 역시 push하면 공개될 수 있다.

그래서 오히려 push 전에 무엇을 올리는지 확인하는 습관이 중요했다.

나는 보통 이런 흐름으로 생각하고 있다.

```text
로컬에서 수정
↓
화면 확인
↓
git status로 변경 파일 확인
↓
commit
↓
push
↓
Pages 확인
↓
실제 블로그 확인
```

자동화가 확인 과정까지 대신해 주는 것은 아니었다.

---

## 평소에는 생각보다 단순했다

모든 과정을 설명하면 배포가 복잡해 보이지만 실제 반복 작업은 간단하다.

```bash
git status
git add .
git commit -m "작업 내용"
git push
```

그다음 Pages 배포 상태와 실제 블로그만 확인하면 된다.

물론 `git add .`을 사용할 때는 unrelated 파일까지 같이 들어가 있지 않은지 먼저 확인하는 편이 좋다.

결국 어려웠던 것은 명령어 자체보다 각각의 명령이 **어디까지 영향을 주는지** 이해하는 것이었다.

---

## commit, push, deploy를 구분하니 훨씬 단순해졌다

처음에는 세 단어가 모두 비슷하게 느껴졌다.

지금은 이렇게 구분하고 있다.

```text
commit
→ 변경사항을 Git 기록으로 남긴다.

push
→ 그 기록을 GitHub에 올린다.

deploy
→ GitHub Pages가 그 내용을 실제 공개 사이트로 만든다.
```

그리고 현재 내 블로그에서는 마지막 배포 단계가 자동으로 연결되어 있다.

그래서 직접 해야 하는 평소 작업은 사실상 **commit과 push까지**다.

그 이후에는 Pages가 처리한다.

다만 진짜 작업 완료는 `git push`라는 글자가 성공으로 끝난 순간이 아니었다.

GitHub Pages가 정상적으로 배포됐고, 실제 블로그에서도 내가 수정한 내용이 제대로 보이는 것까지 확인해야 했다.

결국 질문에 대한 답은 이렇게 정리할 수 있었다.

> **GitHub Pages 자동 배포가 이미 설정되어 있다면 commit 후 push하는 것만으로 배포 과정은 자동으로 시작된다. 하지만 push 성공과 배포 성공은 다르기 때문에 Pages 상태와 실제 사이트까지 확인하는 것이 좋다.**

한때는 배포를 위해 또 다른 명령이 필요할 것 같았지만, 실제로는 기존 Git 작업 흐름 안에 배포가 자연스럽게 연결되어 있었다.

덕분에 새 글을 작성하거나 작은 디자인을 수정할 때도 배포 자체를 크게 부담스럽게 생각하지 않게 됐다.
