처음 화면을 만들 때 가장 먼저 신경 쓴 것은

```text
예쁜가?
```

였다.

색상이 잘 어울리는지,

카드가 깔끔한지,

아이콘이 세련돼 보이는지,

전체적으로 완성도 있어 보이는지를 많이 봤다.

Figma나 AI 디자인 도구를 사용하면 이런 부분은 생각보다 빠르게 만들 수 있었다.

특히 AI에게

```text
깔끔한 모바일 UI로 만들어줘.
```

라고 요청하면 꽤 그럴듯한 화면이 나온다.

처음에는 이런 화면을 보면

```text
오, 잘 만들었다.
```

라고 생각했다.

그런데 실제로 눌러보고 사용해보면 다른 문제가 보이기 시작했다.

```text
어디를 눌러야 하지?

이 기능은 어디에 있지?

이 설명은 왜 이렇게 길지?

뒤로 가려면 어떻게 하지?

버튼이 너무 많아서 뭘 먼저 눌러야 할지 모르겠다.
```

화면은 예쁜데 사용하기는 불편한 것이다.

그때부터 디자인을 볼 때

```text
예쁜가?
```

보다

```text
사용자가 바로 이해할 수 있는가?
```

를 먼저 생각해야 한다는 것을 알게 됐다.

이번 글에서는 내가 화면을 만들면서 느낀

**예쁜 화면과 사용하기 쉬운 화면의 차이**

를 정리해보려고 한다.

---

## 예쁜 화면은 처음 보자마자 알 수 있다

예쁜 화면은 비교적 빠르게 판단할 수 있다.

```text
색상이 좋다.

폰트가 세련됐다.

카드 디자인이 깔끔하다.

아이콘 스타일이 통일되어 있다.

여백이 넓고 보기 좋다.
```

눈으로 몇 초만 봐도 어느 정도 느낌이 온다.

그래서 디자인을 만들 때도 자연스럽게 이런 부분부터 수정하게 된다.

```text
배경색 변경

Border Radius 조정

그림자 추가

아이콘 교체

폰트 굵기 변경
```

이런 수정은 결과도 바로 보이기 때문에 재미있다.

문제는 사용하기 쉬운지는 화면을 보기만 해서는 판단하기 어렵다는 것이다.

---

## 사용하기 쉬운 화면은 직접 써봐야 보였다

예를 들어 홈 화면이 정말 깔끔하게 만들어졌다고 해보자.

```text
서비스 이름

큰 이미지

짧은 설명

카드 몇 개

버튼
```

보기에는 좋다.

그런데 사용자가 실제로 들어오면 이런 질문을 할 수 있다.

```text
그래서 여기서 뭘 해야 하지?
```

화면에 정보는 있는데 다음 행동이 명확하지 않은 것이다.

반대로 디자인이 화려하지 않아도

```text
지금 어디에 있는지

무엇을 할 수 있는지

어디를 눌러야 하는지
```

가 바로 보인다면 사용하기는 훨씬 쉽다.

그래서

```text
예쁜 화면
=
보기 좋은 화면
```

이라면

```text
사용하기 쉬운 화면
=
다음 행동을 고민하지 않아도 되는 화면
```

에 더 가깝다고 느꼈다.

---

## 사용자는 화면을 감상하러 들어오는 것이 아니다

디자인을 만드는 사람은 화면을 오래 본다.

```text
색상

정렬

간격

아이콘

폰트
```

를 하나씩 살펴본다.

하지만 실제 사용자는 다르다.

대부분 어떤 목적이 있어서 들어온다.

예를 들어 러닝 앱이라면

```text
달리기를 시작하고 싶다.
```

카페 앱이라면

```text
주변 카페를 찾고 싶다.
```

설정 화면이라면

```text
설정을 바꾸고 싶다.
```

사용자는 디자인을 감상하는 것이 아니라

**자신이 하려던 일을 빨리 끝내려고 한다.**

그래서 화면이 아무리 예뻐도 사용자의 목적을 방해하면 좋은 UI라고 보기 어렵다.

---

## 화면을 만들기 전에 한 가지를 먼저 물어야 했다

```text
사용자는 이 화면에 왜 들어왔지?
```

이 질문이다.

예를 들어 검색 화면이라면

```text
찾고 싶은 것이 있어서
```

들어온다.

그렇다면 검색창이 잘 보여야 한다.

그런데 상단에

```text
큰 서비스 소개

이벤트 배너

추천 카드

카테고리 설명
```

이 먼저 나오고 검색창이 아래에 있다면

보기에 풍성할 수는 있지만 사용자는 불편할 수 있다.

그래서 디자인의 기준을

```text
무엇을 보여줄까?
```

보다

```text
사용자가 무엇을 하러 왔을까?
```

에서 시작하는 편이 좋았다.

---

## 기능이 많다고 좋은 화면은 아니었다

프로젝트를 만들다 보면 기능을 많이 보여주고 싶어진다.

```text
검색

추천

즐겨찾기

필터

정렬

알림

내 기록

최근 본 항목
```

모두 사용자에게 도움이 될 것처럼 보인다.

문제는 한 화면에 다 보여주기 시작할 때다.

```text
검색 버튼

필터 버튼

정렬 버튼

추천 버튼

즐겨찾기 버튼

알림 버튼
```

이 한꺼번에 보이면 오히려 사용자가 선택해야 할 것이 많아진다.

이때 생기는 문제가

```text
그래서 뭘 눌러야 하지?
```

다.

기능이 많을수록 좋은 것이 아니라

**지금 필요한 기능이 잘 보이는 것**

이 더 중요했다.

---

## 선택지가 많으면 친절한 것이 아니라 피곤할 수도 있다

처음에는 선택지를 많이 주는 것이 사용자에게 친절하다고 생각했다.

예를 들어 길찾기 기능이 있다면

```text
네이버 지도

카카오맵

Google Maps

주소 복사

전화하기
```

를 모두 보여주면 편할 것 같았다.

하지만 매번 이렇게 많은 선택지를 보여주면 사용자는 하나를 선택해야 한다.

```text
뭘 눌러야 하지?
```

라는 작은 판단이 계속 생긴다.

그래서 자주 사용하는 행동에는 기본값을 둘 수 있다.

```text
[길찾기]
```

를 누르면 기본 지도 앱으로 연결하고,

필요한 경우에만 다른 옵션을 보여주는 방식이다.

즉,

```text
선택지가 많다
=
자유롭다
```

가 항상

```text
사용하기 쉽다
```

는 아니었다.

---

## 설명이 많다고 친절한 것도 아니었다

내가 초반에 특히 많이 했던 실수다.

사용자가 헷갈릴까 봐 계속 설명을 추가한다.

```text
이 버튼을 누르면...

이 기능은...

이 정보는...

주의할 점은...
```

결과적으로 화면이 글로 가득 찬다.

나는 모든 규칙을 알고 있으니

```text
이 정도는 알려줘야 하지 않을까?
```

라고 생각한다.

하지만 사용자는 처음부터 모든 정책을 알고 싶어 하는 것이 아니다.

지금 필요한 것만 알고 싶을 가능성이 높다.

그래서

```text
모든 것을 미리 설명
```

하기보다

```text
필요한 순간에 필요한 만큼 설명
```

하는 것이 더 좋을 수 있다.

---

## 내부 규칙을 화면에 다 보여줄 필요는 없었다

예를 들어 어떤 혜택을 사용할 수 있는 조건이 복잡하다고 하자.

내부적으로는

```text
매장 적립 기록

쿠폰 유효기간

사용 가능 매장

브랜드별 조건
```

같은 규칙이 있을 수 있다.

처음에는 이걸 정확하게 설명하려고 화면에 다 넣고 싶어진다.

하지만 사용자가 지금 알고 싶은 것은

```text
이 쿠폰을 여기서 쓸 수 있는가?
```

일 수 있다.

그렇다면 화면에는

```text
사용 가능
```

또는

```text
이 매장에서는 사용할 수 없어요.
```

정도로 먼저 보여주고,

자세한 규칙은 필요할 때 펼쳐볼 수 있게 하는 편이 더 이해하기 쉽다.

즉,

```text
정확한 서비스
```

와

```text
모든 내부 규칙을 화면에 노출하는 서비스
```

는 같은 것이 아니었다.

---

## 사용자가 알아야 하는 것과 시스템이 알아야 하는 것을 구분한다

이 기준이 꽤 도움이 됐다.

시스템은 많은 정보를 알고 있어야 한다.

```text
사용자 ID

매장 ID

쿠폰 상태

정책 코드

유효기간 계산

위치 좌표
```

하지만 사용자는 이 모든 것을 볼 필요가 없다.

사용자에게는 결과가 더 중요할 수 있다.

```text
쿠폰 1개 사용 가능

3일 뒤 만료

이 매장에서 사용 가능
```

처럼 보여주는 것이다.

그래서 UI를 만들 때

```text
이 정보는 사용자가 알아야 하는가?

아니면 시스템 내부에서만 필요할까?
```

를 구분하려고 한다.

---

## 버튼 이름도 사용성을 좌우했다

예쁜 버튼을 만들어도 글자가 애매하면 사용하기 어렵다.

예를 들어 버튼이

```text
[확인]
```

이라고 되어 있다.

무엇을 확인하는지 상황을 읽어야 한다.

반대로

```text
[기록 저장]
```

이라고 하면 행동이 더 명확하다.

또

```text
[계속]
```

보다

```text
[결제 진행]
```

이 다음 행동을 더 잘 설명할 수 있다.

물론 모든 버튼을 길게 만들 필요는 없다.

중요한 것은

```text
버튼을 눌렀을 때 어떤 일이 일어나는지
예측할 수 있는가?
```

다.

---

## 아이콘만 있는 버튼도 조심해야 했다

디자인에서는 아이콘 버튼이 깔끔하다.

```text
♡
⚙
⋮
+
```

공간도 적게 차지한다.

하지만 사용자가 그 아이콘의 의미를 바로 이해한다는 보장은 없다.

개발하는 사람에게는 익숙한 아이콘도

처음 사용하는 사람에게는 의미가 애매할 수 있다.

특히 서비스 전용 기능이라면 더 그렇다.

그래서 중요한 행동이라면

```text
아이콘 + 텍스트
```

를 함께 사용하는 것이 더 명확할 수 있다.

예를 들어

```text
📍 길찾기
```

처럼 말이다.

---

## 익숙한 UI는 괜히 새롭게 만들지 않는 것이 좋았다

독특한 디자인을 만들고 싶으면 기존 패턴을 바꾸고 싶어진다.

예를 들어

```text
뒤로가기 버튼을 아래에 둔다.

검색 아이콘을 새로운 심볼로 바꾼다.

설정 버튼을 전혀 다른 위치에 둔다.
```

새롭게 보일 수 있다.

하지만 사용자는 기존 앱들을 사용하면서 이미 많은 패턴을 학습했다.

```text
왼쪽 위 화살표
→ 뒤로가기

돋보기
→ 검색

톱니바퀴
→ 설정
```

같은 것이다.

익숙한 기능을 굳이 낯설게 만들면 사용자는 다시 학습해야 한다.

그래서 개성을 넣는 것과

```text
기본 사용법까지 새롭게 만드는 것
```

은 구분할 필요가 있었다.

---

## 사용자는 설명서를 읽지 않는다

화면이 어렵게 만들어진 뒤

```text
안내 문구를 추가하면 되지.
```

라고 생각할 수 있다.

하지만 가장 좋은 것은 안내가 없어도 어느 정도 이해되는 것이다.

예를 들어

```text
현재 위치를 선택하려면
오른쪽 상단의 원형 버튼을 누르세요.
```

라는 설명이 계속 필요하다면

그 버튼 자체가 위치 기능이라는 것이 충분히 명확하지 않은 것일 수도 있다.

그래서 안내 문구를 추가하기 전에

```text
UI 자체를 더 이해하기 쉽게 만들 수 없을까?
```

를 먼저 생각해볼 필요가 있다.

---

## 물론 설명이 필요한 기능도 있다

모든 기능을 설명 없이 이해할 수 있게 만들 수는 없다.

특히 처음 보는 서비스나 복잡한 정책이라면 안내가 필요하다.

문제는 설명의 양이다.

예를 들어 처음 진입했을 때 화면 전체를 가리는

```text
1단계
2단계
3단계
4단계
5단계
```

튜토리얼을 무조건 보여주기보다,

처음 필요한 순간에

```text
여기에서 위치를 변경할 수 있어요.
```

정도의 짧은 도움을 줄 수도 있다.

이런 방식이 사용자 흐름을 덜 방해할 수 있다.

---

## 입력을 줄이는 것도 사용성이었다

디자인을 만들 때 입력창은 깔끔해 보인다.

```text
이름

주소

날짜

수량

메모
```

문제는 사용자가 직접 입력해야 한다는 것이다.

화면 하나에서 입력창이 많아질수록 사용자는 해야 할 일이 늘어난다.

그래서

```text
정말 직접 입력해야 하는가?
```

를 생각해야 했다.

예를 들어 현재 위치는 사용자가 주소를 매번 입력하는 대신

```text
GPS 사용
```

을 제공할 수 있다.

기존 값을 다시 확인하는 상황에서는 숫자를 다시 입력하게 하지 않고

```text
현재 값이 맞아요
```

같은 확인 방식도 생각할 수 있다.

사용성은 단순히 버튼 위치만이 아니라

**사용자가 해야 하는 작업의 양**

과도 관련되어 있었다.

---

## 클릭 수가 적다고 무조건 좋은 것도 아니었다

사용성을 이야기하면

```text
클릭 수를 줄여야 한다.
```

는 말을 자주 보게 된다.

물론 불필요한 단계를 줄이는 것은 좋다.

하지만 모든 것을 한 화면에 넣어 클릭을 줄이면 화면이 너무 복잡해질 수 있다.

예를 들어

```text
상세 정보

편집

삭제

공유

기록

설정
```

을 한 화면에 전부 펼쳐놓으면 한 번에 접근할 수 있다.

하지만 이해하기는 더 어려울 수 있다.

그래서 중요한 것은

```text
클릭 수 최소화
```

자체가 아니라

```text
불필요한 단계 최소화
```

라고 생각한다.

한 번 더 눌러도 구조가 훨씬 명확하다면 그 단계가 꼭 나쁜 것은 아니다.

---

## 자주 사용하는 기능은 가까이 둔다

사용 빈도도 화면 구성에 영향을 준다.

예를 들어 사용자가 매번 앱을 열어서 하는 행동이

```text
러닝 시작
```

이라면 이 기능은 찾기 쉬워야 한다.

반대로 거의 사용하지 않는

```text
회원 탈퇴
```

같은 기능이 홈 화면에 있을 필요는 없다.

그래서 기능을 배치할 때

```text
중요도

+

사용 빈도
```

를 같이 생각하면 도움이 됐다.

---

## 위험한 행동은 쉽게 누르면 안 됐다

사용하기 쉽다는 것이

```text
모든 버튼을 크게 만들고
바로 누를 수 있게 한다.
```

는 의미는 아니다.

예를 들어

```text
삭제

로그아웃

계정 탈퇴
```

같은 행동은 실수로 눌렀을 때 문제가 생길 수 있다.

이런 기능은 주요 행동과 다르게 표현할 수 있다.

또 정말 중요한 삭제라면

```text
정말 삭제하시겠어요?
```

같은 확인 단계가 필요할 수도 있다.

즉 좋은 사용성은

```text
빠르기
```

만이 아니라

```text
실수를 줄이는 것
```

도 포함한다.

---

## 사용자에게 기억하게 하지 않는 것이 좋았다

예를 들어 앱이 이렇게 안내한다고 해보자.

```text
쿠폰을 사용하려면
혜택 화면에서 매장명을 기억한 뒤
지도 화면에서 같은 매장을 찾아주세요.
```

사용자가 정보를 기억해서 다른 화면에서 다시 찾아야 한다.

불편하다.

대신 혜택 카드에서

```text
[사용 가능 매장 보기]
```

를 눌러 바로 이동하게 만들 수 있다.

사용자가

```text
기억

복사

비교

계산
```

해야 할 일이 적을수록 사용하기 쉬워진다.

---

## 상태를 보여주는 것도 중요했다

버튼을 눌렀는데 아무 반응이 없다.

사용자는 생각한다.

```text
눌린 건가?

안 된 건가?

한 번 더 눌러야 하나?
```

그래서 시스템 상태를 알려주는 것이 중요하다.

예를 들면

```text
저장 중...

저장 완료

로그인 중...

위치를 찾고 있어요.
```

같은 것이다.

아주 짧은 피드백만 있어도 사용자는 현재 상황을 이해할 수 있다.

---

## 로딩 화면도 사용성의 일부였다

데이터를 불러오는데 시간이 조금 걸릴 수 있다.

그런데 빈 화면만 보여주면

```text
고장 난 건가?
```

라고 느낄 수 있다.

그래서

```text
주변 카페를 찾고 있어요.
```

또는 Loading UI를 보여주면 현재 무슨 일이 일어나는지 알 수 있다.

사용성을 생각하면 정상 상태만 디자인해서는 부족했다.

```text
Loading

Error

Empty

Success
```

상태도 함께 봐야 한다.

Empty State는 뒤에서 따로 더 자세히 정리하려고 한다.

---

## 오류 메시지도 사용자 언어로 보여줘야 했다

개발할 때는 이런 오류를 볼 수 있다.

```text
400 Bad Request

Unauthorized

Validation failed
```

개발자에게는 의미가 있다.

하지만 사용자에게 그대로 보여주면 무엇을 해야 하는지 알기 어렵다.

예를 들어

```text
로그인이 만료되었습니다.
다시 로그인해주세요.
```

처럼 현재 문제와 다음 행동을 알려주는 것이 낫다.

즉 오류 메시지도

```text
무슨 일이 일어났는지

+

사용자는 무엇을 해야 하는지
```

를 알려줘야 한다.

---

## "안 되는 이유"보다 "다음에 뭘 하면 되는지"가 중요했다

예를 들어 버튼을 사용할 수 없는 상태라고 하자.

```text
사용할 수 없습니다.
```

만 보여주면 사용자는 이유를 모른다.

조금 더 구체적으로

```text
현재 위치 권한이 필요합니다.
```

라고 알려줄 수 있다.

더 나아가

```text
위치 권한을 허용하면
주변 매장을 확인할 수 있어요.

[권한 설정]
```

처럼 다음 행동까지 제공할 수 있다.

이런 작은 차이가 사용성을 크게 바꿀 수 있다.

---

## Disabled 버튼만 보여주는 것도 조심했다

입력 폼에서 값이 부족하면 버튼을 비활성화할 수 있다.

```text
[저장] ← 회색
```

문제는 왜 비활성화되었는지 알 수 없을 때다.

사용자는 여러 입력칸을 다시 확인해야 한다.

가능하다면

```text
닉네임을 입력해주세요.
```

처럼 원인을 가까운 위치에서 알려주는 편이 낫다.

버튼을 막는 것만으로 끝내지 않는 것이다.

---

## 사용자의 실수를 막는 것보다 쉽게 복구할 수 있게 만드는 것도 중요했다

모든 실수를 사전에 막으려고 하면 확인 창이 너무 많아질 수 있다.

```text
정말 이동하시겠습니까?

정말 수정하시겠습니까?

정말 저장하시겠습니까?
```

사용할 때마다 확인해야 한다.

오히려 피곤하다.

경우에 따라서는

```text
삭제
↓
삭제됨
↓
[실행 취소]
```

처럼 복구할 수 있게 하는 방식이 더 편할 수 있다.

즉,

```text
실수하지 못하게 만들기
```

와

```text
실수해도 쉽게 되돌리기
```

중 어떤 것이 적절한지 판단해야 한다.

---

## 실제 사용 환경을 생각해야 했다

디자인은 큰 모니터에서 만든다.

마우스로 정확하게 클릭한다.

하지만 사용자는 모바일에서 손가락으로 누른다.

버튼이 너무 작으면

```text
보이기는 예쁜데
누르기는 어려운
```

상태가 될 수 있다.

특히

```text
닫기

뒤로가기

작은 아이콘
```

같은 요소는 충분한 터치 영역이 필요하다.

화면에서 보이는 아이콘 크기와

실제로 눌릴 수 있는 영역은 다르게 만들 수도 있다.

---

## 버튼 사이 간격도 중요했다

예를 들어

```text
[저장][삭제]
```

가 너무 붙어 있다면 실수로 삭제를 누를 수 있다.

특히 모바일에서는 손가락으로 누르기 때문에 더 위험하다.

그래서 버튼을 배치할 때도

```text
보기 좋은 간격
```

뿐 아니라

```text
잘못 누르지 않을 간격
```

을 생각해야 했다.

---

## 색상만으로 상태를 전달하지 않는 것이 좋았다

예를 들어

```text
초록색
→ 사용 가능

빨간색
→ 사용 불가
```

만 사용한다고 해보자.

색상을 구분하기 어렵거나 화면 상황에 따라 의미를 이해하기 어려울 수 있다.

그래서

```text
사용 가능

사용 불가
```

텍스트나 아이콘을 함께 제공할 수 있다.

즉 중요한 정보는 한 가지 시각적 신호에만 의존하지 않는 것이 좋다.

---

## 사용자에게 중요한 것은 기능명이 아닐 수도 있다

개발자는 기능 이름으로 생각하기 쉽다.

```text
Preset

OAuth

Location Picker

Benefit CRUD
```

하지만 사용자는 이런 용어를 알고 싶어 하지 않는다.

사용자에게는

```text
자주 가는 장소

소셜 로그인

위치 변경

내 혜택 관리
```

가 더 자연스럽다.

UI 문구는 개발 구조를 보여주는 것이 아니라

**사용자가 이해하는 언어**

를 사용하는 것이 중요했다.

---

## 기술적으로 정확한 말보다 익숙한 말이 나을 때도 있었다

예를 들어

```text
Geolocation을 활성화해주세요.
```

보다

```text
현재 위치를 확인하려면
위치 권한이 필요해요.
```

가 더 이해하기 쉽다.

```text
Authentication Error
```

보다

```text
로그인에 실패했습니다.
다시 시도해주세요.
```

가 사용자에게 도움이 된다.

서비스 안에서는 개발 용어보다 사용자 언어를 선택한다.

---

## 예쁜 문구보다 명확한 문구가 먼저였다

마케팅 화면이라면 감성적인 문구가 도움이 될 수 있다.

하지만 기능 버튼이나 안내까지 전부 감성적으로 만들면 의미가 모호해질 수 있다.

예를 들어

```text
새로운 여정을 시작해보세요
```

가 실제로

```text
회원가입
```

버튼이라면 사용자가 바로 이해하지 못할 수도 있다.

그래서

```text
감성

vs

명확성
```

중 기능 UI에서는 명확성을 먼저 두는 편이 좋았다.

---

## 사용하기 쉬운 화면은 정보를 숨기는 화면이 아니다

여기서 조심할 부분도 있다.

```text
깔끔하게 만들어야 한다.
```

고 해서 정보를 무조건 없애면 안 된다.

사용자가 중요한 결정을 해야 하는데 정보가 부족할 수도 있다.

예를 들어 쿠폰 화면에서

```text
쿠폰 1개
```

만 보여주고

```text
유효기간
```

을 숨기면 디자인은 깔끔해질 수 있다.

하지만 사용자에게 중요한 정보가 사라진다.

그래서 목표는

```text
정보를 적게 보여주기
```

가 아니라

```text
지금 필요한 정보를 명확하게 보여주기
```

다.

---

## 숨길 정보와 보여줄 정보를 나누는 기준

나는 이런 질문이 도움이 된다고 생각한다.

```text
이 정보가 없으면
사용자가 잘못된 결정을 할 수 있는가?
```

그렇다면 중요한 정보일 가능성이 높다.

예를 들어

```text
쿠폰 유효기간

사용 가능 여부

결제 금액
```

같은 정보다.

반대로

```text
내부 처리 방식

정책 코드

DB 식별자
```

같은 정보는 화면에서 필요하지 않을 가능성이 높다.

---

## Progressive Disclosure라는 생각

모든 정보를 한 번에 보여주지 않고

필요할 때 조금씩 보여주는 방법이 있다.

예를 들어 카드에서는

```text
쿠폰 1개
3일 뒤 만료
```

만 보여준다.

사용자가 상세로 들어가면

```text
발급일

사용 조건

사용 가능 매장

주의사항
```

을 보여준다.

즉,

```text
목록
→ 핵심 정보

상세
→ 자세한 정보
```

로 나눈다.

이렇게 하면 목록은 단순하게 유지하면서도 필요한 정보를 없애지 않을 수 있다.

---

## 그래서 목록과 상세 화면의 역할이 달랐다

목록 화면에서 모든 것을 보여주려고 하면 카드가 계속 커진다.

```text
이름

주소

거리

혜택

유효기간

정책

메모

버튼
```

이 전부 들어간다.

그러면 목록을 빠르게 훑기 어렵다.

목록의 역할은 보통

```text
비교

탐색

선택
```

에 가깝다.

상세 화면의 역할은

```text
확인

이해

행동
```

에 더 가깝다.

이렇게 역할을 나누면 화면이 훨씬 단순해진다.

이 내용은 「[정보 구조와 페이지 구성]({{ site.baseurl }}{% post_url 2026-09-25-information-architecture-and-pages %})」에서도 다시 다뤘다.

---

## 실제 사용성을 확인하려면 설명 없이 눌러봐야 했다

내가 만든 화면은 내가 너무 잘 알고 있다.

어디에 뭐가 있는지,

버튼을 누르면 어디로 가는지,

무슨 기능인지 다 알고 있다.

그래서 사용하기 쉬워 보인다.

하지만 처음 보는 사람은 다르다.

그래서 가장 좋은 방법 중 하나는

```text
아무 설명 없이
한번 사용해보게 하는 것
```

이다.

그리고 관찰한다.

```text
어디서 멈추는가?

어떤 버튼을 잘못 누르는가?

무엇을 물어보는가?

어떤 기능을 못 찾는가?
```

이게 실제 UI 문제를 발견하는 데 매우 도움이 된다.

---

## "여기 누르면 돼"라고 말하고 싶다면 문제가 있을 수도 있다

누군가 테스트하는 모습을 보고 있으면 답답해질 수 있다.

```text
아니 거기 말고
여기 누르면 되는데...
```

라고 말하고 싶어진다.

그런데 바로 그 순간이 중요한 정보다.

내가 설명하지 않으면 사용자가 찾지 못한 것이다.

그렇다면

```text
사용자가 못 찾았다
```

를 문제로 봐야지

```text
사용자가 잘못했다
```

고 보면 안 된다.

---

## 사용자가 예상한 위치도 중요했다

예를 들어 사용자가 설정을 찾으려고 한다.

나는 설정을 프로필 안에 넣었다.

하지만 여러 사용자가 화면 오른쪽 위 톱니바퀴를 먼저 찾는다면

그것도 중요한 힌트다.

사용자는 기존 서비스 경험을 바탕으로

```text
여기쯤 있을 것이다.
```

라고 예상한다.

이 기대와 너무 다르면 학습 비용이 생긴다.

---

## 내가 사용성을 볼 때 확인하는 것

화면을 만든 뒤에는 이런 질문을 해보려고 한다.

```text
1. 이 화면의 목적은 한 문장으로 설명할 수 있는가?

2. 사용자가 가장 먼저 해야 할 행동이 보이는가?

3. 버튼 이름만 보고 결과를 예상할 수 있는가?

4. 중요한 기능을 찾기 위해 설명을 읽어야 하는가?

5. 선택지가 너무 많지 않은가?

6. 사용자가 직접 입력해야 하는 것이 너무 많지 않은가?

7. 중요한 정보가 숨겨져 있지는 않은가?

8. 필요 없는 내부 정보까지 보여주고 있지는 않은가?

9. 오류가 났을 때 다음 행동을 알 수 있는가?

10. 로딩 중인지 완료됐는지 상태가 보이는가?

11. 실수했을 때 복구할 수 있는가?

12. 모바일에서 버튼을 실제로 누르기 쉬운가?
```

---

## 예쁜 화면을 버리라는 의미는 아니다

여기까지 보면

```text
그러면 디자인은 안 예뻐도 된다는 건가?
```

싶을 수 있다.

그렇지는 않다.

보기 좋은 화면도 중요하다.

깔끔한 디자인은 서비스에 대한 신뢰감을 줄 수 있고,

사용하고 싶은 느낌을 만들 수 있고,

브랜드의 분위기를 전달할 수 있다.

문제는 순서다.

```text
예쁨
↓
사용성
```

이 아니라

```text
사용 가능
↓
이해 가능
↓
편리함
↓
그 위에 시각적 완성도
```

를 쌓는 편이 더 안정적이라고 생각한다.

---

## 사용하기 불편한 화면을 예쁘게 꾸며도 문제는 남는다

예를 들어

```text
버튼 위치를 찾기 어렵다.
```

라는 문제가 있다고 하자.

그 버튼에

```text
예쁜 색

멋진 그림자

깔끔한 아이콘
```

을 추가해도

위치 자체가 잘못되어 있으면 문제는 그대로다.

또 정보가 너무 많은 카드에

```text
더 좋은 폰트

더 예쁜 색상
```

을 적용해도 정보가 너무 많다는 문제는 남는다.

그래서 문제를 정확하게 구분해야 했다.

```text
시각적 문제인가?

구조 문제인가?

정보 문제인가?

사용 흐름 문제인가?
```

---

## AI 디자인에서도 사용성을 따로 검토해야 했다

Figma Make나 Claude Design으로 화면을 만들면

처음부터 상당히 완성도 있는 결과가 나올 수 있다.

그럴수록

```text
예쁘니까 됐다.
```

고 넘어가기 쉽다.

하지만 다시 확인해야 한다.

```text
사용자가 무엇을 해야 하는지 보이는가?

기능이 너무 많이 추가되지는 않았는가?

버튼의 의미가 명확한가?

정보가 너무 많지는 않은가?
```

AI는 일반적으로 그럴듯한 UI를 빠르게 만들 수 있지만

내 서비스의 실제 사용자가 편한지는 별도의 문제다.

---

## AI에게도 사용성 기준으로 수정 요청할 수 있다

예를 들어 AI가 만든 화면에 버튼이 네 개 있다고 하자.

```text
추천

검색

필터

시작
```

그런데 가장 중요한 행동은 시작이다.

그렇다면 이렇게 요청할 수 있다.

```text
현재 화면은 네 개 버튼의 강조 정도가 비슷하다.

사용자가 가장 먼저 해야 하는 행동은
'시작'이다.

시작 버튼만 Primary Action으로 강조하고,
나머지 세 기능은 보조 행동으로 낮춰줘.
```

단순히

```text
더 깔끔하게 해줘.
```

보다 문제 해결이 구체적이다.

---

## 실제 프로젝트에서 느낀 가장 큰 변화

처음에는 화면을 보고

```text
예쁜가?
```

부터 판단했다.

지금은 먼저

```text
사용자가 이걸 어떻게 쓸까?
```

를 생각하려고 한다.

그리고 그다음에

```text
이걸 더 보기 좋게 만들려면?
```

을 고민한다.

순서가 바뀐 것이다.

```text
예전

디자인
↓
기능 끼워 넣기
```

에서

```text
지금

사용자 행동
↓
정보 구조
↓
UI
↓
시각적 디자인
```

으로 조금씩 바뀌고 있다.

## 내가 화면을 만들 때 지키고 싶은 기준

지금까지 정리한 내용을 간단히 모으면 이렇다.

```text
1. 화면의 목적을 먼저 정한다.

2. 사용자가 이 화면에 들어온 이유를 생각한다.

3. 가장 중요한 행동을 하나 정한다.

4. 기능을 많이 보여주는 것을 목표로 하지 않는다.

5. 선택지를 필요 이상으로 늘리지 않는다.

6. 모든 정책을 한꺼번에 설명하지 않는다.

7. 필요한 순간에 필요한 정보를 보여준다.

8. 버튼 문구는 행동을 예상할 수 있게 만든다.

9. 익숙한 UI 패턴은 특별한 이유 없이 바꾸지 않는다.

10. 직접 입력해야 하는 항목을 줄일 수 있는지 확인한다.

11. 상태와 오류에 대한 피드백을 제공한다.

12. 사용자가 실수했을 때 복구할 수 있는지 생각한다.

13. 목록과 상세의 역할을 구분한다.

14. 예쁨보다 이해 가능성을 먼저 확인한다.

15. 실제 사용 테스트 후 다시 수정한다.
```

## 마무리

처음 디자인을 공부하면서는

```text
어떻게 하면 더 예쁘게 만들까?
```

가 가장 큰 질문이었다.

지금은 조금 다르게 생각한다.

```text
사용자는 이 화면을 보자마자
무엇을 해야 하는지 알 수 있을까?
```

가 먼저다.

예쁜 화면은 처음 봤을 때 좋은 인상을 줄 수 있다.

하지만 사용하기 어려우면 오래 사용할수록 불편함이 드러난다.

반대로 사용하기 쉬운 화면은

사용자가 화면을 오래 분석하지 않아도 된다.

```text
보고

↓

이해하고

↓

행동한다.
```

이 흐름이 자연스럽다.

결국 내가 만들고 싶은 것은

```text
예쁜 화면
```

하나가 아니라

```text
예쁘면서도
사용자가 고민하지 않아도 되는 화면
```

이다.

그리고 사용하기 쉬운 화면을 만들려면

다음으로 중요한 것이 있다.

화면 안에서

```text
어떤 정보가 가장 중요한지

어떤 버튼이 가장 중요한지

무엇을 강하게 보여주고
무엇을 약하게 보여줄지
```

를 결정해야 한다.
