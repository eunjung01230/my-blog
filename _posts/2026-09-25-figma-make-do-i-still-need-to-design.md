Figma의 기본 기능을 배우고 Education 인증까지 마치면서 다음으로 관심이 갔던 기능이 **Figma Make**였다.

이름만 처음 봤을 때는 정확히 무엇을 하는 기능인지 감이 잘 오지 않았다.

그런데 설명을 보면 상당히 강력해 보였다.

```text
프롬프트 입력
↓
AI가 화면 생성
↓
동작하는 프로토타입 확인
```

여기까지만 보면 이런 생각이 자연스럽게 든다.

```text
그러면 Frame이나 Auto Layout을
직접 공부할 필요가 없는 것 아닌가?
```

특히 AI를 이용해서 개발하는 것에 익숙하다면 더 그렇다.

원하는 화면을 글로 설명하면 AI가 만들어주는데 굳이 하나씩 직접 배치해야 하나 싶었다.

하지만 실제로 Figma Make가 어떤 도구인지 살펴보면서 생각이 조금 달라졌다.

Figma Make는 Figma를 대신하는 기능이라기보다 **아이디어를 아주 빠르게 화면과 동작으로 확인하기 위한 또 하나의 방법**에 가까웠다.

---

## Figma Make란?

Figma Make는 자연어 프롬프트를 이용해서 아이디어나 기존 디자인을 **동작하는 앱 또는 프로토타입 형태로 만들어볼 수 있는 AI 기반 prompt-to-app 도구**다.

단순히 화면 이미지를 한 장 생성하는 것이 아니라 인터랙션이 포함된 결과물을 만들고, 다시 대화하면서 수정할 수 있다. 기존 Figma 디자인이나 컴포넌트 같은 자료도 컨텍스트로 활용할 수 있다.

예를 들어

```text
카페 혜택을 관리하는 모바일 앱 홈 화면을 만들어줘.

상단에는 현재 위치,
중앙에는 주변 카페 목록,
각 카드에는 브랜드와 거리,
보유 혜택을 보여줘.
```

처럼 입력하면 단순 설명에서 시작해서 화면을 빠르게 만들어볼 수 있다.

그리고 여기서 끝나는 것이 아니라

```text
카드를 누르면 상세 화면으로 이동하게 해줘.
```

```text
혜택이 없을 때 Empty State를 추가해줘.
```

처럼 계속 대화하면서 수정할 수도 있다.

그래서 내가 이해한 Figma Make는

```text
AI 이미지 생성
```

보다는

```text
AI와 대화하면서 만드는
빠른 프로토타입 제작 도구
```

에 더 가까웠다.

---

## 일반 Figma와 무엇이 다를까?

기존 Figma Design에서는 내가 직접 화면을 만든다.

예를 들어 버튼 하나를 만들려면

```text
Frame 생성
↓
Text 추가
↓
Auto Layout
↓
Padding 설정
↓
색상 설정
↓
Component 생성
```

같은 과정을 거친다.

반면 Figma Make에서는 먼저 결과를 설명한다.

```text
로그인 화면을 만들어줘.

Google / Kakao / Naver 로그인 버튼이 있고
전체적으로 밝고 단순한 모바일 UI로 만들어줘.
```

그러면 AI가 먼저 결과를 만든다.

즉 시작 방향이 다르다.

```text
Figma Design

구조를 직접 만든다
↓
결과물
```

```text
Figma Make

원하는 결과를 설명한다
↓
AI가 초안을 만든다
↓
수정한다
```

처음에는 Make 쪽이 훨씬 쉬워 보인다.

실제로 아이디어를 빠르게 확인하는 데는 확실히 편하다.

하지만 이것 때문에 일반 Figma가 필요 없어지는 것은 아니었다.

---

## 처음 생성된 화면은 빠르지만 내 디자인은 아닐 수 있다

AI에게 화면을 만들어달라고 하면 꽤 그럴듯한 결과가 나온다.

이게 Figma Make를 처음 사용할 때 가장 재미있는 부분이었다.

빈 화면에서 시작했다면 꽤 많은 시간이 필요했을 UI가 금방 만들어진다.

하지만 자세히 보면 문제가 생긴다.

```text
내가 원하는 버튼 위치가 아니다.

색상이 서비스와 맞지 않는다.

필요 없는 설명이 추가됐다.

카드 구조가 원래 기획과 다르다.

내가 요청하지 않은 기능이 생겼다.
```

화면 자체는 예뻐 보이는데 **내가 만들려고 했던 서비스와는 조금씩 다른 경우**가 생길 수 있다.

[Figma](https://www.figma.com/blog/introducing-make-kits-and-make-attachments/) 역시 Make에 실제 디자인 시스템, 컴포넌트, 데이터와 제약을 더 많이 전달할수록 결과가 프로젝트의 맥락에 가까워진다는 방향으로 기능을 확장하고 있다. 2026년에는 Make kits와 첨부 기능을 통해 이런 컨텍스트를 제공하는 기능도 강화됐다.

결국

```text
AI가 알아서 좋은 디자인을 만들어준다.
```

보다는

```text
AI가 빠르게 첫 번째 안을 만들어주고
내가 기준에 맞게 수정한다.
```

라고 생각하는 편이 더 맞았다.

---

## 프롬프트가 너무 짧으면 AI가 대신 결정한다

예를 들어 이렇게 요청한다고 해보자.

```text
예쁜 카페 앱 만들어줘.
```

AI 입장에서는 결정해야 할 것이 너무 많다.

```text
어떤 카페 앱인지?

사용자는 누구인지?

홈에서 무엇을 보여줘야 하는지?

주요 기능은 무엇인지?

어떤 디자인 분위기인지?

모바일인지 웹인지?
```

결국 이런 부분을 AI가 임의로 결정하게 된다.

그러면 결과는 꽤 그럴듯해도 내가 생각했던 것과 달라질 가능성이 높다.

그래서 조금 더 구체적으로 설명하는 것이 좋았다.

예를 들면

```text
모바일 카페 혜택 관리 서비스의 홈 화면을 만들어줘.

사용자는 여러 저가 커피 프랜차이즈를 이용한다.

상단에는 현재 위치를 표시하고,
그 아래에는 주변 카페를 카드 목록으로 보여줘.

카드에는
- 브랜드
- 매장명
- 예상 도보 시간
- 사용자가 보유한 혜택

을 표시해줘.

가장 중요한 행동은
주변 카페를 확인하는 것이다.

전체 화면은 정보를 너무 많이 보여주지 않고
단순하게 구성해줘.
```

처럼 작성할 수 있다.

같은

```text
카페 앱
```

이라도 결과의 방향이 훨씬 명확해진다.

---

## 내가 프롬프트를 작성한다면

Figma Make에서는 처음부터 아주 긴 프롬프트 하나에 모든 것을 넣는 방법보다 **큰 구조를 먼저 만들고 하나씩 수정하는 방식**이 편했다.

예를 들면 첫 번째 요청에서는

```text
무엇을 만드는지
```

를 알려준다.

```text
러닝 기록을 보여주는 모바일 앱의
홈 화면과 러닝 진행 화면을 만들어줘.
```

그다음 구조를 추가한다.

```text
홈에서는 지도를 가장 크게 보여주고
화면 아래쪽에 러닝 시작 버튼을 배치해줘.
```

그다음 우선순위를 수정한다.

```text
러닝 시작 버튼이 현재보다 더 눈에 띄게 해줘.
다른 버튼은 강조하지 마.
```

마지막으로 세부 디자인을 조정한다.

```text
전체적으로 어두운 배경을 사용하고
중요한 러닝 정보만 강하게 보이게 해줘.
```

이렇게 하면

```text
생성
↓
확인
↓
수정
↓
다시 확인
```

의 흐름으로 작업할 수 있다.

Claude 같은 AI와 대화하면서 코드를 수정하는 것과 꽤 비슷한 느낌이었다.

## 한 번에 완벽하게 만들려고 하지 않는 것이 좋았다

AI 도구를 사용하다 보면 자꾸 이런 프롬프트를 만들고 싶어진다.

```text
완성도 높은 앱 전체를 만들어줘.

로그인,
홈,
검색,
상세,
설정,
마이페이지,
반응형,
애니메이션까지 전부 구현해줘.
```

물론 요청 자체는 할 수 있다.

하지만 생성되는 범위가 커질수록 내가 확인해야 하는 것도 많아진다.

화면이 10개 만들어졌는데

```text
1번 화면의 버튼 위치가 잘못됨

3번 화면의 정보 구조가 다름

6번 화면에는 필요 없는 기능이 있음

8번 화면에서는 이동할 곳이 없음
```

같은 문제가 한꺼번에 생기면 오히려 수정하기 어렵다.

그래서 나는 AI를 사용할수록

```text
작게 만든다.
↓
확인한다.
↓
확정한다.
↓
다음으로 간다.
```

는 방식이 중요하다고 느꼈다.

## 디자인을 먼저 주고 시작할 수도 있다

Figma Make의 장점 중 하나는 텍스트 프롬프트만 사용할 필요가 없다는 것이다.

기존 Figma 디자인이나 컴포넌트, 파일 등을 컨텍스트로 첨부해서 시작할 수 있다. 현재 Figma Make는 Figma 디자인뿐 아니라 여러 자료를 프롬프트에 첨부해 결과 생성에 활용할 수 있도록 지원한다.

이 방식이 중요한 이유는

```text
AI에게 처음부터 디자인을 결정하게 하기
```

와

```text
내 디자인을 기준으로
AI에게 동작을 만들어달라고 하기
```

가 완전히 다르기 때문이다.

예를 들어 이미 Home 화면을 만들었다면

```text
이 Home 디자인을 기준으로
카드를 클릭했을 때 이동할
상세 화면을 만들어줘.
```

처럼 요청할 수 있다.

그러면 AI가 아무 디자인이나 새로 만드는 것보다 기존 프로젝트의 방향을 유지하기 쉬워진다.

---

## 결국 디자인 기준이 있어야 했다

여기서 첫 글인 [개발자가 Figma를 배우는 이유]({{ site.baseurl }}{% post_url 2026-09-25-why-developers-learn-figma %})에서 했던 이야기가 다시 연결된다.

AI를 사용할수록 오히려

```text
내가 원하는 것이 무엇인지
```

가 중요해진다.

기준이 없다면 Figma Make가 무언가를 만들 때마다 이런 고민을 하게 된다.

```text
이게 좋은 디자인인가?

그냥 AI가 이렇게 만들었으니까 쓰면 되나?

버튼은 원래 여기 있는 게 맞나?
```

반대로 이미

```text
주요 사용자

핵심 기능

화면 구조

정보 우선순위

디자인 방향
```

이 정해져 있다면 결과를 판단할 수 있다.

```text
이 화면에는 이 기능이 필요 없다.

이 정보가 더 먼저 보여야 한다.

이 버튼은 주 행동이 아니므로 강조하면 안 된다.
```

라고 말할 수 있다.

결국 AI가 강해질수록 사람이 할 일이 없어지는 것보다

**사람이 무엇을 판단해야 하는지가 더 분명해지는 느낌**이었다.

## Point and Edit으로 부분 수정하기

Figma Make에서 마음에 들지 않는 부분이 있다고 해서 항상 전체 화면을 다시 만들어달라고 할 필요는 없다.

현재 Figma Make에는 결과물의 특정 요소를 선택해서 직접 수정하거나, 해당 요소를 대상으로 AI에게 변경을 요청할 수 있는 **Point and Edit** 방식이 제공된다.

예를 들어 버튼을 선택한 뒤

```text
이 버튼의 강조를 줄여줘.
```

처럼 요청할 수 있다.

이 방식은 꽤 중요하다.

AI에게 그냥

```text
화면 좀 더 깔끔하게 만들어줘.
```

라고 하면 화면 전체가 바뀔 수도 있다.

반대로 수정할 대상을 정확하게 선택하면

```text
이 버튼

이 카드

이 영역
```

처럼 범위를 좁힐 수 있다.

Claude에게 코드를 수정시킬 때도

```text
다른 부분은 건드리지 말고
이 부분만 수정해줘.
```

라고 요청하는 것과 비슷했다.

## 디자인과 코드를 같이 볼 수 있다는 점

Figma Make의 결과물은 단순한 이미지가 아니라 **코드 기반 결과물**이다.

[Figma](https://www.figma.com/make/)는 Make에서 생성한 결과를 시각적으로 편집하면서 코드와 캔버스를 오갈 수 있는 구조를 제공하고 있다.

이 부분은 개발자 입장에서 꽤 흥미로웠다.

기존 Figma에서

```text
디자인
```

을 만들었다면,

Figma Make에서는

```text
디자인

+

동작

+

코드
```

까지 조금 더 가까워진다.

그래서 단순히

```text
예쁜 화면을 하나 만들어보는 것
```

보다

```text
실제로 눌렀을 때 어떻게 움직이는가?
```

를 확인하는 데 더 의미가 있었다.

## Prototype을 빠르게 만들 때 특히 유용하다

프로젝트를 기획할 때 화면을 만드는 이유 중 하나는

```text
실제로 사용하면 어떤 느낌일까?
```

를 확인하기 위해서다.

정적인 화면만 보면 괜찮아 보일 수 있다.

하지만 직접 사용해보면 다르다.

```text
버튼을 눌렀는데 다음 행동이 애매하다.

한 기능을 사용하기 위해 화면을 너무 많이 거친다.

상세 화면에서 다시 돌아갈 방법이 불편하다.

정보 입력 과정이 너무 길다.
```

이런 문제는 직접 눌러볼 때 더 쉽게 보인다.

Figma Make는 자연어로 화면과 인터랙션을 빠르게 생성할 수 있기 때문에 이런 **아이디어 검증용 프로토타입**을 만드는 데 특히 잘 맞는다. [Figma](https://help.figma.com/hc/en-us/articles/31304412302231-Explore-Figma-Make) 역시 Make의 주요 용도로 기능적인 형태에서 디자인을 미리 경험하고, 아이디어와 제품 방향을 검토하며 여러 해결책을 탐색하는 것을 제시하고 있다.

## 여러 디자인 방향을 비교할 때도 사용할 수 있다

화면 하나를 만들더라도 정답이 하나인 것은 아니다.

예를 들어 홈 화면을

```text
지도 중심
```

으로 만들 수도 있고,

```text
카드 목록 중심
```

으로 만들 수도 있다.

직접 두 디자인을 처음부터 모두 만든다면 시간이 오래 걸린다.

Figma Make를 이용하면 빠르게 여러 안을 확인해볼 수 있다.

```text
A안
지도를 중심으로 구성

B안
카페 카드 목록 중심

C안
사용자의 보유 혜택 중심
```

이렇게 만든 다음

```text
어느 구조가
이 서비스의 핵심 목적과 가장 맞는가?
```

를 비교하는 것이다.

여기서 중요한 것은 AI에게

```text
제일 좋은 걸 골라줘.
```

라고 맡기는 것이 아니라

AI를 이용해 **비교할 선택지를 빠르게 만드는 것**이라고 생각한다.

---

## 실제 데이터와 비슷한 상황을 만들어볼 수도 있다

UI를 만들 때 흔히 사용하는 것이 이런 데이터다.

```text
카페 이름

Lorem ipsum

사용자 이름

Sample data
```

처음 디자인할 때는 괜찮다.

하지만 실제 데이터는 항상 그렇게 예쁘게 들어오지 않는다.

```text
매장 이름이 매우 길다.

혜택이 하나도 없다.

쿠폰이 여러 개 있다.

주소가 두 줄을 넘어간다.
```

같은 상황이 발생한다.

현재 Figma Make는 웹의 최신 정보를 검색하거나 특정 URL의 내용을 가져오는 기능도 제공하고 있고, 실제 데이터와 연결된 동작을 실험하는 방향으로 사용할 수 있다.

이런 기능을 이용하면 단순히 보기 좋은 샘플 화면을 만드는 것을 넘어 조금 더 현실적인 상황도 시험해볼 수 있다.

---

## 그렇다고 생성된 결과를 바로 서비스에 쓰는 것은 조심해야 한다

Figma Make가 코드를 만들고 인터랙션까지 생성한다고 하면 이런 생각이 들 수 있다.

```text
그럼 여기서 만든 것을
바로 서비스로 배포하면 되는 것 아닌가?
```

현재 Figma Make는 단순 디자인 도구를 넘어 코드 기반 프로토타입과 앱 제작 영역까지 계속 확장되고 있다. 2026년 현재 Figma도 디자인에서 코드, 그리고 실제 제품 제작으로 이어지는 흐름을 강조하고 있다.

하지만 내 프로젝트에서는 Make 결과를 바로 최종 코드라고 생각하기보다

```text
아이디어

↓

빠른 프로토타입

↓

검증

↓

디자인 확정

↓

실제 구현
```

단계의 일부로 보는 것이 더 맞다고 생각한다.

AI가 코드를 만들었다고 해서

```text
데이터 구조

인증

권한

보안

예외 처리

유지보수

프로젝트 구조
```

까지 내가 원하는 방식으로 설계됐다는 뜻은 아니기 때문이다.

화면이 잘 움직이는 것과 서비스가 제대로 구현된 것은 다른 문제다.

## Figma Make를 사용해도 Figma 기초가 필요한 이유

처음 가졌던 질문으로 다시 돌아가보자.

```text
Figma Make가 있는데
굳이 Figma 기초를 배워야 할까?
```

나는 **그래도 기본은 알아야 한다**고 생각하게 됐다.

AI가 화면을 만들었는데 간격이 이상하다면

```text
간격이 좀 이상해.
```

라고만 말하는 것보다

```text
카드 내부 Padding은 유지하고
카드 사이 Gap만 줄여줘.
```

라고 말하는 것이 더 정확하다.

버튼 크기가 이상하다면

```text
버튼 크기 수정해줘.
```

보다

```text
버튼 높이는 고정하고
가로는 부모 Frame을 채우게 해줘.
```

라고 설명할 수 있다.

즉,

```text
Frame

Auto Layout

Padding

Gap

Component

Hierarchy
```

같은 기본 개념을 알고 있으면 AI에게도 더 정확하게 지시할 수 있다.

---

## AI를 사용하면서 오히려 기본 공부가 필요했다

이건 개발에서도 비슷했다.

AI에게

```text
React로 만들어줘.
```

라고 요청하는 것은 쉽다.

하지만 결과를 보고

```text
이 상태 관리 방식이 맞는가?

Component 분리가 적절한가?

왜 여기서 오류가 나는가?
```

를 판단하려면 결국 React를 알아야 한다.

디자인도 비슷했다.

```text
AI에게 UI 생성 요청
```

은 누구나 할 수 있다.

하지만

```text
왜 이 화면이 불편한가?

어떤 정보를 위로 올려야 하는가?

버튼이 왜 너무 많아 보이는가?

왜 정렬이 어색한가?
```

를 판단하려면 UI/UX와 디자인의 기본을 알아야 한다.

그래서 AI가 생겼기 때문에 공부할 필요가 없어졌다기보다

**공부한 내용을 사용하는 방법이 달라졌다고 보는 편이 더 맞았다.**

## 내가 생각하는 Figma와 Figma Make의 역할

둘을 비교하면 이렇게 정리할 수 있을 것 같다.

| Figma Design   | Figma Make      |
| -------------- | --------------- |
| 직접 화면 구조를 설계   | 프롬프트로 빠르게 초안 생성 |
| 세밀한 디자인 조절     | 빠른 아이디어 탐색      |
| Auto Layout 구성 | 인터랙션 빠르게 생성     |
| Component 관리   | 동작하는 프로토타입 제작   |
| 디자인 시스템 관리     | 여러 방향 빠르게 시험    |
| 최종 디자인을 다듬기 좋음 | 초기 검증에 특히 유용    |

둘 중 하나만 선택해야 하는 관계라고 생각하지 않는다.

오히려 이런 식으로 연결할 수 있다.

```text
아이디어
↓
Figma Make로 빠르게 확인
↓
필요한 구조 선택
↓
Figma에서 디자인 정리
↓
Prototype 확인
↓
개발
```

반대로 이미 디자인이 있다면

```text
Figma Design
↓
Make에 디자인 전달
↓
동작 추가
↓
실제 사용 흐름 확인
↓
다시 디자인 수정
```

처럼 사용할 수도 있다.

---

## AI에게 디자인 전체를 맡기지 않는 이유

Figma Make를 사용하면 화면이 너무 빨리 만들어지기 때문에 한 가지 함정이 생긴다.

```text
화면이 만들어졌으니까
기획이 끝났다.
```

고 생각하기 쉬워진다.

하지만 화면이 있다는 것과 서비스 구조가 제대로 결정됐다는 것은 다르다.

AI가 만들어준 화면에는 내가 생각하지 않았던 기능이 자연스럽게 들어갈 수도 있다.

예를 들어

```text
즐겨찾기

평점

알림

검색 필터

추천
```

같은 기능이다.

보기에 자연스럽다는 이유만으로 하나씩 받아들이기 시작하면 원래 만들려고 했던 MVP가 계속 커질 수 있다.

그래서 Make 결과물을 볼 때도 계속 확인할 필요가 있다.

```text
이 기능이 정말 필요한가?

원래 기획에 있었는가?

사용자가 이 화면에서 해야 할 행동은 무엇인가?

이 정보가 지금 필요한가?
```

AI는 화면을 빠르게 만드는 도구지만,

**서비스의 범위를 결정하는 역할까지 넘길 필요는 없다.**

---

## 내가 Figma Make를 사용할 때 지키고 싶은 기준

정리하면서 내가 사용할 기준도 만들었다.

```text
1. 처음부터 전체 서비스를 만들게 하지 않는다.

2. 한 화면 또는 한 흐름부터 시작한다.

3. 핵심 기능과 사용자 행동을 먼저 설명한다.

4. 디자인 스타일보다 정보 구조를 먼저 정한다.

5. 이미 디자인이 있으면 그것을 기준으로 제공한다.

6. 마음에 들지 않는 부분은
   전체를 다시 만들기보다 범위를 좁혀 수정한다.

7. AI가 추가한 기능을 그대로 받아들이지 않는다.

8. 실제로 눌러보면서 사용자 흐름을 확인한다.

9. 결과를 최종 구현이라고 생각하지 않는다.

10. 마지막 판단은 내가 정한 기획과 디자인 기준으로 한다.
```

이 정도만 지켜도

```text
AI가 만든 화면에 끌려가는 방식
```

보다

```text
내가 AI를 이용해서
화면을 빠르게 검증하는 방식
```

에 가까워질 것 같다.

---

## Figma Make가 가장 유용한 순간

내 기준에서는 Figma Make가 특히 이런 상황에서 유용해 보였다.

### 아이디어가 아직 머릿속에만 있을 때

```text
이걸 화면으로 만들면
어떤 모습일까?
```

를 빠르게 확인할 수 있다.

### 두 가지 구조 중 고민될 때

```text
A안

B안
```

을 빠르게 만들어 비교할 수 있다.

### 정적인 디자인의 동작을 확인하고 싶을 때

```text
버튼 클릭

페이지 전환

입력

상태 변화
```

등을 실제로 눌러볼 수 있다.

### 개발하기 전에 사용자 흐름을 확인할 때

코드를 작성하기 전에 불편한 흐름을 발견하면 수정 비용을 줄일 수 있다.

### AI에게 구현을 맡기기 전에 기준을 만들 때

먼저 화면과 동작을 확인한 다음 개발 AI에게 전달할 기준으로 활용할 수 있다.

## 결국 Make도 도구였다

AI 도구를 처음 접하면 항상 비슷한 기대를 하게 되는 것 같다.

```text
이제 이걸 직접 안 해도 되는 건가?
```

Figma Make를 봤을 때도 그랬다.

하지만 조금씩 사용하고 구조를 알아보니

```text
Figma를 배우지 않아도 되는 도구
```

라기보다

```text
Figma와 디자인을 알고 있을수록
더 잘 사용할 수 있는 도구
```

에 가까웠다.

AI가 첫 번째 결과를 만드는 속도는 매우 빠르다.

그다음부터는 결국 사람이 결정해야 한다.

```text
무엇을 남길지

무엇을 없앨지

무엇을 강조할지

사용자가 무엇을 먼저 해야 하는지

이 화면이 서비스의 목적과 맞는지
```

를 판단해야 한다.

## 마무리

Figma Make를 정리하면서 가장 크게 바뀐 생각은 이것이다.

처음에는

```text
프롬프트
↓
완성된 디자인
```

이라고 생각했다.

지금은 조금 다르게 생각한다.

```text
아이디어
↓
프롬프트
↓
빠른 초안
↓
직접 확인
↓
수정
↓
다시 확인
↓
디자인 기준 확정
```

Figma Make의 가장 큰 장점은 내가 해야 할 생각을 대신해주는 것이 아니라

**생각한 것을 빠르게 눈앞에 보여주는 것**이라고 생각한다.

그래서 앞으로도

```text
직접 Figma를 사용하는 것

+

Figma Make로 빠르게 시험하는 것
```

둘 중 하나만 선택하기보다 상황에 따라 같이 활용하려고 한다.

그리고 Figma Make로 좋은 결과를 만들려면 결국 한 가지가 더 필요했다.

**어떤 디자인을 좋은 디자인이라고 판단할 것인가?**

AI가 아무리 빠르게 화면을 만들어도 내가 참고할 기준이 없다면

```text
이게 좋은 건지

예쁘기만 한 건지

우리 서비스와 맞는 건지
```

판단하기 어렵다.

그래서 다음에는 실제 디자인을 시작하기 전에 내가 참고했던 **디자인 레퍼런스를 어떻게 찾고, 무엇을 보고 분석해야 하는지** 정리해보려고 한다.
