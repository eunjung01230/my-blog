「파비콘까지가 디자인이다」에서는 favicon을 정리했다.

사이트 안에서는 거의 보이지 않지만,

브라우저 탭에서는 계속 보이는 작은 아이콘이었다.

```text
[파비콘] MY-BLOG
```

처음에는

```text
사이트 화면만 잘 만들면 되지
브라우저 탭 아이콘까지 중요할까?
```

라고 생각했다.

하지만 파비콘을 알아보고 나니

서비스 디자인이 페이지 안에서 끝나는 것이 아니라는 것을 알게 됐다.

그리고 조금 더 밖으로 나가면 또 하나의 화면이 있었다.

바로 **링크 공유 화면**이다.

예를 들어 내가 작성한 블로그 글 주소를 누군가에게 보낸다고 해보자.

단순히

```text
https://example.com/post
```

라는 URL만 보일 수도 있지만,

메신저나 SNS에서는 링크를 분석해서

```text
┌──────────────────────────────┐
│                              │
│         미리보기 이미지       │
│                              │
├──────────────────────────────┤
│ 게시글 제목                   │
│ 짧은 설명                     │
│ example.com                  │
└──────────────────────────────┘
```

같은 **링크 미리보기 카드**를 보여주기도 한다.

나는 처음에는 이것도 공유하는 플랫폼에서 알아서 만들어주는 것이라고 생각했다.

하지만 웹사이트에서 어떤 정보를 제공하느냐에 따라

미리보기에서 사용할

```text
제목

설명

대표 이미지

URL
```

등을 지정할 수 있다.

여기에서 자주 사용되는 것이 **Open Graph**, 줄여서 **OG**였다.

이번 글에서는

```text
OG가 무엇인지

OG 이미지는 왜 필요한지

어떤 이미지를 만들어야 하는지

블로그 글마다 이미지를 따로 만들어야 하는지

구현 후 무엇을 확인해야 하는지
```

정리해보려고 한다.

---

## Open Graph란?

Open Graph Protocol은 웹페이지를 외부 서비스에서 더 풍부하게 표현할 수 있도록

페이지에 메타데이터를 제공하는 방식이다.

[공식 Open Graph Protocol 문서](https://ogp.me/)에서는 기본 속성으로

```text
og:title

og:type

og:image

og:url
```

을 정의하고 있고,

`og:description`, `og:site_name` 같은 추가 정보도 사용할 수 있다.

HTML에서는 보통 `<head>` 안에 이런 형태로 들어간다.

```html
<meta property="og:title" content="게시글 제목">
<meta property="og:type" content="article">
<meta property="og:url" content="https://example.com/post">
<meta property="og:image" content="https://example.com/og-image.png">
<meta
  property="og:description"
  content="게시글 내용을 짧게 소개하는 설명">
```

사용자는 이 코드를 직접 보지 않는다.

하지만 링크를 읽는 외부 서비스에서는 이 정보를 참고해

링크를 조금 더 풍부하게 표현할 수 있다.

[MDN](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/Webpage_metadata)에서도 Open Graph 메타데이터를 사용하면 링크를 공유했을 때

이미지, 제목, 설명 등을 함께 보여줄 수 있다고 설명하고 있다.

---

## 즉 OG는 화면에 직접 보이는 HTML이 아니었다

처음에는

```text
이미지를 화면 어딘가에 넣어야
공유할 때 보이는 건가?
```

라고 생각할 수 있다.

그렇지 않다.

페이지 본문에는 OG 이미지가 전혀 보이지 않아도 된다.

```text
페이지
├─ 제목
├─ 본문
└─ 댓글
```

처럼 되어 있어도

`<head>` 안에는 별도로

```text
og:title
og:description
og:image
```

가 존재할 수 있다.

즉,

```text
페이지 안에서 보여주는 디자인
```

과

```text
페이지가 공유되었을 때 보여주는 디자인
```

을 따로 설정할 수 있는 것이다.

---

## 이것을 알고 나니 블로그에도 또 하나의 화면이 있다는 느낌이 들었다

블로그를 만들면서 생각했던 화면은 보통

```text
Home

Post

Category

About
```

같은 페이지였다.

그런데 실제로 글을 공유하면

사용자는 블로그 본문부터 보는 것이 아니다.

먼저

```text
공유된 링크
```

를 본다.

예를 들어 누군가에게

```text
CSS Grid 공부한 글인데 한번 봐봐.
```

라고 링크를 보내면

상대방은 먼저 미리보기 카드에서

```text
CSS Grid를 처음 공부하며 헷갈렸던 것들

[대표 이미지]

Grid Row와 Column을 직접 사용하며...
```

같은 내용을 볼 수 있다.

즉 링크 미리보기가

**블로그에 들어오기 전의 첫 화면**

이 될 수 있었다.

---

## OG 이미지란?

Open Graph의 `og:image`에 지정하는 대표 이미지다.

예를 들어

```html
<meta
  property="og:image"
  content="https://example.com/images/post-og.png">
```

처럼 지정할 수 있다.

[Open Graph 공식 문서](https://ogp.me/)에서는 `og:image`를 해당 객체를 대표하는 이미지 URL로 정의하고,

추가로

```text
og:image:width
og:image:height
og:image:type
og:image:alt
```

같은 구조화된 속성도 제공한다.

즉 단순히

```text
페이지에 있는 첫 번째 이미지를
적당히 가져가겠지.
```

라고 맡기는 대신

```text
이 페이지를 대표하는 이미지는 이것이다.
```

라고 명시할 수 있다.

---

## 처음에는 대표 이미지 하나면 충분하지 않을까 생각했다

블로그라면 가장 간단한 방법은 사이트 공통 이미지 하나를 만드는 것이다.

예를 들어

```text
┌───────────────────────────────┐
│                               │
│            MY-BLOG            │
│                               │
│     개발하면서 배운 것 기록     │
│                               │
└───────────────────────────────┘
```

이 이미지를 모든 페이지에서 사용한다.

그러면 구현도 단순하다.

```text
Home 공유
→ MY-BLOG 이미지

Git 글 공유
→ MY-BLOG 이미지

CSS 글 공유
→ MY-BLOG 이미지

프로젝트 글 공유
→ MY-BLOG 이미지
```

적어도 아무 이미지도 없는 것보다는

사이트의 정체성을 보여줄 수 있다.

---

## 그런데 모든 글이 같은 이미지면 구분이 어렵다

글이 몇 개 없을 때는 괜찮을 수 있다.

하지만 글이 많아지면

```text
Git 브랜치 글

HTML 글

Supabase 글

프로젝트 회고

Figma 글
```

이 전부 같은 이미지로 보인다.

링크를 여러 개 공유하면

```text
[MY-BLOG 이미지]
Git...

[MY-BLOG 이미지]
HTML...

[MY-BLOG 이미지]
Figma...
```

가 된다.

제목은 다르지만 시각적으로는 거의 같다.

그래서 블로그에서는

```text
사이트 기본 OG 이미지

+

게시글별 OG 이미지
```

를 구분하는 방법도 생각할 수 있었다.

---

## 사이트 기본 OG 이미지

사이트 자체를 공유할 때 사용하는 이미지다.

예를 들어

```text
https://example.com/
```

을 공유했을 때

```text
┌───────────────────────────────┐
│                               │
│            MY-BLOG            │
│                               │
│      작은 배움을 기록합니다     │
│                               │
└───────────────────────────────┘
```

처럼 보이게 한다.

여기에서는

```text
블로그 이름

대표 심볼

블로그 분위기
```

가 중요하다.

---

## 게시글별 OG 이미지

개별 글을 공유할 때는

글의 내용을 조금 더 보여줄 수 있다.

예를 들어 이 글이라면

```text
┌───────────────────────────────┐
│ DESIGN                        │
│                               │
│ OG 이미지와                   │
│ 링크 공유 디자인              │
│                               │
│                        MY-BLOG│
└───────────────────────────────┘
```

처럼 만들 수 있다.

다른 글은

```text
┌───────────────────────────────┐
│ GIT                           │
│                               │
│ Git Branch는                  │
│ 왜 사용하는 걸까?             │
│                               │
│                        MY-BLOG│
└───────────────────────────────┘
```

처럼 바뀐다.

이렇게 하면

```text
같은 블로그라는 통일감

+

각 게시글의 차이
```

를 동시에 보여줄 수 있다.

---

## 그렇다면 100개의 글에 이미지 100개를 직접 만들어야 할까?

여기서 바로 걱정이 생긴다.

```text
글 하나 작성

↓

Figma 열기

↓

OG 이미지 만들기

↓

Export

↓

파일 저장

↓

Front Matter 연결
```

을 매번 한다면

블로그 글을 쓰는 것보다 이미지 만드는 일이 더 번거로워질 수도 있다.

특히 글이 많아지면 부담이 커진다.

그래서 OG 이미지도

```text
얼마나 자동화할 것인가?
```

를 생각할 수 있다.

---

## 방법 1 — 모든 글에 공통 OG 사용

가장 간단하다.

```text
모든 글
→ default-og.png
```

장점은 명확하다.

```text
관리 쉬움

구현 간단

디자인 일관성 유지
```

반면

```text
글마다 시각적 차이가 없음
```

이라는 단점이 있다.

처음 블로그를 운영하거나,

아직 글 수가 많지 않다면 충분히 사용할 수 있는 방법이라고 생각한다.

---

## 방법 2 — 중요한 글만 개별 OG 이미지 제작

모든 글을 만들 필요 없이

```text
프로젝트 소개

대표 포스트

공유가 많은 글
```

정도만 별도 이미지를 만들 수 있다.

예를 들어

```text
기본 글
→ 공통 OG

프로젝트 글
→ 전용 OG

대표 학습 글
→ 전용 OG
```

방식이다.

작업량과 완성도의 중간 정도다.

---

## 방법 3 — 템플릿으로 글별 OG 이미지 생성

디자인 구조는 하나로 고정하고

```text
Category

Title

Blog Name
```

만 바꾸는 방법도 있다.

예를 들어 기본 Template이

```text
┌───────────────────────────────┐
│ {CATEGORY}                    │
│                               │
│ {POST TITLE}                  │
│                               │
│                        MY-BLOG│
└───────────────────────────────┘
```

라고 하면

게시글에 따라 내용만 바뀐다.

이 방식이 글이 많은 블로그에는 특히 잘 맞을 수 있다.

---

## OG 이미지도 디자인 시스템처럼 생각할 수 있었다

매번 완전히 새로운 이미지를 만들 필요는 없다.

오히려 블로그라면 반복되는 규칙이 있는 편이

같은 사이트라는 느낌을 주기 좋다.

예를 들어

```text
배경색

카테고리 위치

제목 위치

폰트

심볼

블로그 이름 위치
```

를 고정한다.

그리고 글마다

```text
카테고리

제목
```

정도만 변경한다.

```text
Git
→ 파란 계열

Frontend
→ 다른 강조

Design
→ 또 다른 강조
```

처럼 카테고리별 변화를 줄 수도 있지만,

색상이 너무 많아져 전체 브랜딩이 흐려지는 것은 조심할 수 있다.

---

## OG 이미지에 정보를 많이 넣고 싶어졌다

공간이 꽤 크다 보니 욕심이 생긴다.

```text
게시글 제목

카테고리

작성 날짜

작성자

태그

블로그 이름

설명

URL

아이콘
```

을 다 넣을 수 있을 것 같다.

하지만 링크 미리보기 자체에도

이미 제목과 설명이 별도로 표시될 수 있다.

그러면 이미지 안에서 같은 내용을 또 반복하게 된다.

예를 들어

```text
[이미지]
Figma 기초
Figma를 처음 배우면서...
2026.09.25
MY-BLOG

제목:
Figma 기초

설명:
Figma를 처음 배우면서...
```

처럼 된다.

정보가 반복된다.

---

## OG 이미지는 포스터라고 생각하는 편이 이해하기 쉬웠다

모든 내용을 이미지 안에서 읽게 만들기보다

```text
이 글이 무엇에 대한 것인지
```

빠르게 알아볼 수 있는 표지에 가깝게 만든다.

예를 들어

```text
DESIGN

반응형 디자인

MY-BLOG
```

정도만 보여준다.

필요하면 작은 그래픽을 넣을 수 있다.

```text
모바일

태블릿

데스크톱
```

을 연상시키는 간단한 형태 정도다.

상세 설명은

```text
og:description
```

이 담당하도록 역할을 나눌 수 있다.

---

## 이미지와 메타데이터의 역할을 나눌 수 있었다

예를 들어

### OG 이미지

```text
DESIGN

반응형 디자인

MY-BLOG
```

### og:title

```text
반응형 디자인 — 화면이 작아지면 그냥 줄이면 되는 걸까?
```

### og:description

```text
모바일과 데스크톱에서 같은 정보를
어떻게 다르게 배치할지 공부한 내용을 정리했습니다.
```

각각의 역할이 조금 다르다.

이미지는

```text
빠른 시각적 인식
```

을 담당하고,

제목과 설명은

```text
내용 이해
```

를 담당할 수 있다.

---

## OG 이미지에 너무 작은 글씨를 넣으면 안 됐다

Figma에서는 큰 Canvas로 작업한다.

그래서 작은 부가 정보를 많이 넣기 쉽다.

```text
category

date

author

tag

url
```

하지만 실제 링크 미리보기에서는 이미지가 작게 축소된다.

모바일 메신저에서는 더 작게 보일 수 있다.

그러면 작은 텍스트는 거의 읽히지 않는다.

파비콘에서 배웠던 원칙이 다시 나타났다.

```text
작아질수록
덜 넣어야 한다.
```

---

## OG 이미지도 실제 크기로 축소해서 봐야 했다

Figma에서 크게 볼 때

```text
완벽하다.
```

라고 판단하지 않는다.

미리보기 카드처럼 작게 만들어 본다.

```text
큰 원본

↓

모바일 링크 카드

↓

작은 미리보기
```

그리고 확인한다.

```text
제목을 읽을 수 있는가?

블로그 이름이 보이는가?

이미지가 너무 복잡하지 않은가?

무엇에 대한 링크인지 알 수 있는가?
```

---

## 화면 비율도 중요했다

OG Protocol 자체가

```text
모든 OG 이미지는 반드시 이 크기
```

라고 하나의 픽셀 크기를 강제하는 것은 아니다.

[공식 프로토콜](https://ogp.me/)은 `og:image`와 함께 이미지의 width, height 등을 제공할 수 있도록 정의한다.

실제로 링크 미리보기용 이미지를 만들 때는

여러 서비스에서 넓은 가로형 카드로 사용하기 편하도록

```text
약 1.91 : 1
```

비율을 사용하는 경우가 많고,

대표적인 작업 크기로

```text
1200 × 630
```

을 자주 사용한다.

다만 이것을

```text
Open Graph 공식 필수 크기
```

라고 이해하면 안 된다.

플랫폼마다 표시 방법이 달라질 수 있기 때문이다.

---

## 플랫폼마다 똑같이 보인다고 생각하면 안 됐다

같은 URL을 공유해도

서비스마다 카드 디자인이 다를 수 있다.

```text
이미지가 크게 보이거나

작게 보이거나

설명이 생략되거나

일부 영역이 잘릴 수 있다.
```

그래서 OG 이미지를

```text
특정 미리보기 화면 한 곳에
완벽하게 맞춘 이미지
```

보다는

```text
조금 잘리거나 작아져도
핵심이 살아남는 이미지
```

로 만드는 편이 안전했다.

---

## 중요한 내용은 이미지 가장자리에 붙이지 않는 것이 좋았다

예를 들어 제목을

```text
|반응형 디자인
```

처럼 왼쪽 끝에 아주 가깝게 붙였다고 하자.

특정 플랫폼에서 이미지가 일부 Crop되거나

미리보기 레이아웃이 달라지면

글자가 답답하게 보일 수 있다.

그래서

```text
┌───────────────────────┐
│                       │
│   반응형 디자인       │
│                       │
└───────────────────────┘
```

처럼 적당한 안전 여백을 남기는 것이 좋다.

---

## 중앙에 다 몰아넣는 것도 정답은 아니었다

잘릴 수 있다는 걱정 때문에

모든 요소를 중앙에 몰아넣을 수도 있다.

```text
        DESIGN

     반응형 디자인

        MY-BLOG
```

이 방식도 가능하지만

모든 OG 이미지가 똑같이 중앙 정렬되어야 하는 것은 아니다.

중요한 것은

```text
핵심 정보가 가장자리 Crop에 취약하지 않은가?
```

다.

브랜드 스타일에 따라 왼쪽 정렬을 사용해도 충분하다.

---

## 긴 게시글 제목은 특히 문제였다

블로그 글 제목은 짧지만은 않다.

예를 들어

```text
Figma → Claude로 구현하기 — 디자인을 코드로 옮길 때 AI에게 어디까지 맡길까?
```

같은 제목을 그대로 이미지에 넣는다고 해보자.

한 줄에는 들어가지 않는다.

```text
Figma → Claude로 구현하기
디자인을 코드로 옮길 때
AI에게 어디까지 맡길까?
```

여러 줄이 된다.

제목이 더 길어지면 네 줄,

다섯 줄이 될 수도 있다.

그러면 OG 이미지 전체가 제목으로 가득 찬다.

---

## 그래서 OG용 제목을 따로 줄일 수도 있었다

게시글 실제 제목은 그대로 유지한다.

```text
Figma → Claude로 구현하기
— 디자인을 코드로 옮길 때 AI에게 어디까지 맡길까?
```

하지만 OG 이미지 안에서는

```text
Figma → Claude로 구현하기
```

정도로만 보여줄 수 있다.

즉,

```text
페이지 제목

≠

이미지 안에 반드시 들어가야 하는 전체 문장
```

이다.

이미지는 시각적 표지이기 때문에

핵심만 보여줘도 된다.

---

## 하지만 og:title 자체는 정확하게 유지할 수 있다

이미지 안의 제목은 줄이더라도

HTML의

```html
<meta property="og:title" content="...">
```

에는 실제 게시글 제목을 넣을 수 있다.

그러면 미리보기 카드에서

```text
이미지
→ 짧은 시각적 제목

텍스트 영역
→ 전체 게시글 제목
```

으로 역할을 나눌 수 있다.

---

## 블로그 글에서는 게시물마다 title을 가져올 수 있었다

내 블로그처럼 정적 사이트에서 게시물을 관리한다면

각 글에 이미

```yaml
title: "OG 이미지와 링크 공유 디자인"
```

같은 정보가 있다.

그러면 Layout에서 이 값을 사용해

{% raw %}
```html
<meta
  property="og:title"
  content="{{ page.title }}">
```
{% endraw %}

처럼 연결하는 구조를 만들 수 있다.

Jekyll 같은 정적 사이트 생성기를 사용하는 경우에는

실제 프로젝트 구조에 맞춰 Liquid 변수를 이용할 수 있다.

중요한 것은 코드를 그대로 복사하는 것보다

```text
현재 사이트에서
게시글 제목이 어디에 저장되어 있는지
```

를 먼저 확인하는 것이다.

---

## description도 게시글마다 다르게 만들 수 있다

페이지에 설명 정보가 있다면

{% raw %}
```html
<meta
  property="og:description"
  content="{{ page.description }}">
```
{% endraw %}

처럼 활용할 수 있다.

설명이 없을 경우 사이트 기본 설명을 사용하는 방식도 생각할 수 있다.

개념적으로는

```text
게시글 description 있음
→ 게시글 설명

없음
→ 사이트 기본 설명
```

이다.

이런 **fallback** 구조를 만들어두면

모든 글에 반드시 같은 필드를 작성하지 않아도 된다.

---

## 이미지도 fallback 구조를 만들 수 있었다

예를 들어

```text
게시글 전용 OG 이미지 있음
→ 그 이미지 사용

없음
→ 기본 OG 이미지 사용
```

방식이다.

개념적으로

```text
page.ogImage

있음?
├─ Yes → page.ogImage
└─ No  → default-og.png
```

구조다.

이 방식이 있으면

```text
모든 글에 이미지가 있어야만
공유 미리보기가 동작한다.
```

는 부담을 줄일 수 있다.

---

## 기본 이미지가 있다는 것이 중요했다

개별 이미지 시스템을 만들더라도

기본 이미지는 준비해두는 편이 좋다.

왜냐하면

```text
이미지 설정을 깜빡한 글

About 페이지

Category 페이지

Home
```

처럼 전용 이미지가 없는 페이지가 생길 수 있기 때문이다.

이때

```text
og:image 없음
```

으로 두는 것보다

사이트 기본 이미지를 fallback으로 사용할 수 있다.

---

## OG 이미지는 절대 URL을 사용하는 편이 안전했다

페이지 안의 일반 이미지라면

```html
<img src="/assets/og.png">
```

같은 상대 경로를 자주 사용한다.

하지만 Open Graph와 같이 외부 서비스가 페이지의 메타데이터를 읽어가는 경우에는

이미지 URL을 완전한 URL로 제공하는 것이 중요하다.

[MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/base)도 Open Graph 태그에서는 `<base>`를 이용한 상대 경로 해석에 의존하지 말고 완전한 URL을 사용해야 한다고 설명한다.

예를 들면

```html
<meta
  property="og:image"
  content="https://example.com/assets/og.png">
```

형태다.

---

## 로컬 경로를 넣으면 외부 서비스는 볼 수 없다

개발 중에는

```text
http://localhost:4000/assets/og.png
```

이미지가 잘 보일 수 있다.

하지만 누군가 인터넷에서 내 링크를 읽는다면

내 컴퓨터의 localhost에는 접근할 수 없다.

따라서 실제 배포에서는

```text
공개된 HTTPS URL
```

을 사용해야 한다.

이것도 로컬에서는 정상인데

공유에서는 이미지가 안 뜨는 원인이 될 수 있다.

---

## 이미지 파일도 외부에서 접근할 수 있어야 한다

예를 들어

```text
Private Storage

로그인이 필요한 이미지

로컬 파일
```

을 `og:image`로 지정하면

링크 미리보기 시스템이 이미지를 가져오지 못할 수 있다.

따라서 OG 이미지는 일반적으로

```text
외부에서 URL로 접근 가능한 이미지
```

로 준비하는 편이 자연스럽다.

---

## og:url도 있었다

Open Graph의 기본 속성 중 하나가

```text
og:url
```

이다.

[공식 프로토콜](https://ogp.me/)에서는 이것을 해당 객체의 영구적인 식별자로 사용할 canonical URL로 정의한다.

예를 들어

```html
<meta
  property="og:url"
  content="https://example.com/design/og-image/">
```

처럼 현재 게시글의 주소를 넣는다.

사이트 모든 페이지에서

```text
https://example.com/
```

만 넣으면 개별 글을 제대로 표현하지 못할 수 있다.

---

## og:type도 있었다

사이트 메인처럼 일반적인 페이지라면

```html
<meta property="og:type" content="website">
```

를 사용할 수 있다.

게시글이라면

```html
<meta property="og:type" content="article">
```

을 사용할 수 있다.

[Open Graph Protocol](https://ogp.me/)은 `website`와 `article` 같은 객체 타입을 정의하고 있고,

article에는 작성일이나 작성자 같은 추가 속성도 정의되어 있다.

처음 블로그를 만들 때부터 이 모든 값을 자세하게 넣을 필요는 없더라도

```text
사이트

vs

게시글
```

의 종류를 구분할 수 있다는 정도는 알아둘 수 있었다.

---

## og:image:alt도 존재했다

이미지에는 대체 설명을 제공할 수 있다.

[Open Graph 공식 문서](https://ogp.me/)에서는 `og:image`를 지정할 경우

이미지 내용을 설명하는

```text
og:image:alt
```

도 함께 지정할 것을 안내한다.

예를 들면

```html
<meta
  property="og:image:alt"
  content="MY-BLOG의 반응형 디자인 학습 포스트 대표 이미지">
```

처럼 사용할 수 있다.

단순히

```text
image
```

라고 쓰기보다

무엇을 보여주는 이미지인지 설명한다.

---

## OG와 일반 meta description은 다른 것이었다

HTML에는

```html
<meta
  name="description"
  content="페이지 설명">
```

도 사용할 수 있다.

그리고 Open Graph에는

```html
<meta
  property="og:description"
  content="공유 미리보기용 설명">
```

이 있다.

둘의 내용이 같을 수도 있다.

하지만 목적은 조금 다르다.

```text
meta description
→ 일반적인 문서 메타데이터

og:description
→ Open Graph 소비자가 사용할 설명
```

이다.

처음에는 하나만 넣으면 모든 곳에서 자동으로 똑같이 사용하는 줄 알기 쉽다.

---

## X 같은 서비스에는 별도 메타데이터도 있다

Open Graph 외에도 플랫폼별 메타데이터가 존재할 수 있다.

[MDN](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/Webpage_metadata)에서도 Open Graph와 함께 X/Twitter의 카드용 메타데이터가 별도로 존재한다고 설명한다.

예를 들어

```html
<meta name="twitter:card" content="summary_large_image">
<meta name="twitter:title" content="게시글 제목">
<meta name="twitter:image" content="...">
```

같은 형태를 볼 수 있다.

처음부터 모든 서비스의 메타데이터를 완벽하게 지원할 필요는 없다.

우선 Open Graph 구조부터 이해하고,

필요한 플랫폼이 생겼을 때 추가하는 방식도 가능하다.

---

## 메타태그를 많이 넣는 것이 목적은 아니었다

관련 설정을 찾다 보면

```text
og:title
og:type
og:url
og:image
og:description
og:site_name
og:locale
og:image:width
og:image:height
og:image:alt
twitter:card
twitter:title
twitter:image
...
```

계속 나온다.

처음에는

```text
이거 전부 넣어야 하나?
```

싶어진다.

하지만 공부 초기에는 핵심부터 이해하면 된다.

```text
제목

대표 이미지

페이지 URL

페이지 종류

설명
```

정도다.

필요할 때 확장하면 된다.

## OG 이미지를 ChatGPT로 만들 수도 있었다

「ChatGPT로 이미지·아이콘 만들기」에서 ChatGPT로 이미지와 아이콘을 만드는 방법을 정리했다.

OG 이미지도 만들 수 있다.

예를 들어

```text
개발 블로그의 기본 OG 이미지를 만들어줘.

용도:
링크 공유 미리보기

비율:
가로형 1.91:1

분위기:
단순하고 차분한 개발 블로그

포함:
MY-BLOG라는 이름
단순한 블로그 심볼

제외:
복잡한 코드 배경
작은 글씨
과도한 3D 효과
너무 많은 장식
```

처럼 요청할 수 있다.

---

## 하지만 텍스트는 Figma에서 넣는 방법이 더 관리하기 쉬울 수도 있었다

예를 들어 배경 그래픽 자체는 ChatGPT로 만든다.

```text
ChatGPT
→ 배경 그래픽
```

그리고

```text
Figma
→ 글 제목
→ 카테고리
→ 블로그 이름
```

을 넣는다.

이렇게 나누면 나중에 글자만 쉽게 수정할 수 있다.

```text
AI 이미지 안에 제목 포함
```

방식은 빠르지만

제목을 바꿀 때 이미지를 다시 생성하거나 편집해야 할 수 있다.

---

## 블로그라면 오히려 단순한 템플릿이 관리하기 좋을 수 있었다

예를 들어 내 블로그의 OG 디자인 규칙을

```text
배경
→ 블로그 기본 색

왼쪽 위
→ Category

가운데
→ Title

오른쪽 아래
→ Blog Name / Symbol
```

로 고정한다.

그러면 글이 늘어나도

```text
제목 교체

카테고리 교체
```

정도로 만들 수 있다.

매번 새로운 디자인을 고민할 필요가 없다.

---

## 글 100개에 서로 다른 화려한 디자인이 꼭 필요한 것은 아니다

오히려 매번 다른 스타일로 만들면

```text
이 링크도 MY-BLOG

저 링크도 MY-BLOG
```

라는 느낌이 약해질 수 있다.

블로그에서는

```text
일관된 템플릿
+
글마다 다른 내용
```

이 더 적합할 수 있다.

예를 들어

```text
Design 글

Backend 글

Git 글
```

이어도

같은 Grid,

같은 Typography,

같은 로고 위치를 유지한다.

## OG 이미지와 썸네일을 같은 것으로 사용할 수도 있을까?

가능한 경우도 있다.

예를 들어 블로그 카드에 사용하는 게시글 썸네일이 이미

```text
글 제목

대표 그래픽
```

을 잘 보여주고 있다면

OG 이미지로 재사용할 수 있다.

그러면 관리할 이미지가 줄어든다.

하지만 역할이 다를 수도 있다.

```text
블로그 카드 Thumbnail
→ 사이트 내부에서 사용

OG Image
→ 외부 링크 공유에서 사용
```

내부 카드의 비율과 외부 공유 카드의 비율이 다르다면

같은 이미지를 억지로 재사용했을 때 잘릴 수 있다.

---

## 그래서 하나의 원본에서 여러 버전을 만드는 방법도 있었다

예를 들어 디자인 원본을

```text
Figma Component
```

하나로 만든다.

그 안의

```text
제목

카테고리

심볼
```

을 유지하면서

```text
Blog Thumbnail

OG Image
```

각 비율에 맞춰 Variant를 만들 수 있다.

그러면 브랜딩은 유지하면서

각 사용 환경에 맞는 이미지를 만들 수 있다.

---

## OG 이미지에서도 실제 제목 길이를 테스트해야 했다

디자인할 때는

```text
Figma 기초
```

처럼 짧은 제목만 넣으면 안 된다.

실제로는

```text
ChatGPT / Claude / Gemini를 나눠 쓰는 이유
```

처럼 긴 제목도 있다.

더 길 수도 있다.

그래서 일부러

```text
짧은 제목

중간 제목

가장 긴 제목
```

을 넣어본다.

그리고 확인한다.

```text
몇 줄까지 허용할 것인가?

폰트 크기를 자동으로 줄일 것인가?

일정 길이 이후 잘라낼 것인가?

OG용 짧은 제목 필드를 따로 둘 것인가?
```

---

## 제목이 길다고 무조건 글자를 작게 만들면 안 됐다

「반응형 디자인」에서도 비슷한 문제를 봤다.

```text
공간 부족
↓
폰트 축소
```

만 반복하면 결국 읽을 수 없게 된다.

OG 이미지에서도

```text
제목 길어짐
↓
폰트 계속 축소
```

는 좋은 해결이 아닐 수 있다.

대신

```text
최대 줄 수 지정

긴 제목은 적절히 줄바꿈

필요하면 이미지용 제목 축약
```

을 생각할 수 있다.

---

## 제목보다 블로그 이름이 더 커지면 이상할 수 있었다

사이트를 알리고 싶어서

```text
MY-BLOG
```

를 크게 넣고 싶어진다.

그런데 개별 게시글을 공유하는 목적이라면

사용자가 가장 궁금한 것은

```text
무슨 글인가?
```

다.

따라서

```text
게시글 제목
→ 1순위

카테고리
→ 2순위

블로그 이름
→ 브랜드 표시
```

정도로 시각적 우선순위를 만들 수 있다.

「버튼과 정보의 우선순위」에서 공부했던 정보 우선순위가 여기에서도 다시 사용된다.

---

## 사이트 전체를 공유할 때는 반대일 수 있다

Home의 OG 이미지라면

가장 중요한 것이 사이트 자체다.

```text
MY-BLOG
```

를 크게 보여줄 수 있다.

그 아래

```text
개발하면서 배우고 막혔던 과정을 기록합니다.
```

같은 설명을 둘 수 있다.

즉

```text
사이트 OG

vs

게시글 OG
```

에서도 정보 우선순위가 다를 수 있다.

---

## 링크를 공유하는 사람의 입장도 생각하게 됐다

내가 내 글을 공유한다고 해보자.

카카오톡이나 다른 메신저에 URL을 붙였다.

그런데 미리보기가

```text
제목 없음

이미지 없음

이상한 설명

긴 URL
```

처럼 보인다면

링크 자체가 조금 불안해 보일 수도 있다.

반대로

```text
[대표 이미지]

글 제목

짧은 설명

MY-BLOG
```

가 보이면

클릭하기 전에도 어떤 링크인지 이해하기 쉽다.

---

## 받는 사람에게도 정보가 필요했다

링크만 보면

```text
https://...
```

가 어디로 연결되는지 잘 모를 수 있다.

미리보기는

```text
어떤 사이트인지

무슨 내용인지

클릭할 가치가 있는지
```

판단하는 데 도움을 준다.

그래서 OG 설정은 단순히

```text
예쁜 이미지 보여주기
```

보다

**링크에 대한 맥락을 제공하는 UI**

라고 생각하게 됐다.

---

## OG 이미지는 콘텐츠 디자인이기도 했다

Favicon은 사이트 전체를 대표한다.

OG 이미지는 페이지 하나,

특히 콘텐츠 하나를 대표할 수도 있다.

그래서 블로그에서는

```text
브랜드 디자인

+

콘텐츠 디자인
```

이 만나는 지점이라고 느꼈다.

```text
같은 MY-BLOG

하지만
각각 다른 글
```

을 동시에 표현해야 하기 때문이다.

---

## 글 제목을 이미지 안에 넣을지 고민할 수 있었다

방법은 크게 두 가지다.

### 제목 포함

```text
┌───────────────────────────┐
│ DESIGN                    │
│                           │
│ OG 이미지와               │
│ 링크 공유 디자인          │
│                           │
│                    MY-BLOG│
└───────────────────────────┘
```

장점:

```text
이미지만 봐도 글을 알 수 있음
```

단점:

```text
긴 제목 처리 필요

이미지 생성 과정 복잡
```

---

## 제목 미포함

```text
┌───────────────────────────┐
│                           │
│         MY-BLOG           │
│                           │
│      [대표 그래픽]        │
│                           │
└───────────────────────────┘
```

실제 제목은 미리보기 카드의

```text
og:title
```

영역에서 보여준다.

장점:

```text
이미지 재사용 쉬움

관리 간단
```

단점:

```text
글마다 시각적 차이가 적음
```

어느 쪽이 무조건 정답은 아니다.

---

## 내 블로그처럼 글이 많아질 예정이라면

글이 몇 개뿐이라면

전부 전용 이미지를 직접 만들어도 큰 부담이 아니다.

하지만 글이 수십 개,

100개 이상으로 늘어난다면

```text
글 작성

+

OG 수동 디자인
```

을 계속 반복하는 것이 부담이 될 수 있다.

그래서 처음부터

```text
기본 이미지

+

필요한 글만 전용 이미지
```

또는

```text
자동화 가능한 템플릿
```

구조를 만들어두는 편이 관리하기 쉬울 수 있다.

---

## 디자인 완성도보다 운영 가능성도 봐야 했다

OG 이미지를 아주 화려하게 만들었다.

하지만 새 글을 작성할 때마다

```text
20분씩 이미지 제작
```

이 필요하다면

나중에는 귀찮아서 안 만들 수도 있다.

그렇다면 처음부터

```text
2~3분이면 새 글 OG를 만들 수 있는 디자인
```

이 더 좋은 시스템일 수 있다.

블로그 디자인은 한 번 만드는 것뿐 아니라

계속 운영해야 하기 때문이다.

---

## 자동 생성도 가능하지만 처음부터 필요하지는 않았다

개발 블로그라면 나중에는

게시글 제목과 카테고리를 읽어

OG 이미지를 자동으로 만드는 구조도 생각할 수 있다.

개념적으로는

```text
Post

title:
반응형 디자인

category:
Design

↓

Template

↓

자동 OG Image
```

형태다.

하지만 글 몇 개를 작성하는 단계에서

자동 생성 시스템부터 만드는 것은 오히려 일이 커질 수 있다.

먼저

```text
어떤 디자인으로 만들지
```

를 확정하는 것이 우선이다.

자동화는 반복 규칙이 생긴 뒤에 해도 된다.

---

## 먼저 수동으로 해봐야 자동화할 규칙도 알 수 있었다

예를 들어 실제로 몇 개를 만들어보니

```text
제목은 최대 3줄

카테고리는 왼쪽 위

블로그 이름은 오른쪽 아래

배경은 카테고리별로 약간 변경
```

이라는 규칙이 생겼다고 하자.

그때 자동화하면 된다.

```text
사람이 반복하는 규칙
↓
코드로 자동화
```

하는 것이다.

처음부터 규칙도 없는데 자동화부터 만들 필요는 없다.

---

## 이미지 파일 용량도 확인할 수 있었다

OG 이미지는 사용자 화면 안에 항상 렌더링되는 이미지와 성격이 조금 다르지만

그래도 불필요하게 거대한 파일을 사용할 이유는 없다.

예를 들어 단순한 텍스트와 배경만 있는 OG 이미지가

```text
10MB
```

일 필요는 없다.

적절하게 Export하고,

필요하면 압축한다.

「Figma Export」에서 공부했던

```text
이미지 형식

크기

최적화
```

가 다시 연결된다.

---

## PNG와 JPG 중 무엇을 쓸까?

OG 이미지가

```text
단색 배경

텍스트

단순한 그래픽
```

중심이라면 PNG가 편할 수 있다.

사진 중심이라면

JPG가 파일 크기 측면에서 더 적합할 수 있다.

중요한 것은

```text
무조건 PNG

무조건 JPG
```

라고 외우는 것이 아니라

이미지 내용과 품질,

용량을 보고 선택하는 것이다.

---

## WebP는 어떨까?

웹 페이지 안의 이미지에서는 WebP를 많이 사용할 수 있다.

하지만 외부 링크 미리보기처럼

여러 서비스가 이미지를 가져가는 경우에는

지원 범위를 확인하는 편이 안전하다.

OG Protocol 자체는 `og:image:type`을 통해 이미지의 MIME type을 제공할 수 있지만, 실제 링크 미리보기를 만드는 서비스의 지원 범위는 각각 다를 수 있다.

그래서 공유 호환성을 중요하게 본다면

널리 지원되는 일반적인 이미지 형식을 우선 고려하는 것도 방법이다.

---

## 적용했는데 미리보기 이미지가 바로 안 바뀔 수도 있었다

OG 이미지를 새것으로 교체했다.

사이트를 직접 열면 새 이미지가 있다.

그런데 메신저에 링크를 다시 보내보니

예전 이미지가 나온다.

```text
왜 안 바뀌지?
```

할 수 있다.

외부 플랫폼은 링크 정보를 매번 처음부터 가져오는 대신

이전에 수집한 미리보기 정보를 캐시할 수 있다.

그래서 코드를 수정했다고

모든 외부 서비스의 미리보기가 즉시 바뀐다고 생각하면 안 된다.

---

## 이것 때문에 테스트할 때 혼란스러울 수 있었다

예를 들어

```text
OG v1 적용
↓
링크 공유
↓
플랫폼이 정보 저장

OG v2 적용
↓
다시 공유
↓
여전히 v1 표시
```

가 될 수 있다.

그러면

```text
코드가 잘못됐나?

배포가 안 됐나?
```

를 계속 확인하게 된다.

실제로는 캐시 문제일 수도 있다.

따라서 OG 수정에서는

```text
페이지 HTML이 실제로 변경됐는지

og:image URL이 맞는지

이미지 URL에 접근 가능한지
```

를 먼저 직접 확인하는 것이 좋다.

---

## 이미지 파일명을 바꾸는 것도 방법이 될 수 있었다

예를 들어 계속 같은

```text
og-image.png
```

URL을 사용하면서 내용만 바꾸면

외부 캐시에 이전 파일이 남아 있을 수 있다.

경우에 따라

```text
og-image-v2.png
```

처럼 URL 자체를 바꾸는 것이 캐시된 이미지와 구분하는 데 도움이 될 수 있다.

다만 매번 무작정 버전을 늘리기보다

먼저 현재 플랫폼과 캐시 상황을 확인하는 것이 좋다.

---

## OG 메타데이터는 최종 HTML에서 확인해야 했다

Jekyll 같은 정적 사이트에서는 Template에 코드를 넣는다.

하지만 실제 중요한 것은

```text
작성한 Liquid 코드
```

가 아니라

```text
빌드 결과 HTML
```

이다.

예를 들어 Template에는

{% raw %}
```html
<meta property="og:title" content="{{ page.title }}">
```
{% endraw %}

가 있다.

실제 배포된 HTML에서는

```html
<meta
  property="og:title"
  content="OG 이미지와 링크 공유 디자인">
```

처럼 나와야 한다.

그래서 문제가 생기면

브라우저에서 실제 페이지의 `<head>`를 확인하는 것이 도움이 된다.

---

## 페이지마다 값이 제대로 달라지는지도 확인해야 했다

예를 들어 모든 글을 열어봤는데

```text
og:title
→ 항상 MY-BLOG
```

로 되어 있다면

개별 글 제목이 적용되지 않은 것이다.

또는

```text
og:url
→ 모든 페이지가 Home URL
```

이라면 문제가 있을 수 있다.

그래서 최소한 서로 다른 글 두세 개를 확인한다.

```text
Post A

Post B

Home
```

에서 값이 각각 맞는지 보는 것이다.

---

## OG 설정도 중복될 수 있었다

테마나 기존 Layout이 이미 Open Graph를 지원할 수 있다.

그런데 내가 모르고

```html
<meta property="og:title" ...>
```

를 또 추가하면

HTML 안에 같은 속성이 여러 개 생길 수 있다.

[Open Graph Protocol](https://ogp.me/)은 동일 속성 값이 여러 개 존재할 경우 배열처럼 다룰 수 있고 첫 번째 값을 우선하는 규칙도 정의하고 있기 때문에, 의도하지 않은 중복 메타데이터는 결과를 헷갈리게 만들 수 있다.

그래서 favicon과 마찬가지로

```text
현재 설정 확인
↓
필요한 부분만 수정
```

이 좋았다.

---

## Claude에게 작업시킬 때도 먼저 확인하게 한다

예를 들어 내 블로그에 OG를 추가한다면

단순히

```text
OG 이미지 넣어줘.
```

라고 하기보다

```text
현재 블로그의 <head>, SEO, Open Graph 관련 설정을 먼저 확인해줘.

기존 og:title, og:description, og:image, og:url 설정이 있는지 확인하고
이미 존재한다면 중복 구현하지 마.

현재 Jekyll 구조와 Front Matter를 기준으로

- 사이트 기본 OG
- 게시글별 title / description
- 게시글에 별도 OG 이미지가 없을 때 기본 이미지 fallback

구조를 제안해줘.

아직 수정하거나 커밋하지 말고
현재 구조와 필요한 변경점만 보고해줘.
```

처럼 먼저 조사하도록 할 수 있다.

이 방식이면 기존 테마 기능을 모르고 새 코드를 덧붙이는 문제를 줄일 수 있다.

---

## OG 이미지부터 만들기 전에 현재 블로그 구조를 보는 것이 좋았다

예를 들어 이미

```text
post.image
```

라는 Front Matter가 있을 수 있다.

또는

```text
thumbnail
```

필드가 있을 수도 있다.

그렇다면 새로운

```text
ogImage
```

필드를 또 만들 필요가 있는지 확인해야 한다.

기존 대표 이미지와 OG를 같은 이미지로 사용할 수 있다면

관리 필드를 늘리지 않을 수도 있다.

---

## 반대로 OG 전용 필드가 필요한 경우도 있다

게시글 본문의 대표 이미지는 세로형인데

링크 공유에서는 가로형이 필요하다고 하자.

```text
Post Image
→ 세로형 Screenshot

OG Image
→ 가로형 공유 카드
```

역할이 다르다.

이 경우에는 별도 필드를 두는 것이 자연스러울 수 있다.

예:

```yaml
image: /assets/posts/figma-screen.png
og_image: /assets/og/figma.png
```

이런 구조다.

---

## Front Matter가 너무 많아지는 것도 조심해야 했다

블로그 글 하나를 작성할 때

```yaml
title:
date:
category:
tags:
description:
thumbnail:
og_image:
og_title:
og_description:
twitter_image:
```

를 전부 매번 입력해야 한다면

운영이 매우 번거롭다.

그래서 가능한 값은 재사용한다.

```text
og_title
→ 기본적으로 page.title

og_description
→ 기본적으로 page.description

og_image
→ 없으면 default image
```

처럼 한다.

특별한 경우에만 Override하는 편이 관리하기 쉽다.

---

## 좋은 시스템은 안 적어도 기본적으로 동작해야 했다

내가 생각하기에 블로그에서 편한 구조는 이런 것이다.

```text
최소 Front Matter

title
date
category
```

만 있어도

```text
OG title
→ 자동 생성

OG URL
→ 자동 생성

OG image
→ 기본 이미지
```

가 동작한다.

필요할 때만

```text
description

og_image
```

를 추가한다.

즉

```text
기본 동작

+

선택적인 커스텀
```

구조다.

---

## OG 이미지 때문에 글 작성 자체가 귀찮아지면 안 됐다

블로그의 목적은 글을 기록하는 것이다.

OG 이미지가 중요하다고 해서

```text
글 쓰기 20분

OG 만들기 30분
```

이 되어버리면

운영 방향이 뒤집힐 수 있다.

특히 개발 블로그라면

콘텐츠가 먼저다.

그래서

```text
공유 디자인 완성도

vs

운영 부담
```

을 같이 생각해야 했다.

---

## 처음에는 기본 OG 하나만 있어도 충분할 수 있었다

처음 구현한다면

```text
1. 기본 OG 이미지 제작

2. 사이트 title / description 설정

3. 게시글 title 자동 반영

4. 실제 공유 테스트
```

정도만 해도 충분하다.

그리고 블로그를 운영하면서

```text
글별 OG가 필요하겠다.
```

고 느낀다면 그때 확장할 수 있다.

처음부터 완벽한 시스템을 만들 필요는 없다.

---

## 링크를 공유하기 전에는 몰랐던 문제였다

이것이 이번 글에서 가장 기억하고 싶은 부분이다.

사이트 안에서만 확인했다면

OG 이미지는 존재하지 않아도 아무 문제를 못 느낄 수 있다.

```text
Home 정상

Post 정상

Navigation 정상

Responsive 정상
```

모두 잘 된다.

그런데 링크를 밖으로 가져가는 순간

새로운 화면이 나타난다.

```text
공유 미리보기
```

이다.

「실제 시연 후 발견한 UI 문제」에서 실제 시연을 해야 UI 문제가 보였던 것과 비슷했다.

**서비스가 사용되는 환경으로 가져가야 보이는 디자인 문제**가 또 있었던 것이다.

---

## 파비콘과 OG 이미지를 같이 보니 서비스 경계가 넓어졌다

처음 내가 생각했던 디자인 영역은

```text
웹페이지
```

였다.

지금은 조금 넓어졌다.

```text
사이트 내부
│
├─ Home
├─ Post
└─ Navigation

사이트 주변
│
├─ Favicon
├─ 브라우저 제목
└─ Bookmark

사이트 외부
│
└─ 링크 공유 미리보기
   ├─ OG Image
   ├─ Title
   └─ Description
```

사용자가 서비스를 만나는 모든 접점이

어느 정도 디자인 대상이 될 수 있었다.

---

## OG 이미지는 단순한 SNS용 광고 이미지가 아니었다

처음에는

```text
SNS 홍보하는 사람만 필요한 것 아닌가?
```

라고 생각할 수 있다.

하지만 블로그 링크를 친구에게 보내는 것만으로도

공유 미리보기를 만날 수 있다.

팀 프로젝트 주소를

```text
단체 채팅

Discord

Slack
```

등에 보내는 상황도 있다.

즉 서비스 링크를 외부에서 공유한다면

한 번쯤 확인할 가치가 있다.

실제 표시 방식은 각 플랫폼이 메타데이터를 처리하는 방식에 따라 달라질 수 있다.

---

## 프로젝트 포트폴리오에서도 사용할 수 있었다

예를 들어 내가 만든 프로젝트 주소를 누군가에게 보낸다.

미리보기가

```text
기본 프레임워크 이미지

Untitled

No description
```

처럼 보인다면

서비스 자체는 잘 만들어졌어도

첫인상에서 아쉬울 수 있다.

반대로

```text
CupPick

내 카페 혜택으로
오늘 갈 카페를 고르는 서비스

[대표 이미지]
```

처럼 나온다면

사이트에 들어가기 전에

서비스가 무엇인지 어느 정도 이해할 수 있다.

---

## 프로젝트별 OG 이미지는 앱의 한 장짜리 소개가 될 수도 있었다

예를 들어 프로젝트 OG에

```text
서비스 이름

한 줄 설명

대표 화면 일부

브랜드 심볼
```

정도만 넣으면

포트폴리오에서 링크를 공유할 때

작은 프로젝트 소개 카드 역할을 할 수 있다.

하지만

```text
기능 10개

기술 스택

GitHub 주소

개발 기간

팀원
```

을 전부 넣으려고 하면 너무 복잡해질 수 있다.

여기서도 핵심만 남기는 것이 중요하다.

---

## OG 이미지도 실제 링크로 확인해야 했다

Figma에서 이미지를 만들었다.

코드에도 연결했다.

그래도 끝이 아니다.

최종 확인은

```text
실제 배포 URL
```

을 공유해보는 것이다.

확인할 것은

```text
이미지가 나오는가?

제목이 올바른가?

설명이 너무 긴가?

이미지가 이상하게 잘리지 않는가?

이전 이미지가 캐시되어 있지는 않은가?
```

등이다.

---

## 개발자 도구에서 Meta Tag도 확인할 수 있었다

공유하기 전에 HTML 자체를 확인하는 것도 도움이 된다.

예를 들어 페이지 Source나 개발자 도구에서

```html
<meta property="og:title" ...>
<meta property="og:image" ...>
<meta property="og:description" ...>
<meta property="og:url" ...>
```

이 실제로 존재하는지 확인한다.

특히 정적 사이트 생성기를 사용한다면

Template 코드를 보는 것보다

**빌드된 최종 HTML을 확인하는 것이 중요하다.**

---

## OG 이미지 URL을 직접 열어보는 것도 간단한 확인 방법이었다

예를 들어

```html
<meta
  property="og:image"
  content="https://example.com/assets/og/design.png">
```

가 있다.

이 URL을 브라우저 주소창에 직접 입력한다.

이미지가 정상적으로 열린다면

적어도

```text
경로 오류

404

Private 접근
```

같은 기본 문제는 확인할 수 있다.

---

## OG 이미지를 수정할 때 원본도 보관하면 좋았다

파비콘과 마찬가지로

Export된 최종 이미지만 가지고 있으면

나중에 제목 위치를 바꾸기 어렵다.

그래서

```text
Figma 원본

↓

Export된 OG 이미지
```

를 구분해서 관리할 수 있다.

예를 들어

```text
design/
└─ og-template

assets/
└─ og/
   ├─ default.png
   └─ posts/
```

같은 구조다.

실제 프로젝트에 따라 달라질 수 있지만

원본과 배포 Asset을 구분한다는 생각은 도움이 됐다.

---

## 파일 이름도 관리하기 쉽게 만들고 싶었다

글이 많아지면

```text
og1.png

og2.png

final.png

final2.png
```

로 관리하면 찾기 어렵다.

예를 들어

```text
responsive-design.png

empty-state.png

figma-basic.png
```

처럼 게시글 slug와 비슷하게 만들면 관리하기 쉽다.

또는 자동 생성한다면

게시글 slug를 그대로 사용할 수 있다.

---

## 링크가 바뀌어도 이미지가 무엇인지 알 수 있게 한다

파일명만 보고

```text
이 이미지가 어느 글이지?
```

를 알 수 있으면

나중에 수정하거나 삭제할 때 편하다.

작은 파일 관리 규칙도

글이 많아질수록 중요해진다.

---

## 내가 OG 디자인을 만들 때 확인하고 싶은 것

정리하면 디자인 측면에서는 이런 것을 볼 수 있다.

```text
□ 링크를 작게 봐도 무슨 글인지 알 수 있는가?

□ 가장 중요한 제목이 잘 보이는가?

□ 작은 부가 정보가 너무 많지 않은가?

□ 블로그 이름이 제목보다 더 강하지 않은가?

□ 긴 제목에서도 Layout이 유지되는가?

□ 이미지 가장자리와 핵심 요소 사이에 충분한 여백이 있는가?

□ 일부가 잘려도 핵심 정보가 남는가?

□ 다른 게시글 OG와 같은 블로그처럼 보이는가?

□ 파비콘과 전체적인 브랜드 분위기가 연결되는가?

□ 실제 모바일 미리보기 크기에서도 읽을 수 있는가?
```

---

## 구현에서는 이런 것을 확인하고 싶었다

```text
□ og:title이 현재 페이지 제목을 사용하는가?

□ og:url이 현재 페이지의 올바른 URL인가?

□ og:image가 실제 접근 가능한 URL인가?

□ 이미지 경로가 절대 URL 형태인가?

□ og:description이 적절하게 설정되어 있는가?

□ og:type이 페이지 성격과 맞는가?

□ 기본 OG 이미지 fallback이 있는가?

□ 기존 테마의 OG 설정과 중복되지 않는가?

□ 여러 게시글에서 메타데이터가 각각 다르게 생성되는가?

□ 배포된 최종 HTML에서도 값이 정상인가?
```

---

## 운영에서는 또 다른 기준이 필요했다

```text
□ 새 글을 작성할 때 OG 작업이 너무 번거롭지 않은가?

□ 모든 글에 수동 이미지를 만들어야 하는가?

□ 공통 Template으로 해결할 수 있는가?

□ 이미지가 없을 때도 기본적으로 정상 동작하는가?

□ 제목이 긴 글을 처리할 규칙이 있는가?

□ 나중에 자동화하기 쉬운 구조인가?
```

디자인 하나를 예쁘게 만드는 것만큼

계속 운영 가능한 구조를 만드는 것도 중요했다.

---

## 내가 처음 적용한다면 이렇게 시작하고 싶다

복잡하게 시작하지 않고

```text
1. 블로그 기본 OG 이미지 하나 제작

2. Home에 기본 OG metadata 적용

3. 게시글에서는 page.title 사용

4. 게시글 설명이 있으면 description 사용

5. 개별 이미지가 없으면 기본 OG 사용

6. 실제 배포 URL 공유 테스트
```

정도로 시작한다.

그다음 필요하면

```text
7. 대표 게시글 개별 OG

8. 공통 OG Template

9. 글별 자동 이미지 생성
```

순서로 확장할 수 있다.

---

## 처음부터 모든 글의 OG 이미지를 만들 필요는 없었다

특히 이미 작성된 글이 많다면

```text
전체 글 이미지부터 만들자.
```

라고 시작하면 작업량이 매우 커질 수 있다.

우선 기본 이미지가 모든 글에 나오게 만든다.

그러면 최소 기준은 충족된다.

그다음

```text
새 글부터

대표 글부터

프로젝트 글부터
```

천천히 개별 OG를 적용할 수 있다.

블로그를 계속 운영해야 하기 때문에

기존 글 전체를 한 번에 완벽하게 바꾸는 것보다 현실적인 방법일 수 있다.

---

## OG를 공부하면서 또 알게 된 것

처음에는

```text
OG 이미지
=
SNS에 보이는 큰 사진
```

정도로 생각했다.

하지만 실제로는

```text
Title

Description

URL

Image

Page Type
```

등이 함께 하나의 링크 정보를 만든다.

그래서 이것은 이미지 파일 하나의 문제가 아니라

**페이지가 외부에서 어떻게 소개되는지를 설계하는 일**

에 더 가까웠다.

---

## Favicon과 OG Image의 차이

「파비콘까지가 디자인이다」와 연결하면 이렇게 정리할 수 있다.

### Favicon

```text
목적
→ 사이트 식별

위치
→ 브라우저 탭 / 북마크 등

특징
→ 매우 작음
→ 단순해야 함
```

### OG Image

```text
목적
→ 공유된 페이지 소개

위치
→ 링크 미리보기

특징
→ 상대적으로 큼
→ 페이지의 내용까지 표현 가능
```

둘 다 사이트 화면 밖에서 보인다.

하지만 역할은 다르다.

---

## 둘을 같이 디자인하면 브랜드가 연결됐다

예를 들어 파비콘에

```text
갈색 원형 심볼
```

을 사용했다고 해 보자.

OG 이미지에서도

같은 심볼과 색상을 사용한다.

```text
Favicon
→ ●

OG
→ ● + MY-BLOG + 게시글 제목
```

그러면

```text
브라우저 탭

링크 공유

실제 블로그
```

가 조금씩 연결된다.

작은 디자인 시스템이 생기는 것이다.

---

## 이것이 거창한 브랜딩이어야 하는 것은 아니었다

개인 개발 블로그라고 해서

전문 브랜드 회사처럼

```text
Brand Guideline 100page
```

를 만들 필요는 없다.

간단하게

```text
대표 색상

심볼 하나

글꼴 스타일

이미지 Layout
```

정도만 일정하게 사용해도 된다.

중요한 것은

```text
내 사이트라는 느낌
```

을 조금씩 일관되게 만드는 것이다.

---

## 작은 디자인 디테일이 하나씩 연결되기 시작했다

처음에는 각각 별개의 작업처럼 보였다.

```text
Favicon

OG Image

Empty State

Button

Loading
```

하지만 계속 공부하다 보니

모두 같은 질문으로 연결됐다.

```text
사용자는 지금 무엇을 보고 있는가?

그것만 보고 현재 상황을 이해할 수 있는가?

다음 행동이나 대상이 명확한가?

서비스 전체와 일관성이 있는가?
```

디자인의 크기만 다를 뿐이었다.

## 내가 OG 이미지와 링크 공유에서 지키고 싶은 기준

마지막으로 정리하면 다음과 같다.

```text
1. 링크 공유 미리보기도 하나의 사용자 접점으로 생각한다.

2. 기본 OG 이미지를 준비한다.

3. 페이지 제목과 설명을 적절한 Meta Tag로 제공한다.

4. OG 이미지는 페이지를 대표할 수 있게 만든다.

5. 이미지 안에 정보를 너무 많이 넣지 않는다.

6. 게시글 제목을 가장 중요한 정보로 둔다.

7. 긴 제목에서도 디자인이 깨지지 않게 한다.

8. 이미지 가장자리에 핵심 정보를 붙이지 않는다.

9. 플랫폼마다 표시 방식이 다를 수 있음을 고려한다.

10. 개별 이미지가 없을 때 사용할 fallback을 만든다.

11. 글이 많다면 운영 비용을 고려한다.

12. 필요하면 Template이나 자동화를 사용한다.

13. 기존 SEO / OG 설정을 먼저 확인하고 중복 구현하지 않는다.

14. 실제 배포된 HTML에서 Meta Tag를 확인한다.

15. 최종적으로 실제 URL을 공유해서 확인한다.
```

## 마무리

처음에는 링크를 공유한다는 것을

```text
URL 복사

↓

붙여넣기

↓

끝
```

이라고 생각했다.

하지만 링크를 받은 사람에게는

그 URL 주변에 나타나는 미리보기가

사이트를 처음 만나는 순간일 수도 있었다.

```text
대표 이미지

제목

설명

사이트 이름
```

을 보고

```text
어떤 사이트인지

무슨 글인지

눌러볼지
```

를 판단한다.

그래서 OG 이미지는 단순히

```text
공유할 때 예쁘게 나오는 사진
```

이 아니었다.

> **페이지 밖에서 그 페이지가 어떻게 소개될 것인지를 디자인하는 작업**

에 더 가까웠다.

파비콘을 만들면서는

```text
브라우저 탭까지 디자인의 일부구나.
```

라고 생각했다.

OG 이미지를 공부하면서는

한 단계 더 나아갔다.

```text
링크가 다른 서비스로 나간 뒤에도
내 디자인의 일부가 남는구나.
```

라는 것을 알게 됐다.

그리고 이런 작은 부분을 하나씩 확인하다 보니

아직도 놓치기 쉬운 UI가 많았다.

```text
버튼을 눌렀을 때의 상태

Loading

Hover

Focus

Disabled

Toast

Error Message

긴 텍스트

스크롤

아이콘의 미세한 정렬
```

각각은 작은 부분이다.

기능 구현만 놓고 보면

없어도 서비스가 어느 정도 돌아갈 수 있다.

하지만 이런 작은 차이가 계속 쌓이면

```text
뭔가 어색한 서비스
```

와

```text
세세한 부분까지 정리된 서비스
```

의 차이가 될 수 있다.
