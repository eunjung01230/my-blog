블로그에 글이 쌓이면서 한동안 꼭 만들고 싶었던 기능이 있었다.

**블로그 안에서 직접 포스트를 추가하고 수정할 수 있는 관리자 기능**이었다.

처음에는 포스트를 수정하려면 프로젝트를 열고 원본 파일을 찾아 내용을 바꾼 뒤 Git에 반영하는 방식으로 관리했다.

개발 블로그를 직접 만드는 입장에서는 익숙한 과정이지만, 오타 하나나 날짜 하나를 수정할 때도 개발 환경을 열어야 한다는 점은 조금 번거로웠다.

그래서 처음에는 아주 단순하게 생각했다.

> 관리자만 사용할 수 있는 버튼을 만들고, 블로그 안에서 글을 수정하면 되지 않을까?

화면만 생각하면 어렵지 않아 보였다.

하지만 구조를 하나씩 확인하면서 이 기능은 예상했던 것보다 훨씬 큰 작업이라는 것을 알게 됐다.

그리고 결국 이 시점에서는 **관리자 기능을 만들지 않기로 했다.**

기능 구현에 실패한 것이 아니라, 현재 블로그 구조와 필요한 작업량을 확인한 뒤 **지금 만들 필요가 없다고 판단한 것**에 가까웠다.

---

## 시작은 정말 단순했다

처음 원했던 모습은 복잡하지 않았다.

포스트 페이지에는 수정 버튼이 있고,

글 목록에는 포스트 추가 버튼이 있고,

필요하면 날짜나 제목도 변경할 수 있는 정도였다.

예를 들면 이런 흐름이었다.

```text
포스트 확인
    ↓
관리자 수정 버튼
    ↓
제목 / 날짜 / 본문 수정
    ↓
저장
```

지금처럼 VS Code를 열고 파일을 찾지 않아도 블로그를 보면서 바로 수정할 수 있다면 훨씬 편할 것 같았다.

관리자만 사용할 수 있도록 간단한 코드나 비밀번호를 입력하는 방식도 처음에는 생각했다.

이 정도만 보면 작은 편의 기능처럼 보였다.

---

## 그런데 '저장'에서 바로 막혔다

수정 화면을 만드는 것 자체는 큰 문제가 아니었다.

입력창을 만들고 기존 제목과 내용을 표시한 뒤 수정하게 할 수 있다.

문제는 그다음이었다.

> 저장 버튼을 누르면 수정한 내용을 어디에 저장하지?

내 블로그의 포스트는 데이터베이스에서 불러오는 것이 아니었다.

프로젝트 안에 있는 포스트 파일이 원본이고, GitHub Pages가 그 파일을 바탕으로 사이트를 만들어 보여주는 구조였다.

즉,

```text
포스트 파일
    ↓
GitHub
    ↓
빌드 / 배포
    ↓
블로그 화면
```

이라는 방향이었다.

블로그 화면은 포스트의 원본이 아니었다.

이미 만들어진 결과였다.

브라우저에서 내용을 바꾼다고 원본 파일이 자동으로 수정되는 것은 아니었다.

여기에서부터 생각했던 관리자 기능의 규모가 달라지기 시작했다.

---

## 화면에서 수정하는 것과 원본을 수정하는 것은 달랐다

처음에는 관리자 페이지에서 글을 수정하면 당연히 블로그 글도 수정될 것처럼 생각했다.

하지만 실제로는 두 가지를 구분해야 했다.

```text
화면에서 입력값을 바꾼다
```

와

```text
실제 포스트 원본을 바꾼다
```

는 전혀 다른 문제였다.

브라우저에서 입력한 값은 페이지를 새로고침하면 사라질 수 있다.

영구적으로 저장하려면 그 데이터를 받아서 보관할 곳이 필요하다.

현재 구조를 그대로 유지한다면 결국 GitHub에 있는 원본 포스트 파일을 수정하는 방법이 필요하고,

다른 구조로 바꾼다면 별도의 데이터베이스에 포스트를 저장하는 방식까지 생각해야 했다.

단순히 `수정 버튼`을 만드는 문제에서 갑자기 **데이터를 어디에서 관리할 것인가**라는 문제로 넘어갔다.

---

## 관리자 비밀번호도 화면에 넣는다고 해결되는 문제가 아니었다

다음으로 생각한 것은 관리자 인증이었다.

나만 사용하는 블로그이니 간단한 관리자 코드를 하나 만들면 되지 않을까 싶었다.

예를 들어 특정 값을 입력했을 때 수정 버튼을 보여주는 방식이다.

하지만 이 역시 제대로 만들려면 문제가 있었다.

프론트엔드 코드에서 관리자 비밀번호를 직접 비교하면 그 값 역시 사용자에게 전달되는 코드 안에 들어갈 수 있다.

화면에서 버튼을 숨긴다고 해서 실제 권한까지 안전하게 보호되는 것도 아니다.

이 차이가 중요했다.

```text
수정 버튼을 숨긴다
≠
수정 권한을 보호한다
```

정말 관리자만 데이터를 변경할 수 있게 만들려면 인증과 권한 확인이 필요했다.

그리고 이런 중요한 검증을 브라우저에만 맡기기보다는 서버 쪽에서 처리하는 구조가 필요했다.

관리자 기능에 갑자기 백엔드 이야기가 등장한 이유였다.

---

## 제대로 만들려면 필요한 것이 생각보다 많았다

하나씩 확인해 보니 관리자 기능에는 최소한 다음과 같은 문제가 연결되어 있었다.

```text
관리자 인증
      ↓
수정할 포스트 불러오기
      ↓
내용 편집
      ↓
수정 데이터 저장
      ↓
권한 확인
      ↓
블로그에 반영
```

그리고 여기에서 또 질문이 생긴다.

포스트는 계속 Markdown 파일로 관리할 것인가?

데이터베이스로 옮길 것인가?

GitHub 파일을 직접 수정한다면 어떤 방식으로 연결할 것인가?

잘못 수정했을 때는 어떻게 되돌릴 것인가?

관리자 인증 정보는 어디에서 관리할 것인가?

이쯤 되니 관리자 기능은 더 이상 작은 버튼 하나가 아니었다.

**작은 CMS(Content Management System)를 만드는 것에 가까워지고 있었다.**

---

## 데이터베이스를 붙이는 방법도 생각했다

관리자 기능을 제대로 만들려면 DB를 연결하는 방법도 생각할 수 있었다.

포스트 내용을 데이터베이스에서 관리한다면 관리자 화면에서 데이터를 불러와 수정하고 다시 저장하는 구조를 만들 수 있다.

인증된 관리자만 수정 API를 사용할 수 있도록 하는 방식도 가능하다.

하지만 문제가 하나 있었다.

현재 내 블로그는 이미 파일 기반으로 잘 돌아가고 있었다.

글을 작성하고,

Git으로 변경 이력을 남기고,

push하면 자동으로 배포되는 구조가 있었다.

관리자 기능 하나를 위해 포스트 관리 구조 전체를 DB 중심으로 바꾸면 오히려 일이 훨씬 커질 수 있었다.

DB가 생기면 DB만 추가되는 것도 아니다.

인증,

API,

환경 변수,

보안,

배포 환경,

데이터 구조까지 같이 관리해야 한다.

그 순간 질문이 바뀌었다.

> 관리자 기능을 만들 수 있는가?

가 아니라

> **이 기능 때문에 지금 이 정도 구조까지 필요한가?**

였다.

---

## 지금 가진 방식도 생각보다 나쁘지 않았다

관리자 기능을 고민하면서 오히려 현재 방식의 장점도 다시 보게 됐다.

포스트가 파일로 남아 있기 때문에 구조가 단순했다.

Git에서 어떤 글이 어떻게 수정됐는지도 볼 수 있다.

잘못 변경했다면 이전 커밋을 확인할 수도 있다.

Claude를 사용하면 내가 직접 파일을 일일이 찾는 부담도 많이 줄어들었다.

예전에는

```text
파일 찾기
→ 수정 위치 찾기
→ 직접 수정
```

해야 했다면 지금은 Claude에게 수정할 포스트와 내용을 알려주고 변경된 결과를 확인하는 방법도 사용할 수 있었다.

물론 블로그 안에서 바로 수정하는 것보다는 단계가 하나 더 있다.

하지만 이 불편함을 없애기 위해 관리자 시스템 전체를 만드는 것이 지금 필요한지는 별개의 문제였다.

---

## 편리함 하나를 위해 복잡도를 크게 늘리고 있었다

여기에서 내가 만들려던 기능을 다시 봤다.

관리자 기능이 있으면 분명 편하다.

하지만 실제로 해결하려던 문제는 무엇이었을까.

대부분

오타 수정,

글 일부 수정,

새 포스트 추가,

날짜나 카테고리 변경

정도였다.

현재 방법으로도 할 수 없는 작업은 아니었다.

조금 번거로울 뿐이었다.

반면 관리자 기능을 제대로 만들면 앞으로 관리해야 할 것이 크게 늘어난다.

```text
얻는 것
→ 글 관리가 조금 더 편해짐

추가되는 것
→ 인증
→ 권한
→ 저장 구조
→ DB 또는 GitHub 연동
→ 보안
→ 유지보수
```

비교해 보니 이 시점에서는 비용이 더 크게 느껴졌다.

---

## 기능이 좋아 보여도 우선순위는 따로 판단해야 했다

처음에는 관리자 기능이 있으면 블로그가 훨씬 완성된 서비스처럼 보일 것 같았다.

직접 만든 관리자 화면에서 포스트를 관리하면 재미있을 것 같기도 했다.

하지만 프로젝트를 하면서 점점 **만들 수 있다는 것과 지금 만들어야 한다는 것은 다르다**는 것을 느끼고 있었다.

관리자 기능을 만드는 동안 다른 중요한 작업은 멈춘다.

아직 정리해야 할 포스트도 있었고,

검색이나 정렬처럼 실제 블로그를 사용하는 데 더 직접적인 기능도 생각하고 있었다.

DB 연결까지 시작하면 블로그 관리 기능 하나가 별도의 프로젝트처럼 커질 수도 있었다.

그래서 우선순위를 다시 잡았다.

지금 당장 없어도 블로그를 운영할 수 있는 기능이라면 잠시 미뤄도 된다.

---

## 결국 관리자 기능은 만들지 않았다

처음에는 관리자 코드를 입력하고 글을 수정할 수 있는 기능을 만들고 싶었다.

구조를 분석하면서 인증과 저장 방식도 생각했다.

DB를 연결해야 하는 상황까지 검토했다.

하지만 결국 실제 구현까지 진행하지 않았다.

이유는 단순했다.

**현재 블로그에서 해결하려는 문제에 비해 구현 비용이 너무 컸기 때문이다.**

지금도 포스트를 수정할 수 있다.

Git으로 변경 내역도 관리할 수 있다.

Claude를 활용하면 수정 과정의 번거로움도 줄일 수 있다.

그 상태에서 관리자 기능을 추가하기 위해 블로그의 데이터 구조까지 크게 바꾸는 것은 지금 단계에서는 필요하지 않았다.

그래서 관리자 기능은 구현하는 대신 **나중에 정말 필요한 시점에 다시 검토할 기능**으로 남겨두기로 했다.

---

## 안 만든 기능에서도 배울 것은 있었다

결과적으로 코드로 완성된 기능은 없었다.

하지만 이 과정을 의미 없는 작업이라고 생각하지는 않는다.

오히려 기능 하나를 만들기 전에 구조를 확인하는 경험이 됐다.

처음에는 화면에 버튼 하나 추가하는 문제라고 생각했다.

하지만 실제로는

```text
UI
→ 인증
→ 권한
→ 데이터 저장
→ 백엔드
→ 배포 구조
```

까지 연결될 수 있었다.

덕분에 서비스에서 보이는 화면 뒤에 어떤 구조가 필요한지 조금 더 구체적으로 이해할 수 있었다.

특히

**사용자가 데이터를 수정할 수 있는 순간부터 저장과 권한 문제가 시작된다**

는 것이 기억에 남았다.

---

## '안 만드는 것'도 하나의 개발 결정이었다

예전에는 아이디어가 생겼는데 구현하지 않으면 작업을 포기한 것처럼 느껴질 때도 있었다.

하지만 이번에는 조금 달랐다.

관리자 기능이 필요하다고 생각해서 구조를 확인했다.

현재 블로그 방식으로 어디까지 가능한지 알아봤다.

필요한 기술과 작업 범위를 확인했다.

그리고 현재 우선순위와 비교해 구현하지 않기로 결정했다.

이 과정 자체도 하나의 개발 판단이었다.

기능을 많이 만드는 것이 항상 좋은 프로젝트를 만드는 것은 아니다.

특히 혼자 관리하는 프로젝트에서는 추가하는 순간부터 그 기능을 계속 관리해야 한다.

그래서 이제는 새로운 기능을 볼 때

> 구현할 수 있는가?

다음에 한 가지를 더 생각하게 됐다.

> **지금 이 기능을 유지할 가치가 있는가?**

---

## 관리자 기능을 고민하며 얻은 가장 큰 결론

처음에는 블로그 안에서 글을 바로 수정할 수 있다면 훨씬 편할 것이라고 생각했다.

그 생각 자체는 지금도 같다.

언젠가 글이 훨씬 많아지고 파일 기반 관리가 실제로 큰 부담이 된다면 관리자 기능이 필요해질 수도 있다.

그때는 인증과 데이터베이스까지 포함해서 제대로 설계하는 편이 맞을 것이다.

하지만 지금은 아니었다.

현재 방식으로 충분히 운영할 수 있는데 미래의 편의를 예상해서 구조를 먼저 복잡하게 만들 필요는 없었다.

이번에 관리자 기능을 결국 만들지 않으면서 오히려 하나의 기준이 생겼다.

> **필요해 보이는 기능을 바로 만드는 것이 아니라, 현재의 불편함이 그 기능의 복잡도를 감당할 만큼 큰지 먼저 확인한다.**

블로그를 발전시키면서 기능을 추가하는 법만 배운 것이 아니었다.

어떤 기능은 지금 만들고,

어떤 기능은 나중으로 미루고,

어떤 기능은 아예 만들지 않는 판단도 필요했다.

관리자 기능은 실제 블로그에는 남지 않았다.

대신 **기능을 구현하기 전에 구조와 비용을 먼저 보는 습관**이 남았다.

결국 이번 작업에서 가장 중요한 결과는 관리자 페이지가 아니라, **만들지 않는 선택에도 이유가 필요하다는 것을 알게 된 것**이었다.
