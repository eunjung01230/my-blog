Figma를 배우고 Figma Make까지 사용해보면서 화면을 만드는 속도는 확실히 빨라졌다.

그런데 또 다른 문제가 생겼다.

```text
어떤 화면이 좋은 화면이지?
```

직접 디자인을 만들려고 하면 생각보다 막막했다.

버튼을 어디에 둬야 하는지,

카드는 어떻게 나눠야 하는지,

정보를 어떤 순서로 보여줘야 하는지,

전체 화면을 얼마나 단순하게 만들어야 하는지

기준이 잘 없었다.

그래서 자연스럽게 다른 서비스의 화면을 찾아보기 시작했다.

처음에는 단순했다.

```text
예쁜 앱 디자인

깔끔한 웹 디자인

모바일 UI

대시보드 디자인
```

같은 키워드로 검색하고 마음에 드는 화면을 저장했다.

그런데 어느 순간 문제가 생겼다.

레퍼런스를 많이 모았는데도

```text
그래서 내 화면은 어떻게 만들어야 하지?
```

라는 질문은 그대로였다.

그때부터 단순히 레퍼런스를 **보는 것**과 **분석하는 것**은 다르다는 것을 알게 됐다.

---

## 처음에는 그냥 예쁜 화면을 찾았다

디자인을 처음 공부할 때 가장 먼저 눈에 들어오는 것은 아무래도 전체 분위기다.

```text
색상이 예쁘다.

카드가 깔끔하다.

아이콘이 세련됐다.

여백이 넓어서 보기 좋다.
```

그래서 나도 처음에는 이런 기준으로 레퍼런스를 저장했다.

하지만 프로젝트에 실제로 적용하려고 하면 생각보다 도움이 되지 않았다.

예를 들어 멋진 금융 앱 화면을 봤다고 해보자.

디자인은 마음에 든다.

하지만 내가 만드는 서비스는 카페 혜택 관리 서비스일 수도 있고,

러닝 기록 서비스일 수도 있다.

그대로 가져올 수는 없다.

그때 알게 됐다.

```text
예쁜 디자인
≠
내 서비스에 필요한 디자인
```

이라는 것을.

---

## 레퍼런스는 정답지가 아니었다

처음에는 좋은 레퍼런스를 찾으면 그대로 따라 만들면 될 것 같았다.

하지만 실제 프로젝트에서는 그렇게 단순하지 않았다.

서비스마다 목적이 다르기 때문이다.

예를 들어 쇼핑 앱의 홈 화면은

```text
상품 노출

추천

이벤트

카테고리

검색
```

이 중요할 수 있다.

반면 러닝 앱의 홈 화면은

```text
현재 상태

러닝 시작

거리

위치
```

가 더 중요할 수 있다.

그래서 화면이 아무리 예뻐도 서비스 목적이 다르면 구조까지 그대로 가져오는 것은 맞지 않았다.

결국 레퍼런스는

```text
이 화면을 그대로 만들어야 한다.
```

가 아니라

```text
이 화면에서는 무엇을 배울 수 있을까?
```

라는 관점으로 봐야 했다.

---

## 레퍼런스를 볼 때 질문을 바꿨다

예전에는 화면을 보고 이렇게 생각했다.

```text
예쁘다.

깔끔하다.

이 스타일 좋다.
```

지금은 조금 다른 질문을 하려고 한다.

```text
왜 이 정보가 가장 위에 있을까?

왜 이 버튼만 크게 만들었을까?

왜 이 화면에는 버튼이 하나밖에 없을까?

왜 이 정보는 카드 안에 들어가 있을까?

왜 이 메뉴는 아래쪽에 있을까?

왜 이 화면은 여백이 이렇게 넓을까?
```

이 질문을 하기 시작하면 화면이 조금 다르게 보인다.

단순한 이미지가 아니라

**누군가가 여러 선택을 한 결과**

처럼 보이기 시작한다.

---

## 가장 먼저 보는 것은 화면의 목적

레퍼런스를 분석할 때 가장 먼저 확인하려고 하는 것은

```text
이 화면에서 사용자가 무엇을 해야 하는가?
```

다.

예를 들어 로그인 화면이라면 목적은 명확하다.

```text
로그인하기
```

그런데 화면 안에

```text
로그인

회원가입

비밀번호 찾기

소셜 로그인

서비스 설명

이벤트 배너

공지사항
```

이 모두 비슷하게 강조되어 있다면 사용자는 어디부터 봐야 할지 헷갈릴 수 있다.

반대로 잘 정리된 화면은 보통

```text
가장 중요한 행동
```

이 눈에 먼저 들어온다.

그래서 레퍼런스를 볼 때도

```text
이 화면의 1순위 행동은 무엇인가?
```

를 먼저 찾는다.

---

## 두 번째는 정보의 순서

화면 안에는 여러 정보가 있다.

그런데 모든 정보를 똑같이 보여주지는 않는다.

보통 중요한 정보는

```text
크게

위쪽에

강한 대비로
```

보여준다.

덜 중요한 정보는

```text
작게

아래쪽에

약한 색상으로
```

표현하는 경우가 많다.

예를 들어 러닝 결과 화면이라면

```text
총 거리

시간

평균 페이스

세부 기록
```

이 있다고 해보자.

서비스가 거리 기록을 가장 중요하게 본다면

```text
총 거리
```

가 가장 크게 보일 가능성이 높다.

이런 구조를 보면서

```text
무엇을 먼저 보여줄지
```

가 단순한 디자인 문제가 아니라 서비스의 우선순위라는 것을 알게 됐다.

---

## 세 번째는 화면을 어떻게 묶었는지 본다

UI를 처음 만들 때는 정보를 그냥 위에서 아래로 나열하기 쉽다.

```text
제목

설명

거리

시간

혜택

버튼

메모
```

하지만 실제 서비스 화면을 보면 관련 있는 정보끼리 묶여 있다.

예를 들어

```text
사용자 정보

카페 정보

혜택 정보

행동 버튼
```

처럼 구역이 나뉘어 있다.

카드를 사용하는 이유도 이와 비슷하다.

단순히 화면을 예쁘게 만들기 위해서가 아니라

```text
이 정보들은 서로 관련 있다.
```

는 것을 보여주는 역할도 한다.

그래서 레퍼런스를 볼 때

```text
어디서 영역이 나뉘는지

어떤 정보끼리 한 카드에 들어가는지
```

를 보려고 한다.

---

## 버튼의 개수와 크기도 본다

예전에는 버튼 디자인을 볼 때 주로 색상을 봤다.

```text
파란색 버튼

검은색 버튼

둥근 버튼
```

정도였다.

하지만 레퍼런스를 분석하면서 중요한 것은 색상보다 **우선순위**라는 것을 알게 됐다.

예를 들어 화면에 버튼이 세 개 있다고 해보자.

```text
저장

삭제

취소
```

세 버튼이 모두 크고 강한 색이면

```text
뭘 눌러야 하지?
```

가 된다.

반대로

```text
저장
```

만 강하게 보이고

```text
삭제

취소
```

는 덜 강조되어 있다면 사용자의 행동이 명확해진다.

그래서 레퍼런스를 볼 때

```text
가장 큰 버튼은 무엇인지

강조 버튼은 몇 개인지

보조 행동은 어떻게 표현했는지
```

도 같이 확인한다.

---

## 빈 공간도 디자인이었다

처음에는 빈 공간을 보면 이렇게 생각했다.

```text
여기 뭔가 더 넣어야 하지 않나?
```

화면이 비어 있으면 괜히 부족해 보였다.

그래서

```text
버튼 하나 더

설명 하나 더

아이콘 하나 더
```

를 넣고 싶어졌다.

하지만 레퍼런스를 많이 보다 보니 오히려 잘 만든 화면일수록 빈 공간을 적극적으로 사용하는 경우가 많았다.

```text
제목

        여백

핵심 정보

        여백

버튼
```

이런 구조다.

여백 덕분에 중요한 정보가 더 눈에 들어온다.

그래서 이제는 빈 공간을

```text
아무것도 없는 공간
```

이 아니라

```text
정보를 구분하는 공간
```

으로 보려고 한다.

---

## 레퍼런스 하나만 보지 않으려고 한다

마음에 드는 화면을 하나 찾으면 그대로 따라가고 싶어진다.

하지만 하나만 보면 문제가 생긴다.

```text
이 구조가 일반적인가?

아니면 이 서비스만의 특징인가?
```

를 알기 어렵기 때문이다.

그래서 같은 종류의 화면을 여러 개 보는 편이 좋았다.

예를 들어 로그인 화면이라면

```text
서비스 A 로그인

서비스 B 로그인

서비스 C 로그인
```

을 같이 본다.

그러면 반복해서 나타나는 패턴이 보인다.

```text
로고

입력창

주요 로그인 버튼

소셜 로그인

회원가입
```

이런 식이다.

반대로 특정 서비스에만 있는 요소도 보인다.

```text
이벤트 배너

추천 코드

특별 안내
```

그러면

```text
공통적으로 필요한 요소
```

와

```text
특정 서비스만 필요한 요소
```

를 구분할 수 있다.

---

## 같은 서비스의 여러 화면도 같이 본다

한 화면만 보고 디자인을 참고하면 전체 서비스의 일관성을 놓치기 쉽다.

예를 들어 홈 화면만 보면

```text
카드 디자인 예쁘다.
```

정도로 끝날 수 있다.

하지만

```text
홈

상세

설정

프로필
```

을 같이 보면 반복되는 규칙이 보인다.

```text
같은 버튼 모양

같은 카드 모서리

같은 제목 크기

같은 여백

같은 아이콘 스타일
```

이런 것을 통해

```text
디자인 시스템
```

이라는 개념도 조금씩 이해하게 됐다.

좋은 화면 하나보다

**여러 화면에서 같은 규칙이 유지되는 것**

도 중요했다.

---

## 레퍼런스는 기능별로 찾는 것이 좋았다

처음에는

```text
예쁜 앱 디자인
```

처럼 너무 넓게 검색했다.

그러면 정말 다양한 디자인이 나온다.

문제는 내 화면과 연결하기 어렵다는 것이다.

그래서 이제는 기능을 기준으로 찾는 편이 더 좋다고 생각한다.

예를 들어

```text
mobile login UI

map app UI

running app result screen

coupon wallet UI

empty state mobile

settings screen UI
```

처럼 찾는 것이다.

이렇게 하면

```text
내가 지금 만들 화면
```

과 비슷한 목적을 가진 사례를 볼 수 있다.

---

## 스타일 레퍼런스와 구조 레퍼런스를 나눠본다

이것도 꽤 중요했다.

레퍼런스를 보면 모든 것을 한 화면에서 가져오려고 하기 쉽다.

하지만 나는 점점

```text
구조

스타일
```

을 나눠서 보게 됐다.

예를 들어 A 서비스에서는

```text
카드 배치 구조
```

가 마음에 들고,

B 서비스에서는

```text
색상과 타이포
```

가 마음에 들 수 있다.

C 서비스에서는

```text
버튼 우선순위
```

가 좋을 수도 있다.

그러면

```text
A의 구조

+

B의 분위기

+

C의 버튼 우선순위
```

처럼 참고할 수 있다.

이게 한 서비스를 통째로 따라 하는 것보다 훨씬 유용했다.

---

## 레퍼런스를 그대로 복사하지 않는 이유

레퍼런스를 참고할 때 가장 조심해야 하는 부분이다.

참고와 복사는 다르다.

예를 들어 어떤 서비스에서

```text
검은 배경

큰 흰색 숫자

네온 색 버튼

둥근 카드
```

를 사용한다고 해서 그대로 가져오면 결과적으로 매우 비슷한 화면이 될 수 있다.

그래서 내가 가져오려는 것이 무엇인지 명확하게 구분하려고 한다.

예를 들어

```text
큰 숫자를 통해 핵심 정보를 먼저 보여준다.
```

라는 원칙을 참고하는 것과

```text
폰트 크기

위치

색상

카드 형태
```

까지 그대로 복사하는 것은 다르다.

좋은 레퍼런스를 본다면

```text
무엇을 만들었는가
```

보다

```text
왜 이렇게 만들었는가
```

를 가져오는 것이 좋다고 생각한다.

---

## 내가 레퍼런스를 저장할 때 분류하고 싶은 기준

레퍼런스를 무작정 저장하기 시작하면 나중에 다시 찾기 어렵다.

```text
이거 왜 저장했지?
```

가 된다.

그래서 가능하면 저장할 때 이유를 같이 남기는 것이 좋았다.

예를 들면

```text
홈 화면
- 정보 우선순위 참고

지도 화면
- 하단 카드 구조 참고

로그인
- 소셜 로그인 배치 참고

설정
- 메뉴 간격 참고

Empty State
- 안내 문구와 버튼 위치 참고
```

처럼 남긴다.

그냥

```text
예뻐서 저장
```

보다 훨씬 활용하기 쉽다.

---

## 실제 프로젝트에서는 먼저 필요한 화면부터 찾는다

프로젝트를 시작했다고 해서 처음부터 레퍼런스를 수십 개 찾을 필요는 없었다.

오히려 화면 하나를 만들 때마다 필요한 사례를 찾는 방식이 편했다.

예를 들어 현재 만들어야 할 화면이

```text
혜택 목록
```

이라면

```text
wallet app

coupon list

membership card UI
```

등을 찾아본다.

그다음 상세 화면으로 넘어가면

```text
coupon detail UI

membership detail screen
```

을 찾는다.

이렇게 하면 레퍼런스 수집 자체가 별도 일이 되는 것을 줄일 수 있다.

---

## AI에게 레퍼런스를 줄 때도 기준이 필요했다

Figma Make나 다른 AI 디자인 도구를 사용할 때도 레퍼런스를 활용할 수 있다.

처음에는 그냥 이미지를 주고

```text
이런 느낌으로 만들어줘.
```

라고 하면 될 것 같았다.

하지만 이 표현은 생각보다 모호하다.

```text
무엇이 이런 느낌인지?
```

AI가 판단해야 하기 때문이다.

예를 들어 나는

```text
카드 구조
```

를 참고하고 싶었는데 AI는

```text
색상
```

만 따라 할 수도 있다.

그래서 더 구체적으로 설명하는 편이 낫다.

```text
이 화면에서 색상은 참고하지 말고,
카드의 정보 구조와
하단 버튼 배치만 참고해줘.
```

또는

```text
전체 레이아웃은 현재 디자인을 유지하고,
첨부한 레퍼런스처럼
주요 숫자 정보만 크게 강조해줘.
```

같은 방식이다.

이렇게 하면 레퍼런스를

```text
복사 대상
```

이 아니라

```text
특정 문제를 해결하기 위한 참고 자료
```

로 사용할 수 있다.

---

## 여러 레퍼런스를 AI에게 줄 때도 역할을 나눈다

예를 들어 세 개의 화면을 참고한다고 해보자.

그냥

```text
이 세 개 참고해서 만들어줘.
```

라고 하면 AI가 세 디자인을 임의로 섞을 수 있다.

대신

```text
레퍼런스 A
→ 전체 화면 구조 참고

레퍼런스 B
→ 카드 디자인 참고

레퍼런스 C
→ 버튼 배치 참고
```

처럼 역할을 나누는 것이 낫다.

그러면 내가 무엇을 원하는지도 더 명확해진다.

사실 이 과정에서 중요한 것은 AI보다도

```text
내가 레퍼런스를 제대로 분석했는가?
```

였다.

---

## 레퍼런스와 내 기획이 충돌하면 기획이 먼저다

프로젝트를 하다 보면 정말 예쁜 화면을 발견할 때가 있다.

그러면 넣고 싶어진다.

```text
이 카드 좋다.

이 탭도 넣고 싶다.

이 필터도 좋다.

이 화면도 있으면 좋겠다.
```

하지만 원래 서비스에 필요하지 않았던 기능이라면 문제가 된다.

예를 들어 내가 만들고 있는 MVP에는

```text
즐겨찾기
```

가 없는데,

레퍼런스 앱에 즐겨찾기 버튼이 자연스럽게 있다고 해서 추가할 필요는 없다.

이걸 계속 반복하면

```text
레퍼런스 참고
↓
기능 추가
↓
또 다른 레퍼런스
↓
또 기능 추가
```

가 된다.

결국 디자인 레퍼런스가 기획을 끌고 가게 된다.

그래서 기준은 항상

```text
내 서비스에 필요한가?
```

가 먼저여야 했다.

---

## 실제 화면을 따라 만들어보는 것도 공부가 됐다

레퍼런스를 분석하는 방법 중 하나는 직접 따라 만들어보는 것이다.

상업적으로 그대로 사용하는 것이 아니라

```text
연습용
```

으로 한 화면을 똑같이 만들어본다.

직접 만들기 시작하면 그냥 볼 때는 몰랐던 것이 보인다.

```text
여백이 생각보다 크네.

글자 크기 차이가 크네.

카드 내부 Padding이 일정하네.

버튼 높이가 전부 같네.

색상 종류가 별로 없네.
```

단순히 화면을 보는 것보다 직접 Figma에서 만들어보면 훨씬 구체적으로 이해할 수 있다.

그래서 초반에는 좋아하는 화면 하나를 정해서

```text
분석

↓

Figma로 따라 만들기

↓

원본과 비교
```

하는 것도 좋은 연습이라고 생각한다.

---

## 내가 화면을 분석할 때 보는 순서

지금 기준으로 레퍼런스를 하나 보면 대략 이런 순서로 확인하려고 한다.

```text
1. 이 화면의 목적은 무엇인가?

2. 사용자가 가장 먼저 해야 하는 행동은 무엇인가?

3. 가장 먼저 보이는 정보는 무엇인가?

4. 정보가 어떤 그룹으로 묶여 있는가?

5. 가장 강조된 버튼은 무엇인가?

6. 보조 행동은 어떻게 표현되어 있는가?

7. 여백은 어떻게 사용했는가?

8. 반복되는 UI 규칙은 무엇인가?

9. 다른 화면에서도 같은 규칙이 유지되는가?

10. 내 서비스에 가져올 수 있는 원칙은 무엇인가?
```

이 정도만 생각해도

```text
예쁘다.
```

에서 끝나지 않는다.

---

## 레퍼런스를 볼 때 기록해두면 좋은 것

나는 다음처럼 간단하게 기록하는 방식이 좋다고 생각한다.

```text
[레퍼런스]

화면:
홈

좋았던 점:
핵심 기능 버튼이 바로 보임

참고할 부분:
버튼 우선순위
카드 간격

참고하지 않을 부분:
색상
하단 탭 구조

내 프로젝트 적용:
시작 버튼을 다른 기능보다 더 강조
```

이렇게 적어두면 나중에 다시 봤을 때도

```text
왜 저장했는지
```

바로 알 수 있다.

---

## 예쁜 화면을 많이 보는 것만으로는 부족했다

처음에는 디자인 감각을 키우려면 그냥 좋은 디자인을 많이 보면 된다고 생각했다.

물론 많이 보는 것도 도움이 된다.

하지만 아무 생각 없이 넘겨보면

```text
예쁘다.

이것도 예쁘다.

이것도 괜찮다.
```

로 끝난다.

조금 더 공부하려면 한 화면을 보고

```text
왜?
```

를 한 번 더 묻는 것이 중요했다.

```text
왜 버튼이 여기 있지?

왜 이 정보가 큰가?

왜 카드가 두 개로 나뉘었지?

왜 배경색을 다르게 했지?
```

이 질문이 쌓이면서 화면을 보는 방식이 달라지는 것 같다.

---

## AI 시대에는 오히려 레퍼런스 분석이 중요해졌다

AI에게

```text
깔끔한 앱 만들어줘.
```

라고 하면 정말 빠르게 화면을 만들어준다.

그래서 예전보다

```text
화면 하나를 만드는 능력
```

자체는 쉽게 얻을 수 있게 됐다.

하지만 그만큼

```text
이 화면이 좋은가?

우리 서비스에 맞는가?

무엇을 수정해야 하는가?
```

를 판단하는 능력이 중요해진다.

AI가 여러 디자인을 빠르게 만들 수 있을수록

```text
어떤 것을 선택할 것인가?
```

가 사람이 해야 할 일이 된다.

레퍼런스를 분석하는 것도 결국 이 판단 기준을 만드는 과정이라고 생각한다.

---

## 레퍼런스를 활용하는 나의 흐름

정리하면 앞으로는 이런 흐름으로 사용하려고 한다.

```text
만들 화면 결정
↓
비슷한 목적의 레퍼런스 여러 개 확인
↓
공통 구조 찾기
↓
각 레퍼런스에서 참고할 부분 구분
↓
내 서비스 기획과 비교
↓
필요한 구조만 적용
↓
Figma 또는 AI로 초안 제작
↓
다시 레퍼런스와 비교
↓
내 서비스 기준으로 최종 수정
```

중요한 것은 마지막이다.

```text
레퍼런스처럼 만들기
```

가 목표가 아니라

```text
레퍼런스에서 배운 것을
내 서비스에 맞게 적용하기
```

가 목표다.

---

## 내가 레퍼런스를 활용하면서 지키고 싶은 기준

지금까지 정리한 것을 기준으로 몇 가지 규칙을 만들었다.

```text
1. 예쁘다는 이유만으로 저장하지 않는다.

2. 왜 저장했는지 이유를 적는다.

3. 같은 종류의 화면을 여러 개 비교한다.

4. 구조와 스타일을 나눠서 본다.

5. 화면의 가장 중요한 행동을 찾는다.

6. 정보의 우선순위를 확인한다.

7. 레퍼런스의 기능을 그대로 추가하지 않는다.

8. 내 기획과 충돌하면 기획을 우선한다.

9. AI에게 전달할 때
   어떤 부분을 참고할지 명확하게 말한다.

10. 결과를 그대로 복사하지 않고
    원리와 구조를 가져온다.
```

---

## 마무리

처음에는 디자인 레퍼런스를 찾는다는 것이

```text
예쁜 화면을 많이 저장하는 것
```

이라고 생각했다.

지금은 조금 다르게 생각한다.

```text
좋은 화면을 찾고

↓

왜 그렇게 만들었는지 분석하고

↓

내 서비스에 필요한 원칙만 가져오는 것
```

이 레퍼런스를 제대로 활용하는 방법에 더 가깝다고 생각한다.

특히 직접 디자인을 해야 하는 개발자라면

모든 UI를 처음부터 새롭게 생각하려고 하기보다

이미 많은 서비스에서 해결한 문제를 살펴보는 것이 훨씬 효율적이다.

그렇다고 그대로 복사할 필요는 없다.

중요한 것은

```text
어떤 문제를
어떤 방식으로 해결했는지
```

를 이해하는 것이다.

그리고 레퍼런스를 찾고 분석하다 보면 결국 다시 Figma로 돌아오게 된다.

이제 좋은 구조를 찾았다면

```text
실제 프로젝트에서 사용할 수 있는 이미지와 에셋을 어떻게 내보낼지
```

도 알아야 한다.

아이콘이나 이미지를 아무 방식으로 저장해서 코드에 넣는 것과,

웹이나 앱에서 사용할 목적에 맞게 Export하는 것은 조금 다르다.

다음 글에서는

**PNG, JPG, SVG 같은 형식은 언제 사용하고, Figma에서 에셋을 어떻게 Export해서 개발과 연결할 수 있는지**

정리해보려고 한다.
