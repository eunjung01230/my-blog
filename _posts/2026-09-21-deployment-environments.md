## 들어가며

프로젝트를 시작하기 전에 나는 배포를 이렇게 이해하고 있었다.

```text
로컬에서 실행
↓
GitHub에 올림
↓
Vercel 배포
↓
끝
```

세 단계면 끝나는 줄 알았다. 그런데 실제로 해보니 로컬에서는 잘 되던 기능이 배포하니 안 되고, 빌드는 성공했다는데 화면에서는 오류가 나고, 같은 코드인데 어떤 주소에서는 되고 어떤 주소에서는 안 됐다.

알고 보니 저 세 단계 사이에 Build, Deployment, Environment, Environment Variable, Domain, Runtime, 외부 서비스 설정 같은 것들이 각각 따로 존재하고 있었다. 그래서 배포 관련 개념을 기초부터 다시 정리해두려고 한다.

이 글은 프로젝트 회고가 아니라 개념 정리 노트다. 중심은 **Local → Build → Environment → Preview → Production** 이 흐름이다.

## 1. 로컬 개발 환경이란?

**Local(로컬)** 은 **내 컴퓨터**를 뜻한다. 개발할 때는 보통 내 컴퓨터에서 개발 서버를 실행해놓고 작업한다.

```text
내 컴퓨터
↓
개발 서버        내 컴퓨터 안에서 애플리케이션을 실행한다
↓
localhost:3000   그 서버가 응답을 받는 주소
↓
브라우저         그 주소로 접속해서 결과를 본다
```

**localhost**는 **"이 컴퓨터 자신"을 가리키는 주소**다. 뒤에 붙는 `:3000` 같은 숫자는 **포트(port)** 인데, 한 컴퓨터 안에서 여러 프로그램이 동시에 돌아갈 때 서로를 구분하기 위한 번호다. 개발 서버는 3000번, 다른 도구는 4000번 하는 식으로 나눠 쓴다.

여기서 중요한 점이 있다. **localhost는 인터넷에 공개된 주소가 아니다.**

내 브라우저에서 `localhost:3000`이 잘 열린다고 해서 다른 사람도 그 주소로 들어올 수 있는 게 아니다. 팀원이 같은 주소를 입력하면 자기 컴퓨터의 3000번 포트를 찾아가기 때문에, 내가 만든 화면은 보이지 않는다.

이 사실이 배포가 왜 필요한지에 대한 출발점이었다. 포트 자체는 Terminal을 정리할 때 더 자세히 볼 예정이라 여기서는 이 정도만 짚고 넘어간다.

## 2. 배포란 무엇인가?

**Deployment(배포)** 는 **내 컴퓨터에서만 돌아가던 애플리케이션을, 다른 사람도 접근할 수 있는 환경에서 실행되게 만드는 과정**이다.

핵심은 "올린다"가 아니라 **"실행되게 한다"** 는 쪽에 있다. 파일을 어딘가에 복사해두는 것으로 끝나는 게 아니라, 그 코드가 실제로 돌아가는 서버가 있어야 한다.

### 배포는 GitHub에 push하는 것이 아니다

처음에 가장 크게 착각했던 부분이다.

```text
GitHub에 코드를 push했다
       (같지 않다)
배포가 됐다
```

GitHub는 **코드를 보관하고 버전을 관리하는 저장소**다. 코드를 올려두는 곳일 뿐, 그 코드를 실행해서 사용자에게 서비스해주는 곳이 아니다.

전체 흐름으로 보면 이렇게 나뉜다.

```text
Local                  내 컴퓨터에서 코드를 작성하고 실행해본다
↓
GitHub                 코드를 저장하고 공유한다
↓
Deployment Platform    그 코드를 가져와 실행 가능한 형태로 만들고 실행한다
↓
실제 웹사이트           사용자가 접속할 수 있는 주소가 생긴다
```

GitHub까지는 "코드가 있다"는 단계이고, 그 다음부터가 "코드가 돌아간다"는 단계다. 둘 사이에 배포 플랫폼이 하는 일이 따로 있다.

## 3. Hosting은 무엇인가?

배포와 함께 자주 나오는 단어가 **Hosting(호스팅)** 이다. 비슷하게 쓰이지만 완전히 같은 말은 아니다.

| 구분 | 무엇인가 |
|---|---|
| Deployment | 코드를 실행 가능한 형태로 만들어 실제 환경에 올리는 **과정** |
| Hosting | 애플리케이션이나 파일을 사용자가 접근할 수 있도록 서버 환경에서 제공하는 **것** |

내가 이해한 방식으로 정리하면, Deployment는 **"올리는 행위"** 에 가깝고 Hosting은 **"계속 제공해주는 상태와 그 환경"** 에 가깝다. 배포는 한 번의 작업이지만, 호스팅은 그 이후로 계속 유지된다.

Vercel이나 GitHub Pages 같은 이름이 여기에 해당한다. 다만 이 글은 서비스 비교가 목적이 아니라서, 이름은 예시로만 쓴다.

## 4. Build란 무엇인가?

**Build(빌드)** 는 **개발자가 작성한 소스 코드를 실제로 실행하거나 배포하기 적합한 형태로 준비하는 과정**이다.

내가 쓴 코드는 사람이 읽기 좋게 여러 파일로 나뉘어 있고, 브라우저가 바로 이해하지 못하는 문법이 섞여 있을 수도 있다. Build는 그것들을 정리하고 변환해서 실행 가능한 결과물로 만든다.

이 과정에서 문제가 발견되기도 한다. 요즘 프레임워크들은 Build 중에 문법 오류나 타입 오류, 없는 파일을 가져오려는 시도 같은 것들을 잡아낸다. 그래서 Build가 일종의 검사 역할도 해준다.

### 하지만 Build 성공이 전부는 아니다

여기가 가장 중요한 부분이다.

```text
Build 성공
       (같지 않다)
실제 서비스 기능 전체 정상
```

Build가 확인하는 건 **"이 코드가 실행 가능한 형태로 만들어지는가"** 까지다. Database 접속 주소가 맞는지, 외부 서비스가 응답하는지, 필요한 설정값이 실제로 존재하는지는 **확인하지 않는다.** 그건 실행해봐야 알 수 있는 것들이기 때문이다.

"빌드 성공"이라는 초록색 표시를 보고 다 됐다고 생각했다가 화면에서 오류를 만난 이유가 여기에 있었다.

## 5. Runtime이란 무엇인가?

Build와 짝을 이루는 개념이 **Runtime(런타임)** 이다.

| 구분 | 언제 |
|---|---|
| Build | 실행하기 **전에** 준비하는 단계 |
| Runtime | 애플리케이션이 **실제로 실행되는** 단계 |

Build가 요리 재료를 손질하는 단계라면 Runtime은 실제로 불을 켜고 조리하는 단계다. 재료 손질이 잘 끝났다고 조리가 성공한다는 보장은 없다.

Build는 멀쩡히 성공했는데 Runtime에서 실패하는 경우는 흔하다.

- Database 연결에 실패한다
- 외부 API가 응답하지 않거나 거절한다
- 필요한 환경변수가 그 환경에 없다
- 등록해둔 주소와 실제 주소가 달라서 인증이 막힌다

이런 문제들은 **코드 자체에는 문제가 없고 환경에 문제가 있는 경우**다. 그래서 Build로는 잡히지 않는다.

## 6. Build 오류와 Runtime 오류

두 오류는 성격이 달라서 확인할 곳도 다르다.

| 구분 | 의미 | 대체로 이런 것들 |
|---|---|---|
| Build Error | 배포용 결과물을 만드는 과정에서 실패 | 코드 문법, 타입, 빌드 설정, 없는 파일 참조 |
| Runtime Error | 배포된 앱이 실행되는 중에 실패 | DB 연결, 외부 API, 환경변수 누락, 서버 오류 |

다만 이 목록을 절대적인 기준으로 삼으면 안 된다. 환경변수가 없어서 Build 단계에서 실패하는 경우도 있고, 설정 방식에 따라 경계가 달라지기도 한다.

그래서 이렇게 이해하는 편이 정확했다. **오류가 Build 중에 났는지 실행 중에 났는지를 먼저 구분하면, 코드를 봐야 할지 환경 설정을 봐야 할지 방향을 정할 수 있다.**

## 7. Development 환경

이제 환경 이야기다. **Environment(환경)** 는 **애플리케이션이 실행되는 무대**라고 생각하면 된다. 같은 코드라도 어느 무대에서 실행되느냐에 따라 연결되는 데이터베이스나 설정값이 달라질 수 있다.

**Development(개발 환경)** 는 **개발자가 기능을 만들고 확인하는 환경**이다.

여기서는 자주 바뀌고 자주 깨져도 괜찮다. 실험하고 되돌리는 것이 목적이기 때문이다. 실제 사용자가 보는 곳이 아니라서 부담 없이 시도해볼 수 있다.

한 가지 짚어둘 점이 있다. **"Development"라는 말이 항상 같은 것을 가리키지는 않는다.** 내 컴퓨터에서 개발 서버를 돌리는 Local Development를 뜻할 때도 있고, 배포 플랫폼이 제공하는 Development라는 이름의 환경 설정을 뜻할 때도 있다. 문맥에 따라 다르니 어느 쪽을 말하는지 확인하는 습관이 필요했다.

## 8. Preview 환경

**Preview(프리뷰 환경)** 는 **변경사항을 실제 운영에 반영하기 전에, 배포된 상태로 미리 확인해보는 공간**이다.

왜 필요할까? 내 컴퓨터에서 잘 되는 것과 배포된 환경에서 잘 되는 것이 다르기 때문이다. 앞에서 본 것처럼 환경이 다르면 결과도 달라질 수 있다. 그렇다고 실제 사용자가 쓰는 곳에서 바로 확인할 수는 없다.

팀으로 일할 때 차이가 특히 컸다.

| 방식 | 한계 또는 장점 |
|---|---|
| 내 컴퓨터에서만 확인 | 나만 볼 수 있다. 내 환경에서만 되는 문제를 못 걸러낸다 |
| Preview URL로 확인 | 팀원이 같은 주소로 들어와서 함께 확인할 수 있다 |

"제 화면에서는 되는데요"라는 상황을 줄여주는 것이 Preview였다. 실제 배포와 같은 방식으로 Build되고 실행되기 때문에, 배포 후에야 드러날 문제를 미리 만날 수 있다.

## 9. Production 환경

**Production(운영 환경)** 은 **실제 사용자가 사용하는 환경**이다. 진짜 서비스가 돌아가는 곳이고, 여기에 있는 데이터는 진짜 사용자의 데이터다.

Preview와 비교하면 이렇다.

| 구분 | Preview | Production |
|---|---|---|
| 사용하는 사람 | 개발자, 팀원 | 실제 사용자 |
| 목적 | 반영 전 확인 | 실제 서비스 제공 |
| 데이터 | 테스트용을 쓰는 경우가 많다 | 실제 데이터 |
| 실수의 영향 | 대체로 제한적 | 사용자에게 직접 영향 |
| 주소 | 변경마다 생성되기도 한다 | 보통 고정된 대표 주소 |

여기서 단정하면 안 되는 것이 있다.

**"Preview는 무조건 develop 브랜치, Production은 무조건 main 브랜치"가 아니다.** 그렇게 연결해서 쓰는 팀이 많을 뿐이고, 배포 플랫폼 설정에 따라 얼마든지 다르게 구성할 수 있다. 어떤 브랜치가 어떤 환경으로 가는지는 프로젝트마다 확인해야 한다.

## 10. Git Branch와 Deployment Environment는 다른 개념

앞에서 이어지는 이야기인데, 이 부분이 개인적으로 가장 헷갈렸다.

두 개는 아예 다른 층에 있는 개념이다.

```text
Git 쪽
  main / develop / feature-...     코드의 버전을 관리하는 Branch

Deployment 쪽
  Development / Preview / Production    애플리케이션이 실행되는 Environment
```

| 구분 | 무엇을 나누는가 |
|---|---|
| Git Branch | 코드의 갈래. "어떤 버전의 코드인가" |
| Deployment Environment | 실행 무대. "어디에서 어떤 설정으로 돌아가는가" |

```text
Git Branch
       (같지 않다)
Deployment Environment
```

브랜치는 파일의 상태일 뿐이고, 환경은 그 코드가 실행되는 장소와 설정이다. 브랜치를 만든다고 환경이 생기지 않고, 환경이 있다고 브랜치가 생기지도 않는다.

### 그런데 왜 헷갈릴까

배포 플랫폼에서 **특정 브랜치와 특정 환경을 연결해둘 수 있기 때문**이다.

예를 들어 우리 팀에서는 이런 식으로 연결해서 사용했다.

```text
develop 브랜치에 반영  →  Preview 환경으로 배포
main 브랜치에 반영     →  Production 환경으로 배포
```

이렇게 써놓으면 "develop = Preview"처럼 보인다. 하지만 이건 **우리가 그렇게 설정했기 때문**이지 정해진 규칙이 아니다. 브랜치 이름을 바꾸거나 연결을 다르게 설정하면 전혀 다르게 동작한다.

이 구분이 잡히고 나서야 "브랜치를 바꿨는데 왜 환경변수가 그대로지?" 같은 혼란이 정리됐다. 브랜치와 환경 설정은 서로 다른 곳에서 관리된다.

## 11. Vercel은 무엇을 해주는가?

앞까지가 일반적인 개념이고, 이제 실제 예시를 하나 보자. **Vercel**은 배포 플랫폼 중 하나다.

GitHub 저장소와 연결해두면 이 과정이 자동으로 이어진다.

```text
코드 변경을 GitHub에 반영
↓
Build                        플랫폼이 변경을 감지하고 빌드한다
↓
Deployment                   결과물을 실행 가능한 상태로 올린다
↓
Preview 또는 Production URL  접속할 수 있는 주소가 만들어진다
```

직접 서버를 준비하고 실행해두는 대신, 이 과정을 대신 처리해주는 것이 배포 플랫폼의 역할이다. 앞에서 정리한 Build, Deployment, Environment 개념이 여기에 그대로 대응된다.

이 글은 Vercel 사용법을 다루는 글이 아니라서, **일반적인 배포 개념이 실제 서비스에서는 이런 모습으로 나타난다** 정도까지만 짚는다.

## 12. Domain과 URL

배포하면 주소가 생긴다. 관련 용어를 정리해둔다.

| 용어 | 무엇인가 |
|---|---|
| URL | 특정 자원에 접근하기 위한 주소 전체 |
| Domain | 그 주소에서 어떤 서비스인지를 가리키는 이름 부분 |
| localhost | 내 컴퓨터를 가리키는 주소. 나만 접근할 수 있다 |
| Preview URL | 변경사항을 확인하기 위해 만들어지는 주소 |
| Production URL | 실제 사용자가 접속하는 대표 주소 |

여기서 중요한 사실이 하나 있다.

**내 입장에서는 같은 프로젝트여도, 외부 서비스 입장에서는 주소가 다르면 다른 곳으로 취급될 수 있다.**

```text
http://localhost:3000        나에게는 "개발 중인 내 프로젝트"
https://preview-....app      나에게는 "확인용 내 프로젝트"
https://myservice.com        나에게는 "배포된 내 프로젝트"

외부 서비스 입장에서는        전부 서로 다른 주소
```

나는 전부 같은 서비스라고 생각하지만, 외부 API나 인증 제공자는 주소를 기준으로 판단한다. 이 차이가 뒤에 나올 "로컬에서는 되는데 배포에서는 안 되는" 문제의 큰 원인 중 하나였다.

## 13. Environment Variable이란?

이번 글의 핵심 중 하나다.

**Environment Variable(환경변수)** 는 **코드와 분리해서, 환경별로 다른 설정값을 애플리케이션에 제공하는 방법**이다.

이런 값들이 여기에 해당한다.

```text
DATABASE_URL     데이터베이스 접속 주소
CLIENT_ID        외부 서비스에서 우리 앱을 식별하는 값
CLIENT_SECRET    우리 앱임을 증명하는 비밀 값
API_KEY          외부 API를 사용할 자격을 나타내는 값
```

### 비밀을 숨기는 기능이라고만 이해하면 안 된다

처음에는 환경변수를 "비밀번호를 코드에 안 쓰기 위한 장치"로만 알고 있었다. 물론 그것도 맞지만, 절반만 맞는 이해였다.

환경변수에는 두 가지 목적이 있다.

| 목적 | 설명 |
|---|---|
| 민감한 값 보호 | 코드에 직접 쓰면 저장소에 함께 공개된다 |
| 환경별로 다른 값 제공 | 같은 코드가 환경에 따라 다른 곳을 바라보게 한다 |

두 번째가 오히려 배포에서는 더 중요했다. 비밀이 아닌 값이라도, 환경마다 달라져야 한다면 환경변수로 뺀다. 이유는 바로 다음에 나온다.

## 14. 환경마다 같은 변수 이름에 다른 값이 들어갈 수 있다

이 구조를 이해하고 나서 환경을 왜 나누는지가 납득됐다.

같은 `DATABASE_URL`이라는 이름을 쓰지만, 환경에 따라 실제 값은 다를 수 있다.

```text
DATABASE_URL

Development  →  개발용 DB       마음껏 넣고 지워도 되는 곳
Preview      →  테스트용 DB     확인용 데이터가 들어 있는 곳
Production   →  실제 운영 DB    진짜 사용자 데이터가 있는 곳
```

코드에는 `DATABASE_URL`을 읽어서 접속하라고만 적혀 있다. **코드는 그대로인데 실행되는 환경에 따라 연결 대상이 달라진다.**

이것이 환경을 나누는 핵심 이유 중 하나다. 만약 접속 주소를 코드에 직접 써버리면, 개발 중에 실수로 실제 사용자 데이터를 건드릴 수도 있고, 환경을 바꿀 때마다 코드를 고쳐야 한다.

이렇게 연결해서 보니 왜 배포 플랫폼이 환경별로 환경변수를 따로 설정하게 해두는지 이해가 됐다.

## 15. Public 값과 Secret

환경변수라고 해서 전부 비밀은 아니다. 두 종류를 구분해야 한다.

| 구분 | 무엇인가 | 어디까지 가도 되는가 |
|---|---|---|
| Public 값 | 브라우저에 노출되어도 되는 용도로 설계된 값 | 브라우저까지 내려가도 괜찮다 |
| Secret | 서버에서만 안전하게 관리해야 하는 민감한 값 | 서버 안에만 있어야 한다 |

Client Secret이나 데이터베이스 접속 정보 같은 값은 Secret이다. 브라우저로 내려가면 **사용자가 개발자 도구를 열어서 그대로 볼 수 있다.** 그러면 누구든 우리 데이터베이스에 접속하거나 우리 앱인 척할 수 있게 된다.

### 환경변수에 넣었다고 안전해지는 것이 아니다

이게 가장 조심해야 할 부분이었다.

```text
환경변수에 넣었다
       (같지 않다)
안전하다
```

환경변수는 **값을 코드 바깥에 두는 방법**일 뿐이다. 그 값을 브라우저에서 실행되는 코드에서 사용하면, 결국 결과물에 포함되어 사용자에게 전달된다. 환경변수라는 이름이 붙었다고 자동으로 가려지지 않는다.

그래서 **"이 값을 어디에서 쓰는가"** 가 중요하다. Secret은 서버에서 실행되는 코드에서만 사용해야 한다. 프레임워크에 따라 브라우저로 내보낼 값에 별도의 이름 규칙을 두기도 하는데, 그 규칙을 따르는 이유도 이 구분 때문이다.

## 16. `.env` 파일은 무엇인가?

로컬에서 개발할 때는 환경변수를 어떻게 줄까? 배포 플랫폼의 설정 화면은 로컬 개발 서버와 상관이 없다.

그래서 `.env`, `.env.local` 같은 파일을 사용한다. **내 컴퓨터에서 실행할 때 읽어갈 설정값을 적어두는 파일**이다.

같은 역할을 하지만 값이 저장되는 위치가 다르다.

| 실행 위치 | 설정값이 있는 곳 |
|---|---|
| 내 컴퓨터 | `.env.local` 같은 파일 |
| 배포 환경 | 배포 플랫폼의 Environment Variables 설정 |

둘 다 애플리케이션에 설정값을 제공한다는 목적은 같다. 하지만 **서로 자동으로 동기화되지 않는다.** 내 `.env.local`에 값을 추가했다고 배포 환경에 생기지 않는다.

그리고 한 가지 더. `.env` 파일에는 Secret이 들어 있는 경우가 많아서 **Git에 올리지 않는 것이 일반적이다.** 보통 `.gitignore`에 넣어서 저장소에 포함되지 않게 한다.

그래서 이런 일이 생긴다. 저장소를 새로 받아온 팀원은 코드는 다 받았는데 `.env` 파일이 없어서 실행이 안 된다. 코드 문제가 아니라 설정값이 없는 것이다. 이것도 다음 이야기와 이어진다.

## 17. 왜 로컬에서는 되는데 배포에서는 안 될까?

배포하면서 가장 많이 만났던 상황이다. 코드는 그대로인데 결과가 다르다.

이유는 대체로 **코드가 아니라 환경이 다르기 때문**이었다. 가능한 원인들을 정리해보면 이렇다.

| 원인 | 설명 |
|---|---|
| 환경변수 누락 | 로컬 `.env`에는 있는데 배포 환경에는 등록하지 않았다 |
| 환경별 값 불일치 | Preview와 Production에 서로 다른 값이 들어가 있다 |
| 외부 서비스에 주소 미등록 | 외부 서비스에 localhost만 등록되어 있다 |
| Redirect URI 불일치 | 등록해둔 주소와 실제 배포 주소가 다르다 |
| DB 접속 대상 차이 | 로컬은 개발용 DB, 배포는 다른 DB를 바라본다 |
| 실행 위치 차이 | 서버에서만 되어야 할 코드가 브라우저 쪽에 있다 |
| Runtime 환경 차이 | 실행 방식이나 버전이 로컬과 다르다 |

공통점이 보인다. **대부분 코드가 아니라 설정과 환경의 문제다.**

그래서 이 결론에 도달했다.

```text
로컬에서 됐다
       (같지 않다)
코드가 완벽하다
```

로컬에서 된다는 건 **"내 컴퓨터의 설정과 내 환경변수와 내 데이터베이스 기준으로는 동작한다"** 는 뜻이다. 그 조건들이 배포 환경에도 똑같이 갖춰져 있는지는 별개로 확인해야 한다.

## 18. 외부 API와 배포 URL

앞에서 "주소가 다르면 외부 서비스는 다른 곳으로 본다"고 했는데, 그게 실제로 문제가 되는 지점이 여기다.

소셜 로그인이나 지도 관련 API 같은 외부 서비스는 **어떤 주소에서 오는 요청을 허용할지**를 설정해둘 수 있다. 허용 URL, Redirect URI, Domain 같은 이름으로 관리된다.

그런데 우리 서비스의 주소는 하나가 아니다.

```text
localhost          개발 중
Preview URL        확인 중
Production URL     실제 서비스
```

**이 셋은 서로 다른 주소다.** 외부 서비스 설정에 localhost만 등록해뒀다면, 배포 환경에서 오는 요청은 등록되지 않은 주소에서 온 요청이 된다. 그러면 거절당한다.

코드는 아무 문제가 없는데도 실패하는 것이다. 배포할 때 **외부 서비스 설정도 함께 확인해야 한다**는 걸 이때 알았다.

OAuth가 어떻게 동작하는지는 Backend 글에서 정리했으니 여기서는 반복하지 않고, 배포 주소와 설정의 관계에만 집중한다.

## 19. Redirect URI와 배포

바로 앞 이야기의 대표적인 예가 Redirect URI다.

인증이 끝난 뒤 사용자를 돌려보낼 주소인데, 환경마다 값이 달라진다.

```text
Local 개발 중
http://localhost:3000/...

Production
https://example.com/...
```

**소셜 로그인 코드 자체는 똑같다.** 그런데 로컬에서는 성공하고 배포 환경에서는 실패한다. 외부 서비스에 등록된 주소 목록에 배포 주소가 없기 때문이다.

이런 경우 코드를 아무리 들여다봐도 원인을 찾을 수 없다. 고쳐야 할 곳이 우리 저장소 안이 아니라 외부 서비스의 설정 화면이기 때문이다.

배포 후 로그인이 안 될 때 **코드보다 먼저 등록된 주소 목록부터 확인**하는 습관이 필요했다.

## 20. Database도 환경별로 나눌 수 있다

환경을 나누는 이야기는 데이터베이스에도 그대로 적용된다.

```text
Development DB     개발하면서 자유롭게 넣고 지우는 곳
Preview / Test DB  확인용 데이터가 들어 있는 곳
Production DB      실제 사용자 데이터가 있는 곳
```

왜 나눌까? **개발하다가 실수로 실제 사용자 데이터를 건드리지 않기 위해서**다.

개발 중에는 테이블을 지웠다가 다시 만들거나, 데이터를 전부 비우고 다시 넣어보는 일이 흔하다. 그 대상이 실제 운영 데이터베이스라면 돌이킬 수 없는 일이 된다.

앞에서 본 것처럼 코드에는 `DATABASE_URL`을 읽으라고만 적혀 있고, 어느 데이터베이스를 바라볼지는 환경변수가 결정한다. 그래서 **환경을 나누는 것만으로 이 위험을 크게 줄일 수 있다.**

데이터베이스 자체에 대한 내용은 Database 글에서 정리했으니 여기서는 환경 분리 관점만 짚는다.

## 21. 배포 성공과 기능 정상은 다르다

Database 글과 Backend 글에서도 반복해서 나왔던 이야기인데, 배포에서도 똑같다.

아래는 전부 **서로 다른 단계**다.

| 단계 | 무엇이 확인된 것인가 |
|---|---|
| Build 성공 | 실행 가능한 결과물이 만들어졌다 |
| 사이트 접속 성공 | 주소가 살아 있고 화면이 뜬다 |
| Database 연결 성공 | 서버가 데이터베이스와 통신할 수 있다 |
| OAuth 정상 | 로그인 과정이 끝까지 진행된다 |
| 외부 API 정상 | 필요한 외부 서비스가 응답한다 |
| 서비스 전체 정상 | 사용자가 하려는 일이 실제로 완료된다 |

앞 단계가 됐다고 뒤 단계가 따라오지 않는다. 화면이 잘 뜨는데 로그인이 안 될 수 있고, 로그인은 되는데 저장이 안 될 수 있다.

그래서 **"배포 성공했어요"라는 말도 어디까지를 뜻하는지 확인이 필요하다.** 배포 플랫폼에 초록색 표시가 떴다는 뜻일 수도 있고, 실제로 기능을 써봤다는 뜻일 수도 있다.

## 22. Deployment 상태를 단계별로 확인하면

그래서 문제가 생겼을 때 순서대로 짚어보는 흐름을 만들어뒀다.

```text
1. Build가 성공했는가?              실패면 코드나 빌드 설정 문제
↓
2. 사이트에 접속되는가?             안 되면 배포나 주소 문제
↓
3. 올바른 Environment인가?          Preview를 보면서 Production을 기대하고 있지 않은가
↓
4. 필요한 환경변수가 있는가?        그 환경에 값이 등록되어 있는가
↓
5. Backend Runtime이 정상인가?      요청이 서버까지 도달하고 처리되는가
↓
6. Database 연결이 되는가?          접속 대상과 주소가 맞는가
↓
7. 외부 API가 정상인가?             주소가 등록되어 있고 응답하는가
↓
8. 실제 사용자 흐름이 정상인가?     처음부터 끝까지 한 번 해봤는가
```

이렇게 단계를 나눠두니 "배포가 안 돼요"라고 뭉뚱그리지 않고 **몇 번에서 막혔는지** 말할 수 있게 됐다. 그러면 찾아야 할 곳도 훨씬 좁아진다.

## 23. 환경변수를 바꿨는데 왜 바로 안 바뀔 수 있을까?

이것도 처음에 당황했던 부분이다. 배포 플랫폼에서 환경변수 값을 고쳤는데 사이트는 그대로였다.

이유는 **이미 배포되어 실행 중인 애플리케이션은 그 시점의 설정을 가지고 돌아가고 있기 때문**이다. 설정 화면에서 값을 바꾼다고 이미 돌아가고 있는 것이 자동으로 따라 바뀌지는 않는다. 그래서 **새로운 Deployment가 한 번 더 필요할 수 있다.**

여기서 단정하면 안 되는 부분이 있다. **이게 모든 플랫폼의 공통 규칙은 아니다.** 플랫폼마다 동작이 다르고, 값이 언제 읽히는지도 프레임워크와 실행 방식에 따라 달라진다. Build 시점에 값을 읽어서 결과물에 넣어버리는 경우도 있고, 실행할 때마다 읽는 경우도 있다.

앞의 경우라면 값을 바꿨을 때 반드시 다시 Build해야 반영된다. 그래서 **"환경변수를 바꿨으면 반영 시점도 같이 확인한다"** 정도로 기억해두는 게 안전했다.

## 24. Redeploy란?

**Redeploy(재배포)** 는 **새로운 코드 변경 없이, 현재 코드와 설정으로 다시 배포하는 것**이다.

코드를 고치지 않았는데 왜 다시 배포할까? 바로 앞에서 본 상황 때문이다.

- 환경변수를 바꾼 뒤 반영하고 싶을 때
- 일시적인 문제로 배포가 실패했을 때 다시 시도할 때
- 같은 코드가 다른 환경에서도 동작하는지 확인할 때

코드를 건드리지 않아도 **환경이 바뀌면 결과가 달라질 수 있다**는 점이 여기서도 드러난다. Redeploy라는 기능이 따로 있다는 것 자체가, 배포 결과가 코드만으로 결정되지 않는다는 증거이기도 했다.

## 25. 배포 로그는 왜 보는가?

로컬에서 개발할 때는 Terminal에 오류가 그대로 찍힌다. 무엇이 잘못됐는지 바로 보인다.

그런데 배포 환경에서는 그 Terminal을 볼 수 없다. 대신 배포 플랫폼이 제공하는 로그를 확인해야 한다.

```text
사용자 화면에서 보이는 것
500 Error

로그에서 보이는 것
DB 연결 실패 - 접속 주소를 찾을 수 없음
```

**사용자가 보는 오류 메시지만으로는 원인을 알 수 없다.** 화면에는 "문제가 발생했습니다" 한 줄만 나오지만, 실제로는 환경변수가 없어서일 수도 있고 데이터베이스가 응답하지 않아서일 수도 있다.

앞에서 정리한 8단계 체크 흐름에서 **몇 번에서 막혔는지 알려주는 것이 로그**다. 배포 후 문제가 생겼을 때 화면만 새로고침하지 말고 로그를 먼저 열어보는 게 훨씬 빨랐다.

## 26. Build Log와 Runtime Log

로그도 종류가 나뉜다. Build와 Runtime이 다른 단계였던 것과 같은 구분이다.

| 구분 | 무엇의 기록인가 | 언제 보는가 |
|---|---|---|
| Build Log | Build 과정의 기록 | 배포 자체가 실패했을 때 |
| Runtime Log | 배포된 앱이 실행되는 중의 기록 | 배포는 됐는데 기능이 안 될 때 |

배포가 아예 안 됐다면 Build Log를, 사이트는 떴는데 기능이 실패한다면 Runtime Log를 본다.

플랫폼마다 이름과 제공 방식은 다를 수 있다. 다만 **"만드는 과정의 기록"과 "실행 중의 기록"이 나뉘어 있다**는 구조 자체는 비슷하다.

## 27. 자동 배포 흐름

GitHub와 배포 플랫폼을 연결해두면 이 과정이 자동으로 이어진다.

```text
Local                      내 컴퓨터에서 코드를 작성한다
↓
Git Commit / Push          변경을 기록하고 원격 저장소로 보낸다
↓
GitHub                     코드가 저장된다
↓
배포 플랫폼이 변경 감지     연결된 저장소에 변경이 생긴 것을 알아챈다
↓
Build                      실행 가능한 형태로 만든다
↓
Deployment                 실행 환경에 올린다
↓
URL 생성                   접속할 수 있는 주소가 만들어진다
```

처음에 "push하면 배포된다"고 생각했던 이유가 이것 때문이었다. 실제로는 push 이후에 이만큼의 단계가 자동으로 실행되고 있었을 뿐이다. **자동으로 일어나는 것과 일어나지 않는 것은 다르다.**

Git 자체는 Git 글에서 정리했으니 여기서는 배포로 이어지는 부분만 본다.

## 28. CI/CD는 무엇인가?

자동 배포 흐름을 이해하다 보면 자연스럽게 만나는 말이 **CI/CD**다. 아주 기초만 짚고 넘어간다.

| 약어 | 대략의 의미 |
|---|---|
| CI (Continuous Integration) | 코드 변경을 자동으로 통합하고 검증하는 흐름 |
| CD | 변경사항을 자동으로 내보내거나 배포하는 흐름과 관련된 개념 |

CI는 코드가 합쳐질 때 자동으로 검사를 돌려서 문제를 일찍 발견하자는 쪽이고, CD는 검증된 변경을 자동으로 배포까지 이어가자는 쪽이다.

한 가지 짚어둘 점이 있다. **CD는 문맥에 따라 Continuous Delivery와 Continuous Deployment로 구분되기도 한다.** 배포 직전까지 자동화하고 마지막은 사람이 승인하는 경우와, 끝까지 자동으로 배포하는 경우를 나눠 부르는 것이다.

앞에서 본 자동 배포 흐름이 이미 이 개념의 일부라는 것 정도만 알아두고, 자세한 내용은 나중에 따로 볼 예정이다.

## 29. 자주 헷갈리는 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Local | 내 컴퓨터. 개발하면서 실행하는 곳 |
| localhost | 내 컴퓨터 자신을 가리키는 주소. 나만 접근할 수 있다 |
| Deployment | 코드를 다른 사람도 접근할 수 있는 환경에서 실행되게 하는 과정 |
| Hosting | 애플리케이션을 사용자가 접근할 수 있도록 서버 환경에서 제공하는 것 |
| Build | 소스 코드를 실행하거나 배포하기 적합한 형태로 준비하는 과정 |
| Runtime | 애플리케이션이 실제로 실행되는 단계 |
| Development | 개발자가 기능을 만들고 확인하는 환경 |
| Preview | 운영에 반영하기 전에 배포된 상태로 확인하는 환경 |
| Production | 실제 사용자가 사용하는 운영 환경 |
| Environment | 애플리케이션이 실행되는 무대. 설정이 환경마다 다를 수 있다 |
| Environment Variable | 코드와 분리해 환경별 설정값을 제공하는 방법 |
| Secret | 서버에서만 관리해야 하는 민감한 값 |
| Public Variable | 브라우저에 노출되어도 되는 용도로 설계된 값 |
| Domain | 주소에서 어떤 서비스인지를 가리키는 이름 부분 |
| URL | 특정 자원에 접근하기 위한 주소 전체 |
| Redeploy | 코드 변경 없이 현재 코드와 설정으로 다시 배포하는 것 |
| Build Log | Build 과정에서 남는 기록 |
| Runtime Log | 배포된 앱이 실행되는 중에 남는 기록 |
| CI | 코드 변경을 자동으로 통합하고 검증하는 흐름 |
| CD | 변경사항을 자동으로 내보내거나 배포하는 흐름과 관련된 개념 |

## 30. 자주 헷갈리는 차이 정리

| 구분 | 차이 |
|---|---|
| Local vs Production | 나만 접근하는 내 컴퓨터 / 실제 사용자가 쓰는 환경 |
| Git Branch vs Deployment Environment | 코드의 갈래 / 실행되는 무대. 연결할 수 있을 뿐 같은 것이 아니다 |
| Build vs Runtime | 실행 전 준비 단계 / 실제 실행 단계 |
| Preview vs Production | 반영 전 확인용 / 실제 서비스용 |
| Deployment vs Hosting | 올리는 과정 / 접근 가능하게 계속 제공하는 것 |
| `.env.local` vs 플랫폼 Environment Variables | 내 컴퓨터용 설정값 / 배포 환경용 설정값. 자동으로 동기화되지 않는다 |
| Public 값 vs Secret | 브라우저까지 가도 되는 값 / 서버 안에만 있어야 하는 값 |
| Build 성공 vs 기능 정상 | 결과물이 만들어진 것 / 실제로 동작하는 것 |

## 31. 전체 흐름 정리

지금까지 나온 것들을 하나로 이어본다.

### 개발

```text
Developer   기능을 만든다
↓
Local       내 컴퓨터에서 실행해보고 확인한다
↓
Git         변경을 기록한다
↓
GitHub      코드를 저장하고 팀과 공유한다
```

### 배포

```text
GitHub      변경된 코드가 올라온다
↓
Build       실행 가능한 형태로 만든다
↓
Preview     배포된 상태로 미리 확인한다
↓
Test        팀원이 함께 확인하고 문제를 찾는다
↓
Production  실제 사용자에게 제공한다
```

### 실제 실행

```text
User                      사용자가 접속한다
↓
Production URL            실제 서비스 주소로 들어온다
↓
Frontend / Backend        화면이 뜨고 요청이 처리된다
↓
Environment Variables     그 환경의 설정값을 읽는다
↓
Database / External API   설정값이 가리키는 곳과 연결된다
```

세 흐름을 나란히 놓고 보니 알게 된 게 있다. **코드는 첫 번째 흐름에서만 만들어지고, 두 번째와 세 번째에서 실제로 결과를 좌우하는 건 환경과 설정**이라는 점이다. 같은 코드가 어디에서 어떤 설정으로 실행되느냐에 따라 전혀 다르게 동작한다.

## 32. 이번에 이해한 핵심

이번에도 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### GitHub에 push했다, 는 배포됐다와 다르다

GitHub는 코드를 보관하는 곳이다. 그 코드를 실행해서 서비스하는 것은 배포 플랫폼의 몫이다.

### Build가 성공했다, 는 서비스 전체가 정상이다와 다르다

Build는 결과물이 만들어지는지까지만 확인한다. 연결과 설정은 실행해봐야 안다.

### Local에서 된다, 는 Production에서도 된다와 다르다

내 컴퓨터의 설정과 환경변수 기준으로 동작한다는 뜻일 뿐이다. 배포 환경에도 같은 조건이 갖춰져 있는지는 별개다.

### main 브랜치, 는 Production과 다르다

브랜치는 코드의 갈래이고 Production은 실행 환경이다. 연결해서 쓸 수 있을 뿐, 같은 것이 아니다.

### develop 브랜치, 는 Preview와 다르다

마찬가지다. 우리 팀이 그렇게 연결해뒀을 뿐, 정해진 규칙이 아니다.

### 환경변수에 넣었다, 는 안전하다와 다르다

환경변수는 값을 코드 바깥에 두는 방법일 뿐이다. 브라우저에서 실행되는 코드에서 쓰면 결국 노출된다.

### Preview에서 된다, 는 Production에서도 된다와 다르다

환경이 다르면 환경변수도, 데이터베이스도, 등록된 주소도 다를 수 있다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> 배포는 단순히 코드를 인터넷에 올리는 작업이 아니라, 코드가 실제 환경에서 실행될 수 있도록 Build, Environment, 환경변수, Database, 외부 서비스 설정을 함께 맞추는 과정이다.

처음에는 배포를 "업로드"라고 생각했다. 파일을 어딘가에 보내면 끝나는 줄 알았다. 하지만 실제로는 **코드를 실행 가능한 형태로 만들고, 어떤 환경에서 돌릴지 정하고, 그 환경에 맞는 설정값을 준비하고, 연결될 데이터베이스와 외부 서비스까지 맞춰두는 작업**이었다.

그래서 배포가 실패했을 때 코드만 들여다보면 답이 안 나왔던 것이다. 봐야 할 곳이 코드 바깥에 더 많았다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **DNS** — 도메인 이름이 실제 서버 주소로 연결되는 원리
- **HTTPS** — 통신을 암호화해 안전하게 주고받는 방식
- **CDN** — 사용자와 가까운 곳에서 파일을 제공해 속도를 높이는 구조
- **CI/CD** — 검증과 배포를 자동화하는 흐름의 실제 구성
- **Docker** — 실행 환경 자체를 통째로 맞춰서 "내 컴퓨터에서만 되는" 문제를 줄이는 방법
- **Serverless** — 서버를 직접 관리하지 않고 코드 단위로 실행하는 방식
- **Edge Runtime** — 사용자와 가까운 위치에서 코드를 실행하는 방식
- **Monitoring** — 배포 후 서비스 상태를 지속적으로 지켜보는 것
- **Logging** — 무엇을 남기고 무엇을 남기지 않을지에 대한 기준
- **Rollback** — 문제가 생겼을 때 이전 배포 상태로 되돌리는 것
