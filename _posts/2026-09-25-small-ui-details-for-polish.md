프로젝트의 주요 화면을 만들고 나면 어느 순간 이런 상태가 된다.

```text
로그인 됨

버튼 동작함

데이터 저장됨

페이지 이동됨

반응형 적용됨
```

기능만 보면 꽤 많이 완성됐다.

그런데 실제 화면을 보면 이상하게

```text
아직 완성품 같지는 않은데...
```

라는 느낌이 남을 때가 있다.

큰 문제가 있는 것은 아니다.

버튼도 제자리에 있고,

색상도 맞고,

카드도 정렬되어 있다.

그런데 조금씩 어색하다.

예를 들어

```text
마우스를 올려도 아무 반응이 없고

버튼을 눌렀는데 처리 중인지 모르겠고

아이콘이 미묘하게 가운데가 아니고

긴 글자가 카드 밖으로 튀어나가고

저장됐는데 아무 안내가 없고

비활성화 버튼은 왜 안 되는지 알 수 없다.
```

각각만 보면 작은 문제다.

하나 때문에 서비스를 사용할 수 없는 것도 아니다.

하지만 이런 작은 문제가 여러 개 쌓이면

전체 서비스가

```text
기능을 구현한 화면
```

처럼 느껴질 수 있다.

반대로 이런 부분이 자연스럽게 정리되어 있으면

큰 디자인을 새로 하지 않아도

```text
잘 다듬어진 서비스
```

라는 느낌이 생긴다.

이번 글에서는 기능 구현 이후에 놓치기 쉬웠던

**작은 UI 디테일들**을 정리해보려고 한다.

---

## 처음에는 큰 화면만 맞으면 된다고 생각했다

디자인을 구현할 때 가장 먼저 보는 것은 큰 구조다.

```text
Header 위치

Card 크기

Button 위치

색상

Grid

Navigation
```

Figma와 비교하면서

```text
전체적으로 비슷하다.
```

면 잘 된 것처럼 보인다.

처음에는 나도 여기까지를 디자인 구현이라고 생각했다.

하지만 실제로 눌러보기 시작하면

큰 구조보다 작은 상태들이 더 자주 눈에 들어왔다.

---

## 사용자는 정지된 화면만 보지 않는다

Figma에서 보는 화면은 대부분 한 순간이다.

예를 들어

```text
[저장하기]
```

버튼이 있다.

하지만 실제 서비스에서 버튼은 여러 상태를 가진다.

```text
기본

마우스 올림

클릭

처리 중

비활성화

완료
```

즉 실제 UI는

```text
한 장의 디자인
```

이 아니라

```text
상태가 계속 변하는 디자인
```

이었다.

---

## 버튼 하나에도 여러 상태가 있었다

예를 들어 Primary Button이 있다고 해보자.

### 기본 상태

```text
[저장하기]
```

사용자가 아직 아무 행동도 하지 않은 상태다.

### Hover

마우스를 올린다.

```text
[저장하기]
```

모양이 조금 달라진다.

### Pressed

실제로 누르고 있는 순간이다.

### Loading

```text
[저장 중...]
```

### Disabled

```text
[저장하기]
```

하지만 클릭할 수 없다.

같은 버튼 하나라도

실제 서비스에서는 여러 디자인이 필요했다.

---

## Hover는 작은 변화지만 중요한 피드백이었다

웹에서 마우스를 사용하는 경우

사용자는 어떤 요소가 클릭 가능한지 확인하기 위해

자연스럽게 마우스를 올려본다.

예를 들어 카드가 클릭 가능한데

마우스를 올려도 아무 변화가 없다.

```text
이거 눌러도 되는 건가?
```

조금 애매할 수 있다.

반대로

```text
테두리 변화

배경색 변화

약간의 그림자

커서 변화
```

같은 반응이 있으면

```text
이 요소는 상호작용할 수 있구나.
```

를 알 수 있다.

---

## Hover 효과를 너무 강하게 만들 필요는 없었다

Hover가 중요하다고 해서

```text
카드가 크게 확대됨

색상이 완전히 변경됨

강한 애니메이션
```

까지 넣을 필요는 없다.

오히려 화면이 산만해질 수 있다.

예를 들어

```css
.card:hover {
  transform: translateY(-2px);
}
```

정도의 작은 변화만으로도 충분할 수 있다.

핵심은

```text
상태가 바뀌었다.
```

를 느낄 수 있는 것이다.

---

## 모바일에는 Hover가 없었다

이 부분도 중요했다.

PC에서

```text
Hover하면 추가 버튼이 나타남
```

이라고 만들어놓으면

마우스가 없는 모바일에서는 문제가 생길 수 있다.

중요한 기능을

```text
Hover할 때만 접근 가능
```

하게 만들면 안 된다.

그래서 Hover는

```text
추가적인 시각 피드백
```

으로 생각하는 편이 좋았다.

핵심 기능의 유일한 진입 방법이 되어서는 안 된다.

---

## Cursor도 작은 힌트였다

웹에서는 클릭 가능한 요소에

```css
cursor: pointer;
```

를 사용할 수 있다.

이것도 아주 작은 차이다.

하지만 카드나 버튼 위에서

커서가 바뀌면

```text
클릭할 수 있는 요소
```

라는 신호가 된다.

반대로 클릭 가능한 카드인데

일반 텍스트 커서 그대로라면

상호작용이 덜 명확하게 느껴질 수 있다.

---

## Focus 상태는 더 쉽게 놓쳤다

마우스로만 테스트하면 Focus를 거의 보지 않을 수 있다.

하지만 키보드로

```text
Tab
```

을 눌러 이동하면

현재 어떤 요소가 선택되어 있는지 보여줘야 한다.

예를 들어

```text
검색창

로그인 버튼

링크

설정
```

사이를 Tab으로 이동한다.

현재 위치가 전혀 표시되지 않으면

사용자는

```text
지금 어디에 선택되어 있지?
```

를 알기 어렵다.

---

## outline을 무조건 없애면 안 되는 이유를 알게 됐다

CSS를 처음 배우다 보면 디자인이 예쁘지 않아서

```css
outline: none;
```

을 사용하고 싶어질 수 있다.

Focus 테두리를 없애면

마우스로 볼 때는 깔끔하다.

하지만 키보드 사용자는 현재 위치를 알 수 없게 될 수 있다.

그래서

```text
기본 Focus 디자인이 마음에 안 든다.
```

면

없애는 것이 아니라

```text
서비스 디자인에 맞는 Focus 상태
```

로 바꾸는 편이 더 적절하다.

---

## Focus 상태도 디자인 시스템에 포함될 수 있었다

예를 들어 입력창에 Focus가 들어오면

```text
기본

회색 Border
```

에서

```text
Focus

Primary Color Border
```

로 바꿀 수 있다.

```text
입력하지 않는 상태

vs

현재 입력하는 상태
```

가 명확해진다.

작은 차이지만 Form에서는 꽤 중요했다.

---

## Disabled 버튼은 회색으로 만들면 끝이라고 생각했다

처음에는

```text
버튼 사용 불가
→ 회색
```

이면 끝이라고 생각했다.

그런데 실제로 보면 또 다른 문제가 생겼다.

```text
왜 안 눌리지?
```

사용자는 버튼이 비활성화된 이유를 모를 수 있다.

예를 들어 회원가입에서

```text
[회원가입]
```

버튼이 회색이다.

사용자는

```text
어떤 항목이 부족하지?
```

를 직접 찾아야 한다.

---

## Disabled 상태보다 원인을 가까이 보여주는 것이 중요했다

예를 들어 비밀번호가 조건에 맞지 않는다면

```text
비밀번호는 8자 이상 입력해주세요.
```

라고 입력창 가까이 알려줄 수 있다.

그러면

```text
버튼이 왜 비활성화되어 있는가
```

도 이해하기 쉽다.

즉,

```text
Disabled 표현
```

만 디자인하는 것이 아니라

```text
왜 Disabled인지 설명하는 UI
```

도 필요할 수 있었다.

---

## Loading 상태를 빼먹기 쉬웠다

개발 중에는 로컬 환경이 빠르다.

버튼을 누르면 결과가 거의 바로 나올 수 있다.

그래서 Loading UI를 잊기 쉽다.

하지만 실제 환경에서는

```text
네트워크

서버

DB

외부 API
```

때문에 시간이 걸릴 수 있다.

예를 들어

```text
[로그인]
```

을 눌렀다.

아무 변화가 없다.

1초.

2초.

사용자는 다시 누른다.

---

## 그래서 버튼 안에서도 Loading 상태가 필요했다

예를 들어

```text
[로그인]
```

에서

```text
[로그인 중...]
```

으로 바뀐다.

또는 Spinner를 보여줄 수 있다.

```text
[ ◌ 로그인 중 ]
```

그리고 처리 중에는

중복 클릭을 막을 수도 있다.

이렇게 하면 사용자는

```text
내 클릭을 서비스가 인식했고
지금 처리하고 있다.
```

는 것을 알 수 있다.

---

## 페이지 Loading과 버튼 Loading도 달랐다

전체 페이지 데이터를 불러오는 상황에서는

```text
Skeleton

Spinner

Loading 문구
```

등을 사용할 수 있다.

반대로 특정 버튼만 처리 중이라면

페이지 전체를 가릴 필요가 없을 수도 있다.

예를 들어

```text
혜택 카드

[삭제 중...]
```

정도로 해당 Action만 상태를 보여줄 수 있다.

즉 Loading도 범위를 생각해야 했다.

---

## Loading이 너무 길면 별도의 정보가 필요할 수도 있었다

아주 짧은 작업이라면 Spinner만으로 충분하다.

하지만 시간이 조금 더 걸리는 작업이라면

```text
데이터를 불러오는 중입니다.
```

처럼 무엇을 하고 있는지 알려주는 것이 좋을 수 있다.

긴 처리에서 아무 설명 없이

계속 돌아가는 Spinner만 있다면

```text
멈춘 건가?
```

라고 느낄 수 있다.

---

## 성공했을 때도 피드백이 필요했다

사용자가 정보를 수정한다.

```text
[저장]
```

을 누른다.

DB에도 잘 저장됐다.

하지만 화면이 그대로다.

사용자는 생각한다.

```text
저장된 건가?
```

기능적으로는 성공했지만

사용자는 성공 여부를 모른다.

---

## Toast가 이런 곳에서 유용했다

예를 들어 저장 후

```text
✓ 저장되었습니다.
```

라는 작은 Toast를 잠깐 보여줄 수 있다.

사용자는

```text
작업 완료
```

를 이해한다.

Toast는 화면 흐름을 크게 방해하지 않으면서

짧은 상태를 전달하기 좋았다.

---

## 모든 성공에 Toast를 띄울 필요는 없었다

예를 들어 버튼을 눌렀더니

새 페이지로 이동하고

방금 작성한 글이 바로 보인다.

그 자체가 이미

```text
성공했다.
```

는 충분한 피드백일 수 있다.

그런데 거기에 또

```text
페이지 이동 완료!

게시글 열기 성공!

데이터 로드 성공!
```

를 계속 보여주면 오히려 방해된다.

Toast는

```text
사용자가 결과를 알아차리기 어려운 경우
```

에 사용하는 편이 자연스러웠다.

---

## Toast 문구도 짧을수록 좋았다

```text
요청하신 데이터 저장 작업이 성공적으로 완료되었습니다.
```

보다

```text
저장했습니다.
```

또는

```text
변경사항을 저장했습니다.
```

정도로 충분한 경우가 많다.

Toast는 오래 읽는 영역이 아니다.

잠깐 나타났다가 사라질 수 있기 때문에

빠르게 이해할 수 있어야 했다.

---

## 오류 메시지는 더 중요했다

성공했을 때는 기분이 좋다.

문제가 생기지 않는다.

하지만 오류가 났을 때 사용자는 멈춘다.

예를 들어

```text
Error 400
```

만 보여준다.

개발자는 원인을 어느 정도 추측할 수 있다.

사용자는 모른다.

---

## 좋은 오류 문구에는 다음 행동이 있었다

예를 들어

```text
로그인에 실패했습니다.
```

보다

```text
로그인에 실패했습니다.
이메일과 비밀번호를 다시 확인해주세요.
```

가 조금 더 도움이 된다.

또 네트워크 문제라면

```text
데이터를 불러오지 못했습니다.

[다시 시도]
```

처럼 해결 행동까지 연결할 수 있다.

오류 메시지의 목적은

```text
문제가 났다는 사실을 알려주는 것
```

에서 끝나지 않았다.

```text
그러면 다음에 무엇을 해야 하는가?
```

까지 알려주는 것이 좋았다.

---

## 오류를 빨간색으로 만드는 것만으로는 부족했다

Error라면 빨간색을 사용할 수 있다.

하지만

```text
빨간 Border
```

만 있고 설명이 없으면

사용자는 여전히 문제를 모를 수 있다.

예를 들어 이메일 입력창이 빨간색이 됐다.

```text
왜?
```

가 남는다.

그래서

```text
올바른 이메일 형식을 입력해주세요.
```

같은 문구를 입력창 가까이 표시하는 편이 이해하기 쉽다.

---

## 에러 문구는 문제가 생긴 곳 가까이에 두는 것이 좋았다

Form 상단에

```text
입력값에 오류가 있습니다.
```

라고 한 줄만 보여주고

입력창 10개 중 무엇이 문제인지 알려주지 않는다면

사용자는 하나씩 찾아야 한다.

반대로

```text
이메일
[abc]

올바른 이메일 형식을 입력해주세요.
```

처럼 가까이에 보여주면 빠르게 수정할 수 있다.

---

## Placeholder를 Label 대신 쓰면 문제가 생길 수 있었다

Form을 깔끔하게 만들려고

```text
[ 이메일을 입력하세요 ]
```

Placeholder만 사용할 수 있다.

처음에는 깔끔하다.

하지만 사용자가 입력하기 시작하면

Placeholder가 사라진다.

```text
[eunjung@example.com]
```

이때

```text
이 입력칸이 이메일이었나?
```

를 다시 기억해야 할 수 있다.

그래서 중요한 입력은

```text
이메일

[ eunjung@example.com ]
```

처럼 Label을 따로 두는 편이 명확했다.

---

## Placeholder는 예시나 힌트에 더 가까웠다

예를 들어

```text
닉네임

[ 예: 푸름 ]
```

처럼 사용할 수 있다.

Label이

```text
무엇을 입력하는가
```

를 설명하고,

Placeholder는

```text
어떤 형태로 입력할 수 있는가
```

를 보조한다.

---

## 필수 입력도 명확하게 보여줘야 했다

Form에 입력칸이 많다.

그중 일부만 필수다.

그런데 아무 표시가 없다면

사용자는 저장 버튼을 누른 뒤에야

```text
이것도 입력해야 했어?
```

를 알 수 있다.

필요하다면

```text
닉네임 *
```

처럼 표시하거나,

반대로 대부분이 필수라면

```text
메모 (선택)
```

처럼 선택 항목만 표시할 수도 있다.

중요한 것은 기준이 일관된 것이다.

---

## 긴 텍스트 처리는 실제 데이터에서 자주 문제였다

디자인에서는

```text
홍길동

판교점

공지사항
```

같은 짧은 데이터를 사용한다.

실제 서비스에서는

```text
매우긴사용자닉네임123456789

컴포즈커피 성남판교테크노밸리어쩌고점

제목이 굉장히 긴 게시글
```

이 들어올 수 있다.

그 순간 Layout이 깨진다.

---

## 긴 텍스트 처리 방법도 미리 정해야 했다

상황에 따라 여러 방법이 있다.

### 줄바꿈

```text
컴포즈커피 성남
판교테크노밸리점
```

### 말줄임

```text
컴포즈커피 성남판교테...
```

### 최대 줄 수 제한

```text
제목 한 줄
제목 두 줄...
```

### 스크롤

코드나 특정 긴 콘텐츠에서 사용할 수 있다.

무조건 한 가지 방식이 정답은 아니다.

---

## 중요한 정보는 함부로 잘라서는 안 됐다

예를 들어 계좌번호나 중요한 식별 정보처럼

전체 내용을 봐야 하는 값이라면

단순 말줄임이 문제가 될 수 있다.

반대로 카드 목록에서 긴 설명 전체를 보여줄 필요는 없을 수 있다.

그래서

```text
전체를 읽어야 하는 정보인가?

빠르게 구분만 하면 되는 정보인가?
```

를 기준으로 선택했다.

---

## 말줄임을 사용하면 전체 내용을 볼 방법도 생각할 수 있었다

예를 들어

```text
프로젝트 이름이 굉장히 긴...
```

으로 표시했다.

사용자가 전체 이름을 확인해야 한다면

상세 화면에서는 전체를 보여줄 수 있다.

Desktop에서는 경우에 따라 Tooltip 같은 보조 방법도 생각할 수 있다.

핵심은

```text
말줄임으로 정보가 영원히 사라지지 않게 하는 것
```

이었다.

---

## 숫자가 커지는 상황도 테스트해야 했다

처음에는

```text
9

99

999
```

만 생각한다.

실제 데이터가

```text
10,000

1,000,000
```

이 되면 카드가 깨질 수 있다.

특히

```text
순위

거리

금액

카운트

통계
```

를 보여주는 UI에서는 숫자 길이도 확인해야 했다.

---

## 0도 중요한 실제 데이터였다

디자인에서는 내용이 풍부해 보이도록

항상 숫자를 넣는다.

```text
쿠폰 3개

스탬프 8개

기록 24개
```

하지만 실제로는

```text
0
```

일 수 있다.

그때

```text
쿠폰 0개
```

라고 보여줄지,

정보 자체를 숨길지,

Empty State로 바꿀지

결정해야 한다.

상황에 따라 답이 다르다.

---

## 아이콘 정렬은 정말 작은데 눈에 잘 들어왔다

예를 들어

```text
📍 도보 7분
```

에서 아이콘이 텍스트보다 조금 위에 있다.

기능에는 아무 문제가 없다.

그런데 카드가 여러 개 반복되면

미묘한 어색함이 계속 보인다.

그래서

```text
아이콘 크기

텍스트 Baseline

Gap

정렬
```

을 맞추는 것도 중요했다.

---

## 아이콘마다 실제 보이는 크기가 달랐다

CSS에서 모두

```text
24px
```

로 설정했다고 해도

아이콘의 내부 형태에 따라

어떤 아이콘은 커 보이고,

어떤 아이콘은 작아 보일 수 있다.

```text
○

⚙

⌂
```

모두 같은 Bounding Box를 써도

시각적인 무게가 다르다.

그래서 숫자만 같다고

실제 화면에서도 똑같이 보인다고 생각하면 안 됐다.

---

## 아이콘 라이브러리를 섞으면 더 티가 났다

예를 들어

```text
Lucide 검색 아이콘

Material 설정 아이콘

직접 만든 홈 아이콘
```

을 함께 사용한다.

각각

```text
선 굵기

모서리

크기

스타일
```

이 조금씩 다르다.

개별적으로는 괜찮아도 한 화면에 놓으면

통일되지 않아 보일 수 있다.

가능하다면 같은 아이콘 세트를 기준으로 사용하는 편이 관리하기 쉬웠다.

---

## 아이콘과 텍스트 사이 간격도 통일할 수 있었다

예를 들어

```text
아이콘  8px  텍스트
```

로 정했다면

다른 버튼에서도 비슷한 Gap을 사용한다.

```text
검색

길찾기

설정

수정
```

버튼마다 Gap이 제각각이면

미묘하게 정리되지 않은 느낌이 생길 수 있다.

---

## Border Radius도 제각각이면 이상했다

예를 들어

```text
Card
→ 16px

Button
→ 12px

Input
→ 8px
```

처럼 역할에 따라 다른 것은 괜찮다.

문제는 같은 버튼인데

```text
Login Button
→ 10px

Save Button
→ 17px

Add Button
→ 6px
```

처럼 이유 없이 달라지는 경우다.

이런 작은 값들은

한두 개일 때는 눈에 잘 안 띄지만

페이지가 많아질수록 통일감이 깨진다.

---

## 그래서 작은 값도 Token처럼 관리할 수 있었다

예를 들어

```text
Spacing

4

8

12

16

24

32
```

정도의 단계만 사용한다고 정할 수 있다.

Radius도

```text
8

12

16
```

정도로 제한할 수 있다.

색상도 마찬가지다.

이렇게 하면 매번

```text
이번에는 17px?

21px?
```

고민하지 않아도 된다.

---

## 아무 숫자나 쓰기 시작하면 미세한 차이가 계속 생겼다

예를 들어 카드 사이 Gap이

```text
23px
```

이고,

다른 페이지는

```text
25px
```

이다.

눈으로는 비슷해 보인다.

하지만 이런 값이 계속 쌓이면

일관성을 관리하기 어려워진다.

그래서

```text
왜 이 숫자인가?
```

를 설명하기 어려운 값은

기존 Spacing 규칙에 맞춰보는 것도 좋았다.

---

## 그림자도 페이지마다 달라지기 쉬웠다

AI 디자인을 사용하다 보면 특히

카드마다 조금씩 다른 Shadow가 생길 수 있다.

```text
Shadow 약함

Shadow 강함

파란 Shadow

큰 Blur
```

한 페이지 안에서도 달라질 수 있다.

그래서 Shadow 역시

```text
기본 Card Shadow

Floating UI Shadow

Modal Shadow
```

정도로 역할을 나눌 수 있다.

---

## 사실 그림자를 빼는 것이 더 나을 때도 있었다

카드를 구분하기 위해 무조건 Shadow를 사용할 필요는 없다.

```text
Border

Background 차이

Spacing
```

만으로도 충분할 수 있다.

특히 카드가 많은 화면에서

모든 카드에 강한 그림자가 있으면

화면이 더 복잡해질 수 있다.

---

## Divider도 남용하기 쉬웠다

정보를 나누려고

모든 항목 사이에

```text
────────────
```

선을 넣을 수 있다.

하지만 여백만으로 충분히 그룹을 나눌 수 있는 경우도 있다.

```text
제목
설명


다음 Section
```

처럼 말이다.

Divider는 정말 경계가 필요한 곳에서 사용하는 편이 깔끔할 수 있었다.

---

## 화면 가장자리 여백도 페이지마다 맞춰야 했다

Home은

```text
20px
```

인데

Detail은

```text
16px
```

Settings는

```text
24px
```

이면

페이지 전환할 때 콘텐츠가 좌우로 움직이는 느낌이 생길 수 있다.

특별한 이유가 없다면

공통 Page Padding을 정해두는 것이 편했다.

---

## Header 높이도 통일되면 안정적으로 보였다

페이지마다

```text
Header 56px

Header 64px

Header 60px
```

가 제각각이면

Navigation 시 화면이 조금씩 흔들려 보일 수 있다.

같은 유형의 Header라면

높이,

제목 위치,

뒤로가기 위치를 맞추는 것이 좋았다.

---

## 뒤로가기 아이콘 위치도 작은데 중요했다

페이지마다

```text
← 제목
```

이 있다.

어떤 페이지는 아이콘이 위에 있고,

어떤 페이지는 조금 아래에 있고,

어떤 페이지는 제목과 간격이 다르다.

한 화면만 보면 크게 티가 안 난다.

페이지를 연속으로 이동하면 잘 보인다.

공통 Header Component가 도움이 되는 이유다.

---

## 스크롤바도 갑자기 Layout을 바꿀 수 있었다

Desktop에서는 콘텐츠가 짧을 때 스크롤바가 없다.

내용이 길어지면 스크롤바가 생긴다.

환경에 따라 화면 폭이 약간 달라지면서

Layout이 움직이는 것처럼 보일 수도 있다.

모든 프로젝트에서 큰 문제는 아니지만

```text
짧은 페이지

긴 페이지
```

를 둘 다 확인해보는 이유 중 하나다.

---

## 스크롤 위치도 사용자 경험의 일부였다

목록에서 아래까지 내려갔다.

카드 하나를 눌렀다.

상세를 봤다.

뒤로갔다.

그런데 다시 목록 맨 위다.

```text
아까 보던 카드 어디 갔지?
```

이런 작은 불편함도 실제 사용에서는 꽤 크게 느껴질 수 있다.

그래서 페이지 이동과 함께

```text
스크롤 위치

검색어

필터 상태
```

가 유지되어야 하는 상황도 있었다.

---

## Sticky UI도 편하지만 조심해야 했다

예를 들어

```text
Header

TOC

하단 버튼
```

을 화면에 고정할 수 있다.

사용자는 언제든 접근할 수 있어 편하다.

하지만 너무 많은 것을 고정하면

실제 콘텐츠가 보이는 영역이 줄어든다.

모바일에서는 특히 그렇다.

```text
상단 Header

하단 Navigation

하단 CTA
```

가 모두 고정되어 있으면

본문 영역이 아주 작아질 수 있다.

---

## 고정 UI끼리 겹치는지 확인해야 했다

예를 들어

```text
Bottom Navigation
```

이 이미 있다.

거기에

```text
[저장하기]
```

고정 버튼을 추가했다.

둘 다 화면 아래를 사용한다.

잘못 구현하면 겹친다.

그래서

```text
하단 Navigation 높이

CTA 위치

Safe Area

본문 Padding
```

을 함께 계산해야 했다.

---

## Tooltip은 필요한 곳에만 사용한다

아이콘만 있는 기능에서

Desktop이라면 Hover 시 설명을 보여줄 수 있다.

예:

```text
⚙
```

에 마우스를 올리면

```text
설정
```

Tooltip이 나타난다.

하지만 Tooltip이 없으면 아무도 이해하지 못하는 아이콘이라면

애초에 텍스트를 같이 보여주는 것이 나을 수도 있다.

Tooltip은

```text
없어도 기본 의미를 이해할 수 있지만
추가 설명이 있으면 좋은 경우
```

에 더 적합했다.

---

## 애니메이션은 있으면 무조건 좋은 것이 아니었다

버튼,

카드,

Modal에 Transition을 넣으면

부드러운 느낌을 줄 수 있다.

예를 들어

```css
transition: 0.2s;
```

정도의 짧은 변화다.

하지만 모든 요소가

```text
움직이고

커지고

흔들리고

Fade
```

한다면

사용자는 피곤할 수 있다.

---

## 애니메이션에도 목적이 필요했다

좋은 Animation은

```text
상태가 바뀌었다.

어디에서 어디로 이동했다.

새로운 요소가 등장했다.
```

를 이해하도록 도와줄 수 있다.

반대로

```text
그냥 예뻐 보여서
```

계속 움직이는 요소는

오히려 핵심 정보를 방해할 수 있다.

---

## 아주 긴 Animation도 사용성을 떨어뜨릴 수 있었다

페이지 전환 때마다

1초 이상 기다려야 한다면

처음 몇 번은 멋있어도

반복 사용에서는 답답할 수 있다.

특히

```text
자주 사용하는 버튼

목록

설정
```

같은 기능에서는

빠른 반응이 더 중요할 수 있다.

---

## Modal이 열렸을 때 배경도 생각해야 했다

Modal만 화면 중앙에 띄운다.

그런데 뒤쪽 페이지가 그대로 강하게 보인다.

시선이 분산될 수 있다.

그래서

```text
Overlay
```

를 이용해 배경을 약하게 만들 수 있다.

사용자가

```text
지금은 Modal에 집중해야 한다.
```

는 것을 이해하기 쉬워진다.

---

## Modal 밖을 누르면 닫을지도 정해야 했다

어떤 Modal은

밖을 클릭하면 닫힌다.

다른 Modal은 닫히지 않는다.

페이지마다 기준이 다르면 사용자가 혼란스러울 수 있다.

특히 중요한 입력을 작성 중인데

실수로 바깥을 눌렀다가 모두 사라지면 문제가 된다.

```text
간단한 선택 Modal

vs

중요한 Form Modal
```

은 닫기 정책이 달라질 수 있다.

---

## 닫기 버튼도 찾기 쉬워야 했다

Modal 오른쪽 위에

```text
×
```

가 너무 작으면

모바일에서 누르기 어렵다.

시각적으로 작은 `×`를 사용하더라도

실제 클릭 영역은 더 크게 만들 수 있다.

파비콘과 달리

UI에서는 작은 아이콘이라고

클릭 영역까지 작을 필요는 없었다.

---

## Confirm Dialog 문구도 자세히 봐야 했다

예를 들어 삭제를 누른다.

```text
정말 삭제하시겠습니까?
```

라고 나온다.

무엇을 삭제하는지 명확하지 않을 수 있다.

조금 더 구체적으로

```text
이 혜택을 삭제할까요?

삭제한 혜택은 목록에서 보이지 않습니다.
```

처럼 표시할 수 있다.

위험한 행동일수록

사용자가 무엇을 하는지 확인할 수 있어야 했다.

---

## "예 / 아니오"보다 행동 이름이 더 명확할 때가 있었다

예를 들어

```text
정말 로그아웃하시겠습니까?

[예] [아니오]
```

보다

```text
정말 로그아웃할까요?

[취소] [로그아웃]
```

처럼 버튼 자체에 행동을 쓰는 편이

무엇을 누르는지 더 명확할 수 있다.

---

## 날짜와 시간 표기 방식도 일관되어야 했다

같은 서비스에서

```text
2026.09.25

2026-09-25

9월 25일

25 Sep 2026
```

이 섞이면 어색할 수 있다.

상황에 따라 표현이 달라질 수 있지만

비슷한 화면에서는 하나의 규칙을 정하는 편이 좋았다.

예를 들어

```text
목록
→ 9월 25일

상세
→ 2026년 9월 25일 14:30
```

처럼 역할에 따라 정할 수 있다.

---

## 숫자 단위도 붙이는 방식이 같아야 했다

```text
7km

7 km

7.0 KM
```

이 페이지마다 다르면

작은 차이지만 완성도가 떨어져 보일 수 있다.

```text
거리
→ km

시간
→ 32분

페이스
→ 6'20"/km
```

처럼 표현 규칙을 정해두는 것이 좋다.

---

## 0, 소수점, 천 단위도 규칙이 필요했다

예를 들어

```text
7

7.0

7.00
```

중 어떤 것을 보여줄지 정해야 한다.

금액이라면

```text
10000원

10,000원
```

차이도 있다.

데이터가 맞는 것만큼

사용자에게 일관된 방식으로 보여주는 것도 중요했다.

---

## 문구의 존댓말도 통일되어야 했다

한 화면에서는

```text
저장되었습니다.
```

라고 하고,

다른 화면에서는

```text
저장 완료!
```

또 다른 곳에서는

```text
저장했어요.
```

라고 한다.

각각은 자연스러울 수 있다.

하지만 같은 서비스 안에서 계속 바뀌면

서비스의 목소리가 일정하지 않아 보일 수 있다.

그래서

```text
~합니다.

~해요.

명사형
```

중 어떤 스타일을 사용할지 정하는 것도 작은 디자인 규칙이었다.

---

## 마침표 하나도 일관성이 있었다

예를 들어 짧은 Label에는

```text
현재 위치
```

처럼 마침표를 사용하지 않는다.

안내 문장에는

```text
현재 위치를 확인할 수 없습니다.
```

처럼 사용한다.

모든 문장에 반드시 같은 방식이 정답인 것은 아니지만

비슷한 역할의 문구끼리는 통일하면 더 깔끔하다.

---

## 영어 대소문자도 신경 쓰게 됐다

예를 들어

```text
GitHub

Github

github
```

가 섞일 수 있다.

브랜드 이름이나 기술 이름은

공식 표기를 가능한 한 일관되게 사용하는 것이 좋았다.

이것도 기능에는 전혀 영향을 주지 않지만

글이나 UI의 완성도에는 영향을 준다.

---

## Loading 문구도 서비스 말투와 연결됐다

```text
Loading...
```

라고 할 수도 있고

```text
불러오는 중...
```

이라고 할 수도 있다.

또

```text
주변 카페를 찾고 있어요.
```

처럼 현재 작업을 설명할 수도 있다.

기술적인 상태를 그대로 보여줄지,

사용자의 행동 언어로 바꿀지도 디자인의 일부였다.

---

## 빈 공간을 보면 무언가 넣고 싶어졌다

디자인에서 빈 곳이 있으면

```text
여기 허전한데
아이콘 하나 넣을까?
```

싶어진다.

하지만 여백은 문제 자체가 아닐 수 있다.

오히려

```text
정보 그룹을 분리하고

시선을 쉬게 하고

핵심 요소를 강조
```

하는 역할을 한다.

작은 디테일을 챙긴다고

모든 빈 공간을 장식으로 채우면 오히려 복잡해질 수 있다.

---

## 작은 디테일을 추가하는 것보다 빼는 것도 중요했다

예를 들어 카드 하나에

```text
Border

Shadow

Badge

Icon

Gradient

Hover Animation
```

이 전부 들어간다.

각각은 작은 개선처럼 보인다.

하지만 모이면 너무 강해진다.

그래서 디테일 개선에서도

```text
무엇을 더 넣을까?
```

만큼

```text
무엇을 뺄까?
```

가 중요했다.

---

## 화면에 필요한 것은 "반응"이지 "장식"만은 아니었다

좋은 작은 디테일을 구분하는 기준으로

나는 이런 질문이 도움이 된다고 생각한다.

```text
이 변화가 사용자가 현재 상태를 이해하는 데 도움이 되는가?
```

예를 들어

```text
Hover

Focus

Loading

Toast

Error
```

는 상태를 알려준다.

반대로 목적 없는 Animation은

상태 이해에는 크게 도움이 되지 않을 수도 있다.

---

## UI 디테일은 기능과 연결되어 있었다

예를 들어

```text
저장 버튼 Loading
```

은 디자인만의 문제가 아니다.

실제로 저장 요청 상태와 연결되어야 한다.

```text
API 요청 시작
↓
Loading
↓
성공
↓
Toast
```

흐름이 필요하다.

그래서 작은 UI를 만들면서

Frontend 상태 관리와도 연결됐다.

---

## 코드에서는 상태를 명확히 나누는 것이 도움이 됐다

개념적으로

```text
idle

loading

success

error
```

상태를 가지고 있다면

UI도 각각 다르게 표현할 수 있다.

```text
idle
→ 저장하기

loading
→ 저장 중...

success
→ 완료 안내

error
→ 오류 안내
```

디자인 상태와 코드 상태가 연결되는 것이다.

---

## 디자인만 있고 상태 구현이 없으면 의미가 없었다

Figma에

```text
Loading Button
```

을 예쁘게 만들어놨다.

그런데 개발에서는 항상 기본 버튼만 보여준다.

그러면 실제 서비스에는 Loading 디자인이 존재하지 않는 것과 같다.

반대로 개발자가 임의로 Loading 상태를 만들면

디자인과 달라질 수 있다.

그래서

```text
디자인 상태 정의

↓

개발 상태 구현
```

이 연결되어야 했다.

---

## 반대로 개발 상태만 만들고 디자인을 안 하면 어색해질 수 있었다

개발자가 기능 구현 중

```text
로딩 필요하네.
```

라고 생각해서

갑자기

```text
Loading...
```

문구 하나를 화면 왼쪽 위에 넣을 수 있다.

기능은 맞다.

하지만 전체 UI와 어울리지 않을 수 있다.

그래서 중요한 상태는

디자인 단계에서도 어느 정도 생각해두는 편이 좋았다.

---

## 모바일에서 키보드가 올라오는 것도 실제 UI 문제였다

입력창을 누르면 모바일 키보드가 화면 절반을 차지할 수 있다.

그 순간

```text
저장 버튼

다음 입력창
```

이 가려질 수 있다.

정적인 모바일 Screenshot에서는 보이지 않는 문제다.

Form이 많은 서비스라면

실제 모바일 입력까지 확인할 필요가 있었다.

---

## 자동 Focus도 조심해야 했다

페이지에 들어오자마자 입력창에 Focus를 주면

모바일에서 바로 키보드가 올라올 수 있다.

사용자가 아직 화면을 보기도 전에

절반이 키보드로 가려진다.

상황에 따라 편할 수도 있지만

항상 좋은 것은 아니었다.

---

## 복사 가능한 정보에는 복사 기능이 유용할 수 있었다

예를 들어

```text
초대 코드

주소

계좌번호

긴 식별값
```

을 사용자가 직접 드래그해서 복사해야 한다면 불편할 수 있다.

```text
[복사]
```

버튼이나 아이콘을 제공할 수 있다.

그리고 누르면

```text
복사했습니다.
```

라고 피드백을 준다.

작은 기능이지만 반복 작업을 줄인다.

---

## 하지만 모든 텍스트에 복사 버튼을 붙일 필요는 없다

이것도 디테일을 과하게 추가하는 문제가 생긴다.

```text
이름 [복사]

날짜 [복사]

상태 [복사]

제목 [복사]
```

가 되면 화면이 시끄러워진다.

정말 복사할 가능성이 높은 정보에만 제공하는 편이 좋다.

---

## 외부 링크라는 것도 표시할 수 있었다

사용자가

```text
길찾기
```

를 눌렀더니 다른 앱이나 사이트로 이동한다.

상황에 따라 사용자는 갑자기 서비스 밖으로 나가서 당황할 수 있다.

필요하다면

```text
외부 링크 아이콘
```

이나 문구로

다른 서비스로 이동한다는 것을 알려줄 수 있다.

모든 외부 링크에 반드시 필요한 것은 아니지만

중요한 이동이라면 생각해볼 수 있다.

---

## 링크와 버튼을 구분하는 것도 중요했다

처음에는 디자인을 위해

모든 것을 Button처럼 만들 수 있다.

하지만 역할이 다르다.

```text
Button
→ 현재 화면에서 행동

Link
→ 다른 위치로 이동
```

개념적으로 이렇게 구분할 수 있다.

실제 구현에서도 적절한 HTML 요소를 사용하면

키보드 접근성과 기본 동작 측면에서도 도움이 된다.

---

## 클릭 가능한 것처럼 보이면 실제로 클릭되어야 했다

예를 들어 Card에 Hover 효과가 있다.

Cursor도 Pointer다.

사용자는 누른다.

아무 일도 없다.

이것도 작은 불일치지만 꽤 당황스럽다.

반대로 클릭 가능한 카드인데

아무 시각적 힌트가 없다면 발견하기 어렵다.

```text
보이는 행동 가능성

vs

실제 행동
```

이 일치해야 했다.

---

## 로딩 중 버튼을 다시 누를 수 있는지도 확인했다

UI는

```text
저장 중...
```

이라고 표시되는데

실제로는 버튼이 계속 클릭 가능하다.

사용자가 여러 번 누른다.

중복 요청이 발생할 수 있다.

따라서 디자인 상태뿐 아니라

실제 Interaction도 맞아야 한다.

---

## 이미지가 없을 때도 생각해야 했다

카드에 항상 사진이 있다고 디자인했다.

실제 데이터에서는 사진이 없을 수 있다.

그때

```text
깨진 이미지 아이콘
```

이 보이면 완성도가 크게 떨어진다.

대신

```text
기본 이미지

브랜드 심볼

이미지 영역 숨김
```

등을 상황에 맞게 사용할 수 있다.

---

## 이미지 로딩 실패도 별도 문제였다

이미지 URL은 있지만

실제로 불러오지 못할 수 있다.

```text
404

네트워크 문제
```

등이다.

이때도 깨진 이미지가 그대로 보이지 않게

Fallback을 생각할 수 있다.

이런 상황은 정상 디자인만 보면 발견하기 어렵다.

---

## Avatar도 기본값이 필요할 수 있었다

사용자가 프로필 이미지를 등록하지 않았다.

그렇다면

```text
빈 원
```

만 보여줄 수도 있지만

```text
기본 프로필 아이콘

이름 첫 글자
```

등으로 표시할 수 있다.

예:

```text
[푸]
푸름
```

처럼 말이다.

---

## 작은 Loading Skeleton의 모양도 실제 콘텐츠와 비슷해야 했다

Skeleton을 사용할 때

실제 카드와 전혀 다른 모양이면

Loading이 끝나는 순간 Layout이 크게 바뀔 수 있다.

```text
작은 Skeleton
↓
엄청 큰 실제 Card
```

보다는

실제 콘텐츠 구조와 비슷한 Placeholder를 사용하는 편이 자연스럽다.

---

## Layout Shift가 생기지 않는지도 확인했다

예를 들어 이미지가 로드되기 전에는 높이가 0이다.

이미지가 로드되자

본문 전체가 아래로 밀린다.

사용자가 누르려던 버튼도 움직일 수 있다.

이미지 영역의 비율이나 크기를 미리 확보하면

이런 움직임을 줄일 수 있다.

이 역시 작은 디테일이지만

실제 사용에서는 꽤 눈에 띈다.

---

## 데이터가 업데이트될 때 갑자기 전체 화면이 깜빡이지 않는지도 봤다

작은 값 하나가 변경되었는데

페이지 전체가

```text
로딩 화면
↓
전체 다시 렌더링
```

되는 것처럼 보이면

사용 흐름이 끊길 수 있다.

가능하다면 변경된 부분만 자연스럽게 업데이트되는 것이 더 편할 수 있다.

물론 구현 방식과 서비스 구조에 따라 다르다.

---

## 숫자가 바뀔 때 위치가 움직이는 것도 있었다

예를 들어 Timer가

```text
9:59
↓
10:00
```

으로 바뀐다.

글자 폭이 달라져 주변 요소가 조금 움직일 수 있다.

러닝처럼 숫자가 계속 바뀌는 화면에서는

이런 미세한 흔들림도 반복해서 보인다.

숫자 표시 영역의 폭을 적절하게 확보하는 방법 등을 생각할 수 있다.

---

## 고정된 숫자 영역이 시각적으로 안정적일 수 있었다

예를 들어

```text
00:09:59
```

처럼 일정한 자리수를 사용하거나,

숫자 영역 자체에 충분한 폭을 둘 수 있다.

모든 경우에 필요한 것은 아니지만

실시간 데이터 화면에서는 이런 세부사항이 중요해질 수 있다.

---

## Empty State, Loading, Error를 같은 화면에서 비교해보는 것이 좋았다

「Empty State 설계」에서 Empty State를 따로 공부했다.

이번에 다른 상태까지 같이 놓고 보면 더 이해하기 쉽다.

```text
Loading
→ 아직 모름

Empty
→ 확인했는데 없음

Error
→ 확인하지 못함
```

세 상태는 화면이 비슷하게 비어 보일 수 있지만

사용자에게 전달해야 하는 의미가 완전히 다르다.

---

## 그 차이를 문구 하나로도 표현할 수 있었다

### Loading

```text
혜택을 불러오고 있어요.
```

### Empty

```text
아직 등록한 혜택이 없어요.
```

### Error

```text
혜택을 불러오지 못했어요.
```

문장은 비슷하지만

상태의 의미는 명확하게 다르다.

---

## 작은 UI 디테일을 한꺼번에 고치면 오히려 혼란스러웠다

서비스가 어느 정도 완성되면

고칠 것이 많이 보인다.

```text
버튼

간격

문구

아이콘

Loading

Toast

Hover
```

전부 한 번에 수정하고 싶어진다.

하지만 한꺼번에 바꾸면

어떤 수정이 실제로 좋아졌는지 확인하기 어렵다.

또 다른 화면과 일관성이 깨질 수도 있다.

---

## 공통 요소부터 고치는 것이 효율적이었다

예를 들어 모든 페이지의 Button이 조금 이상하다.

페이지 10개를 각각 고칠 필요보다

공통 Button Component를 수정하면 될 수 있다.

```text
Button Component 수정
↓
전체 페이지 반영
```

마찬가지로

```text
Input

Card

Header

Modal

Toast
```

같은 공통 UI부터 확인할 수 있다.

---

## 공통 Component가 있다고 자동으로 일관성이 생기는 것은 아니었다

같은 Button Component를 사용하면서도

페이지마다

```text
className

style

size
```

를 임의로 덮어쓰면

다시 제각각이 될 수 있다.

그래서 Component와 함께

```text
언제 어떤 Variant를 사용하는가
```

라는 규칙도 중요했다.

---

## 예를 들어 버튼 규칙을 정한다

```text
Primary
→ 화면당 핵심 행동

Secondary
→ 보조 행동

Ghost
→ 낮은 우선순위

Danger
→ 삭제 등 위험 행동

Icon
→ 익숙하고 짧은 보조 기능
```

이렇게 역할을 정하면

단순히 스타일만 재사용하는 것보다 일관성이 높아진다.

---

## 작은 디테일 체크는 기능 테스트와 따로 볼 수 있었다

기능 QA에서는

```text
로그인 된다.

저장된다.

삭제된다.
```

를 확인한다.

UI 디테일에서는

```text
로그인 중 상태가 보인다.

저장 완료를 알 수 있다.

삭제 버튼이 위험 행동처럼 보인다.
```

를 본다.

같은 기능을 다른 관점에서 보는 것이다.

---

## 내가 마지막에 화면을 볼 때 사용하는 방법

기능이 어느 정도 끝난 뒤

한 화면씩 아주 천천히 확인한다.

```text
Hover

Click

Tab

Scroll

Loading

Error

긴 데이터

빈 데이터

작은 화면
```

을 하나씩 테스트한다.

처음에는 귀찮아 보인다.

하지만 실제로 해보면

큰 기능 오류가 아니라

```text
어딘가 어설픈 느낌
```

의 원인을 찾는 데 도움이 됐다.

---

## 마우스 없이 사용해보는 것도 도움이 됐다

키보드의

```text
Tab

Enter

Space

Escape
```

만 사용해본다.

그러면

```text
Focus가 안 보임

Modal을 닫기 어려움

버튼 순서 이상
```

같은 문제를 찾을 수 있다.

---

## 모바일에서는 한 손으로 실제 눌러보는 것도 중요했다

버튼이 화면에는 잘 보인다.

하지만 엄지손가락으로 누르기 어려울 수 있다.

특히

```text
오른쪽 위 작은 버튼

화면 끝 아이콘

붙어 있는 두 버튼
```

에서 문제가 생긴다.

PC 개발자 도구만 보는 것과

실제 손으로 사용하는 것은 달랐다.

---

## 화면을 확대해서만 보면 안 됐다

개발 중에는 큰 모니터에서

UI를 크게 본다.

하지만 실제 사용자는

작은 스마트폰이나

축소된 브라우저에서 볼 수 있다.

그래서

```text
원래 사용 크기
```

에서 다시 보는 것이 필요하다.

파비콘이나 OG 이미지는 실제 사용 크기로 축소해서 확인해야 하는 것과 비슷하다.

---

## 작은 디테일은 각각 다른 문제가 아니라 연결되어 있었다

예를 들어 사용자가 저장 버튼을 여러 번 누른다.

표면적으로는

```text
사용자가 여러 번 클릭했다.
```

다.

하지만 원인은

```text
Loading 상태 없음

버튼 비활성화 안 됨

처리 중 Feedback 없음
```

일 수 있다.

즉 작은 UI 문제 하나가

실제 기능 문제로 이어질 수도 있다.

---

## UI 디테일은 신뢰감과도 연결됐다

예를 들어

```text
버튼 눌림

↓

아무 반응 없음

↓

3초 후 갑자기 페이지 이동
```

하면

사용자는

```text
이거 제대로 되는 거 맞아?
```

라고 생각할 수 있다.

반대로

```text
버튼 눌림

↓

처리 중 표시

↓

완료 안내
```

가 있으면

같은 3초여도 더 안정적으로 느껴질 수 있다.

서비스 속도를 실제로 빠르게 만들지 않아도

상태를 잘 알려주는 것만으로

사용 경험은 달라질 수 있었다.

---

## 작은 디테일이 서비스의 성격도 만들었다

예를 들어 같은 기능이어도

문구가

```text
삭제하시겠습니까?
```

인 서비스와

```text
이 기록을 삭제할까요?
```

인 서비스는 느낌이 조금 다르다.

Animation 속도,

Radius,

Icon,

Toast 문구 같은 요소가 반복되면서

서비스의 분위기가 만들어진다.

즉 디테일은 단순한 장식이 아니라

브랜드의 일부가 될 수도 있었다.

---

## 그렇다고 완벽한 UI를 만들려고 끝없이 수정하면 안 됐다

디테일을 보기 시작하면

끝이 없다.

```text
여기 1px

저기 2px

색 조금

Shadow 조금

Animation 조금
```

계속 고칠 수 있다.

그리고 어느 순간

```text
사용자가 느낄 차이
```

보다

```text
내가 알고 있기 때문에 보이는 차이
```

만 고치고 있을 수도 있다.

그래서 디테일 수정에도 우선순위가 필요했다.

---

## 내가 작은 UI 문제를 나누는 기준

### 1순위 — 사용을 방해함

```text
버튼 누르기 어려움

Focus 안 보임

Modal을 닫을 수 없음

긴 글자가 화면 깨뜨림
```

### 2순위 — 상태를 이해하기 어려움

```text
Loading 없음

성공 여부 모름

Error 원인 모름

Disabled 이유 모름
```

### 3순위 — 일관성이 깨짐

```text
Button 스타일 다름

아이콘 크기 다름

Padding 다름

문구 스타일 다름
```

### 4순위 — 순수한 시각적 마감

```text
Shadow 미세 조정

1~2px 정렬

Animation 느낌
```

이런 식으로 생각할 수 있다.

---

## 눈에 보이는 모든 차이를 버그라고 볼 필요는 없었다

Figma와 실제 화면이

```text
1px 다름
```

이라고 무조건 수정해야 하는 것은 아니다.

브라우저의 글꼴 렌더링이나

반응형 Layout 때문에

조금씩 차이가 날 수 있다.

중요한 것은

```text
정보 구조

우선순위

사용성

전체적인 디자인 규칙
```

이 유지되는가였다.

---

## 반대로 작아 보여도 꼭 수정해야 하는 문제도 있었다

예를 들어

```text
삭제 버튼과 저장 버튼 사이가 너무 가까움
```

은 디자인상 아주 작은 간격 문제처럼 보인다.

하지만 실제로는 잘못 누를 위험이 있다.

그러면 작은 시각적 문제이면서

큰 사용성 문제다.

그래서

```text
크기가 작은 문제
=
중요도가 낮은 문제
```

는 아니었다.

---

## "왜 고치는가?"를 설명할 수 있어야 했다

예를 들어

```text
Button Radius 12 → 14
```

로 바꾼다.

왜?

```text
그냥 14가 더 예뻐서
```

일 수도 있다.

하지만 모든 버튼을 수정하고 구현까지 바꾸려면

그 이유가 충분한지 생각해볼 수 있다.

반대로

```text
저장 중인지 알 수 없어 중복 클릭이 발생
```

한다면

Loading 상태를 추가할 이유는 명확하다.

이 차이가 중요했다.

---

## 디테일을 수정할수록 기준이 필요해졌다

처음에는 문제가 크기 때문에 수정한다.

```text
버튼을 못 찾음
```

처럼 명확하다.

서비스가 완성될수록 문제는 작아진다.

```text
이 간격이 조금 더 좁은 게 좋나?

이 아이콘이 1px 아래인가?

이 Toast가 필요한가?
```

판단하기 어려워진다.

그래서

**무엇을 수정하고 무엇을 그대로 둘 것인지 판단하는 기준**

이 필요해졌다.

---

## 지금까지 공부한 내용을 다시 사용할 수 있었다

화면의 작은 부분을 수정할 때도

앞에서 공부한 기준을 다시 사용할 수 있다.

```text
시선 흐름

사용성

정보 우선순위

페이지 목적

반응형

실제 시연 결과
```

예를 들어

```text
버튼 색을 바꿀까?
```

라는 문제도

```text
현재 버튼이 핵심 행동인데
사용자가 잘 못 찾는가?
```

를 기준으로 판단할 수 있다.

---

## 내가 마지막 UI 점검에서 확인하고 싶은 것

전체적으로 정리하면 다음과 같다.

```text
□ 클릭 가능한 요소에 적절한 반응이 있는가?

□ 중요한 Focus 상태가 보이는가?

□ Disabled 이유를 이해할 수 있는가?

□ Loading 상태가 있는가?

□ 중복 클릭이 방지되는가?

□ 작업 성공 여부를 알 수 있는가?

□ 오류 원인과 다음 행동을 알 수 있는가?

□ 긴 텍스트에서도 Layout이 깨지지 않는가?

□ 실제 숫자가 커져도 문제가 없는가?

□ 이미지가 없거나 실패했을 때 대체 UI가 있는가?

□ 아이콘 크기와 정렬이 일관되는가?

□ 같은 종류의 Button / Input / Card가 일관적인가?

□ Padding과 Gap 규칙이 일정한가?

□ Modal을 쉽게 닫을 수 있는가?

□ 위험 행동을 실수로 누르기 어렵게 되어 있는가?

□ 날짜·시간·숫자·단위 표기가 일관적인가?

□ UI 문구의 말투가 통일되어 있는가?

□ 모바일 키보드가 UI를 가리지 않는가?

□ 고정 UI끼리 겹치지 않는가?

□ 실제 기기에서 눌러보기 쉬운가?
```

---

## 모든 항목을 모든 프로젝트에 넣을 필요는 없다

이 체크리스트를 보면

```text
해야 할 게 또 이렇게 많아?
```

싶을 수 있다.

하지만 모든 서비스에 모든 요소가 필요한 것은 아니다.

예를 들어

Form이 없는 페이지라면

입력 오류 UI를 고민할 필요가 없다.

Modal이 없다면

Modal Focus도 필요 없다.

중요한 것은

```text
내 서비스에 존재하는 상호작용을
끝까지 확인하는 것
```

이다.

---

## MVP에서도 최소한의 디테일은 필요했다

MVP라고 해서

```text
Loading 없음

Error 없음

버튼 상태 없음
```

이어야 하는 것은 아니다.

기능을 많이 줄이는 것과

사용자가 현재 상태를 이해하지 못하게 만드는 것은 다른 문제다.

MVP에서도 핵심 흐름에 대해서는

```text
Loading

Error

Success

Empty
```

같은 기본 상태가 필요할 수 있다.

---

## 반대로 MVP에서 굳이 하지 않아도 되는 디테일도 있었다

예를 들어

```text
복잡한 Animation

화려한 Hover

수십 가지 Transition

고급 Motion
```

은 핵심 기능 검증과 직접 관련이 없다면

후순위로 둘 수 있다.

중요한 것은

```text
작은 UI 디테일
=
전부 지금 해야 하는 것
```

이라고 생각하지 않는 것이다.

---

## 작은 디테일도 Backlog로 보낼 수 있었다

지금 고치고 싶지만

MVP 사용을 막지는 않는다.

그러면

```text
Backlog
```

에 기록할 수 있다.

예를 들어

```text
- Toast Animation 개선
- 일부 Icon Alignment 정리
- Hover Transition 통일
```

처럼 남긴다.

그러면

```text
잊지 않으면서도
현재 개발을 멈추지 않을 수 있다.
```

---

## 완성도와 일정 사이에서도 판단해야 했다

디자인을 조금 더 다듬으면 좋아질 것 같다.

하지만 배포 일정이 있다.

그때

```text
지금 반드시 필요한가?
```

를 확인한다.

사용을 방해하는 문제라면 수정한다.

순수한 취향 차이라면

다음 버전으로 보낼 수 있다.

---

## 작은 UI 디테일을 공부하면서 느낀 것

처음에는 완성도란

```text
예쁜 디자인
```

이라고 생각했다.

지금은 조금 다르게 생각한다.

```text
버튼을 누르면 반응하고

기다리면 기다리는 중이라고 알려주고

오류가 나면 이유를 알려주고

데이터가 없으면 다음 행동을 보여주고

긴 글자가 와도 화면이 무너지지 않는 것
```

도 모두 완성도의 일부였다.

---

## 완성도는 사용자의 질문을 줄이는 것이기도 했다

잘 정리된 UI에서는

사용자가 이런 질문을 덜 한다.

```text
눌린 건가?

저장된 건가?

왜 안 돼?

어디를 눌러야 해?

이게 뭔데?

왜 갑자기 움직였어?
```

작은 UI 디테일들이

이런 질문에 화면 스스로 답해주는 것이다.

---

## 큰 디자인보다 작은 상태가 더 자주 보일 수도 있었다

사용자는 Hero Section을 한 번 본다.

하지만 버튼 Hover,

Loading,

Error,

Toast,

Form 입력은

서비스를 사용할 때 계속 만난다.

그래서

```text
눈에 잘 띄는 큰 디자인
```

만큼

```text
반복해서 만나는 작은 상태
```

도 중요했다.

---

## 결국 서비스는 정지된 이미지가 아니었다

Figma에서는

```text
한 화면
```

을 본다.

실제 서비스에서는

```text
마우스를 올리고

누르고

기다리고

입력하고

실수하고

수정하고

저장한다.
```

UI는 계속 변한다.

그래서 완성도를 높인다는 것은

한 장의 Screenshot을 더 예쁘게 만드는 것뿐 아니라

**그 사이의 모든 상태를 자연스럽게 연결하는 것**

이라고 생각하게 됐다.

---

## 내가 작은 UI 디테일을 정리할 때 지키고 싶은 기준

마지막으로 정리하면 다음과 같다.

```text
1. 정지 화면뿐 아니라 상태 변화를 확인한다.

2. Hover를 핵심 기능의 유일한 진입점으로 사용하지 않는다.

3. Focus 상태를 무조건 제거하지 않는다.

4. Disabled 이유를 사용자가 이해할 수 있게 한다.

5. 비동기 작업에는 적절한 Loading Feedback을 준다.

6. 성공 여부가 불분명한 작업에는 완료 피드백을 제공한다.

7. Error는 원인과 다음 행동을 함께 알려준다.

8. 긴 텍스트와 큰 숫자를 실제로 테스트한다.

9. 이미지가 없거나 실패하는 상태도 준비한다.

10. Icon, Gap, Radius, Padding 규칙을 통일한다.

11. Modal과 위험 행동은 실수 가능성을 고려한다.

12. 날짜·단위·문구 표현을 일관되게 사용한다.

13. 고정 UI가 콘텐츠를 가리지 않는지 확인한다.

14. 실제 모바일 환경에서도 눌러본다.

15. 디테일을 추가하는 것뿐 아니라 불필요한 요소를 뺀다.

16. 모든 디테일을 한 번에 고치지 않고 중요도에 따라 수정한다.

17. 사용에 영향을 주지 않는 순수 취향 수정은 후순위로 보낼 수 있다.
```

## 마무리

프로젝트 초반에는

큰 문제만 보였다.

```text
로그인이 안 됨

페이지가 없음

DB 연결 안 됨

버튼이 작동하지 않음
```

그런 문제를 하나씩 해결하고 나니

그제야 작은 것이 보이기 시작했다.

```text
버튼을 눌렀는데 반응이 늦음

Icon이 조금 어긋남

긴 텍스트가 잘림

문구가 페이지마다 다름

저장됐는지 알 수 없음
```

각각만 놓고 보면 사소하다.

하지만 사용자는 서비스를

하나의 전체 경험으로 느낀다.

그래서 이런 작은 차이가 계속 쌓이면

```text
기능은 되는데 어딘가 미완성인 서비스
```

가 될 수도 있고,

반대로 작은 부분이 자연스럽게 연결되어 있으면

```text
세세한 부분까지 정리된 서비스
```

처럼 느껴질 수도 있다.

결국 서비스의 완성도를 높이는 것은

새로운 기능을 계속 추가하는 것만은 아니었다.

> **이미 있는 기능이 사용자의 행동에 자연스럽게 반응하도록 다듬는 것**

도 중요한 작업이었다.

그런데 이런 디테일을 보기 시작하면

또 하나의 문제가 생긴다.

```text
이것도 고칠까?

저것도 바꿀까?

색상을 바꿀까?

간격을 줄일까?

버튼을 더 크게 할까?
```

수정할 수 있는 부분이 끝없이 보이기 시작한다.

실제로 모든 디자인 차이를 계속 수정하다 보면

언제 디자인을 확정해야 하는지도 애매해진다.

그래서 마지막으로 필요한 것은

```text
무엇을 수정해야 하고

무엇은 그대로 두어도 되는지
```

판단하는 기준이었다.
