## 들어가며

처음에 나는 Frontend를 "화면을 예쁘게 만드는 영역"이라고 생각했다. 디자인대로 배치하고 색을 맞추면 끝나는 줄 알았다.

그런데 실제로 프로젝트를 해보니 화면을 다 만들고 나서가 진짜 시작이었다. 버튼을 눌렀을 때 무슨 일이 일어날지, 입력한 값을 어디에 담아둘지, 서버에 언제 요청을 보낼지, 응답을 기다리는 동안 무엇을 보여줄지, 실패하면 어떻게 할지를 전부 정해야 했다.

화면이 있다는 것과 기능이 동작한다는 것이 완전히 다른 일이었다. 그래서 **화면이 실제 기능이 되기까지 무엇이 필요한지**를 처음부터 다시 정리해보려고 한다.

이 글은 프로젝트 회고가 아니라 개념 정리 노트다. 중심은 **UI → Component → State → Event → API → Data → Rendering** 이 흐름이다.

## 1. Frontend란 무엇인가

**Frontend(프론트엔드)** 는 **사용자가 직접 보고 조작하는 영역**이다.

여기까지는 알고 있었는데, 문제는 그 다음이었다. **Frontend가 디자인만 담당하는 게 아니라는 점**을 몰랐다.

실제로 Frontend가 다루는 것들을 적어보면 이렇다.

| 하는 일 | 예 |
|---|---|
| 화면 표시 | 기록 목록을 보여준다 |
| 버튼 클릭 처리 | 저장 버튼을 누르면 무언가 일어난다 |
| 입력값 처리 | 사용자가 친 글자를 받아서 다룬다 |
| 상태 변화 관리 | 로딩 중인지, 로그인했는지를 기억한다 |
| 서버 요청 | 필요한 데이터를 Backend에 요청한다 |
| 받은 데이터 표시 | 응답으로 온 값을 화면에 그린다 |

보다시피 **절반 이상이 "보이는 것"이 아니라 "동작하는 것"** 이다. 모양을 만드는 일은 Frontend가 하는 일 중 일부였다.

## 2. 브라우저는 무엇을 하는가

Frontend 코드는 **브라우저(Browser)** 안에서 실행된다.

브라우저는 서버에서 받아온 파일들을 해석해서 화면과 동작을 만들어낸다.

```text
서버에서 받은 파일
↓
브라우저가 해석
↓
화면이 그려지고 동작이 붙는다
```

해석하는 대상은 크게 세 가지다. HTML, CSS, JavaScript다.

내가 작성한 코드가 그대로 화면이 되는 게 아니라, **브라우저라는 프로그램이 그걸 읽고 해석해서 만들어준다**는 점이 중요했다. 그래서 같은 코드라도 브라우저에 따라 조금씩 다르게 보일 수 있다.

브라우저 내부가 어떻게 동작하는지는 더 깊은 주제라서 여기서는 **"코드를 해석해서 화면으로 만들어주는 프로그램"** 까지만 짚고 넘어간다.

## 3. HTML / CSS / JavaScript 역할

세 가지의 역할은 이렇게 나뉜다.

| 구분 | 담당 | 비유하면 |
|---|---|---|
| HTML | 구조 | 건물의 뼈대와 방 배치 |
| CSS | 표현과 스타일 | 벽지, 색, 가구 배치 |
| JavaScript | 동작과 로직 | 전기와 배관처럼 실제로 작동하는 것 |

버튼을 예로 들면 이렇게 나뉜다.

```text
HTML        "여기 버튼이 하나 있다"
CSS         "그 버튼은 파란색이고 둥글다"
JavaScript  "그 버튼을 누르면 기록이 저장된다"
```

세 개가 다 있어야 **보이고, 예쁘고, 동작하는** 버튼이 된다. HTML과 CSS만 있으면 눌러도 아무 일도 일어나지 않는 그림일 뿐이다.

한 가지 짚어둘 점이 있다. **실제 프로젝트에서는 이 셋이 명확히 나뉘어 보이지 않을 수 있다.** React 같은 도구를 쓰면 하나의 파일 안에 구조와 로직이 함께 들어가고, 스타일도 같은 곳에서 다루는 방식이 있다. 역할은 여전히 나뉘어 있지만 **파일이 나뉘어 있지는 않다**는 점이 처음에 헷갈렸다.

## 4. React는 무엇인가

**React(리액트)** 는 **사용자 인터페이스를 Component 단위로 만들고, 상태가 바뀌면 화면을 다시 반영하기 쉽게 도와주는 라이브러리**다.

React가 해결하려는 문제를 보면 왜 쓰는지가 보인다.

JavaScript만으로 화면을 다루려면 "이 값이 바뀌었으니 저 부분의 글자를 바꾸고, 저 목록에 항목을 하나 추가하고..." 하는 식으로 **바뀔 부분을 하나하나 직접 지시해야 한다.** 화면이 복잡해질수록 이게 감당이 안 된다.

React는 방식이 다르다. **"상태가 이러면 화면은 이렇게 생긴다"고 적어두면, 상태가 바뀔 때 화면을 알아서 맞춰준다.**

```text
직접 다루는 방식   값이 바뀌었다 → 화면의 어디를 어떻게 고칠지 지시
React 방식         값이 바뀌었다 → 화면이 알아서 다시 반영된다
```

여기서 단정하면 안 되는 게 있다. **React가 Frontend 전체는 아니다.** React 없이도 Frontend는 만들 수 있고, React는 그중 UI를 다루는 부분을 도와주는 도구 하나다. 라우팅이나 서버 통신 같은 것들은 React 자체가 담당하지 않는다.

## 5. Component란 무엇인가

**Component(컴포넌트)** 는 **화면을 재사용 가능한 작은 단위로 나눈 것**이다. React의 핵심 개념이다.

화면 하나를 통째로 만드는 대신, 부분부분을 따로 만들어서 조립한다.

```text
RunPage
├─ Header
├─ Map
├─ DistanceCard
├─ Timer
└─ StopButton
```

`RunPage`라는 화면 하나가 다섯 개의 조각으로 나뉘어 있다. 각 조각은 자기 역할만 신경 쓰면 된다.

### 왜 나누는가

| 이유 | 설명 |
|---|---|
| 재사용 | `DistanceCard`를 다른 화면에서도 그대로 쓸 수 있다 |
| 역할 분리 | Timer는 시간만, Map은 지도만 담당한다 |
| 수정 범위 관리 | 타이머를 고칠 때 지도 코드를 건드리지 않는다 |
| 읽기 쉬움 | 화면 구조가 목록만 봐도 파악된다 |

**수정 범위 관리**가 특히 체감됐다. 한 파일에 전부 들어 있으면 뭘 하나 고칠 때마다 다른 게 깨질까 봐 불안하다. 나뉘어 있으면 고칠 곳이 명확하다.

## 6. Component를 너무 잘게 나누면 무조건 좋은가

나누는 게 좋다고 하니 처음에는 최대한 잘게 쪼개려고 했다. 그런데 그것도 답이 아니었다.

너무 잘게 나누면 이런 문제가 생긴다.

- 파일이 너무 많아져서 뭐가 어디 있는지 찾기 어렵다
- 값을 전달하는 단계가 길어져서 따라가기 힘들다
- 한 번만 쓰이는 조각까지 전부 분리하면 오히려 읽기 불편하다

그래서 기준을 이렇게 잡았다.

| 나누는 게 좋은 경우 | 그대로 두는 게 나은 경우 |
|---|---|
| 여러 곳에서 재사용된다 | 그 화면에서만 한 번 쓰인다 |
| 독립적인 역할이 분명하다 | 주변 내용과 떼어놓으면 의미가 없다 |
| 그 부분만 따로 고칠 일이 많다 | 항상 함께 수정된다 |

**"작으면 좋다"가 아니라 "역할이 분명하고 재사용할 만하면 나눈다"** 가 기준이었다.

## 7. Props란 무엇인가

Component를 나눴으면 서로 값을 주고받아야 한다. 그 수단이 **Props(프롭스)** 다.

Props는 **부모 Component가 자식 Component에게 전달하는 값**이다.

```text
RunPage          거리 값 5.2를 가지고 있다
↓ distance 전달
DistanceCard     전달받은 값으로 화면을 그린다
↓
"5.2 km" 표시
```

`DistanceCard`는 거리가 얼마인지 스스로 알아내지 않는다. **부모가 알려준 값을 받아서 보여주기만 한다.** 그래서 같은 `DistanceCard`를 다른 화면에서 다른 값으로 재사용할 수 있다.

여기서 중요한 성질이 하나 있다. **Props는 받은 쪽에서 마음대로 바꾸는 값이 아니다.**

일반 변수라면 받아서 고쳐 쓸 수 있다. 하지만 Props를 자식이 임의로 바꾸면 **화면에 보이는 값과 부모가 알고 있는 값이 달라진다.** 그러면 누가 진짜인지 알 수 없어진다.

그래서 **값을 내려주는 방향은 부모에서 자식으로 한 방향**이고, 값을 바꿔야 한다면 그 값을 가진 쪽에서 바꾼다. 이 규칙 덕분에 값이 어디서 왔는지 따라가기 쉬워진다.

## 8. State란 무엇인가

**State(상태)** 는 **화면이 기억해야 하는 현재 상태**다.

Frontend에서 가장 중요한 개념이라고 느꼈다.

화면은 고정된 그림이 아니다. 사용자가 무언가를 하면 바뀌어야 한다. 그러려면 **지금 어떤 상태인지를 어딘가에 기억하고 있어야 한다.** 그게 State다.

기억해야 하는 것들의 예를 들면 이렇다.

| State | 무엇을 기억하는가 |
|---|---|
| 현재 거리 | 지금까지 몇 km 달렸는지 |
| 경과 시간 | 시작한 지 얼마나 됐는지 |
| 로그인 여부 | 사용자가 로그인했는지 |
| 선택된 탭 | 지금 어느 탭을 보고 있는지 |
| 입력값 | 사용자가 입력창에 뭐라고 쳤는지 |
| 로딩 여부 | 지금 서버 응답을 기다리는 중인지 |

핵심은 이것이다. **State가 바뀌면 화면도 그에 맞게 다시 반영된다.**

```text
State 변경
↓
화면이 그 상태에 맞게 다시 그려진다
```

내가 "이 글자를 바꿔라"라고 지시하지 않는다. **상태만 바꾸면 화면은 따라온다.** 이게 4번에서 말한 React의 방식이다.

## 9. Props와 State 차이

둘 다 Component가 다루는 값이라서 헷갈렸다. 차이는 **누구의 것인가**에 있었다.

| 구분 | Props | State |
|---|---|---|
| 어디서 오는가 | 부모에게서 전달받는다 | 그 Component가 스스로 가진다 |
| 누가 바꾸는가 | 값을 가진 부모가 바꾼다 | 그 Component가 바꾼다 |
| 방향 | 부모에서 자식으로 한 방향 | 자기 안에서 관리 |
| 비유 | 밖에서 건네받은 것 | 내가 기억하고 있는 것 |

```text
Props   →  밖에서 전달받는 값
State   →  Component가 관리하는 현재 상태
```

같은 값이라도 어느 쪽인지는 **어디에서 그 값을 관리하느냐**에 따라 달라진다. `RunPage`가 거리를 State로 가지고 있고, 그걸 `DistanceCard`에 넘기면, 같은 거리 값이 부모에게는 State이고 자식에게는 Props다.

React 내부에서 이 둘을 어떻게 처리하는지는 더 깊은 주제라서 여기서는 **"밖에서 받은 값인가, 내가 가진 값인가"** 까지만 구분해둔다.

## 10. Event란 무엇인가

**Event(이벤트)** 는 **사용자의 행동을 Frontend가 감지하는 것**이다.

| Event | 언제 |
|---|---|
| 클릭 | 버튼이나 요소를 눌렀을 때 |
| 입력 | 입력창에 글자를 칠 때 |
| 제출 | 폼을 제출했을 때 |
| 스크롤 | 화면을 위아래로 움직일 때 |

여기서 중요한 오해가 하나 있었다.

**버튼을 클릭한다고 저절로 무슨 일이 일어나지 않는다.**

HTML로 버튼을 만들면 눌리는 모양은 나온다. 손가락 커서도 뜨고 눌리는 효과도 보인다. 하지만 **거기까지다.** 눌렀을 때 무엇을 할지는 따로 연결해줘야 한다.

그 연결하는 코드를 **Event Handler(이벤트 핸들러)** 라고 한다. "이 버튼이 눌리면 이 함수를 실행하라"고 등록해두는 것이다.

```text
버튼만 있음        →  눌려도 아무 일 없음
Handler 연결됨     →  누르면 등록한 동작이 실행됨
```

"버튼이 있다"와 "버튼이 동작한다"가 다른 이유가 여기에 있다.

## 11. 버튼을 누르면 실제로 무엇이 일어나는가

앞의 개념들을 이어서, 버튼 하나를 누를 때 일어나는 일을 순서대로 보면 이렇다.

```text
사용자
↓
버튼 클릭              브라우저가 클릭을 감지한다
↓
Event Handler 실행      등록해둔 함수가 실행된다
↓
State 변경 또는 API 요청  상태를 바꾸거나 서버에 요청한다
↓
결과 처리               성공/실패에 따라 State를 갱신한다
↓
화면 업데이트           바뀐 State에 맞게 화면이 다시 그려진다
```

처음에는 "버튼을 누르면 저장된다"를 한 덩어리로 생각했다. 그런데 실제로는 이만큼의 단계가 있었다.

그래서 **저장이 안 될 때 확인할 곳이 여러 군데**였다. Handler가 연결이 안 됐을 수도 있고, 실행은 됐는데 요청이 안 나갔을 수도 있고, 요청은 갔는데 실패했을 수도 있고, 성공했는데 화면만 안 바뀌었을 수도 있다.

**이 단계를 알고 나서야 "어디서 멈췄는지" 물어볼 수 있게 됐다.**

## 12. Form과 사용자 입력

사용자에게 값을 받을 때는 입력 요소를 쓴다.

| 요소 | 역할 |
|---|---|
| input | 사용자가 값을 입력하는 칸 |
| form | 여러 입력을 묶어서 한 번에 제출하는 단위 |

입력값도 결국 **State로 관리된다.** 사용자가 글자를 칠 때마다 입력 Event가 발생하고, 그때마다 State를 갱신한다. 그러면 화면에 보이는 글자와 코드가 알고 있는 값이 항상 일치한다.

```text
사용자가 글자를 친다
↓
입력 Event 발생
↓
State에 그 값을 저장
↓
화면에 그 State 값이 표시됨
```

처음에는 "입력창에 글자가 보이니까 값이 있는 것"이라고 생각했는데, **코드가 그 값을 알고 있으려면 State로 받아둬야 한다**는 걸 알았다.

제출할 때는 그 State에 담긴 값을 가지고 다음 단계로 넘어간다. 그 직전에 하는 일이 Validation이다.

## 13. Frontend Validation

**Validation(검증)** 은 **입력된 값이 올바른지 확인하는 것**이다. Frontend에서도 한다.

| 확인하는 것 | 예 |
|---|---|
| 빈 입력값 | 닉네임을 안 적고 제출하려고 하는가 |
| 글자 수 | 너무 짧거나 길지 않은가 |
| 형식 | 이메일 형태가 맞는가, 숫자 자리에 글자가 있지 않은가 |

Frontend에서 검증하는 이유는 **사용자에게 빠르게 알려주기 위해서**다. 서버까지 갔다 와서 "닉네임을 입력하세요"라는 답을 받는 것보다, 입력하는 순간 바로 알려주는 편이 훨씬 낫다.

여기서 중요한 건 **역할의 차이**다.

```text
Frontend Validation   사용자가 실수를 빨리 알아차리게 돕는 것
Backend Validation    잘못된 데이터가 실제로 저장되는 걸 막는 것
```

**Frontend 검증이 Backend 검증을 대신하지 않는다.** 브라우저에서 실행되는 코드는 사용자가 건너뛸 수 있고, 화면을 거치지 않고 서버에 직접 요청을 보낼 수도 있다. 중요한 규칙은 양쪽에서 확인해야 한다.

Backend 쪽 이야기는 Backend 글에서 정리했으니 여기서는 이 연결만 짚어둔다.

## 14. 화면에 보이는 데이터는 어디서 오는가

화면에 숫자 하나가 보인다. 그 값은 어디서 왔을까? **경우가 여러 가지다.**

| 출처 | 어떤 값인가 |
|---|---|
| 코드에 직접 쓴 값 | 개발자가 파일에 적어둔 고정된 값 |
| State에 들어 있는 값 | 화면이 기억하고 있는 현재 상태 |
| 사용자 입력값 | 방금 사용자가 입력한 값 |
| API에서 받은 값 | 서버에 요청해서 받아온 값 |
| 서버나 DB에서 온 값 | 실제로 저장되어 있던 데이터 |

**화면만 봐서는 이 다섯 가지가 구분되지 않는다.** 전부 똑같이 잘 보인다.

그래서 이 결론에 도달했다.

```text
화면에 숫자가 보인다
       (같지 않다)
Database에서 가져온 것이다
```

Database 글에서도 같은 이야기를 했는데, Frontend 쪽에서 보니 왜 그런지가 더 분명해졌다. **화면을 그리는 코드 입장에서는 값이 어디서 왔든 상관없다.** 값만 있으면 그린다.

확인하려면 화면이 아니라 **실제로 요청이 나갔는지, 응답이 왔는지**를 봐야 한다.

## 15. Mock Data란 무엇인가

앞의 첫 번째 경우가 특히 자주 등장한다.

**Mock Data(목 데이터)** 는 **실제 서버 연결 전에 화면이나 기능을 테스트하기 위해 임시로 만든 데이터**다.

```text
const distance = 5.2
```

이런 값이 코드에 들어 있으면 화면에는 "5.2 km"가 잘 나온다. 하지만 이건 **개발자가 적어둔 숫자**일 뿐이다. 러닝 기록 데이터베이스와는 아무 관계가 없다.

왜 이런 걸 쓸까? **화면을 먼저 만들어야 할 때가 있기 때문**이다.

- Backend가 아직 준비되지 않았을 때
- 화면 디자인이 맞는지 먼저 확인하고 싶을 때
- 데이터가 많을 때 어떻게 보이는지 테스트할 때

문제는 **Mock Data를 그대로 두고 "화면 완성"이라고 판단하기 쉽다는 것**이다. 화면은 완벽하게 잘 나오니까 다 된 것처럼 보인다. 실제 연결은 아직 시작도 안 했는데도.

## 16. Mock Data와 실제 Data

둘의 차이를 정리해둔다.

| 구분 | Mock Data | Real Data |
|---|---|---|
| 어디서 오는가 | 코드에 적혀 있다 | 서버나 실제 시스템에서 받아온다 |
| 목적 | 화면과 기능 테스트 | 실제 서비스 제공 |
| 값이 바뀌는가 | 코드를 고쳐야 바뀐다 | 실제 데이터에 따라 바뀐다 |
| 사용자마다 | 모두에게 같다 | 사용자마다 다르다 |
| 연결 상태 | 서버 없이도 보인다 | 서버가 있어야 보인다 |

**"사용자마다 다른가"** 가 구분하기 좋은 기준이었다. Mock Data는 누가 접속해도 똑같은 값이 나온다. 실제 데이터라면 내 기록과 다른 사람의 기록이 달라야 한다.

Mock에서 실제 데이터로 넘어가려면 **API 호출을 붙이는 작업**이 필요하다. 그게 다음 단계다.

## 17. API를 호출한다는 것은 무엇인가

API가 무엇인지는 Backend 글에서 정리했으니, 여기서는 **Frontend 입장에서 무엇을 하는가**만 본다.

Frontend에서 API를 호출한다는 건 **필요한 데이터를 서버에 요청해서 받아오는 것**이다.

```text
Frontend
↓
Request           "내 러닝 기록을 줘"
↓
Backend API       요청을 처리한다
↓
Response          기록 데이터를 돌려준다
↓
Frontend
↓
화면 업데이트      받은 데이터로 화면을 그린다
```

핵심은 **Frontend가 데이터를 직접 가지고 있지 않다**는 점이다. 필요할 때마다 요청해서 받아온다.

그리고 **Frontend는 Database에 직접 접근하지 않는다.** 항상 Backend를 거친다. 브라우저에서 돌아가는 코드는 사용자가 전부 열어볼 수 있기 때문에, 데이터베이스 접속 정보를 거기에 둘 수 없다.

## 18. Fetch란 무엇인가

**Fetch**는 **JavaScript에서 HTTP 요청을 보낼 수 있는 방법 중 하나**다. 브라우저에 기본으로 들어 있다.

```text
fetch 를 사용해서
"기록 데이터를 서버에서 가져온다"
```

이 글에서 사용법을 자세히 다루지는 않는다. 지금 알아둘 것은 **Frontend에서 서버로 요청을 보내는 수단이 있고, 그중 하나가 fetch**라는 정도다.

같은 일을 하는 다른 도구도 있다. Axios 같은 이름을 보게 되는데, **서버에 요청을 보낸다는 목적은 같고 쓰기 편하게 만들어둔 도구**라고 이해하면 된다. 어느 것을 쓰든 오가는 건 앞에서 정리한 Request와 Response다.

여기서 중요한 성질이 하나 있다. **요청을 보낸다고 결과가 바로 오지 않는다.** 서버까지 갔다 와야 하니까 시간이 걸린다. 그래서 다음 이야기가 필요해진다.

## 19. Loading 상태는 왜 필요한가

API 요청은 즉시 끝나지 않는다. 짧으면 몇십 밀리초, 길면 몇 초가 걸린다.

그 사이에 화면은 어떻게 되어 있을까? **아무것도 하지 않으면 빈 화면이 보인다.** 사용자는 고장 났다고 생각한다.

그래서 요청의 진행 상태를 State로 관리한다.

| 상태 | 언제 | 화면에 무엇을 보여주는가 |
|---|---|---|
| loading | 요청을 보내고 기다리는 중 | 로딩 표시, 스켈레톤 화면 |
| success | 응답이 정상적으로 왔을 때 | 받아온 데이터 |
| error | 요청이 실패했을 때 | 오류 메시지, 다시 시도 버튼 |

```text
버튼 클릭
↓
loading = true       로딩 표시가 나타난다
↓
API 요청
↓
응답 도착
↓
loading = false      로딩 표시가 사라지고
success 또는 error    결과에 맞는 화면이 나타난다
```

**화면에는 데이터를 보여주는 것 말고도 "기다리는 중"이라는 상태를 보여줄 자리가 필요했다.** 이걸 처음에는 생각하지 못했다.

## 20. Error 상태는 왜 따로 관리하는가

요청이 실패할 수 있다. 서버가 응답하지 않거나, 권한이 없거나, 네트워크가 끊길 수 있다.

이때 아무 처리도 하지 않으면 **빈 화면**이 남는다. 사용자는 무슨 일이 일어났는지 알 수 없다.

Error 상태를 따로 관리하면 이런 걸 보여줄 수 있다.

| 보여줄 수 있는 것 | 왜 필요한가 |
|---|---|
| 오류 메시지 | 무엇이 잘못됐는지 알려준다 |
| 다시 시도 버튼 | 일시적인 문제면 다시 해볼 수 있다 |
| 대체 UI | 일부가 실패해도 나머지는 쓸 수 있게 한다 |

**성공하는 경우만 만들어두면 절반만 만든 것**이었다. 실제로 쓰다 보면 실패하는 경우가 반드시 생기고, 그때 화면이 어떻게 되는지도 정해둬야 한다.

그래서 기능 하나를 만들 때 **loading, success, error 세 가지 화면을 다 생각하는 습관**을 들이게 됐다.

## 21. 비동기 처리란 무엇인가

요청을 보내고 응답을 기다리는 동안, 브라우저는 무엇을 하고 있을까?

만약 **멈춰서 기다린다면** 큰 문제다. 그동안 스크롤도 안 되고 다른 버튼도 안 눌린다. 화면이 얼어붙는다.

그래서 JavaScript는 **비동기(asynchronous)** 방식으로 처리한다.

```text
요청을 보낸다
↓
기다리지 않고 다른 일을 계속한다    화면은 그대로 움직인다
↓
응답이 오면 그때 처리한다
```

**기다리는 동안 멈추지 않는다**는 것이 핵심이다. 그래서 로딩 표시가 돌아가고, 사용자는 다른 부분을 계속 조작할 수 있다.

대신 코드를 쓸 때 주의할 점이 생긴다. 요청한 다음 줄이 **응답이 오기 전에 먼저 실행될 수 있다.** 그래서 "응답이 온 다음에 이걸 해라"를 따로 지정해줘야 한다.

Promise나 async/await 같은 문법이 그걸 다루는 방법인데, 여기서는 **"기다리는 동안 멈추지 않는다"** 는 성질까지만 알아둔다.

## 22. 렌더링이란 무엇인가

**Rendering(렌더링)** 은 **데이터와 Component의 상태를 바탕으로 화면을 만들어 보여주는 과정**이다.

지금까지 나온 것들이 여기서 합쳐진다.

```text
Component 구조 + Props + State
↓
Rendering
↓
실제 화면
```

같은 Component라도 **State가 다르면 다른 화면이 나온다.** 거리가 5.2일 때와 10.0일 때 화면이 다른 것처럼, 로딩 중일 때와 완료됐을 때도 다르다.

그래서 화면을 "고정된 결과물"이 아니라 **"현재 상태를 그려낸 결과"** 로 보게 됐다. 화면이 잘못 나오면 화면을 고치는 게 아니라 **상태가 왜 그런지**를 봐야 한다.

## 23. Re-render란 무엇인가

**Re-render(리렌더)** 는 **상태가 바뀌어서 Component가 다시 계산되고 화면이 갱신되는 것**이다.

```text
State 변경
↓
Re-render        해당 Component를 다시 계산한다
↓
화면 갱신        바뀐 부분이 화면에 반영된다
```

이게 8번에서 말한 "State가 바뀌면 화면도 따라온다"의 실제 동작이다.

내가 직접 "화면의 이 부분을 바꿔라"라고 지시하지 않는다. **State만 바꾸면 React가 다시 계산해서 화면을 맞춰준다.**

그래서 Frontend에서 화면을 바꾸고 싶으면 방법은 하나다. **State를 바꾼다.** 화면을 직접 건드리려고 하면 오히려 꼬인다.

React가 내부적으로 무엇이 바뀌었는지 비교해서 필요한 부분만 갱신하는 과정이 있는데, 그건 더 깊은 주제라서 여기서는 **"상태가 바뀌면 다시 그려진다"** 까지만 정리한다.

## 24. 조건부 렌더링

**조건부 렌더링**은 **상태에 따라 다른 화면을 보여주는 것**이다.

19번과 20번에서 나온 loading, success, error가 바로 이 방식으로 처리된다.

| 상태 | 보여주는 화면 |
|---|---|
| 로그인 전 | 로그인 버튼 |
| 로그인 후 | 내 기록 |
| Loading | 로딩 표시 |
| Error | 오류 메시지 |

```text
if 로그인하지 않았다면   →  로그인 버튼을 보여준다
if 로딩 중이라면         →  로딩 표시를 보여준다
if 오류가 났다면         →  오류 메시지를 보여준다
그 외                    →  실제 데이터를 보여준다
```

화면 하나에 **여러 가지 모습**이 있는 셈이다. 디자인 시안은 보통 잘 되는 경우 하나만 그려져 있는데, 실제로 만들 때는 **나머지 경우의 화면도 전부 정해야 한다.**

이걸 알고 나서 "화면 하나 만드는 데 왜 이렇게 오래 걸리지?"에 대한 답이 나왔다. 화면이 하나가 아니었던 것이다.

## 25. 목록 렌더링

데이터가 여러 개일 때는 **같은 Component를 반복해서 보여준다.**

```text
records        기록 데이터 3개가 들어 있는 목록
↓
RecordCard     첫 번째 기록으로 카드 하나
RecordCard     두 번째 기록으로 카드 하나
RecordCard     세 번째 기록으로 카드 하나
```

카드를 세 번 직접 쓰는 게 아니다. **데이터 목록을 돌면서 각각에 대해 Component를 만든다.** 그래서 기록이 10개면 카드가 10개, 0개면 하나도 안 나온다.

여기서 데이터가 0개인 경우도 생각해야 한다. **빈 목록일 때 아무것도 안 보이면 고장 난 것처럼 보인다.** "아직 기록이 없습니다" 같은 안내가 필요하다.

React에서는 목록을 그릴 때 각 항목에 **key**라는 값을 붙인다. React가 **어떤 항목이 어떤 것인지 구분**하기 위해 쓴다. 항목이 추가되거나 순서가 바뀔 때 어느 것이 그대로이고 어느 것이 새것인지 알아야 하기 때문이다. 보통 데이터의 id를 쓴다.

## 26. Client와 Server 차이

Backend 글에서 정리한 내용이라 짧게만 짚는다.

| 구분 | 어디서 실행되는가 |
|---|---|
| Client | 사용자의 브라우저 |
| Server | 서비스를 제공하는 쪽의 서버 |

Frontend 입장에서 중요한 건 **Client에서 실행되는 코드는 사용자가 전부 볼 수 있다**는 점이다.

브라우저 개발자 도구를 열면 어떤 코드가 실행되고 있는지, 어떤 값이 들어 있는지 확인할 수 있다. 숨겨지지 않는다.

그래서 이 원칙이 나온다.

```text
Client 코드에 Secret을 넣으면 안 된다
```

API Key나 데이터베이스 접속 정보를 Frontend 코드에 넣으면, **그 값은 사용자에게 공개된 것과 같다.** 환경변수에 넣었더라도 브라우저로 내려가는 코드에서 쓰면 결과는 같다.

Deployment 글에서 Public 값과 Secret을 구분했던 이유가 여기에 있다.

## 27. Client-side와 Server-side

앞의 구분을 코드 실행 위치로 다시 보면 이렇다.

| 구분 | 실행 위치 | 특징 |
|---|---|---|
| Client-side | 브라우저 | 사용자 조작에 반응할 수 있다. 내용이 공개된다 |
| Server-side | 서버 | Secret을 다룰 수 있다. 사용자 조작에 직접 반응하지 않는다 |

처음에 헷갈렸던 이유가 있다. **Next.js 같은 프레임워크에서는 두 종류의 코드가 같은 프로젝트 안에 함께 들어 있다.**

폴더 구조만 보면 다 비슷해 보이는데, 어떤 파일은 브라우저에서 실행되고 어떤 파일은 서버에서 실행된다. 겉보기에 구분이 안 된다.

그래서 **"이 코드는 어디에서 실행되는가"를 항상 의식**해야 했다. 서버에서만 실행되어야 할 코드가 브라우저 쪽에 섞이면 Secret이 노출되고, 반대로 브라우저 기능이 필요한 코드가 서버에서 실행되면 오류가 난다.

## 28. Next.js는 무엇인가

**Next.js**는 **React를 기반으로 웹 애플리케이션을 만들기 위한 프레임워크**다.

React와의 차이를 정리하면 이렇다.

| 구분 | React | Next.js |
|---|---|---|
| 무엇인가 | UI를 만들기 위한 라이브러리 | React를 기반으로 한 프레임워크 |
| 담당 범위 | Component와 상태에 따른 화면 | 그것에 더해 라우팅, 서버 기능, 빌드 등 |
| 비유 | 부품 | 부품을 포함한 완성된 틀 |

React만으로 웹 애플리케이션을 만들려면 **라우팅은 어떻게 할지, 서버 쪽 코드는 어디에 둘지, 빌드는 어떻게 할지**를 각각 정하고 도구를 붙여야 한다.

Next.js는 **그 구조를 미리 정해서 제공한다.** 정해진 위치에 파일을 만들면 라우팅이 되고, 서버에서 실행할 코드를 둘 자리도 마련되어 있다.

```text
React     →  화면을 만드는 부분을 담당
Next.js   →  React를 포함해서 애플리케이션 전체 구조를 제공
```

그래서 **"React를 쓴다"와 "Next.js를 쓴다"는 같은 말이 아니다.** Next.js를 쓰면 React도 함께 쓰는 것이지만, 반대는 성립하지 않는다.

세부 기능은 버전에 따라 계속 바뀌는 부분이 있어서, 여기서는 이 관계까지만 정리해둔다.

## 29. Routing이란 무엇인가

**Routing(라우팅)** 은 **URL에 따라 어떤 화면을 보여줄지 연결하는 것**이다.

```text
/           →  Home 화면
/login      →  Login 화면
/records    →  Records 화면
```

사용자가 주소를 입력하거나 링크를 누르면, 그 주소에 연결된 화면이 나타난다.

Backend 글에서 "Endpoint는 서버가 요청을 받으려고 열어둔 창구"라고 했는데, Frontend의 라우팅도 비슷한 구조다. **주소마다 무엇을 보여줄지 미리 연결해둔다.**

Next.js에서는 이 연결을 **폴더와 파일 구조로** 한다. 정해진 위치에 파일을 만들면 그 경로가 자동으로 주소가 된다. 별도로 "이 주소는 이 화면"이라고 목록을 적어두지 않아도 된다.

## 30. 페이지와 Component는 무엇이 다른가

둘 다 화면을 만드는 것이라서 헷갈렸다.

| 구분 | 무엇인가 |
|---|---|
| Page | 특정 Route에서 보여주는 큰 화면 단위 |
| Component | 그 화면을 구성하는 재사용 가능한 부분 |

```text
/records  (Page)
├─ Header        (Component)
├─ FilterBar     (Component)
├─ RecordCard    (Component)
├─ RecordCard    (Component)
└─ Footer        (Component)
```

**Page도 결국 Component다.** 다만 **주소와 연결되어 있는 특별한 위치의 Component**라고 이해하면 됐다.

구분하는 기준은 **"이 화면에 직접 주소로 들어올 수 있는가"** 였다. `/records`로 접속할 수 있으면 Page이고, `RecordCard`만 따로 볼 수는 없으니 Component다.

다만 이 구조는 **프레임워크에 따라 달라질 수 있다.** 어떤 곳은 Page라는 개념 자체가 없기도 하다.

## 31. Frontend에서 로그인 상태는 어떻게 보일까

인증이 어떻게 동작하는지는 Backend 글에서 정리했으니, 여기서는 **Frontend가 무엇을 다루는지**만 본다.

Frontend는 인증을 직접 처리하지 않는다. **서버에서 알려준 결과를 받아서 화면에 반영할 뿐**이다.

Frontend가 다루는 것은 이 정도다.

| 다루는 것 | 무엇을 하는가 |
|---|---|
| 로그인 여부 | 로그인했는지에 따라 다른 화면을 보여준다 |
| 사용자 정보 | 닉네임 같은 것을 화면에 표시한다 |
| 로딩 상태 | 확인하는 동안 무엇을 보여줄지 정한다 |

24번의 조건부 렌더링이 그대로 적용된다.

```text
확인 중        →  로딩 표시
로그인 안 함   →  로그인 버튼
로그인함       →  내 기록과 닉네임
```

여기서 다시 강조해둘 것이 있다. **로그인 버튼을 만들었다고 인증이 구현된 것은 아니다.** 버튼은 화면 요소일 뿐이고, 실제 인증은 Backend가 처리한다. Frontend는 그 결과를 받아서 화면을 바꾸는 역할이다.

## 32. 화면이 있다고 기능이 있는 것은 아니다

지금까지의 내용을 한 문장으로 모으면 이거다.

| 이것이 있다고 | 이것이 되는 것은 아니다 |
|---|---|
| 검색창 표시 | 검색 기능 구현 |
| 로그인 버튼 표시 | OAuth 구현 |
| 러닝 결과 숫자 표시 | 실제 DB 기록 연결 |
| 지도 화면 표시 | 실제 위치 추적 |
| 버튼 표시 | Event 동작 구현 |

왼쪽은 전부 **화면에 그려져 있다**는 뜻이고, 오른쪽은 **실제로 동작한다**는 뜻이다.

가장 헷갈렸던 이유는 **왼쪽만 있어도 완성된 것처럼 보인다는 것**이다. 스크린샷을 찍으면 구분이 안 된다. 눌러봐야, 그리고 눌러서 실제로 데이터가 바뀌는지 확인해봐야 안다.

그래서 화면을 만들고 나서 스스로에게 물어보는 질문이 생겼다. **"이거 눌렀을 때 실제로 뭐가 일어나지?"**

## 33. 디자인과 Frontend 구현은 무엇이 다른가

디자인 시안을 받아서 화면을 만들 때, 시안에 없는 것들을 전부 정해야 했다.

| 구분 | 담당하는 것 |
|---|---|
| Design | 모양과 배치. 어떻게 보일 것인가 |
| Frontend 구현 | Component 구조, State, Event, Data, API, 실제 동작 |

```text
Design        →  모양과 배치

Frontend      →  Component    어떻게 나눌 것인가
              →  State        무엇을 기억해야 하는가
              →  Event        무엇을 하면 무엇이 일어나는가
              →  Data         값이 어디서 오는가
              →  API          언제 무엇을 요청하는가
              →  실제 동작    전부 이어서 작동하게 만드는 것
```

시안은 보통 **잘 되는 경우의 화면 한 장**이다. 그런데 실제로 만들려면 로딩 중인 화면, 데이터가 없는 화면, 오류가 난 화면, 로그인 전 화면까지 전부 있어야 한다.

**디자인은 결과물의 모습을 정하고, Frontend 구현은 그 모습에 도달하는 모든 경우를 만든다.** 이 차이가 작업량 차이로 이어졌다.

## 34. Frontend 기능 하나의 전체 흐름

"내 기록 보기" 화면 하나를 예로, 지금까지의 개념을 전부 이어보면 이렇다.

```text
사용자
↓
Records Page 접속        주소에 맞는 화면이 열린다 (Routing)
↓
Component 렌더링          화면 구조가 먼저 그려진다
↓
Loading State             "불러오는 중" 표시가 나타난다
↓
API Request               서버에 기록 데이터를 요청한다
↓
Backend                   요청을 처리하고 데이터를 찾는다
↓
Response                  기록 데이터가 돌아온다
↓
State 업데이트             받은 데이터를 State에 담는다
↓
RecordCard 렌더링          목록만큼 카드가 만들어진다
↓
화면 표시                  사용자가 자기 기록을 본다
```

**화면이 열리자마자 데이터가 보이는 게 아니다.** 구조가 먼저 그려지고, 로딩이 보이고, 요청이 갔다 오고, 그 다음에 데이터가 채워진다.

이 순서를 알고 나니 "왜 화면이 깜빡이지?", "왜 잠깐 빈 화면이 보이지?" 같은 현상이 이해됐다. **그게 정상 동작의 일부**였다.

## 35. 저장 기능의 전체 흐름

반대로 데이터를 보내는 경우도 보자.

```text
사용자 입력              입력창에 값을 친다
↓
Frontend State           입력값이 State에 담긴다
↓
Submit Event             저장 버튼을 누른다
↓
Validation               값이 올바른지 먼저 확인한다
↓
API Request              서버로 저장 요청을 보낸다
↓
Backend                  검증하고 처리한다
↓
Database                 실제로 저장된다
↓
Response                 성공했다는 응답이 온다
↓
Frontend State 변경      결과에 맞게 상태를 갱신한다
↓
완료 UI                  "저장되었습니다" 같은 화면을 보여준다
```

34번과 비교하면 방향만 반대이고 구조는 같다. **State → 요청 → 응답 → State → 화면**이다.

그리고 여기서도 실패하는 경우를 생각해야 한다. Validation에서 막힐 수도 있고, 서버에서 거절할 수도 있고, 네트워크가 끊길 수도 있다. **각 경우에 사용자에게 무엇을 보여줄지**까지 정해야 기능이 완성된다.

## 36. 자주 헷갈리는 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Frontend | 사용자가 보고 조작하는 영역. 화면과 동작을 모두 다룬다 |
| Browser | HTML, CSS, JavaScript를 해석해 화면과 동작을 만드는 프로그램 |
| HTML | 화면의 구조를 정하는 언어 |
| CSS | 화면의 표현과 스타일을 정하는 언어 |
| JavaScript | 화면의 동작과 로직을 담당하는 언어 |
| React | UI를 Component 단위로 만들고 상태 변화에 따라 화면을 반영하는 라이브러리 |
| Next.js | React 기반으로 라우팅, 서버 기능, 빌드 구조까지 제공하는 프레임워크 |
| Component | 화면을 재사용 가능한 작은 단위로 나눈 것 |
| Props | 부모 Component가 자식에게 전달하는 값 |
| State | Component가 관리하는, 화면이 기억해야 하는 현재 상태 |
| Event | 클릭이나 입력 같은 사용자 행동을 감지하는 것 |
| Rendering | 데이터와 상태를 바탕으로 화면을 만들어 보여주는 과정 |
| Re-render | 상태가 바뀌어 Component가 다시 계산되고 화면이 갱신되는 것 |
| Routing | URL에 따라 어떤 화면을 보여줄지 연결하는 것 |
| Page | 특정 Route에서 보여주는 큰 화면 단위 |
| Mock Data | 실제 연결 전 테스트를 위해 임시로 만든 데이터 |
| API | 서버와 데이터를 주고받기 위한 창구 |
| Fetch | JavaScript에서 HTTP 요청을 보내는 방법 중 하나 |
| Async | 응답을 기다리는 동안 멈추지 않고 다른 일을 계속하는 방식 |
| Loading | 요청을 보내고 결과를 기다리는 중인 상태 |
| Error | 요청이 실패한 상태 |
| Client | 사용자의 브라우저 쪽. 코드 내용이 공개된다 |
| Server | 요청을 처리하는 서버 쪽 |
| Client-side | 브라우저에서 실행되는 코드 |
| Server-side | 서버에서 실행되는 코드 |

## 37. 자주 헷갈리는 차이 정리

| 구분 | 차이 |
|---|---|
| Frontend vs Backend | 보이고 조작하는 영역 / 요청을 받아 처리하는 영역 |
| HTML vs CSS vs JavaScript | 구조 / 표현 / 동작 |
| React vs Next.js | UI를 만드는 라이브러리 / 애플리케이션 구조까지 제공하는 프레임워크 |
| Page vs Component | 주소와 연결된 큰 화면 단위 / 그 화면을 구성하는 재사용 부분 |
| Props vs State | 밖에서 전달받은 값 / 스스로 관리하는 현재 상태 |
| Mock Data vs Real Data | 코드에 적어둔 임시 값 / 서버에서 받아온 실제 값 |
| Client vs Server | 사용자 브라우저 쪽 / 서비스 제공자 서버 쪽 |
| Client-side vs Server-side | 브라우저에서 실행 / 서버에서 실행. Secret은 서버 쪽만 |
| Design vs Frontend 구현 | 모양과 배치를 정하는 것 / 상태와 동작까지 만들어내는 것 |
| 화면 존재 vs 기능 구현 | 그려져 있는 것 / 눌렀을 때 실제로 작동하는 것 |

## 38. "Frontend 구현 완료"는 어디까지인가

다른 공부 글에서 계속 나온 문제가 여기에도 있었다.

아래는 **전부 다른 단계**다.

| 단계 | 어디까지 된 것인가 |
|---|---|
| 1 | 화면 구조 존재 — 요소들이 배치되어 있다 |
| 2 | 스타일 적용 — 디자인대로 보인다 |
| 3 | Component 분리 — 재사용 가능한 단위로 나뉘었다 |
| 4 | Event 동작 — 눌렀을 때 뭔가 실행된다 |
| 5 | State 관리 — 상태가 기억되고 화면에 반영된다 |
| 6 | 사용자 입력 처리 — 입력값을 받아서 다룬다 |
| 7 | API 연결 — 서버와 실제로 통신한다 |
| 8 | Loading / Error 처리 — 기다림과 실패도 화면이 있다 |
| 9 | 실제 데이터 표시 — Mock이 아닌 진짜 데이터가 보인다 |
| 10 | 실제 사용자 흐름 확인 — 처음부터 끝까지 해봤다 |

**"프론트 구현 끝났어요"라는 말로는 이 중 몇 번인지 알 수 없다.**

특히 1~3번까지만 하고 완료라고 느끼기 쉬웠다. 화면이 디자인대로 잘 나오면 다 된 것처럼 보이기 때문이다. 하지만 그 시점에서 실제로 동작하는 건 아무것도 없다.

그리고 8번 Loading/Error 처리는 가장 자주 빠뜨렸다. 잘 되는 경우만 확인하고 넘어가면, 실제 사용 중에 빈 화면을 만나게 된다.

## 39. 이번에 이해한 핵심

이번에도 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### 화면이 있다, 는 기능이 구현됐다와 다르다

그려져 있는 것과 눌렀을 때 작동하는 것은 완전히 다른 작업이다.

### 버튼이 있다, 는 Event가 연결됐다와 다르다

버튼은 HTML로 만들면 생긴다. 누르면 무엇을 할지는 따로 연결해야 한다.

### 데이터가 보인다, 는 실제 DB 데이터다와 다르다

코드에 적어둔 Mock Data도 화면에는 똑같이 잘 나온다.

### React를 쓴다, 는 Next.js와 같은 개념이다와 다르다

React는 UI를 만드는 라이브러리이고, Next.js는 그 위에 구조를 더한 프레임워크다.

### Frontend, 는 단순 디자인과 다르다

Component, State, Event, API 연결까지가 Frontend의 영역이다.

### Frontend Validation, 은 Backend Validation을 대신하지 않는다

브라우저의 검증은 건너뛸 수 있다. 중요한 규칙은 서버에서도 확인해야 한다.

### API 코드가 있다, 는 실제 요청이 성공한다와 다르다

호출하는 코드를 썼다는 것과 실제로 응답이 오는 것은 별개다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> Frontend는 단순히 화면을 만드는 영역이 아니라, 사용자의 행동과 상태, 서버에서 받은 데이터를 연결해 실제로 사용할 수 있는 화면을 만드는 영역이었다.

처음에는 Frontend를 "디자인을 코드로 옮기는 일"이라고 생각했다. 하지만 실제로는 **무엇을 기억할지 정하고(State), 사용자가 무엇을 하면 무엇이 일어날지 연결하고(Event), 필요한 데이터를 언제 요청할지 결정하고(API), 기다릴 때와 실패할 때의 화면까지 만드는 일**이었다.

디자인은 그중 첫 번째 화면 한 장이었을 뿐이다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **DOM** — 브라우저가 HTML을 다루는 구조. React가 무엇을 대신해주는지 알게 된다
- **Event Loop** — JavaScript가 비동기를 처리하는 방식의 바탕
- **Promise / async-await** — 비동기 결과를 다루는 문법
- **React Hooks** — State나 다른 기능을 Component에서 사용하는 방법
- **useEffect** — 화면이 그려진 뒤 실행할 일을 다루는 것. API 호출과 자주 엮인다
- **상태 관리** — State가 여러 Component에 걸쳐 필요할 때의 해결 방법
- **Context** — 값을 깊은 곳까지 전달할 때 Props를 계속 넘기지 않는 방법
- **Server Components / Client Components** — 어디에서 실행될지를 구분하는 최근 방식
- **SSR / CSR** — 화면을 서버에서 그릴지 브라우저에서 그릴지의 차이
- **Accessibility** — 모든 사용자가 쓸 수 있게 만드는 것
- **Responsive Design** — 화면 크기에 따라 배치를 바꾸는 것
- **Frontend Testing** — 화면과 동작이 의도대로 작동하는지 확인하는 방법
