앞 글에서는 한 화면 안에서

```text
무엇을 먼저 보여줄지

어떤 버튼을 가장 강조할지

어떤 정보는 약하게 보여줄지
```

를 정리했다.

그런데 실제 프로젝트를 만들다 보면 그보다 더 큰 문제가 생긴다.

```text
이 정보는 홈에 있어야 하나?

상세 화면에 있어야 하나?

설정에 넣어야 하나?

별도 페이지를 만들어야 하나?
```

한 화면 안의 우선순위를 잘 정해도

애초에 정보가 잘못된 화면에 들어가 있다면 사용하기 어려울 수 있다.

예를 들어 홈 화면에

```text
프로필

설정

사용 기록

상세 정책

알림 설정

계정 관리
```

를 모두 보여준다면

각 요소를 아무리 예쁘게 정리해도 화면이 복잡해질 수밖에 없다.

그래서 화면을 만들기 전에

**정보를 어떻게 나눌 것인지**

부터 생각해야 했다.

이번 글에서는 서비스의 정보를 여러 페이지에 어떻게 나누고,

각 페이지가 어떤 역할을 가져야 하는지 정리해보려고 한다.

---

## 처음에는 필요한 정보를 전부 홈에 넣고 싶었다

프로젝트를 처음 만들 때는 홈 화면이 가장 중요해 보인다.

그래서

```text
사용자가 자주 봐야 할 것

사용자가 알아야 할 것

서비스에서 제공하는 기능
```

을 전부 홈에 넣고 싶어진다.

예를 들어 카페 서비스를 만든다고 해보자.

홈에

```text
현재 위치

주변 카페

내 혜택

즐겨찾기

최근 본 카페

알림

이벤트

설정

프로필
```

을 모두 넣을 수 있다.

기능만 보면 풍부하다.

하지만 실제 사용자는 홈에 들어와서

```text
그래서 지금 뭘 보면 되지?
```

라고 느낄 수 있다.

서비스가 가진 모든 기능을 홈에서 보여주는 것이

좋은 홈 화면은 아니었다.

---

## 페이지마다 역할이 있어야 했다

화면을 나눌 때 가장 도움이 된 질문은 이것이었다.

```text
이 페이지는 무슨 일을 하는 페이지인가?
```

한 문장으로 답할 수 있어야 한다.

예를 들어

```text
Home
→ 지금 필요한 정보를 빠르게 확인

List
→ 여러 항목을 비교하고 선택

Detail
→ 하나의 항목을 자세히 확인

Edit
→ 정보를 수정

Settings
→ 서비스 환경을 변경
```

처럼 나눌 수 있다.

페이지 역할이 명확하면

```text
이 정보가 왜 여기 있지?
```

라는 문제도 줄어든다.

---

## 한 페이지에 여러 목적을 넣으면 복잡해졌다

예를 들어 한 화면에서

```text
카페 찾기

혜택 수정

프로필 변경

알림 확인
```

을 모두 하게 만든다고 해보자.

각각은 필요한 기능이다.

하지만 사용자의 목적이 완전히 다르다.

```text
카페 찾기
→ 탐색

혜택 수정
→ 관리

프로필 변경
→ 계정 설정

알림 확인
→ 상태 확인
```

이런 기능을 한 화면에 넣으면

화면 자체도 복잡하지만

사용자의 생각도 계속 바뀌어야 한다.

그래서

```text
한 페이지
=
가능하면 하나의 주요 목적
```

이라는 기준을 생각하게 됐다.

---

## 정보 구조란?

처음에는 정보 구조라는 말이 어렵게 느껴졌다.

하지만 프로젝트에서는 간단하게 생각할 수 있었다.

> **어떤 정보를 어디에 두고, 사용자가 어떻게 찾아가게 할 것인가**

를 정하는 것이다.

예를 들어 서비스 안에 이런 정보가 있다고 해보자.

```text
주변 카페

카페 상세 정보

내 혜택

혜택 상세

사용 기록

계정

설정
```

이것을 아무 페이지에나 배치하는 것이 아니라

관계에 따라 구조를 만든다.

```text
Home
├─ 주변 카페
│  └─ Cafe Detail
│
├─ 내 혜택
│  └─ Benefit Detail
│
└─ My
   ├─ 기록
   └─ 설정
```

이런 구조 자체가 정보 구조의 일부라고 생각하면 이해하기 쉬웠다.

---

## 사용자의 흐름부터 생각하면 페이지가 보였다

페이지 목록부터 만들기보다

사용자가 서비스를 사용하는 흐름을 먼저 생각하는 것이 도움이 됐다.

예를 들어

```text
주변 카페를 찾는다
↓
카페를 선택한다
↓
혜택을 확인한다
↓
길찾기를 한다
```

라는 흐름이 있다면

자연스럽게

```text
Home / Map
↓
Cafe Detail
↓
Benefit Information
↓
Navigation
```

같은 화면 구조가 나온다.

즉,

```text
페이지를 먼저 만든 뒤
기능을 넣는 것
```

보다

```text
사용자 행동을 먼저 정하고
필요한 페이지를 만드는 것
```

이 더 자연스러웠다.

---

## 목록 화면의 역할

목록 화면은 여러 항목을 한 번에 보여준다.

예를 들어

```text
카페 목록

기록 목록

쿠폰 목록

게시글 목록
```

같은 화면이다.

목록의 주요 목적은 보통

```text
빠르게 훑기

비교하기

하나를 선택하기
```

다.

그래서 목록 카드에 모든 정보를 다 넣을 필요는 없다.

---

## 목록에 너무 많은 정보를 넣으면 비교하기 어렵다

카페 목록 카드에

```text
브랜드

매장명

주소

거리

도보 시간

혜택

유효기간

메모

사용 조건

전화번호
```

를 다 넣는다고 해보자.

한 항목의 정보는 자세하다.

하지만 카드가 너무 커진다.

사용자는 여러 카페를 한 번에 비교하기 어려워진다.

그래서 목록에서는

```text
브랜드

매장명

거리

핵심 혜택
```

정도만 보여주고

나머지는 상세로 보내는 방식이 더 자연스러울 수 있다.

---

## 목록은 요약, 상세는 설명

이 구분이 가장 이해하기 쉬웠다.

```text
List
→ 핵심 정보 요약

Detail
→ 전체 정보 확인
```

예를 들어

### 목록

```text
메가MGC 판교점
도보 7분
스탬프 8개
```

### 상세

```text
메가MGC 판교점

주소
거리
도보 시간
스탬프
쿠폰
유효기간
사용 조건
메모
길찾기
```

처럼 나눈다.

목록과 상세가 같은 정보를 똑같은 양으로 보여줄 필요는 없다.

---

## 상세 화면의 역할

상세 화면은 하나의 대상을 깊게 보는 곳이다.

예를 들어

```text
카페 하나

쿠폰 하나

러닝 기록 하나
```

를 자세히 보여준다.

사용자는 이미

```text
이 항목을 보고 싶다.
```

고 선택한 상태다.

따라서 목록보다 많은 정보를 보여줘도 된다.

하지만 그렇다고 모든 정보를 한 번에 펼칠 필요는 없다.

---

## 상세 화면 안에서도 우선순위가 필요했다

예를 들어 쿠폰 상세에는

```text
브랜드

쿠폰 수량

유효기간

사용 가능 매장

발급일

메모

사용 조건

수정

삭제
```

가 있을 수 있다.

상세라고 해서 전부 같은 강도로 보여주면 다시 복잡해진다.

그래서

```text
핵심 정보

추가 정보

관리 기능
```

처럼 구분한다.

예를 들면

```text
[핵심]
쿠폰 1개
3일 뒤 만료

[사용 정보]
사용 가능 매장
사용 조건

[관리]
수정
삭제
```

형태다.

---

## 입력 화면과 조회 화면을 나누는 것도 좋았다

처음에는 상세 화면 안에 수정 기능까지 전부 넣고 싶었다.

예를 들어

```text
카페 상세

매장명 [입력창]

메모 [입력창]

쿠폰 [입력창]

[저장]
```

처럼 만들 수 있다.

하지만 사용자가 단순히 정보를 보러 왔는데

항상 입력 가능한 상태라면 화면이 복잡해진다.

그래서

```text
Detail
→ 확인

Edit
→ 수정
```

으로 분리할 수 있다.

---

## 조회와 편집을 분리하면 행동도 명확해졌다

예를 들어 상세에서는

```text
혜택 정보

[수정]
```

만 보여준다.

수정을 누르면

```text
Benefit Edit
```

페이지나 모달로 이동한다.

그러면 사용자는

```text
지금은 보는 중

지금은 수정하는 중
```

을 명확하게 이해할 수 있다.

이 구조는 실수로 값을 바꾸는 것도 줄일 수 있다.

---

## 그렇다고 무조건 페이지를 많이 나눌 필요는 없었다

여기서 반대 문제도 생긴다.

기능을 하나씩 전부 페이지로 나누면

```text
홈
↓
목록
↓
상세
↓
편집
↓
확인
↓
완료
```

처럼 이동이 너무 많아질 수 있다.

그래서

```text
페이지를 나눈다
=
무조건 좋은 구조
```

는 아니었다.

중요한 것은

```text
같이 있어야 이해하기 쉬운가?

분리해야 더 명확한가?
```

를 판단하는 것이다.

---

## 작은 수정은 같은 화면에서 처리할 수도 있다

예를 들어 닉네임 하나만 수정한다면

별도의 큰 페이지를 만들지 않고

```text
Modal

Bottom Sheet

Inline Edit
```

같은 방식도 사용할 수 있다.

반대로

```text
주소

전화번호

혜택 정보

유효기간

메모
```

처럼 입력할 내용이 많다면

별도 편집 화면이 더 나을 수 있다.

---

## Modal을 쓸지 페이지를 만들지

이것도 자주 고민되는 문제였다.

나는 단순하게 이렇게 생각했다.

### Modal / Dialog

```text
짧은 확인

작은 입력

현재 흐름을 유지해야 하는 작업
```

예:

```text
삭제 확인

이름 변경

로그아웃 확인
```

### 별도 Page

```text
정보가 많음

집중해서 해야 함

여러 입력이 필요함

독립적인 흐름이 있음
```

예:

```text
프로필 편집

혜택 등록

상세 설정
```

이렇게 나누면 이해하기 쉬웠다.

---

## Bottom Sheet도 모바일에서는 유용했다

모바일에서는 화면 아래에서 올라오는 Bottom Sheet를 자주 볼 수 있다.

예를 들어

```text
길찾기 앱 선택

정렬 기준 선택

간단한 옵션 선택
```

같은 기능이다.

현재 화면의 맥락을 유지하면서

짧은 선택지만 보여줄 때 잘 맞는다.

반대로 긴 폼 전체를 Bottom Sheet 안에 넣으면

공간이 좁고 사용하기 어려울 수 있다.

---

## 설정 화면은 기능 창고가 아니었다

프로젝트를 만들다 보면 어디에 넣어야 할지 애매한 기능을

```text
설정
```

에 몰아넣기 쉽다.

```text
프로필

알림

위치

기록

도움말

로그아웃

서비스 정보

개인정보
```

전부 넣을 수 있다.

설정 화면 자체가 너무 복잡해질 수 있다.

그래서 설정에서도 그룹이 필요하다.

```text
계정

앱 설정

알림

정보

계정 관리
```

처럼 나눌 수 있다.

---

## 설정은 자주 쓰는 기능이 아닐 수 있다

홈 화면에서 설정 버튼을 너무 강하게 보여줄 필요도 없다.

사용자가 매번 앱에 들어와서

```text
설정 변경
```

을 하는 것은 아닐 가능성이 높다.

그래서

```text
핵심 기능
→ 강하게

설정
→ 접근 가능하지만 보조적으로
```

두는 것이 자연스러울 수 있다.

---

## 홈 화면의 역할을 정해야 했다

홈 화면은 특히 욕심이 많이 나는 페이지다.

서비스의 모든 것을 보여주고 싶어진다.

하지만 홈은

```text
서비스 설명 페이지
```

가 아니라

사용자가 서비스에 들어왔을 때

```text
가장 먼저 필요한 행동을 시작하는 곳
```

이라고 생각하니 훨씬 단순해졌다.

예를 들어 러닝 서비스라면

```text
현재 위치

러닝 시작

간단한 상태
```

가 핵심일 수 있다.

모든 과거 기록이나 상세 통계까지 홈에 넣을 필요는 없다.

---

## 홈에서 보여줄지 말지를 결정하는 질문

나는 이런 질문이 도움이 된다고 생각한다.

```text
사용자가 앱을 열 때마다
이 정보를 확인해야 하는가?
```

그렇다면 홈에 있을 가능성이 높다.

반대로

```text
가끔 필요할 때만 보는 정보인가?
```

라면 다른 페이지로 보내도 될 수 있다.

예를 들어

```text
현재 위치
→ 자주 필요

주변 카페
→ 자주 필요

계정 삭제
→ 거의 필요 없음
```

우선순위가 확실히 다르다.

---

## Navigation은 페이지 구조를 보여준다

하단 Navigation이나 상단 메뉴를 만들면

서비스의 큰 구조가 그대로 드러난다.

예를 들어

```text
Home

Map

Benefits

My
```

라는 하단 메뉴가 있다면

사용자는

```text
이 서비스는 크게 네 영역으로 구성되어 있구나.
```

라고 이해한다.

그래서 Navigation 항목을 정하는 것도 단순한 디자인 문제가 아니었다.

서비스의 핵심 영역을 정하는 일이다.

---

## Bottom Navigation에 너무 많은 메뉴를 넣으면 복잡해졌다

기능이 많아지면

```text
Home

Map

Search

Benefits

Record

Community

Profile
```

를 전부 하단에 넣고 싶어진다.

그러면 메뉴 자체가 많아진다.

모바일에서는 특히 공간도 부족하다.

그래서

```text
자주 이동하는 최상위 영역
```

만 Navigation에 두는 것이 좋았다.

나머지는 각 영역 안에서 접근하게 한다.

---

## Navigation 이름도 사용자 언어로 정한다

개발자 입장에서

```text
Dashboard

Management

Preset

History
```

같은 표현이 익숙할 수 있다.

하지만 실제 사용자가 이해하기 어려울 수도 있다.

예를 들어

```text
내 혜택

기록

설정
```

처럼 더 익숙한 이름이 좋을 수 있다.

Navigation은 사용자가 길을 찾는 기준이기 때문에

이름 자체가 명확해야 한다.

---

## 같은 정보가 여러 페이지에 반복되는 문제

프로젝트가 커지면 같은 정보가 여러 곳에 나타난다.

예를 들어

```text
현재 위치
```

가

```text
홈

지도

검색
```

에 모두 있을 수 있다.

반복 자체가 무조건 나쁜 것은 아니다.

사용자에게 필요한 맥락이라면 반복해도 된다.

문제는 페이지마다 다른 방식으로 보여줄 때다.

```text
Home
→ 판교

Map
→ 경기도 성남시 분당구 판교동

Search
→ 현재 지역
```

처럼 표현이 너무 다르면 혼란스러울 수 있다.

---

## 반복되는 정보는 표현 규칙을 맞춘다

같은 상태를 보여준다면

```text
위치 이름

아이콘

변경 버튼

표시 방식
```

을 가능하면 비슷하게 유지한다.

그러면 사용자는 다른 페이지에서도

```text
아, 이건 같은 위치 정보구나.
```

라고 빠르게 이해한다.

---

## 같은 기능이 여러 곳에 있어도 되는 경우

예를 들어

```text
새 혜택 등록
```

기능이

```text
내 혜택 목록

Empty State
```

두 곳에 있을 수 있다.

둘 다 같은 행동이지만

사용 맥락이 다르다.

```text
목록
→ 새 항목 추가

Empty State
→ 첫 항목 만들기
```

이런 반복은 사용성을 높일 수 있다.

즉 중복 자체보다

```text
왜 여기에도 필요한가?
```

가 중요하다.

---

## 뒤로가기를 누르면 어디로 가야 하는가

페이지 구조를 만들면서 생각보다 중요한 부분이었다.

예를 들어

```text
Home
↓
Cafe Detail
```

이라면 뒤로가기는 자연스럽게 Home으로 돌아간다.

하지만

```text
Search
↓
Cafe Detail
```

로 들어왔을 수도 있다.

이때 무조건 Home으로 보내면

사용자가 방금 보던 검색 결과가 사라진다.

따라서 Navigation 구조를 만들 때는

```text
어디에서 들어왔는가?
```

도 중요하다.

---

## 페이지 이동은 사용자의 맥락을 유지해야 했다

사용자가

```text
카페 검색
↓
상세 확인
↓
뒤로가기
```

를 했는데

검색어와 목록이 전부 초기화된다면 불편하다.

사용자는 다시 검색해야 한다.

그래서 페이지 구조는 단순히

```text
A → B
```

만 그리는 것이 아니라

```text
B에서 돌아왔을 때 A가 어떤 상태인가?
```

까지 생각할 필요가 있었다.

---

## 사용자의 위치를 잃지 않게 하기

페이지가 깊어지면 사용자가

```text
내가 지금 어디에 있지?
```

라고 느낄 수 있다.

특히 웹 서비스에서

```text
설정
↓
계정
↓
보안
↓
비밀번호 변경
```

처럼 구조가 깊어질 때 그렇다.

이런 경우

```text
페이지 제목

뒤로가기

Breadcrumb

Navigation 선택 상태
```

등을 이용해서 현재 위치를 알려줄 수 있다.

---

## 깊은 구조보다 얕은 구조가 항상 좋은 것은 아니다

클릭 횟수를 줄이려고

모든 메뉴를 한 단계에 펼칠 수도 있다.

```text
Home

Profile

Notification

Security

Password

Privacy

Help

Delete Account
```

그러면 깊이는 얕다.

하지만 메뉴가 너무 많아진다.

반대로

```text
Settings
├─ Account
│  ├─ Profile
│  └─ Security
├─ Notification
└─ Help
```

처럼 묶으면 한 단계 더 들어가지만 찾기 쉬울 수 있다.

그래서

```text
단계 수
```

보다

```text
사용자가 어디에 있을지 예상할 수 있는 구조
```

가 더 중요했다.

---

## 기능별로 나눌지 사용자 행동별로 나눌지

페이지를 구성할 때도 여러 방식이 있다.

예를 들어 개발자 관점에서는

```text
User

Location

Benefit

Record
```

처럼 데이터 기준으로 나눌 수 있다.

하지만 사용자는

```text
내 정보

주변 카페

내 혜택

내 기록
```

처럼 생각할 수 있다.

UI 구조에서는 시스템 내부 구조보다

사용자의 생각에 맞추는 편이 자연스러웠다.

---

## 데이터베이스 구조와 페이지 구조는 같지 않았다

이것도 중요한 부분이었다.

DB에는

```text
users

benefits

stores

locations
```

같은 테이블이 있다고 해보자.

그렇다고 화면도

```text
Users Page

Benefits Page

Stores Page

Locations Page
```

로 나눌 필요는 없다.

한 화면에서 여러 데이터가 합쳐질 수 있다.

예를 들어 카페 상세 화면은

```text
store

location

benefit
```

데이터를 함께 보여줄 수 있다.

UI는 사용자 행동을 기준으로 만들어야 했다.

---

## URL 구조도 페이지 관계를 보여줄 수 있다

웹 프로젝트에서는 페이지 구조가 URL에도 나타날 수 있다.

예를 들어

```text
/cafes

/cafes/123

/benefits

/benefits/456

/settings
```

처럼 만들 수 있다.

이 구조가 명확하면 개발하면서도

```text
이 페이지는 어떤 역할인가?
```

를 이해하기 쉬워진다.

다만 URL까지 완벽하게 설계하는 것이 이번 글의 핵심은 아니다.

중요한 것은

```text
페이지 사이의 관계가 코드에서도 어느 정도 드러난다.
```

는 점이었다.

---

## 화면을 만들기 전에 Sitemap처럼 정리하기

프로젝트 초기에 페이지가 많아진다면

간단한 구조도를 만들어보는 것도 좋았다.

예를 들어

```text
Home
│
├─ Cafe
│  └─ Cafe Detail
│
├─ Benefits
│  ├─ Benefit Detail
│  ├─ Add Benefit
│  └─ Edit Benefit
│
└─ My
   ├─ Record
   └─ Settings
```

이 정도만 있어도 전체 구조가 보인다.

그리고 질문할 수 있다.

```text
이 페이지가 왜 필요한가?

비슷한 페이지가 두 개 있지 않은가?

이동 경로가 너무 깊지 않은가?
```

---

## User Flow와 Sitemap은 조금 달랐다

처음에는 둘을 비슷하게 생각했다.

하지만 이렇게 구분하니 편했다.

### Sitemap

```text
서비스에 어떤 페이지가 있는가?
```

### User Flow

```text
사용자가 목표를 달성하기 위해
어떤 페이지를 순서대로 이동하는가?
```

예를 들어 Sitemap에는

```text
Home
Cafe Detail
Benefit
Settings
```

가 있다.

하지만 사용자 흐름은

```text
Home
↓
Cafe Detail
↓
길찾기
```

일 수 있다.

또 다른 흐름은

```text
Home
↓
Benefits
↓
Benefit Edit
```

일 수 있다.

두 가지를 같이 보면 페이지가 필요한 이유가 더 명확해진다.

---

## 한 페이지가 여러 Flow에 사용될 수도 있다

Cafe Detail은

```text
Home에서 들어올 수도 있고

Search에서 들어올 수도 있고

Benefits에서 들어올 수도 있다.
```

그렇다면 상세 화면은 특정 한 흐름에만 맞춰 만들면 안 된다.

다양한 진입 경로에서도 이해할 수 있어야 한다.

예를 들어 페이지 제목이나 뒤로가기 동작을 생각해야 한다.

---

## 로그인 전과 로그인 후 구조도 달라질 수 있다

서비스에 로그인 정책이 있다면

정보 구조에도 영향을 준다.

예를 들어 비로그인 사용자는

```text
Home

카페 탐색
```

까지만 사용할 수 있고

로그인 후에는

```text
내 혜택

기록

설정
```

까지 사용할 수 있다고 하자.

그러면 페이지 구조를

```text
Public

Authenticated
```

로 나눠 생각할 수도 있다.

---

## 로그인 유도 시점도 정보 구조의 일부였다

모든 페이지 진입 전에 로그인시키는 방법도 있고,

일부 기능을 사용하려 할 때 로그인시키는 방법도 있다.

예를 들어

```text
카페 탐색
→ 비로그인 가능

혜택 등록
→ 로그인 필요
```

라면

사용자는 서비스가 어떤 것인지 먼저 경험할 수 있다.

이 역시 단순 인증 기능이 아니라

사용자 Flow의 문제다.

---

## 페이지를 나누면서 로그인 장벽도 확인한다

예를 들어 사용자가

```text
카페 상세 보기
```

만 하려는데 로그인 화면으로 보내버리면

서비스를 사용하기 전에 이탈할 수 있다.

반대로 개인 데이터가 필요한

```text
혜택 등록
```

은 로그인이 필요하다.

그래서 각 페이지마다

```text
로그인이 꼭 필요한가?
```

를 따로 생각해야 했다.

---

## Empty State도 페이지 역할에 따라 달랐다

같은

```text
데이터 없음
```

이라도 화면 목적에 따라 다르게 보여줘야 한다.

예를 들어 내 혜택 목록이 비어 있다면

```text
아직 등록한 혜택이 없어요.

[혜택 등록하기]
```

가 자연스럽다.

검색 결과가 없다면

```text
검색 결과가 없습니다.

검색어를 바꿔보세요.
```

가 자연스럽다.

단순히

```text
데이터가 없습니다.
```

를 모든 페이지에 쓰는 것은 적절하지 않을 수 있다.

이 부분은 다음 Empty State 글에서 더 자세히 정리하려고 한다.

---

## 상태에 따라 페이지 구성이 달라진다

화면을 설계할 때 정상 상태만 생각하기 쉽다.

```text
데이터가 있다.
```

하지만 실제 서비스에는

```text
Loading

Empty

Error

Permission Denied

Offline
```

등이 있다.

예를 들어 주변 카페 페이지라면

```text
위치 권한 있음
→ 주변 카페

위치 권한 없음
→ 권한 안내

검색 결과 없음
→ Empty State

네트워크 오류
→ Retry
```

처럼 완전히 다른 구성이 필요할 수 있다.

그래서 한 페이지를 만든다는 것은

정상 화면 한 장만 만드는 것이 아니었다.

---

## 페이지 수가 늘어날 때 중복 화면을 확인한다

프로젝트가 진행되면서 화면이 늘어난다.

예를 들어

```text
혜택 추가

혜택 수정
```

페이지를 따로 만들었다고 하자.

두 화면이 거의 같다.

```text
브랜드

쿠폰

유효기간

메모

저장
```

차이는

```text
초기 값이 있느냐 없느냐
```

정도다.

이럴 때 완전히 별도 화면과 코드를 만들기보다

같은 Form 구조를 재사용할 수 있다.

---

## 디자인에서도 재사용 가능한 구조를 찾는다

Figma에서도

```text
Add Benefit

Edit Benefit
```

을 완전히 별개로 만들기보다

같은 Component나 Form 구조를 기반으로 만들 수 있다.

개발에서도 같은 Component를 사용할 수 있다.

이렇게 하면 디자인과 코드 양쪽에서 일관성이 생긴다.

---

## 페이지 이름도 중요했다

프로젝트 안에서

```text
Page1

Page2

SubPage
```

처럼 이름을 붙이면 나중에 헷갈린다.

가능하면 역할이 보이게 한다.

```text
Home

Cafe Detail

Benefit List

Benefit Edit

Settings
```

처럼 정리한다.

Figma Frame 이름,

문서 이름,

코드 Route 이름도 어느 정도 연결되면 관리하기 편하다.

---

## 같은 페이지를 사람마다 다르게 부르는 문제

팀 프로젝트에서

```text
내 기록 화면

기록 페이지

히스토리

History
```

가 사실 같은 화면인데 표현이 다를 수 있다.

이게 쌓이면 대화할 때 혼란스러워진다.

그래서 화면 이름도 초기에 통일하면 좋다.

예를 들어

```text
Record List

Record Detail
```

같이 기준을 정해둔다.

---

## AI에게 페이지를 만들게 할 때도 구조부터 준다

AI에게

```text
카페 앱 전체 만들어줘.
```

라고 하면 AI가 임의로 페이지를 만든다.

```text
Home

Search

Favorites

Review

Profile
```

등이다.

하지만 내 기획과 다를 수 있다.

그래서 먼저

```text
현재 서비스 화면은 다음과 같다.

Home
Cafe Detail
Benefits
Benefit Detail
Settings

이외 페이지는 추가하지 마.
```

처럼 알려주는 편이 좋다.

---

## 화면 단위로 Source of Truth를 만드는 방법

예를 들어 문서에

```text
S0 Login

S1 Home

S2 Cafe Detail

S3 Benefits

S4 Settings
```

처럼 정의할 수 있다.

그리고 각각

```text
목적

진입 경로

핵심 정보

Primary Action
```

을 적는다.

그러면 AI든 사람이든

```text
이 화면에서 무엇을 해야 하는가?
```

를 이해하기 쉬워진다.

---

## 내가 페이지를 정의한다면

간단하게 이렇게 적을 수 있다.

```text
[Home]

목적
→ 주변 카페 확인

핵심 정보
→ 현재 위치, 주변 카페, 혜택 요약

Primary Action
→ 카페 선택

진입
→ 앱 첫 화면

이동
→ Cafe Detail / Benefits
```

이런 형식이다.

페이지마다 길게 문서를 만들지 않아도

핵심 역할을 정리할 수 있다.

---

## 화면을 줄일 수 있는지 확인한다

기획하다 보면 페이지가 계속 늘어난다.

```text
Home

Search

Map

Nearby

Recommendation
```

그런데 자세히 보면 역할이 겹칠 수 있다.

예를 들어

```text
Search
+
Map
+
Nearby
```

를 하나의 화면에서 해결할 수도 있다.

그래서 페이지를 새로 만들기 전에

```text
기존 화면에서 해결할 수 없는가?
```

를 확인하는 것이 좋았다.

---

## 반대로 한 화면을 나눠야 하는지도 확인한다

예를 들어 Settings에

```text
프로필

알림

로그인 계정

개인정보

앱 설정

회원 탈퇴
```

가 전부 있고 너무 길다면

```text
Settings

Account Settings

Notification Settings
```

등으로 나눌 수 있다.

즉

```text
페이지를 줄이는 것
```

만 목표가 아니다.

너무 많은 역할을 가진 화면은 나눌 필요가 있다.

---

## 페이지를 나누는 기준

내가 사용하기 쉬웠던 질문은 이런 것들이다.

```text
목적이 다른가?

사용자가 다른 행동을 하는가?

정보량이 너무 많은가?

독립적으로 자주 접근하는가?

별도의 URL이나 상태가 필요한가?

뒤로가기 했을 때 현재 맥락을 유지해야 하는가?
```

여러 항목이 해당된다면 별도 페이지가 필요할 가능성이 높다.

---

## 페이지를 합치는 기준

반대로

```text
정보가 적다.

같은 목적이다.

같은 데이터 흐름을 사용한다.

분리하면 오히려 이동만 늘어난다.
```

면 한 페이지에서 처리할 수도 있다.

예를 들어

```text
프로필 이름

프로필 이미지
```

만 수정하는 작은 설정이라면

같은 Profile Edit 화면에서 처리하는 것이 자연스럽다.

---

## 탭을 사용할 때

한 페이지 안에서 서로 관련 있지만 성격이 조금 다른 정보를 보여줄 때 Tab을 사용할 수 있다.

예를 들어

```text
전체

사용 가능

만료
```

처럼 같은 혜택 목록을 상태별로 보는 방식이다.

Tab은 페이지 이동처럼 완전히 새로운 곳으로 가는 느낌보다

```text
같은 영역 안에서 보는 기준 변경
```

에 가깝다.

---

## 탭을 너무 많이 쓰면 또 복잡해진다

예를 들어

```text
전체

사용 가능

만료

쿠폰

스탬프

브랜드별

매장별
```

Tab이 너무 많으면 사용자가 다시 구조를 이해해야 한다.

그럴 때는

```text
Tab

Filter

Sort
```

중 무엇이 적합한지 다시 볼 필요가 있다.

---

## Tab과 Filter는 다르게 생각했다

예를 들어

```text
전체 / 사용 가능 / 만료
```

가 사용자가 자주 오가며 보는 큰 상태 구분이라면 Tab이 자연스러울 수 있다.

반대로

```text
브랜드

거리

유효기간
```

처럼 조건을 조합하는 기능은 Filter에 더 가까울 수 있다.

이것도 결국 정보 구조의 일부다.

---

## 검색은 Navigation을 대신하는 기능이 아니다

기능이 많아지면

```text
그냥 검색으로 찾게 하면 되지.
```

라고 생각할 수 있다.

하지만 사용자가 정확한 이름을 모를 수도 있다.

Navigation은

```text
무엇이 있는지 보여주는 역할
```

도 한다.

검색은

```text
이미 찾고 싶은 것을 알고 있을 때
빠르게 접근하는 방법
```

에 더 가깝다.

둘의 역할은 다르다.

---

## 사용자가 길을 잃으면 구조 문제가 있을 수 있다

테스트하면서 자주 듣게 되는 질문이 있다.

```text
이 기능 어디 있어요?

아까 그 화면으로 어떻게 돌아가요?

여기서 설정은 어디로 가요?
```

이런 질문이 반복된다면

사용자가 기능을 잘못 이해한 것이 아니라

정보 구조나 Navigation이 명확하지 않은 것일 수 있다.

---

## 실제 사용 테스트에서 페이지 구조를 확인하는 방법

사용자에게 이렇게 요청할 수 있다.

```text
내 혜택을 수정해보세요.

지난 기록을 찾아보세요.

주변 카페 중 하나의 상세 정보를 확인해보세요.
```

그리고 아무 설명 없이 보는 것이다.

```text
어디로 이동하는지

어디서 멈추는지

뒤로 갔다가 다시 찾는지
```

를 관찰한다.

이 과정에서

```text
페이지 이름

Navigation

정보 위치
```

문제를 발견할 수 있다.

---

## 페이지 구조가 좋으면 기능을 설명할 일이 줄었다

예를 들어 사용자가

```text
혜택 수정
```

을 하려 한다.

구조가 명확하면

```text
내 혜택
↓
혜택 선택
↓
수정
```

이 자연스럽다.

별도의 설명이 필요 없다.

반대로 수정 버튼이

```text
설정
↓
고급 기능
↓
혜택 관리
```

안에 있다면 사용자가 예상하기 어렵다.

좋은 정보 구조는

**사용자에게 서비스 사용법을 설명해야 하는 양 자체를 줄여준다.**

---

## 페이지를 많이 만들기 전에 종이로 그려도 됐다

정보 구조 단계에서는 디자인이 필요하지 않을 수도 있다.

```text
Home
↓
Detail
↓
Edit
```

정도만 적어도 된다.

또는

```text
[Home]

[Benefits] → [Benefit Detail] → [Edit]

[Settings]
```

처럼 간단히 그린다.

이 단계에서 중요한 것은

```text
색상

폰트

아이콘
```

이 아니라

```text
어떤 화면이 있고

어떻게 연결되는가
```

다.

---

## 디자인 전에 구조를 잡으면 수정 비용이 줄었다

Figma에서 화면을 10개 예쁘게 만든 뒤

```text
이 화면 사실 필요 없는데?
```

라고 하면 많은 작업을 버려야 한다.

반대로 구조부터 정하면

```text
필요한 화면
```

을 어느 정도 확정한 뒤 디자인할 수 있다.

```text
User Flow
↓
Page Structure
↓
Wireframe
↓
Visual Design
```

순서가 도움이 되는 이유다.

---

## AI를 사용해도 구조는 먼저 보는 것이 좋았다

Claude Design이나 Figma Make로 전체 서비스를 요청하면

정말 빠르게 여러 화면을 만들어준다.

문제는 AI가 만든 페이지 구조를 자연스럽게 받아들이게 된다는 것이다.

```text
AI가 Search를 만들었으니
Search가 필요한가 보다.
```

```text
Favorites 화면이 있으니
즐겨찾기도 넣자.
```

가 될 수 있다.

그래서 AI로 디자인하기 전에

```text
현재 필요한 페이지 목록
```

을 먼저 정해두는 것이 좋았다.

---

## AI는 빠르게 페이지를 만들고, 나는 필요성을 판단한다

AI 디자인의 장점은

```text
A 구조

B 구조

C 구조
```

를 빠르게 비교할 수 있다는 것이다.

하지만 어떤 구조를 쓸지는 서비스 목적을 기준으로 결정해야 한다.

즉,

```text
AI
→ 구조 후보 생성

사람
→ 실제 서비스 기준으로 선택
```

이다.

---

## 정보 구조는 나중에 바꾸기 어려웠다

색상을 바꾸는 것은 상대적으로 쉽다.

```text
브라운 → 블루
```

버튼 Radius를 바꾸는 것도 쉽다.

하지만

```text
Home에 있던 기능을

새로운 Page로 분리하고

Navigation을 수정하고

Route를 변경하고

데이터 Flow도 바꾸는 것
```

은 훨씬 큰 작업이 된다.

그래서 프로젝트 초기에 정보 구조를 고민하는 것이 중요했다.

---

## 완벽하게 정할 수는 없다

그렇다고 처음부터 완벽한 구조를 만드는 것도 어렵다.

실제로 사용해봐야

```text
이 정보는 여기보다 저기에 있는 게 낫겠다.

이 화면은 굳이 필요 없겠다.

두 화면을 합쳐도 되겠다.
```

가 보인다.

그래서 정보 구조도

```text
초안
↓
Prototype
↓
실제 사용
↓
수정
```

과정을 거친다.

---

## 내가 페이지 구조를 만들 때 확인할 것

정리하면 다음 질문들을 사용하려고 한다.

```text
1. 이 페이지의 목적은 한 문장으로 설명할 수 있는가?

2. 사용자는 왜 이 페이지에 들어오는가?

3. 이 페이지의 Primary Action은 무엇인가?

4. 목록과 상세의 역할이 구분되어 있는가?

5. 조회와 편집을 분리해야 하는가?

6. 같은 목적의 화면이 중복되어 있지는 않은가?

7. 한 페이지가 너무 많은 역할을 가지고 있지는 않은가?

8. Navigation에 정말 필요한 최상위 기능만 있는가?

9. 사용자가 원하는 기능이 있을 위치를 예상할 수 있는가?

10. 뒤로 갔을 때 이전 맥락이 유지되는가?

11. 로그인 전후의 접근 범위가 자연스러운가?

12. Loading / Empty / Error 상태도 고려했는가?

13. 실제 데이터가 들어가도 구조가 유지되는가?

14. 화면을 하나 줄이거나 합칠 수 있는가?

15. 반대로 분리해야 더 명확한 화면은 없는가?
```

---

## 내가 생각하는 기본 페이지 역할

프로젝트마다 다르지만 초보 단계에서 구분하기 쉬웠던 역할은 이렇다.

| 화면         | 주요 역할              |
| ---------- | ------------------ |
| Home       | 현재 필요한 정보와 핵심 행동   |
| List       | 여러 항목 탐색·비교        |
| Detail     | 하나의 항목 자세히 확인      |
| Add / Edit | 데이터 입력·수정          |
| Search     | 원하는 대상 찾기          |
| Settings   | 서비스와 계정 환경 설정      |
| Empty      | 데이터가 없을 때 다음 행동 안내 |
| Error      | 문제 설명과 복구 행동 제공    |

이것을 그대로 모든 프로젝트에 적용해야 하는 것은 아니다.

다만 페이지를 만들 때

```text
이 화면은 어떤 역할인가?
```

를 생각하기 위한 기준이 된다.

---

## 페이지 수보다 역할이 중요했다

화면이 5개라고 좋은 것도 아니고,

20개라고 나쁜 것도 아니다.

중요한 것은

```text
각 화면이 필요한 이유가 있는가?
```

다.

화면이 적어도 하나의 페이지에 너무 많은 기능이 몰려 있다면 불편할 수 있다.

화면이 조금 많아도 사용자가 자연스럽게 이동할 수 있다면 문제가 없을 수 있다.

그래서

```text
페이지 개수
```

보다

```text
페이지 역할과 관계
```

를 먼저 보려고 한다.

---

## 정보 구조는 디자인보다 먼저 시작되는 UI/UX였다

처음에는 UI/UX라고 하면

```text
버튼 위치

색상

카드 디자인

폰트
```

를 생각했다.

하지만 페이지 구조를 공부하면서

그보다 앞에 있는 것이 있다는 것을 알게 됐다.

```text
어떤 정보가 있는가?

어떻게 묶을 것인가?

어디에서 보여줄 것인가?

사용자는 어떻게 이동할 것인가?
```

이것들이 정해진 뒤에야

실제 화면 디자인이 의미를 가진다.

---

## 디자인이 복잡하다면 구조부터 의심해보기

화면이 너무 복잡할 때 자꾸

```text
폰트를 줄일까?

카드를 작게 할까?

간격을 좁힐까?
```

만 고민할 수 있다.

하지만 문제는

```text
한 화면에 너무 많은 정보를 넣었다.
```

일 수도 있다.

이럴 때는 시각적 디자인보다

```text
정보를 다른 페이지로 옮길 수 있는가?

상세 화면으로 보낼 수 있는가?

접어서 필요할 때만 보여줄 수 있는가?
```

를 먼저 보는 것이 더 효과적일 수 있다.

---

## 마무리

처음 페이지를 만들 때는

```text
무슨 화면을 만들까?
```

를 생각했다.

지금은 그 전에 한 번 더 질문하려고 한다.

```text
사용자는 왜 이 화면이 필요한가?
```

그리고

```text
이 정보는 정말 여기 있어야 하는가?
```

도 확인한다.

정보 구조가 잘 잡혀 있으면

화면마다 역할이 명확해진다.

```text
홈에서는 시작하고

목록에서는 고르고

상세에서는 확인하고

편집에서는 수정하고

설정에서는 환경을 바꾼다.
```

사용자도 각 화면에서 무엇을 해야 하는지 이해하기 쉬워진다.

결국 정보 구조와 페이지 구성은

> **서비스가 가진 많은 정보와 기능을 사용자의 생각에 맞게 정리하는 일**

이라고 생각한다.

그리고 페이지 구조를 정하고 나면

다음으로 생각해야 할 화면이 있다.

서비스에 데이터가 항상 있는 것은 아니다.

```text
첫 가입이라 아무 기록이 없거나

검색 결과가 없거나

아직 혜택을 등록하지 않았을 수도 있다.
```

이때 화면을 그냥 비워두면

사용자는

```text
오류인가?

아직 없는 건가?

내가 뭘 해야 하지?
```

를 알기 어렵다.
