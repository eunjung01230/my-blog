블로그를 처음 수정할 때는 작업마다 순서가 조금씩 달랐다.

생각난 부분부터 고치고, 화면을 확인하고, 또 다른 파일을 수정했다. 어느 정도 마음에 들면 commit하고 push했지만, 무엇을 확인한 뒤 배포해야 하는지까지 정해져 있지는 않았다.

블로그에 기능이 늘어나고 Claude에게 맡기는 작업도 많아지자 이런 방식이 조금 불안해졌다.

작은 문구 하나를 바꾸는 작업도 있었지만 검색, 카테고리, TOC처럼 여러 파일이 연결되는 작업도 생겼다. 한 부분을 수정했는데 다른 화면이 같이 바뀔 수도 있었고, Claude가 내가 예상한 것보다 넓은 범위를 수정할 수도 있었다.

그래서 어느 순간부터는 **블로그를 수정하는 순서 자체를 하나의 작업 흐름으로 만들기 시작했다.**

지금은 대체로 다음 순서로 작업하고 있다.

```text
수정할 내용 정하기
↓
Claude에게 작업 범위 전달
↓
수정 결과와 변경 파일 확인
↓
로컬에서 직접 테스트
↓
commit
↓
push
↓
GitHub Pages 배포 확인
↓
실제 블로그에서 최종 확인
```

명령어 자체보다 이 순서를 지키는 것이 더 중요했다.

---

## 한 번에 하나의 목적만 잡는다

예전에는 블로그를 보다가 여러 가지가 눈에 들어오면 한꺼번에 수정하고 싶었다.

검색도 추가하고 싶고,

사이드바도 바꾸고 싶고,

포스트 디자인도 손보고 싶은 식이었다.

하지만 작업 범위가 커질수록 문제가 생겼을 때 원인을 찾기 어려웠다.

그래서 지금은 가능하면 하나의 목적만 정한다.

예를 들면

```text
카테고리 접기/펼치기 추가

검색 메뉴 위치 수정

404 페이지 추가

포스트 하나 작성
```

정도로 나눈다.

작업이 작으면 Claude에게 요청하기도 쉽고 결과를 검토하기도 쉽다.

무엇보다 문제가 생겼을 때 어느 변경에서 시작됐는지 찾기 편하다.

---

## Claude에게는 바꿀 것과 유지할 것을 같이 말한다

Claude를 많이 사용하면서 가장 중요하게 느낀 부분이다.

단순히

> 검색 기능 추가해줘.

라고 요청하는 것보다 현재 구조를 먼저 확인하고 수정 범위를 분명히 전달하는 편이 안정적이었다.

특히 자주 사용하는 조건이 있다.

```text
기존 디자인은 유지한다.

현재 기능은 그대로 둔다.

요청한 부분만 수정한다.

관련 없는 파일은 건드리지 않는다.

새로운 기능을 임의로 추가하지 않는다.

확실하지 않은 부분은 임의로 결정하지 않는다.
```

AI는 프로젝트 파일을 볼 수 있어도 내가 머릿속에서 유지하고 싶은 기준까지 자동으로 알 수는 없다.

그래서 **작업 범위를 정해주는 것 자체가 구현의 일부**가 됐다.

---

## Claude의 완료 메시지보다 실제 변경 내용을 본다

Claude가

> 작업을 완료했습니다.

라고 알려줘도 바로 commit하지 않는다.

먼저 어떤 파일이 바뀌었는지 확인하고, 예상하지 않은 파일이 수정됐다면 이유를 본다.

이 과정에서 자주 사용하는 것이

```bash
git status
git diff
```

다.

처음에는 Git을 commit과 push를 위한 도구로만 생각했지만, 지금은 **AI가 수정한 범위를 검수하는 도구**로도 사용하고 있다.

내 기준에서는

```text
Claude 작업 완료
≠
내 작업 완료
```

다.

Claude가 수정을 끝낸 뒤부터 내가 확인하는 단계가 시작된다.

---

## 로컬에서는 실제로 사용해 본다

변경 파일이 예상한 범위 안에 있다면 실제 화면에서 확인한다.

카테고리를 수정했다면 눌러보고,

검색을 수정했다면 검색어를 입력해 보고,

링크를 추가했다면 실제로 이동해 본다.

새 포스트라면 목록에서 보이는지, 본문이 열리는지, 제목과 날짜가 정상적으로 표시되는지도 확인한다.

필요하면 정상적인 경우뿐 아니라 실패 상황도 본다.

예를 들어

```text
검색 결과 없음

없는 주소로 접근한 404 화면

카테고리 접기/펼치기 상태

잘못된 링크 이동
```

같은 경우다.

이전에는 단순히

> 작동하는가?

만 봤다면 지금은

> **의도한 방식으로 작동하는가?**

를 확인하려고 한다.

---

## 수정 범위에 따라 확인 범위도 다르게 잡는다

모든 작업을 똑같이 크게 테스트할 필요는 없었다.

오타 하나를 수정했다면 해당 글만 확인하면 된다.

반대로 사이드바나 공통 레이아웃처럼 여러 페이지에서 사용하는 요소를 바꿨다면 홈, 포스트, 모바일 화면처럼 영향을 받을 수 있는 곳을 더 넓게 본다.

새 기능도 마찬가지다.

포스트 하나 추가하는 작업과 검색 기능을 추가하는 작업은 확인해야 할 범위가 다르다.

그래서 지금은

> **수정 범위만큼만 테스트 범위를 넓힌다.**

라는 기준을 두고 있다.

---

## 확인이 끝난 뒤 commit한다

로컬에서 원하는 결과가 확인되면 그때 Git 기록을 남긴다.

```bash
git add .
git commit -m "작업 내용"
```

다만 서로 다른 목적의 작업을 하나의 commit에 너무 많이 넣지 않으려고 한다.

예를 들어 404 페이지를 추가하고 검색 기능을 수정하고 포스트 여러 개까지 한 번에 넣으면 나중에 기록을 봤을 때 무엇 때문에 문제가 생겼는지 파악하기 어렵다.

그래서 commit 하나를

> 이번 작업에서 무엇을 했는가?

에 대한 하나의 답처럼 사용하려고 한다.

```text
feat: add custom 404 page

feat: add post search

fix: correct broken links

docs: add deployment post
```

이렇게 남겨두면 나중에 최근 변경사항을 확인하기도 쉽다.

---

## push는 운영 사이트에 넘기는 단계로 생각한다

commit은 로컬 기록이지만 push하면 GitHub에 변경사항이 전달된다.

```bash
git push
```

내 블로그는 GitHub Pages 자동 배포가 연결되어 있기 때문에 push 이후 운영 사이트 배포가 시작된다.

그래서 push를 단순히

> GitHub에 백업한다.

정도로 생각하지 않는다.

**실제 공개 블로그에 반영할 변경사항을 넘기는 단계**라고 생각한다.

그렇기 때문에 push 전에 로컬 화면과 변경 파일을 확인하는 과정이 중요해졌다.

---

## push 후에는 Pages와 실제 사이트를 차례로 확인한다

push가 성공했다고 바로 블로그가 바뀌는 것은 아니다.

```text
push
↓
GitHub 저장소 반영
↓
Pages 빌드
↓
배포
↓
실제 사이트 반영
```

과정이 있기 때문이다.

그래서 push 직후 화면이 그대로라고 다시 push하지 않는다.

먼저 GitHub Pages 배포 상태를 확인한다.

Pages에서 성공했다고 나오면 마지막으로 실제 블로그를 연다.

이때는 로컬 테스트를 전부 반복하기보다 **이번에 수정한 핵심 부분만 확인**한다.

예를 들어

* 새 글이면 실제 글 주소
* 404 페이지면 없는 주소
* 링크 수정이면 실제 링크
* 디자인 수정이면 해당 화면

정도다.

GitHub Pages에서는 로컬과 실제 배포 환경의 경로 차이 때문에 로컬에서는 정상인데 배포 후 문제가 생길 수도 있다.

그래서 내 작업 완료 기준은

```text
Pages 성공
```

이 아니라

```text
실제 블로그에서 의도한 결과 확인
```

에 더 가깝다.

---

## 문제가 생기면 어느 단계까지 정상인지부터 본다

이 작업 흐름을 만들고 가장 편해진 부분은 오류가 생겼을 때였다.

예전에는 반영되지 않으면 commit이나 push부터 다시 해볼 수 있었다.

지금은 먼저 어디까지 정상인지 확인한다.

```text
로컬은 정상인가?

GitHub에 최신 commit이 있는가?

Pages 빌드는 성공했는가?

실제 사이트에서만 문제가 생기는가?
```

GitHub에는 최신 commit이 있는데 Pages만 실패했다면 push 문제가 아니다.

Pages도 성공했는데 이미지 하나만 깨졌다면 경로를 확인하면 된다.

이렇게 단계별로 나누면 전체 프로젝트를 처음부터 다시 볼 필요가 없다.

---

## 글 작성도 같은 흐름 안에 들어왔다

이 작업 방식은 코드 수정에만 사용하는 것이 아니다.

새 포스트를 작성할 때도 비슷하다.

먼저 실제 경험에 맞게 글을 작성하고,

이전 글과 중복되는 내용은 없는지,

아직 구현하지 않은 기능을 이미 구현한 것처럼 쓰지는 않았는지 확인한다.

그다음 포스트 파일을 추가하고 실제 블로그 화면에서 읽어본다.

긴 글은 채팅창에서 볼 때와 실제 블로그 폭에서 읽을 때 느낌이 다르기 때문이다.

결국 글 작성도

```text
작성
↓
적용
↓
실제 화면 확인
↓
수정
↓
배포
```

라는 개발 작업과 비슷한 흐름으로 바뀌었다.

---

## 지금은 이 순서가 가장 편하다

현재 내가 블로그를 수정하고 배포하는 과정은 특별한 자동화 시스템은 아니다.

하지만 아무 순서 없이 수정하던 때와 비교하면 훨씬 안정적이다.

정리하면 다음과 같다.

```text
1. 한 번에 하나의 작업만 정한다.

2. Claude에게 수정 범위와 유지 조건을 전달한다.

3. 변경 파일과 실제 화면을 확인한다.

4. 작업 목적별로 commit한다.

5. push해 GitHub Pages 배포를 시작한다.

6. 실제 공개 블로그에서 최종 결과를 확인한다.

7. 문제가 있으면 실패한 단계부터 다시 본다.
```

결국 내가 만든 흐름을 한 문장으로 줄이면 이렇다.

> **작게 수정하고, 직접 확인한 뒤, 확인된 변경만 배포한다.**

블로그가 커지고 글과 기능이 함께 쌓일수록 이 순서가 점점 더 중요해지고 있다.

처음에는 블로그를 만드는 방법을 배우고 있었다면, 이제는 조금씩 **내 블로그를 안정적으로 관리하는 방법**도 만들어가고 있다.
