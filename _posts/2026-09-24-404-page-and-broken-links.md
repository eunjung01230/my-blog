블로그를 만들 때는 대부분 정상적인 화면부터 확인하게 된다.

홈이 잘 열리는지,

포스트를 눌렀을 때 본문으로 이동하는지,

카테고리와 메뉴가 제대로 연결되는지를 먼저 본다.

나 역시 그랬다.

그런데 글이 늘어나고 카테고리와 메뉴를 계속 수정하다 보니 정상적인 주소뿐 아니라 **잘못된 주소로 들어왔을 때는 어떻게 되는지**도 생각하게 됐다.

글 주소가 바뀌거나,

링크에 오타가 있거나,

예전에 공유했던 주소가 더 이상 존재하지 않을 수도 있다.

이럴 때 사용자가 마주치는 것이 `404` 페이지다.

처음에는 단순한 오류 화면이라고 생각했지만, 실제로는 **잘못된 주소에 들어온 사용자가 다시 블로그로 돌아올 수 있게 만드는 페이지**에 더 가까웠다.

---

## 404는 여러 이유로 생길 수 있었다

블로그에서는 생각보다 다양한 이유로 404가 생길 수 있다.

```text
포스트 주소가 변경됨

파일 이름이나 경로가 바뀜

카테고리 구조가 바뀜

링크에 오타가 있음

삭제된 글을 가리키고 있음

예전에 공유한 주소가 더 이상 존재하지 않음
```

특히 블로그를 계속 개편하고 있다면 구조를 바꾸면서 기존 주소까지 달라지지 않는지 확인할 필요가 있었다.

화면에서 새 페이지가 정상적으로 보인다고 해서 이전 링크까지 안전한 것은 아니었다.

---

## 글 제목과 URL은 같은 무게로 보면 안 됐다

포스트 제목은 필요하면 수정할 수 있다.

더 자연스러운 제목이 생각날 수도 있고, 글 내용을 보완하면서 제목도 달라질 수 있다.

하지만 URL은 한 번 공개되면 다른 곳에 남을 수 있다.

블로그의 다른 글에서 연결했을 수도 있고,

메신저로 공유했을 수도 있고,

나중에는 검색 결과에 남을 수도 있다.

그래서

```text
글 제목
→ 필요하면 수정 가능

이미 공개된 URL
→ 변경 전 영향 확인
```

정도로 구분해서 생각하는 편이 맞았다.

주소는 단순한 내부 값이 아니라 **외부와 연결되는 정보**였다.

---

## 카테고리나 구조 변경도 링크에 영향을 줄 수 있었다

블로그를 운영하다 보면 카테고리 이름을 바꾸거나 비슷한 분류를 합치고 싶을 수 있다.

문제는 블로그 구조에 따라 카테고리나 파일 위치가 URL과 연결되어 있을 수 있다는 점이다.

그렇다면 이름 하나를 바꾸는 작업이 기존 링크 변경으로 이어질 수도 있다.

그래서 구조를 수정할 때는

> 화면에서 더 깔끔해졌는가?

뿐 아니라

> **기존 주소가 달라지지는 않는가?**

도 같이 봐야 했다.

---

## GitHub Pages에서는 실제 배포 경로도 확인해야 했다

내 블로그는 GitHub Pages를 사용하고 있고 프로젝트 경로 아래에서 열리는 구조다.

이런 환경에서는 로컬에서는 정상인데 실제 배포 후 링크가 잘못되는 경우도 있을 수 있다.

예를 들어 경로를 루트 기준으로 작성했는데 실제 사이트는 `/my-blog/` 아래에서 동작한다면 내가 예상한 위치와 달라질 수 있다.

그래서 링크는

```text
로컬에서 열린다
```

만 확인하는 것으로 끝내지 않고

```text
배포된 실제 사이트에서도 열린다
```

까지 확인해야 했다.

---

## 내부 링크와 외부 링크는 관리 방식이 달랐다

블로그 안에서 다른 포스트로 연결하는 내부 링크는 내가 직접 관리할 수 있다.

하지만 원본 포스트의 주소를 바꾸면 연결된 링크도 함께 영향을 받는다.

포스트가 많아질수록

> 어디에서 이 글을 링크했지?

를 기억하기 어려워질 수 있다.

그래서 가능하면 이미 공개된 주소는 유지하는 편이 관리하기 쉽다.

반면 외부 링크는 내가 통제할 수 없다.

GitHub 문서나 공식 사이트, 다른 블로그의 주소가 나중에 변경될 수도 있다.

그래서 중요한 외부 자료를 연결할 때는 URL만 던져두기보다 **무엇을 참고한 링크인지 글 안에서도 설명해 두는 편**이 낫다고 생각했다.

링크가 사라져도 글의 의미까지 같이 사라지는 것을 줄일 수 있기 때문이다.

---

## 404 페이지는 단순해도 충분했다

404 페이지를 화려하게 꾸밀 필요는 없었다.

목적은 두 가지면 충분했다.

```text
현재 페이지가 존재하지 않는다는 것을 알려준다.

다시 정상적인 페이지로 이동할 방법을 제공한다.
```

예를 들면

```text
페이지를 찾을 수 없습니다.

주소가 변경되었거나 삭제된 페이지일 수 있습니다.

[홈으로 이동]
```

정도다.

필요하다면 포스트 목록이나 검색으로 이동할 수 있게 할 수도 있다.

중요한 것은 많은 기능을 넣는 것이 아니라 **막힌 곳에서 다시 이동할 수 있게 하는 것**이었다.

---

## 404 페이지는 깨진 링크를 고쳐주지 않는다

이 부분은 명확히 구분할 필요가 있었다.

```text
깨진 링크 예방
→ URL과 링크를 제대로 관리

404 페이지
→ 문제가 생겼을 때 다시 이동할 방법 제공
```

404 페이지가 잘 만들어져 있다고 해서 내부 링크가 계속 깨져 있어도 되는 것은 아니다.

가장 먼저 해야 하는 것은 정상적인 링크를 유지하는 것이다.

404는 그다음의 안전장치에 가깝다.

---

## 일부러 잘못된 주소로 들어가 보는 테스트도 필요했다

404 페이지는 정상적인 블로그 사용만으로는 보기 어렵다.

그래서 확인하려면 일부러 존재하지 않는 주소로 들어가 보는 편이 가장 확실하다.

예를 들면

```text
/my-blog/없는-페이지
```

같은 경로다.

이렇게 접속해서

404 화면이 정상적으로 나오는지,

홈으로 돌아가는 링크가 작동하는지,

전체 디자인과 너무 동떨어져 보이지 않는지를 확인할 수 있다.

정상 상태뿐 아니라 **실패 상태도 일부러 만들어보는 테스트**였다.

---

## 중요한 링크는 실제로 눌러보는 것이 가장 간단했다

현재 블로그 규모에서는 복잡한 검사 도구보다 직접 확인하는 방법이 더 현실적이었다.

메뉴,

카테고리,

GitHub 링크,

포스트 안의 중요한 내부 링크를 실제로 눌러보면 된다.

특히 구조를 수정한 직후에는 관련된 링크만이라도 바로 확인하는 편이 좋다.

```text
수정
↓
관련 링크 직접 클릭
↓
배포 환경에서도 확인
```

간단하지만 나중에 어디에서 문제가 생겼는지 추적하는 것보다 훨씬 빠르다.

포스트가 훨씬 많아져 직접 확인이 부담스러워지면 그때 링크 검사 도구나 자동화를 생각해도 늦지 않다.

---

## 삭제할 때도 연결 관계를 생각해야 했다

포스트 삭제 역시 파일 하나를 지우는 문제로 끝나지 않을 수 있다.

다른 글에서 해당 포스트를 연결하고 있다면 삭제한 순간 그 링크는 깨진다.

그래서 글을 삭제하거나 크게 이동할 일이 생기면

> 이 글을 가리키는 링크가 있는가?

> 다른 페이지로 연결할 필요가 있는가?

정도는 한 번 확인하는 편이 좋겠다.

글이 많아질수록 블로그 관리에는 **새 글을 만드는 일뿐 아니라 기존 글의 연결 관계를 지키는 일**도 포함된다.

---

## 앞으로 URL을 조금 더 조심해서 다루려고 한다

블로그 초기에는 글을 만들고 화면에 잘 나오면 끝이라고 생각하기 쉬웠다.

하지만 글이 쌓이고 서로 링크되기 시작하면 URL 자체도 관리해야 하는 정보가 된다.

그래서 앞으로는 몇 가지 기준을 두려고 한다.

```text
공개된 포스트 URL을 이유 없이 자주 바꾸지 않는다.

카테고리나 구조를 수정할 때 기존 링크 영향을 확인한다.

내부 링크를 추가하면 실제로 눌러본다.

로컬뿐 아니라 배포된 사이트에서도 확인한다.

없는 주소에서는 404 페이지를 통해 다시 이동할 수 있게 한다.
```

복잡한 규칙은 아니지만 이런 기본적인 습관이 깨진 링크를 줄이는 데 더 도움이 될 것 같다.

---

## 404보다 중요한 것은 '길이 끊기지 않게 하는 것'이었다

처음에는 404 페이지도 하나의 디자인 요소라고 생각했다.

하지만 정리해 보니 핵심은 더 단순했다.

가장 좋은 것은 애초에 깨진 링크를 최대한 만들지 않는 것이다.

그럼에도 잘못된 주소나 오래된 링크를 완전히 없앨 수는 없다.

그때 404 페이지가 사용자를 다시 블로그로 돌려보내는 역할을 한다.

결국 내가 챙기고 싶은 것은 `404.html` 파일 하나가 아니다.

**기존 링크는 가능한 오래 유지하고, 문제가 생기더라도 사용자가 막다른 곳에 남지 않게 하는 것.**

블로그가 쌓일수록 새 페이지를 만드는 것만큼 **이미 만들어둔 페이지로 가는 길을 지키는 일**도 중요해질 것 같다.

---

## 직접 404 페이지 확인해 보기

글을 작성한 뒤 실제 블로그에도 커스텀 404 페이지를 추가했다.

존재하지 않는 주소로 접속하면 GitHub Pages의 기본 오류 화면 대신 블로그 디자인에 맞춘 404 페이지가 나타나고, **홈으로 이동**을 눌러 다시 블로그로 돌아올 수 있도록 했다.

아래 주소는 일부러 존재하지 않는 경로로 만든 테스트 링크다.

**404 페이지 확인:** [eunjung01230.github.io/my-blog/없는-페이지](https://eunjung01230.github.io/my-blog/%EC%97%86%EB%8A%94-%ED%8E%98%EC%9D%B4%EC%A7%80)

글에서 정리한 내용을 실제 블로그에도 적용해 보면서, 404 페이지의 목적은 오류 화면을 꾸미는 것이 아니라 **잘못된 주소에 도착했을 때 다시 돌아갈 길을 만들어주는 것**이라는 점이 더 분명해졌다.
