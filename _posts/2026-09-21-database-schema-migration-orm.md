## 들어가며

탄천런 프로젝트를 하면서 데이터베이스를 처음 제대로 만져봤다. 그때는 Schema, Migration, ORM 같은 말이 전부 비슷한 것처럼 들렸고, 어디까지 해야 "DB 연결이 끝난 것"인지도 몰랐다.

그래서 프로젝트에서 스쳐 지나간 개념들을 처음부터 다시 공부해서, 다음에 다른 프로젝트를 할 때도 그대로 꺼내 쓸 수 있는 일반적인 지식으로 정리해두려고 한다. 이 글은 프로젝트 회고가 아니라 개념 정리 노트다.

순서는 Database에서 시작해서 ORM과 실제 애플리케이션 연결까지 한 줄로 이어지도록 잡았다.

## 1. Database란 무엇인가

### 데이터란

데이터(data)는 프로그램이 다루는 값 하나하나다. 사용자의 닉네임, 러닝 기록의 거리, 기록을 저장한 시각 같은 것이 전부 데이터다.

혼자 쓰는 계산기 프로그램이라면 데이터를 굳이 어딘가에 남겨둘 필요가 없다. 하지만 서비스는 다르다. **어제 저장한 기록이 오늘도 남아 있어야 하고, 프로그램을 껐다 켜도 사라지면 안 된다.** 이렇게 "계속 남아 있어야 하는 데이터"를 어디에 어떻게 둘지의 문제에서 데이터베이스가 출발한다.

### Database

데이터베이스(database, DB)는 **데이터가 정해진 구조에 맞춰 모여 있는 저장 공간**이다. 그냥 쌓아두는 창고가 아니라, 어떤 형태로 들어가야 하는지가 미리 정해져 있는 창고에 가깝다.

### 왜 파일이나 코드에 직접 저장하지 않는가

처음에는 "그냥 파일에 저장하면 안 되나?"라고 생각했다. 실제로 아주 작은 데이터는 파일에 저장해도 된다. 문제는 서비스 규모가 조금만 커져도 아래 상황을 전부 직접 해결해야 한다는 점이다.

| 상황 | 파일에 직접 저장하면 | 데이터베이스를 쓰면 |
|---|---|---|
| 특정 조건으로 찾기 | 파일을 처음부터 끝까지 읽어서 직접 걸러야 함 | 조건을 주고 요청하면 찾아줌 |
| 여러 사람이 동시에 저장 | 같은 파일을 동시에 쓰다가 내용이 깨질 수 있음 | 동시 접근을 처리하는 장치가 들어 있음 |
| 저장 도중 오류 발생 | 반만 저장된 상태로 남을 수 있음 | 다 되거나 아예 안 되거나로 처리할 수 있음 |
| 잘못된 값 입력 | 코드에서 일일이 막아야 함 | 구조 자체에서 막을 수 있음 |
| 데이터가 아주 많아질 때 | 점점 느려짐 | 빠르게 찾는 장치가 준비되어 있음 |

코드에 값을 직접 써두는 것은 더 문제다. 값을 바꾸려면 코드를 고쳐서 다시 배포해야 하고, 사용자가 만든 데이터는 아예 저장할 수가 없다.

### DBMS란

여기서 헷갈렸던 게 Database와 DBMS의 차이였다.

DBMS(Database Management System, 데이터베이스 관리 시스템)는 **데이터베이스를 실제로 저장하고 꺼내주고 관리해주는 소프트웨어**다.

```text
Database  = 데이터가 모여 있는 저장 공간 / 구조
DBMS      = 그 저장 공간을 만들고 관리하고 응답해주는 프로그램
```

내가 이해한 방식으로 비유하면, 데이터베이스가 "책이 정리되어 있는 서가"라면 DBMS는 "그 서가를 관리하고 책을 찾아다 주는 사서"다. 우리가 코드에서 말을 거는 대상은 사실 서가가 아니라 사서 쪽이다.

일상적으로는 둘 다 그냥 "DB"라고 부르는 경우가 많아서, 처음에는 이 구분이 잘 보이지 않았다.

## 2. 관계형 데이터베이스

### 관계형 데이터베이스란

관계형 데이터베이스(relational database, RDB)는 **데이터를 표 형태로 저장하고, 표와 표 사이를 연결해서 관리하는 방식**의 데이터베이스다.

엑셀 시트를 여러 장 만들어두고 시트끼리 서로를 가리키게 해둔 모습을 떠올리면 비슷하다. 지금 널리 쓰이는 데이터베이스 상당수가 이 방식이다.

### Table, Row, Column

| 용어 | 쉬운 설명 |
|---|---|
| Table (테이블) | 하나의 표. 보통 "사용자", "러닝 기록"처럼 한 종류의 데이터를 담는다 |
| Row (행, 레코드) | 표의 가로 한 줄. 데이터 한 건을 뜻한다. 사용자 1명, 기록 1개 |
| Column (열, 필드) | 표의 세로 한 칸. 그 데이터가 가지는 항목의 종류를 뜻한다 |

users 테이블을 예로 들면 이렇다.

| id | nickname | created_at |
|---|---|---|
| 1 | eunjung | 2026-09-21 10:00:00 |
| 2 | runner_kim | 2026-09-21 11:30:00 |
| 3 | tanchun | 2026-09-21 14:20:00 |

- **Table**은 `users` 전체다. "사용자"라는 한 종류의 데이터를 모아둔 표다.
- **Row**는 가로 한 줄이다. 위 표에는 Row가 3개 있고, 사용자가 3명 저장되어 있다는 뜻이다.
- **Column**은 `id`, `nickname`, `created_at` 세 개다. "모든 사용자는 이 세 가지 항목을 가진다"는 뜻이다.

여기서 중요한 점이 하나 있다. Column은 **타입(type, 값의 종류)** 도 함께 정해진다. `id`는 숫자, `nickname`은 문자열, `created_at`은 시각이다. 타입이 정해져 있기 때문에 `nickname` 자리에 날짜가 들어가는 일을 데이터베이스가 막아줄 수 있다.

## 3. PostgreSQL은 무엇인가

PostgreSQL이라는 이름을 처음 봤을 때는 이게 데이터베이스 그 자체인 줄 알았다. 하지만 앞에서 정리한 구분을 적용하면 위치가 명확해진다.

```text
Database    = 개념. 데이터가 모여 있는 저장 공간
RDB         = 그중 표 형태로 저장하는 방식
PostgreSQL  = 그 방식을 실제로 구현해서 관리해주는 DBMS 제품 중 하나
```

같은 자리에 올 수 있는 다른 이름으로는 MySQL, SQLite, MariaDB 같은 것들이 있다. 이들은 서로 경쟁 제품이라기보다 **같은 역할을 하는 다른 선택지**로 보는 편이 이해하기 쉬웠다. 무엇이 무조건 더 좋다기보다 프로젝트의 상황과 필요한 기능에 따라 고르는 것이다.

정리하면 "우리 프로젝트는 PostgreSQL을 쓴다"는 말은 **"관계형 데이터베이스를 쓰는데, 그걸 관리하는 소프트웨어로 PostgreSQL을 골랐다"** 는 뜻이다.

## 4. Primary Key와 ID

### 왜 ID가 필요한가

users 테이블에서 `nickname`으로 사용자를 구분하면 안 될까? 처음에는 그래도 될 것 같았다. 하지만 문제가 생긴다.

- 닉네임은 바뀔 수 있다. 사용자가 닉네임을 바꾸는 순간, 그 사람을 가리키던 기준이 사라진다.
- 닉네임이 겹칠 수 있다. 같은 닉네임이 두 명이면 누구를 말하는지 알 수 없다.
- 한글이나 이모지가 들어가면 비교하고 찾는 과정이 복잡해진다.

그래서 **절대 바뀌지 않고, 절대 겹치지 않는 값**을 따로 하나 둔다. 그게 `id`다.

### Primary Key

**Primary Key(기본 키, PK)** 는 **테이블에서 Row 하나를 확실하게 구분해주는 Column**이다. 보통 `id`가 그 역할을 맡는다.

Primary Key에는 두 가지 규칙이 있다.

| 규칙 | 의미 |
|---|---|
| 고유값 (unique) | 같은 값이 두 번 나올 수 없다 |
| 비어 있을 수 없음 (not null) | 값이 없는 Row는 존재할 수 없다 |

이 두 규칙은 코드가 지키는 게 아니라 **데이터베이스가 직접 막아준다.** 같은 id를 또 넣으려고 하면 저장 자체가 거부된다.

이걸 이해하고 나니 서비스에서 닉네임을 자유롭게 바꿀 수 있는 이유도 같이 이해됐다. 실제로 데이터가 연결되어 있는 기준은 닉네임이 아니라 뒤에 숨어 있는 id이기 때문에, 닉네임이 바뀌어도 그 사람의 기록은 그대로 따라온다.

## 5. Foreign Key와 데이터 관계

### 1:N 관계

사용자 1명은 러닝 기록을 여러 개 남길 수 있다. 반대로 러닝 기록 1개는 반드시 사용자 1명의 것이다.

이런 관계를 **1:N 관계(일대다 관계)** 라고 부른다.

```text
users (사용자)
  |
  |   사용자 1명
  |     -> 러닝 기록 여러 개
  v
running_records (러닝 기록)
```

### Foreign Key

그러면 "이 기록이 누구 것인지"를 어떻게 표시할까? 러닝 기록 표에 **사용자의 id를 적어두는 Column**을 하나 만든다.

running_records 테이블은 이런 모습이 된다.

| id | user_id | distance_km | created_at |
|---|---|---|---|
| 1 | 1 | 5.2 | 2026-09-21 07:00:00 |
| 2 | 1 | 3.8 | 2026-09-22 07:10:00 |
| 3 | 2 | 10.0 | 2026-09-22 08:00:00 |

`user_id`를 보면 1번 기록과 2번 기록은 1번 사용자(eunjung)의 것이고, 3번 기록은 2번 사용자(runner_kim)의 것이라는 걸 알 수 있다.

이렇게 **다른 테이블의 Primary Key를 가리키는 Column**을 **Foreign Key(외래 키, FK)** 라고 한다.

여기서 "그냥 숫자 하나 적어둔 것 아닌가?"라고 생각할 수 있는데, Foreign Key로 지정해두면 데이터베이스가 한 가지를 더 해준다. **존재하지 않는 사용자의 id를 적으려고 하면 막아준다.** 예를 들어 users에 없는 99번 사용자의 기록을 저장하려고 하면 거부된다.

주인 없는 기록이 생기는 것을 데이터베이스가 구조적으로 막아주는 셈이다. 이 부분이 "관계형"이라는 이름이 붙은 이유이기도 하다.

## 6. Schema란 무엇인가

여기서부터가 내가 가장 헷갈렸던 부분이다.

### Schema의 정의

**Schema(스키마)** 는 **데이터베이스에 어떤 테이블이 있고, 각 테이블에 어떤 Column이 어떤 타입으로 있으며, 테이블끼리 어떻게 연결되는지를 정의해둔 구조**다.

지금까지 정리한 내용을 전부 글로 적어둔 설계도라고 보면 된다.

| Schema가 정하는 것 | 예 |
|---|---|
| 어떤 테이블이 있는가 | users, running_records |
| 각 테이블에 어떤 Column이 있는가 | users에는 id, nickname, created_at |
| 각 Column의 타입은 무엇인가 | id는 숫자, nickname은 문자열 |
| 어떤 제약이 있는가 | id는 Primary Key, nickname은 비어 있으면 안 됨 |
| 테이블끼리 어떻게 연결되는가 | running_records.user_id는 users.id를 가리킴 |

요즘 프로젝트에서는 이 Schema를 코드 파일로 작성해두는 경우가 많다. 그래야 설계도도 Git으로 버전 관리가 되고, 팀원들이 같은 구조를 공유할 수 있기 때문이다.

### Schema 작성과 실제 DB는 다르다

내가 가장 크게 착각했던 부분이 이것이다.

```text
Schema 파일을 작성했다
       (같지 않다)
실제 데이터베이스에 테이블이 만들어졌다
```

Schema 파일은 **"이런 구조여야 한다"고 적어둔 설계도일 뿐**이다. 설계도를 그렸다고 해서 건물이 저절로 지어지지 않는 것과 같다.

실제 데이터베이스는 그 파일의 존재를 알지 못한다. Schema는 내 프로젝트 폴더 안의 파일이고, 데이터베이스는 그와 별개로 돌아가는 소프트웨어이기 때문이다.

설계도를 실제 건물로 옮기는 별도의 과정이 반드시 필요하다. 그게 다음에 나오는 Migration이다.

## 7. Migration이란 무엇인가

### 왜 필요한가

처음에 users 테이블을 이렇게 만들었다고 하자.

```text
users
  - id
  - nickname
```

그런데 나중에 "가입한 시각도 저장하고 싶다"는 요구가 생겼다. 그래서 Schema 파일을 이렇게 고친다.

```text
users
  - id
  - nickname
  - created_at   <- 새로 추가
```

이때 실제 데이터베이스는 어떻게 될까? **아무 일도 일어나지 않는다.** 데이터베이스에는 여전히 id와 nickname만 있는 users 테이블이 그대로 있다. 그리고 그 테이블에는 이미 저장된 사용자 데이터가 들어 있다.

여기서 문제가 까다로워진다. 이미 데이터가 들어 있는 테이블의 구조를 바꿔야 하기 때문이다. 테이블을 지우고 새로 만들 수는 없다. 실제 서비스라면 사용자 데이터가 전부 날아간다.

### Migration

**Migration(마이그레이션)** 은 **데이터베이스 구조의 변경 사항을, 기존 데이터를 지키면서 순서대로 안전하게 적용하는 방법**이다.

흐름은 이렇다.

```text
1. Schema 변경        코드에서 설계도를 고친다
        |
        v
2. Migration 생성     바뀐 부분을 찾아서 "변경 지시서"를 만든다
        |
        v
3. Migration 적용     그 지시서를 실제 데이터베이스에 실행한다
        |
        v
4. 실제 DB 구조 변경  이제야 진짜 테이블이 바뀐다
```

2번에서 만들어지는 Migration 파일에는 "users 테이블에 created_at Column을 추가하라" 같은 **변경 내용만** 담긴다. 전체 구조를 처음부터 다시 만드는 게 아니라, 이전 상태에서 다음 상태로 가는 차이만 담는 것이다.

### Migration의 두 가지 성격

Migration을 이해할 때 도움이 됐던 관점이 두 가지 있다.

**첫째, Migration은 이력이다.** Migration 파일들은 순서대로 쌓인다. 1번 적용, 2번 적용, 3번 적용처럼 이어진다. 이 순서를 그대로 따라가면 텅 빈 데이터베이스에서도 현재 구조를 똑같이 만들어낼 수 있다. Git의 커밋 기록과 성격이 비슷하다.

**둘째, Migration은 적용 여부가 따로 기록된다.** 데이터베이스는 "지금까지 몇 번까지 적용했는지"를 스스로 기억한다. 그래서 같은 Migration이 두 번 실행되는 일이 생기지 않는다.

이 두 가지 덕분에 내 컴퓨터의 데이터베이스와 팀원의 데이터베이스와 배포 환경의 데이터베이스가 같은 구조를 유지할 수 있다.

### 다시 강조

```text
Schema 파일 수정  =  설계도를 고친 것
Migration 적용    =  실제 건물을 고친 것
```

Schema만 고치고 Migration을 적용하지 않으면, 코드는 created_at이 있다고 믿고 동작하는데 실제 데이터베이스에는 그 Column이 없는 상태가 된다. 프로젝트에서 부딪혔던 오류 상당수가 결국 이 상태였다.

## 8. Query란 무엇인가

지금까지는 **구조**에 대한 이야기였다. 이제 그 구조 안에 든 **데이터를 실제로 다루는** 이야기다.

**Query(쿼리)** 는 **데이터베이스에 보내는 요청**이다. "이런 데이터를 찾아줘", "이 데이터를 저장해줘" 같은 부탁이다.

이 요청을 쓸 때 사용하는 언어가 **SQL(Structured Query Language)** 이다. 관계형 데이터베이스에서 표준처럼 쓰이는 언어다.

아주 짧은 예만 보면 이렇다.

```sql
SELECT nickname FROM users;
```

users 테이블에서 nickname을 가져와 달라는 요청이다.

```sql
INSERT INTO users (nickname) VALUES ('eunjung');
```

users 테이블에 nickname이 eunjung인 Row를 하나 넣어 달라는 요청이다.

이번 글에서 SQL 문법을 더 파고들지는 않는다. 지금 중요한 건 **데이터베이스와 대화하려면 결국 Query를 보내야 하고, 그 언어가 SQL이라는 것**을 아는 데까지다.

## 9. CRUD

데이터를 다루는 요청은 종류가 많아 보여도 결국 네 가지로 묶인다. 그 네 가지의 앞 글자를 딴 말이 **CRUD**다.

| CRUD | 의미 | 예시 |
|---|---|---|
| Create | 생성 | 러닝 기록 저장 |
| Read | 조회 | 내 기록 보기 |
| Update | 수정 | 닉네임 수정 |
| Delete | 삭제 | 기록 삭제 |

처음 봤을 때는 그냥 외워야 하는 약어인 줄 알았는데, 실제로는 **기능을 설계할 때 빠진 게 없는지 확인하는 체크리스트**로 쓸 수 있는 개념이었다.

예를 들어 "러닝 기록 기능을 만든다"고 하면 이렇게 나눠서 생각해볼 수 있다.

- Create: 기록을 저장할 수 있는가
- Read: 저장한 기록을 다시 볼 수 있는가
- Update: 잘못 입력한 기록을 고칠 수 있는가
- Delete: 기록을 지울 수 있는가

이렇게 쪼개놓으면 "저장은 되는데 목록에서 안 보인다" 같은 상황에서 어느 부분이 문제인지 훨씬 빨리 좁힐 수 있다.

## 10. ORM이란 무엇인가

### ORM은 데이터베이스가 아니다

ORM이라는 말을 처음 들었을 때는 데이터베이스의 한 종류인 줄 알았다. 하지만 아니었다.

```text
ORM 은 Database 가 아니다
ORM 은 PostgreSQL 이 아니다
```

**ORM(Object-Relational Mapping, 객체 관계 매핑)** 은 **애플리케이션 코드에서 데이터베이스를 다루기 쉽게 도와주는 도구이자 방식**이다.

이름을 풀어보면 의미가 조금 더 잡힌다. 데이터베이스는 데이터를 **표(관계형)** 로 다루고, 프로그래밍 언어는 데이터를 **객체(object)** 로 다룬다. 이 서로 다른 두 세계를 이어준다(mapping)는 뜻이다.

### 위치

```text
애플리케이션 코드
       |
       v
      ORM          코드를 SQL로 바꿔서 전달하고, 결과를 다시 코드로 바꿔준다
       |
       v
  PostgreSQL       실제로 데이터를 저장하고 찾아준다
```

ORM은 데이터베이스를 **대신하는** 게 아니라 데이터베이스 **앞에 서 있는** 층이다.

### 무엇이 편해지는가

| 항목 | ORM 없이 | ORM을 쓰면 |
|---|---|---|
| Query 작성 | SQL 문자열을 직접 작성 | 코드의 함수 호출처럼 작성 |
| 오타 확인 | 실행해봐야 알 수 있음 | 작성 중에 미리 잡히는 경우가 많음 |
| 결과 처리 | 받아온 값을 직접 변환 | 코드에서 쓰는 형태로 바로 받음 |
| Schema 관리 | 직접 관리 | Schema 정의와 Migration 도구를 함께 제공하는 경우가 많음 |

### 그래도 SQL과 DB를 알아야 한다

여기가 중요한 부분이다. ORM을 쓴다고 SQL이 사라지는 게 아니다.

ORM은 결국 **내부에서 SQL을 만들어서 데이터베이스에 보낸다.** 내가 SQL을 직접 안 쓸 뿐이지, 오가는 것은 여전히 SQL이다.

그래서 이런 일이 생긴다.

- 문제가 생겼을 때 오류 메시지는 데이터베이스가 보낸 SQL 기준의 메시지다
- 왜 느린지 알아보려면 어떤 SQL이 나갔는지 확인해야 한다
- Foreign Key나 타입 제약에 걸리면 원인은 결국 데이터베이스 구조 쪽에 있다

**ORM을 사용한다는 것은 DB와 SQL을 몰라도 된다는 뜻이 아니라, 매번 직접 쓰지 않아도 된다는 뜻**이었다.

### 제품 이름에 대해

ORM은 하나의 개념이고, 그 개념을 구현한 도구가 여러 개 있다. 일반적으로 이름이 자주 언급되는 것으로는 Drizzle, Prisma, TypeORM, Sequelize 같은 것들이 있다. 여기서는 개념을 설명하기 위해 예시로 든 이름이고, 각각을 비교하는 것은 이 글의 범위가 아니다.

참고로 탄천런 프로젝트에서 실제로 사용했던 것은 PostgreSQL과 Drizzle이었다. 다만 이 글에서 정리한 ORM의 개념 자체는 특정 도구와 상관없이 공통으로 적용되는 내용이다.

## 11. 로컬 DB와 클라우드 DB

### 같은 PostgreSQL, 다른 위치

데이터베이스가 "어디에서 돌아가는가"도 처음에는 헷갈렸다.

| 구분 | 위치 | 주로 쓰는 상황 |
|---|---|---|
| 로컬 DB | 내 컴퓨터 안에서 실행 | 혼자 개발하고 실험할 때 |
| 클라우드 / 서버 DB | 인터넷 너머의 서버에서 실행 | 팀이 함께 쓰거나, 실제 서비스를 운영할 때 |

여기서 중요한 점은 **둘 다 PostgreSQL일 수 있다는 것**이다. 종류가 다른 게 아니라 **같은 DBMS가 놓인 위치가 다를 뿐**이다.

로컬 DB는 내 컴퓨터가 꺼지면 접근할 수 없고, 다른 사람이 볼 수도 없다. 그래서 실제 서비스는 계속 켜져 있는 서버 쪽 데이터베이스를 쓴다.

### 클라우드 DB 서비스

PostgreSQL을 서버에 직접 설치하고 관리하는 일은 꽤 번거롭다. 그래서 **PostgreSQL을 클라우드에서 바로 쓸 수 있게 제공해주는 서비스**들이 있다. Neon 같은 이름이 여기에 해당한다.

여기서 또 한 번 층을 구분해야 한다.

```text
PostgreSQL   = DBMS. 데이터베이스를 관리하는 소프트웨어
Neon 등      = 그 PostgreSQL을 클라우드에서 사용할 수 있게 제공하는 서비스의 예
```

"PostgreSQL을 쓴다면서 왜 다른 서비스 이름도 같이 나오지?"라고 생각했었는데, 둘 중 하나를 고르는 관계가 아니었다. **그 서비스 위에서 PostgreSQL을 쓰는 것**이다.

이 문단의 서비스 이름은 개념을 설명하기 위한 일반적인 예시다.

### DATABASE_URL

어느 쪽이든 애플리케이션은 "어느 데이터베이스에 접속할지"를 알아야 한다. 그 접속 정보를 담은 값이 보통 `DATABASE_URL`이라는 이름으로 환경 변수에 들어간다.

로컬에서 개발할 때는 내 컴퓨터의 데이터베이스를 가리키고, 배포 환경에서는 서버의 데이터베이스를 가리킨다. 코드는 그대로인데 이 값만 달라지는 구조다.

## 12. 화면의 데이터와 실제 DB 데이터

### 화면에 보인다고 DB에 있는 게 아니다

이것도 프로젝트를 하면서 크게 헷갈렸던 부분이다.

화면에 러닝 기록 목록이 잘 나오고 있으면 "데이터베이스에 데이터가 들어 있구나"라고 생각하게 된다. 하지만 그게 아닐 수 있다.

**Mock Data(목 데이터, 임시로 만들어둔 가짜 데이터)** 라는 게 있다. 화면을 먼저 만들 때 데이터베이스가 아직 준비되지 않았으면, 코드 안에 값을 직접 적어두고 화면을 그린다.

```text
코드 안에 직접 적어둔 값     ->  Mock / 임시 데이터일 수 있음
데이터베이스에서 가져온 값   ->  진짜 데이터
```

화면만 봐서는 이 둘이 구분되지 않는다. 둘 다 똑같이 화면에 잘 나온다.

### 실제 데이터가 오가는 흐름

진짜 데이터는 이런 경로를 지난다.

저장할 때(Create):

```text
Frontend    사용자가 화면에서 기록을 입력하고 저장 버튼을 누른다
    |
    v
Server      요청을 받아서 값이 올바른지 확인하고 저장을 요청한다
    |
    v
Database    실제로 Row를 하나 추가한다
```

조회할 때(Read):

```text
Database    조건에 맞는 Row들을 찾아서 돌려준다
    |
    v
Server      받은 데이터를 화면에서 쓸 형태로 정리한다
    |
    v
Frontend    화면에 목록으로 그린다
```

이 흐름이 보이고 나서야, 화면에 값이 보인다는 건 **이 경로 중 어딘가에서 값이 왔다는 뜻일 뿐**이라는 걸 알게 됐다. 그 어딘가가 데이터베이스가 아니라 코드 안일 수도 있는 것이다.

확인하는 방법도 단순했다. **데이터베이스를 직접 들여다보고 Row가 실제로 늘어났는지 보는 것**이다. 화면이 아니라 데이터베이스 쪽에서 확인해야 한다.

## 13. "DB 연결 완료"는 어디까지인가

프로젝트에서 "DB 연결됐어?"라는 질문을 자주 주고받았는데, 이 말이 사람마다 다른 뜻이었다. 나중에 정리해보니 아래 단계들이 **전부 서로 다른 상태**였다.

| 단계 | 상태 | 이게 됐다고 다음이 되는 건 아니다 |
|---|---|---|
| 1 | DATABASE_URL이 존재한다 | 주소만 적혀 있는 상태. 틀린 주소일 수도 있다 |
| 2 | 서버가 DB 접속에 성공한다 | 접속만 된 것. 안에 테이블이 없을 수 있다 |
| 3 | Schema가 존재한다 | 설계도만 있는 것. 실제 DB에는 반영 전일 수 있다 |
| 4 | Migration이 적용됐다 | 이제야 실제 구조가 바뀐다 |
| 5 | 실제 Table이 존재한다 | 구조만 있고 비어 있는 테이블일 수 있다 |
| 6 | Create가 성공한다 | 저장은 되지만 꺼내오지 못할 수 있다 |
| 7 | Read가 성공한다 | 서버까지는 왔지만 화면에 안 그려질 수 있다 |
| 8 | 화면에 실제 데이터가 표시된다 | 여기까지 와야 끝이다 |

이 표를 만들고 나서 얻은 결론은 이것이다.

**"DB 연결 완료"라는 말 하나로는 지금이 몇 번 상태인지 알 수 없다.**

그래서 문제가 생겼을 때 "연결이 안 되는 것 같다"고 뭉뚱그리지 말고, 몇 번 단계까지 확인했는지를 짚는 편이 훨씬 빨랐다. 예를 들어 "접속은 되는데 테이블이 없다"는 2번은 됐고 4번이 안 된 상태다. 원인이 Migration 쪽이라는 게 바로 좁혀진다.

## 14. 전체 흐름 정리

지금까지 나온 개념들을 한 그림으로 합치면 이렇게 된다.

### DB 구조를 바꿀 때

```text
Schema      코드에서 "이런 구조여야 한다"를 정의한다
   |
   v
Migration   바뀐 부분을 변경 지시서로 만들고 실행한다
   |
   v
Database    실제 테이블 구조가 그에 맞게 바뀐다
```

| 단계 | 역할 |
|---|---|
| Schema | 구조의 설계도. 코드 파일로 관리된다 |
| Migration | 설계도의 변경 사항을 실제 DB에 안전하게 옮기는 과정 |
| Database | 최종적으로 구조와 데이터를 가지고 있는 곳 |

### 데이터를 저장할 때

```text
Frontend   사용자 입력을 받는다
   |
   v
Backend    요청을 받아 검증하고 처리한다
   |
   v
ORM        코드를 SQL로 바꿔서 보낸다
   |
   v
Database   실제로 Row를 저장한다
```

### 데이터를 조회할 때

```text
Database   조건에 맞는 Row를 찾아서 돌려준다
   |
   v
ORM        받은 결과를 코드에서 쓸 형태로 바꿔준다
   |
   v
Backend    화면에 필요한 형태로 정리해서 응답한다
   |
   v
Frontend   화면에 그린다
```

| 단계 | 역할 |
|---|---|
| Frontend | 사용자가 보고 조작하는 화면. 직접 DB에 접근하지 않는다 |
| Backend | 요청을 받아 검증하고, 무엇을 저장하고 꺼낼지 결정한다 |
| ORM | 코드와 SQL 사이를 번역한다. 없어도 되지만 있으면 편하다 |
| Database | 데이터가 실제로 남아 있는 곳 |

이렇게 늘어놓고 보니, 데이터베이스가 **단독으로 존재하는 저장소**가 아니라 **이 줄의 맨 끝에 있는 한 칸**이라는 게 보였다.

## 15. 자주 헷갈리는 용어 한 번에 정리

| 용어 | 한 줄 설명 |
|---|---|
| Data | 프로그램이 다루는 값 하나하나. 닉네임, 거리, 시각 같은 것 |
| Database | 데이터가 정해진 구조에 맞춰 모여 있는 저장 공간 |
| DBMS | 그 저장 공간을 만들고 관리하고 응답해주는 소프트웨어 |
| RDB | 데이터를 표 형태로 저장하고 표끼리 연결하는 방식의 데이터베이스 |
| PostgreSQL | 관계형 데이터베이스를 관리하는 DBMS 제품 중 하나 |
| Table | 한 종류의 데이터를 담는 하나의 표. 예를 들면 users |
| Row | 표의 가로 한 줄. 데이터 한 건. 사용자 1명 |
| Column | 표의 세로 한 칸. 데이터가 가지는 항목의 종류와 타입 |
| Primary Key | Row 하나를 확실히 구분해주는 Column. 고유하고 비어 있을 수 없다 |
| Foreign Key | 다른 테이블의 Primary Key를 가리키는 Column. 테이블 사이를 연결한다 |
| Schema | 어떤 테이블에 어떤 Column과 타입과 관계가 있어야 하는지 정의한 구조 |
| Migration | 구조 변경을 기존 데이터를 지키면서 순서대로 적용하는 방법 |
| SQL | 관계형 데이터베이스와 대화할 때 쓰는 언어 |
| Query | 데이터베이스에 보내는 요청. SQL로 작성한다 |
| CRUD | 데이터를 다루는 네 가지 동작. Create, Read, Update, Delete |
| ORM | 코드에서 DB를 다루기 쉽게 도와주는 도구. DB 자체가 아니다 |

## 16. 이번에 이해한 핵심

정리하면서 가장 크게 남은 건 개별 용어의 뜻보다 **"이건 이거고 저건 저거다"라는 구분**이었다.

### Schema를 작성했다, 는 실제 DB에 적용됐다와 다르다

Schema는 설계도다. 파일을 고쳤다고 데이터베이스가 알아서 바뀌지 않는다. Migration을 적용해야 비로소 실제 구조가 바뀐다.

### DB에 Table이 있다, 는 Frontend와 연결됐다와 다르다

테이블이 생긴 것과 그 데이터가 화면까지 오는 것은 완전히 다른 단계다. 그 사이에 Backend와 ORM이 있고, 각 구간에서 따로 막힐 수 있다.

### 화면에 데이터가 보인다, 는 실제 DB 데이터다와 다르다

코드에 적어둔 Mock 데이터도 화면에는 똑같이 잘 나온다. 확인은 화면이 아니라 데이터베이스 쪽에서 해야 한다.

### ORM을 사용한다, 는 DB나 SQL을 몰라도 된다와 다르다

ORM은 SQL을 없애주는 게 아니라 대신 써주는 도구다. 문제가 생기면 결국 SQL과 데이터베이스 구조를 읽어야 한다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> 데이터베이스는 단순한 저장 공간 하나가 아니라, 애플리케이션의 데이터가 저장되고 다시 사용되기까지의 흐름 속에서 이해해야 한다.

처음에는 데이터베이스를 "값을 넣어두는 상자"로만 생각했다. 하지만 실제로는 Schema로 구조를 정하고, Migration으로 그 구조를 반영하고, ORM을 거쳐 Backend가 요청하고, Frontend가 그 결과를 보여주는 **하나의 긴 흐름의 끝**이었다. 이렇게 보니 어디가 막혔는지 짚는 것도 훨씬 쉬워졌다.

## 더 학습하면 좋은 개념

- **트랜잭션(Transaction)** — 여러 개의 변경을 "전부 성공하거나 전부 취소"로 묶는 단위다. 기록을 저장하면서 통계도 같이 갱신해야 하는 경우처럼, 중간에 실패하면 데이터가 어긋나는 상황을 막아준다. CRUD 다음으로 반드시 만나게 되는 개념이다.
- **인덱스(Index)** — 데이터가 많아졌을 때 원하는 Row를 빠르게 찾게 해주는 장치다. 책의 찾아보기와 같은 역할을 한다. "왜 조회가 느린가"라는 질문의 답이 대부분 여기서 시작한다.
- **정규화(Normalization)** — 같은 데이터가 여러 테이블에 중복되지 않게 구조를 나누는 설계 원칙이다. 테이블을 어떻게 쪼갤지 판단하는 기준을 주기 때문에, Schema를 직접 설계하기 전에 한 번은 봐야 한다.
- **N+1 문제** — ORM을 쓸 때 자주 마주치는 성능 문제다. 목록 하나를 가져오려다 Query가 수십 번 나가는 상황인데, ORM이 내부에서 SQL을 만든다는 사실을 모르면 원인을 찾기 어렵다. ORM 다음 단계로 꼭 봐야 할 주제다.
- **제약 조건(Constraints)** — NOT NULL, UNIQUE, CHECK처럼 잘못된 데이터가 애초에 들어오지 못하게 막는 장치들이다. 검증을 코드에서만 할지 데이터베이스에서도 할지 판단할 수 있게 된다.
