## 들어가며

탄천런 프로젝트를 하면서 화면을 만드는 것과 기능이 실제로 동작하는 것이 전혀 다른 일이라는 걸 알게 됐다. 버튼도 있고 목록도 잘 나오는데 정작 저장이 안 되거나, 로그인 화면은 있는데 로그인이 되지 않는 상황을 여러 번 만났다.

그때마다 "Frontend 뒤에서는 대체 무슨 일이 일어나는 거지?"가 궁금했다. 그래서 Backend가 정확히 어떤 역할을 맡는지 처음부터 다시 공부해서 정리해두려고 한다.

이 글은 프로젝트 회고가 아니라 개념 정리 노트다. 요청이 들어와서 응답이 나갈 때까지를 한 줄로 따라가보는 것이 목표다.

## 1. Frontend와 Backend

### 각각 무엇인가

**Frontend(프론트엔드)** 는 **사용자가 직접 보고 만지는 부분**이다. 화면, 버튼, 입력창처럼 눈에 보이는 것이 전부 여기에 속한다. 사용자의 브라우저나 앱 안에서 실행된다.

**Backend(백엔드)** 는 **화면 뒤에서 요청을 받아 처리하는 부분**이다. 사용자에게 보이지 않고, 서비스를 제공하는 쪽의 컴퓨터(서버)에서 실행된다.

### 둘은 어떻게 연결되는가

Frontend는 데이터를 직접 가지고 있지 않다. 필요할 때마다 Backend에 물어본다.

```text
사용자
↓
Frontend       화면에서 입력을 받는다
↓
Backend        요청을 받아 규칙을 적용하고 처리한다
↓
Database       데이터를 실제로 저장한다
```

조회할 때는 이 순서가 그대로 뒤집힌다.

```text
Database       조건에 맞는 데이터를 찾아준다
↓
Backend        화면에 필요한 형태로 정리한다
↓
Frontend       화면에 그린다
↓
사용자
```

여기서 중요한 점이 하나 있다. **Frontend는 Database에 직접 접근하지 않는다.** 항상 Backend를 거친다. 브라우저에서 돌아가는 코드는 사용자가 마음대로 열어볼 수 있기 때문에, 데이터베이스 접속 정보를 거기에 둘 수 없다. 이 이유는 뒤에서 환경변수 이야기를 할 때 다시 나온다.

## 2. Client와 Server

Frontend와 Backend가 "어떤 코드인가"에 대한 구분이라면, Client와 Server는 **"요청을 보내는 쪽인가, 받는 쪽인가"** 에 대한 구분이다.

| 구분 | 역할 |
|---|---|
| Client (클라이언트) | 요청을 보내고 결과를 받는 쪽 |
| Server (서버) | 요청을 받아 처리하고 결과를 돌려주는 쪽 |

브라우저는 대표적인 Client다. 주소창에 주소를 입력하면 브라우저가 그 서버에 요청을 보내고, 받은 결과를 화면에 그린다. 모바일 앱도 Client가 될 수 있다.

처음에 헷갈렸던 건 **Client와 Server가 고정된 신분이 아니라 역할 이름**이라는 점이다. 우리 Backend가 외부 서비스에 무언가를 요청할 때, 그 순간 우리 Backend는 Client가 된다. 누가 요청을 보내느냐에 따라 이름이 바뀐다.

## 3. Request와 Response

Client와 Server가 주고받는 것이 **Request(요청)** 와 **Response(응답)** 다.

| 용어 | 의미 |
|---|---|
| Request | Client가 Server에게 보내는 부탁. "이 데이터를 줘", "이걸 저장해줘" |
| Response | Server가 그 부탁에 대해 돌려주는 답. 요청한 데이터이거나, 실패했다는 알림 |

기록 조회를 예로 들면 이렇게 오간다.

```text
Frontend
↓
기록 조회 Request        "이 사용자의 러닝 기록을 줘"
↓
Backend                  누구인지 확인하고, 무엇을 꺼낼지 정한다
↓
Database                 조건에 맞는 데이터를 찾는다
↓
Backend                  받은 결과를 응답 형태로 정리한다
↓
Response                 "여기 기록 3개 있어"
↓
Frontend                 화면에 목록으로 그린다
```

여기서 기억할 점은 **Request 하나에 Response 하나가 짝을 이룬다**는 것이다. 요청을 보냈으면 성공이든 실패든 답이 돌아온다. 화면에서 "로딩 중"이 계속 돌고 있다면, 그건 아직 Response가 오지 않았다는 뜻이다.

## 4. HTTP

Request와 Response를 아무 형식으로나 주고받을 수는 없다. 서로 알아들을 수 있는 약속이 필요하다. 그 약속이 **HTTP(HyperText Transfer Protocol)** 다.

HTTP는 **웹에서 Client와 Server가 대화할 때 쓰는 규칙**이다. 이 규칙 덕분에 우리가 만든 Frontend와 남이 만든 서버도 서로 통신할 수 있다.

HTTP 요청은 대략 이런 부분들로 이루어진다.

| 구성 요소 | 무엇인가 |
|---|---|
| URL | 어디로 보낼 것인가. 요청의 목적지 주소 |
| Method | 무엇을 하려는 것인가. 조회인지 저장인지 삭제인지 |
| Header | 요청에 딸린 부가 정보. 형식, 인증 정보 같은 것 |
| Body | 실제로 보내는 데이터. 저장할 내용이 여기 들어간다 |
| Status Code | 응답에 붙는 숫자. 성공했는지 실패했는지를 알려준다 |

지금은 각각이 "이런 역할을 하는 칸이 있구나" 정도로만 알아두면 된다. Header와 Status Code는 뒤에서 조금 더 다룬다.

## 5. HTTP Method

Method는 **"이 요청으로 무엇을 하려는가"** 를 나타낸다. 같은 주소라도 Method가 다르면 다른 동작이 된다.

| Method | 하려는 일 | 예시 |
|---|---|---|
| GET | 가져오기 | 러닝 기록 목록 조회 |
| POST | 새로 만들기 | 러닝 기록 저장 |
| PATCH | 일부 수정하기 | 기록의 거리 값만 수정 |
| DELETE | 지우기 | 러닝 기록 삭제 |

앞서 정리한 CRUD와 비슷해 보이고, 실제로 자주 짝지어 쓰인다. 다만 **정해진 1:1 규칙은 아니다.** 예를 들어 검색처럼 조회에 가까운 동작이지만 보낼 데이터가 많아서 POST를 쓰는 경우도 있고, 수정에 PUT을 쓰는 경우도 있다.

그래서 "GET은 무조건 Read"라고 외우기보다, **Method는 의도를 나타내는 표시**이고 실제 동작은 서버가 어떻게 만들었느냐에 달려 있다고 이해하는 편이 정확했다.

## 6. URL / Route / Endpoint

요청을 보내려면 주소가 필요하다.

```text
GET  /api/runs      기록 목록을 가져온다
POST /api/runs      기록을 새로 저장한다
```

같은 `/api/runs` 주소인데 Method가 달라서 서로 다른 동작이 된다.

| 용어 | 쉬운 설명 |
|---|---|
| URL | 요청을 보낼 주소 전체 |
| Route | 서버 안에서 "이 주소로 오면 이 코드를 실행한다"고 연결해둔 경로 |
| Endpoint | 서버가 특정 요청을 받을 수 있도록 만들어둔 주소 하나 |

**Endpoint(엔드포인트)** 는 **서버가 요청을 받기 위해 열어둔 창구 하나**라고 생각하면 이해가 쉬웠다. 창구가 없는 주소로 요청을 보내면 서버는 "그런 곳 없다"고 답한다.

그리고 여기서 중요한 구분이 하나 생긴다. **Endpoint가 있다는 것과 그 기능이 제대로 동작한다는 것은 다른 이야기다.** 창구는 열려 있는데 안에서 처리가 실패할 수 있다. 이 구분은 뒤에서 다시 나온다.

## 7. API

**API(Application Programming Interface)** 는 **프로그램끼리 정해진 방식으로 주고받기 위해 만들어둔 창구**다.

처음에 나는 API를 "외부 서비스에서 받아오는 Key"라고 잘못 이해하고 있었다. 하지만 그건 API가 아니라 API Key다.

| 용어 | 무엇인가 |
|---|---|
| API | 프로그램끼리 통신하기 위해 정해둔 창구와 규칙 |
| API Key | 그 창구를 쓸 자격이 있는지 확인하기 위한 인증용 값 |

더 중요한 오해가 하나 있었다. **API는 외부 서비스에만 있는 게 아니다.** 우리가 만든 Frontend와 우리가 만든 Backend 사이에도 API가 있다.

```text
우리 Frontend  ──API──▶  우리 Backend      우리가 직접 만든 API
우리 Backend   ──API──▶  외부 서비스        남이 만들어 제공하는 API
```

앞에서 본 `GET /api/runs`가 바로 우리가 만든 API다. 이 경우 API Key는 필요 없을 수도 있다. 자격 확인이 필요한 창구에만 Key나 다른 인증 수단이 붙는다.

## 8. JSON

Request와 Response에 데이터를 실어 보낼 때, 그 데이터를 어떤 형식으로 쓸지도 정해야 한다. 가장 널리 쓰이는 형식이 **JSON(JavaScript Object Notation)** 이다.

```text
{
  "id": 1,
  "nickname": "runner",
  "distance_km": 5.2
}
```

이름과 값을 짝지어 적는 단순한 형식이다. 사람이 읽기도 쉽고 프로그램이 다루기도 쉬워서, Frontend와 Backend가 데이터를 주고받을 때 기본처럼 쓰인다.

Backend는 Database에서 꺼낸 데이터를 이런 JSON 형태로 바꿔서 응답하고, Frontend는 그걸 받아 화면에 그린다.

## 9. Backend가 실제로 하는 일

이제 요청 하나가 Backend 안에 들어왔을 때 무슨 일이 일어나는지 보자. "요청을 받아서 데이터를 돌려준다"는 한 줄 안에 생각보다 많은 단계가 들어 있었다.

```text
Request 도착
↓
1. 요청 확인          어느 Endpoint로, 어떤 Method로 왔는가
↓
2. Validation         보낸 값이 올바른가
↓
3. Authentication     이 요청을 보낸 사람이 누구인가
↓
4. Authorization      그 사람이 이 작업을 해도 되는가
↓
5. Business Logic     서비스 규칙에 따라 무엇을 할지 결정
↓
6. Database 조회/저장  실제 데이터를 다룬다
↓
7. 외부 API 호출       필요하면 다른 서비스와도 통신
↓
8. 오류 처리          위 단계에서 실패하면 어떻게 응답할지 결정
↓
9. Response 생성      결과를 형식에 맞춰 돌려준다
```

이 흐름이 보이고 나서 얻은 게 있다. **"저장이 안 된다"는 현상 하나에도 멈출 수 있는 지점이 아홉 군데나 있다는 것**이다. Validation에서 막힌 건지, 로그인 확인에서 막힌 건지, Database에서 막힌 건지에 따라 고쳐야 할 곳이 완전히 다르다.

아래에서 이 중 몇 가지를 조금 더 자세히 본다.

## 10. Validation

**Validation(검증)** 은 **들어온 값이 올바른지 확인하는 과정**이다.

예를 들면 이런 것들을 확인한다.

- nickname이 비어 있지는 않은가
- distance가 음수는 아닌가
- 필수 값이 빠지지는 않았는가
- 숫자가 들어와야 할 자리에 글자가 오지는 않았는가

### Frontend 검증만 믿으면 안 된다

입력창에서 "닉네임을 입력해주세요"라고 막아주는 것도 Validation이다. 그러면 Backend에서 또 할 필요가 있을까?

**있다.** Frontend의 검증은 사용자를 돕기 위한 것이지, 잘못된 데이터를 막는 최후의 방어선이 아니기 때문이다. 브라우저에서 실행되는 코드는 사용자가 건너뛸 수 있고, 화면을 거치지 않고 Backend에 직접 요청을 보낼 수도 있다.

| 위치 | 주된 목적 |
|---|---|
| Frontend Validation | 사용자가 실수를 빨리 알아차리도록 돕는 것 |
| Backend Validation | 잘못된 데이터가 실제로 저장되는 것을 막는 것 |

**중요한 검증은 Backend에서도 반드시 한다.** 둘은 중복이 아니라 역할이 다르다.

## 11. Business Logic

**Business Logic(비즈니스 로직)** 은 **그 서비스가 정한 실제 규칙**이다.

"러닝 기록을 저장한다"는 요청이 왔을 때, 단순히 Database에 한 줄 넣는 것으로 끝나지 않을 수 있다. 서비스가 이런 규칙을 정해뒀다면 그것도 함께 처리해야 한다.

- 하루에 저장할 수 있는 기록 수에 제한이 있다
- 기록을 저장하면 그 사용자의 누적 거리도 함께 갱신한다
- 일정 거리를 넘으면 배지를 부여한다

이런 규칙들이 Business Logic이다.

### Database 저장과는 다른 개념이다

여기서 구분이 필요했다.

| 구분 | 하는 일 |
|---|---|
| Database 저장 | 정해진 데이터를 실제로 기록하는 것 |
| Business Logic | 무엇을 어떤 조건으로 저장할지 결정하는 규칙 |

Database는 "저장해달라"는 요청을 그대로 수행할 뿐, 그게 서비스 규칙에 맞는지는 판단하지 않는다. **그 판단은 Backend가 한다.** Backend가 단순한 통로가 아니라 처리를 담당하는 영역인 이유가 여기에 있다.

## 12. Backend와 Database

둘을 헷갈리기 쉬워서 정리해둔다.

| 구분 | 무엇인가 |
|---|---|
| Backend | 요청을 처리하고 서비스 규칙을 적용하는 코드 |
| Database | 데이터를 저장하고 조회하는 시스템 |

Backend는 데이터를 **보관하지 않는다.** 필요할 때 Database에 요청해서 가져오고, 저장할 것이 있으면 Database에 넘긴다.

```text
Frontend
↓
Backend          요청을 받아 판단하고 처리한다
↓
ORM / Query      Database에 보낼 요청으로 바꾼다
↓
Database         실제로 저장하고 찾아준다
```

Schema, Migration, Primary Key, Foreign Key, CRUD, ORM 같은 개념은 앞선 Database 글에서 따로 정리했으니 여기서는 반복하지 않는다. 지금 필요한 건 **Backend와 Database가 서로 다른 층이고, Backend가 Database 앞에 서 있다**는 위치 관계까지다.

## 13. Authentication과 Authorization

이름이 비슷해서 가장 많이 헷갈렸던 한 쌍이다. 하지만 묻는 질문이 완전히 다르다.

| 구분 | 묻는 질문 | 우리말 |
|---|---|---|
| Authentication | 당신은 누구인가? | 인증 |
| Authorization | 그 일을 해도 되는가? | 인가, 권한 확인 |

예를 들어 보면 차이가 분명해진다.

- 로그인해서 "이 사람은 eunjung이다"를 확인하는 것 → **Authentication**
- eunjung이 남의 러닝 기록을 지우려 할 때 "그건 안 된다"고 막는 것 → **Authorization**

순서도 정해져 있다. **누구인지 먼저 확인해야 무엇을 해도 되는지 판단할 수 있다.** Authentication이 먼저이고 Authorization이 그 다음이다.

로그인은 했는데(Authentication 통과) 관리자 페이지에는 못 들어가는(Authorization 실패) 상황이 둘이 다르다는 걸 보여주는 대표적인 예다.

## 14. Session

HTTP에는 한 가지 특징이 있다. **요청 하나하나를 서로 독립적으로 처리한다.** 방금 로그인한 사람이 다음 요청을 보내도, 서버는 그 사실을 기본적으로 기억하지 않는다.

그래서 **로그인한 사용자를 계속 같은 사람으로 알아보게 하는 장치**가 필요하다. 그 개념이 **Session(세션)** 이다.

로그인에 성공하면 서버는 "이 사용자는 로그인한 상태"라는 정보를 만들어두고, 이후 요청마다 그 정보를 확인해서 같은 사용자임을 알아본다.

여기서 주의할 점이 있다. Session을 **"데이터베이스의 테이블"이라고 단정할 수는 없다.** 저장하는 방법은 여러 가지다. 서버 메모리에 둘 수도 있고, 별도의 저장소를 쓸 수도 있고, 데이터베이스에 둘 수도 있다.

지금 단계에서는 **Session은 로그인 상태를 이어가기 위한 개념이고, 구현 방법은 여러 가지가 있다**까지만 알아두면 충분했다.

## 15. Cookie

Session과 함께 나오지만 같은 것은 아니다.

**Cookie(쿠키)** 는 **브라우저에 저장될 수 있는 작은 데이터**다.

서버가 응답할 때 "이 값을 저장해두라"고 내려보내면, 브라우저가 그걸 보관했다가 이후 요청마다 같이 보낸다.

| 구분 | 무엇인가 |
|---|---|
| Session | 로그인 상태를 이어가기 위한 개념 |
| Cookie | 브라우저에 값을 저장하고 요청마다 실어 보내는 수단 |

즉 **Cookie는 그릇이고 Session은 그 그릇에 담길 수 있는 내용 중 하나**에 가깝다. Session을 식별하는 값을 Cookie에 담아 주고받는 방식이 흔히 쓰인다.

다만 Cookie에는 다른 것도 담길 수 있고, Session을 Cookie 없이 다루는 방법도 있다. 그래서 둘을 같은 말로 쓰면 안 된다.

## 16. Token

로그인 상태를 이어가는 또 다른 방식으로 **Token(토큰)** 이 있다.

Token은 **"이 사람은 이미 인증된 사용자"라는 사실을 담은 값**이다. 로그인에 성공하면 서버가 Token을 발급하고, Client는 이후 요청마다 그 Token을 함께 보낸다. 서버는 Token을 확인해서 누구인지 판단한다.

자주 언급되는 형식으로 **JWT(JSON Web Token)** 가 있다. 여기서는 그런 형식이 있다는 정도로만 알아둔다.

Session 방식과 Token 방식 중 **무엇이 더 낫다고 말할 수는 없다.** 서비스 구조와 요구사항에 따라 다르고, 둘을 함께 쓰기도 한다. 지금은 **로그인 상태를 이어가는 방법이 하나가 아니다**라는 것까지만 정리해둔다.

## 17. OAuth

"구글로 로그인", "카카오로 로그인" 같은 소셜 로그인의 바탕이 되는 개념이 **OAuth**다.

처음에 가장 크게 오해했던 부분이 이것이다.

**우리 서비스는 사용자의 구글 비밀번호를 받지 않는다.**

비밀번호는 사용자와 구글 사이에서만 오간다. 우리 서비스는 구글로부터 "이 사용자가 맞다는 걸 우리가 확인했다"는 결과만 전달받는다. 그래서 우리 쪽에 비밀번호를 저장할 일이 없고, 사용자도 우리를 믿고 비밀번호를 넘길 필요가 없다.

흐름은 이렇다.

```text
사용자
↓
소셜 로그인 선택          "구글로 로그인" 버튼을 누른다
↓
OAuth Provider           구글 같은 인증 제공자의 화면으로 이동
↓
사용자 인증              사용자가 구글에 직접 로그인하고 동의한다
↓
우리 서비스 Callback     인증 결과를 들고 우리 쪽으로 돌아온다
↓
Backend 처리             결과를 확인하고 우리 서비스의 사용자와 연결한다
↓
로그인 상태 생성          Session이나 Token으로 로그인 상태를 만든다
```

마지막 두 단계가 중요하다. **구글 로그인이 성공했다는 것과, 우리 서비스에 로그인된 것은 다른 단계다.** 구글에서 돌아온 결과를 받아 우리 서비스의 사용자로 연결하는 처리를 Backend가 해야 비로소 로그인이 끝난다.

## 18. Redirect URI와 Callback

OAuth를 볼 때 같이 나오는 두 단어다. 비슷하게 쓰이지만 가리키는 것이 조금 다르다.

| 용어 | 무엇인가 |
|---|---|
| Redirect URI | 인증이 끝난 뒤 사용자를 돌려보내도 되는 주소. 미리 등록해둔다 |
| Callback | 돌아온 결과를 우리 앱이 실제로 처리하는 경로나 단계를 부르는 표현 |

Redirect URI를 미리 등록해두는 이유는 **아무 주소로나 인증 결과를 보내지 못하게 막기 위해서**다. 등록되지 않은 주소로 돌아가려고 하면 인증 제공자가 거부한다. 소셜 로그인을 붙일 때 주소가 조금만 달라도 오류가 나는 이유가 여기에 있다.

실무에서는 같은 주소를 두고 두 단어를 섞어 쓰는 경우가 많아서, **완전히 같은 말이라고 단정하기보다 "등록해둔 돌아올 주소"와 "돌아와서 처리하는 부분"을 가리키는 표현**으로 이해해두는 편이 안전했다.

## 19. 외부 API와 Backend

Backend가 연결하는 대상은 Database만이 아니다. 다른 회사가 제공하는 서비스와도 통신한다.

- 소셜 로그인
- 지도 관련 기능
- 이메일 발송
- 결제

이럴 때 **우리 Backend가 Client가 되어 외부 Server에 요청을 보낸다.** 앞에서 Client와 Server가 고정된 신분이 아니라고 했던 이야기가 여기서 실제로 나타난다.

```text
Frontend
↓
Backend          우리 서버가 요청을 받는다
↓
External API     그 처리를 위해 외부 서비스에 다시 요청한다
↓
Backend          받은 결과를 정리한다
↓
Frontend
```

그러면 Frontend가 외부 API를 직접 부르면 안 될까? 그래도 되는 경우도 있지만, **인증 정보가 필요한 호출은 Backend를 거치는 편이 안전하다.** 브라우저에서 직접 부르면 그 인증 정보가 사용자에게 노출되기 때문이다. 바로 다음에 나오는 내용이다.

## 20. 환경변수와 Secret

### 왜 코드에 직접 쓰지 않는가

Database 접속 정보나 외부 서비스 인증 정보 같은 값들이 있다.

```text
DATABASE_URL     데이터베이스 접속 주소
CLIENT_SECRET    OAuth에서 우리 서비스임을 증명하는 값
API_SECRET       외부 API를 쓸 때 필요한 비밀 값
```

이런 값을 코드에 그대로 적으면 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 노출 위험 | 코드를 저장소에 올리는 순간 그 값도 함께 공개된다 |
| 환경마다 다름 | 로컬과 실제 서비스가 서로 다른 값을 써야 한다 |
| 변경의 번거로움 | 값 하나 바꾸려고 코드를 고치고 다시 배포해야 한다 |

그래서 이런 값들은 코드 바깥에 두고 실행할 때 읽어오게 한다. 이것이 **환경변수(Environment Variable)** 다. 코드는 그대로인데 환경에 따라 값만 달라지는 구조가 된다.

### 노출돼도 되는 값과 안 되는 값

모든 환경변수가 비밀은 아니다.

| 구분 | 예 | 어디까지 가도 되는가 |
|---|---|---|
| 공개돼도 되는 값 | 서비스 이름, 공개용 주소 | 브라우저까지 내려가도 괜찮다 |
| Secret | CLIENT_SECRET, DATABASE_URL | 서버 안에만 있어야 한다 |

**Secret(비밀 값)** 은 이름 그대로 절대 브라우저로 내려가면 안 되는 값이다. 브라우저에 전달된 값은 사용자가 전부 열어볼 수 있기 때문이다.

이 구분을 놓치면, 설정은 다 했는데 비밀 값이 화면 쪽 코드에 섞여 들어가는 일이 생긴다. 배포 환경에서 이 값들을 어떻게 관리하는지는 별도의 주제라 여기서는 다루지 않는다.

## 21. Server-only

앞의 이야기에서 자연스럽게 이어지는 개념이다. **어떤 코드는 서버에서만 실행되어야 한다.**

| 구분 | 실행 위치 | 특징 |
|---|---|---|
| 서버에서 실행되는 코드 | 서비스 제공자의 서버 | 사용자가 내용을 볼 수 없다. Secret을 다룰 수 있다 |
| 브라우저에서 실행되는 코드 | 사용자의 브라우저 | 사용자가 전부 열어볼 수 있다 |

Database에 접속하거나 Secret을 사용하는 코드는 **반드시 서버 쪽에 있어야 한다.** 이런 코드가 실수로 브라우저에서 실행되는 쪽에 섞여 들어가면 비밀 값이 그대로 노출된다.

요즘 프레임워크들은 이 경계를 나눠주는 장치를 제공한다. 다만 도구가 무엇이든 **"이 코드는 어디에서 실행되는가"를 항상 의식해야 한다**는 원칙 자체는 같다.

## 22. Status Code

응답에는 항상 숫자가 하나 붙는다. **Status Code(상태 코드)** 다. 요청이 어떻게 처리됐는지를 숫자로 알려준다.

| Code | 의미 | 언제 |
|---|---|---|
| 200 | OK | 요청이 정상 처리됨 |
| 201 | Created | 새로 만들어짐. 주로 저장 성공 |
| 400 | Bad Request | 보낸 요청에 문제가 있음 |
| 401 | Unauthorized | 누구인지 확인되지 않음 |
| 403 | Forbidden | 누구인지는 알지만 권한이 없음 |
| 404 | Not Found | 요청한 대상이 없음 |
| 500 | Internal Server Error | 서버 쪽에서 문제가 생김 |

### 401과 403의 차이

앞에서 정리한 Authentication과 Authorization이 그대로 여기에 대응된다.

| Code | 질문 | 상황 |
|---|---|---|
| 401 | 누구인가? | 로그인이 안 된 상태. 로그인하면 해결될 수 있다 |
| 403 | 해도 되는가? | 로그인은 됐지만 권한이 없다. 다시 로그인해도 소용없다 |

**401은 "당신이 누구인지 모르겠다", 403은 "누군지는 알겠는데 그건 안 된다"** 로 기억하니 헷갈리지 않았다.

## 23. 오류를 볼 때 400과 500의 차이

Status Code의 앞자리만 봐도 문제의 범위를 어느 정도 좁힐 수 있다.

| 범위 | 대체로 가리키는 것 | 먼저 확인해볼 곳 |
|---|---|---|
| 400번대 | 요청 쪽에 문제가 있다고 서버가 판단함 | 보낸 값, 주소, 인증 정보 |
| 500번대 | 서버가 처리 도중 실패함 | 서버 코드, Database 연결, 외부 API |

다만 여기서 단정하면 안 되는 것이 있다.

**400번대가 나왔다고 무조건 Frontend 잘못은 아니다.** 서버의 Validation 규칙이 잘못 짜여 있어서 올바른 요청을 거절하는 경우도 있고, 주소를 잘못 만들어둔 경우도 있다. 반대로 500이 나왔는데 원인이 잘못된 입력값 처리인 경우도 있다.

그래서 이렇게 이해하는 게 정확했다. **Status Code는 원인을 알려주는 게 아니라 어디부터 찾아볼지 알려주는 힌트다.** 정확한 원인은 다음에 나오는 로그에서 확인한다.

## 24. 로그

화면에 뜨는 오류 메시지는 대부분 짧다. "요청에 실패했습니다" 한 줄로는 무엇이 잘못됐는지 알 수 없다.

**Log(로그)** 는 **서버가 처리 과정에서 남기는 기록**이다. 화면에는 보이지 않지만, 서버 쪽에서는 훨씬 자세한 내용을 볼 수 있다.

```text
화면에서 보이는 것        "요청에 실패했습니다"

Server Log에서 보이는 것  어느 Endpoint로 들어온 요청인지
                          Validation에서 걸린 건지
                          Database 연결이 끊긴 건지
                          외부 API가 응답하지 않은 건지
```

같은 실패라도 로그를 보면 Validation 오류인지 Database 오류인지 구분할 수 있다. 앞에서 정리한 Backend의 아홉 단계 중 **어디에서 멈췄는지 알려주는 것이 로그**다.

한 가지 주의할 점이 있다. **로그에 Secret이나 개인정보를 남기면 안 된다.** 디버깅하려고 요청 내용을 통째로 찍다 보면 비밀번호나 인증 값이 그대로 기록될 수 있다. 로그도 결국 누군가 열어볼 수 있는 기록이다.

## 25. Build 성공과 실제 동작은 다르다

이게 프로젝트에서 가장 많이 착각했던 부분이다.

**Build(빌드)** 는 **코드를 실행할 수 있는 형태로 만드는 과정**이고, **Runtime(런타임)** 은 **그 코드가 실제로 실행되는 시점**이다. 둘은 다른 단계이고, 앞이 성공했다고 뒤가 보장되지 않는다.

| 이것이 됐다고 | 이것이 되는 것은 아니다 |
|---|---|
| Build 성공 | Runtime 정상 |
| API Route 존재 | 실제 Request 정상 처리 |
| Backend 코드 존재 | Database 연결 정상 |
| OAuth 코드 존재 | 실제 로그인 성공 |

Build는 주로 **문법이 맞는지, 필요한 것들이 제자리에 있는지**를 확인한다. 반면 Database 접속 주소가 틀렸는지, 외부 서비스가 응답하는지, 등록해둔 Redirect URI가 맞는지는 **실제로 실행해봐야 알 수 있다.**

그래서 "빌드가 통과했으니 됐다"는 판단은 위험했다. 확인하려면 실제로 요청을 한 번 보내봐야 한다.

## 26. "백엔드 구현 완료"는 어디까지인가

Database 글에서 "DB 연결 완료"가 여러 상태를 뭉뚱그린 말이었던 것처럼, "백엔드 구현 완료"도 마찬가지였다.

| 단계 | 상태 | 여기까지 됐다고 다음이 되는 건 아니다 |
|---|---|---|
| 1 | Endpoint 존재 | 주소만 만들어둔 상태 |
| 2 | Request 수신 | 요청이 들어오는 것까지 확인됨 |
| 3 | Validation | 값 검증이 동작함 |
| 4 | Authentication / Authorization | 사용자 확인과 권한 확인이 동작함 |
| 5 | Business Logic | 서비스 규칙대로 처리됨 |
| 6 | Database / External API 연결 | 실제 데이터와 외부 서비스가 연결됨 |
| 7 | 정상 Response | 성공 응답이 제대로 나감 |
| 8 | Error 처리 | 실패 상황에서도 적절히 응답함 |
| 9 | Frontend 실제 연동 | 화면에서 호출해서 동작함 |
| 10 | 실제 환경 테스트 | 배포된 환경에서도 동작함 |

**"백엔드 구현 완료"라는 한 문장으로는 지금이 몇 번인지 알 수 없다.**

특히 8번 Error 처리와 10번 실제 환경 테스트는 빠뜨리기 쉬웠다. 잘 되는 경우만 확인하고 끝내면, 실패했을 때 화면이 멈추거나 로컬에서만 되는 상태로 남는다.

Database 글의 8단계와 함께 보면, **"연결됐다", "구현됐다" 같은 말은 항상 몇 번 단계인지 같이 말해야 정확하다**는 결론이 된다.

## 27. 전체 흐름 정리

지금까지 나온 개념들을 세 가지 흐름으로 합쳐본다.

### 일반 데이터 요청

```text
사용자
↓
Frontend
↓
HTTP Request
↓
Backend
↓
Validation / Authentication / Business Logic
↓
Database
↓
Backend
↓
HTTP Response
↓
Frontend
```

### 소셜 로그인

```text
사용자
↓
Frontend
↓
OAuth Provider
↓
Callback
↓
Backend
↓
Session / 사용자 확인
↓
Database
↓
Frontend
```

### 외부 API 사용

```text
Frontend
↓
Backend
↓
External API
↓
Backend
↓
Frontend
```

세 흐름을 나란히 놓고 보니 공통점이 보였다. **어떤 경우든 Frontend는 바깥과 직접 연결되지 않고, 항상 Backend가 가운데에서 받아 처리하고 돌려준다.** Backend가 서비스의 중심에 있다는 말의 의미가 이 그림이었다.

## 28. 자주 헷갈리는 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Frontend | 사용자가 직접 보고 조작하는 부분 |
| Backend | 화면 뒤에서 요청을 받아 처리하는 부분 |
| Client | 요청을 보내고 결과를 받는 쪽 |
| Server | 요청을 받아 처리하고 결과를 돌려주는 쪽 |
| Request | Client가 Server에 보내는 요청 |
| Response | Server가 돌려주는 응답 |
| HTTP | 웹에서 요청과 응답을 주고받는 규칙 |
| URL | 요청을 보낼 주소 |
| Endpoint | 서버가 특정 요청을 받으려고 열어둔 주소 |
| API | 프로그램끼리 통신하기 위한 창구와 규칙 |
| JSON | 데이터를 주고받을 때 자주 쓰는 형식 |
| Validation | 들어온 값이 올바른지 확인하는 과정 |
| Business Logic | 그 서비스가 정한 실제 규칙 |
| Authentication | 누구인지 확인하는 것 |
| Authorization | 그 작업을 해도 되는지 확인하는 것 |
| Session | 로그인 상태를 계속 이어가기 위한 개념 |
| Cookie | 브라우저에 저장되어 요청마다 함께 보내지는 작은 데이터 |
| Token | 인증된 사용자임을 나타내는 값 |
| OAuth | 비밀번호를 넘기지 않고 외부 서비스로 인증하는 방식 |
| Redirect URI | 인증 후 돌아오도록 미리 등록해둔 주소 |
| Callback | 돌아온 결과를 앱이 처리하는 경로나 단계 |
| Environment Variable | 코드 바깥에 두고 실행할 때 읽어오는 설정 값 |
| Secret | 서버 안에만 있어야 하는 비밀 값 |
| Status Code | 응답 결과를 알려주는 숫자 |
| Runtime | 코드가 실제로 실행되는 시점 |

## 29. 자주 헷갈리는 차이

| 구분 | 차이 |
|---|---|
| Frontend vs Backend | 사용자에게 보이는 쪽 / 요청을 처리하는 쪽 |
| Client vs Server | 요청을 보내는 역할 / 받아서 처리하는 역할. 고정된 신분이 아니다 |
| Backend vs Database | 규칙을 적용하는 코드 / 데이터를 저장하는 시스템 |
| API vs API Key | 통신하기 위한 창구 / 그 창구를 쓸 자격을 증명하는 값 |
| Authentication vs Authorization | 누구인가 / 해도 되는가 |
| Session vs Cookie | 로그인 상태를 이어가는 개념 / 값을 담아 나르는 수단 |
| Build vs Runtime | 실행 가능한 형태로 만드는 단계 / 실제로 실행되는 시점 |
| Redirect URI vs Callback | 미리 등록해둔 돌아올 주소 / 돌아와서 처리하는 부분 |

## 30. 이번에 이해한 핵심

Database 글 때와 마찬가지로, 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### 화면이 만들어졌다, 는 Backend가 구현됐다와 다르다

버튼과 목록이 보이는 것과 그 버튼이 실제로 무언가를 저장하는 것은 완전히 다른 작업이다.

### Endpoint가 있다, 는 실제 기능이 정상이다와 다르다

창구가 열려 있어도 안에서 처리가 실패할 수 있다. 주소가 응답한다는 것과 기능이 동작한다는 것은 다르다.

### Backend가 있다, 는 Database가 자동으로 연결된다와 다르다

Backend 코드가 있어도 접속 정보가 틀렸거나 테이블이 없으면 연결되지 않는다.

### 로그인 화면이 있다, 는 인증이 구현됐다와 다르다

입력창을 만드는 것과 Authentication을 처리하는 것은 별개다.

### OAuth 로그인이 성공했다, 는 우리 서비스 사용자 연결까지 끝났다와 다르다

구글에서 인증에 성공해도, 그 결과를 받아 우리 서비스의 사용자와 연결하고 로그인 상태를 만드는 처리가 남아 있다.

### Build 성공, 은 Runtime 정상과 다르다

빌드는 문법과 구성을 확인할 뿐이다. 실제로 동작하는지는 요청을 보내봐야 안다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> Backend는 단순히 화면 뒤에 숨어 있는 코드가 아니라, Client의 요청을 받고 서비스 규칙을 적용하고, Database나 외부 서비스와 연결한 뒤 결과를 다시 Client에게 돌려주는 중심 영역이다.

처음에는 Backend를 "데이터를 꺼내다 주는 통로" 정도로 생각했다. 하지만 실제로는 검증하고, 사용자를 확인하고, 권한을 따지고, 서비스 규칙을 적용하고, 외부와 통신하고, 실패했을 때 어떻게 응답할지까지 결정하는 곳이었다. 화면은 그 결과를 보여줄 뿐이었다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **REST API** — Endpoint와 Method를 일관된 규칙으로 설계하는 방식
- **CORS** — 다른 주소의 Frontend가 우리 Backend를 호출할 때 생기는 제약
- **Middleware** — 요청이 본 처리에 도달하기 전에 공통으로 거치는 단계
- **HTTP Header** — 인증 정보나 데이터 형식을 실어 보내는 칸
- **JWT** — Token을 담는 대표적인 형식
- **인증과 보안** — 비밀번호 저장, 권한 설계처럼 실수하면 위험한 영역
- **Logging** — 무엇을 남기고 무엇을 남기지 않을지에 대한 기준
- **Controller / Service / Repository** — Backend 코드를 역할별로 나누는 구조
