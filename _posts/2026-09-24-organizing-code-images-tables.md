글을 어떻게 분류할지 정하고, 긴 글에서 원하는 부분을 찾기 위해 TOC까지 고민하고 나니 다음에는 자연스럽게 **본문 안에 들어가는 요소들**이 눈에 들어오기 시작했다.

개발 블로그의 글은 일반적인 글과 조금 달랐다.

설명만 있는 것이 아니라 코드가 들어가고,

터미널 명령어나 오류 메시지가 들어가고,

화면을 보여주기 위한 이미지가 들어가기도 한다.

여러 방법을 비교할 때는 표가 더 이해하기 쉬운 경우도 있었다.

그런데 이런 요소들을 그냥 본문 중간에 넣기만 하면 오히려 글이 읽기 어려워질 수 있었다.

코드가 너무 길면 본문보다 코드가 더 눈에 띄었고,

이미지가 너무 크면 글의 흐름이 끊겼다.

표에 내용을 너무 많이 넣으면 정리한 것처럼 보이지만 실제로는 읽기 더 어려웠다.

그래서 글을 작성하면서 점점 이런 생각을 하게 됐다.

**무엇을 넣을지뿐 아니라 어떻게 보여줄지도 글의 일부다.**

---

## 개발 글은 내용만 맞는다고 읽기 좋은 글이 되지는 않았다

처음에는 기술적인 내용이 정확하면 충분하다고 생각했다.

코드가 맞고,

설명이 틀리지 않고,

해결 방법이 제대로 적혀 있다면 좋은 기록이라고 생각했다.

물론 정확한 내용이 가장 중요하다.

하지만 내가 직접 다시 읽어보면 내용이 맞는데도 보기 불편한 글이 있었다.

코드와 설명이 구분되지 않아 어디부터 어디까지 봐야 하는지 헷갈리기도 했다.

이미지가 연속으로 여러 장 붙어 있으면 각각 무엇을 봐야 하는지 알기 어려웠다.

표를 만들었는데 한 셀 안에 긴 문장이 들어가면 오히려 일반 문단보다 읽기 힘들었다.

이런 경험을 하면서 **가독성도 정보 전달의 일부**라는 생각이 들었다.

내용이 아무리 정확해도 필요한 정보를 찾기 어렵다면 나중에 다시 보기 불편하다.

특히 내 블로그는 내가 다시 참고하기 위한 목적도 있었기 때문에 이 부분을 더 신경 쓰고 싶었다.

---

## 코드는 '많이 보여주는 것'보다 '필요한 부분을 보여주는 것'이 중요했다

개발 글을 작성하면 자연스럽게 코드를 많이 넣고 싶어진다.

실제로 작성한 코드를 보여주면 글이 더 정확해 보이고, 나중에 그대로 참고하기도 좋을 것 같았다.

하지만 긴 파일 전체를 그대로 붙여놓으면 문제가 생겼다.

내가 설명하려는 부분은 몇 줄인데 코드 블록은 수십 줄이 될 수 있었다.

그러면 독자는 설명을 읽기보다 코드에서 필요한 부분을 먼저 찾아야 한다.

나중의 나 역시

> 이 코드에서 내가 보려고 했던 부분이 어디였지?

라고 다시 찾아야 했다.

그래서 코드 블록에는 가능하면 **현재 설명에 필요한 부분만 남기는 것이 더 좋겠다**고 생각했다.

예를 들어 어떤 속성 하나를 설명하는 글이라면 관련 없는 설정까지 전부 보여줄 필요는 없다.

```css
.menu {
  display: flex;
  gap: 16px;
}
```

이 정도만으로 설명이 된다면 전체 CSS 파일을 붙일 이유는 없다.

코드를 줄인다는 것은 정보를 숨기는 것이 아니라 **지금 봐야 할 부분을 더 잘 보이게 만드는 것**에 가까웠다.

---

## 그렇다고 코드를 너무 잘라내는 것도 조심하고 싶었다

반대로 필요한 부분만 보여주겠다고 코드를 지나치게 잘라내면 문맥이 사라질 수도 있었다.

한 줄만 보여주면 그 코드가 어디에서 사용되는지 이해하기 어려울 수 있다.

예를 들어

```js
return response.json();
```

한 줄만 보여준다고 해서 항상 충분한 것은 아니다.

이 코드가 어떤 요청 뒤에 실행되는지 알아야 설명이 되는 경우도 있다.

그래서 코드 블록의 길이는 단순히 짧을수록 좋은 것이 아니었다.

내가 기준으로 삼고 싶었던 것은

> 이 코드만 봐도 지금 설명하려는 내용을 이해할 수 있는가?

였다.

필요한 문맥은 남긴다.

관련 없는 부분은 줄인다.

결국 코드 역시 본문과 마찬가지로 **현재 글의 질문에 필요한 만큼만 보여주는 것**이 중요했다.

---

## 코드를 넣기 전에 먼저 설명하려고 했다

코드를 바로 보여주면 나에게는 익숙한 내용이라 이해가 되지만 처음 보는 사람에게는 갑자기 코드부터 읽어야 할 수도 있다.

그래서 가능하면 코드 블록 앞에서

이 코드가 왜 필요한지,

무엇을 확인해야 하는지,

어떤 부분이 중요한지

짧게 설명하는 편이 좋다고 생각했다.

예를 들어 단순히

```bash
git pull origin main
```

만 적는 것보다

> 현재 브랜치에서 원격 `main`의 내용을 가져와 병합하려고 다음 명령을 사용했다.

처럼 먼저 맥락을 주면 코드가 무엇을 위한 것인지 바로 알 수 있다.

코드 아래에서는 결과나 내가 확인한 부분을 설명할 수 있다.

이렇게 하면

```text
설명
↓
코드
↓
결과 또는 해석
```

흐름이 만들어진다.

코드를 글의 장식처럼 넣는 것이 아니라 **설명의 한 부분으로 사용하는 방식**이었다.

---

## 터미널 명령어와 일반 코드를 구분해서 보고 싶었다

개발 공부를 기록하다 보면 코드뿐 아니라 터미널 명령어도 자주 등장한다.

예를 들어

```bash
git status
git add .
git commit -m "message"
```

같은 내용이다.

처음에는 이것도 모두 코드라고 생각하고 같은 방식으로 넣었다.

하지만 나중에 다시 볼 때는 일반 소스 코드와 실행해야 하는 명령어가 조금 다르게 느껴졌다.

소스 코드는 구조를 이해하기 위한 경우가 많고,

터미널 명령어는 **실제로 어떤 순서로 실행했는지**가 중요한 경우가 많다.

그래서 명령어를 보여줄 때는 단순히 블록만 넣는 것보다 순서와 목적이 같이 보이면 좋았다.

예를 들어

```text
1. 현재 상태 확인
2. 변경 파일 추가
3. 커밋
4. 원격 저장소로 push
```

처럼 흐름을 먼저 보여주고 명령어를 연결할 수 있다.

이렇게 하면 나중에 다시 봤을 때 명령어를 외우기보다 **왜 그 순서였는지**를 이해하기 쉬웠다.

---

## 오류 메시지는 필요한 부분을 그대로 남기는 편이 좋았다

오류를 해결한 글에서는 오류 메시지 자체가 중요한 단서가 된다.

그런데 오류가 발생했을 때 터미널 전체를 캡처해서 이미지로만 남기면 나중에 내용을 다시 읽기 어렵기도 했다.

반대로 긴 로그 전체를 코드 블록으로 붙이면 어디가 실제 오류인지 찾기 어렵다.

그래서 오류 기록에서는 핵심 메시지를 가능한 한 텍스트로 남기는 편이 좋다고 생각했다.

예를 들어

```text
Error: port 3000 is already in use
```

처럼 실제로 판단에 필요했던 부분을 보여주는 방식이다.

그러고 나서

이 메시지에서 무엇을 보고 원인을 추측했는지,

실제로 어떤 문제였는지

설명하면 된다.

오류 기록에서도 중요한 것은 로그 전체를 보존하는 것이 아니라 **내가 문제를 이해하는 데 사용한 단서가 무엇이었는지 남기는 것**이었다.

---

## 이미지는 말로 설명하기 어려운 순간에 가장 유용했다

블로그를 작성하다 보면 화면을 보여주는 것이 글 몇 문장보다 훨씬 빠른 경우가 있다.

디자인 변경 전후를 비교하거나,

설정 화면에서 어떤 위치를 선택해야 하는지 보여주거나,

오류가 실제 화면에서 어떻게 나타났는지 설명할 때는 이미지가 도움이 된다.

처음에는 이미지가 많을수록 글이 풍부해 보이는 것 같기도 했다.

하지만 이미지를 여러 장 넣어보면 생각보다 글의 흐름을 많이 차지한다.

특히 화면 전체 캡처를 계속 넣으면 스크롤 길이가 크게 늘어난다.

그래서 이미지 역시

> 이 이미지가 없으면 설명이 어려운가?

를 한 번 생각해 보기로 했다.

말로 충분히 설명할 수 있다면 굳이 넣지 않아도 된다.

반대로 위치나 모양이 중요하다면 이미지가 훨씬 정확하다.

---

## 이미지에는 '어디를 봐야 하는지'가 필요했다

화면 캡처를 그대로 넣는 것만으로는 설명이 끝나지 않았다.

이미지를 넣은 사람은 무엇을 보여주려는지 알고 있지만 보는 사람은 모를 수 있다.

특히 설정 화면처럼 정보가 많은 이미지에서는 더 그랬다.

그래서 이미지를 넣을 때는 적어도

> 이 이미지에서 무엇을 확인해야 하는지

본문에서 알려주는 것이 필요했다.

예를 들어

> 상단 메뉴에서 `Settings`를 선택한 뒤 오른쪽의 환경 변수 영역을 확인했다.

처럼 설명할 수 있다.

필요하다면 이미지에서 중요한 부분만 잘라서 보여주는 것이 화면 전체를 넣는 것보다 나을 수도 있다.

이미지 역시 많이 보여주는 것보다 **시선을 어디에 둘지 알려주는 것**이 중요했다.

---

## 스크린샷 하나가 글 전체를 대신하게 하고 싶지는 않았다

개발 공부를 하면서 화면을 캡처해 두는 것은 편하다.

그 순간의 상태를 그대로 남길 수 있기 때문이다.

하지만 스크린샷만 연속으로 남기면 시간이 지난 뒤 무슨 의미였는지 기억나지 않을 수 있다.

예를 들어 설정 화면 캡처 하나만 있고 설명이 없다면 몇 달 뒤에는

> 여기서 뭘 설정했던 거지?

가 될 수 있다.

그래서 이미지는 증거처럼 남기되 본문에는 최소한

무엇을 확인했고,

왜 이 화면을 남겼고,

어떤 결과가 있었는지

같이 적는 편이 좋았다.

이미지는 설명을 대신하는 것이 아니라 **설명을 보조하는 자료**라고 생각했다.

---

## 이미지 크기도 읽는 흐름에 영향을 줬다

화면 전체 캡처를 본문 너비에 꽉 차게 넣으면 세부 내용은 잘 보일 수 있다.

하지만 중요하지 않은 이미지까지 크게 들어가면 글의 흐름이 계속 끊긴다.

반대로 너무 작게 줄이면 이미지를 넣은 의미가 없어진다.

그래서 이미지 크기도 내용에 따라 달라질 필요가 있었다.

전체 화면 구성이 중요하다면 넓게 보여줄 수 있다.

작은 설정 하나를 보여주는 것이 목적이라면 해당 부분을 잘라서 보여주는 편이 낫다.

이미지의 크기를 일률적으로 맞추기보다 **그 이미지에서 전달하려는 정보의 범위**를 기준으로 보는 편이 자연스러웠다.

---

## 비교할 내용이 생기면 표가 편했다

글을 작성하면서 두 가지 이상의 내용을 비교해야 할 때가 자주 있었다.

예를 들어

`git pull`과 `git pull origin main`의 차이,

개발 환경과 운영 환경의 차이,

여러 선택지의 장단점

같은 내용이다.

이런 것을 문장으로 계속 설명하면 같은 항목을 반복해서 적어야 할 때가 많다.

그럴 때는 표가 훨씬 빠르게 비교할 수 있었다.

예를 들어

| 구분    | A   | B   |
| ----- | --- | --- |
| 목적    | ... | ... |
| 사용 상황 | ... | ... |
| 차이    | ... | ... |

처럼 구성하면 같은 기준에서 차이를 볼 수 있다.

표의 가장 큰 장점은 정보를 압축하는 것보다 **같은 기준으로 옆에서 비교할 수 있다는 점**이었다.

---

## 표를 많이 쓰면 오히려 글이 딱딱해졌다

표가 편하다고 느끼면 모든 내용을 표로 정리하고 싶어질 수 있다.

하지만 실제로 작성해 보면 표 역시 모든 내용에 어울리지는 않았다.

과정이나 이유를 설명해야 하는 내용은 문장으로 읽는 편이 더 자연스럽다.

예를 들어

> 처음에는 이런 이유로 A를 선택했지만 실제로 적용하면서 이런 문제가 생겨 B로 변경했다.

같은 이야기는 표에 넣으면 오히려 흐름이 끊길 수 있다.

반대로

두 기술의 차이,

설정값 비교,

역할 구분

처럼 같은 기준으로 여러 항목을 비교하는 내용은 표가 잘 맞는다.

그래서 표를 사용하는 기준을

**정리할 수 있는가**보다 **비교할 필요가 있는가**에 가깝게 두고 싶었다.

---

## 표 안의 문장이 길어지면 다시 풀어서 쓰는 편이 나았다

표를 만들었는데 셀 하나에 문장이 세네 줄씩 들어가기 시작하면 읽기 어려워졌다.

특히 모바일 화면에서는 열의 폭이 줄어들기 때문에 긴 내용이 더 답답해질 수 있다.

그래서 표는 가능하면 짧고 명확한 정보를 담는 용도로 사용하려고 했다.

설명이 길어진다면 본문에서 먼저 설명하고 표에서는 핵심만 비교하면 된다.

예를 들어

본문에서는 각각의 방법을 자세히 설명하고,

마지막에

| 방식 | 특징     | 선택한 이유      |
| -- | ------ | ----------- |
| A  | 간단함    | 초기 구현에 적합   |
| B  | 확장성 높음 | 현재 범위에서는 과함 |

처럼 요약할 수 있다.

표가 본문을 대신하기보다 **이미 설명한 내용을 빠르게 다시 비교하는 역할**을 할 수도 있었다.

---

## 코드·이미지·표를 한꺼번에 넣을 때는 더 조심해야 했다

개발 글 하나에는 여러 요소가 동시에 들어갈 수 있다.

문제를 설명하고,

스크린샷을 보여주고,

코드를 넣고,

마지막에 표로 비교할 수도 있다.

각각은 필요한 요소인데 한 구간에 몰리면 글이 복잡해진다.

이미지 바로 아래 코드,

그 아래 큰 표,

다시 이미지가 이어지면 글보다 자료 모음처럼 보일 수 있다.

그래서 가능하면 각 요소 사이에 **왜 다음 자료가 필요한지 설명하는 문장**을 두려고 했다.

예를 들어

```text
문제 상황 설명
↓
실제 화면 이미지
↓
화면에서 확인한 내용 설명
↓
관련 코드
↓
코드에서 바꾼 부분 설명
```

처럼 연결하는 것이다.

이렇게 하면 자료가 따로 놀지 않고 하나의 이야기 안에 들어간다.

---

## 강조는 적을수록 더 잘 보였다

글을 보기 좋게 만들고 싶으면 중요한 문장을 전부 굵게 표시하고 싶을 때가 있다.

하지만 굵은 글씨가 너무 많으면 결국 아무것도 강조되지 않는다.

코드 블록, 이미지, 표도 이미 시각적으로 눈에 띄는 요소였다.

여기에 본문까지 계속 강조하면 화면이 복잡해질 수 있었다.

그래서 정말 다시 보고 싶은 문장이나 글의 핵심 기준 정도만 강조하는 편이 낫다고 생각했다.

**강조의 목적은 눈에 띄게 만드는 것이 아니라 어디를 먼저 봐야 하는지 알려주는 것**이었다.

---

## 꾸미기보다 구분이 잘되는 것이 먼저였다

개발 블로그 디자인을 생각하다 보면 코드 블록에 색상을 넣고,

표에 배경색을 넣고,

이미지에 그림자를 넣고,

중요한 문장에 여러 효과를 사용하는 식으로 꾸밀 수 있다.

하지만 내가 글 내부에서 먼저 해결하고 싶었던 것은 화려함이 아니었다.

본문과 코드가 확실히 구분되는가.

표의 헤더와 내용이 구분되는가.

이미지가 본문과 너무 붙어 있지 않은가.

소제목과 내용 사이의 관계가 보이는가.

이런 기본적인 부분이었다.

가독성이 먼저 해결되지 않은 상태에서 장식을 늘리면 오히려 더 복잡해질 수 있었다.

그래서 **눈에 띄게 만드는 것보다 역할이 구분되게 만드는 것**을 우선하고 싶었다.

---

## 모바일에서는 표와 코드가 특히 문제가 될 수 있었다

데스크톱에서는 긴 코드나 넓은 표가 어느 정도 보인다.

하지만 모바일 화면에서는 상황이 달라진다.

한 줄의 코드가 화면 너비를 넘어갈 수 있고,

열이 많은 표는 한눈에 보기 어렵다.

이미지도 너무 작게 줄어들 수 있다.

그래서 글 내부 요소를 정리할 때는 데스크톱 화면만 보고 끝내기 어렵다고 느꼈다.

코드가 너무 긴 줄로 되어 있다면 모바일에서 읽을 수 있는지,

표가 너무 많은 열을 가지고 있지는 않은지,

이미지 안의 글씨가 작아지지 않는지

같은 부분도 확인할 필요가 있었다.

이때부터 블로그 글을 작성하는 것과 블로그 화면을 디자인하는 것이 완전히 따로 떨어진 일이 아니라는 생각도 들기 시작했다.

---

## 같은 정보를 두 번 보여주지 않으려고 했다

코드를 넣고 바로 아래에서 코드와 같은 내용을 그대로 문장으로 반복하는 경우도 있었다.

표를 만든 뒤 표의 모든 내용을 다시 문장으로 한 번씩 설명할 수도 있다.

이미지에 이미 보이는 텍스트를 본문에 그대로 옮겨 적을 수도 있다.

필요한 설명이라면 괜찮지만 단순한 반복이라면 글만 길어진다.

그래서 각 요소가 어떤 역할을 하는지 구분하려고 했다.

코드는 실제 작성 형태를 보여준다.

본문은 그 코드에서 무엇을 봐야 하는지 설명한다.

표는 여러 항목의 차이를 빠르게 비교한다.

이미지는 글만으로 전달하기 어려운 화면 상태를 보여준다.

역할이 겹치지 않으면 같은 정보를 여러 번 보여줄 이유도 줄어든다.

---

## 중요한 것은 자료를 넣는 기준이 생기는 것이었다

결국 코드, 이미지, 표를 정리하면서 만들고 싶었던 것은 완벽한 디자인 규칙이 아니었다.

글을 작성하다가

> 코드 하나 넣을까?

> 이미지도 넣어야 하나?

> 표로 정리하면 더 좋아 보이지 않을까?

라는 생각이 들 때 판단할 기준이 필요했다.

그래서 나에게는 이런 정도의 질문이 가장 유용했다.

```text
코드
→ 이 설명을 이해하는 데 실제 코드가 필요한가?

이미지
→ 글로 설명하는 것보다 화면을 보여주는 것이 더 정확한가?

표
→ 같은 기준으로 두 개 이상의 항목을 비교해야 하는가?
```

셋 중 어떤 것도 필요하지 않다면 일반적인 문장만으로 충분할 수 있다.

기능이나 요소를 많이 넣는 것이 좋은 글의 기준은 아니었다.

---

## 글을 보기 좋게 만드는 것도 결국 다시 읽기 위해서였다

코드 블록을 정리하고,

이미지를 필요한 만큼만 넣고,

표를 비교가 필요한 곳에 사용하는 이유를 생각해 보면 결국 앞에서 했던 고민과 같은 곳으로 돌아왔다.

**나중에 다시 읽기 편한 기록을 만들고 싶었다.**

처음 작성할 때는 내용을 알고 있으니 조금 복잡해도 이해할 수 있다.

하지만 시간이 지나 다시 보면 처음 보는 글에 가까워질 수 있다.

그때는 코드와 설명이 잘 구분되어 있고,

이미지에서 무엇을 봐야 하는지 알 수 있고,

비교할 내용이 한눈에 들어오는 편이 훨씬 좋다.

그래서 가독성은 단순히 블로그를 예쁘게 보이게 하기 위한 것이 아니라 **기록을 다시 사용할 수 있게 만드는 방법**이라고 생각하게 됐다.

---

## 글 작성 기준을 정하다 보니 블로그 화면 자체가 다시 보였다

글 작성 시스템을 만들면서

무엇을 기록할지,

어떤 구조로 쓸지,

어떻게 분류할지,

긴 글을 어떻게 탐색할지,

코드와 이미지와 표를 어떻게 보여줄지까지 하나씩 고민했다.

그 과정에서 이상하게도 포스트 내용만 보던 시선이 점점 블로그 전체 화면으로 넓어졌다.

글 자체를 아무리 잘 정리해도 주변 화면이 복잡하면 읽기 불편할 수 있었다.

본문 폭이 너무 좁거나 넓을 수도 있고,

사이드바가 글보다 더 눈에 띌 수도 있고,

카테고리 구조가 화면에서 보기 어렵게 배치되어 있을 수도 있다.

처음 블로그를 다시 시작할 때는 기록 방식을 만드는 것이 먼저였다면 이제는 **그 기록을 담고 있는 공간 자체도 다시 보고 싶어졌다.**

내용을 정리하는 기준이 조금씩 생기자 오히려 기존 블로그 화면에서 불편한 점들이 더 잘 보이기 시작했다.

그래서 다음에는 글 하나의 구성에서 벗어나 블로그 전체 디자인을 다시 살펴보기 시작했다.
