현재 내 블로그 포스트에는 이미지가 거의 없다.

홈 화면에는 이미지를 사용하고 있지만 실제 공부 글과 프로젝트 기록은 대부분 텍스트로만 작성되어 있다.

처음에는 개발 블로그니까 크게 문제없다고 생각했다.

공부한 내용을 자세히 남기는 것이 가장 중요했고, 이미지보다 글의 구조를 만드는 데 더 집중했다.

카테고리를 정하고,

포스트 템플릿을 만들고,

긴 글에는 TOC를 넣고,

코드와 표를 보기 좋게 정리하는 방향을 먼저 고민했다.

그런데 포스트가 점점 길어지면서 직접 읽어보니 한 가지 문제가 보이기 시작했다.

**글만 계속 이어지니 생각보다 읽기가 힘들었다.**

내용이 잘못된 것은 아니다.

하지만 실제 화면을 보고 작업했던 내용까지 모두 글로 설명하다 보니 문장이 길어졌고, 한눈에 이해하기 어려운 부분도 생겼다.

그래서 앞으로는 필요한 곳에 실제 캡처와 이미지를 조금씩 넣어보려고 한다.

다만 이미지를 추가하기 시작하기 전에 **어떤 이미지를 넣고 어떻게 관리할지**는 미리 기준을 정해두는 편이 좋겠다고 생각했다.

---

## 글만으로 설명하기 어려운 부분이 있었다

지금까지 작성한 글을 돌아보면 실제 화면을 함께 보여줬다면 더 이해하기 쉬웠을 내용이 꽤 있었다.

GitHub 설정 화면,

VS Code에서 보이는 상태,

배포 설정,

웹페이지 디자인 변경,

오류가 발생한 화면처럼 내가 직접 화면을 보면서 작업한 내용들이다.

예를 들어

> 오른쪽 상단의 설정 메뉴에서 특정 항목을 선택하고 아래 값을 수정했다.

라고 여러 문장으로 설명하는 것보다 실제 화면을 보여주면서 해당 부분을 알려주는 편이 훨씬 빠르게 이해될 수 있다.

특히 내 블로그는 일반적인 개념만 정리하기보다 **내가 실제로 어떤 상황에서 배우고 헷갈렸는지**를 기록하는 글이 많다.

그렇다면 실제 캡처도 중요한 기록 자료가 될 수 있다.

---

## 그렇다고 글이 길다고 이미지를 억지로 넣고 싶지는 않았다

현재 블로그가 너무 텍스트 중심이라고 해서 문단 사이마다 이미지를 하나씩 넣고 싶은 것은 아니다.

내용과 관계없는 이미지는 글을 덜 답답하게 보이게 만들 수는 있어도 이해에는 크게 도움이 되지 않는다.

오히려 읽는 흐름을 끊을 수도 있다.

그래서 앞으로 이미지를 넣는다면 이런 경우를 먼저 생각하려고 한다.

```text
실제 화면을 보는 편이 설명보다 이해하기 쉬운가?

내가 겪었던 상황을 보여주는 데 도움이 되는가?

수정 전·후를 비교할 필요가 있는가?

오류나 설정 화면처럼 나중에 다시 확인할 가치가 있는가?
```

즉, 이미지를 많이 넣는 것이 목적이 아니다.

**글보다 이미지가 더 빠르고 정확하게 설명할 수 있는 부분에 이미지를 사용하는 것**이 목표다.

---

## 가장 먼저 넣고 싶은 것은 실제 캡처 화면이다

처음부터 포스트마다 화려한 대표 이미지나 일러스트를 만들 생각은 없다.

가장 먼저 활용하고 싶은 것은 실제 작업 과정에서 나온 화면이다.

GitHub 설정을 설명하는 글이라면 실제 GitHub 화면을 보여주고,

디자인을 수정한 글이라면 수정 전후의 블로그 화면을 남기고,

오류를 해결한 글이라면 당시 오류 화면을 보여주는 식이다.

이런 이미지는 단순한 장식이 아니라 **내가 실제로 겪었던 상황을 남기는 기록**에 가깝다.

나중에 내가 다시 글을 볼 때도 글만 읽는 것보다 당시 화면을 함께 보면 훨씬 빠르게 상황을 떠올릴 수 있을 것 같다.

---

## 이미지를 넣기 시작하면 용량도 같이 생각해야 한다

현재는 포스트에 이미지가 없기 때문에 이미지 때문에 블로그가 느려지는 문제도 거의 없다.

하지만 앞으로 실제 캡처를 계속 추가한다면 상황은 달라질 수 있다.

화면 캡처 한 장은 생각보다 용량이 클 수 있다.

한두 장은 큰 차이가 없어 보여도 한 포스트에 여러 장이 들어가고 이런 글이 계속 쌓이면 사용자가 받아야 하는 이미지도 많아진다.

특히 모바일에서는 네트워크 상태에 따라 이미지가 늦게 나타날 수도 있다.

읽기 편하게 만들려고 넣은 이미지 때문에 오히려 글이 늦게 뜬다면 좋은 방향은 아니다.

그래서 앞으로는

> 이미지를 넣는다.

에서 끝내지 않고

> **필요한 이미지를 웹에서 사용할 만큼 적절한 크기로 관리한다.**

까지 같이 생각하려고 한다.

---

## 화면 전체보다 필요한 부분만 캡처하는 편이 낫다

실제 화면을 남긴다고 해서 항상 화면 전체를 캡처할 필요는 없다.

설정 메뉴 하나를 설명하는데 브라우저 전체가 들어가면 정작 봐야 할 부분은 작아진다.

이미지 안에서 어디를 봐야 하는지도 찾기 어려워진다.

필요 없는 영역까지 들어가니 파일 용량도 커진다.

그래서 캡처를 사용할 때는 먼저

> 이 이미지에서 보여주고 싶은 것이 무엇인가?

를 생각하는 편이 좋을 것 같다.

필요한 부분만 잘라내면 보는 사람도 이해하기 쉽고 파일도 자연스럽게 작아진다.

이미지 최적화는 단순히 압축 프로그램을 사용하는 것만이 아니라 **처음부터 필요 없는 영역을 넣지 않는 것부터 시작한다**고 볼 수 있었다.

---

## 이미지 변환 방법 자체는 어렵지 않았다

이미지 용량을 줄이는 방법을 찾아보면 프로그램과 웹서비스가 정말 많이 나온다.

PNG나 JPEG 이미지를 WebP로 변환해 주는 사이트도 있고, 파일 크기를 줄여주는 도구도 쉽게 찾을 수 있다.

그래서 처음에는

> 필요하면 변환 프로그램 하나 쓰면 되겠네.

라고 생각했다.

그런데 실제로 생각해 보니 더 기본적인 문제가 있었다.

**변환하려면 내 로컬에 원본 이미지 파일이 있어야 했다.**

이미 웹페이지에서 사용되고 있는 이미지를 보고

> 이 이미지를 WebP로 바꿔야겠다.

라고 생각해도 실제 파일을 가지고 있지 않으면 바로 변환할 수 없다.

결국 과정은 단순히

```text
이미지 발견
→ 변환
```

이 아니었다.

```text
원본 이미지 위치 확인
→ 로컬 파일 확보
→ 필요한 부분 정리
→ 적절한 크기로 조절
→ WebP 등 웹용 형식으로 변환
→ 프로젝트에 적용
```

같은 과정이 필요했다.

---

## 그래서 앞으로는 원본부터 남겨두려고 한다

현재 포스트에는 이미지가 거의 없기 때문에 오히려 지금부터 관리 방식을 정할 수 있다.

앞으로 직접 화면을 캡처한다면 처음부터 원본 파일을 가지고 시작하게 된다.

그래서 이런 흐름으로 관리하면 좋을 것 같다.

```text
화면 캡처
↓
원본 파일 보관
↓
필요한 부분 자르기
↓
웹에서 사용할 크기로 조절
↓
필요하면 WebP 등으로 변환
↓
블로그에 사용
```

원본을 남겨두면 나중에 이미지 크기를 다시 조절하거나 화질을 다르게 만들고 싶을 때 다시 작업할 수 있다.

반대로 압축된 작은 파일만 가지고 있다면 더 높은 품질이 필요해졌을 때 되돌리기 어렵다.

그래서 앞으로는 **원본 이미지와 실제 블로그에서 사용하는 웹용 이미지를 구분해 관리하는 방식**도 생각하고 있다.

---

## 화면에 작게 보이는 것과 파일이 작은 것은 달랐다

이미지를 CSS로 작게 표시한다고 파일 용량까지 줄어드는 것은 아니다.

예를 들어 큰 이미지를

```css
img {
  width: 600px;
}
```

처럼 작게 보이게 만들어도 사용자는 원래 큰 이미지 파일을 내려받아야 할 수 있다.

그래서

```text
화면에서 보이는 크기
≠
실제 이미지 파일의 크기
```

라는 차이를 구분할 필요가 있었다.

앞으로 이미지를 넣을 때는 화면에서 어떻게 보여줄지만 보는 것이 아니라 **실제 파일 자체가 필요 이상으로 크지는 않은지도 확인하려고 한다.**

---

## 무조건 용량을 작게 만드는 것도 답은 아니다

이미지 최적화라고 하면 파일 크기를 최대한 줄이는 것이 좋을 것처럼 느껴진다.

하지만 개발 블로그에서 사용하는 캡처에는 작은 글자가 많이 들어간다.

터미널,

코드,

설정값,

메뉴 이름처럼 실제로 읽어야 하는 정보가 많다.

용량을 줄이겠다고 지나치게 압축해서 글자가 흐려지면 이미지를 넣은 의미 자체가 사라진다.

그래서 목표는

```text
가장 작은 이미지
```

가 아니라

```text
내용을 읽을 수 있는 화질
+
불필요하게 크지 않은 용량
```

사이의 균형이다.

---

## 실제 캡처에는 개인정보도 확인해야 한다

포스트에 실제 화면을 넣으려고 하니 용량보다 먼저 조심해야 할 부분도 있었다.

개발 화면에는 생각보다 많은 정보가 들어간다.

이메일,

계정 이름,

프로젝트 정보,

환경 변수,

API 키,

개인적인 파일 경로 같은 값이 보일 수도 있다.

특히 설정 화면이나 터미널을 전체 캡처하면 글에서 전혀 필요하지 않은 정보까지 같이 들어갈 수 있다.

그래서 실제 캡처를 추가하기 전에는

> 공개하면 안 되는 내용이 포함되어 있지 않은가?

를 반드시 확인해야 한다.

필요한 부분만 캡처하는 습관은 이런 면에서도 도움이 될 것 같다.

---

## 이미지가 생기면 alt도 함께 작성하려고 한다

앞에서 기본 SEO와 웹 디테일을 정리하면서 이미지의 `alt`에 대해서도 알게 됐다.

현재는 포스트 이미지가 없으니 크게 사용할 일이 없었지만 앞으로 캡처를 넣기 시작하면 같이 작성하려고 한다.

예를 들어

```text
스크린샷
```

이라고 적기보다

```text
GitHub에서 브랜치 목록을 확인하는 화면
```

처럼 이미지가 무엇을 보여주는지 설명하는 방식이다.

이미지가 보이지 않는 상황에서도 어느 정도 내용을 전달할 수 있고, 이미지가 글에서 어떤 역할을 하는지도 더 명확해진다.

---

## 이미지가 많아지면 파일 이름도 문제가 될 수 있다

지금은 홈 화면 외에는 이미지가 거의 없기 때문에 이미지 파일을 관리하는 일이 어렵지 않다.

하지만 포스트마다 실제 캡처를 추가하기 시작하면 파일도 빠르게 늘어날 수 있다.

그때

```text
image1.png
image2.png
final.png
final2.png
```

처럼 저장하면 나중에 어느 글에서 사용하는 이미지인지 알기 어려울 것이다.

그래서 이미지가 실제로 쌓이기 시작하면 파일 이름이나 저장 위치에도 최소한의 규칙이 필요할 것 같다.

다만 아직 이미지가 없는 단계에서 복잡한 구조부터 만들 생각은 없다.

사용하면서 파일이 늘어날 때 필요한 수준으로 정리하면 충분하다.

---

## 지금은 성능 최적화보다 이미지를 넣기 시작하는 것이 먼저다

현재 내 블로그의 문제는 이미지가 많아서 느린 것이 아니다.

오히려 반대다.

**포스트에 이미지가 하나도 없어서 글이 너무 텍스트 중심이다.**

그래서 지금 당장 복잡한 이미지 최적화 기능부터 넣는 것은 순서가 맞지 않는다.

우선 해야 할 것은 실제로 도움이 되는 캡처를 글에 조금씩 사용해 보는 것이다.

그 과정에서 이미지 파일이 늘어나고 실제 페이지 로딩이 부담스러워진다면 그때 압축, WebP 변환, 로딩 방식 같은 최적화를 더 적극적으로 적용하면 된다.

아직 생기지도 않은 성능 문제를 미리 크게 해결하고 싶지는 않다.

---

## 앞으로는 글과 화면을 함께 기록해 보고 싶다

지금까지는 내가 공부한 내용을 대부분 글로만 남겼다.

앞으로는 실제 상황을 보여주는 것이 더 좋은 부분이라면 캡처도 같이 남겨보고 싶다.

예를 들면 이런 흐름이다.

```text
상황 설명
↓
실제 화면 캡처
↓
이미지에서 확인할 부분
↓
내가 이해한 내용
```

이렇게 하면 긴 글이 조금 덜 답답해지고, 실제 경험도 더 정확하게 기록할 수 있을 것 같다.

---

## 목표는 이미지가 많은 블로그가 아니다

이미지를 추가하려는 이유는 블로그를 화려하게 만들기 위해서가 아니다.

현재처럼 글만 길게 이어지는 부분에서 **실제로 보여주는 편이 더 이해하기 쉬운 내용을 보완하기 위해서**다.

그래서 앞으로도 글이 중심이라는 점은 바뀌지 않는다.

다만 글로만 설명하기 어려운 부분에서는 실제 캡처를 사용하고, 그 이미지는 웹에서 필요한 수준으로 가볍게 관리하려고 한다.

현재 내가 정한 방향은 단순하다.

> **우선 필요한 이미지를 넣기 시작한다. 원본은 로컬에 남겨두고, 블로그에는 웹용으로 정리한 이미지를 사용한다.**

이미지 최적화 방법 자체는 검색하면 쉽게 찾을 수 있었다.

오히려 실제로 해보려면 원본 파일이 어디에 있는지부터 관리해야 한다는 점이 더 현실적인 문제였다.

현재는 홈 화면을 제외하면 포스트 이미지가 하나도 없다.

그래서 지금의 이미지 최적화는 이미 느려진 사이트를 개선한 경험이라기보다 **앞으로 이미지를 제대로 사용하기 위해 세워두는 기준**에 가깝다.

이제부터는 설명에 실제 화면이 더 도움이 되는 부분을 글로만 넘기지 않고 가능한 경우 캡처도 함께 남겨보려고 한다.

텍스트만 많은 블로그에서 조금씩 벗어나되, 이미지 때문에 지나치게 무거워지지 않는 것.

그 사이의 균형을 찾아가는 것이 앞으로의 목표다.
