「정보 구조와 페이지 구성」에서는 서비스의 정보를 어떤 페이지에 나누고,

각 페이지에 어떤 역할을 줄 것인지 정리했다.

그런데 페이지를 만들다 보면 한 가지 상황을 자꾸 놓치게 된다.

```text
데이터가 하나도 없을 때는
무엇을 보여주지?
```

예를 들어 기록 목록 화면을 만든다고 해보자.

디자인할 때는 보통 이런 화면부터 생각한다.

```text
내 기록

8월 20일 러닝
8월 18일 러닝
8월 15일 러닝
```

카드가 여러 개 있는 상태다.

카드를 어떻게 만들지,

날짜는 어디에 둘지,

버튼은 어디에 둘지를 디자인한다.

그런데 사용자가 처음 가입했다면?

```text
내 기록

?
```

아무 기록도 없다.

카페 혜택 관리 서비스라면

```text
내 혜택

?
```

아직 등록한 혜택이 하나도 없을 수 있다.

검색 화면에서는

```text
검색 결과

?
```

조건에 맞는 결과가 없을 수도 있다.

처음에는 이런 상황을

```text
나중에 데이터 없으면
"데이터가 없습니다"라고 쓰면 되겠지.
```

정도로 생각했다.

하지만 실제 서비스를 생각해보니

빈 화면도 사용자가 실제로 마주치는 화면이었다.

즉,

> **Empty State도 예외 상황이 아니라 하나의 정상적인 UI 상태였다.**

이번 글에서는 아무것도 없는 화면을 어떻게 설계하면 좋을지 정리해보려고 한다.

---

## Empty State란?

Empty State는 말 그대로

```text
보여줄 데이터가 없는 상태
```

를 말한다.

하지만 데이터가 없다고 해서 모두 같은 상황은 아니다.

예를 들어

```text
첫 가입
→ 아직 데이터가 없음

검색
→ 조건에 맞는 결과가 없음

필터
→ 현재 필터에서는 결과가 없음

삭제
→ 기존 데이터를 모두 삭제함
```

모두 화면에는 아무것도 없을 수 있다.

하지만 사용자에게 전달해야 하는 의미는 다르다.

그래서 단순히

```text
데이터가 없습니다.
```

한 문장으로 처리하면 부족할 수 있었다.

---

## 처음에는 빈 화면이면 그냥 비워두면 된다고 생각했다

예를 들어 카드 목록 UI를 만들었다.

```text
┌─────────────┐
│   카드 1     │
└─────────────┘

┌─────────────┐
│   카드 2     │
└─────────────┘
```

데이터가 없으면 카드 렌더링이 안 된다.

결과는

```text
내 혜택




```

이 될 수 있다.

개발자 입장에서는 이상하지 않다.

```text
배열이 비어 있으니까
렌더링할 카드가 없는 것
```

이다.

하지만 사용자 입장에서는 다르다.

```text
왜 아무것도 없지?

로딩이 안 된 건가?

오류인가?

내 데이터가 사라진 건가?

내가 뭘 해야 하지?
```

를 알 수 없다.

즉 시스템 상태는 정상이어도

사용자는 정상인지 알 수 없다.

---

## Empty State의 첫 번째 역할은 현재 상태를 설명하는 것

그래서 Empty State에는 최소한

```text
지금 왜 아무것도 없는가?
```

에 대한 설명이 필요했다.

예를 들어

```text
등록된 혜택이 없습니다.
```

라고 하면

사용자는

```text
오류가 아니라
아직 등록한 혜택이 없는 상태구나.
```

라고 이해할 수 있다.

검색이라면

```text
검색 결과가 없습니다.
```

라고 알려준다.

기록이라면

```text
아직 저장된 러닝 기록이 없습니다.
```

라고 할 수 있다.

Empty State가 단순한 장식이 아니라

**현재 시스템 상태를 사용자에게 설명하는 UI**

라는 것을 알게 됐다.

---

## 두 번째 역할은 다음 행동을 알려주는 것

상태만 설명하고 끝내면 이런 화면이 된다.

```text
아직 등록된 혜택이 없습니다.
```

사용자는 이해했다.

그다음에는?

```text
그래서 뭘 해야 하지?
```

가 남는다.

사용자가 직접 데이터를 추가할 수 있는 서비스라면

다음 행동까지 연결할 수 있다.

```text
아직 등록된 혜택이 없어요.

첫 혜택을 등록하고
사용 가능한 혜택을 한곳에서 관리해보세요.

[혜택 등록하기]
```

이렇게 하면 Empty State가 단순한 안내 화면에서

```text
현재 상태
↓
다음 행동
```

으로 이어진다.

---

## Empty State는 사용자를 막는 화면이 아니라 시작하게 하는 화면이었다

특히 첫 사용자에게 Empty State는 매우 중요하다.

기존 사용자는 이미 데이터가 있다.

하지만 처음 가입한 사용자는 서비스의 대부분을 빈 화면으로 볼 수도 있다.

예를 들어

```text
내 혜택
→ 없음

기록
→ 없음

즐겨찾기
→ 없음
```

일 수 있다.

이때 모든 화면이

```text
데이터가 없습니다.
```

만 보여준다면

서비스에 아무것도 없는 것처럼 느껴질 수 있다.

반대로

```text
아직 등록한 혜택이 없어요.

[첫 혜택 등록하기]
```

처럼 보여주면

Empty State 자체가 사용 방법을 알려준다.

---

## 빈 화면은 첫 번째 온보딩이 될 수도 있었다

온보딩이라고 하면 보통

```text
앱 처음 실행
↓
설명 화면 1
↓
설명 화면 2
↓
설명 화면 3
```

같은 형태를 떠올린다.

하지만 사용자가 실제 기능에 들어갔을 때

Empty State가 자연스럽게 설명하는 방법도 있다.

예를 들어

```text
아직 등록된 혜택이 없어요.

보유한 스탬프나 쿠폰을 등록하면
주변 카페와 함께 확인할 수 있어요.

[혜택 등록하기]
```

이 문장만으로도

```text
이 화면에서 무엇을 관리하는지

왜 등록해야 하는지

어떻게 시작하는지
```

를 알 수 있다.

별도의 긴 튜토리얼 없이도 기능을 설명할 수 있다.

---

## 그렇다고 Empty State에 설명을 너무 많이 넣으면 안 됐다

사용자가 처음 보는 화면이라고 해서

모든 기능을 설명하고 싶어진다.

예를 들어

```text
아직 등록된 혜택이 없습니다.

혜택에서는 브랜드별 스탬프와 쿠폰을 관리하고
유효기간을 등록할 수 있으며
주변 카페 검색 시 현재 혜택을 함께 확인하고
사용 조건과 매장별 정책도 확인할 수 있습니다...
```

너무 길어진다.

사용자는 지금

```text
빈 화면
```

을 보고 있을 뿐이다.

이때 필요한 것은 대부분

```text
왜 비어 있는지

+

무엇을 하면 되는지
```

정도다.

그래서 Empty State에서도

**정확하게 설명하려는 욕심과 사용자가 읽어야 하는 양을 구분할 필요가 있었다.**

---

## 내가 생각하는 기본 구조

가장 단순하게 만들면 이런 구조가 된다.

```text
[아이콘 또는 이미지]

제목

짧은 설명

[Primary Action]
```

예를 들면

```text
      🎟

아직 등록한 혜택이 없어요

보유한 쿠폰이나 스탬프를
첫 번째 혜택으로 등록해보세요.

[혜택 등록하기]
```

물론 항상 이미지와 버튼이 모두 필요한 것은 아니다.

상황에 따라 줄일 수 있다.

---

## Empty State에도 정보 우선순위가 필요했다

「버튼과 정보의 우선순위」에서 배운 정보 우선순위가 여기에서도 그대로 적용된다.

예를 들어

```text
아직 등록된 혜택이 없습니다.
```

가 핵심이다.

그다음은

```text
혜택을 등록하면 여기에서 확인할 수 있어요.
```

라는 설명이다.

마지막은

```text
[혜택 등록하기]
```

라는 행동이다.

화면에서

```text
제목
↓
설명
↓
행동
```

흐름이 자연스럽게 이어져야 한다.

---

## 모든 Empty State에 버튼이 필요한 것은 아니다

예를 들어 검색 결과가 없는 상황을 생각해보자.

```text
'판교역 커피' 검색 결과가 없습니다.
```

이때 버튼이 반드시 필요한 것은 아니다.

사용자는 이미 검색창을 보고 있고,

검색어를 수정하면 된다.

그래서

```text
검색 결과가 없습니다.

검색어나 지역을 바꿔보세요.
```

정도로 끝낼 수 있다.

반면 처음 혜택이 없는 화면에서는

사용자가 무엇을 해야 할지 명확하므로

```text
[혜택 등록하기]
```

버튼이 도움이 된다.

즉 Empty State도

```text
다음 행동이 명확한가?
```

에 따라 CTA 여부를 결정해야 했다.

---

## 첫 사용 Empty State

첫 번째 종류는

```text
사용자가 아직 아무것도 만들지 않은 상태
```

다.

예를 들어

```text
등록한 혜택 없음

작성한 게시글 없음

러닝 기록 없음
```

등이다.

이때는 사용자가 서비스를 처음 사용할 가능성이 높다.

그래서

```text
무엇을 할 수 있는지

어떻게 시작하는지
```

를 알려주는 것이 좋다.

예:

```text
아직 러닝 기록이 없어요.

첫 러닝을 시작하면
달린 거리와 시간을 여기에서 확인할 수 있어요.

[러닝 시작]
```

단순히

```text
기록 없음
```

보다 훨씬 친절하다.

---

## 검색 결과 없음

두 번째는

```text
사용자가 무엇인가를 찾았지만
조건에 맞는 결과가 없는 상태
```

다.

이 경우에는 의미가 완전히 다르다.

사용자가 데이터를 등록해야 하는 것이 아니다.

대신 검색 조건을 바꿔야 한다.

예를 들어

```text
검색 결과가 없어요.

검색어나 지역명을 다시 확인해보세요.
```

라고 할 수 있다.

또는

```text
다른 지역에서 찾아보기
```

같은 행동을 제안할 수도 있다.

---

## 검색 결과 없음에서 "등록하기" 버튼을 보여주면 이상할 수 있다

예를 들어 사용자가

```text
강남역 카페
```

를 검색했다.

결과가 없다.

그런데 화면이

```text
검색 결과가 없습니다.

[새 카페 등록하기]
```

라고 나온다고 해보자.

서비스가 사용자가 직접 카페를 등록하는 구조가 아니라면

완전히 잘못된 행동을 제안한 것이다.

Empty State의 CTA는

```text
현재 상태를 해결할 수 있는 행동
```

이어야 한다.

그냥 화면을 채우기 위해 버튼을 넣으면 안 된다.

---

## 필터 때문에 결과가 없는 상태

이것도 검색 없음과 조금 다르다.

예를 들어 원래 카페가 20개 있는데

사용자가

```text
도보 5분 이내
+
특정 브랜드
+
쿠폰 보유
```

필터를 적용했다.

결과가 0개다.

이때

```text
주변 카페가 없습니다.
```

라고 하면 잘못된 정보가 된다.

실제로 카페가 없는 것이 아니라

**현재 필터 조건에 맞는 카페가 없는 것**이다.

그래서

```text
현재 조건에 맞는 카페가 없어요.

필터를 변경해보세요.

[필터 초기화]
```

처럼 표현하는 것이 더 정확하다.

---

## 사용자가 왜 결과가 없는지 알 수 있어야 했다

Empty State 문구를 쓸 때

```text
없습니다.
```

만 쓰지 않고

```text
왜 없는가?
```

를 생각해본다.

예를 들어

```text
기록이 없음
→ 아직 러닝한 적 없음

검색 결과 없음
→ 검색 조건과 맞지 않음

필터 결과 없음
→ 필터가 너무 좁음

혜택 없음
→ 아직 등록하지 않음
```

원인이 다르다.

원인이 다르면 해결 방법도 다르다.

---

## 데이터가 원래 없는 것과 데이터를 가져오지 못한 것은 완전히 다르다

이 부분이 특히 중요했다.

화면에 아무것도 없다고 해서 모두 Empty State는 아니다.

예를 들어 서버 요청이 실패했다.

```text
GET /benefits
↓
500 Error
```

그러면 화면에는 혜택이 하나도 표시되지 않을 수 있다.

하지만 이것을

```text
등록된 혜택이 없습니다.
```

라고 보여주면 안 된다.

실제로는 데이터가 있을 수도 있다.

단지 가져오지 못한 것이다.

이것은 Empty State가 아니라 **Error State**다.

---

## Empty와 Error를 구분한다

### Empty

```text
요청 성공

데이터 확인

결과 0개
```

예:

```text
아직 등록된 혜택이 없어요.
```

### Error

```text
요청 실패

데이터 확인 불가
```

예:

```text
혜택을 불러오지 못했습니다.

[다시 시도]
```

둘을 구분하지 않으면 사용자가 잘못된 정보를 받게 된다.

---

## Loading도 Empty가 아니다

데이터를 아직 불러오는 중인데

화면이 잠시 비어 있을 수 있다.

예를 들어

```text
페이지 진입
↓
API 요청
↓
2초 후 데이터 표시
```

라고 해보자.

그 2초 동안 바로

```text
기록이 없습니다.
```

를 보여주면

잠깐 뒤에 기록이 갑자기 나타난다.

사용자는 화면이 깜빡이는 것처럼 느낄 수 있다.

그래서

```text
Loading
```

과

```text
Empty
```

도 구분해야 한다.

---

## 기본 상태를 나누면 이렇게 됐다

예를 들어 목록 화면 하나에도 최소한

```text
Loading

Success

Empty

Error
```

가 있을 수 있다.

조금 더 확장하면

```text
Permission Required

Offline

Filtered Empty
```

같은 상태도 생길 수 있다.

즉 화면 하나를 디자인한다는 것이

```text
정상 데이터가 있는 화면 한 장
```

만 만드는 것은 아니었다.

---

## 위치 권한이 없는 것은 Empty State가 아니다

주변 카페 앱을 예로 들어보자.

현재 위치 권한이 없다.

그래서 주변 카페를 찾을 수 없다.

화면에는 결과가 없다.

그렇다고

```text
주변 카페가 없습니다.
```

라고 하면 안 된다.

카페가 없는 것이 아니라

```text
현재 위치를 알 수 없음
```

이 문제다.

이 경우에는

```text
현재 위치를 확인할 수 없어요.

주변 카페를 찾으려면
위치 권한을 허용해주세요.

[위치 권한 설정]
```

같은 상태가 더 적절하다.

---

## Empty State를 만들기 전에 원인을 먼저 나누는 것이 좋았다

그래서 페이지를 디자인할 때 먼저

```text
왜 비어 있을 수 있지?
```

를 적어본다.

예를 들어 주변 카페 목록이라면

```text
1. 실제 주변 카페가 없음

2. 검색 결과 없음

3. 필터 조건 결과 없음

4. 위치 권한 없음

5. 네트워크 오류

6. 아직 로딩 중
```

처럼 나눌 수 있다.

겉으로는 모두

```text
카드 0개
```

지만 UI는 달라야 한다.

---

## 같은 "없음" 문구를 모든 곳에 사용하지 않는다

개발할 때 공통 Component를 만들다 보면

```text
EmptyState
```

하나를 만들고 싶어진다.

```text
데이터가 없습니다.
```

를 모든 페이지에 재사용할 수 있다.

코드는 간단하다.

하지만 사용자 경험은 좋지 않을 수 있다.

예를 들어

```text
검색 결과 없음

혜택 없음

기록 없음
```

은 모두 의미가 다르다.

공통 Component를 만들더라도

```text
Title

Description

Icon

Action
```

을 화면에 맞게 바꾸는 방식이 더 적절하다.

---

## 예를 들어 공통 구조만 재사용한다

```text
EmptyState

├─ Icon
├─ Title
├─ Description
└─ Action
```

형태는 같게 두고

혜택 화면에서는

```text
Title
→ 등록된 혜택이 없어요.

Description
→ 보유한 혜택을 등록해보세요.

Action
→ 혜택 등록
```

검색에서는

```text
Title
→ 검색 결과가 없어요.

Description
→ 다른 검색어를 입력해보세요.

Action
→ 없음
```

처럼 바꿀 수 있다.

디자인은 일관되지만 내용은 상황에 맞는다.

---

## Empty State에 일러스트를 넣을까?

빈 화면을 보면 허전하다.

그래서 자연스럽게

```text
이미지 하나 넣어야 하나?
```

라는 생각이 든다.

일러스트는 도움이 될 수 있다.

특히 첫 사용 화면에서는

```text
아직 아무것도 없음
```

이라는 부정적인 느낌을 줄이고

조금 더 친근하게 만들 수 있다.

예를 들어

```text
[작은 쿠폰 일러스트]

아직 등록한 혜택이 없어요.
```

처럼 사용할 수 있다.

---

## 하지만 그림이 Empty State의 목적은 아니었다

그림이 예쁘다고 해서 좋은 Empty State가 되는 것은 아니다.

가장 중요한 것은

```text
현재 상태

+

다음 행동
```

이다.

일러스트가 너무 크면 오히려

```text
그림
```

이 가장 먼저 보이고

정작

```text
왜 비어 있는지
```

는 잘 보이지 않을 수 있다.

그래서 이미지 역시 정보 우선순위를 따라야 했다.

---

## Empty State 일러스트는 보조 역할로

내가 생각하는 순서는 대략 이렇다.

```text
1. 상태 이해

2. 다음 행동

3. 분위기를 위한 이미지
```

이다.

즉

```text
일러스트가 없으면
Empty State가 성립하지 않는다.
```

가 아니다.

텍스트만으로 충분하면 굳이 이미지를 넣지 않아도 된다.

---

## 아이콘 하나만으로도 충분할 수 있다

예를 들어 검색 결과가 없을 때

큰 일러스트 대신

```text
🔍
```

또는 간단한 검색 아이콘을 사용할 수 있다.

페이지 전체 분위기에 따라

```text
작은 아이콘

짧은 제목

한 줄 설명
```

만으로도 충분하다.

중요한 것은 빈 공간을 억지로 채우지 않는 것이다.

---

## Empty State에서는 화면 가운데 정렬이 잘 어울릴 때가 있었다

「화면 정렬과 시선의 흐름」에서 중앙 정렬은 긴 정보에서 읽기 어려울 수 있다고 했다.

하지만 Empty State는 정보량이 적다.

```text
아이콘

제목

설명

버튼
```

정도다.

그래서 화면 중앙에 배치하면

```text
현재 보여줄 콘텐츠가 없다.
```

는 상태를 명확하게 보여주기 좋다.

특히 독립적인 빈 화면에서는 중앙 정렬이 자연스럽다.

---

## 목록 일부만 비어 있다면 중앙 정렬이 아닐 수도 있다

예를 들어 홈 화면의 일부 영역만 비어 있다고 해보자.

```text
현재 위치

주변 카페 목록

내 혜택
→ 없음

추천
```

여기에서 `내 혜택` 영역만 비었다고

페이지 전체 중앙에 Empty State를 띄울 수는 없다.

해당 Section 안에서

```text
등록된 혜택이 없어요.

[등록하기]
```

정도로 작게 처리할 수 있다.

즉 Empty State의 크기도

```text
페이지 전체가 비었는가?

일부 영역만 비었는가?
```

에 따라 달라진다.

---

## Full-page Empty State와 Section Empty State

이렇게 나누면 이해하기 쉬웠다.

### Full-page Empty

페이지의 핵심 콘텐츠가 전혀 없는 경우.

```text
내 기록
↓
기록 0개
```

화면 중앙에 Empty State를 크게 보여줄 수 있다.

### Section Empty

페이지의 일부만 비어 있는 경우.

```text
Home
├─ 주변 카페 있음
├─ 내 혜택 없음
└─ 다른 정보 있음
```

작은 안내 형태가 더 자연스러울 수 있다.

---

## Empty State에서 Primary Action은 특히 강력했다

일반 화면에는 버튼이 많을 수 있다.

하지만 Empty State에는 콘텐츠가 없다.

그래서 버튼 하나만 있어도 굉장히 강하게 보인다.

```text
아직 등록한 혜택이 없어요.

[혜택 등록하기]
```

이 상태에서는 사용자가 다음 행동을 고민할 필요가 거의 없다.

Empty State가 좋은 이유 중 하나가

**사용자에게 하나의 행동을 아주 명확하게 제안할 수 있다는 것**이었다.

---

## 그렇다고 버튼을 여러 개 넣으면 다시 복잡해진다

예를 들어

```text
아직 혜택이 없어요.

[혜택 등록하기]

[지원 브랜드 보기]

[사용법 보기]

[주변 카페 보기]
```

버튼이 네 개 생겼다.

빈 화면은 단순했는데 다시 선택지가 많아졌다.

그래서 Empty State에서는 특히

```text
가장 자연스러운 다음 행동 하나
```

를 먼저 찾는 것이 좋았다.

---

## 사용자가 해결할 수 없는 Empty State도 있다

예를 들어 시스템 자체에 아직 콘텐츠가 없는 경우다.

사용자가 버튼을 눌러 해결할 수 없다.

그렇다면 억지로 CTA를 만들 필요가 없다.

```text
아직 공개된 공지가 없습니다.

새로운 소식이 등록되면
여기에서 확인할 수 있어요.
```

정도로 끝낼 수 있다.

다음 행동이 없다는 것도 정상이다.

---

## 부정적인 문구보다 현재 상태를 자연스럽게 설명한다

Empty State 문구를

```text
없음

실패

데이터 없음
```

처럼 너무 시스템적으로 표현할 필요는 없다.

예를 들어

```text
혜택 없음
```

보다

```text
아직 등록한 혜택이 없어요.
```

가 자연스럽다.

```text
기록 없음
```

보다

```text
첫 러닝 기록을 기다리고 있어요.
```

처럼 표현할 수도 있다.

다만 지나치게 감성적으로 만들어 의미가 모호해져서는 안 된다.

---

## 귀엽게 쓰느라 의미를 숨기지 않는다

예를 들어

```text
여기는 아직 조용하네요 🌱
```

라는 문구가 있다.

예쁘다.

하지만

```text
뭐가 없는 거지?
```

가 바로 이해되지 않을 수도 있다.

그래서

```text
아직 러닝 기록이 없어요.

첫 러닝을 시작하면
기록이 여기에 저장됩니다.
```

처럼 명확성을 먼저 두는 편이 좋았다.

감성적인 문구는 그다음이다.

---

## "아직"이라는 표현이 유용했다

```text
데이터가 없습니다.
```

보다

```text
아직 등록한 혜택이 없어요.
```

라고 하면 느낌이 조금 달라진다.

```text
현재는 없지만
앞으로 생길 수 있다.
```

는 의미가 자연스럽게 담긴다.

첫 사용 상태에서 특히 잘 어울린다.

---

## Search Empty에서는 사용자가 입력한 내용을 보여주는 것도 좋았다

예를 들어

```text
'판교역'에 대한 검색 결과가 없습니다.
```

라고 하면

사용자는

```text
내가 무엇을 검색했는지
```

를 다시 확인할 수 있다.

단순히

```text
검색 결과 없음
```

보다 상황을 이해하기 쉽다.

---

## Filter Empty에서는 초기화 버튼이 유용했다

필터가 여러 개 적용되어 결과가 사라졌다면

사용자가 직접 하나씩 해제하게 할 필요가 없을 수도 있다.

```text
현재 필터 조건에 맞는 카페가 없어요.

조건을 조금 넓혀보세요.

[필터 초기화]
```

처럼 바로 해결할 방법을 제공한다.

이것은 좋은 Empty State의 대표적인 구조였다.

```text
문제 설명
↓
해결 방법
↓
행동
```

---

## Empty State를 숨기려고 가짜 데이터를 넣으면 안 됐다

디자인 화면은 데이터가 있어야 예뻐 보인다.

그래서 개발 중

```text
아무것도 없으면 허전하니까
샘플 카드 하나 그냥 보여줄까?
```

싶을 수 있다.

하지만 실제 데이터처럼 보이는 가짜 정보라면

사용자는 자신의 데이터라고 오해할 수 있다.

Demo나 Tutorial이라면 명확하게 표시해야 한다.

실제 사용자 데이터 영역에서는

빈 상태를 그대로 설계하는 편이 낫다.

---

## Skeleton과 Empty State도 다르다

Loading 화면에서 카드 모양의 Skeleton UI를 사용할 수 있다.

```text
██████████
██████
```

처럼 실제 콘텐츠가 들어올 위치를 미리 보여준다.

이것은

```text
조금 기다리면 콘텐츠가 나타남
```

이라는 의미다.

반대로 Empty State는

```text
기다려도 콘텐츠가 생기지 않음
```

이다.

사용자가 행동해야 하거나 현재 실제 데이터가 없는 상태다.

의미가 완전히 다르다.

---

## 개발에서도 상태를 명확하게 구분하는 것이 좋았다

예를 들어 React에서 단순하게

```text
if (!data) {
  return <EmptyState />;
}
```

라고 만든다면 문제가 생길 수 있다.

`data`가 없는 이유가

```text
Loading

Error

진짜 Empty
```

중 무엇인지 구분하지 않았기 때문이다.

개념적으로는

```text
if (loading)
  → Loading

if (error)
  → Error

if (data.length === 0)
  → Empty

else
  → Content
```

처럼 상태를 구분해야 한다.

UI 디자인에서 구분한 상태가 코드 구조에도 영향을 준다.

---

## Empty State를 미리 정의하면 개발도 편했다

디자인 단계에서

```text
데이터 없으면 나중에 생각
```

이라고 하면 개발자가 구현하다가 임의로 문구를 넣게 될 수 있다.

예를 들어

```text
No data
```

라고 끝낼 수도 있다.

하지만 기획이나 디자인 단계에서

```text
혜택 0개
→ "아직 등록한 혜택이 없어요."
→ [혜택 등록하기]
```

까지 정의하면

개발 단계에서도 기준이 명확하다.

---

## AI에게 화면을 만들게 할 때 Empty State도 요청해야 했다

Figma Make나 Claude Design에

```text
혜택 목록 화면 만들어줘.
```

라고 하면 대부분 데이터가 있는 예쁜 화면을 만든다.

```text
쿠폰 카드

스탬프 카드

브랜드 카드
```

가 가득 들어 있다.

하지만 실제 서비스에서는 처음 사용자가 빈 화면을 볼 수 있다.

그래서 별도로 요청한다.

```text
이 화면의 Empty State도 만들어줘.

아직 등록한 혜택이 없는 첫 사용자 상태다.

왜 비어 있는지 알려주고
'혜택 등록하기'를 Primary Action으로 보여줘.

새로운 기능은 추가하지 마.
```

이렇게 하면 정상 상태와 빈 상태를 같이 검토할 수 있다.

---

## 디자인할 때 상태별 Frame을 만들어두는 것도 좋았다

예를 들어

```text
Benefit List / Default

Benefit List / Loading

Benefit List / Empty

Benefit List / Error
```

처럼 만들 수 있다.

그러면 구현 단계에서

```text
이 화면은 Empty일 때 어떻게 보여야 하지?
```

를 다시 고민하지 않아도 된다.

또 상태끼리 비교하기도 쉽다.

---

## 모든 화면의 모든 상태를 처음부터 만들 필요는 없었다

여기서 또 욕심이 생길 수 있다.

```text
모든 페이지에

Loading

Empty

Error

Offline

Permission

Skeleton

Retry
```

를 처음부터 전부 디자인해야 할까?

작은 MVP라면 너무 많은 작업이 될 수 있다.

그래서 우선

```text
사용자가 실제로 자주 만날 가능성이 높은 상태

+

잘못 표현하면 큰 혼란이 생기는 상태
```

부터 정의하면 된다.

예를 들어 목록 화면의

```text
Loading

Empty

Error
```

정도부터 시작할 수 있다.

---

## Empty State를 디자인하면서 기능 부족도 발견할 수 있었다

예를 들어

```text
내 혜택이 없습니다.
```

화면을 만들었다.

그다음 생각한다.

```text
그럼 여기서 혜택 등록은 어떻게 하지?
```

그런데 등록 기능으로 가는 방법이 없다.

이때

```text
Empty State 문제가 아니라

서비스에 진입 경로 자체가 부족하다.
```

는 것을 발견하게 된다.

즉 Empty State를 디자인하다 보면

사용자 Flow의 구멍을 찾을 수도 있다.

---

## 삭제 후 Empty State도 생각해야 했다

처음에는 첫 사용자만 Empty State를 본다고 생각했다.

하지만 기존 사용자가 데이터를 모두 삭제해도 Empty가 된다.

예를 들어 혜택이 하나만 있었다.

```text
혜택 1개
↓
삭제
↓
혜택 0개
```

그 순간 화면은 Empty State로 바뀐다.

따라서 Empty State는

```text
첫 가입 전용 화면
```

이 아니다.

언제든 나타날 수 있는 정상 상태다.

---

## Empty State로 전환되는 순간도 자연스러워야 했다

사용자가 마지막 항목을 삭제한다.

그런데

```text
카드 사라짐
↓
화면 완전히 공백
```

이 되면 어색하다.

바로

```text
아직 등록한 혜택이 없어요.

[혜택 등록하기]
```

상태로 전환되면

사용자는

```text
삭제가 정상적으로 됐고
현재 데이터가 0개구나.
```

를 이해할 수 있다.

---

## 첫 사용과 모든 데이터 삭제 후 문구가 같아도 될까?

상황에 따라 같아도 된다.

현재 상태는 동일하기 때문이다.

```text
데이터 0개
```

다.

하지만 서비스에서 필요하다면 맥락에 따라 다르게 보여줄 수도 있다.

다만 지나치게 복잡하게 나눌 필요는 없다.

MVP라면 하나의 Empty State로 처리해도 충분할 수 있다.

---

## 사용자 데이터를 삭제한 직후에는 피드백도 필요할 수 있다

예를 들어 마지막 혜택을 삭제한 직후

바로

```text
아직 등록한 혜택이 없어요.
```

만 나타난다.

삭제가 성공한 것인지 조금 애매할 수 있다.

이럴 때

```text
혜택을 삭제했습니다.
```

Toast 등을 잠깐 보여주고

Empty State로 전환할 수 있다.

```text
삭제 완료
↓
Empty State
```

흐름이다.

---

## Empty State와 Toast의 역할은 다르다

### Toast

```text
방금 일어난 행동의 결과
```

예:

```text
혜택을 삭제했습니다.
```

### Empty State

```text
현재 페이지의 지속적인 상태
```

예:

```text
아직 등록한 혜택이 없어요.
```

둘은 같이 사용할 수도 있다.

---

## 접근성도 생각해야 했다

Empty State를 그림만으로 표현하면

```text
🗂
```

이미지를 이해하기 어려운 사용자에게 상태가 제대로 전달되지 않을 수 있다.

그래서 핵심 상태는 텍스트로도 표현하는 것이 좋다.

```text
아직 저장된 기록이 없습니다.
```

처럼 말이다.

일러스트는 보조 요소다.

---

## 색상만으로 Empty 이유를 구분하지 않는다

예를 들어

```text
회색
→ Empty

빨강
→ Error
```

만으로 구분하면 충분하지 않을 수 있다.

텍스트와 아이콘을 함께 사용해서

```text
아직 데이터가 없음
```

과

```text
데이터를 불러오지 못함
```

의 의미를 명확하게 구분하는 편이 좋다.

---

## Empty State 문구를 쓸 때 내가 확인할 것

문구를 만들면서 다음 순서로 생각하면 편했다.

```text
1. 지금 어떤 상태인가?

2. 왜 이 상태가 되었는가?

3. 사용자가 해결할 수 있는가?

4. 해결하려면 무엇을 해야 하는가?

5. 지금 설명할 필요 없는 정보는 무엇인가?
```

예를 들어

```text
상태
→ 혜택 0개

이유
→ 아직 등록하지 않음

해결 가능?
→ 가능

행동
→ 혜택 등록
```

이라면

```text
아직 등록한 혜택이 없어요.

보유한 혜택을 등록해보세요.

[혜택 등록하기]
```

가 된다.

---

## 검색 결과라면

```text
상태
→ 결과 0개

이유
→ 현재 검색 조건과 일치하지 않음

해결 가능?
→ 가능

행동
→ 검색어 변경
```

그러면

```text
검색 결과가 없어요.

검색어나 지역을 바꿔보세요.
```

가 된다.

별도 버튼이 없어도 충분할 수 있다.

---

## 오류라면

```text
상태
→ 데이터 표시 불가

이유
→ 요청 실패

해결 가능?
→ 다시 요청 가능

행동
→ Retry
```

결과는

```text
혜택을 불러오지 못했어요.

잠시 후 다시 시도해주세요.

[다시 시도]
```

가 된다.

이것은 Empty State가 아니라 Error State지만

비교해서 생각하면 차이가 명확하다.

---

## 좋은 Empty State인지 확인하는 가장 간단한 질문

화면을 처음 보는 사용자라고 생각하고 묻는다.

```text
1. 지금 왜 아무것도 없는지 알 수 있는가?

2. 오류와 정상적인 빈 상태를 구분할 수 있는가?

3. 다음에 무엇을 해야 하는지 알 수 있는가?
```

세 가지가 모두 해결된다면

기본적인 Empty State 역할은 하고 있다고 볼 수 있다.

---

## 내가 Empty State를 만들 때 지키고 싶은 기준

정리하면 다음과 같다.

```text
1. 빈 화면을 그대로 방치하지 않는다.

2. 왜 비어 있는지 알려준다.

3. 첫 사용 / 검색 없음 / 필터 없음 상태를 구분한다.

4. Empty와 Loading을 구분한다.

5. Empty와 Error를 구분한다.

6. 권한 부족을 Empty로 표현하지 않는다.

7. 사용자가 할 수 있는 다음 행동이 있다면 제공한다.

8. Primary Action은 가능하면 하나로 단순하게 만든다.

9. 모든 Empty State에 억지로 버튼을 넣지 않는다.

10. 설명을 지나치게 길게 쓰지 않는다.

11. 일러스트는 보조 역할로 사용한다.

12. 페이지 전체 Empty와 Section Empty를 구분한다.

13. 공통 Component를 사용하더라도 문구는 상황에 맞춘다.

14. 실제 데이터가 없는 상태를 개발 전에 미리 정의한다.

15. AI로 화면을 만들 때 Empty State도 함께 요청한다.
```

---

## Empty State 체크리스트

조금 더 실무적으로 보면 이렇게 확인할 수 있다.

```text
□ 데이터가 0개일 때 화면이 있는가?

□ 왜 0개인지 알 수 있는가?

□ 로딩 중 화면과 구분되는가?

□ 오류 화면과 구분되는가?

□ 권한 문제와 구분되는가?

□ 사용자가 다음 행동을 할 수 있는가?

□ 버튼이 너무 많지는 않은가?

□ 설명이 너무 길지는 않은가?

□ 모바일에서도 자연스럽게 보이는가?

□ 일부 Section만 비어 있을 때도 대응하는가?
```

이런 체크리스트를 만들어두면

기능 구현 후

```text
아, 데이터 없을 때 화면 안 만들었네.
```

를 조금 줄일 수 있다.

---

## 처음에는 정상 화면만 디자인했다

처음 UI를 만들 때는 항상 가장 예쁜 상태부터 만들었다.

```text
데이터가 충분히 있고

텍스트 길이도 적당하고

이미지도 있고

오류도 없는 상태
```

다.

디자인하기 가장 쉽다.

하지만 실제 사용자는 항상 이런 상태만 보지 않는다.

```text
데이터가 없고

검색 결과가 없고

인터넷이 느리고

권한을 거절하기도 한다.
```

서비스는 이런 순간에도 사용자가 상황을 이해할 수 있어야 했다.

---

## 그래서 화면 하나가 사실 여러 화면이었다

예를 들어 `내 혜택` 하나를 만든다고 해도

```text
내 혜택 / Loading

내 혜택 / Default

내 혜택 / Empty

내 혜택 / Error
```

가 있을 수 있다.

처음에는 페이지 하나라고 생각했는데

실제로는 여러 상태를 가진 하나의 페이지였다.

이 관점이 생기니

UI를 보는 방식도 달라졌다.

---

## Empty State는 서비스의 완성도를 보여주는 부분이었다

정상 데이터가 있는 화면은 대부분 신경 써서 만든다.

사용자가 가장 많이 볼 것이라고 생각하기 때문이다.

하지만 Empty State를 만나면

서비스를 얼마나 세밀하게 만들었는지가 드러난다.

```text
아무것도 없는 흰 화면
```

과

```text
현재 상태를 설명하고
다음 행동을 알려주는 화면
```

은 차이가 크다.

작은 부분이지만

사용자 입장에서는

```text
이 서비스가 정상적으로 작동하고 있다.
```

는 신뢰를 줄 수 있다.

---

## 마무리

처음에는 Empty State를

```text
데이터가 없을 때
대충 보여주는 화면
```

정도로 생각했다.

하지만 실제로 정리해보니 역할이 더 많았다.

```text
현재 상태 설명

↓

왜 비어 있는지 이해

↓

다음 행동 안내
```

를 담당한다.

특히 서비스를 처음 사용하는 사람에게는

Empty State가 사실상

```text
이 기능을 어떻게 시작하는지 알려주는 첫 화면
```

이 될 수도 있다.

그래서

```text
아무것도 없음
```

은 디자인할 것이 없는 상태가 아니었다.

오히려

> **아무것도 없기 때문에 무엇을 보여줄지 더 명확하게 결정해야 하는 상태**

였다.

그리고 Empty State까지 디자인하고 나면

다음에는 또 다른 문제가 생긴다.

Figma에서는 화면 하나를 기준으로 예쁘게 만들었지만

실제 사용자는 같은 크기의 화면만 사용하지 않는다.

```text
작은 모바일

큰 모바일

태블릿

노트북

큰 모니터
```

에서 모두 서비스를 사용할 수 있다.

화면이 좁아졌다고 단순히 모든 요소를 작게 줄이면 되는 것도 아니었다.

정보 순서와 레이아웃 자체가 달라져야 할 때도 있다.
