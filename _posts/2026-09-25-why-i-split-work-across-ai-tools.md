처음 AI를 사용했을 때는 하나만 잘 사용하면 된다고 생각했다.

ChatGPT를 사용하고 있다면 굳이 Claude까지 사용할 이유가 있을까?

Claude를 사용한다면 Gemini까지 열어볼 필요가 있을까?

처음에는 이렇게 생각했다.

```text
AI
↓
질문
↓
답변
```

결국 모두 비슷한 일을 하는 것처럼 보였다.

실제로 지금은 ChatGPT, Claude, Gemini 모두

```text
질문 답변

코드 작성

자료 정리

문서 작성

이미지 이해

웹 정보 활용
```

같은 다양한 작업을 할 수 있다.

그래서

```text
ChatGPT는 이것만 가능

Claude는 이것만 가능

Gemini는 이것만 가능
```

처럼 완전히 분리해서 설명하기도 어렵다.

그런데 프로젝트를 계속 진행하면서 어느 순간부터 자연스럽게 AI를 나눠서 사용하고 있었다.

```text
기획을 정리할 때는 ChatGPT

실제 코드를 수정할 때는 Claude

다른 관점에서 다시 확인할 때는 Gemini
```

같은 식이다.

이것은

```text
어떤 AI가 가장 뛰어난가?
```

를 비교한 결과라기보다

> **각 작업을 어디에서 하는 것이 내가 가장 편한가?**

를 기준으로 조금씩 역할이 생긴 결과였다.

이번 글에서는 내가 여러 AI를 왜 나눠서 사용하게 됐는지 정리해보려고 한다.

---

## 처음에는 ChatGPT 하나로 거의 모든 것을 했다

개발 공부를 시작하면서 AI에게 물어볼 일이 정말 많았다.

```text
이 코드가 왜 안 되지?

Git에서 이 명령은 무슨 뜻이지?

이 화면은 어떻게 만들지?

DB 구조는 어떻게 잡아야 하지?

이 프로젝트 기획 괜찮은가?
```

궁금한 것이 생길 때마다 ChatGPT에 질문했다.

특히 처음 공부할 때는

```text
모르는 개념
↓
질문
↓
설명
↓
다시 질문
```

을 반복할 수 있다는 점이 편했다.

검색하다가 모르는 용어가 또 나오면 다시 검색해야 하는 것과 달리

```text
아직 잘 모르겠는데
더 쉽게 설명해줘.
```

라고 바로 이어갈 수 있었다.

그래서 처음에는

```text
ChatGPT
=
검색 + 과외 + 개발 도움
```

정도로 사용했던 것 같다.

---

## 프로젝트가 커지면서 상황이 조금 달라졌다

간단한 코드 한두 줄을 물어볼 때는 채팅만으로도 충분했다.

그런데 실제 프로젝트를 만들기 시작하니 상황이 달라졌다.

프로젝트 안에는

```text
수십 개의 파일

폴더 구조

환경 변수

DB

API

인증

Git

배포 설정
```

이 연결되어 있었다.

예를 들어

```text
이 페이지의 버튼을 수정해줘.
```

라는 요청도 실제로는

```text
기존 Component 확인

현재 스타일 확인

연결된 페이지 확인

타입 확인

Build 확인
```

등이 필요할 수 있다.

이 단계부터 단순히 코드를 복사해서 AI에게 보여주는 방식보다

**AI가 실제 프로젝트를 읽으면서 작업하는 방식**

이 필요해졌다.

그 과정에서 Claude Code를 많이 사용하게 됐다.

---

## Claude는 실제 코드 작업에 많이 사용하게 됐다

Claude Code는 단순히 코드 예제를 알려주는 채팅 도구와는 조금 다르다.

실제 Repository와 Terminal 환경에서 코드베이스를 읽고, 파일을 수정하고, 테스트나 명령을 실행하면서 작업할 수 있는 Agentic Coding 도구다. [Anthropic](https://code.claude.com/docs/en/overview) 역시 Claude Code를 실제 코드베이스를 탐색하고, 코드를 작성·수정하고, 테스트하고, Git 작업까지 이어갈 수 있는 도구로 설명하고 있다.

내가 프로젝트에서 Claude를 많이 사용하게 된 이유도 이 부분이었다.

예를 들어 내가

```text
설정 화면 구현해줘.
```

라고 요청한다면 단순히 새로운 코드를 만들어주는 것이 아니라

```text
현재 프로젝트 확인
↓
기존 Component 확인
↓
필요한 파일 수정
↓
Type Check
↓
Build 확인
```

까지 하나의 작업 흐름으로 이어갈 수 있었다.

---

## ChatGPT와 Claude의 가장 큰 차이는 내 작업 방식에 있었다

여기서 중요한 것은

```text
ChatGPT는 코딩을 못한다.

Claude는 코딩을 잘한다.
```

라는 의미가 아니다.

두 AI 모두 코딩을 도와줄 수 있다.

내가 나눠서 사용하는 이유는 **사용하는 위치와 목적이 달랐기 때문**이다.

나는 ChatGPT에서는 주로

```text
무엇을 해야 하는가?
```

를 많이 고민한다.

Claude Code에서는

```text
그러면 실제 프로젝트에서
어떻게 구현할 것인가?
```

를 맡기는 경우가 많았다.

즉 내 작업 흐름에서는

```text
ChatGPT
→ 결정과 정리

Claude
→ 실제 실행
```

에 가까워졌다.

---

## 예를 들어 기능 하나를 만든다면

새로운 기능을 추가한다고 해보자.

처음에는 바로 코드를 작성하지 않는다.

먼저 ChatGPT에서 이런 질문을 한다.

```text
이 기능이 정말 필요한가?

MVP에 포함해야 할까?

데이터 구조는 어떻게 잡는 게 좋을까?

사용자는 어떤 흐름으로 사용하게 될까?
```

여기서 기능을 정리한다.

```text
기획
↓
범위 확정
↓
정책 확정
```

그다음 Claude Code로 간다.

```text
현재 문서를 기준으로
이 기능을 구현해줘.

문서에 없는 기능은 추가하지 마.
```

그러면 Claude가 실제 프로젝트를 확인하고 코드를 수정한다.

---

## 이렇게 나누니 AI가 기획까지 마음대로 바꾸는 일이 줄었다

AI에게

```text
좋은 서비스 만들어줘.
```

라고 하면 굉장히 많은 것을 제안한다.

```text
즐겨찾기

알림

추천

리뷰

커뮤니티

통계
```

대부분 나쁜 아이디어는 아니다.

문제는 **지금 필요한가**다.

기획과 구현을 한 AI에게 한 번에 맡기면

```text
기능 구현 중
↓
AI가 개선 기능 제안
↓
괜찮아 보여서 추가
↓
범위 증가
```

가 반복될 수 있다.

그래서 나는 먼저 ChatGPT와

```text
무엇을 만들지
```

를 충분히 결정하고,

그 결과를 Claude에게 넘겨

```text
결정된 것을 구현
```

하게 하는 방식이 편했다.

---

## 문서를 먼저 만들고 Claude에게 넘기는 방식

이 방식은 프로젝트를 진행하면서 특히 많이 사용했다.

```text
ChatGPT
↓
기획 논의
↓
문서 정리
↓
확정

Claude
↓
문서 읽기
↓
구현
```

이렇게 하면 Claude에게 매번 프로젝트 전체를 다시 설명하지 않아도 된다.

Claude Code에서는 `CLAUDE.md` 같은 프로젝트 지침 파일이나 Skills 등을 이용해 코드베이스 규칙과 작업 방식을 지속적으로 제공할 수도 있다. [Anthropic](https://code.claude.com/docs/en/features-overview) 역시 `CLAUDE.md`, Skills, Plugins, Sub-agent 등을 프로젝트 맥락과 작업 규칙을 제공하는 방법으로 안내하고 있다.

이런 구조를 사용하면서

```text
채팅에서 한 말

vs

실제 프로젝트 규칙
```

이 서로 달라지는 문제도 줄일 수 있었다.

---

## Claude Design은 또 역할이 달랐다

Claude를 코드에서만 사용하는 것은 아니었다.

앞 글에서 정리했던 것처럼 Claude Design에서는

```text
기획
↓
디자인 시안
↓
수정
↓
비교
```

과정을 빠르게 진행할 수 있다.

Claude Design은 Claude와 대화하면서 디자인, 프로토타입, 슬라이드 등 시각적 결과물을 만드는 도구로 2026년에 공개됐다.

그래서 Claude 안에서도 역할을 나눠 생각하게 됐다.

```text
Claude Design
→ 디자인 탐색

Claude Code
→ 실제 코드 구현
```

이다.

---

## 그렇다면 ChatGPT는 어디에 가장 많이 사용할까?

내 경우에는 ChatGPT를 가장 넓게 사용한다.

특정 작업 하나를 담당한다기보다

```text
프로젝트 전체를 놓고 같이 생각하는 공간
```

에 가깝다.

예를 들면

```text
서비스 아이디어 검토

문제 정의

기능 우선순위

화면 구성

DB 설계 방향

오류 원인 이해

Git 작업 순서

배포 과정 정리

블로그 글 작성

프로젝트 회고
```

등이다.

작업 중간에도

```text
Claude가 이렇게 했는데 맞는가?

이 구조가 이상하지 않은가?

다음에는 무엇을 해야 하는가?
```

를 다시 질문한다.

---

## ChatGPT는 내게 일종의 중간 검토 단계가 됐다

예를 들어 Claude에게 DB 작업을 시켰다고 하자.

Claude가

```text
migration 생성 완료

schema 적용 완료

build 통과
```

라고 알려준다.

그 내용을 다시 가져와 ChatGPT에서

```text
현재 이 상태면 다음 단계로 넘어가도 되는지 검토해줘.
```

라고 할 수 있다.

그러면

```text
구현하는 AI

+

검토하는 AI
```

가 분리된다.

같은 AI에게

```text
네가 한 거 제대로 한 거 맞아?
```

라고 물어보는 것보다

다른 관점으로 한 번 더 보는 효과가 있다.

---

## 같은 질문을 다른 AI에게 해보는 이유

AI가 항상 맞는 것은 아니다.

특히 내가 잘 모르는 분야라면 문제가 있다.

AI가 자신 있게 답하면

```text
아 그런가 보다.
```

하고 넘어가기 쉽다.

그래서 중요한 결정에서는 가끔 같은 내용을 다른 AI에게도 물어본다.

예를 들어

```text
이 DB 구조에 문제가 있는가?
```

를 ChatGPT에서 검토하고,

Gemini에서도 다시 확인해볼 수 있다.

여기서 목적은

```text
두 AI가 같은 말을 했으니까 무조건 정답
```

이라고 판단하는 것이 아니다.

오히려

```text
서로 다른 부분이 무엇인지
```

를 찾는 것이다.

---

## 두 AI가 다르게 말할 때가 더 도움이 됐다

예를 들어

```text
ChatGPT
→ A 방식 추천

Gemini
→ B 방식도 고려 필요
```

라고 한다면 그때부터 확인할 것이 생긴다.

```text
왜 의견이 다르지?

전제 조건이 다른가?

어느 쪽이 내 프로젝트에 맞나?

공식 문서는 뭐라고 하지?
```

이 과정을 거치면서 단순히 AI의 답을 받아들이는 것이 아니라

**내가 직접 판단할 근거를 찾게 된다.**

그래서 다른 AI의 존재는

```text
첫 AI의 답을 대신할 답
```

이라기보다

```text
첫 답을 다시 생각하게 만드는 두 번째 관점
```

으로 유용했다.

---

## Gemini는 두 번째 관점으로 자주 사용하게 됐다

내가 Gemini를 사용하는 이유도 이쪽에 가깝다.

예를 들어 ChatGPT에서 프로젝트 구조를 오래 논의했다면

같은 맥락 안에서 생각이 한 방향으로 굳어질 수 있다.

그때 Gemini에 필요한 정보만 전달하고

```text
이 구조에서 놓친 문제가 있는지
독립적으로 검토해줘.
```

라고 할 수 있다.

그러면 지금까지의 대화 흐름에 끌려가지 않은 새로운 관점에서 답을 받을 수 있다.

---

## 리서치에서는 Gemini를 함께 확인할 이유도 있다

Gemini에는 웹을 여러 단계로 탐색해 결과를 보고서 형태로 구성하는 Deep Research 기능이 있다. [Google](https://blog.google/innovation-and-ai/models-and-research/gemini-models/next-generation-gemini-deep-research/)은 2026년에도 Deep Research를 장기적인 웹·자료 조사에 활용하는 기능으로 계속 확장하고 있다.

그래서 자료를 많이 확인해야 하는 작업이라면

```text
ChatGPT 검색 결과

Gemini Deep Research 결과

공식 문서
```

를 함께 볼 수도 있다.

중요한 것은

```text
Gemini가 검색에 강하니까
Gemini 답이 정답
```

이라고 생각하는 것이 아니다.

어떤 AI를 사용하든 중요한 정보는 결국 원본 출처를 확인하는 것이 좋다.

---

## Google 서비스와 연결되는 것도 Gemini의 특징이었다

Gemini는 Google Workspace와 연결해서 Gmail, Docs, Drive 등의 정보를 찾거나 요약할 수 있고 Calendar, Tasks, Keep 같은 서비스와도 연결할 수 있다. 사용 가능 여부는 계정과 설정에 따라 달라질 수 있다.

그래서 Google 환경에서 자료를 많이 관리한다면

```text
Gmail

Drive

Docs

Calendar
```

와 연결되는 작업에서 Gemini를 활용할 이유가 생길 수 있다.

이것도

```text
Gemini가 무조건 더 좋다.
```

라는 의미보다는

**내 자료가 어디에 있느냐에 따라 편한 AI가 달라질 수 있다는 예시**에 가깝다.

---

## ChatGPT에서도 웹 검색은 가능하다

이 부분을 잘못 이해하면

```text
검색
→ Gemini
```

로만 나누게 된다.

하지만 ChatGPT도 웹 검색을 통해 최신 정보를 찾고 출처 링크와 함께 답변할 수 있다.

그래서 나는

```text
ChatGPT는 생각만 하고
Gemini는 검색만 한다.
```

처럼 완전히 나누지는 않는다.

필요하다면 ChatGPT에서도 직접 최신 정보를 확인한다.

결국 역할 구분은 기능 가능 여부보다는

```text
내가 어떤 작업 흐름에서
어느 도구를 쓰기 편한가
```

에 가깝다.

---

## 이미지 작업에서는 ChatGPT를 많이 사용한다

앞 글에서 정리했듯 나는 프로젝트에서 필요한

```text
로고

앱 아이콘

파비콘

일러스트

OG 이미지용 그래픽
```

등을 만들 때 ChatGPT Images를 활용할 수 있다.

현재 ChatGPT Images는 새로운 이미지 생성뿐 아니라 기존 이미지 편집, 투명 배경, 화면 비율 변경 등의 작업도 지원한다.

그래서 내 작업 흐름에서는

```text
이미지 아이디어
↓
ChatGPT
↓
여러 시안
↓
수정
↓
Figma / 프로젝트 적용
```

같은 방식이 자연스럽게 생겼다.

---

## ChatGPT 프로젝트 기능도 장기 작업에 잘 맞았다

프로젝트를 몇 주 동안 진행하면 대화가 한두 개로 끝나지 않는다.

```text
기획

DB

디자인

Git

인증

배포

회고
```

가 계속 이어진다.

ChatGPT의 Projects는 특정 작업에 대한 채팅, 파일, 지침과 관련 맥락을 한 공간에 모아서 장기간 이어가는 용도로 제공되고 있다.

그래서 하나의 프로젝트에 대해 계속 의사결정을 해야 할 때

```text
프로젝트의 전체 맥락을 가지고 대화하는 공간
```

으로 활용하기 편했다.

---

## 내 작업에서 세 AI를 간단히 나누면

현재 내가 사용하는 흐름을 아주 단순하게 정리하면 이런 느낌이다.

| 도구      | 내가 주로 사용하는 역할                     |
| ------- | --------------------------------- |
| ChatGPT | 기획, 개념 이해, 구조 정리, 검토, 글 작성, 이미지   |
| Claude  | 실제 프로젝트 코드 수정, 구현, 디자인 시안 및 코드 작업 |
| Gemini  | 별도 관점의 검토, 추가 리서치, Google 환경 활용   |

하지만 이 표를

```text
각 AI가 이것만 할 수 있다.
```

는 의미로 보면 안 된다.

세 AI의 기능은 상당히 겹친다.

이 표는 어디까지나

> **내가 현재 가장 편하게 사용하는 작업 위치**

를 정리한 것이다.

---

## 프로젝트 하나에서는 이런 흐름이 될 수 있다

예를 들어 새로운 서비스를 만든다고 해보자.

## 1. 아이디어 검토

```text
ChatGPT

문제 정의
타깃 사용자
핵심 기능
MVP 범위
```

을 정리한다.

---

## 2. 기획 검증

필요하면 Gemini에

```text
이 서비스 구조에서
놓친 문제나 반대 관점이 있는지 확인해줘.
```

라고 한다.

또 최신 시장이나 기술 정보가 필요하다면 자료도 조사한다.

---

## 3. 디자인

상황에 따라

```text
Figma

Figma Make

Claude Design

ChatGPT Images
```

를 사용한다.

여기에서도 역할을 나눈다.

```text
화면 구조
→ Figma

빠른 시안
→ Claude Design / Figma Make

서비스용 이미지
→ ChatGPT Images
```

정도로 사용할 수 있다.

---

## 4. 구현

기획과 디자인이 확정됐다면 Claude Code로 간다.

```text
현재 기획 문서를 읽고
디자인을 기준으로 구현해줘.

문서에 없는 기능은 추가하지 마.
```

그리고 실제 Repository에서 작업한다.

---

## 5. 구현 결과 검토

Claude가 작업한 내용을 다시 확인한다.

```text
Git diff

Build

실제 화면

DB 상태
```

등을 보고,

이해하기 어려운 부분이 있다면 ChatGPT에 가져와 다시 설명을 듣는다.

---

## 6. 중요한 부분은 다시 검증

예를 들어 인증이나 DB처럼 중요한 구조라면

```text
ChatGPT
+
Gemini
+
공식 문서
```

를 이용해서 다시 확인할 수 있다.

결국 최종 판단은 사람이 한다.

---

## AI끼리 서로 검토하게 하는 것도 유용했다

예를 들어 Claude가 코드를 작성했다.

그 코드를 그대로 ChatGPT에 가져와

```text
이 구현에서 문제가 될 수 있는 부분을 찾아줘.
```

라고 할 수 있다.

반대로 ChatGPT에서 만든 기획을 Claude에게

```text
실제 구현 관점에서 문제가 있는지 검토해줘.
```

라고 할 수도 있다.

Gemini에는

```text
두 의견에서 놓친 부분이 있는지 봐줘.
```

라고 할 수 있다.

이렇게 보면

```text
ChatGPT vs Claude vs Gemini
```

가 아니라

```text
ChatGPT
↕
Claude
↕
Gemini
```

가 된다.

서로 경쟁시키기보다 서로 다른 검토 단계로 사용하는 것이다.

---

## 하지만 무조건 여러 AI에게 물어보는 것도 비효율적이었다

반대로 이런 문제가 생길 수도 있다.

질문 하나가 생길 때마다

```text
ChatGPT 질문

Claude 질문

Gemini 질문

결과 비교
```

를 한다.

그러면 간단한 작업 하나에도 시간이 너무 많이 든다.

예를 들어

```text
CSS에서 가운데 정렬하는 법
```

을 세 AI에게 확인할 필요는 없다.

명확한 답이 있는 작은 문제라면 하나의 AI로 충분하다.

---

## 여러 AI를 사용하는 기준

그래서 나는 모든 질문을 여러 AI에게 물어보지 않는다.

다음과 같은 경우에 두 번째 AI를 사용하는 것이 더 의미 있다고 생각한다.

```text
중요한 구조 결정

답이 확실하지 않을 때

두 가지 방법 중 고민될 때

한 AI의 제안이 이상하게 느껴질 때

큰 비용이 드는 작업을 시작하기 전

최신 정보 확인이 중요할 때

내가 해당 분야를 잘 몰라
답을 스스로 검증하기 어려울 때
```

이런 경우라면 다른 관점이 가치가 있다.

---

## AI 답변이 다르면 다수결을 하지 않는다

세 AI에게 물어봤다고 해보자.

```text
ChatGPT
→ A

Claude
→ A

Gemini
→ B
```

그러면

```text
2 대 1이니까 A
```

로 결정하면 될까?

그렇지 않다.

AI 답변은 투표가 아니다.

중요한 것은

```text
왜 A인가?

왜 B인가?

각 답변이 가정한 조건은 무엇인가?
```

다.

예를 들어

```text
A는 MVP 기준

B는 확장성을 중요하게 본 구조
```

일 수도 있다.

그러면 어느 쪽이 맞는지는 내 프로젝트 상황에 따라 달라진다.

---

## 최종 근거가 필요한 것은 공식 문서로 돌아간다

AI들이 서로 다른 답을 하거나

환경 변수, API, 인증, 프레임워크 버전처럼 정확성이 중요한 내용이라면

결국 공식 문서를 확인한다.

```text
AI
↓
가능한 답 찾기
↓
공식 문서
↓
확인
```

의 순서다.

나는 AI를

```text
공식 문서를 대신하는 존재
```

보다

```text
무엇을 확인해야 하는지 빠르게 찾게 해주는 도구
```

로 보는 편이 더 안전하다고 생각한다.

---

## AI를 여러 개 쓰면 생기는 가장 큰 문제 — 맥락이 나뉜다

여러 AI를 사용하는 데 장점만 있는 것은 아니다.

가장 큰 문제는

```text
ChatGPT에서 결정한 것을

Claude는 모른다.
```

는 것이다.

예를 들어 ChatGPT와 한 시간 동안

```text
이 기능은 제거한다.

로그인은 이 방식으로 한다.

MVP에는 리뷰가 없다.
```

라고 결정했다고 하자.

Claude에게 아무 설명 없이

```text
카페 앱 만들어줘.
```

라고 하면 다시 일반적인 카페 앱을 생각한다.

```text
리뷰

별점

즐겨찾기
```

를 추가할 수 있다.

---

## 그래서 AI 사이에 전달할 기준이 필요했다

가장 좋은 방법 중 하나가 문서였다.

```text
ChatGPT에서 기획
↓
기획 문서에 기록
↓
Claude가 문서 읽음
```

이렇게 한다.

중요한 결정이 채팅 안에서만 존재하지 않도록 만드는 것이다.

예를 들면

```text
01-problem.md

02-workflow.md

03-requirements.md

04-features.md

05-policy.md
```

같은 식으로 문서를 만들 수 있다.

그러면 AI가 바뀌어도 기준은 같다.

---

## AI보다 문서가 Source of Truth가 된다

이 구조가 만들어지면 중요한 변화가 생긴다.

```text
ChatGPT가 이렇게 말했다.

Claude가 저렇게 말했다.
```

가 기준이 아니다.

```text
현재 프로젝트 문서에 무엇이 적혀 있는가?
```

가 기준이 된다.

AI가 문서와 다른 기능을 제안하면

```text
좋은 제안인가?
```

를 먼저 보는 것이 아니라

```text
현재 범위에 포함되어 있는가?
```

를 확인한다.

필요하다면 문서를 먼저 수정하고 구현한다.

---

## 디자인도 마찬가지였다

디자인을 여러 AI에서 수정하다 보면

```text
Figma v1

Claude Design v2

ChatGPT 제안 v3
```

처럼 갈라질 수 있다.

그러면 개발 단계에서

```text
어떤 디자인이 최신이지?
```

가 된다.

그래서 최종 디자인을 정한 뒤에는

```text
이 디자인이 현재 Source of Truth다.
```

라고 정하는 것이 중요했다.

AI는 여러 안을 만드는 데 사용하고,

최종 기준은 하나로 만든다.

---

## 한 작업을 여러 AI가 동시에 수정하게 하지 않으려고 했다

예를 들어 Claude가 프로젝트 코드를 수정하고 있는데

같은 Repository를 다른 AI에게도 동시에 수정하게 한다면

```text
AI A
→ Component 수정

AI B
→ 같은 Component 수정
```

처럼 충돌할 수 있다.

그래서 역할을 나눌 때도

```text
검토

vs

실제 수정
```

을 구분하는 것이 좋다.

예를 들면

```text
Claude
→ 코드 수정

ChatGPT
→ 결과 검토
```

처럼 한다.

검토하는 AI는 코드를 직접 건드리지 않는다.

---

## 비용과 사용량도 이유가 됐다

AI를 사용하다 보면 이용 한도도 있다.

특히 큰 코드베이스를 계속 읽거나 긴 작업을 반복하면 사용량이 커질 수 있다.

그래서 아주 간단한 질문까지 개발 Agent에게 맡기는 것은 아까울 수 있다.

예를 들어

```text
git pull과 git pull origin main 차이
```

를 이해하고 싶다면 일반 채팅에서 설명을 듣는 것이 훨씬 간단하다.

반대로

```text
현재 Repository의 브랜치 상태를 확인하고
충돌 없이 main을 동기화해줘.
```

라면 실제 Repository를 볼 수 있는 Coding Agent가 더 적합하다.

즉 작업의 크기에 맞는 도구를 사용하는 것이다.

---

## 같은 AI도 작업 모드가 다르다

사실 이제는

```text
ChatGPT

Claude

Gemini
```

라는 이름만으로 도구를 구분하는 것도 점점 어려워지고 있다.

하나의 서비스 안에도 여러 기능이 있기 때문이다.

예를 들어 내가 사용하는 흐름만 봐도

```text
Claude
├─ 일반 대화
├─ Claude Design
└─ Claude Code
```

가 있다.

ChatGPT도

```text
일반 대화

웹 검색

이미지 생성

Projects
```

처럼 작업 방식이 달라진다. ChatGPT Images는 생성과 편집을 지원하고, Projects는 파일·채팅·지침을 하나의 장기 작업 공간에 모으는 기능을 제공한다.

Gemini 역시

```text
일반 대화

Deep Research

Connected Apps
```

등으로 나눌 수 있다.

결국 앞으로는

```text
어떤 AI를 쓸까?
```

만큼

```text
어떤 작업 모드를 쓸까?
```

도 중요해질 것 같다.

---

## AI 성능은 계속 바뀐다

이 글에서 가장 조심하고 싶은 부분이다.

```text
ChatGPT는 이것이 가장 좋다.

Claude는 저것이 가장 좋다.

Gemini는 이것이 약하다.
```

처럼 단정하고 싶지는 않다.

AI 모델과 제품 기능은 너무 빠르게 바뀐다.

예를 들어 ChatGPT의 이미지 기능도 2026년 9월에 Images 2.5로 업데이트됐고, Claude Design 역시 2026년에 새롭게 공개된 기능이다. Gemini의 Deep Research도 계속 새로운 모델과 기능으로 확장되고 있다.

몇 달 뒤에는 내가 사용하는 역할도 달라질 수 있다.

그래서 이 글은

```text
AI별 영원한 역할표
```

가 아니라

```text
현재 내가 프로젝트에서
AI를 사용하는 방법
```

에 가깝다.

---

## "최고의 AI"보다 "내 작업 흐름"을 찾는 것이 중요했다

처음에는 새로운 AI 모델이 나오면 궁금했다.

```text
이게 더 좋은가?

저게 더 똑똑한가?

이제 갈아타야 하나?
```

그런데 프로젝트를 하면서 생각이 조금 바뀌었다.

AI 성능 비교보다 더 중요한 것은

```text
내가 이 도구를 어디에 넣을 것인가?
```

였다.

아무리 좋은 AI여도

```text
매번 프로젝트를 처음부터 설명해야 하고

파일을 다시 전달해야 하고

결과를 다시 옮겨야 한다면
```

내 작업에서는 불편할 수 있다.

반대로 조금 다른 도구여도 내 Workflow에 잘 들어오면 계속 사용하게 된다.

---

## 내가 현재 사용하는 역할 분담

내 기준으로 다시 정리하면 다음과 같다.

## ChatGPT

```text
생각 정리

개념 공부

기획

문제 정의

의사결정 정리

자료 확인

구현 결과 검토

블로그 작성

이미지 제작
```

특히

```text
내가 지금 무엇을 해야 하는지
```

가 아직 명확하지 않을 때 많이 사용한다.

---

## Claude

```text
실제 코드베이스 확인

파일 수정

기능 구현

디버깅

Build / Test

디자인 시안

디자인 → 코드 연결
```

특히

```text
무엇을 할지는 정했고
이제 실제로 만들어야 할 때
```

많이 사용한다.

---

## Gemini

```text
두 번째 관점

독립적인 검토

추가 리서치

Google 서비스와 연결되는 작업
```

특히

```text
첫 번째 답을 그대로 믿기보다
다른 관점에서 다시 확인하고 싶을 때
```

활용한다.

---

## 그렇다고 항상 이 순서대로 사용하는 것은 아니다

상황에 따라 달라진다.

Claude와 이야기하다가 기획을 결정할 수도 있고,

ChatGPT에게 코드를 작성해달라고 할 수도 있고,

Gemini에서 먼저 아이디어를 얻을 수도 있다.

내가 역할을 나눈 이유는

```text
규칙
```

을 만들기 위해서가 아니다.

매번

```text
어디서 하지?
```

고민하는 비용을 줄이기 위해서다.

일종의 기본값이다.

## 내 기본 Workflow

현재 내 작업 방식을 가장 단순하게 표현하면 이렇다.

```text
문제 발생
↓
ChatGPT
↓
문제 이해 / 방향 결정
↓
필요하면 Gemini
↓
다른 관점 / 추가 검증
↓
기준 확정
↓
Claude
↓
실제 구현
↓
결과 확인
↓
ChatGPT 또는 Gemini
↓
다시 검토
```

물론 모든 작업에 이 과정을 적용하지는 않는다.

간단한 작업은 바로 끝낸다.

중요한 작업일수록 검토 단계를 추가한다.

## AI가 많아질수록 내가 해야 할 일이 사라지는 것은 아니었다

처음에는 AI를 여러 개 사용하면

```text
내가 할 일이 줄어든다.
```

고 생각했다.

실제로 직접 코드를 작성하거나 이미지를 만드는 시간은 줄었다.

하지만 다른 일이 생겼다.

```text
어떤 AI를 사용할지

무엇을 맡길지

어떤 결과가 맞는지

어느 제안을 받아들일지

무엇을 문서에 남길지
```

를 판단해야 했다.

AI가 많아질수록 중요한 것은

```text
AI 사용 능력
```

보다

```text
판단 기준
```

이라는 생각도 들었다.

---

## AI끼리 의견이 다를 때 결국 내가 선택해야 한다

ChatGPT는 A를 제안한다.

Claude는 B를 제안한다.

Gemini는 C도 가능하다고 한다.

그러면 누군가는 결정해야 한다.

그 결정은 AI를 하나 더 불러도 완전히 사라지지 않는다.

결국

```text
프로젝트 목적

현재 범위

내 기술 수준

일정

유지보수

사용자
```

를 기준으로 내가 선택해야 한다.

그래서 여러 AI를 사용하는 목적도

```text
결정을 AI에게 넘기기
```

가 아니라

```text
더 많은 근거를 가지고
내가 결정하기
```

에 가깝다.

---

## AI에게 끌려다니지 않기 위해 역할을 나눴다

처음에는 하나의 AI와 대화하다 보면 그 AI가 제시하는 방향을 계속 따라가게 되는 경우가 있었다.

```text
이 기능도 좋습니다.

이것도 추가할 수 있습니다.

이 구조가 더 좋습니다.
```

계속 듣다 보면 원래 기획보다 AI의 제안이 프로젝트를 이끌 수 있다.

그래서 역할을 나누고 기준 문서를 만들면서

```text
AI의 제안
```

과

```text
프로젝트 결정
```

을 조금 더 분리하게 됐다.

AI는 제안한다.

나는 검토한다.

문서에 반영된 뒤에야 프로젝트 기준이 된다.

---

## 결국 AI를 나눠 쓰는 이유

처음에는

```text
AI마다 장점이 달라서
```

라고 생각했다.

지금은 이유가 조금 더 많다.

```text
작업의 성격이 다르기 때문

실행과 검토를 분리하기 위해

다른 관점이 필요하기 때문에

프로젝트 맥락을 관리하기 위해

특정 서비스와 연결하기 위해

하나의 AI 제안에 끌려가지 않기 위해
```

서 여러 AI를 사용한다.

그리고 가장 중요한 것은

```text
AI를 여러 개 쓰는 것
```

자체가 아니다.

각 AI를 왜 사용하고 있는지 내가 알고 있는 것이다.

---

## 내가 지키고 싶은 AI 활용 기준

지금까지 사용하면서 만든 기준을 정리하면 다음과 같다.

```text
1. AI를 성능 순위만으로 선택하지 않는다.

2. 작업 성격에 맞는 도구를 선택한다.

3. 간단한 질문은 하나의 AI로 끝낸다.

4. 중요한 결정만 다른 AI로 다시 검토한다.

5. AI들의 의견이 다르다고 다수결하지 않는다.

6. 정확성이 중요한 정보는 공식 문서를 확인한다.

7. 기획과 실제 구현을 가능하면 구분한다.

8. 프로젝트 결정은 문서에 남긴다.

9. AI보다 프로젝트 문서를 Source of Truth로 사용한다.

10. 여러 AI가 동시에 같은 파일을 수정하게 하지 않는다.

11. AI가 추가한 기능을 자동으로 받아들이지 않는다.

12. 최신 모델이나 기능에 따라 역할은 언제든 바뀔 수 있다.

13. 최종 판단은 내가 한다.
```

---

## ChatGPT / Claude / Gemini 중 하나만 사용해도 될까?

물론 가능하다.

모든 프로젝트가 여러 AI를 필요로 하는 것은 아니다.

오히려 단순한 프로젝트라면 하나의 AI에서 끝까지 작업하는 것이 더 편할 수 있다.

여러 AI를 사용하면

```text
맥락 전달

문서 이동

답변 비교

버전 관리
```

같은 비용도 생긴다.

그래서

```text
AI를 많이 쓰는 것
=
AI를 잘 쓰는 것
```

은 아니다.

하나의 AI만으로 충분하다면 굳이 늘릴 필요도 없다.

---

## 내가 여러 AI를 사용하는 이유는 결국 "분업"이었다

개발 프로젝트에서 사람도 역할을 나눈다.

```text
기획

디자인

개발

리뷰
```

를 한 사람이 모두 할 수도 있지만,

역할을 나누면 각 단계에서 다른 관점으로 볼 수 있다.

내가 AI를 사용하는 방식도 점점 비슷해졌다.

```text
ChatGPT
→ 함께 생각하기

Claude
→ 실제 만들기

Gemini
→ 다른 시각에서 다시 보기
```

물론 이 경계는 고정되어 있지 않다.

필요하면 서로의 역할을 바꾼다.

하지만 기본 역할이 있으니 작업이 훨씬 덜 혼란스러웠다.

## 마무리

처음 AI를 사용할 때는

```text
어떤 AI가 가장 좋은가?
```

가 가장 궁금했다.

하지만 여러 프로젝트를 진행하면서 질문이 바뀌었다.

```text
이 작업은
어떤 AI에게 맡기는 것이 가장 편한가?
```

가 됐다.

그리고 더 나아가서는

```text
이 판단을 AI에게 맡겨도 되는가?

아니면 내가 먼저 기준을 정해야 하는가?
```

를 생각하게 됐다.

지금의 내 흐름은 대략 이렇다.

```text
ChatGPT
→ 생각하고 정리한다.

Claude
→ 실제로 만든다.

Gemini
→ 다른 관점에서 다시 확인한다.
```

하지만 가장 위에는 여전히 사람이 있다.

```text
나
│
├─ ChatGPT
├─ Claude
└─ Gemini
```

AI가 프로젝트를 끌고 가는 것이 아니라

내가 필요에 따라 AI를 선택해서 사용하는 구조다.

결국 여러 AI를 나눠 쓰는 이유는

```text
AI가 부족해서
```

가 아니라

**하나의 답에 의존하지 않고 각 도구를 필요한 위치에 배치하기 위해서**였다.

그리고 여기까지가 내가 디자인 과정에서 사용한 AI 도구들의 이야기다.

```text
07 Figma → Claude로 구현하기

08 Claude Design 활용

09 ChatGPT로 이미지·아이콘 만들기

10 ChatGPT / Claude / Gemini를 나눠 쓰는 이유
```

이제 도구를 어떤 식으로 사용하는지는 어느 정도 정리했다.

그다음부터는 더 중요한 문제가 남는다.

도구가 아무리 좋아도

```text
화면에서 무엇을 먼저 보여줄지

어디에 배치할지

사용자의 시선이 어디로 움직일지
```

를 모르면 사용하기 편한 UI를 만들기 어렵다.

이제

**실제로 화면을 구성할 때 필요한 UI/UX 기본 원리**를 공부해보려고 한다.

가장 먼저

```text
왜 어떤 화면은 한눈에 읽히고
어떤 화면은 어디부터 봐야 할지 모르겠는가?
```

를 알아보기 위해

화면의 정렬과 사용자의 시선 흐름부터 정리한다.
