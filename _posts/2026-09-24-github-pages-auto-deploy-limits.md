GitHub Pages를 사용하면서 가장 편하게 느껴졌던 부분은 `push` 이후 배포가 자동으로 이어진다는 점이었다.

로컬에서 수정하고,

commit하고,

GitHub에 push하면,

Pages가 사이트를 다시 빌드해 공개한다.

```text
로컬 수정
↓
commit
↓
push
↓
GitHub Pages 빌드·배포
↓
공개 사이트 반영
```

처음에는 `자동 배포`라는 말을 조금 넓게 이해했다.

하지만 블로그를 계속 운영하면서 알게 된 것은, GitHub Pages가 자동화해 주는 범위는 분명하다는 점이었다.

---

## GitHub Pages가 자동으로 해주는 일

현재 블로그처럼 정적 파일을 기반으로 하는 사이트에서는 GitHub Pages가 잘 맞았다.

예를 들어

* 새 포스트 추가
* 기존 글 수정
* HTML, CSS 수정
* 메뉴나 카테고리 변경
* 정적 이미지 추가

같은 작업은 저장소의 파일만 바뀌면 Pages가 새 사이트를 만들어 공개할 수 있다.

이 과정 덕분에 서버에 직접 접속해서 파일을 올리거나 매번 별도의 배포 명령을 실행할 필요가 없었다.

내가 직접 하는 핵심은 **변경사항을 GitHub에 올리는 것까지**였다.

---

## 자동 배포는 GitHub에 올라간 변경사항부터 시작된다

GitHub Pages는 내 로컬 파일을 직접 보고 있는 것이 아니다.

로컬에서 아무리 많이 수정해도 push하지 않았다면 공개 사이트는 바뀌지 않는다.

```text
로컬 수정
→ 내 컴퓨터 안에만 있음

commit
→ 로컬 Git에 기록됨

push
→ GitHub에 전달됨

Pages
→ 그 이후 빌드·배포 시작
```

그래서 자동 배포의 시작점은 `commit`이 아니라 **GitHub에 변경사항이 실제로 전달된 이후**라고 보는 편이 더 정확했다.

---

## 모든 브랜치가 바로 배포되는 것은 아니다

GitHub 저장소에 push했다고 해서 어느 브랜치든 공개 사이트가 바뀌는 것은 아니다.

Pages가 실제로 어떤 브랜치나 배포 방식과 연결되어 있는지가 중요하다.

운영 사이트와 연결되지 않은 브랜치에서 작업만 했다면 GitHub에는 코드가 있어도 공개 블로그에는 반영되지 않을 수 있다.

그래서

```text
GitHub에 코드가 있음
≠
현재 운영 사이트에 배포되는 코드
```

라고 구분해야 했다.

---

## 빌드까지 자동이지만 성공을 보장하지는 않는다

push 이후 Pages가 빌드와 배포를 자동으로 진행하더라도 실패할 수 있다.

파일 형식,

설정,

빌드 과정에 문제가 있다면 GitHub에는 commit이 정상적으로 올라가 있어도 배포가 실패할 수 있다.

```text
push 성공
→ GitHub가 변경사항을 받음

Pages 성공
→ 공개 사이트를 정상적으로 생성함
```

이 둘은 같은 단계가 아니다.

그래서 문제가 생겼을 때도 push를 반복하기보다 어디에서 실패했는지 먼저 확인하는 편이 맞다.

---

## 배포 성공과 실제 화면 정상도 같은 의미는 아니다

Pages에서 빌드가 성공했다고 해서 모든 것이 내가 원하는 모습이라는 뜻은 아니다.

예를 들어

* 내부 링크가 잘못됨
* 이미지 경로가 깨짐
* CSS가 예상과 다르게 적용됨
* 오타가 그대로 남아 있음

같은 문제는 배포 자체는 성공하면서도 실제 화면에서는 잘못 보일 수 있다.

특히 GitHub Pages의 프로젝트 경로를 사용하는 내 블로그에서는 로컬과 실제 배포 환경에서 경로 차이가 생길 수 있다.

그래서 마지막에는 실제 사이트에서 직접 확인하는 과정이 필요했다.

---

## 자동 배포가 해결해 주지 않는 것

GitHub Pages는 사이트를 공개해 주는 도구이지 블로그 전체를 관리해 주는 시스템은 아니다.

예를 들어 다음과 같은 일은 자동 배포 범위 밖이다.

```text
깨진 링크를 자동으로 수정하기

오타나 잘못된 내용을 판단하기

사용자 로그인 처리하기

DB에 데이터 저장하기

서버에서 권한 확인하기

비밀 API 키를 안전하게 처리하기
```

이런 기능들은 배포보다 애플리케이션 구조에 가까운 문제였다.

---

## 그래서 관리자 기능이 생각보다 커졌다

블로그 안에서 직접 글을 추가하거나 수정하는 관리자 기능을 고민했을 때 이 차이가 더 분명하게 보였다.

브라우저에서 글을 저장하려면 단순히 정적 페이지를 보여주는 것만으로는 부족하다.

누가 수정할 수 있는지 확인해야 하고,

내용을 저장할 공간이 필요하고,

저장된 데이터를 다시 불러와야 한다.

필요하면 DB와 API, 인증도 함께 필요하다.

GitHub Pages는 이런 시스템을 자동으로 만들어주지 않는다.

그래서 관리자 기능은 단순한 UI 추가가 아니라 작은 CMS를 만드는 문제에 가까워졌고, 결국 지금은 만들지 않기로 했다.

---

## 방문자 코멘트도 외부 서비스를 사용한 이유가 있었다

방문자 코멘트에서도 비슷한 문제가 있었다.

댓글을 직접 저장하고 사용자를 구분하려면 DB와 인증이 필요하다.

그래서 현재는 Giscus를 사용해 GitHub Discussions와 로그인 기능을 외부 서비스에 맡겼다.

Giscus가 댓글을 처리해 준다고 해서 내 블로그 자체에 사용자 시스템이 생긴 것은 아니다.

이 경험을 통해

**정적 블로그는 외부 서비스와 조합해서 필요한 기능만 보완할 수도 있다**

는 점도 알게 됐다.

---

## 서버에서 처리해야 하는 기능은 다른 영역이었다

정적 사이트는 미리 만들어진 결과를 보여주는 데 강하다.

반면 다음과 같은 기능은 서버 쪽 처리가 필요할 수 있다.

```text
사용자별 데이터 조회

로그인 권한 검증

DB 저장

비밀값이 필요한 API 호출
```

이런 기능까지 필요해진다면 GitHub Pages만으로 해결하려 하기보다 다른 서버 환경이나 서비스를 함께 사용하는 편이 맞다.

---

## 비밀값은 정적 페이지에 그대로 넣을 수 없다

외부 API를 사용할 때 API 키나 비밀값이 필요한 경우도 있다.

이런 값을 프론트엔드 코드나 공개 저장소에 그대로 넣으면 사용자에게 노출될 수 있다.

GitHub Pages가 자동으로 배포해 준다고 해서 이런 비밀 정보를 안전하게 보호해 주는 것은 아니다.

그래서 새로운 외부 기능을 추가할 때는

> 이 값은 브라우저에 공개돼도 되는가?

> 서버에서만 다뤄야 하는가?

를 먼저 구분해야 했다.

---

## 자동 배포는 콘텐츠 관리까지 대신하지 않는다

사이트가 정상적으로 배포되더라도 블로그 내용은 계속 내가 관리해야 한다.

오래된 글이 틀리지 않았는지,

깨진 링크가 없는지,

이미지 파일이 불필요하게 쌓이지 않았는지,

카테고리가 복잡해지지 않았는지는 GitHub Pages가 판단하지 않는다.

404 페이지와 깨진 링크를 정리하면서도 이 점을 느꼈다.

배포가 성공했다는 것과 블로그 관리가 끝났다는 것은 전혀 다른 이야기였다.

---

## 캐시 문제도 배포와는 별개였다

변경사항이 정상적으로 배포됐는데도 이전 모습이 보일 때가 있다.

favicon이나 OG 이미지처럼 브라우저나 외부 서비스가 오래 저장해 두는 파일에서는 특히 그렇다.

```text
배포 성공
≠
모든 화면이 같은 순간 바로 최신 상태
```

이 경우에는 Pages 배포 상태와 캐시 문제를 따로 봐야 했다.

자동 배포는 새 파일을 공개하는 것까지 담당하지만 브라우저나 외부 서비스의 캐시까지 모두 통제하지는 않는다.

---

## 편한 만큼 실수도 빠르게 공개된다

자동 배포의 편리함에는 반대쪽도 있었다.

운영 브랜치에 잘못된 변경사항을 push하면 그것도 자동으로 배포된다.

특히 Claude와 함께 작업하면 여러 파일이 한 번에 수정될 수 있기 때문에 push 전에 어떤 파일이 바뀌었는지 확인하는 것이 더 중요했다.

```text
자동 배포
→ 수동 배포 과정 감소
→ 대신 push 전 검토 중요
```

자동화가 검수 책임까지 없애주는 것은 아니었다.

---

## 지금 블로그에는 GitHub Pages가 잘 맞는다

현재 블로그의 중심은 여전히 글과 정적 콘텐츠다.

그래서

```text
글 작성
→ commit
→ push
→ 자동 배포
```

라는 흐름이 단순하고 편하다.

관리자 기능이나 DB, 인증이 필요한 서비스까지 억지로 GitHub Pages 안에서 해결하려 할 필요는 없다.

그런 기능이 실제로 많이 필요해지는 시점이 오면 그때 다른 구조를 검토하면 된다.

현재는 **GitHub Pages가 잘하는 범위 안에서 블로그를 운영하는 것이 가장 단순하다.**

---

## GitHub Pages의 역할을 구분하니 오히려 편해졌다

지금은 GitHub Pages의 역할을 이렇게 정리하고 있다.

```text
GitHub Pages가 해주는 것

GitHub에 올라온 정적 사이트를 빌드하고 공개한다.


GitHub Pages가 해주지 않는 것

코드가 올바른지 판단한다.
깨진 링크를 자동으로 고친다.
DB나 인증 시스템을 만든다.
서버 로직을 제공한다.
실제 화면이 원하는 모습인지 검수한다.
```

처음에는 자동 배포라는 말을 `나머지를 전부 알아서 해준다`는 의미처럼 생각했다.

하지만 실제로는 **사이트를 공개하는 반복 작업을 자동화해 주는 것**에 가깝다.

그 범위를 알고 나니 오히려 더 편해졌다.

반복적인 배포는 GitHub Pages에 맡기고,

무엇을 공개할지,

실제 사이트가 정상인지,

어떤 기능에 다른 도구가 필요한지는 내가 판단하면 된다.

자동화의 범위를 정확히 아는 것이 자동화를 잘 쓰는 방법이라는 생각이 들었다.
