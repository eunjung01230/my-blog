## 들어가며

처음에 나는 Terminal을 "개발 명령어를 입력하는 검은 창"이라고 생각했다. 알려준 명령어를 복사해서 붙여넣으면 되는 곳 정도였다.

그런데 실제로 개발을 하다 보니 자꾸 막혔다. 분명 맞는 명령어를 쳤는데 파일을 못 찾는다고 하고, 서버를 켰는데 이미 켜져 있다고 하고, 창을 닫았는데 뭔가 계속 돌고 있었다.

문제는 명령어가 아니었다. **지금 내가 어느 폴더에 있는지, 어떤 프로그램이 실행 중인지, 어떤 번호를 쓰고 있는지**를 모르고 있었던 것이다.

그래서 Terminal 자체보다 **"현재 어떤 환경에서 어떤 Process가 실행되고 있는지"** 를 기준으로 기초부터 다시 정리해보려고 한다.

이 글은 프로젝트 회고가 아니라 개념 정리 노트다. 중심은 **Terminal → Path → Command → Process → 개발 서버 → Port → 종료** 이 흐름이다.

## 1. Terminal이란 무엇인가

**Terminal(터미널)** 은 **명령어를 통해 운영체제와 주고받는 인터페이스**다.

우리가 평소에 컴퓨터를 쓰는 방식과 비교하면 이해가 쉬웠다.

| 방식 | 폴더를 여는 방법 |
|---|---|
| GUI (그래픽 화면) | 마우스로 폴더 아이콘을 더블클릭한다 |
| Terminal | 폴더 이름을 명령어로 입력한다 |

**하는 일은 같고 방식만 다르다.** 둘 다 결국 운영체제에게 "이 폴더를 열어달라"고 말하는 것이다.

여기서 짚어둘 점이 있다. **Terminal 자체는 명령어 언어가 아니다.** Terminal은 입력을 받고 결과를 보여주는 **창**에 가깝다. 실제로 명령어를 알아듣는 건 따로 있다.

## 2. Shell이란 무엇인가

그 "따로 있는 것"이 **Shell(셸)** 이다.

| 구분 | 무엇인가 |
|---|---|
| Terminal | 명령어를 입력하고 결과를 보는 창, 인터페이스 |
| Shell | 입력한 명령어를 해석해서 운영체제에 전달하는 프로그램 |

```text
내가 명령어를 입력
↓
Terminal      입력을 받아서 전달한다
↓
Shell         명령어를 해석한다
↓
운영체제      실제로 일을 수행한다
```

내가 이해한 방식으로 비유하면, **Terminal은 창구이고 Shell은 그 창구에서 내 말을 알아듣는 직원**이다. 창구는 같아도 직원이 바뀌면 알아듣는 말이 달라질 수 있다.

Shell의 종류로는 PowerShell, Bash, zsh 같은 것들이 있다. **종류에 따라 쓰는 명령어가 다를 수 있다**는 점이 나중에 중요해진다.

## 3. PowerShell은 무엇인가

**PowerShell**은 **Windows에서 자주 사용하는 Shell 중 하나**다.

여기서 흔히 하는 오해가 있다.

```text
Terminal 은 PowerShell 이다
       (같지 않다)
```

PowerShell은 **Shell의 한 종류**이고, Terminal은 그 Shell을 띄워놓고 쓰는 창이다. Windows Terminal이나 VS Code의 Terminal 안에서 PowerShell을 실행하는 구조다.

```text
Windows Terminal (창)
└─ PowerShell 실행 중

VS Code Terminal (창)
└─ PowerShell 실행 중
```

같은 PowerShell이라도 어느 창에서 띄웠느냐에 따라 창은 다르다. 반대로 같은 창에서 다른 Shell을 띄울 수도 있다.

이 구분을 알고 나니 **"이 명령어는 PowerShell에서는 안 되고 Bash에서는 된다"** 같은 상황이 이해됐다. 문제가 창이 아니라 Shell 쪽에 있었던 것이다.

## 4. VS Code Terminal은 무엇인가

VS Code 안에도 Terminal이 들어 있다. 코드 편집기에서 나가지 않고 바로 명령어를 칠 수 있어서 편하다.

여기서 알아둘 점이 있다. **VS Code Terminal은 별도의 다른 컴퓨터가 아니다.**

```text
VS Code Terminal
= 내 컴퓨터의 Shell을 VS Code 안에서 사용하는 것
```

별도 창에서 PowerShell을 띄우든 VS Code 안에서 띄우든, **같은 내 컴퓨터에서 실행된다.** 파일도 같고, 실행 중인 프로그램도 공유된다.

그래서 **VS Code Terminal에서 서버를 켜고 창을 닫아도, 그게 별개의 세상이 아니다.** 다른 창에서 확인하면 그 서버가 보인다. 이 사실이 뒤에 나올 Process 이야기와 이어진다.

## 5. 현재 경로란 무엇인가

이 부분이 초반에 가장 많이 막혔던 지점이다.

**Terminal은 항상 어딘가의 폴더 안에 서 있다.** 그 위치를 **현재 작업 디렉터리(Working Directory)** 또는 현재 경로라고 한다.

중요한 건 이것이다. **명령어는 대부분 현재 위치를 기준으로 실행된다.**

```text
C:\project\my-blog      에서 실행하는 것
C:\project              에서 실행하는 것

→ 완전히 다른 결과가 나올 수 있다
```

예를 들어 프로젝트 폴더 안에서 실행해야 하는 명령을 그 바깥에서 실행하면, 필요한 파일을 찾지 못해서 실패한다. **명령어는 정확한데 서 있는 자리가 틀린 것이다.**

처음에는 명령어가 실패하면 명령어를 의심했다. 그런데 실제로는 **위치가 틀린 경우가 훨씬 많았다.**

그래서 습관이 하나 생겼다. **명령어를 치기 전에 지금 어디에 있는지 먼저 본다.** Terminal 프롬프트에 경로가 표시되는 경우가 많아서, 그것만 확인해도 대부분 걸러진다.

## 6. 절대 경로와 상대 경로

경로를 표현하는 방법이 두 가지다.

| 구분 | 무엇인가 | 예 (Windows) |
|---|---|---|
| 절대 경로 | 처음부터 전체 위치를 다 적는다 | `C:\project\my-blog\_posts` |
| 상대 경로 | 현재 위치를 기준으로 적는다 | `_posts` |

```text
현재 위치가  C:\project\my-blog  일 때

절대 경로    C:\project\my-blog\_posts
상대 경로    _posts

→ 둘 다 같은 곳을 가리킨다
```

상대 경로에서 자주 쓰는 표시도 있다.

| 표시 | 의미 |
|---|---|
| `.` | 현재 폴더 |
| `..` | 한 단계 위 폴더 |

**상대 경로는 현재 위치가 바뀌면 가리키는 곳도 바뀐다.** 그래서 같은 상대 경로를 다른 위치에서 쓰면 엉뚱한 곳을 가리키게 된다. 5번에서 위치가 중요하다고 한 이유가 여기에도 있다.

## 7. cd는 무엇을 하는가

**`cd`** 는 **현재 작업 디렉터리를 바꾸는 명령어**다. change directory의 줄임말이다.

```text
cd my-blog

실행 전  C:\project
실행 후  C:\project\my-blog
```

여기서 중요한 건 **`cd`가 파일을 여는 게 아니라 내가 서 있는 자리를 옮기는 것**이라는 점이다. GUI에서 폴더를 더블클릭해서 그 안으로 들어가는 것과 같다.

한 단계 위로 올라갈 때는 `cd ..`을 쓴다.

명령어 자체는 단순한데, **이걸 안 하고 명령을 실행해서 실패하는 경우가 정말 많았다.** 명령어를 외우는 것보다 "지금 어디에 있고, 어디로 가야 하는가"를 아는 게 더 중요했다.

## 8. pwd / Get-Location

현재 위치를 확인하는 명령어다. 그런데 **Shell에 따라 이름이 다르다.**

| Shell | 명령어 |
|---|---|
| PowerShell | `Get-Location` |
| Bash, zsh 등 | `pwd` |

PowerShell에서도 `pwd`가 동작하는 경우가 있는데, 별칭(alias)이 걸려 있어서다. 하지만 **모든 환경에서 보장되지는 않는다.**

이 차이를 처음 만났을 때 당황했다. 검색해서 나온 명령어를 그대로 쳤는데 안 됐기 때문이다. **명령어가 틀린 게 아니라 다른 Shell 기준의 명령어였던 것이다.**

그래서 검색할 때 **"어떤 OS, 어떤 Shell 기준인지"** 를 같이 보는 습관이 생겼다.

## 9. ls / dir

현재 폴더 안에 무엇이 있는지 보는 명령어다. 이것도 Shell마다 다르다.

| Shell | 자주 쓰는 명령어 |
|---|---|
| PowerShell | `Get-ChildItem`, 별칭으로 `ls`나 `dir` |
| Bash, zsh | `ls` |
| 전통적인 Windows 명령 프롬프트 | `dir` |

PowerShell에서 `ls`가 동작하는 것도 별칭 덕분이다. **같은 이름이어도 안에서 하는 일이나 출력 형태가 다를 수 있다.**

`cd` 다음으로 자주 쓰게 됐다. **위치를 옮기고 나서 제대로 왔는지 확인**하는 용도다.

```text
cd my-blog       위치를 옮긴다
ls               여기가 맞는지 확인한다
```

## 10. 명령어는 어디에서 실행해야 하는가

앞의 이야기들이 실제로 문제가 되는 대표적인 상황이다.

Node.js 프로젝트에는 보통 프로젝트 최상단에 `package.json`이라는 파일이 있다. 그리고 이런 명령어는 **그 파일이 있는 폴더에서 실행해야 한다.**

```text
npm run dev
```

왜냐하면 이 명령이 **현재 폴더에서 `package.json`을 찾아서** 그 안에 적힌 내용을 실행하기 때문이다. 파일이 없으면 무엇을 실행해야 할지 알 수 없다.

```text
C:\project\my-app        package.json 있음   →  실행됨
C:\project               package.json 없음   →  실패
C:\project\my-app\src    package.json 없음   →  실패
```

**프로젝트 폴더 안이기만 하면 되는 게 아니라, 정확히 그 파일이 있는 위치여야 한다.**

이걸 알기 전에는 "명령어가 안 먹힌다"고 생각했다. 하지만 **명령어는 멀쩡했고 실행한 자리가 틀렸다.** 명령어보다 현재 위치가 중요할 수 있다는 걸 여기서 배웠다.

## 11. PATH란 무엇인가

또 다른 종류의 "찾을 수 없음" 오류가 있다.

`node`나 `git` 같은 명령어를 쳤는데 **"명령어를 찾을 수 없습니다"** 라고 나오는 경우다. 이건 파일 위치 문제가 아니라 **프로그램 위치 문제**다.

**PATH**는 **명령어 이름을 입력했을 때, 운영체제가 그 실행 파일을 어디에서 찾을지 참고하는 경로 목록**이다.

```text
git 을 입력
↓
운영체제가 PATH에 적힌 폴더들을 하나씩 뒤진다
↓
찾으면 실행, 못 찾으면 "명령어를 찾을 수 없음"
```

그래서 프로그램이 **설치되어 있는데도** 명령어가 안 될 수 있다. 설치는 됐지만 그 위치가 PATH에 등록되지 않은 경우다.

실제로 이 블로그 작업 중에도 겪었다. Ruby가 설치되어 있는데 `bundle` 명령이 안 됐다. 없어서가 아니라 **PATH에 없어서** 찾지 못한 것이었다.

환경변수 자체는 Deployment 글에서 정리했으니, 여기서는 **"설치됐는데 명령어가 안 되면 PATH를 의심해본다"** 까지만 짚어둔다.

## 12. 프로그램을 실행하면 무슨 일이 생기는가

이제 명령어를 실행하는 쪽으로 넘어간다.

명령어를 입력하면 그냥 결과만 나오는 게 아니다. **실제로는 프로그램이 실행되고, 그 실행된 상태가 컴퓨터 안에 만들어진다.**

```text
Terminal
↓
명령 실행         내가 입력한 명령을 Shell이 해석한다
↓
Program 실행      해당 프로그램 파일이 실행된다
↓
Process 생성      실행 중인 상태가 하나 만들어진다
```

`ls` 같은 짧은 명령은 실행되고 바로 끝나서 티가 안 난다. 하지만 개발 서버처럼 **계속 돌아가는 프로그램**은 끝나지 않고 남아 있다.

이 "남아 있는 것"이 무엇인지 알아야 뒤의 이야기가 이해된다.

## 13. Process란 무엇인가

**Process(프로세스)** 는 **실행 중인 프로그램의 인스턴스**다.

쉽게 말하면 **지금 실제로 돌아가고 있는 프로그램 하나하나**다.

| 실행한 것 | 생기는 것 |
|---|---|
| VS Code 실행 | 하나 이상의 VS Code Process |
| 개발 서버 실행 | Node Process |
| 브라우저 실행 | Browser Process |

컴퓨터에서 작업 관리자를 열어보면 목록이 쭉 나오는데, 그게 바로 지금 실행 중인 Process들이다.

**Process는 자원을 차지한다.** 메모리를 쓰고, 파일을 열고 있고, 뒤에 나올 Port를 점유하기도 한다. 그래서 끝나지 않고 남아 있는 Process가 있으면 다른 작업에 영향을 준다.

이 개념을 알기 전에는 "서버를 껐다"는 게 무엇을 끈 건지 몰랐다. **끄는 대상이 Process였다.**

## 14. Program과 Process 차이

둘을 구분하고 나서 많은 게 정리됐다.

| 구분 | 무엇인가 |
|---|---|
| Program | 실행할 수 있는 코드나 파일. 디스크에 저장되어 있다 |
| Process | 그 프로그램이 현재 실제로 실행되고 있는 상태 |

```text
Program   →  요리 레시피 (종이에 적혀 있는 것)
Process   →  지금 불 위에서 조리 중인 요리
```

핵심은 이것이다. **같은 Program을 여러 번 실행하면 여러 개의 Process가 생긴다.**

레시피는 한 장이지만 그 레시피로 요리를 세 번 하면 냄비가 세 개다. 마찬가지로 개발 서버를 세 번 실행하면 **Process가 세 개** 돌아간다.

이게 21번에서 나올 문제의 원인이다. 프로그램은 하나인데 실행된 것은 여러 개일 수 있다.

## 15. Foreground Process와 Terminal

Terminal에서 개발 서버를 실행하면, **그 Terminal이 그 Process와 연결된 상태**가 된다.

```text
npm run dev
↓
Node Process 실행
↓
Terminal에 로그가 계속 출력된다
```

이때 Terminal에는 새 명령어를 입력할 수 없다. 프롬프트가 돌아오지 않고, 대신 서버가 뱉어내는 로그가 계속 찍힌다.

이렇게 **Terminal이 붙잡혀 있는 상태로 실행되는 Process**를 foreground에서 돈다고 표현한다.

처음에는 "Terminal이 멈췄다"고 생각했다. 그런데 멈춘 게 아니라 **서버 Process에 연결되어 그 출력을 계속 보여주고 있는 것**이었다.

그래서 다른 명령을 치려면 **Terminal 창을 하나 더 열거나**, 서버를 종료해야 한다. 이게 35번에서 나올 여러 창 사용의 이유다.

## 16. 개발 서버란 무엇인가

**Development Server(개발 서버)** 는 **개발 중인 웹 애플리케이션을 브라우저에서 확인할 수 있도록 실행하는 서버**다.

```text
Terminal
↓
npm run dev           개발 서버 실행 명령
↓
Development Server    내 컴퓨터에서 서버가 돌기 시작한다
↓
localhost:3000        접속할 수 있는 주소가 생긴다
↓
Browser               그 주소로 들어가서 확인한다
```

개발 서버는 **개발하는 동안 편하게 확인하기 위한 것**이다. 코드를 수정하면 자동으로 화면이 갱신되는 기능이 들어 있기도 하고, 오류를 자세히 보여주기도 한다.

실제 서비스에서 돌아가는 서버와는 목적이 다르다. 배포 환경에서는 최적화된 결과물을 안정적으로 제공하는 게 목적이라서 실행 방식이 다르다. 그 이야기는 Deployment 글에서 정리했으니 여기서는 **"개발 확인용으로 내 컴퓨터에서 띄우는 서버"** 까지만 본다.

## 17. localhost란 무엇인가

**localhost**는 **내 컴퓨터 자신을 가리키는 주소**다.

```text
localhost
= 인터넷 전체에 공개된 주소가 아니라
  지금 이 컴퓨터를 가리키는 특수한 이름
```

개발 서버를 실행하면 **내 컴퓨터가 서버 역할도 하고 접속하는 클라이언트 역할도 한다.** 요청이 내 컴퓨터에서 나가서 내 컴퓨터로 들어온다.

그래서 팀원에게 `localhost:3000`을 알려줘도 소용없다. 그 주소는 **각자 자기 컴퓨터**를 가리키기 때문이다.

Deployment 글에서 이 이야기를 배포 관점으로 다뤘으니, 여기서는 Terminal에서 서버를 띄웠을 때 나오는 그 주소가 무엇인지까지만 짚는다. 이제 뒤에 붙는 숫자를 볼 차례다.

## 18. Port란 무엇인가

**Port(포트)** 는 **같은 컴퓨터 안에서 여러 네트워크 프로그램을 구분하기 위해 사용하는 번호**다.

```text
localhost:3000

localhost   →  내 컴퓨터
3000        →  그 안에서 이 서비스가 기다리고 있는 번호
```

비유하면 **localhost는 건물 주소이고 Port는 호수**다. 같은 건물에 여러 세대가 살 수 있듯이, 같은 컴퓨터 안에서 여러 서버가 각자 다른 번호로 돌아갈 수 있다.

요청이 들어올 때 **"이 컴퓨터의 몇 번으로"** 까지 지정해야 어느 프로그램에게 전달할지 정해진다. 주소만 있고 번호가 없으면 컴퓨터는 알아도 누구에게 줄지 모른다.

처음에는 `:3000`이 그냥 붙어 있는 숫자인 줄 알았다. 그런데 **그게 실제로 어느 프로그램에게 갈지를 정하는 값**이었다.

## 19. 왜 Port가 필요한가

한 컴퓨터에서 **여러 프로그램이 동시에 네트워크 요청을 받을 수 있기 때문**이다.

개발할 때 실제로 이런 상황이 생긴다.

```text
localhost:3000    프론트엔드 개발 서버
localhost:4000    블로그 로컬 서버
localhost:5432    데이터베이스
```

전부 같은 내 컴퓨터에서 돌아가지만, **번호가 다르기 때문에 서로 섞이지 않는다.** 3000번으로 온 요청은 3000번을 쓰는 프로그램에게만 간다.

한 가지 짚어둘 점이 있다. **위 번호들이 고정된 규칙은 아니다.** 프로젝트나 도구에 따라 관례적으로 자주 쓰는 번호가 있을 뿐이고, 설정으로 얼마든지 바꿀 수 있다.

그래서 **"3000번은 프론트엔드"라고 외우기보다, 내가 지금 띄운 서버가 몇 번을 쓰는지 확인하는 게** 정확했다. 서버를 실행하면 Terminal에 그 주소가 출력된다.

## 20. 같은 Port를 두 프로그램이 쓰려고 하면

번호가 겹치면 문제가 생긴다.

```text
Process A
→ Port 3000 사용 중

Process B
→ Port 3000 사용 시도

→ 충돌
```

한 호수에 두 집이 들어갈 수 없는 것과 같다. **먼저 차지한 Process가 그 번호를 쓰고 있으면, 나중에 온 쪽은 쓸 수 없다.**

이때 나오는 오류 메시지가 보통 이런 식이다.

```text
Address already in use
포트가 이미 사용 중입니다
```

처음 이 메시지를 봤을 때는 무슨 말인지 몰라서 명령어를 다시 쳤다. 그런데 **다시 쳐도 똑같다.** 이미 쓰고 있는 쪽이 그대로 있기 때문이다.

이 오류는 **코드가 잘못됐다는 뜻이 아니다.** 자리가 이미 차 있다는 뜻이다. 그래서 해결 방법도 코드 수정이 아니라 **누가 쓰고 있는지 확인하는 것**이다.

## 21. 개발 서버를 두 번 실행하면 어떻게 되는가

14번에서 "같은 Program을 여러 번 실행하면 Process가 여러 개 생긴다"고 했다. 그게 여기서 실제 문제가 된다.

이미 서버가 돌고 있는데 새 Terminal을 열어서 `npm run dev`를 또 실행하면, 상황에 따라 결과가 다르다.

| 일어날 수 있는 일 | 설명 |
|---|---|
| 다른 Port를 자동 선택 | 3000이 차 있으니 3001을 쓰겠다고 알려주고 실행된다 |
| Port 충돌 오류 | 그냥 실패하고 종료된다 |
| 프레임워크마다 다른 동작 | 도구에 따라 처리 방식이 다르다 |

첫 번째 경우가 특히 헷갈렸다. **실행은 성공했는데 주소가 바뀌어 있다.** 그런데 브라우저에서는 원래 주소를 보고 있으니, 방금 수정한 내용이 반영이 안 된 것처럼 보인다. 사실은 **다른 서버를 보고 있었던 것**이다.

그래서 이런 오해를 하면 안 된다.

```text
창이 하나 더 열렸다
       (같지 않다)
서버가 하나뿐이다
```

**서버를 새로 켜기 전에 이미 돌고 있는 게 있는지 확인**하는 습관이 필요했다.

## 22. Terminal 창과 Process는 같은 것이 아니다

여기까지 오니 구분이 분명해진다.

| 구분 | 무엇인가 |
|---|---|
| Terminal 창 | Process와 상호작용하는 인터페이스 |
| Process | 실제로 실행되고 있는 프로그램 |

```text
Terminal 창   →  들여다보는 창문
Process       →  창문 너머에서 실제로 돌아가는 것
```

창문은 여러 개 열 수 있고, 하나의 창에서 여러 Process를 차례로 실행할 수도 있다. **창의 개수와 Process의 개수는 일치하지 않는다.**

이걸 알고 나니 서버가 몇 개 돌고 있는지 헷갈렸던 이유가 이해됐다. **나는 창을 세고 있었는데, 세야 할 것은 Process였다.**

## 23. Terminal 창을 닫으면 Process도 항상 종료되는가

자연스럽게 따라오는 질문이다.

보통은 그 Terminal에 연결되어 foreground로 돌던 Process는 창을 닫을 때 함께 영향을 받는다. 많은 경우 같이 종료된다.

하지만 **항상 그렇다고 단정할 수는 없다.**

- 실행 방식에 따라 Process가 남을 수 있다
- 백그라운드로 분리해서 실행한 경우 계속 돌아간다
- 환경이나 도구에 따라 동작이 다르다

그래서 중요한 건 규칙을 외우는 게 아니라 **이렇게 단정하지 않는 것**이다.

```text
창이 안 보인다
       (같지 않다)
Process가 없다
```

Port 충돌이 났는데 창을 다 닫았다고 생각해서 당황하는 경우가 이래서 생긴다. **보이지 않는 것과 없는 것은 다르다.** 확인하려면 창이 아니라 Process를 봐야 한다.

## 24. Ctrl+C는 무엇을 하는가

Terminal에서 서버를 끌 때 쓰는 `Ctrl+C`가 정확히 무엇인지도 몰랐다.

**`Ctrl+C`는 현재 실행 중인 Process에 중단 신호를 보내 종료를 요청하는 것**이다.

```text
Ctrl+C
↓
실행 중인 Process에게 "그만해달라"는 신호를 보낸다
↓
Process가 정리 작업을 하고 스스로 종료한다
↓
Terminal에 프롬프트가 돌아온다
```

여기서 두 가지를 짚어둔다.

**첫째, 이건 "터미널 창 닫기 단축키"가 아니다.** 창을 닫는 게 아니라 **그 안에서 돌고 있는 Process에게 신호를 보내는 것**이다. 창은 그대로 남고 다시 쓸 수 있게 된다.

**둘째, 이건 "요청"이다.** 강제로 끊는 게 아니라 종료해달라고 부탁하는 것이다. 그래서 Process가 열어둔 파일을 정리하고 저장할 것을 저장한 다음 깔끔하게 끝낼 수 있다.

**서버를 끌 때는 이 방법이 가장 정상적인 종료**였다.

## 25. 강제 종료는 언제 필요한가

정상 종료가 안 되는 경우도 있다. Process가 응답하지 않거나, 이미 창이 사라져서 `Ctrl+C`를 보낼 수 없는 경우다.

그럴 때는 Process를 직접 찾아서 종료해야 한다. 다만 **순서가 중요했다.**

```text
문제 발생
↓
바로 강제 종료          ← 이렇게 하지 않는다
```

내가 정리한 순서는 이렇다.

```text
1. 현재 어떤 Process가 실행 중인지 확인
↓
2. 어떤 Port를 사용 중인지 확인
↓
3. 정상적으로 종료할 수 있는지 확인
↓
4. 그래도 안 되면 그때 강제 종료
```

바로 강제 종료부터 하면 두 가지가 위험하다. **엉뚱한 Process를 끌 수 있고**, Process가 정리할 틈 없이 끊겨서 **작업 중이던 것이 제대로 마무리되지 않을 수 있다.**

구체적인 종료 명령어는 OS와 상황에 따라 다르고 잘못 쓰면 영향이 크기 때문에, 이번 글에서는 **"확인부터 하고 필요할 때만"** 이라는 순서까지만 정리해둔다.

## 26. Process ID(PID)란 무엇인가

Process를 찾으려면 구분할 방법이 필요하다. 그게 **PID(Process ID)** 다.

**PID는 실행 중인 Process를 구분하기 위해 운영체제가 부여하는 식별 번호**다.

```text
PID 1234   →  특정 Node Process
PID 5678   →  또 다른 Node Process
```

여기서 왜 번호가 필요한지가 보인다. **Node 서버를 세 번 실행하면 이름이 전부 "node"로 똑같다.** 이름만으로는 어느 것이 무엇인지 알 수 없다.

Database 글에서 "닉네임 대신 id를 쓰는 이유"를 정리했는데, 구조가 같았다. **이름은 겹칠 수 있지만 PID는 겹치지 않는다.**

그래서 특정 Process를 확인하거나 종료할 때는 이름이 아니라 PID를 기준으로 다룬다.

## 27. 어떤 Process가 Port를 쓰는지 확인하는 이유

Port 충돌이 났을 때 던져야 할 질문은 하나다.

```text
3000번을 지금 누가 사용 중인가?
```

이걸 알아야 다음을 판단할 수 있다.

| 확인 결과 | 어떻게 할지 |
|---|---|
| 아까 켜둔 내 서버였다 | 그걸 쓰거나, 정리하고 다시 켠다 |
| 다른 프로젝트 서버였다 | 그건 그대로 두고 내 서버는 다른 Port로 |
| 뭔지 모르는 것이었다 | 함부로 끄지 않고 먼저 확인한다 |

**무엇인지 모르고 끄는 게 가장 위험하다.** 다른 작업 중인 프로그램일 수도 있다.

확인하는 도구는 OS마다 다르다. Windows에서는 `netstat` 같은 도구를, 다른 OS에서는 `lsof` 같은 도구를 쓴다는 정도로 알아두고 있다. 옵션이 많아서 이번 글에서 자세히 다루지는 않는다.

지금 중요한 건 **"Port 오류가 나면 누가 쓰는지부터 확인한다"** 는 순서다.

## 28. npm은 무엇인가

Node.js 프로젝트를 하면 계속 마주치는 이름이다.

**npm**은 **패키지 관리와 Script 실행 등에 사용하는 도구**다.

처음에는 npm을 "Node를 실행하는 명령어"라고 생각했는데, 그게 아니었다. 하는 일이 여러 가지다.

| 하는 일 | 설명 |
|---|---|
| 패키지 설치 | 프로젝트에 필요한 외부 코드를 받아온다 |
| 패키지 관리 | 무엇이 어떤 버전으로 설치되어 있는지 관리한다 |
| Script 실행 | 프로젝트에 정의해둔 명령을 실행한다 |

여기서 **패키지(package)** 는 남이 만들어둔 코드 묶음이다. 모든 걸 직접 만들 필요 없이 가져다 쓰는 것이다.

우리가 자주 쓰는 `npm run dev`는 이 중 **세 번째, Script 실행**에 해당한다.

## 29. package.json과 npm script

10번에서 나온 `package.json`이 여기서 다시 등장한다.

이 파일 안에는 프로젝트 정보와 함께 **실행할 수 있는 명령들이 이름을 붙여 정의**되어 있을 수 있다.

```text
package.json 안의 scripts

  "dev"    →  개발 서버를 실행하는 명령
  "build"  →  빌드를 수행하는 명령
```

그래서 `npm run dev`는 이런 뜻이 된다.

```text
npm run dev
= package.json의 scripts 중 "dev"라는 이름으로 정의된 명령을 실행하라
```

**`dev`라는 프로그램이 따로 있는 게 아니다.** 프로젝트가 자기 방식대로 붙여둔 이름일 뿐이다.

긴 명령어를 매번 치는 대신 짧은 이름을 붙여두고 쓰는 것이다. 그리고 팀원 모두가 같은 이름으로 같은 동작을 실행할 수 있게 된다.

## 30. npm run dev는 무엇을 하는가

앞의 설명에서 자연스럽게 따라오는 결론이 있다.

**`npm run dev`가 모든 프로젝트에서 같은 일을 하지 않는다.**

```text
npm run dev
= 그 프로젝트의 package.json에 "dev"로 적혀 있는 명령을 실행
```

어떤 프로젝트에서는 개발 서버를 띄우고, 어떤 프로젝트에서는 다른 일을 하도록 설정되어 있을 수 있다. 아예 `dev`라는 이름이 없는 프로젝트도 있다.

Next.js 프로젝트에서는 보통 개발 서버를 실행하도록 설정되어 있는 경우가 많다. 하지만 그것도 **그렇게 설정해뒀기 때문**이지 정해진 규칙이 아니다.

그래서 새 프로젝트를 받으면 **`package.json`의 scripts를 한 번 열어보는 게** 가장 확실했다. 무엇을 실행할 수 있는지 거기에 적혀 있다.

## 31. npx는 무엇인가

npm과 이름이 비슷해서 헷갈리는 **npx**도 정리해둔다.

**npx는 패키지의 실행 파일을 실행할 때 자주 사용하는 도구**다.

npm으로 설치해서 프로젝트에 두고 쓰는 것과 달리, npx는 **일회성으로 실행할 때** 편하다. 프로젝트를 새로 만드는 명령처럼 **한 번만 쓰고 말 것**을 실행할 때 자주 보게 된다.

```text
npm    →  설치하고 관리하고, 정의된 script를 실행
npx    →  패키지의 실행 파일을 바로 실행
```

세부 동작은 버전에 따라 달라지는 부분이 있어서, 여기서는 **이름이 비슷하지만 용도가 다르다**는 것까지만 알아둔다.

## 32. npm과 npx 차이

표로 정리하면 이렇다.

| 구분 | npm | npx |
|---|---|---|
| 주된 용도 | 패키지 설치와 관리, script 실행 | 패키지의 실행 파일 실행 |
| 자주 쓰는 상황 | 프로젝트에 필요한 것을 설치할 때, 정의된 명령을 실행할 때 | 한 번만 실행하면 되는 명령을 쓸 때 |
| 대표적인 예 | `npm install`, `npm run dev` | 프로젝트 생성 명령 같은 일회성 실행 |

**"계속 쓸 것을 준비하고 실행하는 것"과 "한 번 쓰고 말 것을 실행하는 것"** 의 차이로 이해하니 덜 헷갈렸다.

## 33. 명령어가 "찾을 수 없음"이라고 할 때

11번에서 PATH를 다뤘는데, 실제로 이 오류를 만나면 원인이 하나가 아니다.

| 가능성 | 확인할 것 |
|---|---|
| 프로그램이 설치되지 않음 | 정말 설치했는지 |
| PATH에 없음 | 설치는 됐는데 등록이 안 됐는지 |
| Shell마다 명령어가 다름 | 다른 Shell 기준의 명령어를 쓰고 있는지 |
| 터미널 재시작이 필요함 | 설치 후 Terminal을 새로 열지 않았는지 |

마지막 경우가 의외로 자주 있다. **설치하면서 PATH가 등록됐는데, 이미 열려 있던 Terminal은 그 변경을 모른다.** 새로 열면 해결되는 경우가 있다.

여기서 강조하고 싶은 건 이것이다.

```text
"찾을 수 없음" 오류
       (같지 않다)
설치를 다시 해야 한다
```

**무조건 다시 설치하지 않는다.** 이미 설치되어 있는데 또 설치하면 버전이 꼬이거나 상황이 더 복잡해질 수 있다. **먼저 현재 환경을 확인한다.**

## 34. 명령어가 실패했을 때 먼저 볼 것

지금까지 나온 것들을 체크리스트로 정리해뒀다.

```text
1. 현재 경로가 맞는가              엉뚱한 폴더에서 실행하고 있지 않은가
2. 필요한 파일이 있는가            package.json 같은 파일이 여기 있는가
3. 명령어 철자가 맞는가            단순한 오타는 아닌가
4. 프로그램이 설치되어 있는가      애초에 있는가
5. PATH가 잡혀 있는가              있는데 못 찾는 것은 아닌가
6. 다른 Process가 같은 Port를 쓰는가  자리가 차 있지 않은가
7. 이전 서버가 아직 실행 중인가    껐다고 생각한 게 남아 있지 않은가
8. 오류 메시지가 무엇이라고 하는가  실제로 읽어봤는가
```

8번을 마지막에 뒀지만 사실 가장 중요했다. **오류 메시지를 안 읽고 명령어만 다시 치는 경우가 많았다.** 메시지에 원인이 적혀 있는데도 그랬다.

명령어를 반복해서 입력한다고 상황이 달라지지 않는다. **같은 상태에서 같은 명령을 치면 같은 결과가 나온다.** 무언가를 바꿔야 결과가 바뀐다.

그래서 **명령어를 다시 치기 전에 상태를 먼저 파악하는 습관**이 필요했다. Git 글에서 `git status`부터 보라고 정리했던 것과 같은 이야기다.

## 35. 여러 Terminal 창을 사용할 때 주의할 점

15번에서 본 것처럼 서버를 실행하면 그 Terminal은 붙잡힌다. 그래서 실제로는 창을 여러 개 쓰게 된다.

```text
Terminal 1   →  Frontend 개발 서버
Terminal 2   →  블로그 로컬 서버
Terminal 3   →  Git 명령이나 기타 작업
```

역할을 나눠두면 편하다. 서버는 계속 돌려두고, 다른 창에서 자유롭게 명령을 칠 수 있다.

문제는 **창이 늘어나면서 어디에서 무엇이 돌고 있는지 모르게 될 때**다.

- 껐다고 생각한 서버가 다른 창에서 계속 돌고 있다
- 같은 서버를 실수로 두 번 켠다
- 어느 창에서 어느 프로젝트를 보고 있는지 헷갈린다

22번에서 정리한 대로 **창과 Process는 다르다.** 창이 세 개라고 Process가 세 개인 것도 아니고, 창을 닫았다고 Process가 사라진 것도 아니다.

## 36. 개발 중 Terminal을 정리하는 습관

그래서 스스로 지키기로 한 원칙들을 정리해뒀다.

| 습관 | 이유 |
|---|---|
| 서버 실행 창은 역할별로 유지 | 어느 창이 무엇인지 헷갈리지 않는다 |
| 새 서버 실행 전 기존 서버 확인 | 중복 실행과 Port 충돌을 막는다 |
| 명령 전에 현재 경로 확인 | 위치 때문에 실패하는 경우가 가장 많다 |
| 오류가 나면 로그부터 읽기 | 메시지에 원인이 적혀 있는 경우가 많다 |
| 필요 없는 Process는 정리 | 자원을 잡고 있고 충돌의 원인이 된다 |
| 명령을 무작정 재실행하지 않기 | 상태가 그대로면 결과도 그대로다 |

특별한 기술은 없다. **지금 상태를 알고 움직이자**는 것뿐이다. 그런데 이것만 지켜도 겪던 문제의 상당수가 줄었다.

## 37. 자주 헷갈리는 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Terminal | 명령어를 입력하고 결과를 보는 창, 인터페이스 |
| Shell | 입력한 명령어를 해석해서 운영체제에 전달하는 프로그램 |
| PowerShell | Windows에서 자주 쓰는 Shell 중 하나 |
| Command | Shell에게 내리는 명령 |
| Path | 파일이나 폴더의 위치를 나타내는 경로 |
| Working Directory | Terminal이 현재 서 있는 폴더. 명령의 기준이 된다 |
| Absolute Path | 처음부터 전체 위치를 다 적은 경로 |
| Relative Path | 현재 위치를 기준으로 적은 경로 |
| PATH | 명령어의 실행 파일을 어디에서 찾을지 적어둔 경로 목록 |
| Program | 실행할 수 있는 코드나 파일 |
| Process | 그 프로그램이 현재 실행되고 있는 상태 |
| PID | 실행 중인 Process를 구분하는 식별 번호 |
| Development Server | 개발 중인 앱을 브라우저에서 확인하려고 실행하는 서버 |
| localhost | 내 컴퓨터 자신을 가리키는 주소 |
| Port | 같은 컴퓨터 안에서 네트워크 프로그램을 구분하는 번호 |
| npm | 패키지 관리와 script 실행 등에 쓰는 도구 |
| npx | 패키지의 실행 파일을 실행할 때 자주 쓰는 도구 |
| package.json | 프로젝트 정보와 실행할 script가 정의된 파일 |
| npm script | package.json에 이름을 붙여 정의해둔 실행 명령 |
| stdout / log | 프로그램이 내보내는 기본 출력. Terminal에 찍히는 그 내용 |

## 38. 자주 헷갈리는 차이 정리

| 구분 | 차이 |
|---|---|
| Terminal vs Shell | 입력하고 보는 창 / 명령어를 해석하는 프로그램 |
| PowerShell vs Terminal | Shell의 한 종류 / 그 Shell을 띄워 쓰는 창 |
| Program vs Process | 실행할 수 있는 파일 / 지금 실행되고 있는 상태 |
| Path vs PATH | 파일의 위치 / 명령어를 찾을 폴더 목록 |
| localhost vs Port | 어느 컴퓨터인가 / 그 안의 어느 프로그램인가 |
| Terminal 창 vs 실행 중인 Process | 들여다보는 창문 / 실제로 돌아가는 것 |
| npm vs npx | 설치하고 관리하고 script 실행 / 실행 파일을 바로 실행 |
| 파일 저장 vs 서버 재실행 | 디스크에 쓴 것 / 그 내용으로 다시 돌린 것 |
| 창 닫기 vs Process 종료 | 창문을 닫은 것 / 돌아가던 것을 멈춘 것 |

## 39. 개발 서버 실행 전체 흐름

지금까지 나온 것들을 하나로 이으면 이렇게 된다.

```text
VS Code
↓
Terminal 열기            내 컴퓨터의 Shell이 창 안에서 실행된다
↓
프로젝트 경로 확인        package.json이 있는 곳에 서 있는지 본다
↓
npm run dev              package.json의 dev script를 실행한다
↓
Node Process 생성         실행 중인 프로그램 하나가 만들어진다
↓
Development Server 실행   그 Process가 서버 역할을 시작한다
↓
Port 사용                 3000 같은 번호 하나를 차지한다
↓
localhost:PORT            접속할 수 있는 주소가 생긴다
↓
Browser 접속              그 주소로 들어가서 화면을 본다
↓
로그 확인                 Terminal에 서버가 상황을 계속 출력한다
↓
Ctrl+C                    Process에 종료 신호를 보낸다
↓
Process 종료              서버가 멈추고 Port가 풀린다
```

이 사다리를 그려놓고 나서 좋았던 점이 있다. **"서버가 안 켜져요"라고 할 때 몇 번째 칸에서 막혔는지 말할 수 있게 됐다.**

경로가 틀린 것과, Process는 떴는데 Port가 막힌 것과, 서버는 도는데 브라우저에서 안 보이는 것은 **전부 다른 문제**다.

## 40. Port 충돌이 생겼을 때 흐름

가장 자주 만난 상황이라 따로 정리해둔다.

```text
Port 오류 확인
↓
이미 실행 중인 서버가 있는지 확인     다른 창에 남아 있지 않은가
↓
어떤 Process가 Port를 쓰는지 확인     무엇인지 모르고 끄지 않는다
↓
기존 서버가 필요한지 판단             그냥 그걸 쓰면 되는 경우도 많다
↓
정상 종료                            Ctrl+C 로 깔끔하게 끈다
↓
필요한 서버만 다시 실행
```

여기서 자주 놓쳤던 건 **네 번째 칸**이다. 이미 돌고 있는 서버가 **내가 필요했던 바로 그 서버인 경우**가 많았다. 그러면 끌 필요도 없이 그 주소로 들어가면 된다.

Port 오류를 보자마자 끄고 다시 켜는 게 아니라, **왜 이미 쓰이고 있는지부터 확인**하는 순서가 훨씬 안전했다.

## 41. 이번에 이해한 핵심

이번에도 가장 크게 남은 건 **"이것과 저것은 다르다"는 구분**이었다.

### Terminal 창, 은 Process와 다르다

창은 들여다보는 인터페이스이고, Process는 실제로 돌아가는 것이다. 개수도 일치하지 않는다.

### Program, 은 Process와 다르다

프로그램은 하나여도 실행된 Process는 여러 개일 수 있다.

### localhost, 는 Port와 다르다

localhost는 어느 컴퓨터인지이고, Port는 그 안의 어느 프로그램인지다. 둘이 합쳐져야 주소가 된다.

### Terminal을 닫았다, 는 Process가 사라졌다와 다르다

보이지 않는 것과 없는 것은 다르다. 확인하려면 Process를 봐야 한다.

### 명령어가 실패했다, 는 코드가 잘못됐다와 다르다

경로가 틀렸거나, PATH에 없거나, Port가 차 있을 수 있다. 원인이 코드 바깥에 있는 경우가 많다.

### npm run dev, 는 모든 프로젝트에서 같은 서버를 실행한다와 다르다

그 프로젝트의 package.json에 적힌 명령을 실행할 뿐이다.

### 서버 화면이 안 보인다, 는 서버 Process가 없다와 다르다

다른 Port에서 돌고 있거나, 켜져 있는데 다른 주소를 보고 있을 수 있다.

그리고 마지막으로 이것이 가장 크게 바뀐 관점이다.

> Terminal을 잘 쓴다는 것은 명령어를 많이 외우는 것보다, 현재 내가 어느 경로에 있고 어떤 Process가 실행 중이며 어떤 Port를 사용하고 있는지 파악할 수 있는 것에 더 가까웠다.

처음에는 Terminal을 잘 쓰려면 명령어를 많이 알아야 한다고 생각했다. 그래서 명령어 모음을 찾아서 외우려고 했다.

그런데 실제로 막혔던 순간을 돌아보면, **명령어를 몰라서 막힌 적은 거의 없었다.** 대부분 **지금 어디에 있는지, 무엇이 돌고 있는지를 몰라서** 막혔다. 명령어는 필요할 때 찾으면 됐지만, 현재 상태는 내가 파악하지 않으면 아무도 알려주지 않았다.

## 더 공부하면 좋은 것

이번 글에서는 개념 위치만 잡고 자세히 다루지 않았다.

- **Shell Script** — 여러 명령을 묶어서 자동으로 실행하는 방법
- **PowerShell Script** — Windows 환경에서 같은 일을 하는 방식
- **Environment Variable** — Terminal 관점에서 환경변수가 어떻게 전달되는지
- **Process Signal** — Ctrl+C가 보내는 신호를 포함한 여러 종류의 신호
- **stdin / stdout / stderr** — 프로그램의 입력과 출력, 오류 출력이 나뉘는 구조
- **PATH 심화** — 등록 순서와 우선순위가 어떻게 동작하는지
- **Port와 Socket** — 네트워크 연결이 실제로 어떻게 맺어지는지
- **TCP/IP** — 그 통신이 바탕에 두고 있는 규칙
- **SSH** — 원격 컴퓨터의 Terminal에 접속하는 방법
- **Docker Process** — 컨테이너 안에서 Process와 Port가 어떻게 다뤄지는지
