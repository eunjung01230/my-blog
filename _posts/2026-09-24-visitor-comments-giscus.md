블로그를 계속 손보다 보니 이번에는 글을 읽는 사람과 아주 가볍게 소통할 수 있는 공간이 있으면 좋겠다는 생각이 들었다.

포스트마다 긴 댓글을 주고받는 기능까지는 필요하지 않았다.

사이드바나 홈 한쪽에

> 잘 보고 갑니다.

> 이 글 도움됐어요.

처럼 짧은 말을 남길 수 있는 **방문자 코멘트 공간** 정도면 충분했다.

처음에는 꽤 간단한 기능처럼 보였다.

입력창 하나를 만들고,

작성 버튼을 누르면,

작성한 내용이 아래에 보이면 된다.

하지만 조금만 생각해 보니 바로 질문이 생겼다.

> 이 코멘트는 어디에 저장하지?

여기에서 또 DB 이야기가 시작됐다.

그리고 솔직히 말하면 이 순간부터 조금 귀찮아지기 시작했다.

---

## 처음 원했던 것은 아주 작은 방명록이었다

방문자 코멘트를 생각한 이유는 거창하지 않았다.

개인 블로그인데 글만 일방적으로 보여주는 것보다 누군가 짧게 흔적을 남길 수 있으면 조금 더 살아 있는 공간처럼 느껴질 것 같았다.

별도의 커뮤니티 기능을 만들고 싶었던 것은 아니다.

회원가입,

친구,

알림,

댓글 대댓글 같은 기능까지 필요하지 않았다.

원했던 모습은 대략 이 정도였다.

```text
방문자 코멘트

[ 짧은 메시지를 남겨주세요 ]

                작성하기

푸름     잘 보고 갑니다!
visitor  이 글 도움됐어요.
```

정말 이 정도였다.

그런데 기능이 단순해 보여도 작성된 내용을 계속 남겨두려면 결국 저장할 곳이 필요했다.

---

## 정적 블로그에서는 저장이 문제였다

내 블로그는 GitHub Pages를 이용한 정적인 블로그였다.

포스트 역시 파일로 관리하고 있었다.

그래서 방문자가 브라우저에서 입력한 내용을 바로 영구적으로 저장할 공간이 없었다.

화면에 입력창을 만드는 것은 어렵지 않다.

JavaScript로 입력한 내용을 잠깐 화면에 보여주는 것도 가능하다.

하지만 새로고침해도 남아 있고 다른 방문자도 같은 코멘트를 보려면 이야기가 달라진다.

```text
방문자가 메시지 작성
        ↓
어딘가에 저장
        ↓
다른 방문자가 블로그 접속
        ↓
저장된 메시지 불러오기
```

이 흐름이 필요했다.

결국 방문자 코멘트는 아주 작은 기능처럼 보여도 **데이터를 저장하는 기능**이었다.

---

## 직접 DB를 붙이면 원하는 것은 거의 만들 수 있었다

가장 자유로운 방법은 직접 데이터베이스를 연결하는 것이었다.

예를 들어 방문자 코멘트마다

```text
작성자
내용
작성 시간
사용자 ID
```

같은 정보를 저장할 수 있다.

그러면 나중에는 내가 원하는 기능도 추가할 수 있다.

내가 작성한 코멘트와 방문자가 작성한 코멘트를 구분하거나,

삭제 기능을 만들거나,

특정 사용자에게만 기능을 보여주거나,

관리자 화면에서 코멘트를 관리할 수도 있다.

기능의 자유도만 보면 직접 DB를 사용하는 방식이 가장 좋았다.

문제는 **방명록 하나 만들자고 시작한 일이 더 이상 방명록 하나의 작업이 아니게 된다는 것**이었다.

---

## DB를 붙이는 순간 작업 규모가 갑자기 커졌다

데이터베이스 하나 연결하면 끝날 것 같지만 실제로 생각해야 할 것이 계속 생겼다.

DB 테이블을 만들고,

코멘트를 저장하는 기능을 만들고,

저장된 코멘트를 다시 불러오고,

잘못된 입력을 막고,

삭제는 누가 할 수 있는지 정해야 한다.

사용자를 구분하려면 인증도 필요하다.

관리자만 삭제할 수 있게 하려면 권한도 필요하다.

```text
방문자 코멘트
       ↓
DB
       ↓
API
       ↓
인증
       ↓
권한
       ↓
관리 기능
```

처음에는 화면 구석에 작은 입력창 하나 만들 생각이었는데 갑자기 백엔드 작업이 따라오기 시작했다.

관리자 기능을 고민할 때와 비슷했다.

겉으로는 단순한 UI 하나인데 실제로 데이터를 저장하는 순간 뒤에서 필요한 구조가 훨씬 커졌다.

---

## 그래서 먼저 외부 서비스를 활용하는 방법을 봤다

방문자 코멘트 하나 때문에 처음부터 DB와 인증을 만들고 싶지는 않았다.

그래서 이미 만들어진 댓글 서비스를 사용하는 방법을 찾아봤다.

그중 사용하게 된 것이 **Giscus**였다.

Giscus는 GitHub Discussions를 이용해 댓글을 남길 수 있는 방식이라 별도의 댓글 DB를 내가 직접 만들 필요가 없었다.

사용자는 GitHub 계정으로 로그인할 수 있고,

작성한 내용은 GitHub Discussions 쪽에서 관리된다.

나에게는 상당히 매력적인 선택이었다.

```text
직접 구현

DB 구축
인증 구현
댓글 저장
댓글 조회
권한 처리

vs

Giscus

설정
블로그에 연결
사용
```

당장 필요한 것이 단순한 코멘트 기능이라면 두 번째가 훨씬 가벼웠다.

---

## 일단 Giscus로 방문자 코멘트를 만들었다

Giscus를 연결하고 나니 내가 원했던 기본적인 기능은 생각보다 빠르게 만들 수 있었다.

GitHub 로그인을 통해 댓글을 작성할 수 있고,

작성한 내용도 계속 남아 있었다.

별도의 데이터베이스를 만들지 않아도 됐다.

내가 서버를 운영할 필요도 없었다.

블로그에 작은 방문자 코멘트 영역이 생기니 처음 원했던 목적은 어느 정도 해결됐다.

이때까지만 보면

> 굳이 DB를 만들 필요 없겠는데?

라는 생각이 들었다.

실제로 단순한 댓글 기능만 필요하다면 외부 서비스를 활용하는 것이 훨씬 효율적이었다.

---

## 그런데 사용자를 구분하고 싶어지면서 문제가 생겼다

기능이 생기면 항상 다음 욕심이 생긴다.

GitHub 로그인을 하고 있으니 처음에는 이런 생각을 했다.

> 그러면 블로그에서도 지금 로그인한 사람이 누구인지 알 수 있지 않을까?

사용자를 구분할 수 있다면 더 많은 것을 할 수 있다.

내 코멘트와 다른 사람의 코멘트를 구분할 수도 있고,

특정 사용자에게 기능을 제공할 수도 있다.

나중에는 사용자별 데이터도 관리할 수 있다.

하지만 구조를 확인해 보니 생각했던 것과 달랐다.

Giscus의 로그인은 **Giscus 안에서 처리되고 있었다.**

블로그 페이지 자체가 로그인 정보를 받는 구조가 아니었다.

---

## GitHub로 로그인했다고 내 블로그가 사용자를 아는 것은 아니었다

이 부분이 처음에는 조금 헷갈렸다.

화면에서는 분명 내 블로그 안에 Giscus가 보인다.

사용자는 거기서 GitHub 로그인을 한다.

그러면 자연스럽게

```text
내 블로그
→ GitHub 로그인 정보도 알 수 있음
```

처럼 느껴질 수 있다.

하지만 실제로는 Giscus가 별도의 iframe 형태로 들어와 있었다.

```text
내 블로그

┌─────────────────────┐
│       Giscus        │
│ GitHub 로그인 처리   │
│ 댓글 처리            │
└─────────────────────┘
```

Giscus 안에서는 사용자가 누구인지 알 수 있어도 내 블로그 코드가 그 사용자 정보를 그대로 가져다 쓸 수 있는 것은 아니었다.

내 블로그 입장에서는 그냥 Giscus 위젯을 보여주고 있는 것이었다.

이 차이를 이해하고 나니

> 외부 서비스를 붙이는 것과 그 서비스의 사용자 시스템을 내 서비스에서 사용하는 것은 다른 문제구나.

라는 것이 분명해졌다.

---

## Giscus는 댓글에는 충분했지만 내 사용자 시스템은 아니었다

처음 목적만 보면 Giscus는 충분했다.

방문자가 로그인하고,

댓글을 남기고,

그 댓글을 다시 볼 수 있다.

내가 직접 DB를 만들지 않아도 된다.

하지만 요구사항이

> 댓글을 남긴다.

에서

> 로그인한 사용자를 블로그에서도 구분한다.

로 바뀌는 순간 Giscus만으로는 해결할 수 없었다.

이 차이가 중요했다.

```text
Giscus가 잘하는 것
→ 댓글 기능

내가 추가로 원했던 것
→ 블로그 자체 사용자 구분
```

서로 비슷해 보이지만 완전히 같은 기능은 아니었다.

---

## 결국 선택지는 다시 두 가지가 됐다

구조를 확인하고 나니 선택지는 꽤 분명했다.

### 1. Giscus를 그대로 사용한다

장점은 단순했다.

이미 동작한다.

DB가 필요 없다.

로그인과 댓글 저장을 직접 구현하지 않아도 된다.

관리 부담도 적다.

대신 Giscus가 제공하는 범위 안에서 사용해야 한다.

### 2. 블로그 자체 사용자 시스템과 DB를 만든다

이 방식이면 자유도가 훨씬 높다.

사용자 ID를 직접 관리할 수 있고,

방문자 코멘트를 내 DB에 저장할 수 있다.

관리 기능도 원하는 대로 만들 수 있다.

하지만 그만큼 구현해야 할 것도 많아진다.

```text
로그인
사용자 데이터
DB
API
권한
보안
관리 기능
```

사실상 작은 백엔드 프로젝트가 하나 더 시작되는 셈이었다.

---

## 그리고 솔직히 지금은 DB까지 하기 귀찮았다

기술적으로 불가능해서 멈춘 것은 아니었다.

오히려 어떻게 해야 하는지는 조금씩 보이고 있었다.

DB를 붙이고,

사용자 인증을 만들고,

사용자별 ID를 관리하면 된다.

문제는 **지금 그걸 하고 싶은가**였다.

블로그에서 아직 하고 싶은 작업이 많았다.

포스트도 추가해야 하고,

검색이나 정렬 같은 기능도 손보고 싶었고,

글 자체도 계속 작성해야 했다.

그 상황에서 방문자 코멘트 하나 때문에 인증과 DB 작업을 시작하면 블로그가 또 다른 프로젝트로 커질 수 있었다.

그리고 무엇보다 당시에는 시간이 많지 않았다.

그래서 생각했다.

> 일단 이건 나중에 하자.

기술적인 판단이기도 했지만 아주 현실적인 이유도 있었다.

**귀찮고, 지금 하기에는 일이 너무 커졌다.**

---

## 모든 불편함을 바로 해결할 필요는 없었다

예전 같았으면

> 여기까지 생각했으니 그냥 끝까지 만들어야 하지 않을까?

라고 생각했을 수도 있다.

하지만 블로그 기능을 계속 발전시키면서 조금씩 생각이 달라졌다.

불편한 부분을 발견했다고 반드시 즉시 해결해야 하는 것은 아니다.

현재 기능으로도 목적을 어느 정도 달성하고 있다면 그대로 사용할 수 있다.

Giscus만으로도 방문자는 코멘트를 남길 수 있었다.

내가 로그인 사용자를 직접 구분하지 못한다는 것이 당장 블로그 운영을 막는 문제는 아니었다.

그렇다면 지금은 굳이 구조를 복잡하게 만들 필요가 없었다.

---

## DB 연결 여부도 기능 하나만 보고 결정할 문제는 아니었다

처음에는

> 이 기능에 DB가 필요하네.

라는 사실을 알면 바로 DB를 연결해야 할 것처럼 느껴졌다.

하지만 이번에는 반대로 생각해 봤다.

DB가 필요한 기능이 앞으로 얼마나 더 생길까?

방문자 사용자 구분,

관리자 기능,

직접 만든 댓글,

사용자별 기능처럼 DB가 필요한 요구사항이 여러 개 쌓인다면 그때는 이야기가 달라진다.

한 기능 때문에 DB를 연결하는 것보다 **여러 요구사항이 쌓였을 때 한 번에 구조를 만드는 편이 더 낫다**고 생각했다.

그래서 방문자 코멘트 하나를 위해 지금 바로 DB를 붙이는 대신 나중에 다른 기능과 함께 다시 검토하기로 했다.

이렇게 생각하니 미루는 것도 조금 덜 찝찝했다.

단순히 하기 싫어서 던져둔 일이 아니라 우선순위를 뒤로 보낸 일이 됐다.

---

## 외부 서비스를 사용하는 것도 충분히 개발적인 선택이었다

직접 구현하지 않으면 뭔가 덜 만든 것처럼 느껴질 때가 있다.

특히 개발 공부를 하고 있으면

> 이것도 직접 만들어봐야 하지 않을까?

라는 생각이 들기 쉽다.

하지만 실제 서비스에서는 모든 기능을 직접 구현하는 것이 항상 좋은 선택은 아니다.

이미 안정적으로 제공되는 기능이 있고 현재 요구사항을 충족한다면 그것을 사용하는 것도 하나의 선택이다.

이번 방문자 코멘트에서는 Giscus가 그런 역할을 했다.

내가 댓글 시스템 자체를 공부하는 것이 목적이었다면 직접 만드는 것도 의미가 있다.

하지만 당시 목적은

> 내 블로그에 방문자가 짧은 코멘트를 남길 수 있게 하는 것

이었다.

그 목적만 본다면 Giscus로도 충분했다.

---

## 대신 외부 서비스의 경계는 알아야 했다

Giscus를 사용하면서 중요한 것은

> 외부 서비스를 쓰면 편하다.

에서 끝나지 않았다.

어디까지 그 서비스가 처리하고,

어디부터 내 블로그가 처리해야 하는지 알아야 했다.

```text
Giscus

GitHub 로그인
댓글 작성
댓글 저장
댓글 표시

내 블로그

Giscus 위젯 표시
블로그 자체 기능 관리
```

이 경계를 알고 나니 나중에 기능을 확장할 때도 판단하기 쉬워졌다.

Giscus 내부의 로그인 정보를 활용하려고 계속 억지로 연결할 것이 아니라, 블로그 자체 사용자 정보가 필요하다면 그때 별도의 인증 구조를 만들어야 한다는 것을 알 수 있었다.

---

## 결국 방문자 코멘트는 '적당한 선'에서 멈췄다

처음에는 단순한 방명록을 원했다.

Giscus를 붙여 기본적인 코멘트 기능을 만들었다.

그러다 사용자를 직접 구분하고 싶은 욕심이 생겼고, 구조를 확인해 보니 내 블로그에서는 Giscus 로그인 정보를 사용할 수 없다는 것을 알게 됐다.

그다음 선택은 분명했다.

직접 DB와 인증을 만들거나,

현재 기능으로 만족하고 잠시 멈추거나.

나는 두 번째를 선택했다.

현재 필요한 방문자 코멘트는 이미 동작하고 있었고, 추가 요구사항 때문에 블로그 전체 구조를 크게 만드는 것은 우선순위가 아니었다.

---

## 이 기능에서 가장 많이 배운 것은 '어디까지 만들 것인가'였다

방문자 코멘트 자체는 아주 작은 기능이었다.

하지만 이 기능을 고민하면서

외부 서비스,

iframe,

로그인,

사용자 정보,

DB,

백엔드

가 어떻게 연결되는지 조금 더 구체적으로 볼 수 있었다.

무엇보다 기능을 구현할 때는 기술적으로 가능한지만 보는 것이 아니라 **어디까지 직접 만들 것인지 결정하는 일**도 중요하다는 것을 다시 느꼈다.

직접 DB를 붙이면 더 많은 것을 할 수 있다.

하지만 더 많은 것을 할 수 있다는 이유만으로 반드시 지금 해야 하는 것은 아니다.

현재 목적에 Giscus가 충분하다면 일단 그것을 사용해도 된다.

그리고 나중에 DB가 필요한 기능이 여러 개 생겼을 때 다시 구조를 만들면 된다.

결국 이번에 내린 판단은 단순했다.

> **지금 필요한 것은 방문자 코멘트이지, 새로운 사용자 시스템을 만드는 것이 아니었다.**

그래서 DB 연결은 잠시 미뤘다.

조금은 기술적인 이유였고,

조금은 시간 때문이었고,

솔직히 조금은 귀찮아서이기도 했다.

하지만 블로그를 계속 만들면서 이제는 그런 이유까지 포함해서 **현재 가장 필요한 작업을 선택하는 것도 개발 과정의 일부**라고 생각하게 됐다.
