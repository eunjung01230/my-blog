블로그에 글이 쌓이기 시작하면서 독자가 글을 읽는 기능만큼 **내가 글을 관리하는 과정**도 눈에 들어오기 시작했다.

처음에는 별문제가 없었다.

새 글을 작성하려면 프로젝트를 열고 포스트 파일을 만든다.

내용을 작성하고,

Git에 커밋하고,

push한 뒤 배포된 블로그에서 확인한다.

블로그 구조를 알고 있는 내가 직접 관리하는 것이니 이 방식으로도 충분했다.

하지만 포스트가 늘어나고 블로그를 자주 수정하다 보니 작은 불편함이 생겼다.

블로그에서 글을 보고 있다가 수정하고 싶은 부분을 발견해도 다시 VS Code로 돌아가 해당 파일을 찾아야 했다.

새 글을 쓰고 싶을 때도 블로그 화면과 실제 작성 과정이 완전히 분리되어 있었다.

그때부터 이런 생각을 하기 시작했다.

> **블로그를 보고 있는 화면에서 바로 글을 추가하거나 수정하는 작업으로 이어질 수 없을까?**

처음에는 버튼 하나의 문제처럼 보였다.

하지만 실제로 생각해 보니 포스트 추가·수정 기능은 단순한 UI보다 훨씬 많은 문제와 연결되어 있었다.

---

## 처음에는 파일을 직접 만들고 수정했다

내 블로그의 포스트는 프로젝트 안의 파일로 관리됐다.

새 포스트를 작성한다는 것은 결국 새로운 포스트 파일을 만드는 일이었다.

수정 역시 마찬가지였다.

블로그 화면에서 글을 읽다가 오타를 발견하면 실제 프로젝트에서 해당 글의 파일을 찾아 내용을 수정해야 했다.

이 방식의 장점은 분명했다.

원본이 어디에 있는지 명확했고,

Git으로 변경 내역을 관리할 수 있었고,

잘못 수정해도 이전 기록을 확인할 수 있었다.

개발 공부를 하면서 Git을 같이 사용하고 있었기 때문에 나에게는 익숙한 방식이기도 했다.

하지만 블로그를 실제로 사용하는 흐름과 글을 관리하는 흐름이 따로 떨어져 있다는 점은 조금씩 불편해졌다.

```text
블로그에서 글 확인
        ↓
VS Code 열기
        ↓
해당 포스트 파일 찾기
        ↓
내용 수정
        ↓
commit / push
        ↓
배포 결과 확인
```

과정 자체가 어렵지는 않다.

다만 작은 수정 하나에도 항상 이 흐름을 거쳐야 했다.

---

## Claude를 사용하면서 파일을 찾는 부담은 줄었다

Claude와 블로그 프로젝트를 같이 관리하기 시작한 뒤에는 조금 편해졌다.

내가 모든 파일을 직접 찾아서 수정하지 않아도

> 이 포스트의 이 부분을 바꾸고 싶다.

라고 요청하면 관련 파일을 확인하고 수정할 수 있었다.

이 방식은 특히 블로그 구조가 복잡해질수록 편했다.

하지만 Claude를 사용한다고 해서 블로그 자체에 관리 기능이 생긴 것은 아니었다.

여전히 작업의 시작점은 개발 환경이었다.

블로그를 보다가

> 여기 문장을 수정해야겠다.

라고 생각하면 Claude나 VS Code로 돌아가야 했다.

그래서 다음 단계에서는 **블로그 화면과 관리 작업을 조금 더 가까이 연결하고 싶었다.**

---

## 페이지마다 바로 작업할 수 있는 버튼을 생각했다

처음 떠올린 방법은 복잡하지 않았다.

현재 보고 있는 페이지와 관련된 관리 작업으로 바로 이동할 수 있는 버튼을 두는 것이었다.

예를 들어 포스트 목록에서는

```text
+ 포스트 추가
```

프로젝트 페이지에서는

```text
+ 프로젝트 추가
```

About에서는

```text
소개 편집
```

처럼 각 페이지에 맞는 작업을 바로 시작할 수 있으면 편할 것 같았다.

이 아이디어가 마음에 들었던 이유는 별도의 관리자 페이지를 처음부터 새로 만들 필요가 없었기 때문이다.

평소 사용하는 블로그 화면에서 내가 자주 하는 작업으로 바로 이어지면 됐다.

관리 기능도 사용자의 흐름을 따라가는 편이 자연스럽다고 느꼈다.

---

## '추가 버튼'과 실제 글 작성 기능은 다른 문제였다

처음에는 버튼을 하나 추가하면 글 작성 기능이 생기는 것처럼 생각하기 쉬웠다.

하지만 실제로는 그렇지 않았다.

버튼은 어디론가 이동하게 만들 수 있다.

문제는 그다음이다.

새 포스트의 내용을 어디에 입력할 것인지,

작성한 내용을 어디에 저장할 것인지,

포스트 파일을 누가 생성할 것인지,

저장 후 Git에는 어떻게 반영할 것인지까지 결정해야 했다.

즉,

```text
[포스트 추가 버튼]
```

을 만드는 것과

```text
블로그 안에서 포스트를 실제로 생성한다
```

는 완전히 다른 규모의 작업이었다.

이 차이를 알게 된 것이 포스트 관리 기능을 생각하면서 가장 중요했던 부분 중 하나였다.

---

## 수정 기능은 추가 기능보다 더 복잡했다

새 글을 만드는 것보다 기존 글을 수정하는 기능은 더 생각할 것이 많았다.

본문만 수정하는 것이 아니었기 때문이다.

포스트에는 내용 외에도 여러 정보가 붙어 있다.

예를 들면

```yaml
title:
date:
categories:
tags:
```

같은 정보다.

블로그를 운영하다 보면 나중에 제목을 조금 바꾸고 싶을 수도 있고,

날짜나 카테고리를 수정하고 싶을 수도 있다.

태그를 추가하거나 잘못된 분류를 고칠 수도 있다.

그러다 보니 처음의

> 글 내용을 수정할 수 있으면 좋겠다.

는 생각이 점점

> **포스트의 정보 전체를 관리할 수 있으면 좋겠다.**

로 확장됐다.

---

## 블로그 안에서 바로 수정하고 싶었다

이상적으로는 포스트를 읽다가 수정할 부분을 발견했을 때 같은 화면에서 바로 편집할 수 있으면 가장 편하다.

예를 들어 관리자에게만 보이는 수정 버튼을 누르면

```text
제목
날짜
카테고리
태그
본문
```

을 편집할 수 있고,

저장하면 블로그에도 반영되는 방식이다.

사용하는 입장에서는 단순해 보인다.

하지만 실제 구현을 생각해 보면 바로 질문이 생겼다.

> 저장 버튼을 누른 내용은 어디에 저장하지?

내 블로그는 파일을 기반으로 만들어지고 있었다.

브라우저에서 입력한 내용을 바꿨다고 해서 프로젝트 안의 원본 파일이 자동으로 수정되는 것은 아니다.

결국 수정 결과를 실제 원본과 연결하는 방법이 필요했다.

---

## GitHub Pages가 정적인 블로그라는 점이 중요했다

내 블로그는 별도의 서버에서 데이터를 읽어오는 서비스가 아니라 GitHub에 있는 파일을 기반으로 배포되는 구조였다.

그래서 브라우저에서

```text
수정
→ 저장
```

을 누른다고 바로 파일이 바뀌는 구조가 아니었다.

실제로 수정 내용을 영구적으로 반영하려면 어딘가에서는 원본이 바뀌어야 한다.

현재 구조라면 결국 GitHub 저장소의 포스트 파일과 연결되어야 했다.

이 지점에서 관리자 기능이 단순한 프론트엔드 기능이 아니라는 것을 알게 됐다.

화면에는 버튼 하나로 보일 수 있지만 뒤에서는

```text
관리자 확인
        ↓
수정할 데이터 불러오기
        ↓
내용 변경
        ↓
원본에 저장
        ↓
변경사항 반영
        ↓
다시 배포
```

같은 과정이 필요했다.

---

## '나만 수정할 수 있게' 만드는 것도 별도의 문제였다

블로그 화면에서 수정 기능을 제공한다면 아무나 사용할 수 있어서는 안 된다.

처음에는 관리자 코드처럼 나만 알고 있는 값을 입력하면 수정할 수 있게 하는 방식도 떠올렸다.

사용자 입장에서는 간단하다.

```text
관리자 인증
→ 수정 버튼 표시
→ 포스트 편집
```

하지만 이것 역시 단순히 화면에서 코드를 비교하는 것으로 끝낼 문제는 아니었다.

프론트엔드 코드 안에 중요한 인증 정보를 그대로 넣으면 결국 사용자에게 전달되는 코드에서 확인될 가능성이 있다.

그리고 누가 실제 관리자인지 안전하게 확인하려면 인증을 어디에서 처리할지도 생각해야 한다.

여기에서 다시 **보이는 화면과 실제 보안은 다른 문제**라는 것을 느꼈다.

수정 버튼을 숨기는 것과 수정 권한을 보호하는 것은 같지 않았다.

---

## 결국 관리자 기능에는 저장 공간과 권한이 필요했다

처음에는

> 관리자 코드 하나 넣고 수정 버튼 만들면 되지 않을까?

정도로 시작한 생각이었다.

하지만 하나씩 따져보니 제대로 구현하려면 필요한 것이 많았다.

```text
누가 관리자인지 확인하는 방법
        +
수정할 데이터를 불러오는 방법
        +
수정한 데이터를 저장하는 방법
        +
기존 포스트와 연결하는 방법
        +
저장 후 블로그에 반영하는 방법
```

여기까지 오면 더 이상 단순한 디자인 기능이라고 보기는 어려웠다.

작은 관리자 시스템에 가까워졌다.

블로그 기능을 발전시키면서 자주 경험했던 것처럼 **화면에서는 단순한 버튼 하나인 기능도 뒤에서는 훨씬 큰 구조가 필요할 수 있었다.**

---

## DB를 연결하면 가능한 범위가 커질 수 있었다

글과 사용자 정보를 데이터베이스에서 관리한다면 브라우저에서 수정한 내용을 저장하는 구조를 만들기 쉬워질 수 있다.

관리자를 확인하고,

포스트 데이터를 불러오고,

수정 내용을 저장하는 흐름을 만들 수 있기 때문이다.

하지만 현재 블로그는 파일 기반으로 잘 동작하고 있었다.

포스트 하나를 수정하기 위해 바로 전체 구조를 데이터베이스 중심으로 바꾸는 것이 맞는지도 생각해야 했다.

DB를 붙이면 얻는 기능은 늘어나지만 관리해야 할 것도 같이 늘어난다.

인증,

데이터 구조,

배포 환경,

보안,

백업 같은 문제도 생긴다.

그래서

> 가능하니까 DB를 붙인다.

가 아니라

> **현재 필요한 기능이 DB까지 사용할 만큼 중요한가?**

를 먼저 판단할 필요가 있었다.

---

## 지금 당장 필요한 것과 나중에 할 것을 나눴다

이 시점에는 다른 작업도 계속 진행하고 있었다.

포스트를 추가하고,

블로그 기능을 개선하고,

글을 정리하는 작업도 남아 있었다.

관리자 기능 하나를 완성하기 위해 인증과 DB까지 한꺼번에 시작하면 다른 작업이 모두 멈출 수도 있었다.

그래서 모든 아이디어를 바로 구현하려고 하지 않았다.

현재 파일 기반 작성 방식은 유지하고,

블로그에서 관리 작업으로 쉽게 이어지는 부분은 먼저 개선하고,

실제 DB나 관리자 인증이 필요한 기능은 별도의 작업으로 남겨두는 편이 낫다고 판단했다.

이전에는 기능 아이디어가 생기면 바로 만들어야 할 것처럼 느꼈다.

하지만 블로그를 계속 관리하면서 **좋은 아이디어와 지금 구현해야 하는 기능은 다를 수 있다**는 것도 배우게 됐다.

---

## 수정 기능을 생각하면서 '원본이 무엇인지'가 중요해졌다

포스트 관리 기능을 고민하면서 새롭게 중요하게 느낀 개념이 있었다.

바로 **어떤 것이 실제 원본인가**였다.

현재 블로그에서는 배포된 화면이 원본이 아니다.

GitHub에 있는 포스트 파일이 원본이다.

화면은 그 파일을 기반으로 만들어진 결과다.

이 관계를 제대로 이해하지 않으면 블로그 화면에서 내용을 바꾸는 것만으로 수정이 끝났다고 생각하기 쉽다.

```text
포스트 파일
→ 실제 원본

배포된 페이지
→ 원본을 보여주는 결과
```

그렇다면 편집 기능을 만들 때도 결국 원본을 어떻게 바꿀지를 먼저 생각해야 했다.

이 개념은 블로그뿐 아니라 다른 서비스를 만들 때도 중요할 것 같았다.

---

## 관리 기능도 사용자 경험이었다

보통 사용자 경험이라고 하면 방문자가 사용하는 화면만 생각하기 쉽다.

하지만 내가 직접 운영하는 블로그에서는 나 역시 사용자였다.

나는 글을 읽기도 하지만

글을 추가하고,

수정하고,

분류하고,

배포하고,

결과를 확인한다.

이 과정이 지나치게 번거로우면 블로그를 계속 운영하는 데 영향을 줄 수 있다.

처음 만든 블로그가 오래 지속되지 못했던 이유 중 하나도 글 한 편을 작성할 때 반복해서 결정하고 처리해야 하는 일이 많았기 때문이다.

그래서 관리 기능을 개선하는 것은 단순한 편의 기능 이상의 의미가 있었다.

**글을 계속 작성할 수 있는 환경을 만드는 일**과 연결되어 있었다.

---

## 그렇다고 개발 환경을 완전히 없애고 싶지는 않았다

블로그 안에서 모든 것을 관리할 수 있으면 편할 것 같지만, 기존 개발 방식에도 장점이 있었다.

VS Code에서 전체 파일을 볼 수 있고,

Git diff로 변경사항을 확인할 수 있으며,

commit 단위로 수정 기록을 남길 수 있다.

Claude와 함께 여러 파일을 확인하면서 수정하기에도 현재 방식이 편했다.

그래서 최종 목표를

> 앞으로는 블로그에서만 모든 것을 수정한다.

로 잡고 싶지는 않았다.

오히려

```text
간단한 작업
→ 더 쉽게 접근

구조적인 수정
→ 기존 개발 환경 사용
```

처럼 작업의 성격에 따라 편한 방법을 사용할 수 있는 것이 더 현실적이었다.

관리자 기능이 생긴다고 개발 환경을 대체해야 하는 것은 아니었다.

## 작은 버튼 하나에서 백엔드까지 이어졌다

포스트 추가·수정 기능을 생각하기 시작했을 때는 화면에 버튼 몇 개를 추가하는 정도로 생각했다.

하지만 실제로 고민을 이어가니

UI,

파일 구조,

Git,

인증,

권한,

데이터 저장,

배포까지 연결됐다.

이 과정이 재미있었던 이유도 여기에 있었다.

겉으로는 아주 단순해 보이는 기능이 실제 서비스에서는 여러 영역과 연결되어 있었다.

특히 백엔드를 공부하기 시작하면서

> 왜 이런 기능에 서버가 필요하지?

라는 질문이 조금 더 구체적으로 보이기 시작했다.

사용자가 입력한 값을 안전하게 저장하고,

권한을 확인하고,

다시 불러오는 일이 필요해지는 순간 프론트 화면만으로는 해결하기 어려운 부분이 생겼다.

블로그 기능 개선이 자연스럽게 백엔드의 필요성을 이해하는 작은 예제가 됐다.

## 지금은 '편집 화면'보다 관리 흐름을 먼저 정리하고 있다

처음에는 예쁜 관리자 화면을 먼저 상상했다.

포스트 목록이 있고,

수정 버튼이 있고,

입력창에서 제목과 날짜를 바꾸는 모습이다.

하지만 실제로 중요한 것은 화면보다 그 뒤의 흐름이라는 것을 알게 됐다.

누가 수정할 수 있는가.

어떤 데이터를 수정하는가.

수정한 내용의 원본은 어디에 저장되는가.

현재 파일 기반 블로그와 어떻게 연결되는가.

잘못 수정했을 때 되돌릴 수 있는가.

이 질문들이 먼저 정해져야 했다.

그래서 관리자 화면을 크게 만드는 것보다 **현재 블로그의 관리 방식을 먼저 이해하고 필요한 부분부터 개선하는 것**이 우선이라고 생각했다.

## 포스트 관리 기능은 아직 발전 중이다

포스트 추가·수정 기능은 한 번에 완성된 기능이 아니었다.

처음에는 파일을 직접 수정했다.

Claude를 사용하면서 파일을 찾고 수정하는 과정이 편해졌다.

그다음에는 블로그 화면에서 바로 추가·수정 작업으로 이어지는 방법을 생각했다.

그리고 실제 브라우저 안에서 내용을 직접 관리하려고 하니 인증과 데이터 저장이라는 더 큰 문제가 있다는 것을 알게 됐다.

현재는 이 과정을 모두 한 번에 구현하기보다 단계별로 나누어 보고 있다.

```text
파일 직접 관리
        ↓
Claude를 활용한 관리
        ↓
페이지에서 관리 작업으로 쉽게 접근
        ↓
간단한 편집 기능
        ↓
필요하다면 인증·DB를 포함한 관리자 기능
```

처음부터 마지막 단계까지 갈 필요는 없다.

실제로 사용하면서 필요한 수준까지 발전시키면 된다.

## 가장 크게 바뀐 것은 기능보다 관리 방식을 보는 시선이었다

처음에는 포스트를 추가하고 수정하는 것이 단순한 파일 작업이라고 생각했다.

그리고 블로그 안에 버튼이 있으면 더 편해질 것이라고 생각했다.

하지만 기능을 하나씩 생각하면서 그 뒤에 있는 구조까지 보게 됐다.

**화면에서 수정할 수 있다는 것은 결국 누가, 무엇을, 어디에 저장할 수 있는지를 결정하는 문제였다.**

이것을 알게 된 뒤에는 새로운 기능을 볼 때도 화면만 보지 않게 됐다.

사용자가 버튼을 누른 다음 데이터가 어디로 가는지,

어떤 권한이 필요한지,

무엇이 실제 원본인지까지 생각하게 됐다.

포스트 추가·수정 기능은 아직 계속 발전하고 있다.

하지만 완성된 관리자 페이지보다 먼저 얻은 것은 분명했다.

단순히 글을 보여주는 블로그를 만들던 단계에서 벗어나, **내가 직접 계속 운영할 수 있는 블로그의 구조를 고민하기 시작했다는 것**이다.

결국 포스트 관리 기능을 발전시키는 목적도 버튼을 하나 더 만드는 데 있지 않았다.

**글을 쓰고 수정하는 과정에서 반복되는 불편을 줄여서, 기록을 계속 이어갈 수 있게 만드는 것.**

그것이 내가 이 기능을 발전시키고 싶은 가장 큰 이유였다.
