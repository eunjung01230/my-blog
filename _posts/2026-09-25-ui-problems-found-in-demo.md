지금까지 UI를 공부하면서 여러 기준을 정리했다.

```text
시선의 흐름

사용하기 쉬운 화면

버튼과 정보의 우선순위

페이지 구성

Empty State

반응형 디자인
```

이런 내용을 알고 나면

화면을 만들 때 이전보다 훨씬 많은 것을 생각하게 된다.

Figma에서도 확인하고,

Claude Design이나 AI가 만든 화면도 검토하고,

실제 코드로 구현된 화면도 비교할 수 있다.

그런데 여기까지 해도 끝이 아니었다.

실제로 서비스를 실행하고 직접 눌러보면

또 다른 문제가 보였다.

```text
Figma에서는 괜찮았는데
왜 실제로 보니까 작지?

버튼이 있기는 한데
왜 잘 안 보이지?

설명은 정확한데
왜 이렇게 읽기 싫지?

화면은 정리되어 있는데
왜 사용 순서가 어색하지?
```

디자인 화면을 보는 것과

**실제로 서비스를 사용하는 것**

은 달랐다.

이번 글에서는 실제 화면을 시연하면서 알게 된

```text
디자인 단계에서는 발견하기 어려웠던 UI 문제
```

를 정리해보려고 한다.

---

## Figma에서는 모든 것을 알고 있는 상태였다

디자인을 만드는 사람에게는 문제가 하나 있다.

자신이 만든 화면을 너무 잘 알고 있다.

예를 들어 내가 화면을 만들었다면 이미 알고 있다.

```text
시작 버튼은 여기 있다.

설정은 오른쪽 위다.

이 카드를 누르면 상세로 간다.

이 숫자는 이런 의미다.
```

그래서 화면을 봤을 때 전혀 어렵지 않다.

버튼이 조금 작아도 바로 찾는다.

아이콘만 있어도 무슨 기능인지 안다.

설명이 부족해도 이미 의미를 알고 있다.

즉 나는 처음 보는 사용자가 아니다.

---

## 그래서 만든 사람이 보는 화면은 항상 조금 쉬워 보였다

예를 들어 이런 화면이 있다고 해보자.

```text
현재 거리

3.42 km

시간
18:24

탄천 인정 거리
2.81 km

[종료]
```

나는 이미

```text
이 화면은 러닝 진행 화면이고

종료 버튼을 누르면 러닝이 끝난다.
```

는 것을 알고 있다.

그러니 버튼이 작아도 문제를 느끼지 못할 수 있다.

하지만 실제 러닝 중인 상황을 생각하면 다르다.

```text
움직이고 있고

화면을 오래 보기 어렵고

짧은 순간에 숫자를 확인해야 하고

버튼도 바로 눌러야 한다.
```

그때는 화면을 책상 앞에서 보는 기준과 달라진다.

---

## 실제 시연을 하면서 가장 먼저 느낀 것은 크기였다

Figma에서는 적당해 보였던 요소들이 실제 화면에서는 작게 느껴질 수 있었다.

특히 중요한 행동일수록 더 그랬다.

러닝 화면을 정리하면서 실제로

```text
시작 버튼 확대

종료 버튼 확대

주요 텍스트 확대
```

같은 수정이 필요했다.

디자인 단계에서는

```text
버튼이 너무 크면 촌스럽지 않을까?
```

라고 생각할 수 있다.

하지만 실제 사용에서는

```text
바로 보여야 하는가?

쉽게 누를 수 있는가?
```

가 더 중요했다.

---

## 중요한 버튼은 보기 좋은 크기보다 사용하기 좋은 크기가 중요했다

예를 들어 시작 버튼이 있다.

```text
[시작]
```

처음 디자인에서는 주변 UI와 균형을 맞추기 위해 적당한 크기로 만들 수 있다.

하지만 이 서비스에서 사용자가 홈에 들어온 가장 큰 이유가

```text
러닝 시작
```

이라면 이야기가 달라진다.

시작 버튼은 다른 요소들과 같은 정도로 보여서는 안 될 수 있다.

```text
현재 위치

내 기록

설정

러닝 시작
```

이 모두 비슷하게 보이면

핵심 행동이 약해진다.

그래서 실제 화면을 보면서

```text
이건 생각보다 더 커도 되겠다.
```

는 판단이 생길 수 있었다.

---

## 종료 버튼은 더 어려운 문제였다

종료 버튼은 중요하다.

러닝을 끝내려면 바로 찾을 수 있어야 한다.

하지만 동시에 위험한 행동이기도 하다.

실수로 누르면 안 된다.

즉 두 가지 요구가 동시에 있다.

```text
잘 보여야 함

+

실수로 눌리면 안 됨
```

그래서 단순히

```text
크게 만들자.
```

로 끝나는 문제가 아니었다.

위치,

크기,

색상,

주변 버튼과의 거리,

종료 후 확인 흐름까지 함께 생각해야 했다.

실제 사용 상황을 생각하지 않았다면 놓치기 쉬운 부분이었다.

---

## 숫자도 화면에서 직접 보니 중요도가 달라졌다

러닝 화면에는 여러 숫자가 있다.

```text
총 거리

시간

인정 거리

페이스
```

디자인할 때는

```text
모두 운동 정보니까
비슷한 스타일로 정리하자.
```

라고 생각할 수 있다.

하지만 실제 진행 중에는 모든 숫자를 똑같이 읽지 않는다.

사용자가 빠르게 확인해야 할 숫자가 있다.

그래서

```text
어떤 숫자가 가장 먼저 보여야 하는가?
```

를 다시 보게 된다.

「버튼과 정보의 우선순위」에서 공부했던 정보 우선순위가

실제 화면에서는 훨씬 직접적인 문제로 나타났다.

---

## 실제 사용 상황을 생각하면 글자 크기의 기준도 달라졌다

책상에 앉아서 화면을 보는 것과

밖에서 움직이면서 화면을 보는 것은 다르다.

```text
조명

거리

손의 움직임

사용 시간
```

이 다르다.

그래서 단순히

```text
디자인상 균형이 맞는 글자 크기
```

보다

```text
실제 상황에서 바로 읽을 수 있는 크기
```

를 생각해야 했다.

---

## 또 다른 문제는 설명이 너무 많아지는 것이었다

프로젝트를 정확하게 만들려고 할수록

설명도 많아진다.

예를 들어 혜택 관리 서비스에는 여러 규칙이 있을 수 있다.

```text
유효기간

사용 가능 매장

브랜드 정책

적립 조건

등록 상태

사용 조건
```

서비스를 만든 사람 입장에서는

```text
이것도 알려줘야 하고

저것도 정확하게 설명해야 한다.
```

고 생각하게 된다.

결과적으로 화면에 글이 많아진다.

---

## 정확하게 만들려다 오히려 화면이 어려워질 수 있었다

내가 만들면서 중요하게 생각했던 것도

```text
최대한 정확하게
```

였다.

잘못된 정보를 보여주고 싶지 않았다.

문제는 정확성을 화면에 그대로 다 노출하려고 할 때였다.

예를 들어 내부적으로 판단해야 하는 규칙을 모두 화면에 적으면

사용자는 서비스를 이용하기 전에 설명부터 읽어야 한다.

```text
이 혜택은 해당 브랜드 정책에 따라
특정 조건을 만족한 매장에서...
```

내용 자체는 맞을 수 있다.

하지만 사용자가 지금 알고 싶은 것은 훨씬 단순할 수 있다.

```text
여기서 쓸 수 있어?
```

이다.

---

## 그래서 내부 규칙을 한 단계 아래로 숨기는 방법을 생각했다

핵심 화면에서는 결과부터 보여준다.

```text
사용 가능

3일 뒤 만료
```

그리고 필요한 사용자가

```text
사용 조건 보기
```

를 눌렀을 때 자세한 내용을 보여준다.

```text
핵심 결과
↓
필요하면 상세 규칙
```

구조다.

이렇게 하면 정확성을 버리는 것이 아니다.

정보의 위치를 바꾸는 것이다.

---

## 모든 정보를 보여주는 것과 정보를 숨기는 것은 같은 문제가 아니었다

여기서

```text
그럼 설명을 전부 없애면 되는 건가?
```

라는 생각이 들 수 있다.

그렇지는 않다.

사용자가 판단하는 데 필요한 정보까지 숨기면 안 된다.

예를 들어

```text
쿠폰 1개
```

만 보여주고

```text
오늘 만료
```

정보를 숨긴다면 문제가 된다.

따라서 기준은

```text
이 정보가 지금 행동하는 데 필요한가?
```

였다.

필요하다면 바로 보여준다.

아니라면 한 단계 아래로 보낼 수 있다.

---

## 시연하면서 알게 되는 것은 정보량만이 아니었다

실제 화면을 보면

```text
이 설명이 길다.
```

뿐 아니라

```text
이 카드 자체가 너무 크다.

이 버튼이 너무 많다.

여기가 비어 보인다.

같은 내용이 반복된다.
```

같은 것도 발견할 수 있다.

Figma에서 하나씩 만든 화면을 볼 때는 괜찮았는데

서비스를 처음부터 끝까지 이어서 사용하면

반복이 훨씬 잘 보인다.

---

## 페이지 하나가 아니라 흐름으로 보게 됐다

디자인할 때는 화면을 하나씩 본다.

```text
Home

Detail

Record

Settings
```

각각 예쁘게 만든다.

하지만 실제 시연에서는

```text
Home
↓
Detail
↓
뒤로가기
↓
Record
↓
Record Detail
```

처럼 이동한다.

이때 다른 문제가 보인다.

```text
왜 같은 정보를 또 보여주지?

왜 이 페이지를 한번 더 거쳐야 하지?

뒤로 갔더니 아까 상태가 사라졌네?

이 버튼은 왜 갑자기 다른 위치에 있지?
```

개별 화면만 볼 때는 발견하기 어려운 문제다.

---

## 페이지 이동 횟수가 실제로 많게 느껴질 수 있었다

기획 문서에서

```text
A
↓
B
↓
C
```

를 보면 크게 불편해 보이지 않는다.

하지만 실제로 매번 눌러보면

```text
굳이 이 페이지를 한번 더 들어가야 하나?
```

싶을 수 있다.

반대로 화면을 합쳐놓았더니 너무 복잡할 수도 있다.

결국

```text
페이지 수를 적게 만들기
```

보다

```text
사용자의 행동 흐름이 자연스러운가
```

가 중요했다.

---

## 뒤로가기도 직접 써보면 문제가 보였다

예를 들어

```text
목록
↓
상세
```

로 이동한다.

상세에서 뒤로간다.

그런데

```text
스크롤 위치 초기화

필터 초기화

검색어 초기화
```

가 되어버릴 수 있다.

기능적으로는 목록으로 돌아갔다.

하지만 사용자는

```text
아까 보던 곳 어디 갔지?
```

가 된다.

이런 문제는 정적인 디자인만 보고는 거의 발견하기 어렵다.

---

## 버튼 위치가 페이지마다 달라지는 것도 불편했다

예를 들어

```text
Home
→ 설정 오른쪽 위

Detail
→ 설정 없음

Record
→ 설정 왼쪽 아래
```

처럼 같은 기능의 위치가 계속 달라진다면

사용자가 매번 다시 찾아야 한다.

디자인할 때 각 페이지를 따로 보면

각각 자연스러워 보일 수 있다.

하지만 연속해서 사용하면

```text
왜 같은 기능이 계속 이동하지?
```

라는 문제가 보인다.

그래서 공통 기능은 가능한 한 위치와 표현을 일정하게 유지하는 것이 좋았다.

---

## 아이콘만 보고 의미를 알 수 있다고 생각했던 것도 다시 보게 됐다

개발자나 디자이너에게는 익숙한 아이콘이 많다.

```text
⚙
→ 설정

🔍
→ 검색

✎
→ 수정
```

하지만 서비스 전용 아이콘은 이야기가 다르다.

내가 만든 사람이라면 의미를 알고 있다.

처음 보는 사용자는 모른다.

시연하면서

```text
이 아이콘만 보고 기능을 알 수 있을까?
```

를 다시 생각하게 된다.

중요한 기능이라면

```text
아이콘 + 텍스트
```

가 더 나을 수도 있다.

---

## "누르면 알겠지"는 좋지 않은 기준이었다

어떤 버튼의 의미가 애매한데

```text
눌러보면 알 수 있으니까 괜찮겠지.
```

라고 생각할 수 있다.

하지만 사용자가 잘못 누르는 것을 꺼릴 수도 있다.

특히

```text
삭제

결제

종료

데이터 변경
```

같은 행동이라면 더 그렇다.

가능하면 누르기 전에 결과를 어느 정도 예상할 수 있어야 한다.

---

## 실제 화면에서는 버튼의 개수가 더 많아 보였다

Figma에서 버튼 하나씩 볼 때는 괜찮다.

하지만 전체 화면에서

```text
[수정]

[삭제]

[길찾기]

[공유]

[상세보기]

[추가]
```

가 동시에 보이면

생각보다 매우 많아 보일 수 있다.

이럴 때

```text
정말 버튼이어야 하는가?
```

를 다시 확인한다.

---

## 버튼을 줄이는 방법도 여러 가지였다

예를 들어

```text
[상세보기]
```

는 카드 전체 클릭으로 대체할 수 있다.

```text
[공유]
```

는 작은 아이콘으로 바꿀 수 있다.

```text
삭제
```

는 더보기 메뉴 안에 둘 수 있다.

```text
[저장]
```

처럼 핵심 행동만 강하게 남긴다.

결과적으로

```text
버튼 디자인 수정
```

이 아니라

```text
행동 구조 정리
```

가 된다.

---

## 터치하면서 느끼는 문제도 있었다

Figma에서는 마우스로 화면을 만든다.

PC 브라우저에서도 마우스로 확인할 수 있다.

하지만 모바일 서비스라면 실제 사용은 손가락이다.

그러면 작은 차이가 커진다.

```text
아이콘이 너무 작음

버튼끼리 너무 가까움

화면 끝에 붙어 있음

하단 영역을 누르기 불편함
```

같은 문제다.

---

## 보이는 크기와 눌리는 크기는 다르게 생각해야 했다

예를 들어 아이콘 자체는 24px이어도 된다.

하지만 실제 클릭 영역까지 24px일 필요는 없다.

주변에 충분한 터치 영역을 줄 수 있다.

```text
보이는 아이콘

   24px

클릭 가능한 영역

   더 크게
```

이렇게 하면 디자인을 복잡하게 만들지 않으면서 사용하기 쉬워질 수 있다.

---

## 실수로 눌릴 가능성도 실제 사용에서 더 잘 느껴졌다

예를 들어

```text
[저장] [삭제]
```

버튼이 붙어 있다.

PC에서 마우스로는 정확하게 선택할 수 있다.

모바일에서는 손가락이다.

특히 급하게 사용하는 상황이라면 잘못 누를 가능성이 더 커진다.

이때는

```text
간격을 늘리거나

삭제를 다른 위치로 보내거나

확인 단계를 추가
```

할 수 있다.

---

## 스크롤도 직접 해봐야 알 수 있었다

디자인에서는 전체 Frame을 한 번에 본다.

아래까지 모두 보인다.

실제 모바일에서는 화면 일부만 보이고 스크롤해야 한다.

그러면

```text
Primary 버튼이 너무 아래에 있음

중요 정보가 첫 화면에 안 보임

설명이 길어서 핵심 기능이 밀림
```

같은 문제가 나타난다.

Figma 전체 화면에서는 멀쩡해 보였던 것이

실제 Viewport에서는 달라진다.

---

## 첫 화면에서 무엇이 보이는지 다시 확인했다

예를 들어 사용자가 Home에 들어왔는데

첫 화면에

```text
서비스 설명

안내 문구

배너
```

만 보이고

정작 핵심 버튼은 스크롤해야 나온다면 문제가 될 수 있다.

그래서 실제 크기로 띄워놓고 확인해야 했다.

```text
스크롤하지 않은 상태에서
무엇이 보이는가?
```

이것이 중요했다.

---

## Fixed 버튼도 실제로 써봐야 했다

모바일에서 하단 CTA를 고정하면 편하다.

```text
[러닝 시작]
```

같은 버튼이다.

하지만 실제로 적용하면

```text
마지막 카드가 가림

하단 Navigation과 겹침

화면이 작은 기기에서 공간 부족
```

같은 문제가 나타날 수 있다.

그래서 고정 요소 자체뿐 아니라

```text
고정 요소가 주변 UI에 어떤 영향을 주는가
```

를 확인해야 했다.

---

## 지도 화면은 시연했을 때 특히 느낌이 달랐다

지도 중심 화면은 정적인 디자인과 실제 사용의 차이가 크다.

Figma에서는

```text
지도

현재 위치

카드

버튼
```

이 모두 깔끔하게 배치되어 있다.

실제 지도에서는

```text
지도 정보

Marker

내 위치

Zoom

Overlay
```

가 계속 바뀐다.

그 위에 카드나 버튼이 올라가면

생각보다 화면이 복잡해질 수 있다.

---

## 지도 위 UI는 특히 크기와 위치가 중요했다

지도는 이미 정보량이 많다.

그 위에

```text
검색창

GPS 버튼

카드

Navigation

설정
```

까지 올라간다.

각 UI만 따로 보면 작고 깔끔하지만

전체를 실제 지도 위에 올리면

```text
지도보다 UI가 더 많이 보임
```

상황이 생길 수 있다.

그래서 지도 서비스는 실제 지도 상태에서 확인하는 것이 중요했다.

---

## 화면 설명이 많으면 지도를 가릴 수도 있었다

지도 기반 서비스에서 사용 방법을 친절하게 알려주려고

안내 카드나 설명을 계속 추가하면

정작 지도 영역이 줄어든다.

즉

```text
설명 친절함

vs

핵심 기능 사용 공간
```

사이의 균형이 필요했다.

이런 문제도 실제 화면을 보면 훨씬 쉽게 느껴진다.

---

## 실제 데이터가 들어오면 카드 높이가 달라졌다

디자인에서는 데이터를 예쁘게 맞춘다.

```text
컴포즈커피 판교점
```

한 줄이다.

실제 데이터는 길 수 있다.

```text
컴포즈커피 성남판교테크노밸리○○점
```

두 줄이 된다.

그러면

```text
카드 높이 증가

버튼 위치 이동

옆 카드와 높이 차이
```

가 생긴다.

---

## 긴 데이터는 UI 테스트의 좋은 재료였다

실제 시연 전에도 일부러 넣어볼 수 있다.

```text
가장 긴 매장명

가장 긴 사용자 이름

가장 긴 설명

혜택이 가장 많은 상태
```

를 넣는다.

이런 테스트용 데이터를 보면

예쁜 정상 상태에서는 발견하지 못한 문제를 빨리 찾을 수 있다.

---

## 반대로 데이터가 너무 적을 때도 문제였다

카드가 10개 있을 때는 화면이 자연스럽다.

카드가 1개뿐이면

```text
화면이 지나치게 비어 보임
```

일 수 있다.

데이터가 0개면 Empty State가 필요하다.

즉

```text
0개

1개

많음
```

을 각각 봐야 했다.

---

## 실제 시연에서는 Loading도 보인다

Figma에서는 데이터가 이미 화면에 있다.

실제 서비스에서는 시간이 걸린다.

```text
화면 진입

↓

로딩

↓

데이터 표시
```

가 있다.

이때 1~2초 동안 아무것도 보이지 않는다면

사용자는

```text
안 되는 건가?
```

라고 생각할 수 있다.

그래서 실제 시연을 해야

```text
Loading UI가 필요하겠다.
```

는 것이 더 잘 느껴졌다.

---

## 버튼을 눌렀을 때 반응도 중요했다

예를 들어

```text
[저장]
```

을 눌렀다.

아무것도 안 바뀐다.

실제로는 서버 요청 중이다.

사용자는 모른다.

다시 누를 수 있다.

그래서

```text
[저장]
↓
[저장 중...]
↓
저장 완료
```

같은 피드백이 필요하다.

정적인 화면 디자인에서는 놓치기 쉬운 부분이다.

---

## 성공했을 때도 알려줘야 했다

사용자가 값을 저장했다.

화면이 그대로다.

```text
저장된 건가?
```

알 수 없다.

이때

```text
저장되었습니다.
```

Toast를 보여주거나,

화면 상태를 바꿔줄 수 있다.

즉 UI에는

```text
행동 전

행동 중

행동 후
```

가 있다.

---

## 오류도 실제로 만나야 문제를 느끼기 쉬웠다

개발 중에는 정상 흐름부터 테스트한다.

하지만 실제 서비스에서는 오류가 발생할 수 있다.

```text
네트워크 실패

로그인 만료

권한 없음

데이터 요청 실패
```

이때 화면에

```text
400

500

Unauthorized
```

만 나오면 사용자는 이해하기 어렵다.

시연 과정에서 일부러 실패 상황도 확인할 필요가 있었다.

---

## 오류 화면의 핵심은 기술 설명이 아니었다

사용자에게 필요한 것은

```text
무슨 문제가 생겼고

지금 무엇을 하면 되는가
```

이다.

예를 들어

```text
위치 정보를 가져올 수 없습니다.

잠시 후 다시 시도해주세요.

[다시 시도]
```

처럼 보여줄 수 있다.

개발 로그는 개발자가 보고,

화면은 사용자의 언어로 보여준다.

---

## 실제 시연에서 가장 중요한 것은 내가 설명하지 않는 것이었다

내가 서비스를 보여주고 있는데 상대방이 멈춘다.

그 순간 바로

```text
여기 누르면 돼요.
```

라고 설명하고 싶어진다.

하지만 UI를 확인하는 상황이라면 조금 기다려보는 것이 더 도움이 된다.

왜냐하면

```text
어디에서 멈추는가
```

자체가 정보이기 때문이다.

---

## 설명하지 않고 관찰해야 하는 것

예를 들어 사용자에게

```text
러닝을 시작해보세요.
```

라고만 말한다.

그리고 본다.

```text
어디를 먼저 보는가?

바로 시작 버튼을 찾는가?

다른 버튼을 누르는가?

설명 문구부터 읽는가?

멈추는가?
```

이런 행동이 실제 UI를 평가하는 자료가 된다.

---

## 사용자의 질문도 중요한 자료였다

시연 중 이런 질문이 나올 수 있다.

```text
이건 뭐예요?

여기 누르면 어떻게 돼요?

저장은 어디에 있어요?

뒤로가기는 어디예요?

이 숫자는 무슨 뜻이에요?
```

이 질문들은

그 사람이 서비스를 못 이해했다는 뜻으로만 볼 것이 아니다.

화면에서 설명이 부족하거나,

정보 우선순위가 잘못되었거나,

표현이 애매할 수 있다는 신호다.

---

## 반복해서 나오는 질문은 더 중요했다

한 사람만 특정 기능을 못 찾는다면

개인 차이일 수도 있다.

하지만 여러 번 시연하면서 같은 부분에서 계속

```text
이거 어디 있어?
```

가 나온다면

UI 문제일 가능성을 더 생각해볼 수 있다.

그러면

```text
사용자에게 알려주는 법
```

보다 먼저

```text
화면에서 더 쉽게 찾게 만들 방법
```

을 고민한다.

---

## 시연할 때 내가 옆에서 너무 많이 설명하면 문제를 놓칠 수 있었다

발표나 시연에서는 서비스를 설명해야 한다.

그래서

```text
여기서 이걸 누르고요.

다음에는 이 버튼을 누르면...
```

이라고 알려준다.

그러면 서비스가 아주 자연스럽게 작동하는 것처럼 보인다.

하지만 실제 사용자에게는 그 설명자가 없다.

따라서

```text
발표용 시연
```

과

```text
사용성 확인
```

은 조금 다르게 볼 필요가 있었다.

---

## 발표 전에 한 번은 설명 없이 사용해보는 것이 좋았다

내가 직접 만든 서비스라도

처음 사용자라고 생각하면서

```text
설명 없이 처음부터 사용
```

해보는 것이다.

그리고 일부러 질문한다.

```text
이 화면이 무슨 화면인지 바로 알 수 있나?

다음 행동이 보이나?

버튼 이름만 보고 결과를 예상할 수 있나?
```

완벽한 사용자 테스트는 아니더라도

많은 문제를 발견할 수 있다.

---

## 실제 기기에서 확인하는 것도 중요했다

PC 브라우저의 작은 창으로 모바일 크기를 확인하는 것과

실제 스마트폰을 손에 들고 사용하는 것은 다르다.

```text
손가락 크기

화면 밝기

기기 비율

스크롤 느낌

하단 시스템 영역
```

등이 다르다.

모바일 중심 서비스라면 가능하면 실제 기기에서도 확인하는 것이 좋았다.

---

## 배포된 화면에서 또 다르게 보일 수도 있었다

로컬 개발 환경에서는 잘 보였는데

실제 배포 URL로 접속했을 때

```text
폰트 로딩

이미지

환경 변수

실제 데이터

브라우저 차이
```

때문에 다르게 보일 수 있다.

그래서

```text
로컬 확인
```

으로 끝내지 않고

```text
배포된 서비스 확인
```

까지 해보는 것이 필요했다.

---

## 링크로 직접 들어오는 상황도 있었다

개발할 때는 항상 Home부터 시작한다.

하지만 실제 사용자는

```text
공유 링크

검색 결과

북마크
```

를 통해 Detail 페이지로 바로 들어올 수도 있다.

그때도

```text
이게 어떤 서비스인지

어디에 있는지

다음에는 어디로 갈 수 있는지
```

알 수 있어야 한다.

페이지를 순서대로 들어온다는 가정만 하면 놓칠 수 있다.

---

## 시연을 통해 발견한 문제를 바로 전부 고칠 필요는 없었다

문제가 보이면 전부 수정하고 싶어진다.

```text
버튼 위치 수정

색상 변경

새 기능 추가

Navigation 수정

설명 추가
```

를 한 번에 할 수 있다.

하지만 그러면 무엇 때문에 좋아졌는지 알기 어렵다.

또 수정하면서 새로운 문제가 생길 수도 있다.

그래서 문제를 먼저 정리하는 것이 좋았다.

---

## 문제와 해결책을 분리한다

예를 들어

```text
문제:
사용자가 시작 버튼을 바로 찾기 어렵다.
```

가 있다고 하자.

바로

```text
해결:
초록색으로 바꾼다.
```

라고 결정하지 않는다.

가능한 해결책은 여러 개다.

```text
크기 확대

위치 이동

주변 정보 약화

색상 강조

문구 변경
```

가 있다.

먼저 문제를 정확하게 적어두고

그다음 가장 적절한 방법을 선택한다.

---

## "화면이 별로다"는 문제 정의로 부족했다

시연 후

```text
홈이 좀 별로다.
```

라고 적으면 수정하기 어렵다.

조금 더 구체적으로 바꾼다.

```text
Home에서 가장 중요한 시작 버튼보다
상단 카드가 먼저 눈에 들어온다.
```

이렇게 쓰면 해결 방향도 보인다.

```text
카드 강조를 줄이거나

버튼 크기를 키우거나

위치를 변경
```

할 수 있다.

---

## UI 문제를 종류별로 나눠볼 수 있었다

예를 들어 이렇게 나눌 수 있다.

```text
발견성
→ 기능을 찾지 못함

가독성
→ 글자나 정보가 잘 안 읽힘

우선순위
→ 무엇이 중요한지 모름

Navigation
→ 어디로 가야 할지 모름

Feedback
→ 눌렀는데 결과를 모름

Content
→ 설명이 너무 많거나 부족함

Responsive
→ 특정 크기에서 깨짐

Touch
→ 누르기 어려움
```

문제를 분류하면 수정하기도 쉬워진다.

---

## 예시 — 버튼을 찾기 어려움

```text
현상
→ 사용자가 시작 버튼을 바로 찾지 못함

가능한 원인
→ 버튼이 작음
→ 주변 요소와 강조 정도가 비슷함
→ 위치가 예상과 다름

수정 후보
→ 크기 확대
→ 주변 요소 강조 감소
→ 위치 변경
```

이런 식이다.

---

## 예시 — 화면에 글이 너무 많음

```text
현상
→ 사용자가 설명을 읽지 않고 넘어감

가능한 원인
→ 화면에 내부 규칙까지 노출
→ 핵심 정보와 보조 설명이 구분되지 않음

수정 후보
→ 핵심 결과만 먼저 표시
→ 상세 규칙은 펼쳐보기
→ 문구 축약
```

단순히

```text
폰트 크기 줄이기
```

로 해결할 문제가 아닐 수 있다.

---

## 예시 — 기능은 있는데 사용자가 찾지 못함

이 경우

```text
기능을 새로 만들어야 하는가?
```

부터 생각할 필요는 없다.

기존 기능의

```text
위치

이름

아이콘

강조 수준
```

문제일 수 있다.

이것이 실제 시연이 중요한 이유다.

코드에 기능이 존재한다는 것과

사용자가 기능을 사용할 수 있다는 것은 다르다.

---

## "구현 완료"와 "사용 가능"은 다르다는 것을 알게 됐다

개발 기준에서는

```text
버튼 존재

클릭 이벤트 연결

API 정상 동작
```

이면 구현이 끝난 것으로 볼 수 있다.

하지만 UI/UX 기준에서는

```text
사용자가 버튼을 찾고

무슨 기능인지 이해하고

실수 없이 누르고

결과를 이해
```

할 수 있어야 한다.

그래서

```text
기능 구현 완료
```

와

```text
사용 경험 완료
```

는 같지 않았다.

---

## 디자인 QA라는 생각도 이해하게 됐다

코드를 만들고 나면 기능 테스트를 한다.

```text
로그인 됨?

저장 됨?

삭제 됨?
```

UI에서도 비슷하게 확인할 수 있다.

```text
Figma와 비슷한가?

정렬이 맞는가?

간격이 일정한가?

반응형이 깨지지 않는가?

상태별 화면이 있는가?
```

이런 확인을 일종의 Design QA처럼 생각할 수 있었다.

---

## 기능 QA와 UI QA를 같이 보면 좋았다

예를 들어 혜택 등록 기능이라면

### 기능 확인

```text
등록 성공?

DB 저장?

새로고침 후 유지?
```

### UI 확인

```text
등록 버튼 찾기 쉬움?

입력 중 오류 표시됨?

저장 중 상태 보임?

완료 후 결과 알 수 있음?

등록 후 목록에 바로 보임?
```

둘 다 통과해야 실제 기능이 완성된다.

---

## 시연 후 수정 우선순위도 필요했다

UI 문제를 여러 개 발견했다고 해보자.

```text
버튼 2px 어긋남

핵심 기능 못 찾음

아이콘 크기 조금 다름

모바일에서 버튼 겹침

설명 문구 어색함
```

전부 같은 중요도는 아니다.

먼저

```text
기능을 사용할 수 없는 문제

핵심 행동을 방해하는 문제

실수할 가능성이 큰 문제
```

를 해결하는 편이 좋다.

---

## 내가 생각하는 수정 우선순위

대략 이렇게 나눠볼 수 있었다.

### 1순위 — 사용 불가

```text
버튼을 누를 수 없음

화면이 깨짐

핵심 기능 접근 불가
```

### 2순위 — 사용하기 어려움

```text
버튼을 못 찾음

의미를 이해하기 어려움

중요한 정보가 잘 안 보임
```

### 3순위 — 불편함

```text
이동 단계가 많음

설명이 많음

반복 입력이 있음
```

### 4순위 — 시각적 디테일

```text
간격

색상 미세 차이

아이콘 정렬
```

모두 중요할 수 있지만

순서가 있다.

---

## 예쁘게 다듬는 것은 마지막이어도 됐다

처음에는

```text
Border Radius가 조금 이상하다.
```

가 크게 보인다.

하지만 사용자가

```text
저장 버튼이 어디 있는지 모르겠다.
```

고 한다면 우선순위는 명확하다.

```text
사용 흐름
↓
시각적 디테일
```

순서로 수정한다.

---

## 시연 후 기능을 추가하고 싶을 때도 조심했다

사용자가 어떤 행동을 못 했다.

그러면 바로

```text
새 버튼 만들자.
```

고 생각하기 쉽다.

하지만 기존 기능을 찾지 못한 것일 수도 있다.

예를 들어

```text
길찾기가 없다고 생각함
```

→ 실제로는 아이콘 버튼으로 있음.

그렇다면 새로운 기능이 아니라

```text
발견성 개선
```

이 필요하다.

---

## 사용자 요청과 사용자 문제도 구분해야 했다

누군가

```text
여기에 버튼 하나 더 있으면 좋겠어요.
```

라고 할 수 있다.

그 의견을 그대로 기능으로 추가하기 전에

```text
왜 버튼이 필요했을까?
```

를 생각한다.

원인은

```text
기존 기능을 찾기 어려움
```

일 수도 있다.

그렇다면 더 좋은 해결법은 기존 기능을 잘 보이게 만드는 것이다.

---

## 시연 결과가 기획까지 바꿀 수도 있었다

UI를 확인하다가

```text
이 페이지 자체가 필요 없겠다.
```

는 결론이 나올 수도 있다.

또

```text
이 기능은 생각보다 사용 흐름을 너무 복잡하게 만든다.
```

고 느낄 수도 있다.

그렇다면 디자인 수정만의 문제가 아니다.

```text
기획
↓
정보 구조
↓
UI
```

까지 다시 볼 수 있다.

---

## 하지만 한번 시연했다고 모든 것을 바꾸지도 않는다

한 번 사용해보고

```text
이상한 것 같아.
```

라는 느낌만으로 전체 구조를 뒤집으면 또 문제가 생길 수 있다.

특히 다른 사람의 한 번의 의견만으로

서비스 전체 방향을 바꾸는 것도 조심해야 한다.

그래서

```text
반복해서 나타나는 문제인가?

핵심 흐름을 방해하는가?

실제 사용 환경에서 발생하는가?
```

를 보고 판단한다.

---

## 기록을 남기면 다음 프로젝트에서도 도움이 됐다

시연 후 발견한 문제를 간단히 적어둘 수 있다.

예를 들어

```text
문제
→ 시작 버튼이 작아 발견성이 낮음

수정
→ 버튼 크기 확대

결과
→ 핵심 행동이 더 명확해짐
```

또는

```text
문제
→ 혜택 카드의 설명이 너무 많음

수정
→ 핵심 정보만 노출하고
   상세 규칙은 한 단계 아래로 이동
```

처럼 기록한다.

그러면 다음 프로젝트에서 같은 실수를 덜 반복할 수 있다.

---

## Before / After를 남기는 것도 좋았다

예를 들어

```text
Before

작은 시작 버튼

↓

After

핵심 CTA 크기 확대
```

처럼 저장해두면

왜 디자인을 바꿨는지 기억하기 쉽다.

단순히

```text
최종 디자인
```

만 남기는 것보다

```text
어떤 문제 때문에 바뀌었는지
```

가 학습에는 더 도움이 된다.

---

## 블로그에 기록할 때도 완성된 화면만 보여주지 않아도 됐다

개발 기록을 남기다 보면

완성된 결과만 보여주고 싶어진다.

하지만 내가 실제로 공부하는 데 더 도움이 되는 것은

```text
처음에는 이렇게 만들었다.

↓

실제로 써보니 이런 문제가 있었다.

↓

이렇게 수정했다.
```

라는 과정이다.

특히 UI/UX는

결과만 보면 왜 그렇게 설계했는지 알기 어렵다.

수정 이유까지 기록하면

디자인 판단 기준도 남길 수 있다.

---

## 시연하면서 발견한 문제는 실패 기록이 아니었다

처음에는

```text
Figma에서 제대로 했으면
수정할 일이 없어야 하는 것 아닌가?
```

라고 생각할 수 있다.

하지만 실제 서비스는 디자인 화면보다 훨씬 복잡하다.

```text
실제 데이터

실제 기기

실제 사용 행동

로딩

오류

권한

네트워크
```

가 들어온다.

따라서 시연 후 문제가 발견되는 것은 자연스럽다.

중요한 것은

```text
문제를 발견하지 않는 것
```

이 아니라

```text
문제를 발견한 뒤 어떤 기준으로 수정하는가
```

였다.

---

## 내가 직접 시연할 때 확인하고 싶은 것

앞으로는 화면을 실제로 띄웠을 때 이런 순서로 보려고 한다.

```text
1. 처음 화면에서 무엇이 가장 먼저 보이는가?

2. 핵심 행동을 바로 찾을 수 있는가?

3. 버튼 문구만 보고 결과를 예상할 수 있는가?

4. 글자가 실제 기기에서 충분히 잘 보이는가?

5. 터치 영역이 너무 작지는 않은가?

6. 설명을 읽지 않아도 기본 기능을 사용할 수 있는가?

7. 화면 이동 후 이전 맥락이 유지되는가?

8. 실제 긴 데이터에서도 Layout이 유지되는가?

9. 로딩 중이라는 것을 알 수 있는가?

10. 성공과 실패 결과를 알 수 있는가?

11. 데이터가 없을 때 다음 행동을 알 수 있는가?

12. 모바일 크기에서 중요한 UI가 겹치지 않는가?
```

---

## 다른 사람에게 보여줄 때 확인할 것

내가 너무 잘 알고 있는 화면이라는 문제를 줄이기 위해

다른 사람이 사용한다면 이런 것을 본다.

```text
□ 어디를 먼저 보는가?

□ 어디를 먼저 누르는가?

□ 어디에서 멈추는가?

□ 잘못 누르는 버튼이 있는가?

□ 반복해서 묻는 내용이 있는가?

□ 설명 없이 핵심 흐름을 완료할 수 있는가?

□ 예상했던 행동과 실제 행동이 다른가?
```

정답을 알려주는 것보다 관찰하는 것이 중요하다.

---

## 수정할 때 확인할 것

문제가 발견된 뒤에는

```text
□ 정확한 문제를 문장으로 적었는가?

□ 원인과 해결책을 구분했는가?

□ 기존 기획을 바꿀 정도의 문제인가?

□ 가장 작은 수정으로 해결할 수 있는가?

□ 다른 화면에도 같은 문제가 있는가?

□ 수정 후 다시 실제 화면에서 확인했는가?
```

를 본다.

---

## UI 문제는 연결되어 있었다

실제 시연하면서 느낀 가장 중요한 부분은

지금까지 공부한 UI 주제들이 서로 따로 있는 것이 아니라는 점이었다.

예를 들어 사용자가 버튼을 못 찾는다.

원인은 여러 가지일 수 있다.

```text
시선 흐름 문제

버튼 우선순위 문제

정보가 너무 많음

페이지 구조 문제

모바일 반응형 문제
```

중 하나거나 여러 개가 섞여 있을 수 있다.

그래서

```text
버튼을 못 찾음
→ 버튼 색만 변경
```

처럼 바로 해결하려 하기보다

전체 구조를 같이 보는 것이 좋았다.

---

## 실제 사용은 지금까지 배운 기준의 최종 확인이었다

「화면 정렬과 시선의 흐름」에서는

```text
사용자의 시선
```

을 봤다.

「예쁜 화면보다 사용하기 쉬운 화면」에서는

```text
사용하기 쉬운 화면
```

을 생각했다.

「버튼과 정보의 우선순위」에서는

```text
버튼과 정보의 우선순위
```

를 나눴다.

「정보 구조와 페이지 구성」에서는

```text
페이지 구조
```

를 정리했다.

「Empty State 설계」에서는

```text
Empty State
```

를 만들었다.

「반응형 디자인」에서는

```text
반응형
```

을 공부했다.

그리고 실제 시연은 이 모든 것이 정말 작동하는지 확인하는 단계였다.

---

## Figma가 틀렸다기보다 Figma만으로 알 수 없는 것이 있었다

Figma는 화면을 설계하는 데 정말 유용하다.

하지만 Figma의 정적인 Frame만으로는

```text
손가락으로 누르는 느낌

로딩 시간

실제 데이터 길이

페이지 이동

오류

실제 기기 크기
```

까지 완전히 느낄 수 없다.

그래서

```text
Figma
↓
구현
↓
시연
↓
수정
```

과정이 필요했다.

---

## 디자인은 구현하면 끝나는 것이 아니었다

처음에는

```text
Figma 완료
↓
코드 구현
↓
끝
```

이라고 생각했다.

실제로는

```text
기획

↓

Figma

↓

구현

↓

실제 사용

↓

문제 발견

↓

수정

↓

다시 사용
```

에 더 가까웠다.

그리고 이 반복 과정에서

처음보다 조금씩 더 사용하기 좋은 화면이 만들어졌다.

---

## 내가 시연 후 UI를 수정할 때 지키고 싶은 기준

정리하면 다음과 같다.

```text
1. 디자인 화면과 실제 사용 화면을 구분한다.

2. 중요한 버튼은 실제 사용 상황에서 충분히 보이는지 확인한다.

3. 글자 크기는 실제 기기에서 확인한다.

4. 화면에 설명이 너무 많지 않은지 확인한다.

5. 내부 규칙을 모두 첫 화면에 노출하지 않는다.

6. 개별 화면뿐 아니라 전체 사용자 흐름으로 확인한다.

7. 뒤로가기와 이전 상태 유지도 테스트한다.

8. 실제 긴 데이터와 데이터 0개 상태를 확인한다.

9. Loading / Success / Error 상태를 직접 확인한다.

10. 모바일에서는 실제 터치 가능성을 확인한다.

11. 시연 중에는 가능하면 바로 답을 알려주지 않는다.

12. 사용자가 멈춘 지점을 기록한다.

13. 문제와 해결책을 분리해서 생각한다.

14. 사용을 방해하는 문제부터 우선 수정한다.

15. 수정 후 반드시 다시 시연한다.
```

## 마무리

UI를 처음 만들 때는

```text
Figma에서 잘 보이면
디자인은 끝난다.
```

고 생각했다.

하지만 실제로 서비스를 실행해보니 달랐다.

```text
작아 보이는 버튼

읽지 않는 설명

찾지 못하는 기능

예상과 다른 클릭

겹치는 화면

긴 실제 데이터
```

같은 문제가 나타났다.

그리고 그 문제들은 대부분

정적인 화면만 보고 있을 때는 잘 보이지 않았다.

그래서 지금은 디자인을

```text
화면을 만드는 일
```

로만 생각하지 않는다.

```text
만들고

↓

직접 사용하고

↓

문제를 찾고

↓

다시 수정하는 일
```

까지 포함한다고 생각한다.

결국 시연은

> **완성된 디자인을 보여주는 마지막 단계가 아니라, 디자인이 정말 사용 가능한지 확인하는 테스트 단계**

였다.

그리고 실제 서비스를 완성해가다 보면

이제 기능이나 큰 Layout이 아닌

더 작은 부분들이 눈에 들어오기 시작한다.

예를 들어 브라우저 탭을 열었는데

```text
기본 아이콘
```

이 그대로 보일 수 있다.

기능에는 아무 문제가 없다.

사이트도 정상적으로 열린다.

하지만 서비스 전체를 보면

조금 덜 완성된 느낌이 든다.

이런 작은 요소들이 하나씩 쌓여

서비스의 인상을 만든다는 것도 알게 됐다.
