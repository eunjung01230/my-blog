favicon과 웹사이트 아이콘을 정리한 뒤에는 링크를 다른 곳에 공유했을 때 블로그가 어떻게 보이는지가 눈에 들어왔다.

브라우저 탭에서는 내 블로그 아이콘이 잘 보였지만, 메신저나 SNS에 링크를 붙여 넣으면 제목만 나오거나 내가 의도하지 않은 이미지가 보일 수 있었다.

처음에는 favicon을 바꾸면 공유 화면에도 비슷하게 적용될 것이라고 생각했지만 둘은 역할이 달랐다.

```text
favicon
→ 브라우저 탭에서 사이트 구분

OG 이미지
→ 링크를 공유했을 때 보여주는 대표 이미지
```

그래서 이번에는 블로그 안의 화면이 아니라 **블로그 링크가 밖에서 어떻게 보이는지** 정리해 보기로 했다.

---

## 링크는 URL만 공유되는 것이 아니었다

웹사이트 주소를 메신저나 SNS에 붙여 넣으면 서비스에 따라 이런 정보가 함께 표시된다.

```text
[대표 이미지]

포스트 제목
간단한 설명
사이트 주소
```

처음에는 서비스가 페이지를 알아서 읽고 적당한 내용을 보여주는 줄 알았다.

하지만 웹페이지에서 어떤 제목, 설명, 이미지를 사용할지 직접 알려줄 수 있었다.

그때 사용하는 대표적인 정보가 **Open Graph**, 줄여서 OG였다.

```html
<meta property="og:title" content="포스트 제목">
<meta property="og:description" content="포스트 설명">
<meta property="og:image" content="대표 이미지 주소">
<meta property="og:url" content="페이지 주소">
```

이 정보는 페이지 안에 직접 보이는 것은 아니지만 외부 서비스가 링크 미리보기 카드를 만들 때 활용할 수 있다.

---

## favicon과 OG 이미지는 목적이 달랐다

favicon과 OG 이미지는 모두 사이트를 대표하는 이미지처럼 보이지만 사용 환경이 다르다.

favicon은 아주 작은 크기로 사용되기 때문에 단순한 형태가 중요하다.

OG 이미지는 더 넓은 카드에서 사용되므로 블로그 이름이나 포스트 분위기를 조금 더 보여줄 수 있다.

```text
favicon
→ 작은 표식

OG 이미지
→ 링크를 열기 전에 보여주는 대표 화면
```

그래서 favicon 하나를 만들어 모든 곳에 그대로 쓰는 것보다 **사용 위치에 맞게 역할을 나누는 편**이 자연스러웠다.

---

## OG 이미지가 없으면 예상하지 못한 이미지가 나올 수 있었다

OG 이미지를 따로 지정하지 않아도 서비스가 페이지 안의 이미지를 찾아 대표 이미지로 사용하는 경우가 있다.

문제는 내가 그 이미지를 선택한 것이 아니라는 점이다.

본문 스크린샷이 대표 이미지처럼 보일 수도 있고, 이미지가 없다면 미리보기가 비어 있을 수도 있다.

같은 블로그인데 링크마다 전혀 다른 모습으로 보일 수 있었다.

그래서 별도의 대표 이미지가 없는 페이지에서도 사용할 수 있는 **기본 OG 이미지**를 두는 편이 좋겠다고 생각했다.

---

## 모든 포스트마다 이미지를 새로 만들 필요는 없었다

OG 이미지를 알게 되면 포스트마다 대표 이미지를 따로 만들고 싶어질 수 있다.

하지만 그렇게 하면 글을 하나 작성할 때 해야 할 일이 계속 늘어난다.

내 블로그의 가장 중요한 목적은 여전히 공부 내용을 기록하는 것이었다.

그래서 처음에는 단순하게 생각했다.

```text
포스트 전용 이미지가 있음
→ 해당 이미지 사용

별도의 이미지가 없음
→ 기본 OG 이미지 사용
```

이 정도만으로도 공유 화면은 어느 정도 일관되게 유지할 수 있었다.

---

## 제목과 설명도 같이 봐야 했다

링크 미리보기는 이미지 하나로 끝나지 않는다.

보통 제목, 설명, 이미지, 주소가 함께 나타난다.

```text
제목
+
설명
+
대표 이미지
+
페이지 주소
```

모든 페이지가 똑같이 `MY-BLOG`로 표시되면 어떤 글인지 구분하기 어렵다.

포스트라면 현재 글의 제목을 보여주는 편이 자연스럽고, 설명도 너무 길거나 비어 있지 않은 편이 좋다.

그래서 OG 이미지만 따로 생각하기보다 **링크 카드 전체를 하나의 정보 묶음으로 보는 것**이 더 맞았다.

---

## 기존 포스트 정보를 활용하는 편이 관리하기 쉬웠다

포스트에는 이미 제목과 설명에 사용할 정보가 있다.

그 값을 OG용으로 다시 직접 작성하면 같은 정보를 두 번 관리하게 된다.

예를 들어 포스트 제목을 `og:title`에도 그대로 사용할 수 있다.

대표 이미지가 있다면 `og:image`에 연결하고, 없다면 기본 이미지를 사용하면 된다.

```text
포스트 제목 있음
→ 포스트 제목

없음
→ 블로그 이름
```

```text
포스트 대표 이미지 있음
→ 해당 이미지

없음
→ 기본 OG 이미지
```

이렇게 기본값을 두면 페이지마다 모든 정보를 일일이 입력할 필요도 줄어든다.

---

## 로컬에서 보인다고 끝은 아니었다

OG 이미지는 외부 서비스가 직접 가져가는 이미지다.

그래서 로컬에서 정상적으로 보인다는 것만으로 충분하지 않았다.

특히 GitHub Pages처럼 배포 경로가 따로 있는 경우에는 실제 배포 주소에서 이미지에 접근할 수 있는지 확인해야 했다.

```text
로컬에서 보인다
≠
공유 서비스에서도 가져올 수 있다
```

결국 OG 설정은 실제 배포된 페이지를 기준으로 확인해야 했다.

---

## 바로 바뀌지 않으면 캐시도 생각해야 했다

OG 정보를 수정한 뒤 링크를 다시 공유했는데 예전 이미지가 계속 나올 수도 있다.

처음에는 설정이 잘못됐다고 생각하기 쉽다.

하지만 서비스가 이전 링크 정보를 캐시하고 있을 수도 있다.

그래서 결과가 바로 바뀌지 않는다면

현재 배포본의 메타 정보가 맞는지,

이미지 주소가 정상적으로 열리는지,

이전 미리보기가 캐시되어 있는 것은 아닌지

순서대로 확인하는 편이 좋았다.

favicon을 바꿀 때 브라우저 캐시를 신경 썼던 것과 비슷했다.

---

## 최종 확인은 실제 링크로 해야 했다

코드에 OG 태그가 들어간 것을 확인하는 것만으로는 끝나지 않았다.

최종 목적은 링크 미리보기이기 때문이다.

그래서 배포된 포스트 주소를 직접 공유해 보며 다음을 확인하는 편이 가장 확실했다.

* 제목이 현재 포스트와 맞는가
* 설명이 자연스럽게 보이는가
* 대표 이미지가 제대로 나오는가
* 다른 페이지의 이미지가 잘못 나오지는 않는가
* 링크를 눌렀을 때 올바른 페이지로 이동하는가

웹 작업을 하면서 계속 느낀 것처럼 **코드가 존재하는 것과 사용자가 원하는 결과를 보는 것은 다른 단계**였다.

---

## 모든 플랫폼에서 똑같이 보이지는 않았다

OG 정보를 설정해도 모든 메신저나 SNS에서 완전히 같은 카드가 나오는 것은 아니다.

어떤 서비스는 설명을 길게 보여주고, 어떤 곳은 짧게 자를 수 있다.

이미지 비율이나 카드 크기도 다를 수 있다.

그래서 특정 플랫폼 하나에 완벽하게 맞추기보다 **어디에서 사용되더라도 기본 정보가 제대로 전달되게 하는 것**을 목표로 했다.

내가 정할 수 있는 것은 페이지가 제공하는 정보까지이고, 실제 표현 방식은 각 서비스가 결정한다.

---

## 링크도 블로그의 일부였다

OG 설정을 하기 전에는 링크 공유를 단순히 URL을 보내는 일이라고 생각했다.

하지만 제목과 설명, 대표 이미지가 함께 보이기 시작하니 링크 자체가 작은 포스트 카드처럼 느껴졌다.

favicon이

> 이 사이트가 어디인가?

를 알려주는 표식이라면,

OG 미리보기는

> 이 링크에는 어떤 내용이 있는가?

를 알려주는 역할에 가까웠다.

블로그는 페이지에 들어온 뒤에만 보이는 것이 아니었다.

브라우저 탭에서도 보이고, 다른 곳에 공유된 링크에서도 보였다.

그래서 OG 이미지는 단순한 꾸미기보다 **블로그가 외부에서 자신의 콘텐츠를 어떻게 소개할지 정하는 설정**이었다.

처음에는 링크 미리보기를 예쁘게 만들고 싶어서 시작했지만, 결국 알게 된 것은 더 단순했다.

**웹사이트의 완성도는 페이지 안쪽뿐 아니라 밖에서 어떻게 보이는지까지 포함해 결정된다는 것**이었다.
