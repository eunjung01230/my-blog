Figma에서 화면을 만들었다.

레이아웃도 정했고,

버튼 위치도 정했고,

색상과 카드 구조도 어느 정도 결정했다.

그러면 이제 다음 단계가 남는다.

```text
디자인
↓
실제 코드
```

처음에는 이 과정도 단순하게 생각했다.

Claude에게 Figma 화면을 보여주고

```text
이 디자인 그대로 구현해줘.
```

라고 하면 끝날 것 같았다.

AI가 코드를 잘 작성하니까

디자인을 보고 React와 CSS까지 알아서 만들어줄 것이라고 생각했다.

실제로 어느 정도는 가능했다.

하지만 프로젝트를 몇 번 진행하면서 알게 된 것은

> **디자인을 AI에게 보여주는 것과
> 디자인을 정확하게 구현하게 하는 것은 다른 문제**

라는 것이었다.

Claude가 화면을 이해하더라도

내가 어떤 부분을 반드시 유지해야 하는지,

어떤 부분은 수정해도 되는지,

기존 코드 구조는 어떻게 되어 있는지,

어떤 기능까지 구현해야 하는지를 모르면

결과가 조금씩 다른 방향으로 갈 수 있었다.

이번 글에서는 Figma에서 만든 디자인을 Claude에게 넘겨 실제 코드로 구현하면서 내가 사용하게 된 방법을 정리해보려고 한다.

---

## Figma에서 예쁘게 보이는 것과 실제 구현은 다르다

Figma에서는 화면이 이미 완성되어 있다.

예를 들어 이런 구조가 있다고 해보자.

```text
Home

├─ Header
├─ Search
├─ Location
├─ Cafe List
│  ├─ Cafe Card
│  ├─ Cafe Card
│  └─ Cafe Card
└─ Bottom Navigation
```

Figma에서는 이미

```text
위치

크기

색상

간격

텍스트

아이콘
```

이 모두 정해져 있다.

하지만 개발에서는 이것을 다시 코드 구조로 해석해야 한다.

```text
Home Page

├─ Header Component
├─ SearchBar Component
├─ LocationSelector Component
├─ CafeList Component
│  └─ CafeCard Component
└─ BottomNavigation Component
```

그리고 각 요소에

```text
CSS

상태

이벤트

데이터

라우팅
```

을 연결해야 한다.

즉,

```text
Figma
```

에서 완성된 화면이

그대로 코드로 복사되는 것은 아니다.

중간에

```text
디자인 구조
↓
개발 구조로 해석
```

하는 과정이 필요하다.

---

## 처음에는 화면 캡처만 보여주면 되는 줄 알았다

가장 쉬운 방법은 화면을 캡처해서 AI에게 보여주는 것이다.

```text
이 화면 그대로 만들어줘.
```

물론 Claude는 이미지를 보고 상당히 많은 것을 이해할 수 있다.

예를 들어

```text
상단에 제목이 있다.

중앙에 카드가 있다.

버튼은 하단에 있다.

카드는 둥근 형태다.
```

같은 구조를 파악할 수 있다.

하지만 캡처에는 없는 정보도 많다.

```text
정확한 Padding

정확한 Gap

폰트 크기

Component 관계

화면 이동

hover 상태

모바일 반응형

데이터가 없을 때 상태
```

같은 것들이다.

그래서 이미지 하나만 전달하면 AI가 빈 부분을 추측하게 된다.

---

## AI가 추측하기 시작하면 디자인이 조금씩 바뀐다

예를 들어 Figma에는 버튼이 하나 있다.

```text
[ 시작하기 ]
```

그런데 Claude가 화면을 구현하면서

```text
[ 시작하기 ]

[ 자세히 보기 ]
```

를 하나 더 만들 수도 있다.

사용자에게 편할 것이라고 판단했기 때문이다.

또는

```text
설정 아이콘
```

이 작다고 생각해서 위치를 바꿀 수도 있다.

카드가 너무 단순하다고 판단해서

```text
아이콘

설명

상태 Badge
```

를 추가할 수도 있다.

AI 입장에서는 개선일 수 있다.

하지만 이미 디자인을 확정한 프로젝트라면 문제가 된다.

```text
Figma
≠
실제 구현
```

이 되어버리기 때문이다.

---

## 그래서 먼저 기준을 하나 정했다

내가 프로젝트를 진행하면서 중요하게 생각하게 된 것이 있다.

> **확정된 디자인을 Source of Truth로 사용한다.**

즉,

```text
무엇을 만들지 모르겠으면
→ Figma를 본다.

버튼 위치가 헷갈리면
→ Figma를 본다.

정보 구조가 다르면
→ Figma를 기준으로 판단한다.
```

라는 것이다.

AI가 더 좋은 아이디어를 제안할 수도 있다.

하지만 디자인 구현 단계에서는

```text
새로운 디자인 제안
```

보다

```text
확정된 디자인 구현
```

이 먼저다.

---

## 디자인 단계와 구현 단계를 분리했다

이 구분이 중요했다.

### 디자인 단계

```text
버튼을 어디에 둘까?

카드를 어떻게 만들까?

정보 우선순위는?

이 기능이 필요한가?
```

를 고민한다.

### 구현 단계

```text
정해진 버튼을 어떻게 코드로 만들까?

이 카드 구조를 Component로 어떻게 나눌까?

이 화면을 반응형으로 어떻게 구현할까?
```

를 고민한다.

구현하면서 다시 디자인 결정을 시작하면 작업 범위가 계속 커진다.

```text
구현
↓
AI가 디자인 수정
↓
다시 확인
↓
기획 수정
↓
코드 수정
```

이 과정이 반복될 수 있다.

그래서 이미 디자인을 확정했다면 Claude에게도 명확하게 알려주는 편이 좋았다.

```text
현재 Figma 디자인은 확정본이다.

레이아웃과 정보 구조를 임의로 변경하지 말고
디자인을 기준으로 구현해줘.
```

---

## Claude에게 처음 전달하는 정보

디자인 구현을 요청할 때 나는 크게 네 가지 정보를 주는 것이 좋다고 느꼈다.

```text
1. 기준 디자인

2. 현재 프로젝트 구조

3. 구현 범위

4. 변경 금지 범위
```

예를 들어 이런 식이다.

```text
첨부한 Figma 디자인을 기준으로
Home 화면을 구현해줘.

현재 프로젝트는 Next.js + React 구조다.

이번 작업 범위는 Home 화면 UI 구현까지만이다.

디자인에 없는 기능은 추가하지 말고,
기존 인증 / DB 코드는 수정하지 마.
```

단순히

```text
이거 만들어줘.
```

보다 훨씬 명확하다.

---

## "그대로 구현해줘"도 생각보다 모호하다

나는 처음에

```text
디자인 그대로 구현해줘.
```

면 충분히 명확한 지시라고 생각했다.

하지만 여기에도 애매한 부분이 있다.

Claude 입장에서는

```text
그대로
```

가 어느 수준인지 모른다.

예를 들어

```text
픽셀 단위 위치까지 동일?

전체 분위기만 동일?

기능도 동일?

모바일만 구현?

Desktop까지 구현?
```

여러 해석이 가능하다.

그래서 가능하면 유지할 항목을 구체적으로 적는다.

```text
다음 항목은 디자인을 그대로 유지해줘.

- 전체 레이아웃
- 요소 순서
- 텍스트
- 버튼 위치
- 카드 구조
- 색상
- Border Radius
- 아이콘 위치
```

그리고 반대로 자유롭게 구현할 부분도 말해준다.

```text
컴포넌트 분리 방식과
내부 코드 구조는 현재 프로젝트에 맞게 결정해줘.
```

이렇게 하면

```text
겉모습은 고정

구현 방법은 Claude가 판단
```

이라는 경계가 생긴다.

---

## Claude에게 모든 화면을 한 번에 맡겼을 때

처음에는 효율적으로 보였다.

```text
홈

로그인

상세

설정

프로필
```

다섯 개 화면이 있다면

```text
전부 구현해줘.
```

라고 요청하면 된다.

하지만 작업 범위가 커질수록 검토하기 어려워졌다.

예를 들어 결과가 이렇게 나왔다고 해보자.

```text
Home      → 거의 동일
Login     → 버튼 위치 다름
Detail    → 정보 하나 빠짐
Settings  → 새로운 기능 추가됨
Profile   → 레이아웃 조금 다름
```

그러면 수정할 내용이 너무 많아진다.

게다가 화면끼리 연결되어 있기 때문에 한 화면을 수정하면 다른 화면까지 영향을 받을 수도 있다.

---

## 한 화면씩 구현하는 것이 오히려 빨랐다

그래서 지금은 가능하면

```text
Home
↓
확인
↓
수정
↓
확정
↓
Detail
```

처럼 진행하는 편이 낫다고 생각한다.

조금 느려 보이지만 실제로는 그렇지 않았다.

한 화면에서

```text
간격

Component

색상

레이아웃 기준
```

이 확정되면 다음 화면에서 재사용할 수 있기 때문이다.

예를 들어 Home에서

```text
Header

Button

CafeCard
```

를 제대로 만들었다면 다음 화면에서는 해당 Component를 그대로 활용할 수 있다.

---

## 먼저 전체 구조를 확인하게 한다

바로 코드를 수정하게 하는 것보다 먼저 현재 프로젝트를 읽게 하는 것도 중요했다.

예를 들어 이미 프로젝트에

```text
components/

app/

styles/

lib/
```

같은 구조가 있는데 Claude가 이를 확인하지 않고 작업하면

```text
새로운 폴더

새로운 Button

새로운 Header
```

를 별도로 만들 수 있다.

그러면 기존 코드와 중복된다.

그래서 구현 전에

```text
현재 프로젝트 구조를 먼저 확인해줘.

기존 Component와 스타일을 재사용할 수 있는지 확인하고,
새 파일이 필요한 경우에만 만들어줘.
```

라고 하는 것이 좋았다.

---

## "기존 코드 건드리지 마"도 구체적으로 써야 했다

AI에게 작업을 시키면서 자주 사용하게 되는 표현이 있다.

```text
다른 부분은 건드리지 마.
```

하지만 이것도 조금 모호하다.

예를 들어 Home을 수정하려면

```text
app/page.tsx
```

만 수정하면 되는지,

공통 Button Component도 수정해야 하는지 판단하기 어렵다.

그래서 범위를 더 구체적으로 적는 편이 좋았다.

```text
현재 작업 범위:

- app/page.tsx
- Home에서 사용하는 신규 Component

변경 금지:

- 인증 관련 코드
- DB 관련 코드
- 환경 변수
- 다른 페이지
```

이런 식이다.

작업 범위가 좁을수록 결과를 검토하기도 쉽다.

---

## 구현 전에 계획만 받는 방법도 유용했다

규모가 조금 있는 작업이라면 바로 코드를 수정시키지 않고

```text
우선 코드는 수정하지 말고
구현 계획만 정리해줘.
```

라고 할 수 있다.

그러면 Claude가

```text
수정할 파일

새로 만들 Component

재사용할 기존 Component

예상 영향 범위
```

를 먼저 설명한다.

이 단계에서

```text
아니, 그 파일은 건드리면 안 되는데?
```

라는 것을 발견하면 코드가 변경되기 전에 막을 수 있다.

---

## 내가 자주 사용하는 흐름

현재는 대략 이런 과정이 가장 안정적이라고 느낀다.

```text
Figma 디자인 확정
↓
Claude에게 프로젝트 구조 확인
↓
구현 대상 화면 지정
↓
수정 계획 확인
↓
코드 구현
↓
브라우저에서 확인
↓
Figma와 비교
↓
차이 수정
↓
다음 화면
```

중요한 부분은

```text
코드 구현
```

에서 끝나지 않는다는 것이다.

---

## 구현됐다고 하면 실제 화면을 봐야 한다

Claude가

```text
구현 완료했습니다.
```

라고 말해도 실제 브라우저에서 보면 다를 수 있다.

예를 들어 코드상으로는

```text
width

padding

flex

gap
```

이 맞아 보이는데 실제 화면에서는

```text
버튼이 너무 작다.

텍스트가 두 줄이 된다.

카드 높이가 다르다.

하단 Navigation이 잘린다.
```

같은 문제가 생길 수 있다.

그래서 반드시 실제 화면을 확인한다.

---

## Figma와 실제 화면을 나란히 비교한다

이 방법이 가장 단순하지만 효과적이었다.

```text
왼쪽
Figma

오른쪽
실제 브라우저
```

를 놓고 비교한다.

그리고 하나씩 본다.

```text
Header 높이

좌우 Padding

제목 위치

카드 너비

버튼 높이

폰트 크기

아이콘 크기

하단 여백
```

막연하게

```text
뭔가 다른데?
```

라고 하는 것보다 차이를 찾기 쉽다.

---

## 수정할 때도 범위를 작게 잡는다

예를 들어 전체적으로 괜찮지만 버튼이 다르다고 해보자.

그때

```text
디자인이 좀 다르니까 다시 고쳐줘.
```

라고 하면 Claude가 다른 부분까지 수정할 수 있다.

대신

```text
현재 구현에서 다른 부분은 유지해줘.

하단 시작 버튼만 수정한다.

Figma와 비교하면
- 버튼 높이가 작음
- 좌우 여백이 큼
- 텍스트가 작음

이 세 부분만 수정해줘.
```

처럼 요청한다.

즉,

```text
전체 수정
```

보다

```text
차이 하나씩 수정
```

이 안정적이었다.

---

## 이미지로 차이를 보여주는 것도 좋았다

말로

```text
조금 위로

조금 크게

조금 좁게
```

라고 설명하는 것은 애매하다.

그래서 실제 브라우저 화면을 캡처하고

```text
여기가 Figma와 다르다.
```

라고 보여주는 방법이 훨씬 편하다.

특히

```text
정렬

위치

크기

여백
```

같은 시각적 문제는 이미지로 전달하는 것이 빠르다.

---

## Claude가 디자인을 개선하려 할 때

AI를 사용하면서 자주 만난 상황이다.

내가 요청한 것은

```text
이 화면 구현
```

인데 Claude가

```text
사용성을 위해 이 버튼을 추가했습니다.

UX 개선을 위해 구조를 변경했습니다.
```

라고 하는 경우다.

제안 자체는 틀리지 않을 수 있다.

하지만 프로젝트에서는 문제가 될 수 있다.

특히 이미 기획 문서와 디자인이 확정됐다면 더 그렇다.

그래서 나는 구현 단계에서는

```text
디자인에 없는 요소는 추가하지 않는다.

UX 개선 아이디어가 있더라도
코드에 적용하지 말고 별도로 알려준다.
```

는 식으로 구분하는 것이 좋다고 생각한다.

그러면

```text
구현
```

과

```text
개선 제안
```

이 섞이지 않는다.

---

## Figma에 없는 기능을 Claude가 만들지 않게 하기

예를 들어 카페 카드가

```text
브랜드

매장명

거리

혜택

길찾기
```

만 보여주도록 설계되어 있다고 하자.

AI가 일반적인 카페 앱을 떠올리면

```text
별점

리뷰

즐겨찾기
```

를 자연스럽게 추가할 수 있다.

화면은 더 그럴듯해 보인다.

하지만 원래 기획에는 없는 기능이다.

이런 것이 반복되면

```text
디자인 구현
```

이 아니라

```text
AI가 서비스를 다시 기획
```

하게 된다.

그래서

> **디자인에 없는 기능 추가 금지**

라는 기준이 생각보다 중요했다.

---

## Placeholder 데이터와 실제 기능도 구분한다

Figma에는 실제 데이터가 연결되어 있지 않다.

그래서 화면에는 보통 예시 데이터가 있다.

```text
컴포즈커피 판교점

도보 8분

스탬프 7개
```

Claude가 이것을 구현하면서 바로 DB까지 연결할 수도 있다.

하지만 아직 UI 구현 단계라면 그럴 필요가 없다.

```text
현재는 UI 검증용 Mock Data만 사용하고
DB 연결은 하지 마.
```

라고 범위를 정할 수 있다.

반대로 이미 API가 구현되어 있다면

```text
현재 API 응답 구조를 확인하고
기존 API를 사용해 디자인과 연결해줘.
```

라고 한다.

---

## 디자인 구현과 기능 구현을 나누면 편하다

한 화면에서도 사실 작업은 두 가지다.

```text
UI 구현

기능 구현
```

예를 들어 검색창이라면

### UI

```text
검색 아이콘

입력창 모양

높이

색상

Padding
```

### 기능

```text
검색어 상태

API 요청

검색 결과

오류 처리
```

가 있다.

처음부터 둘 다 한 번에 하면 문제가 생겼을 때

```text
UI 문제인가?

기능 문제인가?
```

가 섞인다.

그래서 가능하면

```text
디자인 구현
↓
화면 확인
↓
기능 연결
```

순서로 진행하는 것도 좋았다.

---

## Component를 어디까지 나눌지도 Claude에게 맡길 수 있다

Figma에는 Frame과 Component가 있다.

하지만 Figma Component와 React Component가 반드시 1:1로 대응해야 하는 것은 아니다.

예를 들어 Figma에서는 하나의 큰 카드로 디자인되어 있어도 개발에서는

```text
CafeCard
├─ CafeInfo
├─ BenefitInfo
└─ DirectionButton
```

으로 나눌 수 있다.

이 부분은 코드 유지보수와 관련되어 있기 때문에 Claude에게 현재 프로젝트 구조를 기준으로 판단하게 할 수 있다.

다만

```text
화면 디자인은 변경하지 말 것
```

이라는 조건은 유지한다.

즉,

```text
겉모습
→ Figma 기준

내부 구조
→ 개발 구조에 맞게
```

라고 생각한다.

---

## 반응형은 Figma 한 장만 보고 자동으로 알 수 없다

Desktop 디자인 하나만 보여주고

```text
반응형까지 만들어줘.
```

라고 하면 Claude가 모바일 구조를 추측해야 한다.

반대로 모바일 디자인만 있다면 Desktop을 추측한다.

이때도 AI가 알아서 잘 만들 수 있지만

내가 원했던 구조와 같다는 보장은 없다.

그래서 가능하면

```text
Desktop에서 카드 3열

Tablet에서 2열

Mobile에서 1열
```

처럼 기준을 같이 제공한다.

또는 아직 반응형을 결정하지 않았다면

```text
이번 작업에서는 모바일 디자인만 구현하고
Desktop 구조를 임의로 만들지 마.
```

라고 해도 된다.

---

## "적당히 반응형"이라는 말이 위험했다

이런 요청은 편하다.

```text
적당히 반응형으로 만들어줘.
```

하지만 결과를 검증할 기준이 없다.

Claude가

```text
768px

1024px
```

를 기준으로 나눌 수도 있고,

다른 Breakpoint를 사용할 수도 있다.

카드 배치도 임의로 결정하게 된다.

그래서 적어도 중요한 부분은 기준을 정하는 게 낫다.

```text
모바일 우선 구현

768px 이상에서는
콘텐츠 최대 너비만 제한

레이아웃 구조는 유지
```

처럼 말할 수 있다.

---

## 브라우저 크기를 바꿔보는 것도 중요했다

Figma에서 한 화면만 봤을 때는 문제가 없었다.

하지만 실제 브라우저에서는

```text
작은 모바일

큰 모바일

태블릿

노트북
```

처럼 크기가 다양하다.

그래서 구현이 끝나면 창 크기를 직접 바꿔본다.

이때 자주 발견되는 문제가 있다.

```text
텍스트 줄바꿈

버튼 잘림

카드 폭

고정 요소 겹침

하단 Navigation
```

같은 것들이다.

---

## Pixel Perfect가 항상 목표일까?

디자인을 구현한다고 하면

```text
Figma와 100% 동일
```

을 목표로 생각할 수 있다.

물론 가능한 한 디자인에 맞추는 것이 좋다.

하지만 실제 브라우저에서는

```text
폰트 렌더링

운영체제

브라우저

화면 비율

데이터 길이
```

때문에 완전히 동일할 수 없는 부분도 있다.

그래서 나는

```text
숫자 하나까지 무조건 동일
```

보다

```text
레이아웃

우선순위

간격 체계

색상

사용 흐름
```

이 유지되는지를 더 중요하게 보려고 한다.

---

## 디자인에 이상한 부분이 있다면?

Figma를 Source of Truth로 정했다고 해서 무조건 잘못된 디자인까지 그대로 구현해야 한다는 뜻은 아니다.

실제 구현하면서

```text
이 버튼은 클릭하기 너무 작다.

텍스트가 실제 데이터에서는 잘린다.

모바일에서 이 구조는 불가능하다.
```

같은 문제가 발견될 수 있다.

이럴 때 AI가 몰래 수정하는 것이 아니라

```text
현재 디자인 그대로 구현하면
이런 문제가 생길 가능성이 있습니다.

디자인을 유지할지
수정할지 결정이 필요합니다.
```

처럼 문제를 먼저 알려주는 방식이 좋다.

그다음 디자인을 수정하고 다시 구현한다.

```text
문제 발견
↓
디자인 수정
↓
기준 확정
↓
코드 수정
```

이 순서다.

---

## Figma와 코드가 서로 다른 방향으로 발전하지 않게 하기

프로젝트가 진행되면 이런 상황이 생기기 쉽다.

```text
Figma v1

↓

코드 수정

↓

코드에 새로운 UI 추가

↓

Figma는 그대로

↓

또 코드 수정
```

나중에는

```text
Figma가 최신인가?

코드가 최신인가?
```

알기 어려워진다.

그래서 큰 디자인 변경이 있다면 Figma도 함께 수정하는 편이 좋다.

```text
Figma
=
현재 디자인 기준
```

이 계속 유지되도록 한다.

---

## 디자인을 구현한 뒤 Figma도 다시 보게 됐다

재미있는 점은 개발을 시작하고 나면 Figma 디자인의 문제도 더 잘 보인다는 것이다.

Figma에서는 괜찮았는데 실제로 눌러보면

```text
버튼 위치가 불편하다.

내용이 길어지면 카드가 이상하다.

페이지 이동이 너무 많다.
```

는 것이 보인다.

그래서 실제 과정은 완전히 일방향은 아니었다.

```text
Figma
↓
Claude 구현
↓
실제 사용
↓
문제 발견
↓
Figma 수정
↓
다시 구현
```

이런 반복이 생긴다.

이 과정 자체가 이상한 것은 아니다.

오히려 화면을 실제 서비스로 옮기는 과정에서 자연스럽게 생기는 수정이라고 생각한다.

---

## Git을 사용하는 프로젝트라면 더 조심해야 했다

Claude가 코드를 구현하는 것은 빠르다.

문제는 변경되는 파일이 많아질 수 있다는 것이다.

그래서 작업 전후로

```text
git status
```

를 확인하는 습관도 중요했다.

예를 들어 내가 Home 화면만 요청했는데

```text
12 files changed
```

라고 나온다면

```text
왜 이렇게 많이 바뀌었지?
```

를 확인해야 한다.

AI가 작성한 코드라고 해서 바로 Commit할 필요는 없다.

---

## 구현 확인 전에 Commit하지 않기

특히 디자인 작업은 실제 화면을 보기 전까지 결과를 판단하기 어렵다.

그래서 나는 이런 순서가 더 안전하다고 생각한다.

```text
Claude 수정
↓
실행
↓
브라우저 확인
↓
Figma 비교
↓
필요한 수정
↓
최종 확인
↓
Commit
```

반대로

```text
수정
↓
바로 Commit
↓
화면 확인
```

하면 작은 디자인 수정마다 Commit이 계속 생길 수 있다.

---

## 처음부터 Commit을 금지하는 방법

Claude에게 작업을 요청할 때

```text
코드 수정까지만 하고
Commit과 Push는 하지 마.
```

라고 명확하게 말할 수도 있다.

그러면 내가 직접 화면을 확인한 뒤

```text
이제 Commit해줘.
```

라고 별도로 요청한다.

특히 디자인을 여러 번 비교하면서 수정할 때 편했다.

---

## 개발 서버를 직접 확인하는 것도 중요하다

코드가 Build된다고 해서 UI가 제대로 된 것은 아니다.

```text
npm run build
```

가 성공해도

```text
카드가 겹침

버튼이 안 보임

색상이 다름

모바일 레이아웃 깨짐
```

은 존재할 수 있다.

그래서 디자인 작업에서는

```text
Build 성공
```

과

```text
UI 구현 성공
```

을 따로 확인해야 한다.

---

## AI에게 검증까지 요청할 수 있다

구현이 끝난 뒤 이런 식으로 요청할 수도 있다.

```text
지금은 코드를 더 수정하지 말고
Figma 디자인과 현재 구현을 비교해서

- 일치하는 부분
- 다른 부분
- 수정이 필요한 부분

만 정리해줘.
```

그러면 바로 수정시키는 것보다 한 번 검토 단계를 둘 수 있다.

내가 결과를 보고

```text
1번과 3번만 수정
```

처럼 결정할 수 있다.

---

## 내가 사용하기 좋은 기본 명령 형태

Figma 디자인을 구현할 때는 대략 이런 구조가 편했다.

```text
첨부한 Figma 디자인을 기준으로
[화면 이름]을 구현해줘.

[기준]
- 현재 디자인은 확정본이다.
- 레이아웃과 정보 구조를 임의로 변경하지 않는다.
- 디자인에 없는 기능을 추가하지 않는다.
- 기존 프로젝트의 Component와 스타일을 우선 재사용한다.

[작업 범위]
- 이번에는 [화면] UI만 구현한다.
- 기능 연결은 하지 않는다.

[변경 금지]
- 인증
- DB
- 환경변수
- 다른 페이지

[작업 방식]
1. 먼저 현재 코드 구조를 확인한다.
2. 수정 계획을 간단히 정리한다.
3. 필요한 파일만 수정한다.
4. Build / Type check를 확인한다.
5. Commit과 Push는 하지 않는다.
```

매번 전부 써야 하는 것은 아니다.

하지만 작업이 커질수록 이런 기준이 도움이 됐다.

## 기능을 연결하는 두 번째 단계

UI가 디자인과 맞는 것을 확인했다면 그다음 기능을 연결한다.

예를 들어 버튼이 있다면

```text
UI 완료

↓

클릭 기능 연결
```

검색창이라면

```text
검색 UI 완료

↓

상태 연결

↓

API 연결
```

카드 목록이라면

```text
Mock Data

↓

실제 DB 데이터
```

로 바꾼다.

이렇게 단계가 나뉘면 문제가 생겼을 때 원인을 찾기 편하다.

---

## Figma Export도 여기에서 연결된다

앞 글에서 정리한 Export가 실제로 사용되는 것도 이 단계다.

예를 들어 Figma 디자인에

```text
서비스 로고

전용 아이콘

일러스트
```

가 있다면 필요한 Asset을 Export한다.

반면

```text
버튼

카드

텍스트

입력창
```

은 이미지로 가져오는 것이 아니라 코드로 구현한다.

그래서 전체 흐름은

```text
Figma
│
├─ UI 구조
│     ↓
│   React / CSS
│
└─ 필요한 Asset
      ↓
    SVG / PNG
```

처럼 나뉜다.

## Figma와 Claude 사이에서 내가 해야 하는 일

처음에는

```text
Figma
↓
Claude
↓
완성
```

이라고 생각했다.

하지만 실제로는 중간에 내가 해야 할 일이 많았다.

```text
Figma
↓
구현 기준 결정
↓
Claude에게 범위 전달
↓
결과 확인
↓
디자인과 비교
↓
수정할 부분 판단
↓
Claude 수정
↓
최종 확인
```

AI가 코드를 작성하는 속도는 빠르지만

```text
이게 맞는가?
```

를 판단하는 것은 결국 내가 해야 한다.

---

## AI에게 모든 판단을 맡기면 생기는 문제

AI는 일반적으로 좋은 UI 패턴을 알고 있다.

그래서 자연스럽게 개선하려고 한다.

하지만 프로젝트에는 이미 결정된 것이 있다.

```text
MVP 범위

사용자 흐름

디자인

기획 문서

데이터 구조
```

이런 맥락을 충분히 주지 않으면 Claude는

```text
일반적으로 좋은 서비스
```

를 만들려고 할 수 있다.

하지만 내가 필요한 것은

```text
일반적으로 좋은 서비스
```

가 아니라

```text
내가 기획한 서비스
```

다.

그래서 AI에게 맡기는 범위와 내가 결정하는 범위를 나눌 필요가 있었다.

---

## 내가 결정하는 것

```text
어떤 기능을 만들 것인지

어떤 정보를 보여줄 것인지

사용자의 주요 행동

디자인 기준

작업 범위
```

---

## Claude에게 맡기는 것

```text
코드 작성

Component 분리

반복 코드 정리

스타일 구현

기존 코드와 연결

오류 수정
```

물론 상황에 따라 달라질 수 있다.

하지만 적어도

```text
무엇을 만들 것인가
```

와

```text
어떻게 코드로 만들 것인가
```

를 구분하니 훨씬 편했다.

---

## Figma → Claude가 편했던 이유

직접 모든 CSS를 작성하는 것보다 확실히 빠른 부분도 있었다.

Figma 디자인이 이미 명확하다면

```text
레이아웃

Component

스타일
```

의 목표가 있기 때문이다.

Claude도 빈 화면에서 디자인까지 결정하는 것보다

```text
이 화면을 구현한다.
```

라는 명확한 목표가 있을 때 작업하기 쉽다.

그래서 내가 느낀 가장 좋은 흐름은

```text
사람
→ 무엇을 만들지 결정

Figma
→ 화면 기준 작성

Claude
→ 코드 구현

사람
→ 결과 검증
```

이었다.

---

## Figma 없이 Claude에게 바로 만들게 할 수도 있다

물론 Figma가 항상 필수인 것은 아니다.

작은 페이지라면

```text
Claude에게 직접 UI 생성
↓
브라우저에서 확인
↓
수정
```

으로도 충분하다.

하지만 프로젝트가 커지고

```text
화면이 많아지고

디자인 통일이 필요하고

팀원이 생기고

기능이 복잡해지면
```

기준이 있는 것이 훨씬 편했다.

그래서 모든 작업을 무조건 Figma부터 시작해야 한다기보다

```text
간단한 화면
→ Claude에서 바로 만들어도 가능

중요한 화면 / 여러 페이지 프로젝트
→ Figma 기준을 만드는 것이 유리
```

정도로 생각하고 있다.

---

## 내가 Figma → Claude 구현에서 지키고 싶은 기준

지금까지의 경험을 정리하면 이렇다.

```text
1. 먼저 디자인을 확정한다.

2. Figma를 구현 기준으로 사용한다.

3. Claude에게 현재 프로젝트 구조를 먼저 확인하게 한다.

4. 한 번에 너무 많은 화면을 구현하지 않는다.

5. 디자인에 없는 기능을 추가하지 못하게 한다.

6. UI 구현과 기능 구현을 가능하면 분리한다.

7. 변경 가능한 부분과 변경 금지 영역을 알려준다.

8. 구현 후 반드시 실제 브라우저에서 확인한다.

9. Figma와 실제 화면을 직접 비교한다.

10. 수정할 때는 범위를 좁혀서 요청한다.

11. 디자인 확인이 끝나기 전에는 Commit하지 않는다.

12. 구현 중 디자인 문제가 발견되면
    코드에서 임의로 해결하지 않고
    디자인 기준부터 다시 확인한다.
```

---

## 결국 중요한 것은 "그대로 만들어줘"가 아니었다

처음에는 좋은 프롬프트가

```text
이 디자인 그대로 만들어줘.
```

라고 생각했다.

하지만 실제로 중요한 것은 그 문장 뒤에 있었다.

```text
무엇이 기준인지

무엇을 변경하면 안 되는지

어디까지 구현할 것인지

기존 코드 중 무엇을 재사용할지

결과를 어떻게 검증할지
```

를 정하는 것이었다.

AI에게 정확하게 지시한다는 것이 꼭 긴 프롬프트를 작성한다는 뜻은 아니었다.

오히려

> **결정된 것과 아직 결정되지 않은 것을 분리해서 알려주는 것**

에 가까웠다.

---

## Figma와 Claude의 역할을 나눠보니

내가 이해한 두 도구의 역할은 이렇게 정리할 수 있을 것 같다.

| Figma       | Claude       |
| ----------- | ------------ |
| 화면 기준 결정    | 코드 구현        |
| 정보 구조 확인    | Component 구성 |
| 디자인 비교      | 반복 코드 작성     |
| 시각적 우선순위 결정 | 기능 연결        |
| 화면 흐름 설계    | 오류 수정        |
| 구현 결과 검증 기준 | 실제 동작 구현     |

그리고 그 사이에는 내가 있다.

```text
Figma
↓
내가 기준을 확인
↓
Claude
↓
내가 실제 화면 검증
```

AI 도구끼리 자동으로 연결해버리는 것보다

내가 중간에서 기준을 확인하는 과정이 중요했다.

---

## 마무리

처음 Figma와 Claude를 같이 사용했을 때 기대했던 흐름은 단순했다.

```text
Figma 디자인
↓
Claude
↓
완성된 서비스
```

실제로 사용해보니 조금 달랐다.

```text
Figma 디자인
↓
구현 범위 결정
↓
Claude 코드 작성
↓
브라우저 확인
↓
Figma 비교
↓
차이 수정
↓
기능 연결
↓
다시 확인
```

단계가 더 많다.

하지만 이 방식이 오히려 안정적이었다.

Claude가 코드를 작성하는 속도를 활용하면서도

내가 정한 디자인과 기획이 흐트러지는 것을 막을 수 있기 때문이다.

결국 Figma에서 Claude로 넘어가는 과정에서 가장 중요한 것은

```text
AI가 디자인을 얼마나 잘 읽는가
```

보다

```text
내가 AI에게
무엇을 기준으로 구현해야 하는지
얼마나 명확하게 알려주는가
```

였다.

그리고 Figma를 Claude와 연결하는 방법은 이것만 있는 것이 아니다.

지금까지는 **이미 확정된 Figma 디자인을 Claude에게 구현시키는 과정**을 다뤘다면,

Claude 자체를 활용해 디자인을 만들고 수정하는 방법도 있다.

다음 글에서는 Figma 디자인을 코드로 옮기는 것과는 조금 다른 흐름인

**Claude Design을 어떻게 활용할 수 있는지, 일반 Claude 코드 구현과 무엇이 다른지**

정리해보려고 한다.
