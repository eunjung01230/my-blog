개발 공부를 처음 시작했을 때는 디자인 도구까지 배워야 할 거라고 생각하지 않았다.

HTML과 CSS를 배우고, React를 배우고, 백엔드와 데이터베이스까지 공부하기에도 배울 것이 너무 많았다.

그래서 처음에는 화면 디자인도 그냥 코드를 작성하면서 만들면 된다고 생각했다.

```text
일단 HTML을 만들고
↓
CSS를 적용하고
↓
화면을 보면서 수정하고
↓
마음에 안 들면 다시 고친다
```

실제로 간단한 페이지를 만들 때는 이 방법도 가능했다.

하지만 프로젝트의 화면이 늘어나기 시작하면서 문제가 생겼다.

버튼 위치를 바꾸면 다른 요소도 같이 움직이고,

페이지마다 간격이 조금씩 달라지고,

새로운 화면을 만들 때마다

> 이 화면은 어떻게 구성하지?

부터 다시 고민하게 됐다.

그때부터 코드를 작성하기 전에 **화면을 먼저 설계하는 과정이 필요하다**는 생각이 들었다.

그리고 그 과정에서 사용하기 시작한 도구가 Figma였다.

---

## 처음에는 Figma가 디자이너용 프로그램인 줄 알았다

Figma를 처음 봤을 때는 솔직히 개발자가 꼭 배워야 하는 도구라고 생각하지 않았다.

디자이너가 화면을 그리고,

개발자는 그 디자인을 보고 구현하는 방식이라고 생각했다.

그래서 역할을 단순하게 나누면 이런 느낌이었다.

```text
디자이너
↓
Figma
↓
개발자
↓
코드 구현
```

하지만 직접 프로젝트를 만들어보니 상황이 조금 달랐다.

개인 프로젝트에서는 디자인을 해주는 사람이 따로 없다.

팀 프로젝트에서도 항상 전문 디자이너가 있는 것은 아니다.

결국 개발자가 직접 화면 구조를 고민해야 하는 상황이 자주 생긴다.

특히 내가 만들고 싶은 서비스를 처음부터 설계할 때는

* 어떤 화면이 필요한지
* 사용자가 어디서 시작하는지
* 버튼은 어디에 있어야 하는지
* 어떤 정보를 먼저 보여줘야 하는지
* 페이지 사이를 어떻게 이동하는지

같은 것을 먼저 정해야 했다.

이건 단순히 CSS를 예쁘게 작성하는 문제와는 조금 달랐다.

---

## 코드를 먼저 작성하면 생겼던 문제

처음에는 디자인을 따로 만들지 않고 바로 구현하는 경우가 많았다.

예를 들어 홈 화면을 만든다고 하면 바로 코드를 작성했다.

```text
헤더 만들기
→ 카드 만들기
→ 버튼 넣기
→ 간격 수정
→ 색상 수정
→ 다시 배치
```

그런데 완성한 뒤 보면 뭔가 이상한 경우가 많았다.

버튼이 너무 많거나,

중요하지 않은 정보가 너무 눈에 띄거나,

반대로 사용자가 가장 먼저 눌러야 하는 버튼이 잘 보이지 않는 경우도 있었다.

문제는 여기서 끝나지 않았다.

이미 코드로 만들어 놓은 상태였기 때문에 화면 구조를 수정하려면 구현한 코드도 같이 수정해야 했다.

예를 들어

```text
상단 버튼을 하단으로 이동
```

이라는 단순한 변경도 실제 코드에서는

```text
컴포넌트 구조 수정
CSS 수정
간격 수정
반응형 확인
다른 화면 영향 확인
```

까지 이어질 수 있었다.

화면을 그리는 단계에서 바꿨다면 몇 초 만에 끝났을 일을 코드까지 작성한 뒤 수정하고 있었다.

---

## Figma는 코드를 작성하기 전의 실험 공간이었다

Figma를 사용하면서 가장 크게 느낀 장점은 **실제 구현 전에 화면을 마음껏 바꿔볼 수 있다는 것**이었다.

버튼이 왼쪽에 있는 게 좋은지,

오른쪽에 있는 게 좋은지,

카드를 세로로 배치할지,

가로로 배치할지,

중요한 정보를 위에 둘지 아래에 둘지

코드를 수정하지 않고 바로 비교할 수 있다.

예를 들어 이런 두 가지 구조를 고민한다고 해보자.

### A

```text
서비스 이름
설명
지도
혜택 정보
시작 버튼
```

### B

```text
서비스 이름
지도
시작 버튼
혜택 정보
설명
```

코드로 두 가지를 모두 만들어 비교하려면 시간이 꽤 걸린다.

하지만 Figma에서는 요소를 이동하는 것만으로 금방 비교할 수 있다.

그래서 나에게 Figma는 처음부터 완벽한 디자인을 만드는 도구라기보다

> **코드를 작성하기 전에 여러 방법을 시험해보는 공간**

에 가까웠다.

---

## 화면 하나보다 전체 흐름을 볼 수 있었다

프로젝트를 만들면서 화면 하나만 잘 만드는 것으로는 부족했다.

사용자는 한 페이지에서만 머무르지 않는다.

예를 들어 서비스를 사용한다고 하면

```text
홈
↓
로그인
↓
정보 입력
↓
결과
↓
상세 화면
```

처럼 여러 화면을 이동한다.

각 화면을 따로 개발하면 각각은 괜찮아 보이는데 전체 흐름이 이상해질 수 있다.

예를 들어

```text
홈에는 시작 버튼이 있는데

결과 화면에는 다시 돌아가는 버튼이 없다.
```

또는

```text
목록에서는 상세 화면으로 들어갈 수 있는데

상세 화면에서는 목록으로 돌아가는 방법이 애매하다.
```

같은 문제가 생긴다.

Figma에서 여러 화면을 옆에 놓고 보면 이런 문제를 훨씬 쉽게 발견할 수 있었다.

```text
Home
   ↓
Login
   ↓
Main
   ↓
Detail
   ↓
Result
```

코드를 보기 전에 서비스 전체 구조를 눈으로 볼 수 있는 것이다.

---

## 개발하면서 디자인을 바꾸는 일이 줄었다

물론 Figma에서 디자인을 만들었다고 해서 구현하면서 수정할 일이 완전히 사라지는 것은 아니다.

실제로 브라우저에서 보면 생각했던 것과 다를 수도 있고,

모바일 화면에서는 공간이 부족할 수도 있고,

직접 버튼을 눌러보면 불편한 부분이 생길 수도 있다.

하지만 최소한

> 화면 구조 자체를 처음부터 다시 고민하는 일

은 많이 줄어든다.

예전에는 구현하면서 이런 고민을 했다.

```text
버튼을 어디에 두지?
카드는 몇 개로 나누지?
이 정보는 어디에 표시하지?
```

Figma를 사용한 이후에는 구현 단계에서 조금 더 이런 부분에 집중할 수 있었다.

```text
이 디자인을 컴포넌트로 어떻게 나누지?
이 UI를 React에서 어떻게 구현하지?
모바일에서는 어떻게 바뀌어야 하지?
```

즉,

**디자인 고민과 구현 고민을 어느 정도 분리할 수 있었다.**

---

## 개발자도 화면을 읽을 줄 알아야 했다

Figma를 사용하면서 또 하나 느낀 점은

개발자가 직접 디자인을 하지 않더라도 **디자인을 읽을 수 있어야 한다**는 것이었다.

화면을 보면 단순히

```text
여기에 버튼이 있다
```

만 보는 것이 아니라

```text
왜 이 버튼이 여기 있을까?
```

를 생각해야 했다.

예를 들어 버튼 하나에도

* 크기
* 위치
* 색상
* 간격
* 다른 버튼과의 관계
* 클릭했을 때 이동하는 화면

같은 정보가 들어 있다.

카드 하나에도

```text
제목
설명
상태
버튼
간격
정렬
```

같은 구조가 존재한다.

이런 것을 이해하지 않고 화면만 비슷하게 만드는 것은 가능하지만,

프로젝트가 커질수록 수정하기 어려운 코드가 될 가능성이 높았다.

---

## Figma를 배우고 코드를 보는 방식도 조금 달라졌다

Figma를 사용하기 전에는 화면을 보면 바로 HTML이나 CSS부터 생각했다.

```text
div
display flex
gap
margin
```

같은 것을 먼저 떠올렸다.

하지만 화면 설계를 조금씩 공부하면서 순서가 달라졌다.

먼저

```text
이 화면에서 가장 중요한 정보가 무엇인지
```

를 생각하고,

그다음

```text
사용자가 무엇을 먼저 봐야 하는지
```

를 생각하게 됐다.

그리고 마지막에

```text
그 구조를 코드로 어떻게 구현할지
```

를 고민하게 됐다.

즉,

```text
코드
→ 화면
```

이었던 생각이

```text
사용자
→ 화면 구조
→ 디자인
→ 코드
```

로 조금씩 바뀌었다.

---

## AI로 개발할수록 Figma가 더 중요하게 느껴졌다

AI를 활용해 코드를 작성하기 시작하면서 오히려 디자인 기준을 먼저 만드는 것이 중요하다고 느꼈다.

AI에게 단순히

```text
예쁜 홈 화면 만들어줘
```

라고 요청하면 화면을 만들어주기는 한다.

하지만 내가 원하는 화면과 정확히 일치할 가능성은 높지 않았다.

반대로 디자인이 이미 있다면 요청이 훨씬 구체적으로 바뀐다.

```text
이 디자인을 기준으로 구현해줘.

레이아웃과 간격은 그대로 유지하고,
기능만 연결해줘.
```

이렇게 하면 AI도 무엇을 기준으로 코드를 작성해야 하는지 명확해진다.

그래서 내가 프로젝트에서 사용하게 된 흐름도 점점 이런 형태가 됐다.

```text
아이디어
↓
화면 구조 정리
↓
Figma / 디자인 도구
↓
디자인 확정
↓
AI를 활용한 코드 구현
↓
실제 화면 확인
↓
수정
```

AI가 디자인을 대신 생각하게 하는 것보다

**내가 기준을 만들고 AI가 그 기준을 구현하게 하는 방식**이 훨씬 관리하기 편했다.

---

## 실제 프로젝트에서도 디자인이 기준점이 됐다

프로젝트를 진행하다 보면 계속 새로운 아이디어가 생긴다.

버튼을 추가하고 싶기도 하고,

새로운 기능을 넣고 싶기도 하고,

화면 구성을 바꾸고 싶기도 하다.

문제는 이런 수정이 계속 쌓이면 처음 생각했던 서비스와 점점 달라질 수 있다는 것이다.

그래서 어느 시점부터는

> 지금 구현하는 화면이 우리가 정한 디자인과 맞는가?

를 기준으로 확인하는 방식이 필요했다.

특히 AI를 이용해 구현할 때는 이 기준이 더 중요했다.

AI는 요청하면 새로운 UI나 기능을 쉽게 제안한다.

하지만 제안이 많다고 해서 모두 서비스에 필요한 것은 아니다.

디자인이 미리 정리되어 있으면

```text
이 기능은 현재 디자인에 없다.
```

```text
이 버튼은 원래 위치와 다르다.
```

```text
이 화면은 기존 흐름과 맞지 않는다.
```

처럼 판단할 기준이 생긴다.

---

## Figma를 잘하는 것과 디자인을 잘하는 것은 달랐다

Figma를 배우면서 가장 먼저 구분해야 했던 것도 이것이었다.

**Figma를 사용할 줄 아는 것과 좋은 UI를 만드는 것은 다른 문제다.**

Figma에서

* Frame 만들기
* Auto Layout 사용하기
* Component 만들기
* 색상 바꾸기
* 아이콘 넣기

를 할 수 있다고 해서 바로 좋은 디자인이 만들어지는 것은 아니다.

도구 사용법과 디자인 원리는 따로 공부해야 했다.

그래서 이번 Design 카테고리도 두 부분을 나누어 정리하려 한다.

먼저

```text
Figma라는 도구를 어떻게 사용하는지
```

를 공부하고,

그다음

```text
화면을 어떻게 구성해야 사용하기 편한지
```

를 공부한다.

---

## 개발자에게 필요한 수준은 어디까지일까

아직 나는 전문 디자이너처럼 Figma를 사용하는 것을 목표로 하고 있지는 않다.

내가 필요한 수준은 조금 다르다.

적어도 내가 만들 서비스를 직접 설계할 수 있고,

다른 디자인을 보면서 구조를 이해할 수 있고,

AI나 다른 사람에게 구현 방향을 설명할 수 있는 정도가 우선 목표다.

정리하면 이런 능력이 필요하다고 생각했다.

```text
화면 구조를 만들 수 있다.

페이지 흐름을 정리할 수 있다.

간격과 정렬을 맞출 수 있다.

반복되는 UI를 관리할 수 있다.

디자인을 개발 코드로 연결해서 생각할 수 있다.

다른 사람이나 AI에게 디자인 의도를 설명할 수 있다.
```

이 정도만 가능해져도 프로젝트를 만드는 과정이 상당히 달라진다.

---

## 내가 Figma를 배우려는 이유

처음에는 단순히

> 프로젝트 화면을 조금 더 예쁘게 만들고 싶다.

는 이유로 시작했다.

하지만 사용하면서 목적이 조금 달라졌다.

지금은 Figma를

**예쁜 화면을 만드는 프로그램이라기보다 개발 전에 생각을 정리하는 도구**라고 보고 있다.

코드를 작성하기 전에 화면을 설계하고,

사용자의 이동 흐름을 확인하고,

AI에게 구현할 기준을 제공하고,

프로젝트 전체 디자인을 일정하게 유지하는 역할이다.

그래서 개발자에게 Figma는 반드시 전문적으로 다뤄야 하는 도구라고 생각하지는 않는다.

하지만 직접 서비스를 만들고 싶다면 한 번쯤 배워볼 가치가 충분히 있다.
