MY-BLOG는 처음부터 오래 운영할 개인 개발 블로그를 만들겠다는 계획에서 시작한 것은 아니었다.

부트캠프를 진행하면서 주어진 **개인 과제로 만든 블로그**였다.

당시에는 페이지를 만들고, 포스트를 올리고, GitHub Pages로 배포해서 실제 주소로 접속할 수 있으면 일단 목적을 달성한 셈이었다.

그래서 처음에는

> 앞으로 이 블로그를 어떻게 운영할까?

보다

> 과제를 완성하려면 무엇이 필요한가?

를 더 많이 생각했다.

그런데 과제가 끝난 뒤에도 공부는 계속됐다.

Git, 프론트엔드, DB, 배포, AI 도구를 공부했고 탄천런, CupPick, NoSpo 같은 프로젝트를 진행하면서 다시 찾아보고 싶은 내용도 빠르게 늘어났다.

그때부터 과제로 만든 블로그를 버리고 새로 시작하기보다 **이미 만들어둔 공간을 내 공부 기록으로 바꿔보기 시작했다.**

이번 2차 수정은 그 변화가 가장 크게 드러난 작업이었다.

---

## 과제를 완성하는 블로그에서 계속 사용하는 블로그로

과제에서는 요구사항을 만족하는 것이 중요했다.

페이지가 있고,

포스트가 보이고,

정상적으로 배포되면 제출할 수 있다.

하지만 계속 사용할 블로그가 되니 기준이 달라졌다.

새로운 공부를 할 때마다 글이 추가되고, 예전에 공부했던 내용을 다시 찾아보게 됐다.

그러다 보니 처음에는 신경 쓰지 않았던 불편이 보이기 시작했다.

긴 글에서는 원하는 부분으로 다시 이동하기 어려웠고, 카테고리가 늘어나자 사이드바가 길어졌다. 포스트가 많아지면서 예전에 특정 내용을 어느 글에 적었는지 기억하기도 어려워졌다.

그래서 긴 글에는 TOC를 추가했고, 카테고리는 없애는 대신 접었다 펼칠 수 있게 했다. 포스트가 더 쌓이면서 검색 기능도 필요하다고 느꼈다.

처음에는 **과제가 요구하는 화면**을 만들었다면, 이제는 **내가 실제로 계속 사용할 화면**을 보고 있었다.

---

## 직접 사용해 보니 '사용자 관점'이 조금 더 구체적으로 보였다

프로젝트를 하면서 `사용자 관점`이라는 말을 자주 들었다.

예전에는 단순히 사용하기 편하게 만들면 된다는 정도로 생각했다.

그런데 내 블로그를 직접 만들고 계속 사용하면서 조금 더 구체적인 질문으로 바뀌었다.

```text
긴 글에서 원하는 내용을 쉽게 찾을 수 있는가?

카테고리가 너무 많은 공간을 차지하지 않는가?

예전에 작성한 글을 다시 찾기 쉬운가?

없는 주소에 들어갔을 때 다시 돌아갈 수 있는가?

브라우저 탭에서는 사이트가 어떻게 보이는가?

링크를 공유하면 어떤 정보가 먼저 보이는가?
```

하나씩 보면 아주 작은 부분이다.

하지만 실제로 사이트를 사용하면 이런 작은 상황을 계속 만나게 된다.

이때부터 기능이 동작하는 것과 사용하기 편한 것은 조금 다른 문제라는 생각이 들었다.

---

## favicon, OG처럼 화면 밖의 요소도 보이기 시작했다

MY-BLOG를 처음 만들 때는 본문과 메뉴처럼 화면 안에서 바로 보이는 요소가 먼저였다.

2차 수정에서는 그동안 잘 보이지 않았던 부분까지 눈에 들어오기 시작했다.

그중 하나가 favicon이었다.

브라우저 탭에 표시되는 작은 아이콘이라 없어도 글을 읽는 데 문제는 없다.

하지만 여러 탭을 열어두면 아이콘과 제목으로 사이트를 구분하게 된다.

favicon을 직접 바꿔보면서 작은 크기에서도 형태가 보여야 한다는 점, 변경했는데도 브라우저 캐시 때문에 이전 이미지가 남을 수 있다는 점도 알게 됐다.

OG와 링크 미리보기를 보면서는 한 단계 더 바깥을 생각하게 됐다.

사용자가 블로그를 처음 만나는 순간이 반드시 홈페이지일 필요는 없었다.

누군가 공유한 링크의

제목,

설명,

대표 이미지가 먼저 보일 수도 있다.

이 경험 이후 프로젝트를 볼 때도 기본 프레임워크 아이콘이 그대로 남아 있는지, 브라우저 탭의 제목은 제대로 되어 있는지, 링크를 공유했을 때 서비스가 무엇인지 알 수 있는지가 눈에 들어오기 시작했다.

예전에는 배포 주소가 열리고 주요 기능이 동작하면 먼저 `완성됐다`고 생각했던 부분들이다.

---

## 정상적인 화면만 보는 것도 부족했다

404와 깨진 링크를 정리하면서는 또 다른 것을 느꼈다.

사이트를 만들 때는 대부분 정상적인 사용 흐름부터 확인한다.

홈이 열리고,

포스트가 열리고,

버튼이 동작하는지를 본다.

하지만 실제 사용에서는 항상 정상적인 상황만 생기지는 않는다.

없는 주소로 들어갈 수도 있고, 링크가 잘못될 수도 있다. 검색 결과가 하나도 없을 수도 있다.

기존에는 없는 주소로 들어가면 GitHub Pages의 기본 404 화면이 나오고 블로그로 다시 돌아갈 방법도 없었다.

그래서 404 페이지도 블로그 디자인에 맞추고 홈으로 돌아가는 길을 만들었다.

이런 경험을 하면서 **실패했을 때 어떻게 보이는지도 사용자 경험의 일부**라는 것을 알게 됐다.

---

## 블로그에서 배운 디테일이 프로젝트에서도 보이기 시작했다

블로그를 고치면서 얻은 가장 큰 변화는 블로그 자체보다 다른 프로젝트를 보는 기준이었다.

예전에는 프로젝트에서 먼저 이런 부분을 봤다.

```text
로그인이 되는가?

데이터가 저장되는가?

버튼이 동작하는가?

배포에 성공했는가?
```

당연히 지금도 가장 중요한 부분이다.

하지만 이제는 그다음도 조금씩 생각하게 됐다.

```text
처음 들어온 사용자가 무엇을 해야 하는지 알 수 있는가?

데이터가 없을 때는 무엇이 보이는가?

잘못된 주소에 들어가면 어떻게 되는가?

모바일에서도 사용할 수 있는가?

favicon과 브라우저 제목은 서비스에 맞는가?

링크를 공유하면 무엇이 보이는가?
```

탄천런, CupPick, NoSpo 같은 프로젝트에서도 주요 기능만 구현하는 것과 실제 서비스를 하나의 완성된 경험으로 만드는 것은 다를 수 있다는 생각이 들었다.

블로그에서 직접 놓친 부분을 하나씩 발견한 경험이 다른 프로젝트에서도 작은 디테일을 보는 연습이 된 셈이다.

---

## 그런데 한 번은 기준이 너무 방문자 쪽으로 흔들렸다

문제도 있었다.

MY-BLOG의 가장 중요한 목적은 여전히 **내 공부를 기록하는 것**이다.

그런데 블로그 자체를 계속 수정하다 보니 어느 순간 방문자에게 있으면 좋을 기능을 너무 많이 고민하고 있었다.

방문자 코멘트를 넣으면서 사용자 구분까지 생각했고, 블로그 안에서 글을 쓰고 고친 내용을 직접 저장까지 처리하는 본격적인 관리자 기능도 고민했다.

하지만 관리자 기능을 제대로 만들려면 단순히 버튼 하나를 추가하는 것으로 끝나지 않았다.

누가 수정할 수 있는지 확인하기 위한 인증과 권한이 필요하고, 브라우저에서 수정한 내용을 어디에 저장할지도 정해야 했다. DB와 기존 포스트 파일의 관계까지 생각해야 했다.

현재는 파일과 Git, Claude만으로도 충분히 관리하고 있었고, 여기에 인증과 DB까지 붙이는 것은 지금 블로그에 비해 복잡도가 지나치게 커지는 일이었다.

그래서 서버 인증과 DB를 갖춘 별도의 관리자 시스템은 만들지 않았다.

그렇다고 관리 기능 자체를 완전히 포기한 것은 아니다.

Markdown 포스트 파일을 원본으로 두는 지금 구조는 그대로 유지하면서 `/write/`와 `/edit/`을 만들었다.

새 글은 `/write/`에서, 기존 글은 각 포스트의 `수정` 버튼으로 들어가는 `/edit/`에서 블로그 화면을 보며 편하게 준비한다. 다만 실제 원본 반영은 저장 코드를 확인한 뒤 GitHub의 편집·저장 화면에서 이어가도록 했다.

즉 본격적인 관리자 시스템은 만들지 않았지만, 지금 구조에 맞는 가벼운 작성·편집 보조 기능은 만든 셈이다.

이 경험을 통해 **사용자 관점을 생각하는 것과 기능을 많이 만드는 것은 같은 의미가 아니라는 것**을 알게 됐다.

필요에 비해 복잡도가 너무 큰 기능은 만들지 않고 지금 구조에 맞는 방식을 고르는 것도 하나의 판단이었다. 뒤에서 다시 정리한 "필요 이상의 기능과 복잡도는 만들지 않는다"는 기준도 이 선택에서 나왔다.

---

## 결국 가장 먼저 생각해야 할 사용자는 나였다

검색, TOC, 카테고리 접기처럼 지금 남기고 싶은 기능에는 공통점이 있다.

나도 실제로 사용하면서 필요성을 느꼈다는 것이다.

검색은 다른 방문자가 글을 찾기 편하라고 먼저 만든 것이 아니라 내가 예전에 공부했던 내용을 다시 찾기 어려워져 필요했다.

TOC 역시 내가 긴 글을 다시 읽으면서 불편했다.

카테고리 접기 또한 실제로 사이드바를 사용하면서 생긴 문제였다.

그래서 앞으로 기능을 고민할 때는

> 방문자에게 있어 보이는 기능인가?

보다

> **내가 공부 기록으로 사용하는 데 실제로 도움이 되는가?**

를 먼저 확인하려고 한다.

방문자에게도 편하면 좋지만 그 때문에 블로그의 원래 목적이 밀리지는 않았으면 한다.

---

## 글을 쓰는 방식에서도 비슷한 문제가 생겼다

이번 수정 과정에서는 블로그 기능뿐 아니라 포스트 작성 기준도 한 번 흔들렸다.

favicon,

OG,

404,

commit과 push,

GitHub Pages 자동 배포,

배포 실패 확인처럼 새롭게 공부하는 내용이 계속 생겼다.

각각 처음 알았을 때는 모두 기록할 가치가 있어 보였다.

그래서 작은 주제까지 각각 긴 포스트로 작성하기 시작했다.

그런데 목록이 늘어난 뒤 다시 보니 문제가 있었다.

```text
commit과 push만 하면 자동으로 배포될까

GitHub Pages 자동 배포의 범위와 한계

배포가 실패했을 때 어디를 확인해야 할까

블로그를 수정하고 배포하는 나만의 작업 흐름
```

각각의 질문은 다르지만 결국 하나의 **GitHub Pages를 운영하면서 배운 과정**으로 묶을 수도 있는 내용이었다.

favicon, OG, title, description, 404와 깨진 링크도 마찬가지였다.

각각 독립된 개념이기는 하지만 모두 웹사이트를 만들면서 놓치기 쉬웠던 디테일이라는 흐름으로 묶을 수 있다.

새로운 것을 하나 배울 때마다 포스트 하나를 만드는 방식으로 계속 가면 글의 개수만 많아지고 비슷한 설명도 반복될 수 있었다.

---

## 기록을 많이 남긴다는 것과 포스트를 잘게 나누는 것은 달랐다

여기에서 블로그의 목적을 다시 생각하게 됐다.

내가 원하는 것은 포스트 개수가 많은 블로그가 아니다.

내가 공부한 내용을 나중에 다시 이해하기 쉬운 형태로 남기는 것이다.

그래서 앞으로는 모든 배움을 같은 크기의 글로 만들지 않으려고 한다.

```text
짧은 개념이나 작은 궁금증
→ 짧은 Learning Note

서로 연결되는 여러 개념
→ 하나의 포스트로 묶기

프로젝트에서 실제로 겪은 문제와 해결 과정
→ 독립 포스트

여러 선택지 사이에서 판단이 바뀐 경험
→ 독립 포스트
```

예를 들어 `commit`과 `push`의 차이만 기록한다면 짧은 노트로 충분하다.

반면 GitHub Pages로 블로그를 운영하면서 commit과 push를 이해하고, 자동 배포 구조를 알게 되고, 실패했을 때 확인하는 순서와 내 작업 흐름까지 만들어졌다면 하나의 긴 경험으로 묶을 수 있다.

앞으로는 **배운 개수보다 경험의 단위로 글을 나누는 것**이 더 맞을 것 같다.

---

## 디테일은 챙기되 디테일마다 포스트를 만들지는 않는다

favicon이나 OG 같은 작은 내용을 알게 된 것은 분명 의미가 있었다.

덕분에 다른 프로젝트에서도 이전에 놓쳤던 요소들이 보이기 시작했다.

하지만 그것을 모두 하나씩 긴 포스트로 만들어야 하는 것은 아니었다.

```text
디테일을 공부한다
≠
디테일마다 포스트 하나를 만든다
```

서로 연결되는 내용은 하나의 경험으로 묶는 편이 읽기에도 좋고, 나중에 내가 다시 찾기에도 좋다.

블로그의 기능을 많이 넣는 것이 항상 좋은 것은 아니었던 것처럼 **포스트의 개수가 많다고 기록이 더 좋은 것도 아니었다.**

## 아직 가장 크게 부족한 것은 실제 화면 기록이다

기능과 글의 구조를 계속 손봤지만 정작 현재 포스트에는 또 하나의 큰 문제가 남아 있다.

**홈 화면을 제외하면 실제 사진이나 캡처가 하나도 없다.**

공부한 내용을 자세하게 남기고 싶어 설명은 계속 길어졌는데, 실제로 어떤 화면을 보고 작업했는지는 제대로 남기지 못했다.

GitHub 설정,

터미널 오류,

배포 상태,

디자인 수정 전후처럼 실제 화면 하나가 여러 문장보다 정확한 경우도 많다.

그동안 탄천런, CupPick, NoSpo와 하루 아이디어톤까지 프로젝트를 진행하면서는 구현 자체가 너무 바빠 과정까지 기록할 여유가 부족했다.

특히 첫 프로젝트에서는 정신없이 따라가느라

> 나중에 블로그에 정리해야지.

라고 생각했던 내용이 많았다.

하지만 나중에 쓰려고 하니 당시의 오류 화면이나 왜 그런 결정을 했는지는 이미 많이 흐려져 있었다.

그래서 앞으로는 완성된 포스트를 프로젝트 중에 쓰려고 하기보다 **나중에 글을 쓸 수 있는 재료부터 남기려고 한다.**

```text
막힌 문제

해결 방법

판단이 바뀐 이유

중요한 화면 캡처

나중에 다시 공부할 키워드
```

정도만 남아 있어도 끝난 뒤 훨씬 정확한 글을 작성할 수 있을 것 같다.

## 환경 구축도 기억으로 쓰기보다 다시 직접 해보고 싶다

환경 구축 관련 글 역시 비슷하다.

처음 Java, Git, VS Code, Node.js 같은 환경을 설정할 때는 블로그 기록까지 생각하지 못했다.

지금 기억만으로 당시 설치 과정을 자세하게 적으면 정확하지 않을 수도 있다.

그래서 제대로 기록하려면 필요할 때 **다시 직접 설치 과정을 확인하면서** 글을 만드는 편이 맞다고 생각한다.

단순히 인터넷에 있는 설치 방법을 옮겨 적는 것이 아니라

어떤 옵션을 선택했는지,

왜 그렇게 선택했는지,

설치 후 무엇을 확인했는지,

어디에서 헷갈렸는지를 실제 과정과 함께 남기는 것이다.

이번에는 결과뿐 아니라 과정도 기록해 보고 싶다.

## 이번 2차 수정에서 다시 잡은 기준

한동안 블로그를 수정하면서 기능 쪽으로도, 포스트 개수 쪽으로도 기준이 조금 흔들렸다.

그래서 다시 정리했다.

앞으로 MY-BLOG에서는 다음을 우선하려고 한다.

```text
내가 실제로 공부한 내용을 남긴다.

결과뿐 아니라 이해 과정과 시행착오를 기록한다.

작은 개념은 짧게, 연결되는 경험은 하나의 글로 묶는다.

실제 화면이 더 정확한 경우에는 캡처를 남긴다.

방문자 기능보다 내가 공부 기록으로 사용하는 데 필요한 기능을 먼저 본다.

필요 이상의 기능과 복잡도는 만들지 않는다.

구현하지 않은 일은 한 것처럼 기록하지 않는다.

나중에 기억해서 쓰기보다 중요한 순간에 기록 재료를 남긴다.
```

## 과제로 시작했지만 이제는 다른 역할을 하고 있다

처음 MY-BLOG를 만든 이유는 부트캠프 과제였다.

그때는 요구사항을 만족하고 배포까지 하면 충분했다.

하지만 지금은 공부한 내용을 남기고, 프로젝트에서 배운 것을 다시 정리하고, 과거의 내가 무엇을 헷갈렸는지 찾아보는 공간이 됐다.

동시에 블로그를 직접 만들고 운영하면서 웹사이트에서 놓치기 쉬운 요소들도 배우고 있다.

favicon,

OG,

404,

검색,

TOC처럼 작은 디테일을 직접 다뤄보면서 다른 프로젝트에서도 사용자 관점으로 화면을 한 번 더 보게 됐다.

반대로 그 과정에서 기능을 너무 많이 고민하거나 작은 배움을 지나치게 여러 포스트로 나누면서 **기록 공간이라는 원래 목적에서 조금 벗어나기도 했다.**

이번 2차 수정에서 가장 크게 바뀐 것은 특정 기능 하나가 아니다.

**무엇을 더 만들 것인지보다 무엇을 남기고, 무엇은 합치고, 무엇은 만들지 않을지를 판단하는 기준이 생기기 시작한 것**에 가깝다.

앞으로 MY-BLOG의 목표는 더 많은 기능이나 더 많은 포스트가 아니다.

필요한 기능은 남기고,

작은 배움은 적절한 크기로 기록하고,

프로젝트 과정에서는 실제 화면과 시행착오를 조금 더 잘 남기고 싶다.

과제로 시작한 블로그가 이제는 내 공부 기록이면서 웹사이트를 직접 운영해 보는 연습 공간이 됐다.

다음 수정에서는 블로그의 크기를 계속 키우는 것보다 **기록의 밀도를 높이는 방향**으로 가져가고 싶다.
