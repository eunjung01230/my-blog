블로그의 전체 구조를 단순하게 정리하고, 사이드바와 모바일 화면까지 살펴보다 보니 한 가지 아쉬운 점이 보이기 시작했다.

글을 읽고 찾는 데는 큰 문제가 없었지만 화면만 봤을 때는 **이 블로그를 누가 운영하는지 알 수 있는 정보가 거의 없었다.**

개발 블로그라고 해서 작성자 소개가 크게 보여야 하는 것은 아니다.

내 블로그에서는 여전히 글이 가장 중요했다.

하지만 개인이 공부하면서 남기는 기록인 만큼 이름 정도는 확인할 수 있고, 실제 코드와 프로젝트가 있는 GitHub로 자연스럽게 이어질 수 있으면 좋겠다고 생각했다.

그래서 본문 중심의 구조는 유지하면서 **작은 프로필과 GitHub 연결을 추가하는 방향**을 생각하기 시작했다.

---

## 깔끔하게 만들수록 개인 블로그라는 느낌이 줄었다

디자인을 개편하면서 가장 중요하게 생각했던 것은 단순함이었다.

본문을 중심에 두고,

불필요한 정보는 줄이고,

사이드바도 글을 탐색하는 데 필요한 역할에 집중하고 싶었다.

이 방향 자체는 마음에 들었다.

그런데 요소를 계속 정리하다 보니 화면이 조금씩 일반적인 문서 사이트처럼 느껴지기도 했다.

글은 있지만 누가 작성한 글인지는 잘 보이지 않았다.

내가 만들고 싶은 것은 기술 문서를 모아놓은 사이트가 아니라 **내가 공부하고 프로젝트를 진행하면서 기록을 쌓는 개인 개발 블로그**였다.

그렇다면 화면을 복잡하게 만들지 않는 범위에서 작성자의 흔적은 남아 있는 편이 자연스러웠다.

---

## 프로필을 크게 만들 필요는 없었다

프로필이라고 하면 넣을 수 있는 정보가 많다.

프로필 사진,

긴 자기소개,

사용 기술,

여러 SNS,

이메일이나 연락처까지 넣을 수 있다.

하지만 처음에는 이런 정보를 모두 넣으면 지금까지 정리한 블로그의 방향과 맞지 않을 것 같았다.

내 블로그에서 가장 중요한 것은 여전히 포스트였다.

그래서 프로필은 별도의 큰 콘텐츠라기보다

> 이 글을 누가 작성했는가?

를 빠르게 확인하는 정보 정도면 충분하다고 생각했다.

처음 보여주고 싶었던 것도 단순했다.

```text
푸름 / eunjung01230

github.com/eunjung01230
```

이름과 GitHub 계정 정도만 있어도 개인 블로그라는 사실은 충분히 드러날 수 있었다.

자세한 자기소개가 필요하다면 About 페이지에서 다루면 된다.

프로필과 About을 굳이 같은 역할로 만들 필요는 없었다.

```text
프로필
→ 작성자를 빠르게 확인하는 정보

About
→ 블로그와 작성자에 대한 자세한 소개
```

이렇게 나누는 편이 더 자연스러웠다.

---

## GitHub는 단순한 외부 링크보다 의미가 있었다

개발 블로그에서 GitHub를 연결하고 싶었던 이유는 다른 SNS를 하나 추가하는 것과는 조금 달랐다.

두 곳에는 서로 다른 종류의 개발 기록이 남기 때문이다.

GitHub에는 실제 프로젝트와 코드 변경 내역이 남는다.

블로그에는 그 코드를 작성하면서 무엇을 배웠는지, 어디에서 막혔는지, 왜 그런 선택을 했는지를 더 자세히 기록할 수 있다.

예를 들어 GitHub를 보면 최종 코드와 커밋은 확인할 수 있다.

하지만

왜 처음 구조를 바꿨는지,

어떤 방법을 시도했다가 포기했는지,

어떤 개념을 잘못 이해하고 있었는지

같은 과정은 코드만으로 전부 알기 어렵다.

반대로 블로그에는 그 과정을 설명할 수 있지만 실제 프로젝트 전체를 보여주지는 않는다.

그래서 둘의 역할을 이렇게 생각하게 됐다.

```text
GitHub
→ 내가 실제로 만든 것

블로그
→ 그것을 만들면서 배운 것
```

이 두 기록이 연결되면 프로젝트의 결과와 과정이 조금 더 자연스럽게 이어질 수 있었다.

---

## 프로젝트 글과 GitHub도 자연스럽게 연결될 수 있었다

앞으로 블로그에는 프로젝트 관련 기록도 계속 쌓일 수 있었다.

기능을 구현하면서 새롭게 이해한 내용,

구조를 결정한 이유,

오류를 해결했던 과정처럼 실제 프로젝트에서 나온 공부 기록들이다.

이런 글을 읽고 실제 결과가 궁금하다면 GitHub에서 프로젝트를 확인할 수 있다.

반대로 GitHub에서 프로젝트를 먼저 본다면 블로그를 통해 그 프로젝트를 진행하면서 어떤 고민을 했는지 볼 수 있다.

그래서 GitHub 링크는 단순히

> 제 GitHub입니다.

라고 보여주는 장식이 아니라 **블로그 밖에 있는 실제 개발 결과로 이어지는 연결점**에 가까웠다.

---

## 위치보다 중요한 것은 역할이었다

프로필을 어디에 둘지도 고민했다.

가장 먼저 떠오른 곳은 사이드바였다.

개인 블로그에서 프로필과 카테고리를 사이드바에 함께 두는 구조는 흔했고 자연스럽기도 했다.

하지만 내 블로그에서는 이미 사이드바를 카테고리와 글 탐색 중심으로 정리하고 있었다.

프로필까지 크게 넣으면 다시 정보가 많아질 수 있었다.

그래서 특정 위치부터 정하기보다 먼저 역할을 생각했다.

프로필은 항상 크게 보여야 하는 정보가 아니다.

한 번 작성자를 확인하고 나면 글을 읽는 동안 계속 볼 필요도 없다.

GitHub 역시 필요할 때 쉽게 이동할 수 있으면 충분했다.

따라서 어느 위치를 선택하더라도 기준은 같았다.

**본문보다 먼저 눈에 띄지 않으면서 필요할 때 쉽게 찾을 수 있을 것.**

이 기준이 위치 자체보다 더 중요했다.

---

## 익숙한 GitHub 아이콘을 활용할 수도 있었다

GitHub는 이미 익숙한 아이콘이 있기 때문에 긴 설명 없이도 링크의 목적을 전달하기 쉬웠다.

텍스트로 주소 전체를 보여줄 수도 있지만 화면을 단순하게 유지하려면 아이콘이나 짧은 계정 정보와 연결하는 방법도 생각할 수 있었다.

다만 아이콘은 어디까지나 기능을 설명하기 위한 보조 요소였다.

장식을 하나 더 추가하기 위해 사용하는 것은 아니었다.

실제로 눌렀을 때 내 GitHub로 이동하고, 주변 디자인과 자연스럽게 어울리는 것이 더 중요했다.

---

## 보여줄 개인정보의 범위도 정해야 했다

프로필을 만들다 보면 자연스럽게 더 많은 정보를 추가하고 싶어질 수 있다.

학교,

이메일,

관심 분야,

사용 기술,

다른 SNS 등 개인을 설명할 수 있는 정보는 많다.

하지만 개인 블로그에 프로필이 있다고 해서 가능한 정보를 모두 공개할 필요는 없었다.

그래서 초기에는 블로그 작성자를 알 수 있는 최소한의 정보와 개발 활동으로 연결되는 GitHub 정도만 넣는 방향으로 생각했다.

나중에 필요성이 생기면 추가하면 된다.

처음부터 완성된 자기소개 페이지처럼 만들 필요는 없었다.

이렇게 범위를 작게 잡는 편이 개인정보 측면에서도 부담이 적었고, 블로그의 단순한 디자인과도 잘 맞았다.

---

## 작은 기능이라도 실제 연결은 확인해야 했다

GitHub 링크 하나를 추가하는 것은 복잡한 기능은 아니다.

그래도 실제 블로그에 넣었다면 기본적인 확인은 필요했다.

링크를 눌렀을 때 정확한 GitHub 페이지로 이동하는지,

아이콘이나 텍스트가 예상한 범위에서 클릭되는지,

다른 화면의 레이아웃을 밀어내지는 않는지,

모바일에서도 너무 작지 않은지

같은 부분이다.

특히 여러 페이지에서 공통으로 보이는 요소라면 한 화면에서 정상적으로 보인다고 끝낼 수 없었다.

작은 변경일수록 적용하고 바로 넘어가기 쉽지만, 실제로 사용하는 기능이라면 한 번은 직접 눌러보고 확인하는 편이 좋았다.

---

## GitHub를 연결해도 블로그의 목적은 달라지지 않았다

GitHub와 프로필을 추가하면 블로그가 조금 더 포트폴리오처럼 보일 수도 있다.

누군가 내 글을 보고 실제 프로젝트까지 확인할 수 있기 때문이다.

그 점은 분명 장점이었다.

하지만 이것 때문에 블로그의 목적을 바꾸고 싶지는 않았다.

블로그를 다시 시작했던 가장 큰 이유는 내가 공부한 내용을 다시 찾고, 프로젝트를 진행하면서 배운 과정을 남기기 위해서였다.

GitHub 연결 역시 그 목적 안에서 생각했다.

누군가에게 보여주기 위해 새롭게 꾸민 정보라기보다 **이미 하고 있는 개발 활동과 공부 기록을 서로 이어주는 것**이었다.

이 차이는 나에게 중요했다.

블로그를 포트폴리오처럼 보이게 만들기 위해 GitHub를 붙인 것이 아니라,

블로그에 적은 과정과 GitHub에 남은 결과가 서로 연결되도록 만든 것이었다.

---

## 프로필 하나가 블로그의 성격을 조금 바꿨다

프로필과 GitHub는 없어도 블로그가 작동하는 데 문제가 없는 요소다.

글을 읽는 기능과도 직접적인 관련은 없다.

그런데 이런 작은 정보가 추가되면 블로그를 바라보는 느낌은 달라질 수 있었다.

이전에는 여러 개발 글이 모여 있는 공간에 가까웠다면,

이제는 한 사람이 공부하고 프로젝트를 진행하면서 계속 기록을 쌓아가는 공간이라는 점이 조금 더 분명해졌다.

내가 원했던 것도 거창한 자기소개가 아니었다.

**누가 기록하고 있는지 알 수 있고, 그 사람이 실제로 만든 결과까지 이어질 수 있는 것.**

그 정도면 충분했다.

결국 프로필과 GitHub를 연결하면서 얻은 결론은 단순했다.

> **개인 개발 블로그에서 프로필은 나를 크게 보여주기 위한 영역이 아니라, 기록의 작성자를 알려주는 작은 표식이고, GitHub는 그 기록을 실제 개발 결과와 연결하는 통로였다.**

본문을 중심에 둔다는 기존 방향을 바꾸지 않으면서도 이 두 요소 덕분에 블로그에는 조금 더 분명한 주인이 생겼다.

---

## 다음에는 블로그 자체를 구분해 주는 표식이 필요했다

작성자를 보여주는 정보가 생기고 나니 다음으로 눈에 들어온 것은 블로그 자체의 모습이었다.

브라우저 탭에서 보이는 작은 아이콘이나 블로그에서 사용하는 로고처럼 아주 작은 요소들이다.

없다고 기능에 문제가 생기는 것은 아니지만, 이런 요소가 있으면 여러 사이트 사이에서 내 블로그를 조금 더 쉽게 구분할 수 있다.

프로필이 **누가 기록하는지**를 보여줬다면, 이제는 **어떤 블로그인지**를 보여주는 작은 표식도 만들어보고 싶었다.

그래서 다음에는 favicon과 로고를 중심으로 블로그의 첫 번째 브랜딩 요소를 고민하기 시작했다.
